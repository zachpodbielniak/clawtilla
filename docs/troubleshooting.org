* Troubleshooting

** A client cannot reach the daemon

#+begin_example
clawtilla: could not reach the daemon at … (is clawtillad running?)
#+end_example

1. Is it running?  ~systemctl --user status clawtilla~, or ~pgrep -x clawtillad~.
2. Is it on the socket you are asking for?  The daemon logs the path on
   startup; ~clawtilla -s <path>~ overrides.
3. Did it fail to start?  ~journalctl --user -u clawtilla -n 50~, or run
   it in the foreground and watch.

*** "another clawtilla daemon is already listening"

Exactly what it says: something is on that socket.  Find it with
~pgrep -x clawtillad~.  clawtilla checks before removing a stale socket
on purpose -- unlinking a live one would leave two daemons quietly
fighting over one fleet.

That check is a connect probe, and a probe answers exactly one question:
did anything reply just now.  It is the second guard rather than the
first.  The thing two daemons must never share is the *state directory*,
and that is what carries a lock.

*** "another clawtilla daemon is using the state directory …"

#+begin_example
another clawtilla daemon is using the state directory
/home/you/.clawtilla (held by pid 40118). Two daemons sharing one state
directory overwrite each other's transcripts, so this one will not
start; use a different daemon.state_dir, or stop the other one
(Resource temporarily unavailable)
#+end_example

The daemon takes an exclusive ~flock~ on ~<state_dir>/daemon.lock~
before anything reads or writes in there, and holds it until it stops.
A second daemon against the same directory is refused whatever socket it
was given, which is the case the socket probe above cannot see.

Either stop the daemon holding it, or give this one a directory of its
own.  That means ~daemon.state_dir~, ~daemon.socket~ and
~defaults.workspace_root~ together -- two fleets sharing any one of the
three is the same problem a layer down.  The workspace root is the one
people forget: its default is the absolute path ~~/.clawtilla/agents~,
so moving ~daemon.state_dir~ does not move it, and the second fleet
scaffolds its agents over the first one's.

The pid comes from the lock file's contents and is a courtesy for
whoever reads the message.  The lock is what excludes; a lock file that
says nothing still refuses, and still means the same thing.

There is no such thing as a stale ~daemon.lock~.  The kernel drops the
lock when the last descriptor on it closes, which covers a daemon killed
with ~SIGKILL~ and a machine that lost power -- so the file existing
means nothing on its own, and deleting it by hand accomplishes nothing
except throwing away the pid that would have named the holder.

*** "the socket path is N bytes; the kernel accepts at most 107"

Unix socket paths are limited.  Put ~daemon.socket~ and
~daemon.state_dir~ somewhere shorter -- under ~$XDG_RUNTIME_DIR~ for the
socket.

This is checked up front because an over-long path does not fail at bind
time: the socket is simply not created where you asked, and the first
sign is an unrelated ENOENT further down.

** The daemon is running and nothing can reach it

~pgrep~ finds it, the journal shows it working, and every client says
the daemon is not running.  The socket it listens on has been unlinked
from the filesystem underneath it.

A listening unix socket survives its path being removed: connections
already made carry on, and the daemon goes on doing everything else --
agents stay linked, routines fire, transcripts are written, and nothing
in its own log says anything is wrong.  What is gone is the name a new
client dials.

~ss~ and ~ls~ disagreeing is the whole diagnosis:

#+begin_src bash
ss -xlp | grep clawtillad
ls -l "${XDG_RUNTIME_DIR}/clawtilla/daemon.sock"
#+end_src

#+begin_example
u_str LISTEN 0 10 /run/user/1000/clawtilla/daemon.sock 27320173 * 0
        users:(("clawtillad",pid=40118,fd=12))
ls: cannot access '/run/user/1000/clawtilla/daemon.sock':
        No such file or directory
#+end_example

(One line each; wrapped here to fit.)

~ss~ reports the name the socket was bound under, which the kernel
remembers whether or not the file is still there; ~ls~ reports what is
on disk now.  A daemon that had failed to start would appear in neither,
which is what makes the pair conclusive.

Restarting the daemon fixes it, and is safe: the bind recreates the
path.

What unlinked it was another ~clawtillad~ starting up.
~clear_stale_socket()~ connects to the path first and only removes it
when nothing answers -- and a live daemon can fail to answer, because a
connect is refused when the accept queue is full or when the daemon is
not accepting at that instant.  A daemon blocked on its main thread is
exactly that -- see [[*The daemon answers nothing and will not stop]].

The common route to it -- two daemons on one state directory -- is
closed by the state lock, which is taken before the socket is touched.
Two daemons with *different* state directories and the same
~daemon.socket~ still can, so check both:

#+begin_src bash
pgrep -a clawtillad
#+end_src

More than one line is the answer, and the next section is the damage.

** Messages are missing from the transcript

Messages that were sent, delivered and answered are not in the chat when
you scroll back.  Not out of order and not garbled: gone, with the
conversation around them intact.

That is what two daemons on one state directory do.  Each keeps its own
~ClawtRoomManager~, and a transcript is rewritten *whole* from memory on
every message -- so the last daemon to flush wins, and the messages the
other one had are overwritten by a file that never contained them.

The event log is what saves you.  It is append-only, one file per UTC
day, and every daemon writing in that directory appends to the same
file, so it has everything that happened whichever daemon handled it.
The transcript is a projection of the same events; the log is the
record.

First, confirm the overlap.  Two ~daemon.started~ with no
~daemon.stopped~ between them is two daemons at once:

#+begin_src bash
jq -r 'select(.kind | startswith("daemon."))
       | (.ts/1000000|floor|strflocaltime("%F %T")) + "  " + .kind' \
   ~/.clawtilla/events/*.ndjson
#+end_src

A daemon refused by the state lock leaves nothing here -- it is refused
before the log is opened -- so these are all daemons that ran.

Then find what the log has and the transcript does not.  A direct room
is ~dm:<a>:<b>~ with the two ids sorted, and the transcript file is that
id with ~.ndjson~ on the end:

#+begin_src bash
ROOM=dm:chief:you
jq -r --arg room "$ROOM" \
   'select(.kind == "message" and .subject == $room) | .detail.id' \
   ~/.clawtilla/events/*.ndjson | sort -u > /tmp/logged
jq -r .id ~/.clawtilla/transcripts/"$ROOM".ndjson | sort -u > /tmp/kept
comm -23 /tmp/logged /tmp/kept
#+end_src

*** Putting them back

Manual, and it is worth saying plainly: there is no ~clawtilla~ verb for
this.  The daemon has no idea it lost anything -- from its side the
transcript it wrote is the transcript it meant to write.

Stop the daemon first.  A running one rewrites the file on the next
message and will happily overwrite whatever you just repaired.

#+begin_src bash
systemctl --user stop clawtilla
ROOM=dm:chief:you
T=~/.clawtilla/transcripts/"$ROOM".ndjson
cp "$T" "$T.before-recovery"

jq -n -c --arg room "$ROOM" --slurpfile kept "$T" '
  [ inputs
    | select(.kind == "message" and .subject == $room)
    | {id: .detail.id, sender: .detail.from, body: .detail.body,
       ts: (.ts / 1000000 | floor), depth: 0}
      + (if .detail.task then {task_id: .detail.task} else {} end)
  ] as $log
  | ($kept | map(.id)) as $have
  | ($kept + [ $log[] | select(.id as $i | $have | index($i) | not) ])
  | sort_by(.ts)[]
' ~/.clawtilla/events/*.ndjson > "$T.rebuilt"

mv "$T.rebuilt" "$T"
systemctl --user start clawtilla
#+end_src

What that does, and why each part is there:

- lines already in the transcript are kept *as they are*, and only ids
  the transcript does not have are added.  A transcript line can carry
  ~sender_name~, ~depth~ and ~parent_id~ that the event never had, so
  rebuilding every line from the log would be a lossy repair of the
  messages that were never lost
- ~ts~ is divided by a million.  An event's timestamp is in
  microseconds and a transcript's is in seconds, and a message left in
  the wrong unit is not merely late: ~g_date_time_new_from_unix_local()~
  cannot represent a number that size at all and answers NULL, so the
  message sorts after everything ever said and is drawn with no time on
  it and no day divider above it
- ~depth~ is 0 because the event does not carry one.  It is the
  agent-to-agent hop count, used by the loop guard on live traffic; a
  recovered line is history and nothing reads it back
- the result is sorted by ~ts~, because the room is loaded in file order
  and appending to the end would put the recovered messages after the
  ones that came later

~jq~ rather than ~yq~, which is the one place in these docs where that
is the right way round: yq has no ~floor~, and its division renders
1756240000 as ~1.75624e+09~, which is not a timestamp any more.

If the transcript file is not there at all, ~touch~ it first --
~--slurpfile~ wants a file to read, and an empty one means every message
in the log is missing, which is the correct answer for a room whose
transcript was deleted rather than overwritten.

Then read it back before trusting it:

#+begin_src bash
clawtilla room history "$ROOM"
#+end_src

The daemon reloads transcripts at start and rebuilds a direct room's
membership from the *id*, not from the file, so a repaired file needs no
other change.  A line it cannot parse is skipped rather than fatal,
which means a mistake in the JSON shows up as a message still missing
rather than as an error -- count them.

Two things this cannot recover.  Anything older than
~daemon.event_log_days~ has been swept from the log, and a room whose
messages predate the log is not in it at all.  And the log holds message
bodies, so ~events/~ deserves the same care as ~transcripts/~ --
[[file:security.org][security.org]] says so in more detail.

** An agent will not start

#+begin_src bash
clawtilla agent show researcher
#+end_src

The ~state~ and the ~detail~ beside it are the answer most of the time.

*** state: shadow

Its configuration could not be understood, and the detail says what.
Common causes: an unknown ~computer.type~, an unknown mount type, a
missing required field, a duplicate id, a second chief of staff.

The rest of the fleet is running normally; fix the block and reload.

*** "Failed to execute child process (Argument list too long)"

The agent's identity files have outgrown what a single command-line
argument may hold, and the error names none of that: not the files, not
the size, not the limit.  =getconf ARG_MAX= reports 2097152 on an
ordinary machine, so the message reads as impossible --- but =ARG_MAX= is
the *total*.  The cap that bites is =MAX_ARG_STRLEN=, 32 pages, and
headroom in the total does not buy it back, because the kernel refuses
the whole call over one long word.

Ask before it happens:

#+begin_src bash
clawtilla agent show researcher | grep identity
#+end_src

#+begin_example
identity:    138104 bytes of the 131072 a command-line argument holds
#+end_example

Past 80% the same command prints the largest files and what to do; both
graphical clients show it in the agent's summary; and an
~agent.identity~ event reaches the alerts panel at every start.

Two things make this hard to catch without asking.  A *resumed* session
is never handed a system prompt, so the agent keeps working and only a
*fresh* session fails --- the symptom appears long after the file that
caused it was written.  And it is silent right up to the cliff: an agent
at 130,000 bytes behaves perfectly and the next paragraph anybody adds
kills it.  It is also self-inflicted by design: the scaffolded
=AGENTS.org= tells the agent to keep =PROJECTS.org= current, and
=PROJECTS.org= is an identity file.

The fix is to move closed or historical sections into a sibling =.org=
that ~persona.identity_files~ does not name.  Nothing is lost --- the
agent can still read it on demand --- and the spawn cost disappears.
[[file:agents.org][agents.org]] has the per-backend table; the short
version is that the default backend spills the prompt to a file and has
no practical ceiling, and =grok-build= has no such flag and does.

*** "there is no libpod-module-container.so in any of: …"

A container, distrobox or vm agent needs podomation's loadable modules,
which libreclaw builds.  The message lists every directory that was
searched.  The module named in the message is the one that backend
wants: =container=, =distrobox= or =vm_virtmanager=.

#+begin_src bash
make -C deps/libreclaw pod-modules
#+end_src

A normal ~make~ links ~build/<type>/pod-modules~ to libreclaw's module
output, so a build tree works uninstalled.  If the modules live
somewhere else -- a system podomation, or another checkout -- name it:

#+begin_src yaml
daemon:
  pod_module_dir: "~/src/podomation/build/release/modules"
#+end_src

That replaces the whole search path with the one directory, so a typo
fails loudly rather than silently loading an older set from elsewhere.

*** "container create failed: Could not connect: …"

The module loaded and podman refused.  Almost always the rootless socket
is not running:

#+begin_src bash
systemctl --user enable --now podman.socket
#+end_src

clawtilla talks to the rootless socket under =XDG_RUNTIME_DIR= unless
=agents.computer.container.connection= says otherwise.  Confirm which one podman
itself thinks it has:

#+begin_src bash
podman info --format '{{.Host.RemoteSocket.Path}}'
#+end_src

A failure here that says "no reason given" means an old podomation -- it
used to fill in an error and then discard it before returning.

*** "no such image: … image not known"

The image is not pulled.  ~create~ does not pull; that is deliberate, so
a typo in an image name fails in a second rather than after a download.

#+begin_src bash
podman pull registry.fedoraproject.org/fedora:latest
#+end_src

*** Its container was removed, and the agent still says running

#+begin_example
$ podman rm -f clawt-researcher
$ clawtilla computer status researcher
state: running
$ clawtilla computer exec researcher -- uname -a
container start failed: HTTP 404: no container with name or ID found
#+end_example

Start the agent.  ~clawtilla agent start researcher~ asks podman what is
really there, finds nothing, and provisions again.

Two things about the output above are worth knowing rather than
investigating.  ~computer status~ reports what the daemon remembers, not
what podman has --- it is a memory read on purpose, since making it a
round trip would put a blocking call on the daemon's main context --- so
it goes on saying =running= until a start corrects it.  And the 404 names
a container id rather than =clawt-researcher=, because the remembered id
is preferred over the name; it is the id of the container that was
removed, which is why it correlates with nothing.

On builds before this behaviour existed, ~agent start~ and ~agent
restart~ both reported success and changed nothing --- relaunching the
libreclaw child genuinely does succeed, since it runs on the host and
does not need the container.  Restarting the whole daemon was the only
way back.

*** The agent is in state error and will not start again

Read the detail -- ~clawtilla agent show <agent>~ -- fix the cause, and
start it again.  Unlike =shadow=, =error= is retryable: a runtime that
was down, an image that was missing, a name that was taken.

=shadow= is the other one: the configuration could not be understood, and
no amount of retrying will change that.

*** "integrations.matrix is enabled but … is not set"

An enabled integration is missing a required key.  It is refused rather
than warned about, because an agent whose Matrix block is incomplete
starts perfectly cleanly and then never receives anything.

*** "could not resolve <reference>"

A secret reference did not resolve.  The message names it by reference,
never by value.

- ~{env: NAME}~ -- the variable is not in the *daemon's* environment
- ~{file: PATH}~ -- check the path and its permissions
- ~{command: …}~ -- run it by hand; if it prompts, it will hit the
  ~secrets.command_timeout_seconds~ bound

*** It starts and immediately stops

#+begin_src bash
clawtilla agent logs researcher
#+end_src

That is the child's own output.  A config error in the rendered file
shows up there, not in the daemon's log.

#+begin_src bash
clawtilla config render researcher
#+end_src

*** It exits 0 immediately and says nothing at all

No error in the child's log, no error in the daemon's, and
~agent show~ reporting *stopped -- exited with status 0*.  Look for a
libreclaw that is still running from a previous daemon:

#+begin_src bash
ps -o pid=,ppid=,cmd= -C libreclaw
#+end_src

A ~PPID~ of ~1~ is the whole answer.  A daemon stopped cleanly stops its
agents; one that is *killed* runs no handler, and its children were then
reparented to init still holding that agent's ports, its session
directory and its sqlite database.  The next daemon knows nothing of
them, starts a second copy alongside, and the second copy exits at once
-- which is the multi-instance collision libreclaw explicitly cannot
survive.  Three accumulated in one afternoon of restarts.

#+begin_src bash
kill <pid>                     # the orphan, then start the agent again
#+end_src

Use ~ps -C~ and read ~PPID~ rather than ~pgrep -af libreclaw~: that
matches your own command line, and then a different daemon's child, and
the second one looks exactly like a pass.  ~readlink /proc/<pid>/exe~
says which binary an orphan is actually running, which is usually the one
from before the last upgrade.

Current builds ask the kernel to signal the child when the daemon
disappears, so this cannot happen to anything started by a daemon newer
than 0.1.0 -- including one that is ~SIGKILL~ed.  What you may find are
orphans from before that.

** "cannot find the libreclaw binary"

#+begin_example
cannot find the libreclaw binary. It was not beside clawtillad, not in
deps/libreclaw's build, and not on PATH. Build it with `make -C
deps/libreclaw`, install it, or set defaults.libreclaw_binary to where it
is.
#+end_example

The daemon runs a ~libreclaw~ per process-runtime agent and looks in
three places: beside ~clawtillad~, then ~deps/libreclaw/build/release~
relative to it, then ~PATH~.

Hitting this means none of the three had one -- usually a ~clawtillad~
copied out of its build tree, or a checkout where ~deps/libreclaw~ was
never built:

#+begin_src bash
git submodule update --init --recursive
make -C deps/libreclaw
#+end_src

~defaults.libreclaw_binary~ overrides all three.  Setting it once and
forgetting is how this failure becomes invisible on one machine and
immediate on another -- so if the key is set, check that what it names is
still there before anything else:

#+begin_src bash
clawtilla config show | grep libreclaw_binary
#+end_src

An *older* message said "the libreclaw binary is not on PATH", which sent
people to install something they had already built, minutes earlier, with
the same ~make~ that produced the daemon doing the complaining.

** The link will not connect

The agent is ~running~ but ~LINK~ stays down.

1. Check the rendered config has the channel:
   ~clawtilla config render researcher | grep -A5 clawtilla:~
2. Check the socket in it exists and is 0600.
3. Check the token file exists at
   ~<state_dir>/agents/<id>/token~.
4. Look at ~clawtilla agent logs~ -- the channel logs each attempt.

An agent inside a container needs ~agents.sock~ mounted into it.

The daemon logs a refusal it made:

#+begin_example
link server: refused a connection claiming to be 'researcher'
#+end_example

That means the token did not match.  Stop the agent, delete its token
file, and start it again -- the daemon writes a new one and the child
reads it at start.

** An agent says it cannot delegate

That is a role, not a fault.  Only the chief of staff and a team's lead
may assign work; a member may assign to nobody, and is not offered
~clawtilla_delegate~ at all.

#+begin_src bash
clawtilla team list                       # who leads what
clawtilla team assign <agent> <team> lead # if it should
#+end_src

A member is not cut off from anybody, though.  It can message, ask and
share a room with any agent in the fleet, so a hand-off in conversation
works and always did.  If an agent has concluded otherwise, check what it
was told: the top of its ~TOOLS.org~ says which of the three it is.

** A lead is refused when it delegates

#+begin_example
builder is not on your team (research), and a lead assigns only within
their own.
#+end_example

Working as intended.  A lead assigns inside its own team; anything else
goes back to the chief of staff, who hands it to the right team's lead.

If those two really are the same team, one of them is on a different one
than you think:

#+begin_src bash
clawtilla agent show <agent> | grep -i team
#+end_src

** Work never reaches a team

Nothing is broken; the chief has nothing to match against.  It chooses a
team by reading descriptions, so a team without one is a team it never
picks.

#+begin_src bash
clawtilla team list      # a team with no description shows as blank
clawtilla team set <id> description "what it handles, and what it does not"
#+end_src

The second half earns its place.  "Reads sources" and "Reads sources, not
for anything that writes code" behave very differently when the chief is
deciding between two plausible teams.

~clawtilla team list~ also prints, to stderr, the things only the whole
fleet shows:

#+begin_example
clawtilla: team 'research' has two leads, 'one' and 'two'. Only one may
assign work; make the other a member.
clawtilla: agent 'x' is on team 'reserch', which is not declared under
teams:
#+end_example

Two leads is not picked between -- which of them may assign is exactly
the question.  A misspelled team leaves the agent running and grouped
under its own name in the sidebar, rather than hidden, because hiding it
is how a typo survives being looked at.

** A team's changes did not reach its agents

~team.set~ rewrites the agents' files, so ~TOOLS.org~ follows a changed
description at once.  Their *sessions* are another matter: an AI CLI
reads its instructions when it starts, so an agent already running has
the old text until it restarts.

#+begin_src bash
clawtilla agent restart <agent>
#+end_src

** One agent went quiet, and its routines produce nothing

An agent that is *stuck* usually says so in the same words every time,
and that is exactly what the cycle detector refuses.  So a wedged agent
and an idle one look identical from the transcript: the first report
arrives, and every repeat after it is dropped before it is enqueued.

The signature is a ~message.refused~ event with no matching message
after it.  Both clients show it as an error alert --- the alerts panel
in the GTK client, the alert list in the web one --- and the reason
names the room and the window.

*** Look in the room, not at the agent

The event's subject is the *room*, because that is where the refusal
happened.  So the obvious command finds nothing:

#+begin_src bash
clawtilla event list fai
#+end_src

#+begin_example
WHEN                 KIND                   SUBJECT
2026-08-27 20:44:20  agent.created          fai
2026-08-27 20:44:20  mailbox.queued         fai
#+end_example

The room is where it is:

#+begin_src bash
clawtilla event list dm:fai:user
#+end_src

#+begin_example
WHEN                 KIND                   SUBJECT
2026-08-27 20:44:20  message                dm:fai:user
2026-08-27 20:44:20  message.refused        dm:fai:user
#+end_example

A bare ~clawtilla event list~ shows the whole fleet and needs no room id.

*** The refusal itself

Sending the same body twice reproduces it directly:

#+begin_example
clawtilla: this exact message has already been sent to 'fai' within the
last 300 seconds. The conversation is going in circles; say something
different, or wait for the window to pass if the repetition is genuinely
what you mean.
#+end_example

Then read the *agent's* logs rather than the transcript.  Whatever it is
repeating is the fault; the refusal is only what stopped you seeing it.

#+begin_src bash
clawtilla agent logs fai
#+end_src

*** If the repetition is legitimate

An agent that reports the same line each time a routine runs is not
looping.  Lower ~orchestration.cycle_seconds~ below the gap between its
runs, or set it to ~0~ to turn the check off.  There is no ~config set~
verb for fleet-level keys: edit the file and reload.

#+begin_src bash
clawtilla config edit          # locally: $EDITOR, then reload on save
#+end_src

#+begin_src bash
clawtilla config reload        # remotely: after editing the file yourself
#+end_src

The reload reaches the running guard, so the next refusal names the new
number rather than waiting for a restart.

*** If the fleet is on an older build

The window used to be a *count* of messages with no duration in it at
all, so how far back the check looked was however long the room's last
~cycle_window~ messages had taken.  In a quiet room that is hours: an
agent whose spawn was failing had its first report delivered and every
one for the next ten hours refused, while looking idle throughout.  If
~cycle_seconds~ is not in ~clawtilla --generate-config~ output, this is
that build.

** The whole fleet went quiet at once

The account's session usage allowance is spent. It is per *account*, so
every agent on it crosses the same wall within the same few minutes ---
which is why this looks like the daemon having failed rather than a
limit being reached.

#+begin_src bash
clawtilla agent logs chief
#+end_src

Look for:

#+begin_example
Session '...': paused -- the account's session usage limit is reached;
it resets at 18:50 on Wednesday 26 August
#+end_example

Nothing is broken and there is nothing to restart. The daemon holds each
paused agent's queued work rather than delivering it, and resumes after
the reset.

*** Why the work is held rather than delivered

Delivery acknowledges an item the moment it reaches the socket, so
handing messages to an agent that cannot answer *consumes* the queue:
each one is delivered, refused by the CLI without reaching a model, and
gone. With the whole fleet behind one wall the entire backlog can be
spent in a couple of minutes. That is how two agents ended an afternoon
holding nothing, and it is what ~clawt_agent_runtime_is_paused()~ now
prevents --- the mailbox is durable precisely so work can outlive an
agent that cannot take it yet.

*** It does not count against the restart budget

An exit while the account is out of allowance is not the agent failing,
so it does not increment the consecutive-failure count. Counting it
spent the restart budget on a wall that would not move, and then left
the agent stopped for a reason that had nothing to do with it.

The backoff also waits for the stated reset rather than doubling from a
second, though it stays capped --- a reset hours away must not become a
timer nothing revisits, and coming back early costs one turn and tells
you whether the wall is still there.

*** If no reset was given

A limit whose message named no reset still pauses, but the agent is
allowed to try again rather than being held indefinitely. Holding it
down on an unknown reset is worse than one wasted turn, and the notice
that comes back carries a time.

** The daemon answers nothing and will not stop

#+begin_example
$ clawtilla agent list
(no reply, no error; times out)
$ kill -TERM $(pgrep clawtillad)
(still running, still starting agents)
$ systemctl --user stop clawtilla
State 'stop-sigterm' timed out. Aborting.
Killing process (clawtillad) with signal SIGABRT.
#+end_example

Something the daemon is waiting on is not answering, and it is waiting
on the main loop's own thread.  In practice that means a container or VM
backend: the API socket for it accepted the connection and then went
quiet.

Confirm it before treating it as anything else, because a daemon that
will not reply looks the same whatever the cause:

#+begin_src bash
# What the main thread is actually doing.
gdb -p "$(pgrep -x clawtillad)" -batch -ex 'thread 1' -ex bt
# Or, if it has already been aborted:
coredumpctl gdb clawtillad
#+end_src

A stack ending in ~container_read_http_response_full~ or
~clawt_pod_bridge_call_for~ is this.

Since 0.1.0 the fleet comes up from an idle source with the waiting done
on a worker thread, so the daemon answers and stops normally while
agents provision, and podomation bounds a silent API socket at
~request_timeout_seconds~ (60 by default) instead of waiting for ever.
A daemon showing the symptoms above is either older than that or is
blocked somewhere else -- and the backtrace says which.

Running a command is answered the same way, and for a sharper reason.  A
provision takes as long as podman takes; an exec takes as long as the
*command* takes, and whoever asked for it chose the command.  One build
would otherwise make the daemon deaf to every other agent, every client,
the event stream and its own SIGTERM -- for as long as the build ran.

Both callers go through ~clawt_computer_exec_async()~: the agent's
~clawtilla_computer_exec~ tool, and the operator-facing ~computer.exec~
IPC verb that ~clawtilla computer exec~ sends.  The second was the later
of the two and is arguably the worse: a person at a terminal is the
caller most likely to run something long on purpose, and a fleet that
appears to hang while a command they can *see* running is still going
reads as the fleet being broken rather than as their own command still
working.

A stack ending in ~clawt_computer_exec~ on the main thread is a build
older than that; on a worker thread it is working as intended, and the
fleet should be answering normally while it sits there.  The verb is
bounded as well as deferred -- it defaults to 120 seconds, enforced on
~host~, ~container~ and ~distrobox~ -- but the bound is a backstop now
rather than the thing that makes it safe.

One caller is left: the agent link's ~mcp.request~ path calls the
synchronous form, because a link handler has no way to defer.  Nothing
reaches tools that way today, so it is a future problem rather than a
current one; it is written down here so it is written down somewhere.

The audit line moved with the wait.  Every command run through this
socket is recorded on the event bus as ~computer.exec~ with its exit
status, and that record is written when the command *ends* -- so
~clawtilla event list~ shows an exit somebody can act on, rather than one
nothing had produced yet.  A command that could not be run at all is
recorded too, with an exit of ~-1~: a trail holding only the successes
reads as "it did not happen" rather than as "we do not know what it
did".

The socket itself is worth checking either way:

#+begin_src bash
curl --unix-socket "${XDG_RUNTIME_DIR}/podman/podman.sock" \
     -m 5 http://d/v1.0.0/libpod/info
#+end_src

An empty reply after five seconds is a wedged podman, not a clawtilla
problem: ~systemctl --user restart podman.socket~.

** The fleet has gone quiet

Nothing arrives, the agent list does not change, and no error appears.

Look at the top of the window first.  A banner under the header saying
the connection is gone means exactly that: the client lost the daemon
and is retrying, and everything on screen is from before it went.  The
same banner in the web client sits under the topbar.  It appears within
about a minute of a network route dying, because that is how long the
keepalive takes to give up on a connection nobody is closing.

If there is no banner, the connection is up and the fleet really is
quiet.

A banner that says the daemon is a different *version* is the other
thing this line can carry, and it is worth acting on even when nothing
looks broken: a client and daemon that disagree fail in whichever
feature happens to use a frame the other does not have, with a message
about that feature rather than about the mismatch.

If the client is reconnecting for a long time, ask the machine directly:

#+begin_src bash
clawtilla remote list          # what is saved
systemctl --user status clawtilla    # on the daemon's own machine
#+end_src

A *toast* saying some events were missed and the view has been reloaded
is not a fault.  It means the outage outlasted the daemon's replay
buffer of 1024 events, the client noticed rather than carrying the hole
silently, and it re-read.  Nothing further is needed.

** A mailbox is stuck

[[file:mailboxes.org][mailboxes.org]] has the full sequence.  Briefly:

#+begin_src bash
clawtilla mailbox list researcher     # is anything waiting?
clawtilla agent list                  # is the link up?
clawtilla mailbox dead researcher     # did they fail?
#+end_src

Items that are all ~leased~ and not progressing mean the agent took
delivery and stopped.  Restart it: the leases expire and the items come
back as ~pending~.

** A mount did not work

*** In a container: it is visible but every access is denied

SELinux.  Add ~relabel: shared~ to the mount.  This is the classic
Silverblue symptom and it reads like a permissions bug rather than a
labelling one.

*** On a host agent: "is outside what this agent may reach"

Check ~clawtilla computer status <agent>~ -- it lists the mounts the
agent actually has.  If yours is not there, the mount was not applied;
if it is there and you are still refused, you are naming a path that is
not under the target.

Mount targets are matched as whole path components, so ~/mnt/sharedx~ is
not inside a mount at ~/mnt/shared~.

*** In a VM: the guest does not see it

~virtiofsd~ must be installed on the host, and the guest kernel needs
virtiofs.  Provisioning checks for ~virtiofsd~ and says so if it is
missing.

** A command was refused

#+begin_example
'/etc/shadow' is outside what this agent may reach
#+end_example

Working as intended.  ~clawtilla computer status <agent>~ says what the
agent *can* reach.  To widen it, add a mount or an ~allow_paths~ entry --
not by switching to ~confine: none~.

#+begin_example
'sudo' is not permitted: this agent runs with allow_sudo: false
#+end_example

Also intended.

** An agent was created and its container or VM is not there

Nothing was ever built.  A computer is built when the agent first
*starts*, so an agent that was created and left alone is a configuration
file and nothing else -- and that looks exactly like a machine that
failed to build.

#+begin_src bash
clawtilla agent list          # "stopped" means it has never run
clawtilla agent start <id>
#+end_src

Creating an agent now starts it, and reports a failure to start rather
than passing over it -- but a guest created by an older build, or with
~--no-start~, is still waiting.  ~defaults.autostart~ will not do it
either: that is false by default, and answers whether an agent comes
back with the daemon rather than whether it exists yet.

** The VM starts and immediately pauses

#+begin_example
internal error: process exited while connecting to monitor:
qemu-system-x86_64: -device {"driver":"vhost-user-fs-pci",...}:
tag property must be 36 bytes or less
#+end_example

A virtiofs tag longer than qemu accepts, and qemu refuses the *device*
rather than the tag -- so the domain never runs.  clawtilla used to use
the target path as the tag, which fits until an agent id reaches
thirteen characters: ~/mnt/clawtilla/exchange/ubuntu-tester~ is 37
bytes.

Fixed by deriving a bounded tag instead.  A guest defined by an older
build keeps the long tag in its domain XML until it is provisioned
again:

#+begin_src bash
clawtilla agent start <id>      # provision rewrites the domain
#+end_src

** A VM will not provision

- libvirt backend: ~systemctl --user status libvirtd~ (or the system
  one, depending on your ~uri~), and check ~virsh -c qemu:///session list~
  works as your user
- QEMU backend: check ~qemu-system-x86_64~ and ~qemu-img~ are on PATH
- either: the base image must exist and be readable
- ~computer.vm.image~ must be *set*, and provisioning refuses outright
  when it is not:

#+begin_example
this VM has no disk image, so there would be nothing for it to boot. Set
computer.vm.image to a qcow2 -- `clawtilla image vm get fedora-44`
fetches one, or pick one under Settings in the GTK client.
#+end_example

clawtilla ships no disk image and downloads none.  The refusal exists
because a diskless domain *defines and starts perfectly*: it boots
nothing, the console is black, and SSH answers "connection reset" because
the forward reaches a guest with no sshd.  Three symptoms, one missing
setting, and nothing anywhere connecting them.

#+begin_src bash
clawtilla image vm list                 # what is already fetched
clawtilla image vm get fedora-44        # or fetch one
clawtilla agent set <id> computer.vm.image /path/to/disk.qcow2
#+end_src

A guest defined by a build older than that refusal is already on disk
with no disk attached, and shows exactly those three symptoms.
~clawtilla computer rebuild <id>~ after setting the image.

** A VM runs but commands in it do nothing

#+begin_example
nothing forwards a port to this VM's SSH, so commands cannot be run in it
#+end_example

Nothing reaches the guest.  In order of likelihood:

- *passt is not installed*, and the backend is libvirt.  libvirt has no
  port forwarding for the SLIRP backend, so passt (Fedora: ~passt~) is
  what makes one possible.  Starting the VM warns about this; install it
  and provision again
- the VM is somewhere clawtilla did not put it.  Set
  ~computer.vm.ssh_host~ (and ~computer.vm.ssh_port~) to an address that
  reaches it; clawtilla then forwards nothing and dials that instead

Check what it is trying:

#+begin_src bash
cat ~/.local/share/clawtilla/vms/<agent>/ssh-port
#+end_src

** The console says "Display output is not active" and ssh is reset

#+begin_example
kex_exchange_identification: read: Connection reset by peer
#+end_example

Three symptoms, one cause, and the same three a VM with no disk gives:
the machine is definitely running, the console shows nothing, and the
forwarded port reaches a guest with no sshd.

If it *has* a disk, look at the CPU.  A domain that names none gets
libvirt's default, ~qemu64~ -- x86-64-v1, from 2003.  Most cloud images
boot on it; a current Enterprise Linux does not:

#+begin_example
Fatal glibc error: CPU does not support x86-64-v2
Kernel panic - not syncing: Attempted to kill init!
#+end_example

That is on the *serial* console, which is why nothing appears on the
graphical one -- the guest panics before it has initialised the display.

#+begin_src bash
virsh -c qemu:///session dumpxml clawt-<agent> | grep -A2 "<cpu"
#+end_src

~host-passthrough~ is what clawtilla emits now.  A domain defined by an
older build keeps ~qemu64~ until it is provisioned again:

#+begin_src bash
clawtilla agent start <agent>      # provision rewrites the domain
#+end_src

** GDM says the system has no primary GPU

#+begin_example
It appears that your system does not have a primary GPU! Proceeding with
any GPU
#+end_example

…and then nothing starts.  Every layer above it looks healthy:
~cloud-init status~ reaches ~done~, ~gdm.service~ is active,
~systemctl get-default~ is ~graphical.target~, and the console sits on the
boot log for ever -- because with no video device the serial console is
the only console there is.

The domain has no ~<video>~ at all, so the guest has no ~/dev/dri~:

#+begin_src bash
virsh -c qemu:///session dumpxml clawt-<agent> | grep -A3 "<video"
#+end_src

Nothing there is the answer.  clawtilla now names a virtio GPU in the XML
for *every* VM, desktop or not -- a guest with no display offers only the
serial console, so a person looking at one cannot tell a broken guest
from a working headless one.  A domain defined by an older build keeps
the omission until it is provisioned again:

#+begin_src bash
clawtilla agent start <agent>      # provision rewrites the domain
#+end_src

This one stayed hidden for a long time because the two backends disagreed
by accident: qemu gives a guest a VGA adapter unless told otherwise, so
the qemu backend had a working desktop while libvirt -- which is the
default, and builds its devices from nothing -- had none.  If a desktop
works on one backend and not the other, this is why.

Related, and a different symptom: virt-manager picks the graphical
console only if the domain had one when the window was *first* opened.  A
domain defined without video keeps the serial console per-VM, which is
why the fix can look as though it did not work.  Close the window and
open it again.

** A VM boots and the login is refused

The guest has no account for clawtilla to use.  Almost always the image:
an installer ISO or a desktop image has no cloud-init, so nothing acts on
the seed.  Use a distribution's *cloud* image.

Otherwise, in order:

- ~xorriso~ missing -- provisioning stops and says so, because it cannot
  build the seed
- ~cloud_init: false~ with an image that does not in fact have a login
  and an authorised key of its own
- an encrypted ~ssh_key~.  Refused with that reason: nothing is present
  to type its passphrase
- the seed was built before you changed ~ssh_user~ or the key, and
  cloud-init only acts on it at *first* boot.  Delete
  ~~/.local/share/clawtilla/vms/<agent>/overlay.qcow2~ and start again

What the guest was told is readable:

#+begin_src bash
cat ~/.local/share/clawtilla/vms/<agent>/cloud-init/user-data
#+end_src

** A setting changed and the VM ignored it

cloud-init reads its seed at *first boot only*, so the login, the
desktop, the flavour and the package list are fixed for the life of that
machine.  Changing one and restarting the agent does nothing visible,
which reads as the setting not working.

#+begin_src bash
clawtilla agent stop <agent>
clawtilla computer rebuild <agent>
#+end_src

That destroys the guest and builds it again -- its contents included.
The GTK client has the same thing as /Rebuild computer/ in the Agent tab.

Settings that are *not* in the seed -- cpus, memory, the disk size --
reach the domain definition and apply at its next boot, with no rebuild
needed.

** The guest boots to a text login prompt with no desktop at all

Not a session problem -- nothing was installed.  cloud-init treats a
package it cannot find as a failure of the *whole* package install, so
one name this distribution does not have costs the entire desktop.

The guest writes down which half failed:

#+begin_src bash
clawtilla computer exec <agent> -- cat /var/lib/clawtilla/desktop-install.status
#+end_src

#+begin_example
failed: gnome-shell is not installed, so the desktop packages did not
install -- one name this distribution does not have fails all of them.
See cloud-init.log.
#+end_example

Then the name itself:

#+begin_src bash
clawtilla computer exec <agent> -- \
    grep -iE "no match|not found|Error:" /var/log/cloud-init-output.log
#+end_src

Fixing it means fixing the flavour's list and rebuilding, since
cloud-init reads its seed at first boot only:

#+begin_src bash
clawtilla computer rebuild <agent>
#+end_src

** A VM has a desktop installed and no session on it

The guest boots, cloud-init reports success, and the agent's screenshots
come back showing a text console -- or the desktop is there and every
automation tool answers that automation is disabled.

Almost always the wrong *family*.  cloud-init picks the package manager
for you and nothing else, so the seed has to know the names, the display
manager's unit and where a couple of binaries live.  Getting it wrong
fails inside the guest, in a log nobody is looking at.

Check what clawtilla thought it was building:

#+begin_src bash
grep -E "^packages:|gdm" \
    ~/.local/share/clawtilla/vms/<agent>/cloud-init/user-data
#+end_src

- ~gdm3~ and ~gdm3.service~ means it decided Debian or Ubuntu; ~gdm~ and
  ~gdm.service~ means Fedora, Enterprise Linux or Arch
- if that does not match the image, set ~computer.vm.desktop.flavour~
  outright rather than leaving it at ~auto~

Starting the agent warns when it could not place the image at all:

#+begin_example
cannot tell which distribution '...' is; installing the desktop with
Fedora package names. Set computer.vm.desktop.flavour to ...
#+end_example

Then read what actually happened *in the guest*, which is where the
failure is:

#+begin_src bash
clawtilla computer exec <agent> -- cloud-init status --long
clawtilla computer exec <agent> -- journalctl -u cloud-final --no-pager
#+end_src

A package that does not exist fails the *whole* install, so one wrong
name costs the desktop rather than one application.  cloud-init acts on
the seed at **first boot only**: fixing the flavour means deleting
~~/.local/share/clawtilla/vms/<agent>/overlay.qcow2~ and provisioning
again, not restarting.

*** On Arch, after the image has sat for a while

~clawtilla image vm rm arch~ and fetch it again.  The ~latest/~ URL
follows a monthly rebuild, so a cached copy ages faster than the others
and a first boot eventually fails on package signatures.

** The guest reaches a GDM login screen

Autologin did not happen, and there is no way past it: the session
account's password is locked on purpose, so the prompt cannot be
answered by anyone.

Almost always the wrong config file.  GDM has three names for it --
=/etc/gdm/custom.conf= on Fedora, Enterprise Linux and Arch,
=/etc/gdm3/daemon.conf= on Debian, =/etc/gdm3/custom.conf= on Ubuntu --
so a guest placed as the wrong family writes a file its GDM never reads.

#+begin_src bash
grep -A3 AutomaticLogin \
    ~/.local/share/clawtilla/vms/<agent>/cloud-init/user-data
#+end_src

If the path does not match the table above, set
~computer.vm.desktop.flavour~ rather than leaving it at ~auto~, and
rebuild: cloud-init acts on the seed at first boot only.

#+begin_src bash
clawtilla computer rebuild <agent>
#+end_src

** The desktop is up and every tool says "DBus object has no attribute"

The session is fine.  A screenshot of the console shows GNOME, ~gdm~ is
active, and the ~clawtilla-desktop~ tools are listed -- and every one of
them fails with a D-Bus error naming nothing.

The tools *are* a GNOME Shell extension.  If it did not install, the
D-Bus name is still owned by GNOME Shell (so a ~Ping~ succeeds, which
makes it look like a live connection) and the object the tools call does
not exist.  Read the guest's own record of the install first:

#+begin_src bash
clawtilla computer exec <agent> -- cat /var/lib/clawtilla/desktop-install.status
#+end_src

#+begin_example
failed: could not create /usr/share/gnome-shell/extensions
#+end_example

That is the answer.  Do not go on to read dconf, list extensions or
introspect the bus -- all three will report exactly what a missing
extension implies, at length.

If the file says ~ok~ but the tools still fail, the extension is on disk
and GNOME Shell has not loaded it.  It scans at session start, so one
installed afterwards needs the session restarted; on Wayland that means a
reboot of the guest.

#+begin_src bash
clawtilla computer exec <agent> -- /usr/local/bin/clawtilla-desktop-install
clawtilla agent restart <agent>
#+end_src

If the file is *not there at all*, the guest was built before clawtilla
installed the desktop this way.  cloud-init acts on the seed at first
boot only, so a fix to the seed cannot reach a guest that has already
booted:

#+begin_src bash
clawtilla computer rebuild <agent>
#+end_src

That destroys the guest and builds it again from the current
configuration, so anything living only inside the VM goes with it.

** Clicks land near the control but not on it

The agent is estimating coordinates from an assumed layout.  An image is
not a coordinate, and nothing in the tool surface turns one into the
other, so it guesses -- and a few dozen pixels out looks exactly like the
pointer being wrong.

Take a screenshot and read the positions out of it:

#+begin_src bash
clawtilla computer exec <agent> -- \
    tesseract /mnt/clawtilla/workspace/screenshots/x.png - tsv
#+end_src

The centre of the bounding box for the text you want is where to click.
The agent is told this in its own description; if it is not doing it,
the guest predates the guidance.

~tesseract: command not found~ on Enterprise Linux is expected: it is in
EPEL, which a cloud image does not enable, and clawtilla will not name a
package cloud-init cannot find because that fails the whole install.

** Text arrives duplicated or with a stray character

~emacsemacs~ where ~emacs~ was meant, or one leftover character in front
of otherwise clean text, right where a field was cleared and retyped.

The clear did not fail; it arrived *after* the typing.  Synthetic events
carried fabricated timestamps that restarted from the current clock on
every call, so a burst was stamped into the future and the next call
began behind it.  Fixed in the desktop extension -- update
~computer.vm.desktop.mcp_repo~'s checkout and rebuild the guest, since
cloud-init clones it at first boot.

** The agent's typing goes somewhere else

Text ends up in GNOME's Activities search box rather than in the
application, while ~list_windows~ reports the window as ~focused: true~.

Both are correct.  ~focused~ is the window manager's focus; the overview
takes the *keyboard* without changing it, and no tool reports that.  It
is open at login, before anything has a window, so the first application
an agent starts opens *behind* it.

Send Escape before typing into a freshly focused window.  A screenshot
shows the overview plainly, which is the reliable check when text is not
appearing where it should.

** A file the agent made in its computer is not there

The agent writes a file inside its VM or container, then cannot open it
-- or a tool hands back a path that does not exist.

Its ~read~, ~write~ and ~bash~ run on the **host**.  Only
~clawtilla_computer_exec~ goes inside.  So a path from inside means
nothing to the tool the agent reaches for first, and an empty result
there reads exactly like a file that was never written.

Put it in a share and use the host name of it:

#+begin_src bash
clawtilla computer exec <agent> -- ls /mnt/clawtilla/workspace
#+end_src

The agent's own description lists every share as
~host path = the path inside~.  Screenshots from a guest desktop already
land in ~/mnt/clawtilla/workspace/screenshots~, which is
~<workspace>/screenshots~ on the host.

If the directory is empty *inside* the guest, the share is not mounted:

#+begin_src bash
clawtilla computer exec <agent> -- findmnt /mnt/clawtilla/workspace
#+end_src

A guest built before clawtilla wrote fstab entries has the device and no
mount.  cloud-init acts on the seed at first boot only, so that needs
~clawtilla computer rebuild <agent>~.  On the qemu fallback backend there
is no share at all and the daemon says so at start -- it has no virtiofsd
of its own; use ~computer.vm.backend: libvirt~.

** An application in the guest renders or behaves oddly

Screenshots of one application come back stale while GNOME's own panel
updates; keystrokes reach it but Return does not commit; that sort of
thing.

Check how it was started.  A plain shell in the guest has no session, so
~DISPLAY=:0 <app>~ is the obvious thing and it *works* -- by putting the
application on Xwayland rather than in the Wayland session, which
composites and delivers synthetic input by a different path.

#+begin_src bash
clawtilla computer exec <agent> -- \
    /usr/local/bin/clawtilla-desktop-run <command>
#+end_src

If the launcher is not there, the guest predates it; ~clawtilla computer
rebuild <agent>~ or run
~/usr/local/bin/clawtilla-desktop-install~ and re-provision.

** A connector's tools are missing, or refuse

*** "not connected yet"

No credential has been stored for it:

#+begin_src bash
clawtilla connector key <name>       # paste a token
clawtilla connector connect <name>   # or authorize, with a client id
#+end_src

*** The agent has the connector and no tools

The catalogue entry names no MCP server and the integration named none
either, so there is a credential and nothing to use it with.  Set
~command~ or ~url~ on the integration; ~clawtilla connector catalog~
shows which entries know a server of their own.

*** "clawtilla does not permit 'x' for this agent"

The connector was narrowed with ~tools~.  Widen or clear that list.

*** "no connector called 'x'"

~provider~ names a catalogue entry that does not exist.  The error names
~connectors.dir~ as well, because the fix is usually a file that adds it.

*** It worked yesterday and stopped

#+begin_src bash
clawtilla connector list      # expiry and whether it can renew itself
clawtilla connector refresh <name>
#+end_src

A credential that expired and has no refresh token needs connecting
again.  One that is expired *and* renewable is normal -- the daemon
renews it on a timer, and the list says so rather than calling it broken.

** An MCP server I added to .mcp.json keeps disappearing

Only if you named it ~clawtilla-something~.  That prefix is *reserved*:
clawtilla rewrites or removes every key beginning with it on each agent
start, which is what lets a revoked integration's entry disappear instead
of pointing the agent at a server the fleet has stopped offering.

Rename it to anything else and it will be left alone for ever.  Every
other key in that file is read back and written out untouched, because
handing an agent MCP servers is exactly what people edit it for.

** The agent has a clawtilla-desktop tool that reaches nothing

An ssh to a VM that is not there, or a port nothing listens on.  The
entry is rewritten on every agent start and dropped when the desktop
grant goes, so a stale one means the agent has not been restarted since
whatever changed:

#+begin_src bash
clawtilla agent restart <agent>
grep -o '"clawtilla[^"]*"' ~/.clawtilla/agents/<agent>/.mcp.json
#+end_src

The port matters here.  It is chosen when the VM is provisioned, which is
*after* the workspace files are written -- so an entry captured at render
time would name a port nothing listens on.  That is why the entry names
the clawtilla CLI rather than ~ssh~ directly, and why editing it by hand
to a literal ssh command breaks on the next provision.

** A permission was granted and the agent says it does not have it

The agent is right about its session and wrong about the fleet.  An AI CLI
lists its tools *once*, when its session starts, so a permission granted
under a running agent reaches its files and not its session.

#+begin_src bash
clawtilla agent restart <agent>
#+end_src

~agent set~ says so in its reply for anything under ~tools.~ or
~persona.~, and both graphical clients show it.  It does *not* say so for
~chief_of_staff~, which behaves the same way -- so a chief granted its
role while running has to be restarted, and nothing will have told you.

To check what the agent was actually handed rather than what the config
says, read the region clawtilla owns in its own file:

#+begin_src bash
sed -n '/BEGIN clawtilla tools/,/END clawtilla tools/p' \
    ~/.clawtilla/agents/<agent>/TOOLS.org
#+end_src

That region is written by the daemon from the same gate that answers the
call, so it cannot disagree with the permission.  If the tool is listed
there and the agent still says it has none, it is the session -- restart.

** An identity file was edited and the agent has not noticed

Restarting is *not* enough, which is the surprising half.  An AI CLI is
not handed a system prompt when it *resumes* a session, so editing
~SOUL.org~, or repointing ~persona.identity_files~, leaves a running
agent with the identity it was created with and leaves a restarted one
resuming from where it was.

#+begin_src bash
clawtilla agent reset <agent>
#+end_src

That clears the session, which is what applies it.  It stops the agent
itself and starts it again if it was running, so there is nothing to do
around it.

It has to clear two places -- the session directory and libreclaw's own
database -- because libreclaw restores from either, and clearing one
leaves the agent resuming from the other and looking exactly like a reset
that did nothing.  The session directory is *moved aside* rather than
deleted, to ~sessions.reset-<timestamp>~ beside it, so a reset that threw
away something you wanted is recoverable.  Those are ignored by the state
directory's git block and are yours to delete.

** A task or routine says completed and the answer is a progress note

#+begin_example
completed: ⏳ Still working... (5m elapsed)
#+end_example

The work is still running; nothing is waiting on it any more.  A task
completes on a message carrying its thread id, and libreclaw puts more
than the answer in a thread -- a progress note every five minutes, a
guardian refusal, a restart notice.

Fixed at both ends, and a running agent picks up the first half at its
next start: the note is no longer generated (~progress_enabled: false~ in
the rendered ~channels.clawtilla~ block), and the daemon no longer acts
on a message that arrives while the agent is still mid-turn.

#+begin_src bash
clawtilla config render <agent> | grep -A5 'clawtilla:'
clawtilla agent restart <agent>
#+end_src

Nothing is lost by the note going: the same turn already raises the
typing indicator, which both clients draw as a live activity line.

** gowl is unreachable

- gowl must be built with ~MCP=1~ and have ~modules.mcp.enabled: true~
- the socket defaults to ~$XDG_RUNTIME_DIR/gowl-mcp.sock~; set

- you must be in the gowl session; there is nothing to connect to from a

** Two agents are talking to each other for ever

They are not -- one of four limits stopped them.  Check which:

#+begin_src bash
clawtilla task list        # a task failed with a budget reason?
clawtilla agent logs chief-of-staff
#+end_src

The refusal names the limit.  If you genuinely need more room, raise
~orchestration.max_hops~ -- but a fleet that needs more than four hops
usually has a chief that is delegating in circles rather than dividing.

** The GTK client shows nothing

Read the top of the content area first; the two causes look identical in
the sidebar and are told apart by whether there is a banner.

*** With a banner saying "Not connected"

There is no daemon on the other end, and there never was one this
session.  The window opens regardless, deliberately: a local daemon that
is not running must not stand between you and the machines in
~connections.yaml~.

Three things you can do, in the order most people want them:

- press *Connections* in the banner and pick another machine;
- start the local one -- ~clawtillad --foreground~, or
  ~systemctl --user start clawtilla~.  The window is still trying in the
  background, so it fills itself in within a second or two of the daemon
  coming up.  You do not have to restart the client;
- read the reason on stderr.  The window says *which* daemon; the
  terminal you launched it from says *why*, which for a remote is usually
  a port or a token.

A banner saying the connection was *lost* is a different thing: the
daemon was there and went away.  That is
[[#route-goes-away][A client on another machine stopped showing new
messages]] below if it happened without anything closing, or an ordinary
daemon restart if it did not -- either way the client reconnects on its
own.

*** With no banner and an empty agent list

The fleet really is empty.  ~clawtilla agent list~ from the CLI will
agree, because both are asking the same daemon.

** A client on another machine stopped showing new messages
:PROPERTIES:
:CUSTOM_ID: route-goes-away
:END:

The window still says it is connected to the remote daemon, the agent
list is drawn, nothing has reported an error --- and no message sent
from anywhere else appears, including the ones you type, which are drawn
from the daemon's own event rather than locally.  Sending eventually
reports:

#+begin_example
the daemon did not answer msg.send within 120 seconds
#+end_example

and that message never reaches the fleet: it is not in
~clawtilla room history~ on the daemon's own machine, because it never
arrived.

The connection died without either end being told.  A route that
disappears --- a laptop that suspended, a tailnet that came back on a
different path, a firewall that forgot an idle flow --- does not close
or reset anything; it just stops carrying packets.  Neither end notices
while neither end is sending.

Every TCP connection is armed with keepalive for this, and a dead one is
now reported in about a minute: the client disconnects, reconnects, and
re-subscribes from the cursor it had reached, so the events it missed
are replayed into the transcript.  You will see a short gap and then the
conversation catching up.

If it does *not* catch up, check the version at both ends --- the arming
happens when the connection is opened, so a client built before this
change goes on believing in a connection its daemon has already given up
on:

#+begin_src bash
clawtilla --host <daemon> --port 8792 --token "$(…)" status
ss -tnp -o state established '( sport = :8792 or dport = :8792 )'
#+end_src

~ss -o~ prints the keepalive timer beside each socket.  A connection
with no timer on it is one nobody will ever notice the death of.

A unix client is not affected and never was: a local peer that goes away
closes its socket, and the reader is told on the next turn of the loop.

** A fix built and tested, and the running daemon still misbehaves

~make test~ builds the library, the test binaries and the plugins.  It
does *not* relink ~clawtillad~.  So a change can be built, tested and
passing while ~build/release/clawtillad~ is still the previous one, and
restarting it to check the fix by hand runs the old code.

#+begin_src bash
make                                    # then restart the daemon
#+end_src

The same applies to the CLI and both graphical clients.  Plain ~make~ is
what relinks everything; ~make test~ is for the suite.

To settle what a running daemon actually is rather than guessing:

#+begin_src bash
readlink /proc/$(pgrep -x clawtillad)/exe
#+end_src

~(deleted)~ after the path means the binary was replaced underneath it,
which is exactly the case that looks like a fix not working.

** Getting more detail

#+begin_src bash
G_MESSAGES_DEBUG=Clawtilla clawtillad --foreground
#+end_src

And the event log, which is the durable version of the same thing:

#+begin_src bash
ls ~/.clawtilla/events/

** The task budget never seems to fire

Check it is not disabled:

#+begin_src bash
clawtilla config show | grep task_budget_usd
#+end_src

Then check the work is a *task*.  Spend is booked against a task id, and
ordinary chat has none -- conversation is deliberately uncapped and only
delegated work is bounded.  ~clawtilla task list~ shows what is running.

Also worth knowing: the first turn an agent takes after the daemon starts
charges nothing.  It sets a watermark instead, so a restart mid-task does
not bill that task for everything the agent has ever done.  See
[[file:spending.org][spending.org]].

** clawtilla cost reports zero for everything

The rows come from each agent's libreclaw database:

#+begin_src bash
ls ~/.clawtilla/agents/*/sessions/libreclaw.db
#+end_src

Note the ~sessions/~ component -- libreclaw builds that path from
~session.persist_dir~, not from ~database.path~.  If the files are there
but empty, no turn has completed: a turn reporting no tokens at all is
deliberately not recorded, because a zero row would inflate the count
with no data behind it.

If the files are missing entirely, the agents have never run.

** The cost looks too large for the tokens beside it

That is correct and expected.  The cost is the figure the provider
reported; the ~IN~ column counts only *new* input tokens.  Cached context
is billed and is not reported as tokens, so a turn can honestly show
eight input tokens against a bill of two cents.

** An imported agent has no personality

It is reading the templates, not the persona you imported.

#+begin_src bash
ls ~/.clawtilla/agents/<id>/
#+end_src

Two complete sets -- =SOUL.md= beside =SOUL.org= -- means the workspace
was imported before clawtilla adopted markdown personas, and the =.org=
blanks are the ones being loaded.  Point it at the real ones:

#+begin_src bash
clawtilla agent set <id> persona.identity_files SOUL.md,USER.md,AGENTS.md
clawtilla agent reset <id>
#+end_src

The reset is not optional.  An AI CLI is not handed a system prompt when
it resumes a session, so the change reaches the agent's files and not its
prompt until the session is cleared.

** A setting was accepted and does nothing

Check whether it is a list:

#+begin_src bash
clawtilla config show | grep -A3 <the key>
#+end_src

A list written as ~key: a,b~ rather than as a YAML sequence is read back
as unset, and everything reports success -- the CLI echoes it, the file
holds it, and the agent runs on the default.  ~agent set~ writes a real
sequence now for every key the schema calls a list; a file edited by hand
before that, or by an older build, still holds the scalar.

The sharp version of this is confinement: ~computer.host.deny_paths~
written as a scalar denies nothing.

** An agent with its own workspace has no skills

#+begin_src bash
clawtilla config render <id> | grep -A2 skills
#+end_src

Skills come from =<workspace>/skills=.  A build before that fix took them
from the state directory, which is the same place only for agents that
never set ~workspace~ -- so an agent given one pointed at a directory
nothing creates.
