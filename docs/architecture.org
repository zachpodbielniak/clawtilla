* Architecture

** The shape of it

#+begin_example
                    ┌──────────────────────────────────┐
   clawtilla CLI ──▶│                                  │
  clawtilla-gtk ──▶ │   ClawtDaemon  (owns everything) │
  clawtilla-web ──▶ │                                  │
   cmacs (in-proc) ─┤   config · agents · rooms · tasks│
                    │   mailboxes · plugins · events   │
                    └───────┬──────────────────┬───────┘
                            │                  │
                   ClawtIpcServer      ClawtLinkServer
                   (daemon.sock)       (agents.sock)
                            │                  │
                        clients            libreclaw
                                          processes
#+end_example

Two sockets, deliberately.  Clients speak one protocol on one socket;
agents speak another on another.  They are not the same audience: a
client is a person's tool and gets the whole surface, while an agent gets
exactly the tools its configuration grants it.

** The rule everything else follows

*The daemon owns every transport, every credential and every agent
process.  Clients hold none of them.*

A client sends typed requests and folds one event stream.  That is what
makes the CLI, the GTK app, the web client and an in-process cmacs embed
the same program with different front ends -- and what makes two clients
open at once agree with each other rather than each having its own idea
of the fleet.

The temptation is always to let a client do something small itself: edit
the config file, start one agent, read one mailbox.  Every one of those
would be a second implementation of a rule the daemon already enforces,
and the two would drift.

** Objects

*** ClawtDaemon

The assembly.  Owns:

| Component | What it is for |
|-----------+----------------|
| ~ClawtConfig~ | the fleet configuration, and the only writer of it |
| ~ClawtAgentManager~ | the agents, their mailboxes and their state |
| ~ClawtRoomManager~ | rooms and their persisted transcripts |
| ~ClawtTaskManager~ | delegated work |
| ~ClawtMailboxRouter~ | turning a message into deliveries |
| ~ClawtLoopGuard~ | hop, rate, budget and cycle limits |
| ~ClawtUsage~ | what each agent has spent, read from its own database |
| ~ClawtEventBus~ | what happened, with a resumable cursor |
| ~ClawtEventLog~ | the same, on disk, secrets scrubbed on write |
| ~ClawtDecisionStore~ | choices an agent needs a person to make |
| ~ClawtExchange~ | the shared drop-box agents pass files through |
| ~ClawtVmImageStore~ | the cloud images on disk, and the downloads in flight |
| ~ClawtLinkServer~ | where agents dial in |
| ~ClawtIpcServer~ | where clients connect |
| ~ClawtMcpTools~ | the tools agents call to work together |
| ~ClawtPluginManager~ | third-party extensions |
| ~ClawtPodBridge~ | podomation, for containers and VMs |
| ~ClawtNotifier~ | telling a person when an agent is blocked or broken |
| ~ClawtRoutineRunner~ | standing work, on presets or cron |
| ~ClawtAutomation~ | clawtilla as a podomation module, both directions |
| the connector catalogue | services an account can be held for, and the flows in progress |

Three of those are worth a sentence each, because they are the ones a
reader does not expect to find on the daemon.

~ClawtUsage~ holds a watermark per agent and nothing else.  Every agent
has been writing one ~token_usage~ row per AI turn into its *own*
libreclaw database since 0.24.0, and nothing had ever read them -- so the
first question an operator running a paid fleet asks had no answer
anywhere in the product.  It is read through libreclaw's own API rather
than by opening its schema, so there is no copy of that column list here
to fall out of step with a table clawtilla does not own.  A missing
database is *zero, not an error*, and must not be opened: opening a
sqlite database creates it, and asking what a stopped agent cost should
not leave one behind.

~ClawtDecisionStore~ sits beside the alerts rather than inside them.  An
alert is something that happened; a decision is something that needs
you, and one badge meaning both is a badge nobody can act on.  Durable
for the same reason the mailbox is: an agent that asked and got no answer
carried on with its default, and an operator who never saw the question
has no way to know that happened.

~ClawtVmImageStore~ exists because a VM needs a disk image, clawtilla
ships none, and they are several hundred megabytes each -- so fetching
one is a deliberate act with progress to watch rather than something that
happens inside an agent's first start.

~clawt_daemon_new(path, main_context)~ takes a ~GMainContext~.  That
parameter is what makes embedding work: a host that owns its own loop
passes its context and gets the identical daemon with no process and no
socket in between.

*** ClawtAgent

One agent: identity, state, capabilities, hop depth, and pointers to its
config, runtime, computer, desktop, mailbox, memory store and link.

Its ~ClawtMemoryStore~ is per-agent and per-agent only -- a searchable
sqlite store an agent writes to and reads back through its own tools.
Note the plural in ~memories.*~: ~agents.memory~ is a completely
unrelated setting, libreclaw's ~MEMORY.md~ size budget, and the two have
been confused before.

~ClawtAgentCaps~ is derived from what the agent *has*, not from what its
config asked for.  A computer that failed to provision leaves the config
saying ~container~ while the agent has nothing; deriving from the object
means no interface offers a control the agent cannot honour, and the
agent is never told it has a tool that is not really there.

*** Teams

Teams have no object.  They are a list in the configuration and two
fields on an agent, and everything that acts on them is a pure function
over that: ~clawt_team_may_assign()~ answers who may hand work to whom,
~clawt_team_validate_fleet()~ answers what only the whole fleet shows.

Deliberately so.  A ~ClawtTeam~ would be a second place holding
membership, and the first thing it would do is disagree with the config
about who is on what -- the same shape as every "two answers to one
question" bug in this codebase.  A team is not a thing that runs; it is a
way of reading the fleet.

Which means the rule is testable without a daemon, a fleet or a running
agent.  A permission check that needs all three to exercise is one that
gets exercised once.

*** ClawtAgentRuntime

Abstract.  Two implementations:

- ~ClawtProcessRuntime~ (default) -- a supervised ~libreclaw~ child.  Its
  own environment, its own credentials, optionally its own container, and
  an interruptible turn because there is a process to signal.
- ~ClawtEmbeddedRuntime~ -- an ~LcApp~ inside the daemon, via
  ~lc_app_new_embedded()~.  Cheaper, and the only option where there is
  no binary to run.  In exchange it cannot have its own environment or
  credentials and cannot be interrupted.  ~get_caps~ reports that
  honestly rather than offering controls that would do nothing: the
  process runtime answers ~INTERRUPT | STREAMING~, the embedded one
  ~STREAMING~ alone.

**** Several LcApps in one process

The embedded runtime is the case where libreclaw's own single-instance
assumptions stop holding, and every one of them is somebody else's
constraint that clawtilla has to render around:

- ~port: 0~ for the dashboard, api, bridge and webhook listeners, then
  read the real port back.  Two agents asking for the same fixed port is
  one agent that will not start.
- distinct ~session.persist_dir~, ~database.*~ and
  ~ai.subagent.state_dir~ per agent.  Sharing a persist directory lets
  one agent resume another's session, which looks like the model
  hallucinating a conversation it never had.
- OTel enabled in at most one.
- ~channels.local~ in none of them.  It owns fd 0 and fd 1, so two agents
  in one process fight over the terminal -- and an agent the daemon
  started has no terminal at all.  clawtilla renders it only when an
  integration explicitly asks.

The daemon's own ~PodEngine~ is deliberately *not* shared with an
embedded ~LcApp~.  Sharing would be cheaper and would also let one
agent's container operations cancel another's, with no way to tell them
apart afterwards.

*** ClawtComputer

Abstract, with ~none~, ~host~, ~container~, ~distrobox~ and ~vm~
implementations, plus an optional desktop add-on.  See
[[file:computers.org][computers.org]].

One rule about the base class belongs here rather than there, because it
is about how a derivable type is written and not about computers.  *A
missing vfunc must not answer TRUE.*  ~clawt_computer_teardown()~ went
through a helper that returned TRUE when the vfunc was NULL, and the VM
backend had no teardown at all -- so removing a VM agent took the success
branch, recorded the computer as removed, and left the libvirt domain
defined and the disk on disk.  A missing feature that reports failure is
a gap; one that reports success is a lie, and it was found by opening
virt-manager and seeing a VM that should not have been there.  The
default is a refusal naming the type now, and the two backends with
genuinely nothing to destroy say so in two lines each.

** What is a GObject and what is not

It matters more than it sounds, because the type system will let one be
passed where the other is expected and the crash lands elsewhere.

GObjects, and the ones with signals worth connecting to:
~ClawtDaemon~ (~started~, ~stopped~, ~reloaded~), ~ClawtAgentManager~
(~agent-added~, ~agent-removed~, ~agent-state-changed~), ~ClawtAgent~
(~state-changed~, ~error~), ~ClawtAgentRuntime~ (~started~, ~exited~,
~log-line~), ~ClawtComputer~ (~state-changed~), ~ClawtMailbox~
(~item-added~, ~item-leased~, ~item-acked~, ~item-dead-lettered~,
~depth-changed~), ~ClawtRoom~ and ~ClawtRoomManager~, ~ClawtTaskManager~
(~task-changed~), ~ClawtLink~ and ~ClawtLinkServer~, ~ClawtEventBus~
(~event~), ~ClawtVmImageStore~ (~progress~, ~finished~), ~ClawtClient~
(~connected~, ~disconnected~, ~event~) and ~ClawtAgentDesigner~
(~draft-changed~).

*Emitting a signal is half the work.*  The manager's
~agent-state-changed~ had been emitted since the manager was written and
nothing had ever connected to it, so an agent that crashed produced no
event on the bus at all: clients found out by polling, and nobody found
out at 3am.  Grep for a connection before assuming a signal is wired.

Everything else with a ~Clawt~ prefix is a *boxed* type -- reference
counted or copied, with a ~G_DEFINE_AUTOPTR_CLEANUP_FUNC~ in its header:
~ClawtAgentConfig~, ~ClawtMessage~, ~ClawtMailboxItem~, ~ClawtEvent~,
~ClawtTask~, ~ClawtMount~, ~ClawtExecResult~, ~ClawtMemory~,
~ClawtDecision~, ~ClawtCron~, ~ClawtRoutine~, ~ClawtSecretRef~,
~ClawtParamInfo~, ~ClawtConnection~, ~ClawtAppearance~,
~ClawtIntegrationConfig~, ~ClawtIntegrationBinding~, ~ClawtOauthToken~,
~ClawtDeviceCode~, ~ClawtNotification~, ~ClawtMatrixLogin~,
~ClawtMatrixRoom~, ~ClawtGuestDesktop~, ~ClawtUsageTotals~, ~ClawtVmImage~.

Which is exactly why the distinction is written down.  ~g_task_new()~
refs its source object, so passing a ~ClawtIntegrationBinding~ -- a plain
reference-counted struct -- ran ~g_object_ref()~ on something that is not
a GObject and took the daemon down on the first health check anybody
asked for.  It builds, it type-checks, and the cast in the callback looks
symmetrical with every other async function in the file.  Carry a
non-GObject in the task *data* and pass NULL as the source.

** How a message moves

#+begin_example
  a client's msg.send          an agent's tool call        an agent's reply
        │                              │                          │
        ▼                              ▼                          │
  ClawtIpcServer                  ClawtMcpTools                    │
        │                              │                    ClawtLinkServer
        └──────────────┬───────────────┘                          │
                       ▼                                          │
             ClawtMailboxRouter::send  ◀───────────────────────────┘
                       │
                       ▼
             resolve destination     room id, or agent id → the direct room
                       │
              ┌────────┴────────┐
              │  ClawtLoopGuard │  hops? rate? budget? cycle?  ── refused here
              └────────┬────────┘
                       ▼
             append to the room's transcript
                       │
                       ▼
             for each member: post to their ClawtMailbox   (durable, SQLite)
                       │
                       ▼
             drain to whoever is connected
                       │
                       ▼
             ClawtLink ──▶ libreclaw's clawtilla channel ──▶ the agent
#+end_example

Three things about that order matter.

*The destination is resolved before the guard runs.*  Not an accident of
ordering: a refusal publishes ~message.refused~ with the *room* as its
subject, and until the destination is resolved there is no room to name.
A refusal a client cannot place in a transcript is a refusal nobody sees.

*Loop safety is applied before anything is enqueued.*  A runaway fan-out
has to be stopped at the source; by delivery time the messages already
exist and refusing means cleaning up rather than preventing.

*The mailbox is written before delivery is attempted.*  That is why
messaging a stopped agent works, and why a daemon killed mid-turn does
not lose the queue.

Every path converges on ~clawt_mailbox_router_send()~, including an
agent's ordinary reply -- which arrives on the link and is routed like
anything else.  That is not merely tidy.  The hop counter is what stops
two agents answering each other for ever, and it was stamped as a flat
depth of 1 on the link path for a long time, so the one limit built for
exactly that case could never fire on the path where it happens.  Two
agents traded fifty messages and nothing stopped them.  *Anything that
stamps a depth must derive it from ~clawt_agent_get_hop_depth()~.*

The same rule caught the budget.  ~orchestration.task_budget_usd~ was
enabled by default, checked on every routed message, and
~clawt_loop_guard_record_spend()~ was called by nothing outside a test --
so the counter the check read was permanently zero.  It is charged from
the link handler now, where an agent's turn actually ends, and drained on
*every* reply rather than only the ones carrying a task id: the drain is
what advances the watermark, so skipping the untasked turns would bank
them and hand the whole accumulated bill to whichever task happened to be
answered next.

*** An agent's mailbox is empty while it is running

Delivery acknowledges an item the moment it reaches the socket and hands
it over as an ordinary turn, so the mailbox only holds what queued while
the agent was stopped.  Anything that reads a running agent's queue is
reading a queue that is almost always empty, and that means nothing.  An
agent checking there for a peer's reply concluded, correctly and
uselessly, that none had come -- while the reply was in the turn it had
just been handed.

** Threading and main contexts

clawtilla is single-threaded by design.  Everything runs on one
~GMainContext~ -- the daemon's own when embedded, the default one when
standalone.

The one rule that catches people: *~g_timeout_add_seconds()~ and
~g_idle_add()~ attach to the default context, not the thread-default
one.*  In an embedded daemon -- one whose host runs its own loop on its
own context -- that means the source never runs at all.  Everything
periodic goes through ~clawt_timeout_add_seconds()~, which exists for
exactly this; an idle uses ~g_idle_source_new()~ plus
~g_source_attach(source, context)~.  Three real bugs came from getting
this wrong: a keepalive and a restart policy that silently never fired,
and an idle that never delivered a single event to an embedded client.

It generalises past the source constructors, and the generalisation is
the part worth keeping: *anything that captures "the current context" is
a bug in an embedded daemon unless it was told which one.*  Two more of
the same shape have already been paid for.

~g_task_new()~ captures ~g_main_context_ref_thread_default()~, and
dispatching a source does *not* make its context thread-default -- GLib
pushes nothing on the way in.  So a task created inside a source callback
takes the process default and completes on a loop the daemon may never
run.  The context is pushed explicitly around every ~g_task_new()~ here.

And anything that *waits* must wait on the context the answer will arrive
on.  ~ClawtProcessRuntime~ holds the context its child's exit will be
delivered to, because ~stop()~ once asked for whatever was thread-default
on its own call stack while ~g_subprocess_wait_async()~ had captured a
different one at start.  On ~clawtillad~ both are the process default and
it worked by luck; the moment a start ran from a ~GTask~ callback -- which
pushes the task's context -- the exit arrived somewhere ~stop()~ was not
looking, so every clean shutdown waited out the full grace period and
SIGKILLed a child that had already gone.  It surfaced as ~pid 0 did not
stop within 5 seconds~, and the zero is the tell:
~g_subprocess_get_identifier()~ returns NULL once the child is reaped, so
the message was reporting a process that had already exited.

The synchronous client (~clawt_client_request~) blocks on a read.  A
client that also wants to iterate a main loop -- the GTK app, or a test
-- runs the request on another thread and pumps the loop meanwhile.

*** An IPC handler must not wait on the network -- nor may daemon start

Every handler runs on the daemon's main context while the client blocks,
so a handler that calls out to the internet stalls that client for as
long as the far end takes -- and stalls everybody else with it, because
nothing else is dispatched meanwhile.  ~model.list~ asked five provider
APIs, and both the new-agent dialog and the agent inspector call it on
every build, so pressing + or clicking an agent appeared to hang.

The rule has a corollary that cost a second bug, and it is the reason the
sentence has two halves.  The daemon used to warm the model cache in
~clawt_daemon_start()~, which called those same five APIs on every start
whether or not anybody would look -- and made ~make test~ reach the
network from every daemon fixture.  *Anything that leaves the machine
happens when a client asks for it, not because the daemon woke up.*

A handler that genuinely must wait has somewhere to wait.
~clawt_ipc_server_defer()~ claims the right to answer later: the handler
returns NULL and ~clawt_ipc_pending_respond()~ sends the frame when the
work finishes.  The dispatcher already tolerated a NULL reply, so it is a
few dozen lines rather than a protocol change, and it is what lets the
health check, the Matrix calls and the connector flows do real network
work.  Measured: a health check against a blackholed address took the
full ten seconds while ~agent list~ answered in 16ms.

The token holds a reference to the client, which is already refcounted
for exactly this reason, so a connection that closes mid-flight is still
there to be answered into and simply drops it.

*** The one thing the daemon does on another thread

Starting an agent's *computer*.  Everything else -- the agent manager,
the config, the workspace files, the child process -- stays on the one
context; only ~clawt_computer_start()~ is handed to a worker, and only
from ~daemon_start_agent_async()~.

It is there because it is the single step that waits on somebody else's
socket: a podman API request per container agent, a libvirt round trip
per VM.  Held on the main thread it is not slow, it is *fatal to the
loop* -- and clawtilla learned that twice over.

Autostart originally ran inside ~clawt_daemon_start()~, which is called
before any main loop exists.  On a fleet of ~30 container agents the
daemon sat in there for minutes, and for that whole window it answered
no IPC frame and dispatched no signal source: ~clawtilla agent list~
hung with no reply and no error, ~kill -TERM~ did nothing because the
handler could not run, and ~systemctl --user stop~ timed out, escalated
to ~SIGABRT~ and dumped core -- so the agents were ~SIGKILL~ed rather
than stopped.

Moving it to an idle source fixes *when* the fleet is started and not
*where* the waiting happens.  An idle that called the blocking start
directly still held the loop for the length of each request, which
against a podman socket that accepted and went quiet is a minute per
agent -- the same three symptoms, from a version that looks fixed.
Both halves are needed, which is why
~/daemon/loop-runs-while-a-computer-provisions~ asserts on an unrelated
timeout source still being dispatched rather than on anything about the
agent.

The split is ~start_agent_prepare()~ / ~start_agent_launch()~, with the
computer between them.  ~clawt_daemon_start_agent()~ runs all three in
a row and stays blocking on purpose: every caller of *that* one has
somebody waiting on the answer, and for a single agent the wait is
bounded by podomation's ~request_timeout_seconds~.

Two consequences worth keeping in mind when touching this:

- ~g_task_new()~ captures ~g_main_context_ref_thread_default()~, and
  *dispatching a source does not make its context thread-default*.  A
  task created inside the autostart idle therefore takes the process
  default and completes on a loop the daemon may never run.  The context
  is pushed explicitly around the ~g_task_new()~ call.
- The launch half takes an *agent id*, not an agent.  The main loop has
  run between the two halves -- that is the entire point -- so a client
  is free to have removed the agent in the meantime.

** How clawtilla and libreclaw divide up

| Concern | Whose |
|---------+-------|
| One agent's model, session, tools, channels | libreclaw |
| Which agents exist, and what each one is | clawtilla |
| An agent's credentials and environment | clawtilla renders, libreclaw consumes |
| Messages between agents | clawtilla |
| Messages between an agent and the outside world | libreclaw's channels |
| Recursion, rate and cost limits across agents | clawtilla |
| Containers and VMs | clawtilla, via podomation |

~clawtilla.yaml~ is the source of truth.  The daemon renders each agent's
libreclaw ~config.yaml~ from it, deterministically, on every start and
reload.  That file carries a header saying so, because the natural thing
to do with a config file is edit it and every edit there is silently
lost.

Anything clawtilla does not model passes through: an agent's
~libreclaw:~ block is copied into the rendered file verbatim, so a
libreclaw option clawtilla has never heard of is still reachable without
waiting for a clawtilla release.

** The transport between them

libreclaw gained an ~LcClawtillaChannel~ in 0.26.0.  It dials *out* to
the daemon's socket.  That direction is deliberate: an agent running in a
container, a VM or on another host has no reachable port, and giving
every agent one would mean allocating and tracking a port per agent for
no benefit.  Dialling out needs nothing but a socket path.

The wire format is libreclaw's existing bridge protocol, so this is a
transport rather than a second protocol to keep in step.

Authentication is two layers: the socket is 0600, so only the owner can
connect at all; and each agent presents a token from a file only it and
the daemon can read, which stops one of your own agents claiming to be
another and reading its mail.

** Events

Everything that happens is published on ~ClawtEventBus~ with a sequence
number.  Clients subscribe with a cursor and are told whether the replay
was complete -- a client that silently receives a partial replay carries
the hole for the rest of its life and shows stale state it has no way to
notice.

~ClawtEventLog~ tees the same events to NDJSON on disk, one file per UTC
day, mode 0600.  Secrets are scrubbed *on write*, not at display time:
transcripts get replayed into every context rebuild, so redacting only
when showing them leaves the leak permanent.

** Reading order in the source

#+begin_example
src/
  clawt-enums.h        every enum, with the reasoning in the doc comments
  clawt-error.h        one domain, and what each code means
  clawt-util.h         path expansion, socket-path limits, context helpers
  config/              the schema table is the single source of truth
  link/                agents dial in here
  ipc/                 clients connect here, and the client library
  mailbox/             the durable queue, and the router that fills it
  agent/               agents, their runtimes, teams and workspaces
  computer/            the five backends, mounts, confinement, cloud images
  chat/                rooms, messages, loop safety, markdown, export
  memory/              an agent's own searchable store
  decision/            questions an agent needs a person to answer
  usage/               what a fleet has spent
  task/                delegated work, and cron and routines
  integration/         how an agent reaches the world, and connectors
  mcp/                 the tools agents get, and the relay in front of them
  core/                events, the log, and ClawtDaemon assembling it all
  plugin/, interfaces/ third-party extensions, and podomation
  ai/                  the agent designer and the model catalogue
#+end_example

That is roughly bottom-up: each layer only knows about the ones above it
in the list.  ~core/~ is next to last because ~ClawtDaemon~ knows about
everything -- it is the assembly, and reading it first is reading a list
of names.

Two files carry more of the reasoning than their size suggests.
~integration/clawt-connector-relay.c~ is where a credential is used
without being handed over, and its header says exactly what that is and
is not worth depending on where the agent runs.
~computer/clawt-guest-desktop.c~ holds the per-distribution table for
building a GNOME session inside a VM, and every entry in it exists
because getting it wrong fails inside a guest rather than here.
