* Connectors

A connector is an account on some service -- GitHub, a GitLab you run
yourself, a calendar -- that clawtilla holds the credential for.  Agents
get the service's tools.  They never get the token.

That distinction is the whole feature.  An ~mcp~ integration's
environment is resolved into the agent's =.mcp.json=, which is fine for
a key you chose to hand it and much less fine for an authorization on
your own account: the agent can read that file, and anything it reads
can end up quoted into a message or an exported transcript.  A
connector's =.mcp.json= entry carries no secret at all.

#+begin_src bash
clawtilla connector catalog
clawtilla connector add gh --provider github --account work \
    --command github-mcp-server --scope all
clawtilla connector key gh
#+end_src

That last command reads a token from stdin with the echo off.  There is
deliberately no =--key= flag: an argument is in your shell history and
in the process table for anybody on the machine to read.

** What it actually protects against

Worth stating plainly, because the answer depends on where the agent
runs and overstating it would be worse than not having it.

For a *container or VM agent* the boundary is real.  The token file and
the relay are on the host; the agent is not.  It can call the tools and
cannot reach the credential, in the way an ordinary user cannot read
another user's files.

For an *unconfined host agent* it prevents the credential leaking by
accident, which is the failure that actually happens: it is not in
=.mcp.json=, not in the agent's environment, not in the process table,
not in its transcript.  It does not stop an agent that goes looking,
because it runs as the same user and =secrets.dir= is right there.
Confinement is what makes that airtight -- see [[file:computers.org][computers.org]] and
[[file:security.org][security.org]].

For a *confined host agent* (~runtime.confine: bwrap~) the relay runs in
the agent's box, started by its CLI, so the box binds -- read-only, one
by one -- the credential of each connector the agent holds, and nothing
else of =secrets.dir=.  The agent can read its own connectors'
credentials, as an unconfined one can; it cannot read another agent's,
an ungranted connector's, the OAuth registrations or any other secret.
See [[file:security.org::*Connectors in a confined box][Connectors in a confined box]].

What it buys everywhere: one place to revoke, renewal that happens
before anything breaks, and a per-agent tool list.

*** Where the credential actually goes

Into a 0600 file under =secrets.dir=, and nowhere else: one directory
per connector, =secrets.dir/connectors/<name>/token.json=, the directory
0700.  A directory each, rather than the flat
=secrets.dir/connector-<name>.json= of earlier releases, because a
confined agent's box binds the directory: a bind of the file would go on
showing the token the box started with after the daemon renewed it.  The
daemon moves a flat file into its directory when it starts and points
~token_file~ at the new path; a ~token_file~ you wrote yourself is never
moved.  The agent's
=.mcp.json= names ~clawtilla connector relay <name>~ and carries no
secret; the relay reads that file *itself* and hands the value to the
tool server it starts.  There are exactly four places it must never
appear, and each is a different way it would leak:

| Not here                | Because                                     |
|-------------------------+---------------------------------------------|
| the agent's =.mcp.json= | the agent can read its own workspace, and anything it reads can be quoted into a message or an exported transcript |
| the agent's environment | it is inherited by everything the agent runs |
| an ~argv~               | =/proc/*/cmdline= is world-readable, so anybody on the machine can read it while the server runs |
| an IPC response         | it would put a live credential into every client's memory, and into whatever that client logs |

The plan the relay builds -- ~ClawtConnectorPlan~ -- is tested with a
*negative* assertion: the credential must be in ~envp~ or in a header,
and nowhere in ~argv~.  That is not something you can see by reading the
code that builds the argv; it is something you see by looking for the
value in the result.

The relay also closes the child's stdin when the agent's CLI goes away.
A stdio MCP server exits when its stdin closes and nothing else tells it
to, so waiting for both directions left an abandoned process holding a
live credential indefinitely.

A remote (HTTP) connector's requests never follow a redirect, because the credential is a request header and libsoup would carry it to whatever host the server named. A tool server that answers with one gets the relay's error instead -- ~clawtilla: the request to the tool server failed: https://mcp.example answered 307, a redirect to https://other.example; ...~ -- and the fix is to set the connector's ~url~ to the address it names. See [[file:security.org::*A credential never follows a redirect][A credential never follows a redirect]].

** How a credential is obtained

Three ways, and the catalogue says which apply to a given service.

*** A token you already have

The simplest, and often the best.  A personal access token works as well
as an authorization and needs no application registered with anybody:

#+begin_src bash
clawtilla connector key gh
#+end_src

*** The device flow

The one that suits a daemon.  No redirect URI, no listening socket, no
browser on the same machine: clawtilla asks for a code, you type it into
a page on whatever device you are holding, and clawtilla polls until you
have.  A workstation you reached over SSH can be connected from a phone.

#+begin_src bash
clawtilla connector add gl --provider gitlab --client-id abc123
#+end_src

#+begin_example
    WDJB-MJHT

Enter that at https://gitlab.com/oauth/authorize_device

Waiting...
Connected.
#+end_example

*The normal case for a poll is an HTTP 400.*  A provider asked about a
code nobody has typed yet answers =400 Bad Request= with
~{"error": "authorization_pending"}~ in the body -- so a client that
reads the status and gives up has built a device flow that can never
once succeed, while looking entirely correct.  clawtilla never looks at
the status here: ~clawt_oauth_read_poll()~ classifies the *body*, and it
is a pure function so the classification can be tested without a
provider.

~slow_down~ lengthens the interval *permanently*.  A provider that has
asked once to be polled less often will ask again, and reverting after a
single slower poll spends the rest of the flow rate limited -- while the
person is standing at the consent screen wondering why nothing happened.

Two frames rather than one, for the same reason: ~connector.begin~
answers as soon as there is a code to show, and ~connector.await~ is the
one that waits.  A device code is good for about fifteen minutes and the
ordinary client timeout is two, so waiting takes an explicit longer
deadline -- and deferring the whole thing would mean showing the person
nothing until it was over.

*** Authorization code with PKCE

For the many services that never implemented device grant.  It costs a
loopback listener and a redirect URI registered with the provider in
advance, which is why it is second choice.  Register
=http://127.0.0.1:8765/callback=, or whatever ~connectors.redirect_port~
says.

The listener binds 127.0.0.1 only.  A redirect carries an authorization
code in a URL, and a listener on every interface offers that code to
whoever on the network reaches the port first.

*** Signing in where the server says

For a remote MCP server, the URL is all a connector needs:

#+begin_src bash
clawtilla connector add notion --url https://mcp.notion.com/mcp
#+end_src

#+begin_example
Added connector 'notion'.
It signs in at https://auth.notion.example.
Signing in at https://auth.notion.example

Open this to approve:
    https://auth.notion.example/authorize?response_type=code&...
#+end_example

A URL with no ~--provider~ is the built-in ~remote~ entry (the first in every client's list).  Its catalogue entry names no endpoints, so the sign-in is asked of the server, the way the MCP authorization spec lays out:

1. *Where is the authorization server?*  The server's RFC 9728 protected-resource document -- at the address a 401's ~WWW-Authenticate: Bearer resource_metadata="..."~ names, or at =/.well-known/oauth-protected-resource= with the server's path and then without -- lists its authorization servers.  A server that publishes none is assumed to be its own, at its origin, as clients of the 2025-03-26 spec did.
2. *What are its endpoints?*  The authorization server's RFC 8414 metadata (=/.well-known/oauth-authorization-server=, then OpenID Connect's =/.well-known/openid-configuration=) names the authorization, token, registration and revocation endpoints.
3. *Who is asking?*  With no ~client_id~ configured, clawtilla registers itself by RFC 7591 dynamic client registration, as a public client (~token_endpoint_auth_method: none~ where the server takes it; otherwise ~client_secret_post~ when offered, else ~client_secret_basic~, and the token endpoint is then sent the client's credentials as HTTP Basic -- whatever the registration reply says it granted wins) whose one redirect is =http://127.0.0.1:<connectors.redirect_port>/callback=, named ~connectors.client_name~ on the consent screen.  The registered id -- and a secret, if the server issues one -- is kept in =secrets.dir=/connector-auth/<name>.json at 0600 and reused for every sign-in after.
4. *Sign in.*  Authorization code with PKCE (S256, refused otherwise) and the RFC 8707 ~resource~ parameter set to the server's URL on the authorization request, the exchange and every renewal, so the token is good for this server and no other the authorization server fronts.

Three things win over anything a server publishes, because each is a decision somebody made: a catalogue entry that names ~auth_url~ and ~token_url~ (every built-in OAuth provider does), a ~client_id~ on the integration, and ~connectors.discovery: false~, which turns the whole chain off.  ~clawt_mcp_auth_plan()~ is that decision as a pure function, and =tests/test-mcp-auth.c= walks it.

Discovery happens when somebody asks for a sign-in -- ~connector connect~, the Sign in button, or adding a connector by URL in any client, which asks straight away -- and never at daemon start.  To ask without signing in:

#+begin_src bash
clawtilla connector discover notion
#+end_src

#+begin_example
Signs in at https://auth.notion.example (protected-resource); clawtilla can register itself there.
Run `clawtilla connector connect notion` to sign in.
#+end_example

A server that publishes no sign-in is not an error: most MCP servers take a key, and the answer says so -- paste one with ~clawtilla connector key~.

**** What it refuses

Every URL in the chain came from the remote server, so:

- *no leg follows a redirect*, not even the metadata fetches;
- *nothing is plain http* unless it is on loopback and the configured server is on loopback too -- a public server's 401 pointing at =http://127.0.0.1:...= is refused rather than fetched;
- *a document about somebody else is refused*: a protected-resource document describing another server, metadata whose ~issuer~ is not the one it was fetched for, and a server with no PKCE S256;
- *a document over 64 KiB is refused* while it is being read.

[[file:security.org::*Signing in where the server says][security.org]] has the reasoning for each.

**** When the server says no: a 401

A remote server that has not been signed in to -- or whose sign-in expired or was withdrawn -- answers 401, sometimes only for ~tools/call~ after it listed its tools to anybody.  The relay answers that itself instead of passing it to the agent's CLI, which would start a sign-in of its own that cannot work and then report only that the server failed.  The agent reads a failed tool result:

#+begin_example
The connector 'notion' needs a sign-in before its tools work (HTTP 401), and nobody has signed in yet, so nothing ran. Do not retry. Ask the person to sign in to 'notion' -- `clawtilla connector connect notion`, or Sign in on its row under Settings, Connectors.
#+end_example

and the relay tells the daemon (~connector.unauthorized~), which records it, keeps the 401's ~resource_metadata~ hint for the sign-in, and announces ~integration.changed~.  From then on every client's connector row says it needs a sign-in, its actions start with *Sign in at <host>*, and ~clawtilla connector list~ prints ~sign in needed~.  A successful sign-in clears it.

A remote connector with no credential at all still gets a relay -- plenty of servers list their tools to anybody -- so its first refused call is what asks for the sign-in.  A stdio server is refused at start instead, because it has nowhere to say so.

** Several accounts on one service

Work and personal GitHub, two GitLab groups: several accounts on one service are the ordinary case, and every one is its own connector with its own token file.

#+begin_src bash
clawtilla connector add gh-work --provider github --account work \
    --command github-mcp-server --scope all
clawtilla connector add gh-home --provider github --account personal \
    --command github-mcp-server --scope all
#+end_src

*** What happened before

Checked rather than assumed.  Each connector is its own =.mcp.json= entry (~clawtilla-gh-work~, ~clawtilla-gh-home~) and its own relay process, so the agent's CLI kept the two servers apart: Claude Code named the tools ~mcp__clawtilla-gh-work__create_issue~ and ~mcp__clawtilla-gh-home__create_issue~, and nothing was silently routed to the first.  But the tool names *inside* were identical -- ~create_issue~ twice -- and the only difference was a server name the operator chose, which may not mention the account at all.  That is what a model reads when it picks a tool, what an action rule matches and what a decision card names; an agent told to "open an issue" picked whichever ~create_issue~ it saw first, and nothing made it say which account it meant.

*** What happens now

When an agent holds more than one account on the same ~provider~ (whatever the instance -- two GitLabs have identical tool names too), each relay renames its account's tools with the account's label and says so in each description:

| Account    | The server's tool | What the agent sees                                    |
|------------+-------------------+--------------------------------------------------------|
| ~work~     | ~create_issue~    | ~work_create_issue~ -- "[work account] Open an issue"  |
| ~personal~ | ~create_issue~    | ~personal_create_issue~ -- "[personal account] ..."    |

A call to the bare ~create_issue~ is *refused*, naming the accounts and the prefixed name to call -- never run as whichever account it reached, because that is the guess this exists to take away.  The prefix comes off before the tool list and the action rules see the call, so ~tools:~ and rules keep naming the server's own tools.  A service the agent holds one account on is not renamed at all, and the agent's =TOOLS.org= says which of its connectors are prefixed and why.

The prefix is part of the relay's one policy (~ClawtMcpRelayPolicy~), so the stdio relay and the HTTP bridge apply it identically: outermost on both sides, before the tool directory on the way out and after it on the way back.  An account presented as a directory (see "Servers with many tools") has its three tools named for the account -- ~work_search_tools~, ~work_describe_tool~, ~work_call_tool~ -- and every tool name it shows in a search or a describe carries the same prefix the flat list of the other account does: ~work_issues_create~ there, ~personal_issues_create~ here.  ~work_call_tool~ takes either the prefixed or the bare name (the account is already chosen), refuses the other account's, and sends the server its own.

The label is the connector's ~account~, folded to lowercase letters, digits and underscores; an account with no label is named for its integration name.  Two labels that fold to the same prefix (~Work~ and ~work!~) are two accounts nobody can tell apart, so every call on both is refused with a message naming both connectors -- not routed to whichever registered first.  Both relays reach the same answer independently, from ~clawt_connector_account_prefix()~.

*** Every new account carries a unique label

Adding a second account on a service without a label, or with one another account on that service already folds to, is refused where it arrives:

#+begin_example
clawtilla: there is already a github account here ('gh-work'); give this one an account label, such as work or personal, so the two can be told apart
#+end_example

The first account may go without; it has nothing to be told apart from yet, and its prefix falls back to its name if a second arrives.  A configuration written before this rule keeps loading: the check is on *adding*, never on reading.  Every client shows the label on the connector's row (~github -- work~), and the add form says it is required for a second account.

Disconnecting is per row: ~revoke~ and ~rm~ act on the one connector named, and a new sign-in on one account never touches another's token file.

** Client IDs

clawtilla ships none, and will not.  It has no OAuth application of its
own to lend, and borrowing another project's would mean every clawtilla
in the world identifying itself as something it is not.

Registering one takes a few minutes per provider.
=clawtilla connector catalog= names where for each, and the
~client_id_help~ field is repeated in the error you get if you try to
authorize without one.

If that is friction you do not want, paste a token instead.  It is not
a lesser option.

** The catalogue

Two things at once: a table compiled into the library covering the
services people reach for, and a directory of YAML files that adds to it
and overrides it.

#+begin_src bash
clawtilla connector catalog
#+end_src

These are somebody else's URLs and somebody else's scopes.  A copy of
them in C goes stale silently and in the wrong direction, so a provider
that moves an endpoint should be fixable by editing a file rather than
by waiting for a clawtilla release.  Drop one in
=$XDG_CONFIG_HOME/clawtilla/connectors.d/=:

#+begin_src yaml
connectors:
  - id: acme
    name: Acme
    summary: Tickets and deployments
    category: Work
    auth: api_key            # none | device | pkce | api_key
    server_command: acme-mcp
    server_args: [stdio]
    placement: env           # env | header
    credential_name: ACME_API_KEY
#+end_src

An entry whose ~id~ matches a built-in one *replaces* it rather than
merging into it.  Half an override -- a new token endpoint against an old
authorization endpoint -- is a combination nobody wrote down, and it
fails pointing at neither file.

A file that will not parse is a warning naming the file, not a failure:
a typo in one connector must not take away the others, and this is read
on the path that starts the daemon.

*** Self-hosted services

A connector with a ~default_instance~ is one you may run yourself, and
its endpoint fields are read as *paths* joined onto whichever instance
the configuration names:

#+begin_src bash
clawtilla connector add work --provider gitlab \
    --instance https://gitlab.example.com --client-id abc123
#+end_src

A host with no scheme gets =https=.  Somebody who typed a bare hostname
did not mean to send an OAuth exchange in the clear.

*** The two generic entries

~api-key~ and ~bearer~ exist so the catalogue is open rather than
closed.  Most MCP servers are not behind OAuth at all -- they want a key
from a dashboard in an environment variable, or a bearer token on an
HTTP endpoint -- and those are worth brokering for exactly the same
reason.  Override ~credential_name~ per instance and one entry covers
every such service.

#+begin_src bash
clawtilla connector add weather --provider api-key \
    --command weather-mcp --credential-name OPENWEATHER_KEY
#+end_src

** VENTURE, and the writes it holds back

VENTURE is an ERP and CRM you run yourself -- sales, expenses,
invoices, tickets, contacts, a ledger -- and it is the one built-in
connector that is *yours* rather than somebody else's service.  It is
compiled in rather than shipped as a pack in =connectors.dir= for
exactly that reason: a fleet that runs VENTURE should reach it out of
the box, and an entry somebody has to copy into a directory before
anything works is an entry most people never find.

#+begin_src bash
clawtilla connector add books --provider venture \
    --instance https://books.example
#+end_src

=default_instance= is =http://localhost:8747=, so a fleet on the same
machine needs no =--instance= at all.

*** The credential is a token you mint yourself

Sign in to VENTURE's web UI and create an API token.  =POST
/api/v1/tokens= returns the plaintext exactly once and stores only its
hash, so copy it then -- there is no way to read it back afterwards, by
design.

clawtilla keeps it in a 0600 file under =secrets.dir= and injects it
into the tool server's environment as =VENTURE_TOKEN=.  It never
reaches the agent's =.mcp.json=, its argument vector or its transcript.
=VENTURE_URL= goes in beside it, because =venturectl mcp= is a separate
program with its own default of localhost and has no other way to learn
which instance it was pointed at.

*** The tools are generated from VENTURE's own schema

=venturectl mcp= fetches =GET /api/v1/schema= at startup and builds its
tools from what came back.  Nothing in its C names a record type, so a
type a plugin registers appears in the =type= enumeration of every tool
that takes one, with no release anywhere.

That is why the catalogue can write the tool list down at all.  There
are nineteen, and they are verbs:

| Tool                      | What it does                                                |
|---------------------------+-------------------------------------------------------------|
| =venture_schema=          | the record types, or one of them in full                    |
| =venture_list=            | list records of a type, filtered                            |
| =venture_get=             | fetch one by id                                             |
| =venture_create=          | create one                                                  |
| =venture_update=          | change named fields of one                                  |
| =venture_delete=          | soft-delete one                                             |
| =venture_reports=         | what reports there are                                      |
| =venture_report=          | run one                                                     |
| =venture_confirmations=   | list, approve or reject what is waiting                     |
| =venture_modules=         | which modules the server runs, and why any is off           |
| =venture_links=           | every link touching one record                              |
| =venture_link=            | link two records; staged like a create                      |
| =venture_dashboards=      | the dashboards, the widget kinds, or the templates          |
| =venture_dashboard=       | one dashboard, evaluated, or its settings or definition     |
| =venture_dashboard_build= | make one from a template or a definition                    |
| =venture_factory=         | the release factory: status, actions, readiness, forecast, changelog, deploy, rollback, publish |
| =venture_inbox=           | the token's own inbox; mark a notification read             |
| =venture_runs=            | the coding runs with cost, or the budgets                   |
| =venture_desk=            | a ticket's clocks, timelines, sprints, triage, summaries, worklogs, macros |

The list is VENTURE's =docs/mcp.org= table and =tests/test-venture.c=
pins it, so a tool renamed upstream fails there.  The writes among the
last ten that are several records at once (a dashboard build, a macro,
a release publish) refuse while staging is on and say which single
writes would propose the same thing; see VENTURE's docs.

They are the entry's =known_tools=, so a =tools:= narrowing that
misspells one is a warning naming it rather than an agent silently
left with nothing.  A tool per record type would be 31 built-in types
times five verbs in every context window, and would be a second copy of
VENTURE's data model besides.

*** One token is one actor

The =connector= integration type declares no identity keys because a
shared account is usually the point.  This entry declares =token_file=,
and the reason is VENTURE's audit trail: every change records who made
it and how, which is what distinguishes an automation's write from a
person's from the AI's.  Two agents holding one token are one name in
every row they write.

So a shared instance covering two agents is reported by
=clawtilla integration list=, with a message that says what it costs.
Give each its own under =per_agent=:

#+begin_src yaml
integrations:
  - name: books
    type: connector
    provider: venture
    scope: selected
    agents: [bookkeeper, analyst]
    instance: "https://books.example"
    per_agent:
      bookkeeper:
        token_file: "~/.clawtilla/secrets/connector-books-bookkeeper.json"
      analyst:
        token_file: "~/.clawtilla/secrets/connector-books-analyst.json"
#+end_src

** Staged writes land in the decision inbox

=venturectl mcp= stages its writes by default: =venture_create=,
=venture_update= and =venture_delete= send the change with =?stage=1=,
and VENTURE builds and validates the record exactly as it would for a
direct write, holds it, and answers =202= with a confirmation.  Nothing
is in the books until somebody says so.

Without a bridge, "somebody says so" means opening VENTURE's own web
interface and finding the card.  So clawtilla polls
=GET /api/v1/confirmations= while a venture connector is bound and
turns each pending change into an ordinary ~ClawtDecision~ -- answerable
from the GTK client, the web client, or ~clawtilla decision~ over ssh,
beside every other thing an agent is waiting on you for.

#+begin_src
$ clawtilla decision list
venture-books-a3f9c118  bookkeeper
  books-agent wants to Create expense "Cover art" (via the 'books'
  connector).

  Record type: expense

  What would change:
    description: Cover art
    amount: {"amount":25000,"currency":"USD"}

  VENTURE drops this card unanswered at 2026-08-29T15:02:11Z.

  approve / reject   (default: reject)

$ clawtilla decision answer venture-books-a3f9c118 approve
#+end_src

Answering posts to =/api/v1/confirmations/<id>/approve= or =/reject=.

*** The fields are used honestly

The *question* is the staged change as VENTURE summarised it, with the
diff rendered underneath so it can be answered without opening
VENTURE at all.  The card is deliberately self-contained upstream, for
this reader.

The *default* is =reject=, and that is a description rather than a
policy: VENTURE drops a card nobody answers when its own confirmation TTL
runs out (an hour by default), so leaving it is the same as rejecting
it.

=reversible_until= stays *unset*.  Nothing is written until an approval,
so there is nothing to reverse -- and after one, VENTURE's soft delete
is the undo.  A deadline invented here would be a promise clawtilla
cannot keep, and the inbox reads a deadline as pressure.

An answer that is not recognisably an approval is a rejection.  A
=ClawtDecision= carries free text because an operator whose answer is
"neither, do X" is giving the most useful answer there is; VENTURE has
only two endpoints, and a misread "yes" writes to somebody's books
while a misread "no" leaves a card to answer again.

*** Polling, and what it costs

The confirmation queue has no change stream out of VENTURE, so this is
a poll -- on a timer attached to the daemon's context, never from a
request handler and never during daemon start.  The first poll is one
interval after the daemon comes up.

| Key                            | Default | What it does                             |
|--------------------------------+---------+------------------------------------------|
| =integrations.confirm_writes=  | =true=  | whether clawtilla polls this connector   |
| =integrations.poll_seconds=    | =60=    | how long between polls                   |

One timer covers every venture connector, so the shortest interval
anybody asked for is the one that runs.  A fleet with no venture
connector arms no timer at all.

=integrations.confirm_writes= does not switch staging on -- =venturectl
mcp= decides that for itself and stages by default.  Turning it off
here stops clawtilla polling, which leaves the staged changes in
VENTURE for somebody to find in its own web interface.

*** Whether the server stages at all

The first poll of each connector also asks =GET /api/v1/health=.  A
VENTURE too old for =?stage=1= *ignores* the parameter and applies the
write, answering as if all was well -- so a bridge that only read the
queue would show an empty inbox while the books changed underneath it.
When the answer lacks =staged_writes: true= the daemon warns once, and
the connector's health check (the row in every client, and ~clawtilla
integration check~) turns red with "this VENTURE server does not stage
writes".  A probe that could not reach the server is asked again on the
next poll rather than remembered as "does not stage".

A confirmation already raised is matched on its own id, so the same
card polled every minute for an hour is one decision, not sixty.  The
match is against the decision store rather than a set held in memory,
so a daemon that restarted does not raise everything again.

*** An answer is owed until it lands

A POST that fails is *kept* and retried on the next poll.  The operator
answered once and has no reason to look again; an answer that vanished
would leave the change waiting in VENTURE until its TTL dropped it, and
nobody would ever know.

That survives a restart too, and not because the queue is durable -- it
is not.  VENTURE still holding the card is itself the proof that the
answer never landed, so a card still pending against a decision the
store says was *answered* is queued again from what the store
remembers.

Dismissing a decision is left alone on purpose.  "I am not deciding
this" is not an answer to post, and VENTURE drops the card on its own
clock.

*** Telling an agent that a record changed

The bridge is a pull in the other direction: clawtilla asks VENTURE
what is waiting.  For a push -- "tell the bookkeeper when an invoice is
paid" -- VENTURE sends signed webhooks, and =provider: venture= on a
trigger verifies them, fills ={{kind}}=, ={{number}}=, ={{title}}= and
={{actor}}= from the envelope, ignores the agent's own writes with
=ignore_actors=, and catches up on the durable business-event lane
through this connector's token with =replay_connector=.  See
[[file:triggers.org::*Telling an agent that a VENTURE record changed][Triggers]].

*** What is still not done

- *A card cannot say which agent staged it.*  Several agents sharing one
  token are one actor to VENTURE, so the first agent in fleet order owns
  every card.  The fleet warns about the shared token for that reason.
- *The answer queue is in memory.*  Recovery after a restart relies on
  VENTURE still holding the card, which it does until its TTL.
- *VENTURE's inbox and coding runs are not alerts here.*  An agent can
  read them with =venture_inbox= and =venture_runs=; clawtilla does not
  poll them into its own alerts panel.

** The open MCP registry

The catalogue above is somebody's opinion, checked in.  The registry at
https://registry.modelcontextprotocol.io is nobody's opinion -- it is
whatever anybody has published -- so it is imported at a lower standard
of trust: an entry from it only ever *fills a gap*.  It never replaces a
built-in connector or one from ~connectors.dir~, both of which are a
choice somebody already made on purpose, and its ids are all prefixed
~registry:~ so one could never collide with a curated id even if it tried.

#+begin_src yaml
connectors:
  registry_enabled: true
#+end_src

Off by default, because turning it on is the one thing in this file that
reaches the network.  When it is on, the import happens on a timer of its
own -- never at daemon start, never inside the handler answering a
client's request -- into a cache under the daemon's state directory.
~connector.registry_refresh~ (~clawtilla connector registry-refresh~, or
the button on the Connectors page in either client) asks for one sooner
than ~connectors.registry_refresh_hours~ would.

#+begin_src bash
clawtilla connector registry-refresh
#+end_src

*** Why this is safe to leave off, and safe to test

~make test~ opens no network socket, which means nothing here is allowed
to either.  The importer is split so that only one function --
~clawt_connector_registry_refresh_async()~ -- ever calls out, and it is
never invoked by anything the test suite runs.  Everything the suite
*does* exercise is a pure function over a fixture: parsing one page of
the registry's own JSON shape, merging entries into a catalogue, and
reading or writing the cache file. That split is the same reasoning
CLAUDE.md already records against ~model.list~, which once asked five
provider APIs from an IPC handler and made pressing a button in the GTK
client feel like it had hung.

*** What an imported entry actually knows

The registry describes a server's *package* (an npm identifier, a
runtime hint like ~npx~ or ~docker~, and the environment variables it
needs) or its *remote* (a plain HTTP or SSE URL) -- never a client id,
and rarely anything OAuth-shaped.  So an imported connector is
~auth: api_key~ whenever a package names a secret environment variable,
and its credential name comes from the registry entry itself rather than
a guess.  A package naming no runtime hint clawtilla recognises falls
back to running its identifier as a bare command on ~PATH~, which is
right for a Rust or Go binary and wrong for an npm package that needs
~npx~ -- the registry does not say which its identifier is, and this file
is not going to guess twice.

** FOSS connector packs

Most of the catalogue's OAuth entries are commercial services.  The
things an operator running their own infrastructure actually reaches for
-- a Forgejo, a Home Assistant, a Grafana -- are shipped as example YAML
files under ~data/connectors.d/~ in the source tree, one per service,
ready to copy into ~connectors.dir~:

#+begin_src bash
cp data/connectors.d/gitlab.yaml $XDG_CONFIG_HOME/clawtilla/connectors.d/
#+end_src

They are examples on purpose and not installed automatically: a person's
own ~connectors.dir~ is theirs, and an upgrade silently adding entries to
it would be indistinguishable from a person's own file mysteriously
gaining content.

| Pack                | What it adds beyond a bare credential            |
|----------------------+---------------------------------------------------|
| ~gitlab.yaml~        | GitLab's own MCP server, ~/api/v4/mcp~ on your instance, once Duo is licensed |
| ~gitea.yaml~         | OAuth2, the same endpoints Forgejo forked from    |
| ~matrix.yaml~        | Tool access to a Matrix account -- see below      |
| ~home-assistant.yaml~ | A long-lived access token's variable name        |
| ~grafana.yaml~       | A service account token's variable name           |
| ~nextcloud.yaml~     | An app password's variable name                   |
| ~jellyfin.yaml~      | An API key's variable name                        |
| ~immich.yaml~        | An API key's variable name                        |
| ~paperless-ngx.yaml~ | A token's variable name                           |
| ~miniflux.yaml~      | An API key's variable name                        |
| ~vaultwarden.yaml~   | The OAuth2 client secret's variable name           |

*** Why most of these have no ~server_command~

The built-in table's own header comment gives the rule: no
~server_command~ unless the provider genuinely ships one under a name
stable enough to survive a release cycle.  As of this writing, GitLab is
the only one of these eleven with an MCP server run by the service
itself; every other one is either a community project with several
competing, sometimes explicitly unstable implementations (Forgejo,
Gitea, Vaultwarden), or a service whose official server runs three
different ways with three different invocations (Grafana's binary,
~uvx~, or Docker) such that naming one would be wrong for the other two.

That is not a gap in the pack -- the credential half is the hard,
fact-checkable part, and it is what these files get right.  Once you have
picked a server, name it on your own integration and it wins over
anything a pack or the built-in table says:

#+begin_src bash
clawtilla connector add gt --provider gitea \
    --command gitea-mcp-server --scope all
#+end_src

*** Matrix, twice

~matrix.yaml~'s ~id: matrix~ is a *connector* -- a tool an existing
session can call to read or post into rooms as an account you already
hold.  It has nothing to do with ~type: matrix~ in ~integrations.yaml~,
which gives an agent a chat identity of its own and is a completely
different feature that happens to share a name for the service, not for
the integration kind.  The two ids live in different tables (~provider:~
values under ~type: connector~, versus top-level ~type:~ values) and
cannot collide, but a person skimming the config could still read one for
the other, which is why it is spelled out here.

*** Writing your own pack

The template is every field ~clawt_connector_catalog_load()~ reads,
named:

#+begin_src yaml
connectors:
  - id: my-service            # required, lowercase, stable
    name: My Service          # shown in a list; defaults to id
    summary: One line about what connecting it gets you
    category: Whatever groups it in a list
    auth: api_key              # none | device | pkce | api_key
    auth_url: /oauth/authorize # device or pkce only
    token_url: /oauth/token    # device or pkce only
    revoke_url: /oauth/revoke  # optional
    scopes: "read write"       # what to request by default
    client_id_help: where to register an application
    docs_url: https://example.com/docs/auth
    default_instance: https://my-service.example  # only if self-hostable
    server_command: my-service-mcp  # only if genuinely stable -- see above
    server_args: [stdio]
    server_url: /mcp                # instead of server_command
    known_tools: [list_things, get_thing]  # what the server offers, if known
    placement: header           # env | header
    credential_name: Authorization
    credential_format: "Bearer %s"  # exactly one %s, or omit entirely
#+end_src

Three things worth getting right the first time:

- *One rule for every URL field.*  Setting ~default_instance~ makes
  ~auth_url~, ~token_url~, ~revoke_url~ *and* ~server_url~ all read as
  paths, joined onto whichever ~instance:~ the integration names.
  Leaving ~default_instance~ unset makes every one of them an absolute
  URL instead.  A pack that sets ~default_instance~ and then writes one
  field as an absolute URL anyway is how a connector quietly
  authenticates against somebody else's server -- ~gitlab.yaml~ is the
  worked example, and the test suite walks every shipped pack checking
  none of them do this.
- *~known_tools~ is optional and worth adding once you know it.*  An
  integration's own ~tools:~ narrows an agent to a subset; ~known_tools~
  is what the pack's author believes the *server* offers, so a typo in
  the former -- a tool name that is not in the latter -- gets a warning
  naming both, rather than silently narrowing an agent down to nothing.
- *~placement~ and the transport must agree.*  A ~server_url~ entry needs
  ~placement: header~, because there is nowhere else on an HTTP request
  for a credential to go; a ~server_command~ entry can use either,
  depending on what the server itself expects.  Setting ~server_url~
  with ~placement: env~ builds a plan with nothing in its header at all.

** Who gets it

The same three answers as any integration: one agent, some agents, or
the fleet.

#+begin_src bash
clawtilla connector add gh --provider github --scope all
clawtilla connector add gh --provider github --scope selected \
    --agents researcher,scribe
#+end_src

Sharing one connector across agents is the *point* of it, and unlike a
Matrix account there is nothing dangerous about it: a connector is a
credential the fleet reads through, not an identity two agents would
both answer as.

** Narrowing the tools

#+begin_src bash
clawtilla connector add gh --provider github --tools list_issues,get_file
#+end_src

Enforced in the relay, and enforced by *removal* rather than refusal: the
tools an agent may not use are taken out of its tool list rather than
rejected when called.  A tool that is advertised and then refused is
worse than one that was never there -- the agent plans around it, calls
it, and has to work out from an error that it never had it.

Leaving ~tools~ unset means every tool the server offers.  An empty list
is treated the same, rather than as a lockout nobody asked for.

** Servers with many tools

Every tool a server lists is read by the model on every call: its name,
its description and its input schema.  For a server with a dozen tools
that is the point of listing them.  For one with four hundred it is tens
of thousands of tokens spent before the agent has read a word of what it
was asked, on tools it will mostly never use -- and an API-model engine
refuses more than 128 tools a turn outright.

So the relay can present a big server as a *directory*: three tools that
stand in for all the others.

| Tool                        | What it does                                                        |
|-----------------------------+---------------------------------------------------------------------|
| ~<name>_search_tools~       | a few words in, the best matches out, each with a one-line description and its input fields; an empty query answers with what the server covers, area by area |
| ~<name>_describe_tool~      | one tool's exact description and input schema                       |
| ~<name>_call_tool~          | runs one tool by name, with its arguments                           |

~<name>~ is the connector's name, so a connector called ~forge~ offers
~forge_search_tools~, ~forge_describe_tool~ and ~forge_call_tool~.  The
search ranks with BM25 over each tool's name (counted double), its
description and the words in its schema, plus the tool's /area/ -- the
part of its name before the first underscore, so ~issues_create~ is in
~issues~.  A query that is a tool's exact name always finds that tool
first.

*** When a server is a directory

Each connector has a ~directory~ setting:

| Value    | Meaning                                                                    |
|----------+----------------------------------------------------------------------------|
| ~auto~   | a directory when the server is big *and* the agent's CLI does not search tools itself (the default) |
| ~always~ | a directory whatever its size and whatever the CLI                         |
| ~never~  | every tool listed, however many there are                                  |

"Big" is more than ~connectors.directory_min_tools~ tools (default 40)
or more than ~connectors.directory_min_chars~ characters of tool
definitions (default 100,000) -- names, descriptions and schemas
together, which is what the model actually reads.  Both are counted
/after/ the connector's ~tools:~ narrowing, because that is the list the
agent would otherwise get.

#+begin_src bash
clawtilla integration set forge directory=always
#+end_src

*** Which CLIs search tools themselves

Claude Code does: past about a tenth of its context in MCP tools it
defers them and looks them up as it needs them.  Wrapping its servers in
a second search would make it search a search, so under ~auto~ its
agents get every tool as before.  ~claude-tmux~ runs the same binary and
is answered the same way, and grok-build searches too.  Every other CLI
-- opencode, codex, antigravity, cursor -- reads the whole list on every
call, and gets the directory.

Whether a CLI searches is a fact about the CLI, and ai-glib states it as
a class datum beside ~AiCliClientClass.config_dir_env~:
~AiCliClientClass.searches_tools~ (ai-glib v0.11.0).
~clawt_mcp_directory_cli_searches_tools()~ builds a probe client through
libreclaw's factory and reads ~ai_cli_client_searches_tools()~ off it, so
a CLI that gains deferred tool loading needs no edit in clawtilla.

*** The search finds only what the agent may use

The directory is built from the tool list *after* the permitted-list
filter, and a call through it is checked against that same list again on
the way out.  The predicate and the builder answer from one list, so a
tool this agent may not use cannot be found by the search, is not
described, and cannot be run through ~<name>_call_tool~ -- the directory
answers "No tool named ... here" for it, in exactly the words it uses
for a tool that does not exist, so the search cannot be used to learn
what was withheld.

*** Approvals name the tool that runs

A call through the directory becomes an ordinary ~tools/call~ naming the
inner tool /before/ anything checks it.  The permitted list, an action
rule (~policy.check~) and an approval card therefore all see
~pulls_merge~, never ~forge_call_tool~.  A search or a describe runs
nothing on the server and asks nobody.

The same decision is made for a connector reached over HTTP.  Until this
release the HTTP bridge applied the permitted list and skipped the
action-rule gate entirely; both transports now go through one function,
~clawt_mcp_relay_policy_outbound()~.  A JSON-RPC batch is refused
whenever a gate or a directory is in the path, since either reads one
call per line and a batch would carry its calls past both.

*** Big tool lists arrive in pages

An MCP server may answer ~tools/list~ a page at a time.  When the relay
might present a directory it follows ~nextCursor~ itself and answers the
client once, with either the three directory tools or the whole list as
a single page.  It stops after 64 pages and says so on stderr.  When it
may not present one (~never~, or Claude Code under ~auto~) every page
passes through untouched and is only counted.

*** How big a server is, and where that shows

clawtilla never starts a connector's server itself -- the relay does, on
an agent's behalf, with the credential.  So the relay reports what it
saw to the daemon (~connector.tools_seen~) whenever a full tool list
arrives, and the daemon keeps the last report per connector in
=<state_dir>/connector-tools.yaml=.  That is what the Connectors page in
every client and =clawtilla connector list= show: the tool count, the
characters of definitions, and whether agents get the server as a
directory.  A connector no agent has used yet says its size is unknown,
never zero.

The agent's =TOOLS.org= describes a directory server as one: "search
it", with the three tool names and the area overview from that report.
It does not enumerate the tools, even a narrowed ~tools:~ list, since
listing four hundred names there would put back into every prompt the
text the directory exists to keep out.  Under ~auto~ a server no relay
has counted yet is described as a list; the agent's next start, after a
relay has seen it, says the right thing.

** Results bigger than the budget

A connector's tool can answer with megabytes -- a repository listing, a log, a search across a whole tracker -- and whatever it answers is read by the model on every later call of the turn.  One careless listing spends the context the rest of the work needed.  So the relay holds each connector to a /result budget/: the most of one tool result the agent is shown, in bytes.

| Key                                | Default  | What it does                                            |
|------------------------------------+----------+---------------------------------------------------------|
| =connectors.max_result_bytes=      | =65536=  | the budget for every connector that does not set one    |
| =integrations.max_result_bytes=    | =-1=     | this connector's own; -1 is the fleet's, 0 is no budget |

Anything below 1024 is read as 1024 -- below that the two notes would be most of what the agent reads.  ~clawt_mcp_result_budget_resolve()~ is the one resolver, used by the relay, the daemon's ~connector.list~ and every client.

#+begin_src bash
clawtilla integration set forge max_result_bytes=200000
clawtilla integration set logs max_result_bytes=0      # no budget
#+end_src

*** What the agent reads

A result past the budget is trimmed before the agent sees it, and the cut is announced at *both* ends, because a model reads a quiet note at the bottom of a long result as the end of the data:

#+begin_example
[clawtilla] TRIMMED: this result from forge's issues_list was 2,104,332 bytes, over the 65,536-byte budget, so only 65,412 bytes of it are shown (.content[0].text.items: 212 of 6,880 items). The rest was NOT shown -- do not assume you have seen everything. The whole result is held as r5f0c1e2d3a4b5c6d. Read the part you need with clawtilla_mcp_result_query -- {"result_id": "r5f0c1e2d3a4b5c6d", "path": ".content[0].text.items", "offset": 212} continues where this stops; "search" finds text in it -- rather than calling the tool again.

{"items":[{"id":1, ...}, ... 212 records ...]}

[clawtilla] END OF TRIMMED RESULT: 65,412 of 2,104,332 bytes shown. The rest is held as r5f0c1e2d3a4b5c6d; read it with clawtilla_mcp_result_query (see the note at the start).
#+end_example

How it is cut, in ~clawt_mcp_result_trim()~:

- *Each text block gets a share*, water-filled: a short block keeps its whole size and the rest go to the long ones.
- *A text that is JSON is cut structurally*: arrays to the records that fit, objects member by member.  What the agent reads still parses -- it is the same shape with fewer records -- and the note names each place it was cut and how many of how many it kept.
- *Prose is cut on a boundary.*  ~clawt_mcp_result_safe_cut()~ never lands inside a UTF-8 sequence, inside a JSON ~\uXXXX~ escape, after a lone backslash, or between the two halves of an escaped surrogate pair -- half an emoji is an invalid string some providers refuse outright.  A run of backslashes is counted, so ~\\u~ is a backslash and a ~u~.
- *~structuredContent~ is trimmed too*, structurally, so the provider is not handed a second full copy of what the text half was cut from.  The two halves share the budget: one that fits in half keeps its size and the other gets the rest.
- *An image, an audio clip or a blob is never cut* -- half of one is garbage.  It stays when it fits and is otherwise replaced by a sentence saying where it is in the held result (~.content[2]~).
- *The server's text is escaped* with ~clawt_preamble_escape_all()~ in a trimmed result and every query answer, so a ~[clawtilla]~ anywhere in it reads ~[not from clawtilla]~ and cannot pass for one of the two notes.

The notes come on top of the budget: the budget is what the server's own content may cost.  A result within the budget is passed through byte for byte, notes and all absent.

*** The whole result is held, and only its agent can read it

Before the trimmed result goes out, the whole message is written to =<state_dir>/agents/<id>/mcp-results/<result_id>.json= -- the directory 0700, the file 0600 -- with a =.meta= beside it naming the connector, the tool, the size and the budget.  A result id is ~r~ and sixteen hex digits from the kernel.  Results are kept for a day and at most 64 per agent, oldest first; every spill sweeps, and the sweep touches only files whose names are held-result ids.

~clawtilla_mcp_result_query~ reads it:

| Argument    | What it does                                                                              |
|-------------+-------------------------------------------------------------------------------------------|
| ~result_id~ | which held result, from the note                                                          |
| ~path~      | jq-like: ~.content[0].text~, ~.structuredContent.items[20:40]~, ~["odd key"]~, ~[-1]~; a string that is JSON is gone into, so ~.content[0].text.items~ works |
| ~search~    | text to find, ignoring ASCII case: each match with what is around it, or the array items that contain it |
| ~offset~    | where to start: a byte of a string, an item of an array                                    |
| ~limit~     | how much: bytes of a string, items of an array                                             |

The answer stays within the budget the result was held to, whatever is asked, and is announced at both ends when it is cut; the result's text in it is escaped.  The tool is offered only to an agent that holds a connector.

The permission is where the lookup happens.  The daemon resolves the id inside the *calling* agent's own =mcp-results= and nowhere else, so there is no id one agent can pass that reaches another's results -- and an id that is not there, is malformed, or belongs to somebody else gets one answer, word for word, so asking cannot be used to learn what another agent's tools returned.  *Under confinement.*  A confined agent's connector relays run inside its bwrap box, so the relay spills there, not the daemon: =mcp-results/= is under =<state_dir>/agents/<id>/=, the agent's own state directory, which ~clawt_agent_confine_build()~ binds read-write at the same path (the rendered config, sessions and link token live there too).  Nothing extra is bound, nothing crosses IPC, and the daemon's query tool reads the same path on the host.  =tests/test-agent-confine.c= (~/agent-confine/held-results-are-writable~) checks both the ~--bind~ and the sandbox's own predicate, built as the daemon builds it.  The same holds for the apps the daemon keeps under =mcp-apps/=, which the box can write but the relay never needs to.  The agent can read its own held results from inside the box; they are what its own tools returned.

*Through the egress gate.*  For a gated agent the HTTP bridge sends every request through ~CLAWTILLA_EGRESS_PROXY~ (see "A gated agent's connector says the egress gate refused it" below, and [[file:security.org][security.org]]); the bounded reader reads the gate's answer like any other, a relay's own ~resources/read~ for an app's view goes the same way, and every request is still answered -- a failure status that is not JSON-RPC is judged on its first 64 KiB and answered with a tool error, and a body that breaks off before a whole message arrived gets one too.

*** A limit applied while reading

The relay used to read a whole line before looking at it -- ~g_data_input_stream_read_line_async()~ grows its buffer until it finds a newline -- so the size of one message was the server's to choose, and the HTTP bridge read a whole response body the same way.  Both now read a chunk at a time through ~ClawtMcpReader~, which holds at most =CLAWT_MCP_RESULT_HOLD_MAX= (64 MiB) of one message in memory.  Past that, the rest is written straight to the held result as it arrives and never held; the message is never parsed, and the agent is shown the start of its raw JSON, cut safely, between the same two notes, with ~search~ and ~offset~ to read the rest (a path cannot be followed into something too big to parse).  The reader finds the message's top-level ~id~ as the bytes go past -- it may come after the result -- so the reply still answers the right call.

That ceiling applies to every relay, whatever the budget says, including a guest desktop's and a connector with ~max_result_bytes: 0~.

*** In the conversation

Every client shows a trimmed result where the turn's tool calls are, as a warning-toned line: "Result trimmed: forge's issues_list returned 2,104,332 bytes; the agent was shown 65,412, and the whole result is held as r5f0c... for it to query."  The relay tells the daemon (~connector.result_trimmed~), which records it as a status step in the room the call was made from (~CLAWTILLA_ROOM_ID~); ~clawt_mcp_result_is_notice()~ is how each client recognises one.  A relay with no room to name -- one started by hand -- shows nothing there, and the agent was told in the result either way.

Each connector's dialog has a *Result budget* field (-1 for the fleet's, 0 for none) with what applies now beside it; the Connectors page has the fleet's.

** Apps in chat

An MCP server can ship an interactive view for a tool -- an MCP App: a ~ui://~ resource of HTML, MIME type ~text/html;profile=mcp-app~, named in the tool's ~_meta.ui.resourceUri~ (the extension is ~io.modelcontextprotocol/ui~).  With *Show its apps in chat* on, a call of such a tool appears in the conversation as an app.

#+begin_src bash
clawtilla integration set draw show_apps=true
#+end_src

Off by default, because the view is the server's own code running in your browser.

*** Where the view is read

mcp-glib 1.0.1 knows nothing of MCP Apps, so this is done at the JSON level in the relay -- which is right anyway, because the relay is the only thing that holds the credential and the only time a connection to the server exists.  With the switch on:

1. The relay's ~initialize~ advertises ~capabilities.extensions["io.modelcontextprotocol/ui"] = {mimeTypes: ["text/html;profile=mcp-app"]}~; the spec has a server leave ~_meta.ui~ out for a client that does not.
2. It notes which tools in ~tools/list~ ship a view.  A tool whose ~_meta.ui.visibility~ leaves out ~"model"~ belongs to the view: it is taken out of the agent's list and a call to it is refused -- the wall and its door.
3. When such a tool answers, the answer goes to the agent untouched and whole (before any budget cut), and the relay sends a ~resources/read~ of its own for the view.  Its answer is kept back from the agent's CLI.  A view read once is reused for the life of the relay.
4. The relay hands the daemon the call -- tool, title, input, result, the view's HTML, the policy built for it and any origins refused -- with ~connector.app~.  The daemon asks the switch again (a relay started before it was turned off must not add an app after), keeps the record 0600 under =<state_dir>/agents/<id>/mcp-apps/= (thirty days, at most 200), and puts a status step in the room: "App: Draw a diagram from draw", carrying the app's id and its web address.

A view bigger than 2 MiB, not UTF-8, or not sent at all is still a call in the conversation, with why it cannot be shown in place of the frame.

*** How it is drawn

The web client draws it; GTK and lrg link to the web client's view of it.  That is the parity decision, recorded in =make parity= as affordance rows rather than an exception: GTK and lrg have no HTML engine, and a frame that cannot be isolated is not worth drawing.

- *Nothing is fetched until somebody opens it.*  The chat shows the app's card with an *Open app* button; pressing it fetches =/a/<agent>/app/<id>/frame= from the web client, which asks the daemon (~connector.app_get~) for the record.
- *The frame has no same-origin access to the client.*  It is an ~<iframe sandbox="allow-scripts">~ -- no ~allow-same-origin~, no forms, no popups, no top navigation, no ~allow~ attribute -- so its origin is opaque, and ~referrerpolicy="no-referrer"~.
- *Its document is built by the daemon* (~clawt_mcp_app_build_document()~): a doctype, then the Content-Security-Policy as a ~<meta>~ before one byte of the server's (its byte-order mark and doctype taken off), set verbatim as ~srcdoc~.
- *The policy* (~clawt_mcp_app_build_csp()~) is the spec's construction with the host's filter: ~default-src 'none'~; inline script and style; fonts, images and media from ~data:~ (and ~blob:~); and only the origins the view's ~_meta.ui.csp.resourceDomains~ and ~connectDomains~ ask for that pass ~clawt_mcp_app_domain_ok()~ -- ~https://~ and a dotted host, a port or a leading ~*.~ at most, no path, query, quote, semicolon, comma or space, sixteen per list; ~http://localhost~ and ~http://127.0.0.1~ only for a server that is itself local.  ~'self'~ is never named.  Frames, objects, ~<base>~ and form posts are refused outright.
- *A small host bridge* in the web client answers the view's ~ui/initialize~, hands it the tool's input and result (~ui/notifications/tool-input~, ~ui/notifications/tool-result~), follows ~ui/notifications/size-changed~, forwards ~tools/call~ (below), and refuses everything else -- ~ui/message~ and ~ui/open-link~ by name.  It answers only messages whose source is that frame.

GTK and lrg draw the step with a link -- ~clawt_mcp_app_link_label()~, "Open Draw a diagram in the browser" -- to ~connectors.apps_web_url~ =/a/<agent>/app/<id>=, the web client's full-page view of the same app.  The daemon builds that address when it records the step, so no client has to know where the web client runs; set ~connectors.apps_web_url~ when it is not on =http://127.0.0.1:8790=.

*** A view calling its own server's tools

A view may call a tool on the server that shipped it -- ~tools/call~ over postMessage -- and clawtilla runs it with exactly the rules an agent's call of that tool goes through, and only for a tool the server lets its apps call.

1. *The page forwards it, the view does not.*  The bridge takes the view's message as it was posted and ~POST~s it, from the page (same origin, the page's credentials -- the frame's origin is opaque and cannot), to the frame's own route, ~data-app-call~ = =/a/<agent>/app/<id>/call=.  The address is built from the app id the daemon gave the frame, never from anything the view said.
2. *The web client reads it* (=clawt_web_app_bridge_parse()=): a ~tools/call~ with an id, a tool name and an arguments object, or a JSON-RPC refusal the view can read.  It asks the daemon with ~connector.app_call~ and posts the JSON-RPC answer, with the view's own id, back into the frame.
3. *The daemon checks the app and the connector*: the app is this agent's (the record under its own state directory); the agent still holds the connector the app came from; *Show its apps in chat* is still on; and the agent is not confined -- see below.  An arguments object larger than 256 KiB is refused.
4. *It runs the call through a relay of the connector's own*: =clawtilla connector relay <name> --agent <id> --app-call=, the command line an agent's =.mcp.json= names (=clawt_workspace_connector_relay_argv()=) with one flag.  So the credential, the granted tool list (~tools:~), the agent's action rules and their approvals apply as they would to the agent -- the approval card names the tool and says it was "asked by an app in chat (not the model)", and the call is never counted as the agent's turn reaching outward (~policy.check~'s ~origin: app~).  In this mode the relay speaks the server's own tool names (the app is the server's code and knows no account prefix), puts no directory in front, keeps no result budget, and turns apps around (=clawt_mcp_apps_set_app_caller()=): ~tools/list~ passes whole and a ~tools/call~ is refused unless the server listed that tool as *visible to apps* (=clawt_mcp_app_tool_app_visible()=: ~_meta.ui.visibility~ names ~app~, or is absent, which the extension defines as both).  A tool only the model may call is never an app's.
5. *The daemon is the relay's MCP client* (=clawt_mcp_app_call_async()=): ~initialize~, every page of ~tools/list~, and ~tools/call~ only when the list says the tool is visible to apps -- refused before anything is sent otherwise, with the sentence.  Asynchronous on the daemon's loop, reading at most 4 MiB per message as it arrives, with a hard limit of ten minutes (an approval can take that long); the relay's stdin is closed and the process stopped when the call has an answer.
6. *It goes in the transcript as the app's.*  Every call, run or refused, is recorded in the room the app is in -- "App call: Flowchart from draw called save_view itself -- the app, not the model." (=clawt_mcp_app_call_note()=, the server's words escaped) -- recorded, never delivered, and published as ~connector.app_called~.

A *confined* agent (~runtime.confine: bwrap~) is refused: its connector relay runs inside its box under its network rule, and the daemon will not start a second one outside the box on an app's behalf.  Ask the agent to make the call instead.

GTK and lrg have no HTML engine, so a view, and so its calls, exist only in the web client; their *Open ... in the browser* link opens the web client's page of the same app, where the calls are made.  That is recorded in =make parity= as an exception for ~connector.app_call~ in GTK and lrg and as the affordance row "MCP app calls its own tools".

*** What is not done

- *A view cannot write into the conversation or open a link.*  ~ui/message~ would put the server's words where the person and the agent read each other's, and ~ui/open-link~ would send the person to an address the server chose; the frame has no popups for the same reason.  The bridge refuses both by name, and a view that has a link to offer can show it as text.
- *An approval past the call's limit* is still open on the Decisions page after the app has been told the call timed out; answering it then does nothing.
- *No fallback for a server that refuses the extension.*  A server whose ~initialize~ rejects the unknown capability fails with the switch on; turn it off for that server.
- *Steps live in memory*, like every step: the app's card leaves the conversation when the daemon restarts, though the app itself stays openable at its address until it is swept.

** An integration broker

Connectors are one account each, and the open MCP registry lists servers somebody still has to run.  What neither gives is a stock of ready-made app integrations -- a CRM, a shop, an ERP, a ticket system -- that sign in with your own OAuth client.  With =broker.enabled= on, clawtilla runs a gateway that has them, in rootless podman, and owns its whole lifecycle: you never write a compose file, and the gateway is one more part of the fleet.

Two gateways, chosen with =broker.type=:

| ~broker.type~   | What it is                                                                                     | Licence    |
|-----------------+------------------------------------------------------------------------------------------------+------------|
| ~anythingmcp~   | AnythingMCP: an MCP gateway whose JSON adapters turn REST, SOAP, GraphQL, OData and SQL into tools, OAuth2 with your own client | AGPL-3.0   |
| ~jentic~        | Jentic One (public beta): a credential broker that checks a per-agent rule before it injects a stored key, and logs every call | Apache-2.0 |

This is not the provider-key broker of ~runtime.network: gated~ (see [[file:security.org][security.org]]), which swaps a model provider's key on the way out of a sandbox.  The names are alike and the jobs are not.

*** Turning it on

#+begin_src yaml
broker:
  enabled: true
  type: anythingmcp       # or jentic
  port: 47400             # the MCP endpoint and API
  dashboard_port: 47300   # AnythingMCP's dashboard; Jentic One serves both on port
#+end_src

#+begin_src bash
clawtilla config reload
clawtilla broker status
#+end_src

#+begin_example
AnythingMCP: Starting -- starting clawt-broker-anythingmcp (pulling its image first if it is not here yet)
  image:     docker.io/helpcodeai/anythingmcp:v0.54.0
  dashboard: http://127.0.0.1:47300
  mcp:       http://127.0.0.1:47400/mcp
#+end_example

The start never waits in anybody's way.  Daemon start, a reload that turns the key on, and ~broker.start~ all answer at once; the containers are pulled, made and started on worker threads through the same machinery agents' container computers use (=clawt-pod-bridge.c=, podomation's ~container~ module), and the state is /starting/ until the gateway answers its health check, then /running/.  On this machine the first AnythingMCP start took about twenty seconds with the images present.

*** What runs

Everything the gateway keeps is under =<state_dir>/broker/= (=~/.clawtilla/broker/= by default), so the containers themselves are disposable: every start makes them again from the config, which is how a changed image or port takes effect, and stopping leaves them and their data in place.

| Container                       | Image (default)                                  | Publishes                                           | Binds                                                       |
|---------------------------------+--------------------------------------------------+-----------------------------------------------------+-------------------------------------------------------------|
| ~clawt-broker-anythingmcp-db~   | ~docker.io/library/postgres:17.12-alpine~        | nothing                                             | =broker/db= at the data volume, =broker/run= for its socket |
| ~clawt-broker-anythingmcp~      | ~docker.io/helpcodeai/anythingmcp:v0.54.0~       | =broker.port= -> 4000, =broker.dashboard_port= -> 3000, on =broker.bind= | =broker/run=                                       |
| ~clawt-broker-jentic~           | ~ghcr.io/jentic/jentic-one-app:0.44.0~           | =broker.port= -> 8000, on =broker.bind=             | =broker/data=                                               |

Some of this differs from the upstream compose files, on purpose and from running them (see "Running it by hand" below):

- *No Caddy.*  The compose file puts Caddy in front for TLS and a public name.  A gateway on loopback reached by a relay on the same machine needs neither.
- *The database publishes no port and listens on no TCP socket.*  The two AnythingMCP containers share a unix socket in =broker/run=; the gateway's ~DATABASE_URL~ names it with ~?host=/clawt-run~.
- *Jentic One is one container running two processes.*  Its control plane hands executions to its broker on its own =127.0.0.1:8100= and sends a bearer over plain http only to loopback; the compose file shares one network namespace between two containers for that, which podomation cannot express.  A small ~bash~ supervisor runs the migrations, then the broker and the control plane, and exits when either does, so the restart policy starts both again.

=broker.image= and =broker.database_image= are refused without a tag or tagged ~latest~: an upgrade of the thing holding every SaaS credential should be an edit somebody made.  A digest is accepted.

*** One gateway server per agent or team

Each agent reaches exactly one gateway server: its own =agents.broker_server=, or else its team's =teams.broker_server=.  clawtilla makes one connector per server -- =broker-agent-<id>= or =broker-team-<id>=, provider ~anythingmcp~ or ~jentic~ -- scoped to exactly the agents that use it.  It is an ordinary connector from there: the relay starts it, the tool list, the tool directory and the action rules apply, and an agent's =.mcp.json= names ~clawtilla connector relay~ and carries no secret.  These connectors are made from the config rather than written into it, so editing one (~integration update~, ~connector key~) is refused with the setting that changes it.

For AnythingMCP, the server's own connector assignment /is/ the agent's permission:

1. Open the dashboard (the URL is on the Broker row, or in ~clawtilla broker status~) and register.  The first account is the admin, and registering asks you to accept AnythingMCP's terms -- clawtilla does not accept them for you.
2. Sign in to the apps you want, with your own OAuth clients, and install their connectors.
3. Make an MCP server for the agent (or the team) and assign it the connectors that agent may use.
4. On that server's page, make an MCP API key.  A key made there works for that server only: any other server answers 403.
5. Tell clawtilla:

#+begin_src bash
clawtilla agent set scout broker_server cmwgvs1dq000736li29o0luha   # the id in the server's MCP URL
clawtilla broker key scout                                         # reads the key from stdin, echo off
clawtilla team set research broker_server cmwgw...                 # a team's
clawtilla broker key team:research
#+end_src

The relay dials =/mcp/<server id>= with the key as a bearer.  AnythingMCP's instance-wide ~MCP_BEARER_TOKEN~ is never set: it reaches every server of every workspace, which is the credential a per-agent server exists not to need.

For Jentic One the identity is the key: register an agent in its web app, approve it, and store that agent's API key with ~clawtilla broker key~.  =broker_server= names the Jentic agent, for the record and for the assignment; the relay dials Jentic One's one =/mcp= endpoint.

Two kinds of agent are not given the broker, each with a warning in the config's warnings and in ~broker status~:

- an agent with ~runtime.network~ ~gated~ or ~none~: the gateway listens on this machine's loopback, and a gated sandbox has a loopback of its own with nothing on it;
- for Jentic One, an agent without ~runtime.confine: bwrap~ -- see below.

*** Jentic One: confined agents only, beta, no telemetry

Jentic One's own threat model ([[https://github.com/jentic/jentic-one/blob/main/docs/security/same-host/README.md][same-host README]]) says that an agent running as the same OS user as the instance can read its credential database and the key that decrypts it, and go around the broker rather than through it.  So:

- ~broker start~ (and the daemon's own start) refuses Jentic One while any agent that names a gateway server lacks ~runtime.confine: bwrap~, naming them, and such an agent is never given the connector;
- a confined agent's box binds its own key file read-only and nothing else of =<state_dir>/broker/=: the relay that reads the key runs in there, and the instance's database and encryption key stay outside.

It is a 0.x public beta whose schemas and CLI may change between releases; =broker.image= pins the one this release was run against.  Its quickstart turns anonymous telemetry on; clawtilla always sets its documented opt-out, ~JENTIC__TELEMETRY__ENABLED=false~, and turns off the GitHub release check and the OTLP exporters too (the latter retry a collector on localhost that is not there and fill the log).

*** When the gateway says no

A refusal names who refused.  clawtilla's own (a narrowed tool list, an action rule) say clawtilla; the gateway's are named as the gateway's, because the fix is somewhere else:

#+begin_example
AnythingMCP, the integration broker, refused this (HTTP 403): Access denied: this API key was created for a different MCP server. ..., so nothing ran. What this agent may use is set on its gateway server in AnythingMCP, not by clawtilla; ask the person if you need it.
AnythingMCP answered: Tool nope not found
AnythingMCP, the integration broker, refused the key clawtilla holds for this connector (HTTP 401), so nothing ran. ... store it with `clawtilla broker key scout`.
AnythingMCP, the integration broker clawtilla runs, did not answer (Could not connect: Connection refused), so nothing ran. It may still be starting; `clawtilla broker status` says.
#+end_example

A tool call gets a failed tool result, which is what a model reads; anything else a JSON-RPC error.  The gateway's own reason is repeated only when it sent one in a readable shape -- a JSON-RPC error message, a ~detail~ or a ~message~ -- cut to one line, never the raw body.  ~clawt_broker_refusal_reply()~ and ~clawt_broker_annotate_reply()~ are the two pure functions; =tests/test-broker.c= walks them.

*** A second credential store

Say it plainly: the SaaS tokens the gateway holds live in /its/ encrypted store, not clawtilla's.  That is a second credential store beside =secrets.dir=, with a key of its own:

| What                                   | Where                                                         | Mode |
|----------------------------------------+---------------------------------------------------------------+------|
| AnythingMCP's encryption key           | =<state_dir>/broker/encryption-key=                           | 0600 |
| AnythingMCP's JWT secret, database password | =<state_dir>/broker/jwt-secret=, =database-password=     | 0600 |
| AnythingMCP's database                 | =<state_dir>/broker/db/= (owned by PostgreSQL's uid in podman's namespace) | 0700 inside |
| Jentic One's encryption key            | =<state_dir>/broker/jentic-encryption-key=                    | 0600 |
| Jentic One's data                      | =<state_dir>/broker/data/=                                    |      |
| each gateway server's key (clawtilla's) | =<state_dir>/broker/keys/agent-<id>.json=, =team-<id>.json=  | 0600 |

The secrets are generated from =/dev/urandom= at the first start and never replaced: a new encryption key would make every stored SaaS credential unreadable.  Back up =<state_dir>/broker/= as a whole -- the key without the database is nothing, and the database without the key is ciphertext.  The secrets reach the containers as environment, which ~podman inspect~ shows to this user and nobody else; =broker/= is 0700, and the directories under it are wider only because the containers' own users are other uids in podman's namespace.

Only the keys are clawtilla's to hold.  They are written 0600, never returned over IPC (~broker.key~ answers with the path; ~broker.status~ says whether each is stored, never what it is), and they never appear in =.mcp.json=, an environment or an argv.  For an unconfined host agent this is the same honest limit every connector has: it runs as the same user, and =<state_dir>= is right there.

*** Lifecycle

| Verb                      | IPC               | What it does |
|---------------------------+-------------------+--------------|
| ~clawtilla broker status~ | ~broker.status~   | on or off, which broker, its state, what it is doing, its dashboard and MCP URLs, every gateway server and whether its key is stored |
| ~clawtilla broker start~  | ~broker.start~    | starts it in the background; refused while =broker.enabled= is off, or for Jentic One while an assigned agent is unconfined |
| ~clawtilla broker stop~   | ~broker.stop~     | stops the containers; everything under =broker/= stays |
| ~clawtilla broker restart~ | ~broker.restart~ | a stop, then a start |
| ~clawtilla broker logs~   | ~broker.logs~     | each container's last hundred lines, credential-shaped text redacted |
| ~clawtilla broker key <agent or team:id>~ | ~broker.key~ | stores a gateway server's key from stdin |

A container that stops on its own is started again under =broker.restart= (~always~ by default; ~on-failure~ behaves the same, since the container module's inspect does not say how a container ended; ~never~ leaves it stopped and says so).  Five restarts within ten minutes stop the retries and leave the broker /failed/, naming the container and ~broker logs~.  The watch asks podman for each container's state -- the container module's ~inspect~, whose =status= is podman's =State.Status= -- and asks the gateway's =/health=.  =running= is up, and so are =paused= and =stopping=, which the health check judges; anything else (=exited=, =created=, =dead=, ...) is a container that stopped.  An inspect that fails while podman still answers its container list is a container that is gone, and counts as stopped; podman not answering at all, or an inspect with no state, is "did not say", logged and not acted on.  A gateway that runs and stops answering three times in a row is reported as failed until it answers again.  Daemon stop stops the broker with it.

~broker logs~ prints each container's last hundred lines under a ~== name ==~ heading.  podman keeps a container's standard output and standard error as two streams and the order between them is lost, so a container that wrote to both gets each under a ~-- stdout --~ / ~-- stderr --~ subheading; one that wrote to only one gets its lines bare, and one that wrote nothing says ~(no lines yet)~.  A container podman cannot read says why in its own section and the others are still shown.  Anything shaped like a credential is redacted.  It needs podomation 1.0.2 or later, whose ~logs~ action demultiplexes podman's log stream; before it the action returned no text at all.

Every client has a Broker row at the top of the Connectors page: the broker, its state in ~clawt_broker_state_label()~'s word, what it is doing or why it failed, the dashboard link, and Start, Stop and Restart where each can do something.  It redraws on ~broker.changed~.

*** Running it by hand

Done once, under rootless podman 5.8 on Fedora 44 (x86_64), before any of the above was written, as the person would.  Kept here because it is what the shapes above rest on.

**** AnythingMCP

#+begin_src bash
D=~/broker-by-hand; mkdir -p $D/db $D/run; chmod 700 $D; chmod 755 $D/db; chmod 777 $D/run
cd $D; (umask 077; openssl rand -hex 32 > jwt; openssl rand -hex 16 > enc; openssl rand -hex 24 > pg)

podman run -d --name amcp-db \
  -e POSTGRES_USER=amcp -e POSTGRES_PASSWORD=$(cat pg) -e POSTGRES_DB=anythingmcp \
  -e PGDATA=/var/lib/postgresql/data/pgdata \
  -v $D/db:/var/lib/postgresql/data:Z -v $D/run:/clawt-run:z \
  docker.io/library/postgres:17.12-alpine \
  postgres -c listen_addresses= -c unix_socket_directories=/var/run/postgresql,/clawt-run

podman run -d --name amcp-app -p 127.0.0.1:47400:4000 -p 127.0.0.1:47300:3000 \
  -v $D/run:/clawt-run:z \
  -e NODE_ENV=production -e PORT=4000 \
  -e DATABASE_URL="postgresql://amcp:$(cat pg)@localhost/anythingmcp?host=/clawt-run" \
  -e JWT_SECRET=$(cat jwt) -e ENCRYPTION_KEY=$(cat enc) \
  -e NEXT_PUBLIC_API_URL=http://127.0.0.1:47400 -e SERVER_URL=http://127.0.0.1:47400 \
  -e CORS_ORIGIN=http://127.0.0.1:47300 -e FRONTEND_URL=http://127.0.0.1:47300 \
  -e MCP_AUTH_MODE=both -e MCP_ALLOW_ANONYMOUS=false -e ALLOW_OPEN_REGISTRATION=false \
  docker.io/helpcodeai/anythingmcp:v0.54.0 ./start.sh

curl -s http://127.0.0.1:47400/health      # healthy after about 12 s
#+end_src

What it showed:

- *The community edition needs PostgreSQL and nothing else.*  Redis is optional (caching and rate limits stay in memory without it), the code-runner is only for Code Mode, whose write mode is enterprise, File Search's worker and extractor are enterprise, and MOTIS is the Deutsche Bahn connector's.  None of them is started.
- *~host.containers.internal~ does not reach this machine's loopback* under pasta: it is mapped to the machine's external address, so the first attempt -- PostgreSQL published on =127.0.0.1= and dialled from the gateway -- failed migrations with ~P1001: Can't reach database server~.  Publishing it wider would put the database on the LAN.  A shared unix socket works and publishes nothing.
- *Bind the database's data /volume/, not PGDATA.*  The entrypoint chowns PGDATA to its own user, and the first layout bound it directly, so the bind source became a subuid's and this user could no longer relabel it at the next start (clawtilla refuses that mount up front, rightly).  Binding the parent at the image's volume path, with PGDATA one level down, keeps the source this user's -- and binding exactly the volume path keeps podman from making an anonymous volume there.  The directory must be 0755: the entrypoint re-runs itself as the postgres user, which has to pass through it.
- *A container computer runs ~sleep infinity~ unless told otherwise*, because an agent's machine exists to be exec'd into; the gateway's command (~./start.sh~) is named explicitly or it comes up "running" and serves nothing.
- *Registration needs ~acceptTerms~*, so the first account is the person's to make in the dashboard; clawtilla does not register one.
- *A server is addressed by id, not slug*: =/mcp/<id>= works and =/mcp/<slug>= answers 404.  A key made with ~mcpServerId~ works as ~Authorization: Bearer~ (and as ~X-API-Key~) for that server and answers 403 for any other.
- Replies are streamed (~text/event-stream~), and the relay reads both shapes.
- Data survives the containers: both removed and made again, the gateway was healthy in six seconds with its account and servers intact.

**** Jentic One

#+begin_src bash
D=~/jentic-by-hand; mkdir -p $D/data; chmod 700 $D; chmod 777 $D/data
(umask 077; openssl rand -base64 32 > $D/key)

podman run -d --name jentic -p 127.0.0.1:47800:8000 -v $D/data:/data:Z \
  -e JENTIC__AUTH__CANONICAL_BASE_URL=http://127.0.0.1:47800 \
  -e JENTIC__DATABASES__REGISTRY__BACKEND=sqlite -e JENTIC__DATABASES__REGISTRY__PATH=/data/registry.db \
  -e JENTIC__DATABASES__CONTROL__BACKEND=sqlite -e JENTIC__DATABASES__CONTROL__PATH=/data/control.db \
  -e JENTIC__DATABASES__ADMIN__BACKEND=sqlite -e JENTIC__DATABASES__ADMIN__PATH=/data/admin.db \
  -e JENTIC__CREDENTIALS__ENCRYPTION__ENTRIES__0__ID=v1 \
  -e JENTIC__CREDENTIALS__ENCRYPTION__ENTRIES__0__MATERIAL_ENV=JENTIC_ENCRYPTION_KEY \
  -e JENTIC_ENCRYPTION_KEY=$(cat $D/key) \
  -e JENTIC__TELEMETRY__ENABLED=false -e JENTIC__RELEASE_CHECK__ENABLED=false \
  -e JENTIC__OBSERVABILITY__METRICS__EXPORTER=none -e JENTIC__OBSERVABILITY__TRACING__EXPORTER=none \
  -e JENTIC__SERVER__MCP__ENABLED=true \

#+end_src

What it showed: the image runs as uid 10001, so the data directory must be writable by another uid (0777 inside a 0700 parent); its default shell is ~dash~, which has no ~wait -n~, so the supervisor is ~bash~; both surfaces answer =/health= (~{"status":"ok"}~, and ~{"surface":"broker"}~ on 8100 inside); =/mcp= lists its tools to anybody and answers 401 to a tool call without an agent's key; and without the two exporter settings it logs a failed OTLP export every second.

**** On aarch64 (the Asahi machines)

AnythingMCP publishes amd64 only, and its own workflow says why: Prisma's WASM schema engine misparses ~onDelete: Cascade~ on linux/arm64.  Building it locally was tried rather than assumed:

#+begin_src bash
git clone https://github.com/HelpCode-ai/anythingmcp && cd anythingmcp
git checkout v0.54.0
podman build --platform linux/arm64 -t localhost/anythingmcp:v0.54.0-arm64 .
#+end_src

Run under qemu-user emulation on this x86_64 machine, the build got through ~npm ci~ and failed at ~RUN npx prisma generate~ with ~RuntimeError: panicked at psl/parser-database/src/types/index_fields.rs:184:22: explicit panic~ -- the upstream bug, reproduced.  So *as of v0.54.0 there is no working local arm64 build*; a native build on an Asahi machine runs the same arm64 Node and the same WASM engine and should be expected to fail the same way until Prisma is fixed.  The options until then:

- run the published amd64 image under emulation -- ~qemu-user-static-x86~ registered with binfmt, then ~podman pull --platform linux/amd64 docker.io/helpcodeai/anythingmcp:v0.54.0~; =broker.image= then names it as usual.  Not tried here, and expect it to be slow;
- use ~broker.type: jentic~, whose image is published for arm64 (~0.44.0~ has both);
- or, once upstream ships a fix, the build above, with =broker.image: localhost/anythingmcp:<tag>-arm64=.

** Renewal

Only the daemon renews or writes a credential.  A relay asks it to
(~connector.refresh~, over IPC) before reading, and reads the file the
daemon wrote -- including a relay inside a confined agent's box, which
sees the renewal because its connector's directory, not the file, is
bound in.  The reply carries no credential.

An access token often lasts an hour.  The daemon renews any that is
within ~connectors.refresh_margin_seconds~ of expiring, on a timer of its
own -- not when a tool server starts, because a server started with a
token that expires forty minutes later keeps running with it, and the
agent's first failure would arrive long after anything could connect the
two.

=clawtilla connector list= shows how long is left.  An expired
credential that can renew itself reads as connected, not as broken:
showing it as broken would light up the list every hour and teach you to
ignore the one that genuinely is.

*** ~expires_in~ is a duration, and is stored as a moment

The wire carries ~expires_in: 3600~.  Kept as it arrived, that reads as
"an hour from now" every time anything looks -- so a token that expired
overnight looks an hour fresh each morning, the renewal never fires, and
every call made with it fails somewhere else entirely.  It is converted
when the response arrives and stored as ~expires_at~, an absolute time,
and the field in the token file is *named* ~expires_at~ so the next
reader is not invited to add it to the moment they loaded it.

Providers also disagree about whether these are numbers or strings.
Reading only one silently treats the other as absent, which gives either
a token that never expires or one that expires immediately; both forms
are read.

*** Granted scopes are never written back over requested scopes

A person can untick things on a consent screen, so what was granted is
often less than what was asked for.  Storing the granted set into
~scopes:~ would mean the next authorization asks for less, and the one
after that less again -- a permission that quietly erodes every time it
is renewed, with nothing to say why.

So ~scopes:~ stays what you asked for.  What was actually granted lives
in the token file, and the daemon reports it separately, as
~granted_scopes~ on the ~connector.list~ reply.

Read the two as different questions.  ~scopes:~ answers "what will the
next authorization ask for"; ~granted_scopes~ answers "what does this
credential currently do".  They agree until somebody unticks something,
which is exactly when the difference matters.

An empty refresh token is likewise never written over a good one.  Some
providers omit the field on a renewal, meaning "keep the one you have",
and taking that literally costs an authorization nobody can see the
reason for.

"Empty" now means what it says.  The guard tested for a *missing* field,
and a provider answering with ~"refresh_token": ""~ produced a non-NULL
empty string that every ~!= NULL~ test downstream read as a value -- so
the blank was stored over the good one and the guard written to prevent
exactly that could not see it.  An empty member is treated as an absent
one at the point the response is parsed, rather than at each of the
places it is read, so no later test can be fooled the same way.  The
symptom was a slow one: the current access token kept working for its
hour, and every renewal after that failed.

** Revoking

#+begin_src bash
clawtilla connector revoke gh
#+end_src

The local copy goes whatever the provider says -- you asked for the fleet
to stop using it now, and a provider that is unreachable must not leave
an agent holding a working credential until the network comes back.

Where the provider offers a revocation endpoint, clawtilla calls it and
says so.  Where it does not, clawtilla says *that*, because deleting our
copy is not revocation: a token you forgot still works for anybody who
has it, for as long as the provider says, which for a refresh token can
be months.  Finishing the job means withdrawing it in their settings.

** What the agent is told

The managed region of the agent's =TOOLS.org= gains a paragraph per
connector, and it says three things the tool list cannot:

- these tools reach a real account belonging to a real person, so
  reading is cheap and anything that writes or sends is worth being sure
  about;
- the agent does not have the credential and cannot get it, said out
  loud so it is not discovered by trying -- an agent that goes looking
  wastes turns and leaves something alarming in a transcript;
- which scopes the connector was configured with, so it does not spend
  turns discovering one call at a time that something was refused.

That last one is the ~scopes:~ key -- what was *asked for*, not what the
provider granted.  The two are the same unless somebody unticked
something on the consent screen, and where they differ the agent is
reading the more generous of the two.  The granted set is on the
~connector.list~ reply as ~granted_scopes~; nothing puts it in front of
an agent yet.

** Troubleshooting

*** "not connected yet"

No credential has been stored.  Either =clawtilla connector key <name>=
or =clawtilla connector connect <name>=.

*** "cannot read the credential for 'x'"

The relay could not open the token file.  On a confined agent
(~runtime.confine: bwrap~) this was every credentialed connector before
the box bound them; now it means the connector is not granted to this
agent (its ~scope~ and ~agents:~), or its ~token_file~ names a file that
did not exist when the agent started -- a file somebody chose is bound
as itself, so it must exist first.  Restart the agent after fixing
either.

*** A gated agent's connector says the egress gate refused it

The agent has ~runtime.network: gated~, and its connector's server is on
this machine, the LAN or the tailnet.  The relay runs in the agent's box
and goes out through the egress gate like everything else there; add the
server's address (with its port, for loopback) to =egress.allow= if the
agent should reach it.  That opens it to the agent's own tools as well.
See [[file:security.org::*Connectors from a gated box][Connectors from a gated box]].

*** "no connector called 'x'"

The ~provider~ names a catalogue entry that does not exist.  The error
names ~connectors.dir~ as well, because the fix is usually a file that
adds it.

*** The flow says the code expired

Device codes are usually good for fifteen minutes.  Start again; nothing
is left behind.

*** The agent has the connector but no tools

The catalogue entry has no server and the integration named none, so
there was a credential and nothing to use it with.  Set ~command~ or
~url~ on the integration.  =clawtilla connector catalog= shows which
entries know a server.

*** An agent says a tool is not permitted

The connector was narrowed with ~tools~.  The refusal names the tool and
says so.

*** A warning names a tool the connector does not offer

The integration's ~tools:~ names something the pack's own ~known_tools~
does not.  Almost always a typo; fix the integration.  A pack that
declares no ~known_tools~ at all -- the ordinary case -- never warns
about this, since there is nothing here to check against.

*** The agent sees three tools instead of the server's

The connector is presented as a directory: its server is past one of the
thresholds and the agent's CLI does not search tools itself, or its
~directory~ is ~always~.  Search it with ~<name>_search_tools~, or set
~directory: never~ on the connector to list every tool again.  See
"Servers with many tools".

*** "No tool named ... here" from a directory

Either the tool does not exist or the connector's ~tools:~ does not
include it.  The directory says the same for both on purpose.

*** "needs a sign-in" on a connector's row

Its server answered the agent's last call with a 401: nobody has signed in yet, or the sign-in expired or was withdrawn.  Sign in from the row, or ~clawtilla connector connect <name>~.

*** "offers no dynamic client registration"

Discovery found the authorization server, but it does not let clients register themselves.  Register one there by hand -- redirect =http://127.0.0.1:8765/callback= -- and set ~client_id~ on the connector.

*** "refused to fetch ... not https"

A document in the discovery chain named a URL in the clear, or a loopback address while the server itself is not on loopback.  The server's metadata is wrong (or hostile); there is nothing to configure here except pasting a token instead.

*** "this agent holds several accounts on this service"

The agent called a tool by its bare name while holding more than one account on that service.  It is told the prefixed name; nothing ran.

*** "both ... accounts labelled"

Two accounts on one service fold to the same label.  Give one of them a different ~account~.

*** A result starts with "[clawtilla] TRIMMED"

It was bigger than the connector's ~max_result_bytes~.  The agent reads the rest with ~clawtilla_mcp_result_query~; raise the budget, or set it to 0 for none, on the connector if that is the wrong trade for it.

*** "There is no held result ... for you"

Held results last a day, sixty-four per agent, and only the agent whose tool returned one can read it.

*** An app's card says its view could not be shown

The server sent no ~text/html~ view for the tool, sent one bigger than 2 MiB, or one that was not UTF-8.  The call's result is still in the conversation.

*** "This tool belongs to an app's view, not to the agent"

The server marks the tool for its view alone (~_meta.ui.visibility~ without ~"model"~), and *Show its apps in chat* is on.

*** "is the integration broker's connector"

~broker-agent-*~ and ~broker-team-*~ are made from =broker.*= and =broker_server=, not read from the file.  Change those, and store the key with ~clawtilla broker key~.

*** "AnythingMCP ... refused this (HTTP 403)"

The key was made for another gateway server than the agent's =broker_server= names, or the server does not allow what was asked.  Make the key on the server's own page.

*** "Jentic One is not started while an agent that uses it is unconfined"

Set ~runtime.confine: bwrap~ on the agents it names, or take their =broker_server= away.  See "Jentic One: confined agents only".

*** The broker says failed after five restarts

A container keeps stopping.  ~clawtilla broker logs~ says why; ~clawtilla broker start~ tries again once it is fixed.

*** "connectors.registry_enabled is off"

~connector.registry_refresh~ refuses until you turn the key on.  Nothing
imports until then, and nothing was ever asked of the network before
this point either.
