* Connectors

A connector is an account on some service -- GitHub, a GitLab you run
yourself, a calendar -- that clawtilla holds the credential for.  Agents
get the service's tools.  They never get the token.

That distinction is the whole feature.  An ~mcp~ integration's
environment is resolved into the agent's =.mcp.json=, which is fine for
a key you chose to hand it and much less fine for an authorization on
your own account: the agent can read that file, and anything it reads
can end up quoted into a message or an exported transcript.  A
connector's =.mcp.json= entry carries no secret at all.

#+begin_src bash
clawtilla connector catalog
clawtilla connector add gh --provider github --account work \
    --command github-mcp-server --scope all
clawtilla connector key gh
#+end_src

That last command reads a token from stdin with the echo off.  There is
deliberately no =--key= flag: an argument is in your shell history and
in the process table for anybody on the machine to read.

** What it actually protects against

Worth stating plainly, because the answer depends on where the agent
runs and overstating it would be worse than not having it.

For a *container or VM agent* the boundary is real.  The token file and
the relay are on the host; the agent is not.  It can call the tools and
cannot reach the credential, in the way an ordinary user cannot read
another user's files.

For an *unconfined host agent* it prevents the credential leaking by
accident, which is the failure that actually happens: it is not in
=.mcp.json=, not in the agent's environment, not in the process table,
not in its transcript.  It does not stop an agent that goes looking,
because it runs as the same user and =secrets.dir= is right there.
Confinement is what makes that airtight -- see [[file:computers.org][computers.org]] and
[[file:security.org][security.org]].

What it buys everywhere: one place to revoke, renewal that happens
before anything breaks, and a per-agent tool list.

*** Where the credential actually goes

Into a 0600 file under =secrets.dir=, and nowhere else.  The agent's
=.mcp.json= names ~clawtilla connector relay <name>~ and carries no
secret; the relay reads that file *itself* and hands the value to the
tool server it starts.  There are exactly four places it must never
appear, and each is a different way it would leak:

| Not here                | Because                                     |
|-------------------------+---------------------------------------------|
| the agent's =.mcp.json= | the agent can read its own workspace, and anything it reads can be quoted into a message or an exported transcript |
| the agent's environment | it is inherited by everything the agent runs |
| an ~argv~               | =/proc/*/cmdline= is world-readable, so anybody on the machine can read it while the server runs |
| an IPC response         | it would put a live credential into every client's memory, and into whatever that client logs |

The plan the relay builds -- ~ClawtConnectorPlan~ -- is tested with a
*negative* assertion: the credential must be in ~envp~ or in a header,
and nowhere in ~argv~.  That is not something you can see by reading the
code that builds the argv; it is something you see by looking for the
value in the result.

The relay also closes the child's stdin when the agent's CLI goes away.
A stdio MCP server exits when its stdin closes and nothing else tells it
to, so waiting for both directions left an abandoned process holding a
live credential indefinitely.

A remote (HTTP) connector's requests never follow a redirect, because the credential is a request header and libsoup would carry it to whatever host the server named. A tool server that answers with one gets the relay's error instead -- ~clawtilla: the request to the tool server failed: https://mcp.example answered 307, a redirect to https://other.example; ...~ -- and the fix is to set the connector's ~url~ to the address it names. See [[file:security.org::*A credential never follows a redirect][A credential never follows a redirect]].

** How a credential is obtained

Three ways, and the catalogue says which apply to a given service.

*** A token you already have

The simplest, and often the best.  A personal access token works as well
as an authorization and needs no application registered with anybody:

#+begin_src bash
clawtilla connector key gh
#+end_src

*** The device flow

The one that suits a daemon.  No redirect URI, no listening socket, no
browser on the same machine: clawtilla asks for a code, you type it into
a page on whatever device you are holding, and clawtilla polls until you
have.  A workstation you reached over SSH can be connected from a phone.

#+begin_src bash
clawtilla connector add gl --provider gitlab --client-id abc123
#+end_src

#+begin_example
    WDJB-MJHT

Enter that at https://gitlab.com/oauth/authorize_device

Waiting...
Connected.
#+end_example

*The normal case for a poll is an HTTP 400.*  A provider asked about a
code nobody has typed yet answers =400 Bad Request= with
~{"error": "authorization_pending"}~ in the body -- so a client that
reads the status and gives up has built a device flow that can never
once succeed, while looking entirely correct.  clawtilla never looks at
the status here: ~clawt_oauth_read_poll()~ classifies the *body*, and it
is a pure function so the classification can be tested without a
provider.

~slow_down~ lengthens the interval *permanently*.  A provider that has
asked once to be polled less often will ask again, and reverting after a
single slower poll spends the rest of the flow rate limited -- while the
person is standing at the consent screen wondering why nothing happened.

Two frames rather than one, for the same reason: ~connector.begin~
answers as soon as there is a code to show, and ~connector.await~ is the
one that waits.  A device code is good for about fifteen minutes and the
ordinary client timeout is two, so waiting takes an explicit longer
deadline -- and deferring the whole thing would mean showing the person
nothing until it was over.

*** Authorization code with PKCE

For the many services that never implemented device grant.  It costs a
loopback listener and a redirect URI registered with the provider in
advance, which is why it is second choice.  Register
=http://127.0.0.1:8765/callback=, or whatever ~connectors.redirect_port~
says.

The listener binds 127.0.0.1 only.  A redirect carries an authorization
code in a URL, and a listener on every interface offers that code to
whoever on the network reaches the port first.

** Client IDs

clawtilla ships none, and will not.  It has no OAuth application of its
own to lend, and borrowing another project's would mean every clawtilla
in the world identifying itself as something it is not.

Registering one takes a few minutes per provider.
=clawtilla connector catalog= names where for each, and the
~client_id_help~ field is repeated in the error you get if you try to
authorize without one.

If that is friction you do not want, paste a token instead.  It is not
a lesser option.

** The catalogue

Two things at once: a table compiled into the library covering the
services people reach for, and a directory of YAML files that adds to it
and overrides it.

#+begin_src bash
clawtilla connector catalog
#+end_src

These are somebody else's URLs and somebody else's scopes.  A copy of
them in C goes stale silently and in the wrong direction, so a provider
that moves an endpoint should be fixable by editing a file rather than
by waiting for a clawtilla release.  Drop one in
=$XDG_CONFIG_HOME/clawtilla/connectors.d/=:

#+begin_src yaml
connectors:
  - id: acme
    name: Acme
    summary: Tickets and deployments
    category: Work
    auth: api_key            # none | device | pkce | api_key
    server_command: acme-mcp
    server_args: [stdio]
    placement: env           # env | header
    credential_name: ACME_API_KEY
#+end_src

An entry whose ~id~ matches a built-in one *replaces* it rather than
merging into it.  Half an override -- a new token endpoint against an old
authorization endpoint -- is a combination nobody wrote down, and it
fails pointing at neither file.

A file that will not parse is a warning naming the file, not a failure:
a typo in one connector must not take away the others, and this is read
on the path that starts the daemon.

*** Self-hosted services

A connector with a ~default_instance~ is one you may run yourself, and
its endpoint fields are read as *paths* joined onto whichever instance
the configuration names:

#+begin_src bash
clawtilla connector add work --provider gitlab \
    --instance https://gitlab.example.com --client-id abc123
#+end_src

A host with no scheme gets =https=.  Somebody who typed a bare hostname
did not mean to send an OAuth exchange in the clear.

*** The two generic entries

~api-key~ and ~bearer~ exist so the catalogue is open rather than
closed.  Most MCP servers are not behind OAuth at all -- they want a key
from a dashboard in an environment variable, or a bearer token on an
HTTP endpoint -- and those are worth brokering for exactly the same
reason.  Override ~credential_name~ per instance and one entry covers
every such service.

#+begin_src bash
clawtilla connector add weather --provider api-key \
    --command weather-mcp --credential-name OPENWEATHER_KEY
#+end_src

** VENTURE, and the writes it holds back

VENTURE is an ERP and CRM you run yourself -- sales, expenses,
invoices, tickets, contacts, a ledger -- and it is the one built-in
connector that is *yours* rather than somebody else's service.  It is
compiled in rather than shipped as a pack in =connectors.dir= for
exactly that reason: a fleet that runs VENTURE should reach it out of
the box, and an entry somebody has to copy into a directory before
anything works is an entry most people never find.

#+begin_src bash
clawtilla connector add books --provider venture \
    --instance https://books.example
#+end_src

=default_instance= is =http://localhost:8747=, so a fleet on the same
machine needs no =--instance= at all.

*** The credential is a token you mint yourself

Sign in to VENTURE's web UI and create an API token.  =POST
/api/v1/tokens= returns the plaintext exactly once and stores only its
hash, so copy it then -- there is no way to read it back afterwards, by
design.

clawtilla keeps it in a 0600 file under =secrets.dir= and injects it
into the tool server's environment as =VENTURE_TOKEN=.  It never
reaches the agent's =.mcp.json=, its argument vector or its transcript.
=VENTURE_URL= goes in beside it, because =venturectl mcp= is a separate
program with its own default of localhost and has no other way to learn
which instance it was pointed at.

*** The tools are generated from VENTURE's own schema

=venturectl mcp= fetches =GET /api/v1/schema= at startup and builds its
tools from what came back.  Nothing in its C names a record type, so a
type a plugin registers appears in the =type= enumeration of every tool
that takes one, with no release anywhere.

That is why the catalogue can write the tool list down at all.  There
are nineteen, and they are verbs:

| Tool                      | What it does                                                |
|---------------------------+-------------------------------------------------------------|
| =venture_schema=          | the record types, or one of them in full                    |
| =venture_list=            | list records of a type, filtered                            |
| =venture_get=             | fetch one by id                                             |
| =venture_create=          | create one                                                  |
| =venture_update=          | change named fields of one                                  |
| =venture_delete=          | soft-delete one                                             |
| =venture_reports=         | what reports there are                                      |
| =venture_report=          | run one                                                     |
| =venture_confirmations=   | list, approve or reject what is waiting                     |
| =venture_modules=         | which modules the server runs, and why any is off           |
| =venture_links=           | every link touching one record                              |
| =venture_link=            | link two records; staged like a create                      |
| =venture_dashboards=      | the dashboards, the widget kinds, or the templates          |
| =venture_dashboard=       | one dashboard, evaluated, or its settings or definition     |
| =venture_dashboard_build= | make one from a template or a definition                    |
| =venture_factory=         | the release factory: status, actions, readiness, forecast, changelog, deploy, rollback, publish |
| =venture_inbox=           | the token's own inbox; mark a notification read             |
| =venture_runs=            | the coding runs with cost, or the budgets                   |
| =venture_desk=            | a ticket's clocks, timelines, sprints, triage, summaries, worklogs, macros |

The list is VENTURE's =docs/mcp.org= table and =tests/test-venture.c=
pins it, so a tool renamed upstream fails there.  The writes among the
last ten that are several records at once (a dashboard build, a macro,
a release publish) refuse while staging is on and say which single
writes would propose the same thing; see VENTURE's docs.

They are the entry's =known_tools=, so a =tools:= narrowing that
misspells one is a warning naming it rather than an agent silently
left with nothing.  A tool per record type would be 31 built-in types
times five verbs in every context window, and would be a second copy of
VENTURE's data model besides.

*** One token is one actor

The =connector= integration type declares no identity keys because a
shared account is usually the point.  This entry declares =token_file=,
and the reason is VENTURE's audit trail: every change records who made
it and how, which is what distinguishes an automation's write from a
person's from the AI's.  Two agents holding one token are one name in
every row they write.

So a shared instance covering two agents is reported by
=clawtilla integration list=, with a message that says what it costs.
Give each its own under =per_agent=:

#+begin_src yaml
integrations:
  - name: books
    type: connector
    provider: venture
    scope: selected
    agents: [bookkeeper, analyst]
    instance: "https://books.example"
    per_agent:
      bookkeeper:
        token_file: "~/.clawtilla/secrets/connector-books-bookkeeper.json"
      analyst:
        token_file: "~/.clawtilla/secrets/connector-books-analyst.json"
#+end_src

** Staged writes land in the decision inbox

=venturectl mcp= stages its writes by default: =venture_create=,
=venture_update= and =venture_delete= send the change with =?stage=1=,
and VENTURE builds and validates the record exactly as it would for a
direct write, holds it, and answers =202= with a confirmation.  Nothing
is in the books until somebody says so.

Without a bridge, "somebody says so" means opening VENTURE's own web
interface and finding the card.  So clawtilla polls
=GET /api/v1/confirmations= while a venture connector is bound and
turns each pending change into an ordinary ~ClawtDecision~ -- answerable
from the GTK client, the web client, or ~clawtilla decision~ over ssh,
beside every other thing an agent is waiting on you for.

#+begin_src
$ clawtilla decision list
venture-books-a3f9c118  bookkeeper
  books-agent wants to Create expense "Cover art" (via the 'books'
  connector).

  Record type: expense

  What would change:
    description: Cover art
    amount: {"amount":25000,"currency":"USD"}

  VENTURE drops this card unanswered at 2026-08-29T15:02:11Z.

  approve / reject   (default: reject)

$ clawtilla decision answer venture-books-a3f9c118 approve
#+end_src

Answering posts to =/api/v1/confirmations/<id>/approve= or =/reject=.

*** The fields are used honestly

The *question* is the staged change as VENTURE summarised it, with the
diff rendered underneath so it can be answered without opening
VENTURE at all.  The card is deliberately self-contained upstream, for
this reader.

The *default* is =reject=, and that is a description rather than a
policy: VENTURE drops a card nobody answers when its own confirmation TTL
runs out (an hour by default), so leaving it is the same as rejecting
it.

=reversible_until= stays *unset*.  Nothing is written until an approval,
so there is nothing to reverse -- and after one, VENTURE's soft delete
is the undo.  A deadline invented here would be a promise clawtilla
cannot keep, and the inbox reads a deadline as pressure.

An answer that is not recognisably an approval is a rejection.  A
=ClawtDecision= carries free text because an operator whose answer is
"neither, do X" is giving the most useful answer there is; VENTURE has
only two endpoints, and a misread "yes" writes to somebody's books
while a misread "no" leaves a card to answer again.

*** Polling, and what it costs

The confirmation queue has no change stream out of VENTURE, so this is
a poll -- on a timer attached to the daemon's context, never from a
request handler and never during daemon start.  The first poll is one
interval after the daemon comes up.

| Key                            | Default | What it does                             |
|--------------------------------+---------+------------------------------------------|
| =integrations.confirm_writes=  | =true=  | whether clawtilla polls this connector   |
| =integrations.poll_seconds=    | =60=    | how long between polls                   |

One timer covers every venture connector, so the shortest interval
anybody asked for is the one that runs.  A fleet with no venture
connector arms no timer at all.

=integrations.confirm_writes= does not switch staging on -- =venturectl
mcp= decides that for itself and stages by default.  Turning it off
here stops clawtilla polling, which leaves the staged changes in
VENTURE for somebody to find in its own web interface.

*** Whether the server stages at all

The first poll of each connector also asks =GET /api/v1/health=.  A
VENTURE too old for =?stage=1= *ignores* the parameter and applies the
write, answering as if all was well -- so a bridge that only read the
queue would show an empty inbox while the books changed underneath it.
When the answer lacks =staged_writes: true= the daemon warns once, and
the connector's health check (the row in every client, and ~clawtilla
integration check~) turns red with "this VENTURE server does not stage
writes".  A probe that could not reach the server is asked again on the
next poll rather than remembered as "does not stage".

A confirmation already raised is matched on its own id, so the same
card polled every minute for an hour is one decision, not sixty.  The
match is against the decision store rather than a set held in memory,
so a daemon that restarted does not raise everything again.

*** An answer is owed until it lands

A POST that fails is *kept* and retried on the next poll.  The operator
answered once and has no reason to look again; an answer that vanished
would leave the change waiting in VENTURE until its TTL dropped it, and
nobody would ever know.

That survives a restart too, and not because the queue is durable -- it
is not.  VENTURE still holding the card is itself the proof that the
answer never landed, so a card still pending against a decision the
store says was *answered* is queued again from what the store
remembers.

Dismissing a decision is left alone on purpose.  "I am not deciding
this" is not an answer to post, and VENTURE drops the card on its own
clock.

*** Telling an agent that a record changed

The bridge is a pull in the other direction: clawtilla asks VENTURE
what is waiting.  For a push -- "tell the bookkeeper when an invoice is
paid" -- VENTURE sends signed webhooks, and =provider: venture= on a
trigger verifies them, fills ={{kind}}=, ={{number}}=, ={{title}}= and
={{actor}}= from the envelope, ignores the agent's own writes with
=ignore_actors=, and catches up on the durable business-event lane
through this connector's token with =replay_connector=.  See
[[file:triggers.org::*Telling an agent that a VENTURE record changed][Triggers]].

*** What is still not done

- *A card cannot say which agent staged it.*  Several agents sharing one
  token are one actor to VENTURE, so the first agent in fleet order owns
  every card.  The fleet warns about the shared token for that reason.
- *The answer queue is in memory.*  Recovery after a restart relies on
  VENTURE still holding the card, which it does until its TTL.
- *VENTURE's inbox and coding runs are not alerts here.*  An agent can
  read them with =venture_inbox= and =venture_runs=; clawtilla does not
  poll them into its own alerts panel.

** The open MCP registry

The catalogue above is somebody's opinion, checked in.  The registry at
https://registry.modelcontextprotocol.io is nobody's opinion -- it is
whatever anybody has published -- so it is imported at a lower standard
of trust: an entry from it only ever *fills a gap*.  It never replaces a
built-in connector or one from ~connectors.dir~, both of which are a
choice somebody already made on purpose, and its ids are all prefixed
~registry:~ so one could never collide with a curated id even if it tried.

#+begin_src yaml
connectors:
  registry_enabled: true
#+end_src

Off by default, because turning it on is the one thing in this file that
reaches the network.  When it is on, the import happens on a timer of its
own -- never at daemon start, never inside the handler answering a
client's request -- into a cache under the daemon's state directory.
~connector.registry_refresh~ (~clawtilla connector registry-refresh~, or
the button on the Connectors page in either client) asks for one sooner
than ~connectors.registry_refresh_hours~ would.

#+begin_src bash
clawtilla connector registry-refresh
#+end_src

*** Why this is safe to leave off, and safe to test

~make test~ opens no network socket, which means nothing here is allowed
to either.  The importer is split so that only one function --
~clawt_connector_registry_refresh_async()~ -- ever calls out, and it is
never invoked by anything the test suite runs.  Everything the suite
*does* exercise is a pure function over a fixture: parsing one page of
the registry's own JSON shape, merging entries into a catalogue, and
reading or writing the cache file. That split is the same reasoning
CLAUDE.md already records against ~model.list~, which once asked five
provider APIs from an IPC handler and made pressing a button in the GTK
client feel like it had hung.

*** What an imported entry actually knows

The registry describes a server's *package* (an npm identifier, a
runtime hint like ~npx~ or ~docker~, and the environment variables it
needs) or its *remote* (a plain HTTP or SSE URL) -- never a client id,
and rarely anything OAuth-shaped.  So an imported connector is
~auth: api_key~ whenever a package names a secret environment variable,
and its credential name comes from the registry entry itself rather than
a guess.  A package naming no runtime hint clawtilla recognises falls
back to running its identifier as a bare command on ~PATH~, which is
right for a Rust or Go binary and wrong for an npm package that needs
~npx~ -- the registry does not say which its identifier is, and this file
is not going to guess twice.

** FOSS connector packs

Most of the catalogue's OAuth entries are commercial services.  The
things an operator running their own infrastructure actually reaches for
-- a Forgejo, a Home Assistant, a Grafana -- are shipped as example YAML
files under ~data/connectors.d/~ in the source tree, one per service,
ready to copy into ~connectors.dir~:

#+begin_src bash
cp data/connectors.d/gitlab.yaml $XDG_CONFIG_HOME/clawtilla/connectors.d/
#+end_src

They are examples on purpose and not installed automatically: a person's
own ~connectors.dir~ is theirs, and an upgrade silently adding entries to
it would be indistinguishable from a person's own file mysteriously
gaining content.

| Pack                | What it adds beyond a bare credential            |
|----------------------+---------------------------------------------------|
| ~gitlab.yaml~        | GitLab's own MCP server, ~/api/v4/mcp~ on your instance, once Duo is licensed |
| ~gitea.yaml~         | OAuth2, the same endpoints Forgejo forked from    |
| ~matrix.yaml~        | Tool access to a Matrix account -- see below      |
| ~home-assistant.yaml~ | A long-lived access token's variable name        |
| ~grafana.yaml~       | A service account token's variable name           |
| ~nextcloud.yaml~     | An app password's variable name                   |
| ~jellyfin.yaml~      | An API key's variable name                        |
| ~immich.yaml~        | An API key's variable name                        |
| ~paperless-ngx.yaml~ | A token's variable name                           |
| ~miniflux.yaml~      | An API key's variable name                        |
| ~vaultwarden.yaml~   | The OAuth2 client secret's variable name           |

*** Why most of these have no ~server_command~

The built-in table's own header comment gives the rule: no
~server_command~ unless the provider genuinely ships one under a name
stable enough to survive a release cycle.  As of this writing, GitLab is
the only one of these eleven with an MCP server run by the service
itself; every other one is either a community project with several
competing, sometimes explicitly unstable implementations (Forgejo,
Gitea, Vaultwarden), or a service whose official server runs three
different ways with three different invocations (Grafana's binary,
~uvx~, or Docker) such that naming one would be wrong for the other two.

That is not a gap in the pack -- the credential half is the hard,
fact-checkable part, and it is what these files get right.  Once you have
picked a server, name it on your own integration and it wins over
anything a pack or the built-in table says:

#+begin_src bash
clawtilla connector add gt --provider gitea \
    --command gitea-mcp-server --scope all
#+end_src

*** Matrix, twice

~matrix.yaml~'s ~id: matrix~ is a *connector* -- a tool an existing
session can call to read or post into rooms as an account you already
hold.  It has nothing to do with ~type: matrix~ in ~integrations.yaml~,
which gives an agent a chat identity of its own and is a completely
different feature that happens to share a name for the service, not for
the integration kind.  The two ids live in different tables (~provider:~
values under ~type: connector~, versus top-level ~type:~ values) and
cannot collide, but a person skimming the config could still read one for
the other, which is why it is spelled out here.

*** Writing your own pack

The template is every field ~clawt_connector_catalog_load()~ reads,
named:

#+begin_src yaml
connectors:
  - id: my-service            # required, lowercase, stable
    name: My Service          # shown in a list; defaults to id
    summary: One line about what connecting it gets you
    category: Whatever groups it in a list
    auth: api_key              # none | device | pkce | api_key
    auth_url: /oauth/authorize # device or pkce only
    token_url: /oauth/token    # device or pkce only
    revoke_url: /oauth/revoke  # optional
    scopes: "read write"       # what to request by default
    client_id_help: where to register an application
    docs_url: https://example.com/docs/auth
    default_instance: https://my-service.example  # only if self-hostable
    server_command: my-service-mcp  # only if genuinely stable -- see above
    server_args: [stdio]
    server_url: /mcp                # instead of server_command
    known_tools: [list_things, get_thing]  # what the server offers, if known
    placement: header           # env | header
    credential_name: Authorization
    credential_format: "Bearer %s"  # exactly one %s, or omit entirely
#+end_src

Three things worth getting right the first time:

- *One rule for every URL field.*  Setting ~default_instance~ makes
  ~auth_url~, ~token_url~, ~revoke_url~ *and* ~server_url~ all read as
  paths, joined onto whichever ~instance:~ the integration names.
  Leaving ~default_instance~ unset makes every one of them an absolute
  URL instead.  A pack that sets ~default_instance~ and then writes one
  field as an absolute URL anyway is how a connector quietly
  authenticates against somebody else's server -- ~gitlab.yaml~ is the
  worked example, and the test suite walks every shipped pack checking
  none of them do this.
- *~known_tools~ is optional and worth adding once you know it.*  An
  integration's own ~tools:~ narrows an agent to a subset; ~known_tools~
  is what the pack's author believes the *server* offers, so a typo in
  the former -- a tool name that is not in the latter -- gets a warning
  naming both, rather than silently narrowing an agent down to nothing.
- *~placement~ and the transport must agree.*  A ~server_url~ entry needs
  ~placement: header~, because there is nowhere else on an HTTP request
  for a credential to go; a ~server_command~ entry can use either,
  depending on what the server itself expects.  Setting ~server_url~
  with ~placement: env~ builds a plan with nothing in its header at all.

** Who gets it

The same three answers as any integration: one agent, some agents, or
the fleet.

#+begin_src bash
clawtilla connector add gh --provider github --scope all
clawtilla connector add gh --provider github --scope selected \
    --agents researcher,scribe
#+end_src

Sharing one connector across agents is the *point* of it, and unlike a
Matrix account there is nothing dangerous about it: a connector is a
credential the fleet reads through, not an identity two agents would
both answer as.

** Narrowing the tools

#+begin_src bash
clawtilla connector add gh --provider github --tools list_issues,get_file
#+end_src

Enforced in the relay, and enforced by *removal* rather than refusal: the
tools an agent may not use are taken out of its tool list rather than
rejected when called.  A tool that is advertised and then refused is
worse than one that was never there -- the agent plans around it, calls
it, and has to work out from an error that it never had it.

Leaving ~tools~ unset means every tool the server offers.  An empty list
is treated the same, rather than as a lockout nobody asked for.

** Servers with many tools

Every tool a server lists is read by the model on every call: its name,
its description and its input schema.  For a server with a dozen tools
that is the point of listing them.  For one with four hundred it is tens
of thousands of tokens spent before the agent has read a word of what it
was asked, on tools it will mostly never use -- and an API-model engine
refuses more than 128 tools a turn outright.

So the relay can present a big server as a *directory*: three tools that
stand in for all the others.

| Tool                        | What it does                                                        |
|-----------------------------+---------------------------------------------------------------------|
| ~<name>_search_tools~       | a few words in, the best matches out, each with a one-line description and its input fields; an empty query answers with what the server covers, area by area |
| ~<name>_describe_tool~      | one tool's exact description and input schema                       |
| ~<name>_call_tool~          | runs one tool by name, with its arguments                           |

~<name>~ is the connector's name, so a connector called ~forge~ offers
~forge_search_tools~, ~forge_describe_tool~ and ~forge_call_tool~.  The
search ranks with BM25 over each tool's name (counted double), its
description and the words in its schema, plus the tool's /area/ -- the
part of its name before the first underscore, so ~issues_create~ is in
~issues~.  A query that is a tool's exact name always finds that tool
first.

*** When a server is a directory

Each connector has a ~directory~ setting:

| Value    | Meaning                                                                    |
|----------+----------------------------------------------------------------------------|
| ~auto~   | a directory when the server is big *and* the agent's CLI does not search tools itself (the default) |
| ~always~ | a directory whatever its size and whatever the CLI                         |
| ~never~  | every tool listed, however many there are                                  |

"Big" is more than ~connectors.directory_min_tools~ tools (default 40)
or more than ~connectors.directory_min_chars~ characters of tool
definitions (default 100,000) -- names, descriptions and schemas
together, which is what the model actually reads.  Both are counted
/after/ the connector's ~tools:~ narrowing, because that is the list the
agent would otherwise get.

#+begin_src bash
clawtilla integration set forge directory=always
#+end_src

*** Which CLIs search tools themselves

Claude Code does: past about a tenth of its context in MCP tools it
defers them and looks them up as it needs them.  Wrapping its servers in
a second search would make it search a search, so under ~auto~ its
agents get every tool as before.  ~claude-tmux~ runs the same binary and
is answered the same way.  Every other CLI -- opencode, grok-build,
antigravity, cursor -- reads the whole list on every call, and gets the
directory.

Whether a CLI searches is a fact about the CLI, and belongs to ai-glib as
a class datum beside ~AiCliClientClass.config_dir_env~.  ai-glib has no
such datum yet, so clawtilla answers it in one place,
~clawt_mcp_directory_cli_searches_tools()~, until it does; the roadmap
carries the move upstream.

*** The search finds only what the agent may use

The directory is built from the tool list *after* the permitted-list
filter, and a call through it is checked against that same list again on
the way out.  The predicate and the builder answer from one list, so a
tool this agent may not use cannot be found by the search, is not
described, and cannot be run through ~<name>_call_tool~ -- the directory
answers "No tool named ... here" for it, in exactly the words it uses
for a tool that does not exist, so the search cannot be used to learn
what was withheld.

*** Approvals name the tool that runs

A call through the directory becomes an ordinary ~tools/call~ naming the
inner tool /before/ anything checks it.  The permitted list, an action
rule (~policy.check~) and an approval card therefore all see
~pulls_merge~, never ~forge_call_tool~.  A search or a describe runs
nothing on the server and asks nobody.

The same decision is made for a connector reached over HTTP.  Until this
release the HTTP bridge applied the permitted list and skipped the
action-rule gate entirely; both transports now go through one function,
~clawt_mcp_relay_policy_outbound()~.  A JSON-RPC batch is refused
whenever a gate or a directory is in the path, since either reads one
call per line and a batch would carry its calls past both.

*** Big tool lists arrive in pages

An MCP server may answer ~tools/list~ a page at a time.  When the relay
might present a directory it follows ~nextCursor~ itself and answers the
client once, with either the three directory tools or the whole list as
a single page.  It stops after 64 pages and says so on stderr.  When it
may not present one (~never~, or Claude Code under ~auto~) every page
passes through untouched and is only counted.

*** How big a server is, and where that shows

clawtilla never starts a connector's server itself -- the relay does, on
an agent's behalf, with the credential.  So the relay reports what it
saw to the daemon (~connector.tools_seen~) whenever a full tool list
arrives, and the daemon keeps the last report per connector in
=<state_dir>/connector-tools.yaml=.  That is what the Connectors page in
every client and =clawtilla connector list= show: the tool count, the
characters of definitions, and whether agents get the server as a
directory.  A connector no agent has used yet says its size is unknown,
never zero.

The agent's =TOOLS.org= describes a directory server as one: "search
it", with the three tool names and the area overview from that report.
It does not enumerate the tools, even a narrowed ~tools:~ list, since
listing four hundred names there would put back into every prompt the
text the directory exists to keep out.  Under ~auto~ a server no relay
has counted yet is described as a list; the agent's next start, after a
relay has seen it, says the right thing.

** Renewal

An access token often lasts an hour.  The daemon renews any that is
within ~connectors.refresh_margin_seconds~ of expiring, on a timer of its
own -- not when a tool server starts, because a server started with a
token that expires forty minutes later keeps running with it, and the
agent's first failure would arrive long after anything could connect the
two.

=clawtilla connector list= shows how long is left.  An expired
credential that can renew itself reads as connected, not as broken:
showing it as broken would light up the list every hour and teach you to
ignore the one that genuinely is.

*** ~expires_in~ is a duration, and is stored as a moment

The wire carries ~expires_in: 3600~.  Kept as it arrived, that reads as
"an hour from now" every time anything looks -- so a token that expired
overnight looks an hour fresh each morning, the renewal never fires, and
every call made with it fails somewhere else entirely.  It is converted
when the response arrives and stored as ~expires_at~, an absolute time,
and the field in the token file is *named* ~expires_at~ so the next
reader is not invited to add it to the moment they loaded it.

Providers also disagree about whether these are numbers or strings.
Reading only one silently treats the other as absent, which gives either
a token that never expires or one that expires immediately; both forms
are read.

*** Granted scopes are never written back over requested scopes

A person can untick things on a consent screen, so what was granted is
often less than what was asked for.  Storing the granted set into
~scopes:~ would mean the next authorization asks for less, and the one
after that less again -- a permission that quietly erodes every time it
is renewed, with nothing to say why.

So ~scopes:~ stays what you asked for.  What was actually granted lives
in the token file, and the daemon reports it separately, as
~granted_scopes~ on the ~connector.list~ reply.

Read the two as different questions.  ~scopes:~ answers "what will the
next authorization ask for"; ~granted_scopes~ answers "what does this
credential currently do".  They agree until somebody unticks something,
which is exactly when the difference matters.

An empty refresh token is likewise never written over a good one.  Some
providers omit the field on a renewal, meaning "keep the one you have",
and taking that literally costs an authorization nobody can see the
reason for.

"Empty" now means what it says.  The guard tested for a *missing* field,
and a provider answering with ~"refresh_token": ""~ produced a non-NULL
empty string that every ~!= NULL~ test downstream read as a value -- so
the blank was stored over the good one and the guard written to prevent
exactly that could not see it.  An empty member is treated as an absent
one at the point the response is parsed, rather than at each of the
places it is read, so no later test can be fooled the same way.  The
symptom was a slow one: the current access token kept working for its
hour, and every renewal after that failed.

** Revoking

#+begin_src bash
clawtilla connector revoke gh
#+end_src

The local copy goes whatever the provider says -- you asked for the fleet
to stop using it now, and a provider that is unreachable must not leave
an agent holding a working credential until the network comes back.

Where the provider offers a revocation endpoint, clawtilla calls it and
says so.  Where it does not, clawtilla says *that*, because deleting our
copy is not revocation: a token you forgot still works for anybody who
has it, for as long as the provider says, which for a refresh token can
be months.  Finishing the job means withdrawing it in their settings.

** What the agent is told

The managed region of the agent's =TOOLS.org= gains a paragraph per
connector, and it says three things the tool list cannot:

- these tools reach a real account belonging to a real person, so
  reading is cheap and anything that writes or sends is worth being sure
  about;
- the agent does not have the credential and cannot get it, said out
  loud so it is not discovered by trying -- an agent that goes looking
  wastes turns and leaves something alarming in a transcript;
- which scopes the connector was configured with, so it does not spend
  turns discovering one call at a time that something was refused.

That last one is the ~scopes:~ key -- what was *asked for*, not what the
provider granted.  The two are the same unless somebody unticked
something on the consent screen, and where they differ the agent is
reading the more generous of the two.  The granted set is on the
~connector.list~ reply as ~granted_scopes~; nothing puts it in front of
an agent yet.

** Troubleshooting

*** "not connected yet"

No credential has been stored.  Either =clawtilla connector key <name>=
or =clawtilla connector connect <name>=.

*** "no connector called 'x'"

The ~provider~ names a catalogue entry that does not exist.  The error
names ~connectors.dir~ as well, because the fix is usually a file that
adds it.

*** The flow says the code expired

Device codes are usually good for fifteen minutes.  Start again; nothing
is left behind.

*** The agent has the connector but no tools

The catalogue entry has no server and the integration named none, so
there was a credential and nothing to use it with.  Set ~command~ or
~url~ on the integration.  =clawtilla connector catalog= shows which
entries know a server.

*** An agent says a tool is not permitted

The connector was narrowed with ~tools~.  The refusal names the tool and
says so.

*** A warning names a tool the connector does not offer

The integration's ~tools:~ names something the pack's own ~known_tools~
does not.  Almost always a typo; fix the integration.  A pack that
declares no ~known_tools~ at all -- the ordinary case -- never warns
about this, since there is nothing here to check against.

*** The agent sees three tools instead of the server's

The connector is presented as a directory: its server is past one of the
thresholds and the agent's CLI does not search tools itself, or its
~directory~ is ~always~.  Search it with ~<name>_search_tools~, or set
~directory: never~ on the connector to list every tool again.  See
"Servers with many tools".

*** "No tool named ... here" from a directory

Either the tool does not exist or the connector's ~tools:~ does not
include it.  The directory says the same for both on purpose.

*** "connectors.registry_enabled is off"

~connector.registry_refresh~ refuses until you turn the key on.  Nothing
imports until then, and nothing was ever asked of the network before
this point either.
