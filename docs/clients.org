* Clients

Four front ends, one daemon.  None of them holds state or a transport of
its own, which is why two of them open at once agree with each other.

The two graphical ones -- ~clawtilla-gtk~ and ~clawtilla-web~ -- are held
to the same feature set by ~make parity~, so a capability added to one is
a build failure until it exists in the other.

** The CLI

#+begin_src bash
clawtilla [OPTION...]
clawtilla <command> [ARGS...]
#+end_src

Global options: ~-c/--config~, ~-s/--socket~, ~-V/--version~,
~--license~, ~--generate-config~, ~--generate-systemd-service~.

Subcommands are dispatched on ~argv[1]~ before option parsing, and each
owns its own option context.  One shared table across a dozen verbs
collapses into mutually exclusive flags that are each valid for one verb,
and the ~--help~ output stops being readable.

*** Reaching a daemon on another machine

Every verb takes ~--host~, ~--port~ and ~--token~, or ~--profile~ to use
one saved earlier:

#+begin_src sh
# On the machine running the fleet
clawtilla daemon token

# On the machine you are sitting at
clawtilla remote add workstation 100.72.0.41 --token "$(ssh box clawtilla daemon token)"
clawtilla --profile workstation agent list
clawtilla --profile workstation send researcher "how far did you get?"
#+end_src

~--host~ beats ~--profile~, which beats the local socket.  The explicit
address is both last-resort and first-priority for the same reason: it is
what you reach for when a saved profile is the thing you are working
around.

~daemon token~ reads the token from disk rather than asking the daemon
for it, because nothing may write a secret's value into an IPC response.
That also means it only works on the machine the daemon runs on, which is
the point -- it is how you get the token to copy somewhere else.

~remote list~ never prints a token.  It is the command you run to check
what you saved, often over somebody's shoulder.

The profiles live in ~$XDG_CONFIG_HOME/clawtilla/connections.yaml~, mode
0600, and are shared with the GTK client's connection menu.  They are in
the *client's* config rather than in ~clawtilla.yaml~ on purpose: the
point of a profile is to reach a daemon that is somewhere else, and a
laptop connecting to a workstation may have no fleet, no state directory
and no ~clawtilla.yaml~ of its own.

*** Choosing where the daemon listens

~clawtillad~ takes ~--bind~ and ~--no-bind~, and its ~--help~ prints what
this machine would listen on with neither:

#+begin_example
Listening, with no --bind:

  unix     /run/user/1000/clawtilla/daemon.sock
  tailnet  100.72.0.41:8792  (daemon.tailscale: true)
  tcp      off (daemon.tcp_enabled: false)
#+end_example

The real address and the real port, not a description of them -- the
whole reason to reach for these flags is wanting to know, and change,
exactly that.

#+begin_src sh
clawtillad --no-bind                    # unix socket only
clawtillad --bind 127.0.0.1:8792        # somewhere specific instead
clawtillad --bind 10.0.0.5:9000 --bind '[fd7a:115c:a1e0::1]:9000'
#+end_src

~--bind~ *replaces* the network addresses rather than adding to them, so
a daemon told where to listen is not also listening somewhere it was not
asked to. It is repeatable, and each address carries its own port; the
port defaults to ~daemon.tcp_port~ when one is not given.

An address you name must bind. That is the difference between it and the
tailnet address, which clawtilla chose for you and only warns about: a
stale process holding the tailnet port should not stop the fleet, but a
daemon that ignored where you told it to listen and started anyway would
be running somewhere you did not know about.

Addresses are parsed before anything is created, so a typo is refused
while you are still looking at the command line:

#+begin_example
clawtillad: --bind: 'localhost' is not a numeric address; clawtillad binds
addresses rather than resolving names
#+end_example

Names are refused rather than resolved on purpose: resolution is a
network round trip on the path that starts the daemon, and a name can
resolve to an address on a different network than the one intended.

IPv6 with a port needs brackets -- ~[fd7a:115c:a1e0::1]:9000~ -- because
an address full of colons has no last-colon to split on. Without a port,
a bare ~fd7a:115c:a1e0::1~ is fine.

*** Exit statuses that mean something

- ~computer exec~ exits with the *command's* exit status, so
  ~clawtilla computer exec … && next-thing~ behaves the way a shell user
  expects
- ~integration health~ exits non-zero if any check failed, so it is
  usable in a pre-flight script
- a subcommand with no arguments prints usage and exits non-zero

*** Connecting an account

#+begin_src bash
clawtilla connector catalog
clawtilla connector add gh --provider github --account work \
    --command github-mcp-server --scope all
clawtilla connector key gh          # reads stdin with the echo off
clawtilla connector list
#+end_src

There is deliberately no =--key= flag, for the same reason there is no
=--password= on the Matrix login: an argument is in your shell history
and in the process table.

=clawtilla connector relay <name>= is the verb an agent's =.mcp.json=
names.  It speaks MCP on stdout and is not for people.

See [[file:connectors.org][connectors.org]].

*** Signing in to Matrix

#+begin_src bash
clawtilla integration add home matrix
clawtilla integration matrix-login home matrix.example.org researcher
#+end_src

The password is read from stdin, and from a terminal without echoing.
There is deliberately no ~--password~ flag: an argument is in the shell
history and in the process table for as long as the command runs, which
is long enough.

Piping works too, for a script:

#+begin_src bash
pass show matrix/researcher | clawtilla integration matrix-login \
    home matrix.example.org researcher
#+end_src

Nothing secret comes back.  The token is written to a file on the
daemon's disk and the config is given its path; the reply says which
file, and the user id the server assigned.  See
[[file:integrations.org][integrations.org]].

** The GTK client

#+begin_src bash
clawtilla-gtk [--socket PATH]
#+end_src

GTK4 and libadwaita.  Agents are presented as chats: a sidebar of who is
here, a transcript in the middle, and everything else about an agent
behind a tab rather than a settings dialog somewhere else.

*** A VM agent's hardware

Cores, memory, disk and screen size sit together in the agent editor,
because they are what the machine is made of.

Screen size is a list of the common ones.  A size set by hand or from
another client that is not among them is added to the list rather than
ignored -- a combo box cannot say "something else", and without that,
opening the page and saving it would quietly replace a chosen size with
the first entry.

It is also the only one of the four that does not need the guest
rebuilt: it reaches the virtual GPU rather than the cloud-init seed, so
it applies at the VM's next boot.

*** Teams in the sidebar

Agents are grouped under their team, with a header showing how many of
that team are running out of how many there are -- running out of total
rather than one number, because "3" could be either and the question
somebody scanning a sidebar is asking is how much of this team is awake.

Click a header to fold the team away. The tally stays, which is what
makes folding safe: a collapsed team still says what is behind it.

Which teams are folded is kept in the client, not in ~clawtilla.yaml~.
It is a view preference like the fonts -- it belongs to the person at
this screen rather than to the fleet, and syncing it between machines
would be actively wrong.

Agents with no team come *first*, because that is where the chief of
staff lives; putting them last would bury the agent you talk to most
under every team in the fleet. Teams follow in ~teams.order~, and agents
within a team in their own ~agents.order~, so dragging still works
inside a group.

An agent on a team the daemon does not declare still appears, under that
team's id. Hiding it is how a typo in ~agents.team~ survives being looked
at.

*** Teams

The Teams page in Settings creates them, edits their name and
description, and removes them. Removing one leaves its agents running and
says how many are now teamless, rather than silently moving them
somewhere nobody chose.

An agent's team and its role on it are also in the agent editor, beside
the chief-of-staff switch -- the three answer one question between them:
who this agent may hand work to.  Moving one agent is quicker from the
sidebar's right-click menu; the editor is where the *role* is set, and
where a team is changed as part of a wider edit.

*** Spending

The Spending page lists one row per agent with what it has cost and how
many turns it took, a fleet total, and a period selector -- all time,
today, the last 7 or 30 days.

The cost is the figure the provider reported for each turn, not an
estimate.  The token counts beside it cover new input and output only:
cached context is billed but is not reported as tokens, so the cost is
larger than those numbers suggest.  See [[file:spending.org][Spending]].

*** Reordering the fleet

Drag a row in the sidebar to move it -- a chief-of-staff to the top, the
testers to the bottom.  Dropping on the upper half of a row puts it
above, the lower half below, which is what makes the last position
reachable at all.

The order lives in ~clawtilla.yaml~ as ~agents.order~, not in the
client.  It is about the agents rather than about reaching them, so it
is the same in every client and on every machine -- the opposite of a
connection profile, which exists precisely because the daemon is
somewhere else.  Numbers go up in tens, leaving room to place one agent
between two others by hand.

Agents that share a number keep the order the file has them in, so a
fleet nobody has dragged comes back exactly as it was written.

*** Dragging an agent onto a team

The same drag also *changes* an agent's team, which is the quickest way
to divide a fleet up.

- Drop it on a *team heading* to put it on that team.  The heading names
  a group rather than a position, so where it lands inside the team is
  left alone.
- Drop it on an *agent row belonging to another team* to do both at once:
  it joins that team and goes exactly where you put it, above or below by
  which half of the row you let go over.
- Drop it on a row in its *own* team and nothing changes but the order,
  as before.

Dropping among another team's agents has to change the team, not only the
order.  The daemon returns the fleet grouped, so an agent merely
reordered under somebody else's heading is sorted straight back under its
own the moment the sidebar redraws -- a drop that visibly worked and then
undid itself, which reads as the sidebar being broken rather than as the
gesture meaning something narrower than it looked.

The heading lights up as a drop target while an agent is over it, using
GtkListBox's own highlight so it follows the theme.  Without that the
only way to discover the gesture is to try it and watch the drag snap
back -- which is also what "not a drop target" looks like.

*** Every team has a heading, including the empty ones

A team the fleet declares gets a heading whether or not anybody is on it,
and there is always a *No team* heading.

Both are there because a heading is what an agent is dropped onto.
Without the first, a team created a moment ago in Settings cannot be
filled by dragging -- which is exactly when somebody would reach for it.
Without the second, a fleet where every agent has a team has nowhere to
drag one back out to, and the gesture works in one direction only.

Their tallies read =0/0=, which is honest, and the fleet's shape is
visible at a glance rather than only through the teams somebody happens
to have populated.

The order is the daemon's, not a second opinion about it: teamless first,
then teams as ~team.list~ gives them, which is the array the daemon sorts
by.  A team an agent names that nobody declared still appears, under the
id it named, after all the declared ones.

*** Deleting an agent, and what goes with it

The confirmation offers two things, both off:

- *its container or VM* -- otherwise it keeps running under a name
  derived from an agent that no longer exists
- *everything it owns* -- its persona, notes, mailbox, memories,
  transcripts and credentials

The second is there so a throwaway agent made to test something can be
thrown away.  Removing an agent from the fleet is reversible and
deleting what it wrote is not, which is why it is asked for rather than
assumed.

#+begin_src bash
clawtilla agent rm scratch --with-computer --purge
#+end_src

Every removal is fenced: a path that is not inside the state directory
or the configured workspace root is refused rather than removed.  Those
paths come from a file somebody edits, and there is no undo on the far
side of this.

*** Settings

The hamburger beside the *+* button, at the top of the sidebar.  It holds
what belongs to the application rather than to any one agent:

| Page | What it is for |
|------+----------------|
| Cloud images | VM disk images on this machine, and fetching more |
| Teams | how the fleet is divided, and what each team handles |
| Spending | what each agent has cost, and the fleet total |
| Integrations | Matrix, mail, MCP servers and notifiers, and who gets each |
| Connectors | connected accounts, and the credential for each |
| Appearance | colour scheme and fonts |

**** Cloud images

That page lists the VM disk images on this machine with their size and
where each came from, offers the suggested ones, takes an ~https~ URL of
your own, and draws a bar per download.  A download is the daemon's, not
the window's: closing Settings does not stop one, one begun with
~clawtilla image vm get~ appears here while it runs, and a failure is
said out loud as a toast even if this window is shut -- otherwise an
image would simply never appear, with nothing anywhere saying why.

See [[file:computers.org][computers.org]] for what to do with one.

**** Integrations

Everything configured once and pointed at one agent, some agents or the
whole fleet.  *+* adds one; the type decides which fields appear, so a
Matrix instance asks for a homeserver and rooms while a notifier asks for
a backend and quiet hours.

Two things here do real work rather than editing a file.  *Sign in* runs
a Matrix password login and stores the resulting token in a 0600 file --
the token never comes back to this window, which is the whole point of
doing it in the daemon.  And *Send a test* delivers a notification
immediately, ignoring both the event list and quiet hours, because a
notifier that is working correctly is indistinguishable from a broken one
by looking at it.

Each agent's own Integrations group, in the agent inspector, shows which
of these that agent actually has and whether each is healthy.

See [[file:integrations.org][integrations.org]].

**** Connectors

Connected accounts.  *+* lists the catalogue with the auth kind beside
each name, because that decides what happens next: a device connector
needs a client id, an ~api_key~ one needs a token pasted.

Clicking a connector offers /Authorize again/, /Paste a token/, /Renew
now/, /Revoke/ and /Remove/.  Authorizing shows the user code as the
dialog's heading at full size -- it is about to be read off this screen
and typed into a phone -- and waits there while you do it.

The list shows three states rather than two.  A credential that has
expired *and can renew itself* reads as connected, because it is: the
daemon renews it on a timer.  Showing that as broken would light the list
up every hour and teach you to ignore the one that genuinely is.

See [[file:connectors.org][connectors.org]].

**** Appearance

Colour scheme, and the fonts.

| Setting | What it covers |
|---------+----------------|
| Colour scheme | Follow the system, Light, or Dark |
| Interface font and size | Everything but code -- sidebar, messages, dialogs |
| Code font and size | Code blocks and inline code in a conversation, and the exec console |

Changes apply as you make them and are saved at once. A preview you can
see but which is not yet saved is the worst of both: it looks applied,
and closing the window loses it.

*An empty font, or a size of 0, means "use whatever the desktop says",*
and that is the default. It is deliberately not the same as naming the
font your desktop currently uses -- a named one stops following it, so
changing your desktop font later would leave this one app behind. The
clear button beside each font goes back to following; a font chooser has
no way to express that, which is why the button exists.

**** A palette has to speak both dialects

~@define-color~ and the ~--token~ custom properties are two namespaces,
not two spellings of one, and *libadwaita's own rules read only the
second*.  A palette emitted as ~@define-color~ alone therefore styles
this client's own rules --- which do read ~@token~ --- and leaves every
libadwaita-drawn accent, error, success and warning at stock GNOME.  A
Catppuccin build drew GNOME blue and red icons on a Mocha surface.

Measured on libadwaita 1.9.3 with the shipped values, forced dark: the
palette as it stood was byte-identical to having no palette at all, and
only a ~:root~ block moved anything.

So both forms are emitted for every token, and the second is *derived*
from the first --- thirty-seven hex values maintained twice would drift
the first time somebody added a colour.  The transform is exactly
libadwaita's own naming, ~accent_color~ to ~--accent-color~, and a line
that is not a ~@define-color~ is skipped rather than guessed at.  Which
tokens bridge between the two namespaces is undocumented and has moved
between releases, which is why the only correct answer is both.

**** Three stylesheets, with stated priorities

- the structure sheet at ~PRIORITY_APPLICATION~, loaded once
- the generated appearance sheet at ~PRIORITY_APPLICATION + 1~
- ~$XDG_CONFIG_HOME/clawtilla/style.css~ at ~PRIORITY_USER~, when it
  exists

They were one concatenated string before, which re-parsed a constant on
every settings change and left nowhere for a person to put a rule of
their own: anything they wrote would have had to out-specify code they
did not write, at the same priority.  Precedence between the first two
is unchanged --- appearance came last in the concatenation and so won
ties, and it sits above structure now.

~@define-color~ does cross a provider boundary, which had to be checked
rather than assumed: the structure sheet is written entirely in
~@token~ references while the palette that defines them is in the other
sheet, and an unresolved reference falls back to libadwaita's value
with no parse error and no warning.

The client also names its own widgets --- ~#clawt-transcript~,
~#clawt-composer~, ~.clawt-chat-run~, ~.clawt-avatar~ and the rest ---
because a stylesheet cannot target what has no name, and before that
the only things addressable were libadwaita's element names.  Nothing
is styled by having a name; a selector nobody has written a rule for
draws nothing.

The settings live in ~$XDG_CONFIG_HOME/clawtilla/appearance.yaml~:

#+begin_src yaml
theme: 'dark'
font: 'Cantarell'
font_size: 12
monospace_font: 'JetBrains Mono'
monospace_size: 10.5
#+end_src

Not in ~clawtilla.yaml~, for the same reason connection profiles are not
-- and the reason is sharper here, because the client can switch daemons
while it is running. Fonts that came from a daemon's config would change
when you connected to a workstation and change back when you went home.
They are per-machine by nature too: the size that is right on a laptop is
not the size that is right on a 4K panel, and that is often the same
fleet seen from both.

A size outside 6--48pt is clamped rather than refused. This file invites
hand-editing, and a 2 or a 2000 in it would make the settings dialog
unreadable and therefore unable to fix itself.

*** The sidebar

Each agent shows a state dot, what it is doing, and badges:

- a filled *unread count* when that agent has said something to you that
  you have not opened -- see below
- a red *HOST* badge when the agent can run commands on the real machine
- a *CHIEF* badge on the chief of staff

Mail waiting for the *agent* is in the subtitle -- =3 waiting to be
read=, or =working… · 3 waiting= when it is mid-turn -- rather than as a
second number beside the unread count.  Two numbers in one narrow row,
both about "messages" and meaning opposite things, is not readable.

Colour is never the only signal: the state is in the tooltip and in the
inspector, and a row with unread messages has its name in *bold* as well
as the pill.

*** Alerts

A collapsible panel on the right of the GTK client, bound to a bell in
the header bar; an =/alerts= page in the web client, reached from the
sidebar.  Both carry a count.

**** An alert that lands in front of you arrives read

An unread count means "one you have not seen".  Both clients used to
record every alert unread and clear the lot when the surface was
*opened*, which is right for one that arrives while the panel is closed
and wrong for one that lands in front of somebody: it was inserted
unread, bumped the badge, and went on counting until the reader closed
the panel and opened it again --- a number pointing at a row they had
watched appear.

~clawt_alert_arrives_read()~ decides it for both clients.  The routine
tier arrives read whatever is on screen, because neither badge counts
it and a flag no badge reads is one a later widening of the filter
would silently start believing.

One visible consequence, worth knowing rather than discovering: a row's
unread highlight follows the same flag, so an alert arriving into an
open panel no longer draws it.  That is consistent --- the highlight
means /not yet seen/, and it has been --- but keeping both the honest
badge and an arrival highlight would need a third state, which is a
larger decision than the fix.

**** Why a surface, and not a toast

Of the 89 places the GTK client raises a toast, **two** are
notifications: a download that failed, and a message the loop guard
refused.  Everything else --- /Saved./, /An agent needs an id./, /That is
not a port./ --- answers a question the operator is holding right now, in
a dialog, waiting to know why the button did nothing.

So the split is by *origin*, not by severity:

| where it came from | where it goes |
|--------------------+---------------|
| it arrived on its own | the panel, and no toast |
| it answers something you just did | it stays a toast |

Filing the second kind into a drawer would be a serious regression, and a
panel whose first twenty rows are /Saved./ buries the one line that
matters.  ~clawt_window_toast()~ is unchanged and so are its other 87
call sites.

**** One list, with a filter

An alert is an event that demanded attention; a routine entry is one that
did not.  Same stream, different weight --- so one list and a filter that
widens it, rather than two tabs.  Two tabs would mean deciding at write
time which tab a thing belongs in, and the interesting case is exactly
the routine event that turns out to matter: a filter lets you widen after
the fact, a tab makes you guess before.

Three tiers, and **only two are coloured**:

| tier | how it is drawn |
|------+-----------------|
| Error | a card with a red edge, body-size text |
| Notice | the same shape, accent instead of red |
| Routine | no card --- one line of quiet caption text |

If everything carries a colour, colour stops meaning anything, and
routine entries are the majority the moment the filter widens.  Making
them quiet is what keeps the loud ones loud.  Severity is carried by
weight and container as much as by hue, so it survives a colourblind
reader and a Catppuccin palette alike.

Which tier an event lands in is ~clawt_alert_tier_for_event()~, in
libclawt, for the same reason: both clients classify the same stream, and
two implementations of that rule differ exactly once --- on the kind
somebody adds next.  It takes the *event* rather than a kind and a loose
string, because which detail decides the tier varies per kind
(~agent.state~ reads =state=, ~image.finished= reads =error=) and a
caller passing the wrong one would classify silently and wrongly.  Only
the wording of a row is decided in the client.

**The count never includes routine entries.**  Otherwise it would be
permanently non-zero and would stop being read, and widening the filter
is a thing you choose rather than something that should change the
number.

**** Scope, and how far back

Fleet-wide.  Alerts fire about agents other than the one being read ---
that is the whole reason the surface exists --- so scoping to the
selected agent by default would hide exactly the cross-agent case that is
hardest to diagnose.  Every row names its agent, and clicking that name
narrows to it and raises a chip that clears the scope again.  One control
for scope, no second dropdown.

The most recent 200 are held in memory, session-scoped.  For anything
older there is ~event.list~, which reads the daemon's own
~ClawtEventLog~ --- NDJSON under the state directory, written since the
daemon was first built, swept on ~daemon.event_log_days~, and until now
read back by nobody.  That is the honest answer to "does it survive a
restart": the surface does not and does not need to, because the log
does.

**Opening it marks everything read.**  Rows stay until they are
dismissed, or until *Clear all*, so nothing is lost by the count going to
zero.

**** Where it sits

In the GTK client the panel is a second ~AdwOverlaySplitView~ *inside*
the existing one's content, not wrapping it: opening alerts must not hide
the agent list, because that is navigation, and losing your place while
reading a notice about something else is the same failure as a toast
covering the composer.

320px, which is load-bearing rather than conventional: 281 for the agent
list plus 600 for the transcript's clamp plus 320 comes to 1201, so on an
ordinary window all three fit and *the transcript does not move when the
panel opens*.  Below 1200px it overlays instead --- the number is derived
from those three widths, not chosen.

*** Unread

A filled pill at the trailing edge of the row, and the fleet-wide total
on the *Chat* tab.  It counts messages an agent sent *to you* while you
were looking somewhere else -- a different agent's conversation, or a
different page.

This is not the same as the transcript's *New messages* rule, and the
two never fire for the same message:

| where the message landed | what says so |
|--------------------------+--------------|
| the conversation on screen, below the fold | the *New messages* rule and pill, no count |
| any other conversation | the sidebar count, and the total on Chat |

So a conversation that is on screen never accrues a count, whatever the
scroll position.

*Opening the conversation is the only thing that clears it.*  Not
scrolling, not the window gaining focus, not time passing: a counter that
decays on its own is a counter you stop trusting.

*The Chat tab is not badged while you are reading Chat* with the sidebar
open, because the sidebar beside it is saying exactly /which/ agent --
strictly more information.  With the sidebar collapsed to a drawer the
badge stays, since then nothing else is saying so.

**Both clients ask the same function.**  ~clawt_unread_should_count()~ is
in libclawt and takes the four conditions --- not your own, not the room
on screen, not a replay, and a room that is somebody's conversation with
the operator.  It was written twice before that, once per client, which
is the shape of drift =make parity= exists to catch and cannot see: a
rule that decides a number sends no frame and answers no command.

Two limits, stated rather than buried:

- *It is what arrived while this client was connected.*  It does not
  survive a restart, and it deliberately ignores the events the daemon
  replays when a client subscribes -- those may well have been read in
  the previous session, and counting them would open a fresh window
  already showing a number for a conversation nobody has touched.
- *In the web client the count belongs to the server, not the browser.*
  ~clawtilla-web~ binds the loopback and the tailnet for one operator; a
  second browser would share the counts rather than get its own.

The number is not capped at =99+=.  The usual justification is width and
it is measurably false: at the client's caption size =99+= is wider than
the three-digit number it would replace.

Agents with unread messages do *not* float to the top.  The list is
grouped by team and hand-ordered, and a list that rearranges itself under
your hand costs the spatial memory that makes a sidebar fast to save you
a glance.

*Right-click an agent* for Start, Stop, Restart, its *Team*, and Delete.
These are on the Agent tab as well, but reaching them there means leaving
the conversation, acting and coming back -- three navigations for the
thing you do to an agent most often.  A long press does the same on
touch, where there is no second button.

The *Team* submenu lists every team the fleet declares, with =No team=
first, and *ticks the one this agent is already on* -- so the menu
answers "where is this" as well as offering to move it.  Choosing an
entry writes ~agents.team~ and the sidebar regroups; the agent keeps
running throughout, since a team decides who may hand it work rather than
anything about how it runs.

An agent naming a team nobody declared gets an entry of its own, under
the id it named.  Without that the tick would land on =No team= and
moving the agent away would look like it had done nothing -- and a typo
in ~agents.team~ is exactly what somebody opens this menu to fix.

The teams offered are the ones the sidebar was drawn from a moment ago,
not a fresh question to the daemon: a menu has to appear at once.

Right-clicking selects the agent first, so the menu always acts on the
row under the pointer rather than on whatever was selected before.
Entries are greyed out by the same rules the inspector's buttons use:
Stop is unavailable on a stopped agent, Start on a running one, and a
shadow agent -- one whose configuration did not parse -- offers no
lifecycle verb at all, because the daemon would refuse every one of
them.  Delete sits in its own section so it is never the neighbour of
Restart, and still asks twice.

*** The tabs

| Tab | What it is |
|-----+------------|
| Chat | the transcript, with bottom-follow that does not yank you down mid-read, and an activity line under it |
| Agent | edit name, description, provider, model, effort, computer, restart policy, autostart and chief-of-staff; credentials by reference; start/stop/restart; delete |
| Mailbox | what is waiting, with acknowledge |
| Computer | an exec console showing stdout *and* stderr |
| Routines | standing work for this agent: the schedule, when it last ran and what happened |
| Tasks | what has been delegated to whom, and where it got to |
| Flow | every conversation between agents, newest first, and what was said |

The Routines tab puts the presets in front -- Manual, Hourly, Daily,
Weekdays, Weekly -- and cron behind /Custom/, because most standing work
is one of the five and nobody should have to write ~0 9 * * 1-5~ to get
weekday mornings.  A routine that did not fire because the machine was
asleep is shown as *missed*, not failed: showing it as broken would train
you to ignore the one that is.  See [[file:routines.org][routines.org]].

*** The transcript

A conversation is drawn as *runs* rather than as one row per message.  A
run is consecutive messages from one sender: it gets one header --- an
avatar, the name, the time --- and the messages tuck under it at the same
indent, tight inside the run and further apart between them.  That
grouping is what makes a stack of paragraphs read as a conversation.

A run ends at a different sender or at a day boundary, and deliberately
*not* at a time gap: a fifteen-minute rule would be a constant with
nothing behind it, and agent traffic arrives in bursts where it would
fire constantly.  ~clawt_chat_run_is_start()~ decides it, in libclawt, so
the two clients cannot disagree about where a run begins.

**** Bubbles on one side only

The operator's own turns are bubbles; the agent's are not.

An agent's turn runs to dozens of lines with headings, lists and code
blocks.  A container that long stops reading as a message and starts
reading as a panel, and a bubble wide enough to *be* a bubble is too wide
to have a measure --- the two constraints pull opposite ways, and only
one side of this conversation is short enough to satisfy both.  So the
bubble goes where it works.  The asymmetry is not a compromise; it is
what tells you who is speaking at a glance.

Within a run the second and later bubbles drop the corner nearest the one
above, which makes a run read as one utterance rather than a stack.

**** Avatars

Initials and a colour derived from the name, which needs no
configuration at all.  ~agents.color~ paints the background when it is
set, and in the GTK client ~agents.avatar~ replaces it with a real image.
Both keys had been in the schema since the beginning and were read by
nothing; this is what finally reads them.

A colour goes through ~clawt_color_ink()~, which accepts only ~#rgb~ and
~#rrggbb~ and answers which of black or white is legible on it.  It is
also the validation: nothing else checks that key, and it is spliced into
a stylesheet.

**** The measure

Both clients cap the column.  In the GTK client that is ~AdwClamp~ at its
own defaults; in the web client it is 40rem, which was *measured* rather
than chosen --- at 52rem a line ran to 117 characters against a
comfortable range of 45 to 90, and 40rem renders 89 at the same font,
taken from the browser's own text metrics.

The composer follows the same column.  A full-width entry under a narrow
column of text reads as a rendering fault rather than as a layout.

On a narrow screen the avatar gutter collapses and the face is hidden:
measured at 375px, the indent would otherwise take the measure to 42
characters, and the avatar is the first thing that should go rather than
the text.

**** Following the live edge

The transcript scrolls itself only while the reader is *at* the end.
Yanking somebody down mid-read because a message arrived is the single
most annoying thing a chat window can do, so both the queued scroll and
the growth handler refuse to move the view when they are not.

"At the end" is ~clawt_transcript_is_at_bottom()~, with a 32px tolerance
--- not zero, because a scrolled window rarely lands on an exact value
and a reader one pixel off has not chosen to be; not large, because every
pixel of it is a pixel of message a new arrival can push off the bottom
without the client noticing it stopped following.  It is a pure function
so the tolerance is exercised on both sides *and at its boundary*, which
is the one part of the follow machinery a test can reach without a
window.

The mechanism that actually does the work is ~notify::upper~ on the
scrolled window's adjustment, not the queued idle beside it: GTK4 lays
out from the frame clock, so an idle reads the height the transcript had
*before* the message was allocated.  The idle stays as a belt to the
growth handler's braces, and a consequence worth knowing follows from
it --- **a window the compositor is not presenting does not lay out, so
it does not scroll.**  Measured on both backends: the frame counter stops
and ~upper~ stops with it while messages are appended perfectly well to
the widget tree.  It resolves on the next frame; there is nothing for the
client to do about it, because there is nobody looking.

**** Day dividers

"Today", "Yesterday", or "Wednesday 25 August", between two rules,
inserted when the date changes and once at the top of a loaded history.
A date change is a bigger break than a speaker change, so it gets more
room than the gap it sits among.

**** One row builder, and the Flow tab uses it

The GTK client had two: the chat's and the Flow tab's.  They had drifted
into visibly different renderings of the same content --- one with runs,
avatars, dividers and a measure, the other a flat list of captions ---
so a reader moving between a conversation and the flow of one saw two
conventions for one kind of thing.

Fixed by deleting one of them rather than by teaching the second the same
tricks, which is the only version that cannot drift again.  What differs
between the two views is a small struct: which box, whose run state, and
how the other party is drawn.  The Flow tab derives an avatar from each
sender's name, because a room there has several participants rather than
one configured agent.

That also gave the chat two things the Flow tab had and it did not: a
*task chip* and a *hop count*.  A delegated reply arriving in your own
chat is exactly the one worth knowing was delegated, and a hop count
climbing towards ~max_hops~ is the only thing on screen that
distinguishes a loop from a conversation.  The web client already drew
both in its chat, so this closed an asymmetry between the clients that
=make parity= could not see.

The web client's Flow view is a *digest* across every room --- one
truncated line per message, so the whole of what the fleet has been
saying fits on a page --- rather than a transcript of one room, which is
why it does not draw through the chat's builder.  What it does share is
where a run begins: consecutive messages from one agent do not repeat the
name, from the same ~clawt_chat_run_is_start()~.

*** Markdown

Agent replies are rendered: bold, italic, inline code, fenced code,
headings, bullet and numbered lists, block quotes and rules. Enough for
what a chat actually contains, and nothing beyond it.

The important word is *rendered*, not *interpreted*.
~clawt_markdown_to_pango()~ walks the document cmark parsed and emits
Pango markup only for the structure cmark identified, escaping every
piece of literal text on the way out. An agent that writes
~<span foreground="red">~ gets those characters on screen; a message
crafted to close a tag cannot reach the parser at all, because the
parser never sees its text. ~tests/test-markdown.c~ throws the obvious
attempts at it and also asserts that the tags in the output are always
balanced -- Pango refuses unbalanced markup, and a GtkLabel handed
something it cannot parse renders *nothing*, so a message would silently
vanish. The client checks with ~pango_parse_markup()~ before using it
and falls back to plain text, which is belt as well as braces.

Links show their target beside the text and are not clickable. A
clickable link in model output is one keystroke between a prompt
injection and a browser; a person who can see where it goes is a person
who can decide.


*** The composer stands on the message column

The transcript and the composer sit in the same clamp, centred alike,
and they still did not line up --- in *either* client --- because only
one of them spends anything on the avatar.  A row is inset from the
clamp and an agent's body is then indented past a gutter, so a body
starts a gutter and a margin in; the composer had neither, so the
entry's frame stood on the avatar's left edge rather than the text's.
That put the strongest vertical line on the page inside the one column
deliberately kept empty.

Both trailing edges were already right.  Only the leading edge was out,
and by exactly the gutter.

The two clients need different numbers --- GTK insets 12 and gutters
44, the web sheet gutters 36 with no inset --- so what is shared is the
derivation and not the values.  ~clawt_chat_body_inset()~ states it
once; the GTK client builds ~CHAT_BODY_INSET~ from its pair and the web
sheet declares ~--chat-gutter~, which its body, its attachments and its
composer all read.

It aligns the *frame*, not the text inside it: a bordered control reads
as a box and the box's edge is the line the eye follows, so aligning
the text would push the frame back into the gutter and restore the
fault.

Narrow enough that the avatar is hidden, there is no gutter to stand
past and the composer returns to the clamp with the bodies.  In the web
sheet that override has to sit *after* the rule it overrides ---
identical specificity means source order is the only thing deciding,
and grouped with the sheet's other narrow overrides it would lose every
time while reading exactly like a fix.  ~/web/narrow-composer-override-can-win~
asserts the ordering rather than trusting it.

*** Writing the message

The box is a text view, not an entry: Ctrl+G hands whatever comes back
from ~$EDITOR~ straight into it, and that is usually several paragraphs.
Enter sends, Shift+Enter is a newline, and the box grows to about ten
lines before it starts scrolling.

*Ctrl+G* writes the current draft to a temporary ~.md~ file, opens
~$CLAWT_EDITOR~ / ~$VISUAL~ / ~$EDITOR~ on it, and takes back whatever
was saved when the editor exits. It is seeded with what is already
typed, so this extends a draft rather than replacing it. ~/compose~ does
the same thing from the keyboard.

*** Slash commands

Typing ~/~ reveals the matching commands above the entry, with what each
does; clicking one fills it in. Anybody who already knows the command
keeps typing and never looks.

| Command | What it does |
|---------+--------------|
| ~/help~ | list them |
| ~/start~ ~/stop~ ~/restart~ | this agent's lifecycle |
| ~/attach~ | pick files to send with the next message |
| ~/compose~ | write the message in $EDITOR |
| ~/edit [file]~ | open a workspace file in $EDITOR |
| ~/files~ | this agent's workspace files |
| ~/memory <query>~ | search what this agent has remembered |
| ~/agents~ | who is in the fleet |
| ~/flow~ ~/tasks~ | go to those pages |
| ~/clear~ | clear the transcript on screen only |
| ~/new~ | create an agent |

Every one is a shortcut to something that already exists -- none of them
is a second way to do anything. A command never reaches the agent, and
an unrecognised one says so rather than being sent: a mistyped command
arriving as a message is how somebody learns not to trust the feature.

*** Sending files and images

Paste an image and it is queued as a PNG. Ctrl+V is intercepted only
when the clipboard actually holds an image -- ordinary text paste is
left to the widget, and an image copied from a browser usually carries a
URL alongside it, so taking both would be worse than taking either.

The paperclip, or ~/attach~, picks files. Queued files appear as chips
above the entry and can be dropped before sending; nothing is written
anywhere until the message is actually sent, so an abandoned draft
leaves nothing behind for the agent to find.

On send, each one goes to the daemon over ~attachment.put~, which writes
it into that agent's exchange directory. The message body then names
them, with *both* paths:

#+begin_example
have a look at this failure

[clawtilla] Files sent with this message. Open them with your own read
tool at the host path below; it runs on the host even when your shell
does not.
- pasted-1750000000.png
  /home/you/.local/share/clawtilla/exchange/researcher/pasted-1750000000.png
  (inside your container: /mnt/clawtilla/exchange/researcher/pasted-1750000000.png)
#+end_example

Both, and the host one first, because they are for different tools. An
agent's own read tool runs on the host even when its shell runs in a
container -- so given only the container path it can stat the file with
~clawtilla_computer_exec~ and never open it, which is exactly what
happened to the first image anybody sent. The container path is there
for shell commands.

Naming them at all is what makes them reachable: an agent reads files
with its own tools, and one it has not been told about is one it will
not open.

*** Seeing them again

A message that carried an image shows a thumbnail under it, and clicking
it opens the picture full size in its own window -- Escape closes it. A
path in a message body is a thing nobody remembers the contents of ten
minutes later, and the whole point of a transcript is that you can
scroll back.

The client recognises its own attachment block and reads the *host*
paths out of it, so this works for anything still on disk and quietly
does nothing for anything that is not -- including for a client running
on a different machine from the daemon. Thumbnails are decoded at
thumbnail size rather than shrunk in the widget: GTK has no
maximum-size property, a size request is a minimum, and a GtkPicture
takes its natural size from the paintable, so a full screenshot handed
to it stays a full screenshot however the widget is configured. They
also turn ~can-shrink~ off, which defaults *on* and sets the minimum
width to zero -- with it left alone the preview was squeezed down to a
few dozen pixels by the layout around it.

The name is rebuilt from its basename rather than trusted --
"../../.ssh/authorized_keys" is a filename -- and 32 MB is the cap,
because this crosses the IPC socket base64-encoded.



*** Right-click

| Where | What you get |
|-------+--------------|
| a message | copy it as markdown, text or org |
| an attachment | open, save a copy, copy path, delete permanently |
| the conversation | copy, open in $EDITOR, or save -- each as markdown, text or org |

Attachments open with the desktop's own handler, so a PDF opens in
whatever reads PDFs here and an image in whatever shows images. A file
that is not an image gets a chip with its icon, name and size instead of
a thumbnail; clicking it opens it the same way.

Deleting asks first, goes through the daemon rather than unlinking from
the client -- a client that deletes by path is a client that can be
asked to delete any path -- and says plainly that the message will still
name the file afterwards.

*** Taking a conversation with you

~Ctrl+Shift+G~ opens the whole conversation in ~$EDITOR~ as org.
~Ctrl+G~ is the message you are writing; the difference is how much of
it you meant.

Conversion is pandoc's, run with ~--wrap=none~ so *one paragraph stays
one line*. pandoc rewraps at 72 columns by default, which turns every
paragraph into a block of hard-wrapped lines: unreadable in an editor
that soft wraps and a nuisance to edit or diff afterwards.

Markdown needs nothing installed. Text and org need pandoc, and say so
rather than quietly handing back markdown under an org label -- which
would be the worst of the three possible answers.

The document is read back from the daemon rather than scraped off the
widgets, so an export is of the conversation rather than of the last
screenful of it.

*** More commands

| Command | What it does |
|---------+--------------|
| ~/reset~ | start the agent's AI session again, from nothing |
| ~/retry~ | send your last message again |
| ~/export [org]~ | save the conversation |
| ~/copy [org]~ | copy the conversation |

~/reset~ is for an agent that has got itself wedged. It stops the agent,
moves its session files aside, clears its stored sessions from
libreclaw's database, and starts it again if it was running -- so the
next turn opens a new CLI session instead of resuming the old one with
~--resume~.

Both places matter: libreclaw restores a session from the files *or* the
database, so clearing only one leaves the agent resuming from the other
and looking like the reset did nothing. The files are moved rather than
deleted, because a reset is what you reach for when something is wedged,
which is exactly when you might want to look at what it was doing.

*** Where a toast lands

~AdwToastOverlay~ places its toast at the bottom of whatever it wraps,
and one overlay wrapped the whole window --- so on the chat page every
confirmation landed on the text being typed.

There are two overlays now, because one cannot mean two places: one
wraps the chat page's transcript region, so a toast settles above the
composer, and one wraps the view stack for every other page, where the
bottom of the page is the right place and there is nothing there to
cover.  ~clawt_window_toast()~ picks between them on the visible page,
so all 87 call sites are untouched --- the choice belongs to where a
toast lands, not to the places that raise one.

Chat is singled out not because it matters more but because it is the
only page holding something a toast can destroy the use of: everything
else a toast covers can be scrolled back to, while the composer holds
text that has not been sent anywhere yet.

*** Following the live edge

~notify::upper~ and ~notify::page-size~ are emitted by ~GtkViewport~
from inside its own size-allocate, after it has positioned its child
for that pass.  Writing the adjustment's value there moves the number
and not the offset, and nothing queues a further pass --- so the view
lands one message short: the adjustment reports the bottom, the newest
reply stays clipped against the composer, and it stays that way rather
than correcting a frame later.

That state is invisible to every other correction in the file, because
they all test the adjustment and the adjustment is already right.  The
handler added to correct the idle was what stopped the idle working.
It queues a scroll instead of writing the value, so the write happens
outside the layout pass.

Whether the reader is at the live edge at all is
~clawt_transcript_is_at_bottom()~, in libclawt and tested on both sides
of ~CLAWT_TRANSCRIPT_FOLLOW_TOLERANCE~ and at its boundary --- every
pixel of that tolerance is a pixel of message an arrival can push off
the bottom without the client noticing it stopped following.

*** Smaller things

Messages carry the time they were sent. What you were typing is kept per
agent, so clicking another agent and coming back does not lose it.


*** The Flow tab

The Chat tab is your conversation with one agent.  Flow is the rest of
it: what the fleet said to each other while you were not looking.

The left-hand list is one row per conversation that has anything in it
-- who, how long ago, who spoke last and the first line of it, with the
message count on the right.  A fleet accumulates a direct room per pair
of agents and most of them are empty, so empty ones are left out. Sorted
by most recent activity, and refreshed on every message, so the top of
the list is what is happening now.

Your own chats are excluded by default.  This page exists to answer
"what did they do without me", and mixing them in buries it; the
checkbox above the list puts them back.

Picking one shows the whole exchange on the right, each message with who
said it and when.  A message that belongs to a delegated task carries a
~task~ chip -- that is the difference between "beta said something" and
"beta said something because alpha asked it to", and it is the thing
that makes this a flow rather than a list of remarks.  The chip opens
the task board, where the rest of the story is.

The conversation you are reading stays open across a refresh.  Messages
arrive continuously, and a list that reselected its first row every time
anything anywhere spoke would take you off what you were reading.

Every control's sensitivity is bound to ~ClawtAgentCaps~, and a disabled
control says why in its tooltip.  A greyed-out button with no
explanation is the interface equivalent of a shrug.

Editing writes through ~agent.set~, which is the same path
~clawtilla agent set~ uses -- the client has no second way to change a
config.  The model and the computer only take effect on the agent's next
start, and the Save toast says so rather than leaving you wondering why
nothing changed.

*Deleting asks twice.*  "Are you sure?", then "ARE YOU REALLY SURE!?".
Removing an agent stops it and takes it out of every room, and one click
between browsing and gone is too few.  Its mailbox and transcripts stay
on disk: removing an agent is reversible, deleting its history is not.

The second dialog carries a checkbox for the agent's container or VM,
named -- "Also delete its container, clawt-researcher".  Off by default:
a container may hold work that was never anywhere else.  Agents with no
computer do not get one.

Message bodies are rendered as labels, never as Pango markup.  Model
output arrives from somewhere the user does not control, and treating it
as markup would let a message rewrite the interface around it.

*** The activity line

Under the transcript, a spinner and a line of text, hidden when there is
nothing to say.  An agent turn runs for minutes, and a chat window that
shows nothing between the question and the answer is indistinguishable
from a broken one.

It shows:

- =delivered -- waiting for a reply= the moment a message is accepted by
  a *running* agent
- =thinking= while the agent holds a typing indicator up, which libreclaw
  raises for the whole turn
- nothing at all once the reply lands, or when the target was not running

That last case is deliberate.  Sending to a stopped agent raises a toast
-- "bravo is stopped -- held in its mailbox until it starts" -- and
leaves the activity line clear, because a spinner for something that is
never going to answer is a worse lie than no spinner.  The daemon
reports the target's state in the ~msg.send~ reply, so this is never
inferred from a sidebar that may be a refresh behind.

Tool calls are not shown yet.  libreclaw runs a turn through
~ai_cli_client_chat_sync()~, which spawns the CLI without streaming and
parses one buffer at the end, so no per-tool event exists to display.
Showing them means moving the session turn onto
~ai_cli_client_stream_run_async()~ upstream first; the frame kind,
event kind and the widget are the easy part.

*** Adding an agent

The ~+~ button is a split button.  Pressing it creates an agent, which is
what it has always done; the arrow beside it also offers *Import an
agent...*.

The create dialog offers both paths: fill in id, model and computer by
hand, or answer six questions and let a model draft it.

The questions ask one thing each -- what it should do, what it should
never do, what it needs to work on, how it should come across, what it is
working on, anything else.  Only the first is required, and a blank
answer becomes a heading marked /Fill this in./ rather than an invention.

/Designed by/ picks which model does the drafting, separately from the
model the agent will run on: there is no reason for them to be the same,
and a person will often want their best model to draft an agent that then
runs on a cheap one.

The model writes the agent's org files as well as its configuration, so a
designed agent arrives with a real ~SOUL.org~ rather than a scaffold full
of /Fill this in./.

Choosing ~container~ reveals an *Image* dropdown, listing your own images
from ~defaults.container_images~ first and clawtilla's suggestions after,
with the full reference shown underneath the selection -- a label like
"Fedora 44" does not say which registry it came from, and that is exactly
what differs between two machines.  /Other.../ reveals a free-text field:
the list is a suggestion, and any reference podman can pull is valid.

The same dropdown is on the Agent tab for a container agent, so the image
can be changed later.  *The AI path shows
the proposed configuration and waits for you to confirm* -- a model's
proposal becoming an agent without anyone reading it is the kind of
convenience nobody asks for twice.

*** Importing an agent

Two different things wear that name, and the dialog shows both, because
which one you want depends on where the agent already is.

*Already on disk* lists workspaces clawtilla can see that no agent
claims -- an agent removed from the config keeps its state, a design that
was never committed leaves a whole workspace, and a config restored from
a backup leaves everything it did not mention.  Those accumulate silently
and were previously reachable only through ~clawtilla agent discover~, so
from the client they were invisible.  Importing one adds the config entry
it is missing; nothing is copied or moved.  Each row says what the
directory holds, because "there is a directory called researcher" is not
enough to decide with: one with a mailbox and a memory database is an
agent somebody ran, and one with nothing but a ~config.yaml~ is a design
abandoned halfway.

*From somewhere else* copies a standalone libreclaw workspace in.  Its
provider and model come with it, so an import does not quietly move the
agent onto the fleet defaults.  /Keep git history/ is off by default: the
new workspace is usually not the same repository.

*** Another machine's fleet

Left of the app title is a menu naming the daemon the window is showing.
It lists *Local* and every saved connection, and switching is one click.

The name is also shown as the window's subtitle and the button is
tinted whenever the connection is remote.  That is deliberate: every
destructive verb in the client -- remove an agent, tear down its VM,
reset its session -- acts on whichever daemon is connected, and someone
who has forgotten they are pointed at another machine will not find out
until afterwards.

*Manage connections...* adds and removes them.  A connection needs a host
and the token from ~clawtilla daemon token~ on that machine; the port
defaults to 8792.  TLS is only worth turning on if that daemon has a
certificate -- inside a tailnet, WireGuard is already encrypting the
connection.

Switching connects the new daemon *before* letting go of the old one, so
a typo in a port leaves you where you were with a toast explaining why,
rather than looking at nothing.  Everything on screen is then cleared:
agent ids, room ids and message ids are all per-daemon, so keeping any of
them would show one daemon's transcript under another daemon's agent.

~clawtilla-gtk~ also takes ~--profile~, ~--host~, ~--port~ and ~--token~,
so a laptop with no fleet of its own can start straight on a workstation
rather than being shown "the daemon is not running" for a daemon it was
never asking about.

*** Adaptive

Below 800px the sidebar becomes a drawer.  Without that the agent list
eats a phone-sized window and the conversation has nowhere to go.

Below ~CLAWT_ALERTS_PUSH_BREAKPOINT~ the alerts panel overlays the
transcript rather than pushing it aside.  That number is *derived* rather
than chosen, by ~clawt_alerts_push_min_width()~, from four numbers other
lines of code own: the agent list's width, the panel's share of what is
left, the transcript's clamp and a row's margin.

Fitting the clamp is deliberately not the criterion.  That is met a long
way below the threshold and looks wrong when it is met, the column
finishing a few pixels from the panel's edge.  The criterion is
~CLAWT_ALERTS_PANEL_GAP~ of clear space measured to the *ink*, which the
row margin contributes to --- so the floor is 1124 and the client breaks
at a round number above it.

The reason it is a function rather than a constant is that every input
belongs to something else.  Widen the panel and the floor moves; nothing
warns, because nothing is broken --- the panel still opens, the
transcript still renders, and the column simply sits against the panel
with nowhere to breathe.  ~/client-rules/alerts-push/shipped-clears-it~
is what fails instead.

Opening the panel does shift the column left, by 122px at a 1280 window.
That is accepted rather than overlooked: the clamp fixes the measure, so
pushing *translates* the column without reflowing it, and neither the
line breaks nor the reader's place in the conversation move.

**** A closed sidebar stays closed

~AdwOverlaySplitView~ opens its own sidebar when it stops being
collapsed, so crossing a breakpoint upward drove ~show-sidebar~ back to
TRUE and an operator's explicit close did not survive a resize.

Both splits therefore remember what they were meant to be showing and
put it back on ~notify::collapsed~ --- that signal rather than
~notify::show-sidebar~, because libadwaita emits the collapsed notify
first, so the correction is already made before anything downstream
reads the property.

That ordering is the whole point rather than a detail.  ~show-sidebar~
on the alerts split is what marks every alert read, and libadwaita's
write satisfied that guard exactly --- so widening a window past the
breakpoint silently zeroed the unread count for alerts nobody had
looked at.  A panel appearing by itself is cosmetic; an unread count
zeroing itself is not.

The client's own write is deliberately kept out of the record: closing
the drawer when an agent is picked on a narrow window is an affordance
getting out of the way, not the operator saying they want no agent
list, so widening the window brings it back.

*** If the daemon is not running

A status page saying so, not an empty window.  An empty window looks like
a fleet with no agents in it, which is a different problem with a
different fix.

** The web client

#+begin_src bash
clawtilla-web [--port 8790] [--bind ADDR] [--no-tailscale] [--socket PATH]
#+end_src

Everything ~clawtilla-gtk~ does, served over HTTP.  The same seven views
-- chat, agent, mailbox, computer, routines, tasks, flow -- the same
eighteen slash commands, and seven settings pages behind them, driven by
the same ~ClawtClient~ over the same socket.  See
[[file:web-client.org][web-client.org]] for the whole of it.

It is a separate binary rather than a mode of the daemon, deliberately.
The page can start, stop, reconfigure and delete every agent on the
machine and run commands inside their computers, so it exists only when
somebody has decided they want it.

*** Where it listens

By default the loopback *and*, when there is one, this machine's tailnet
address.  A tailnet is the one network where listening past the loopback
is defensible without a login of our own: every peer is a device the user
enrolled and WireGuard authenticated, and nothing off the tailnet can
route to a 100.64/10 address at all.  That is the same reasoning
~clawtillad~ already uses for its own convenience listener.

A machine with no tailnet gets the loopback alone.  It does not fall back
to every interface -- widening the audience because an address was
missing is the opposite of what anybody would want.

| Flag              | What it does                                       |
|-------------------+----------------------------------------------------|
| ~--bind ADDR~     | replaces the defaults; repeatable                  |
| ~--no-tailscale~  | this machine only                                  |
| ~--port PORT~     | default 8790                                       |

An address named with ~--bind~ is never optional: failing to bind it is
an error, because a client that ignored where it was told to listen and
started anyway is running somewhere nobody knows about.  The tailnet
address, which clawtilla chose rather than the person, is a warning.

*** It has no login

Anything that can reach a listed address drives the whole fleet.  On a
tailnet that is bounded by WireGuard; anywhere else, put it behind
something that can require one.  It says so on startup, and names every
address it actually bound rather than the ones it was asked for -- a
convenience address whose bind failed is exactly the interesting case.

*** Escaping

Every element is built with htmx-glib's typed classes rather than by
appending to a string, which is not only that library's house style: it
is what escapes agent output.  Names, descriptions and message bodies are
written by people and models, and this client serves them back over HTTP,
so an unescaped ~<~ is script injection into whoever opened the page.
=tests/test-web-render.c= asserts it on the rendered markup rather than
on the code that produces it.

*** Without JavaScript

Every action is a real form or link, so the whole client works with
scripting off -- each action posts and the page re-renders.  htmx is what
makes it feel live: partial swaps instead of full reloads, and an SSE
stream so the fleet updates itself.  Both scripts are served from
=data/web=, never a CDN.  See that directory's README for why.

*** Parity with the GTK client

They answer for the same daemon, so they reach the same parts of it.
That is checked rather than remembered:

#+begin_src bash
make parity
#+end_src

It compares two things: the IPC frame kinds each client sends, and the
slash commands each answers.  Both matter -- the command check exists
because the frame-kind one missed thirteen missing commands entirely,
since they are built out of frames both clients already sent.

Deliberate exceptions live in an exception map inside
=tools/clawt-client-parity.sh=, each with its reason; anything without a
reason somebody would agree with belongs in the client instead.  It also
runs as part of ~make docs-check~ and as a case in ~make test~.

Routing is checked separately, against a running client, because unit
tests cannot see it:

#+begin_src bash
make web-smoke WEB_SMOKE_URL=http://127.0.0.1:8790 WEB_SMOKE_AGENT=chief
#+end_src

** Embedding libclawt

The library is the product; the daemon is one caller.

#+begin_src c
#include <clawtilla.h>

ClawtDaemon *daemon;
GMainContext *context = g_main_context_default();
g_autoptr(GError) error = NULL;

daemon = clawt_daemon_new("~/.clawtilla/config.yaml", context);

if (!clawt_daemon_start(daemon, &error)) {
    g_warning("clawtilla: %s", error->message);
    return;
}

g_signal_connect(daemon, "started", G_CALLBACK(on_started), self);
#+end_src

No process, no socket.  ~clawt_daemon_start()~ returns once the fleet is
up; the host's own main loop drives everything from there.

*** Driving it

Two ways.  Component accessors, for anything structural:

#+begin_src c
ClawtAgentManager *agents = clawt_daemon_get_agents(daemon);
GPtrArray *list = clawt_agent_manager_list(agents);

ClawtEventBus *bus = clawt_daemon_get_event_bus(daemon);
g_signal_connect(bus, "event", G_CALLBACK(on_event), self);
#+end_src

Or the same frames a socket client sends, which keeps a host on exactly
the surface every other client uses:

#+begin_src c
g_autoptr(JsonNode) request = clawt_ipc_request_new("agent.list", "1");
g_autoptr(JsonNode) reply = clawt_daemon_handle_request(daemon, request);
#+end_src

*** The cmacs case

cmacs already owns a main loop and already has libreclaw embedded.  It
calls ~clawt_daemon_new(path, NULL)~ -- ~NULL~ meaning the default
context, which is the one Emacs runs -- then ~clawt_daemon_start()~, and
connects the bus's ~event~ signal.  Agents become buffers; the sidebar
becomes a list.  There is no second process, no socket, and no protocol
in between.

Everything is introspectable (~Clawt-1.0.typelib~), so the elisp side can
work through GObject Introspection rather than through C.

The two things to know when embedding:

- signal handlers are the host's business.  clawtilla installs none;
  ~clawtillad~ installs its own.
- prefer ~runtime.type: embedded~ for agents when there is no
  ~libreclaw~ binary to run, and read the constraints in
  [[file:agents.org][agents.org]] first.
