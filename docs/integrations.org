* Integrations

An integration is how an agent reaches -- or is reached from -- the world
outside the fleet.  There are three directions, and they behave
completely differently:

- a *channel* puts a person on the other end of an agent's reply. Matrix,
  email, a webhook, a terminal, an Emacs session.  A message arrives as an
  ordinary turn and costs the agent a turn to answer.
- a *tools* integration gives an agent an MCP server.  Its tools appear
  beside the agent's own and cost nothing until one is called.
- a *notify* integration runs in neither direction an agent can see: the
  daemon telling a person something, about an agent, without the agent
  being involved or knowing it happened.

They are configured the same way, which is the point: adding support for
something new is a config entry, not a patch.

** Where an integration lives

Two places, and both are legitimate.

*Inside an agent*, for a connection only that agent will ever use:

#+begin_src yaml
agents:
  - id: researcher
    integrations:
      matrix:
        enabled: true
        homeserver: "https://matrix.example.org"
        user_id: "@researcher:example.org"
        access_token: {file: "researcher-matrix"}
#+end_src

*At the top level*, as a named instance with a scope, for a connection
handed to several agents or to the whole fleet:

#+begin_src yaml
integrations:
  - name: github
    type: mcp
    scope: all
    description: "GitHub issues and pull requests"
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_TOKEN: {env: GH_TOKEN}
#+end_src

Everything downstream -- the rendered libreclaw config, the agent's
=.mcp.json=, the paragraph written into its =TOOLS.org=, the health check
-- reads the *resolved* set and never looks at which of the two it came
from.  There is one code path, so there is one behaviour.

That path is ~clawt_integration_resolve_for_agent()~, which returns a
list of ~ClawtIntegrationBinding~ -- one per integration this agent
actually has.  A binding holds no values of its own; every getter reads
through to whichever of the two forms holds them, so nothing downstream
has a branch on where a setting came from.  Two code paths would be two
behaviours, and the one nobody tests is the shared one.

Inline blocks resolve first, then named instances in file order.

** Scope: one bot, some bots, all bots

| =scope=    | Who gets it                                             |
|------------+---------------------------------------------------------|
| =all=      | every agent, including ones created later               |
| =selected= | the ids in =agents:=, and everyone on a team in =teams:= |
| =none=     | nobody -- parked, with its settings and credentials     |

=none= exists so an instance can be switched off without being deleted.
Turning a Matrix account off for an afternoon should not mean retyping
its homeserver, its user id and its rooms, and a credential that has to
be re-entered to be re-enabled tends to end up somewhere worse than a
config file.

The =agents:= list is kept whatever the scope, so switching to =all= and
back does not lose the selection.

*=teams:= reached nobody until 0.1.0.*  Everything downstream goes
through =clawt_integration_resolve_for_agent()=, which asked a predicate
that takes an agent id and forwards a null team -- and the scope rule
answers /no/ for a null team before it ever looks at the team list.  So
a team-scoped instance was accepted, saved, listed, and applied to
nobody; the daemon's own listing asked the same question, so both
clients drew "not applied" and agreed with each other.  The variant that
takes a team existed the whole time and had no callers at all.  It is
now asked through the agent's own configuration, which cannot be called
without the team.

Omitting =scope:= means =selected=, not =all=.  So an instance with no
scope and no =agents:= reaches nobody until somebody says who.

*** An unrecognised scope reaches nobody, not everybody

A =scope:= this build cannot parse is a warning naming the instance and
the word, and the instance reaches *nothing*.  The two failure modes are
not symmetric: a typo that hands a credential to the whole fleet is a
great deal worse than one that hands it to nothing and says so, and only
one of the two is noticed.

#+begin_example
integration home: 'evryone' is not a scope; reaching nobody
#+end_example

Shared folders apply the same rule, and differ only on the *absent*
case -- a mount with no scope goes to every agent, because that is what
a fleet-wide folder is for.  A scope that is written and cannot be read
reaches nobody either way.

#+begin_src bash
clawtilla integration scope home researcher,scribe   # a group
clawtilla integration scope github all               # the fleet
clawtilla integration scope home none                # park it
#+end_src

** Sharing an account that cannot be shared

A Matrix account is one login.  Two agents on the same =user_id= both
receive every message in every room and both answer as the same person,
which reads as the fleet misbehaving rather than as a mistake in a file.

So each type declares the keys that must *differ* between agents sharing
an instance, and those go under =per_agent=:

#+begin_src yaml
integrations:
  - name: home
    type: matrix
    scope: selected
    agents: [researcher, scribe]
    homeserver: "https://matrix.example.org"     # shared
    require_mention: true                        # shared
    per_agent:
      researcher:
        user_id: "@researcher:example.org"
        access_token: {file: "home-researcher-matrix-token"}
      scribe:
        user_id: "@scribe:example.org"
        access_token: {file: "home-scribe-matrix-token"}
#+end_src

Any key may be overridden, not only the identity ones -- a different room
list per agent is an ordinary thing to want.

| Type       | Must differ per agent      |
|------------+----------------------------|
| =matrix=   | =user_id=, =access_token=  |
| =email=    | =username=                 |
| =webhook=  | =port=                     |
| =mcp=      | nothing; share it freely   |
| =notify=   | nothing; share it freely   |
| =connector= | whatever the connector itself declares -- see below |
| =local=    | nothing -- but only one agent in the whole fleet may have it |
| =cmacs=    | nothing                    |

*** A connector answers this for itself

The =connector= *type* names no identity key, and that is deliberate: a
fleet-wide GitHub account every agent reads through is what "give all of
them GitHub" means, and warning about it would be warning about the
feature.

But that is a fact about GitHub rather than about connectors.  A service
that records *who* did something has the opposite answer, so the
catalogue entry says so rather than the type having to choose one answer
for every provider.  The built-in =venture= entry names =token_file=,
because VENTURE audits by actor: two agents holding one token are one
name in every row they write, and which of them filed a change stops
being answerable -- as does whether a person, a rule or the AI did.

The warning says that, not just "give each its own".  An instruction
with no reason attached reads as pedantry and gets ignored.  An overlay
file in =connectors.dir= may declare =identity_keys= and an
=identity_note= of its own the same way.

Two agents that end up sharing one of these are reported by
=clawtilla integration list= and in the Integrations page, because it is
not visible from either agent alone.  Only a *shared instance* is
checked: two agents that each wrote their own inline Matrix block on one
account are two people who did that on purpose, and the fleet check has
nothing to tell them.  An empty value is skipped rather than counted as
a collision, so two agents with no =user_id= yet are not reported as
sharing one.

*** One channel block per agent, so one integration of that type

A channel type is =one_per_agent=: an agent may have at most one
=matrix=, one =email=, one =webhook=, one =local= and one =cmacs=.  That
is not a policy, it is the shape of what is rendered -- libreclaw takes
one ~channels.<type>~ block per agent, so a second Matrix instance for
the same agent has nowhere to go.

When two would apply, the *inline* block wins, because somebody wrote it
inside that agent, and the shared instance is dropped with a warning
naming it.  Dropping it silently is the failure worth avoiding: it would
leave an account that looks configured in the file and receives nothing,
for ever.

=mcp=, =connector= and =notify= carry no such limit.  An agent may have
as many as it likes -- they are entries in a list rather than a block
with one name.

** Matrix

The one people actually want, and the one with a step that used to be
tedious: getting an access token out of a client by hand.  clawtilla logs
in for you.

#+begin_src bash
clawtilla integration add home matrix
clawtilla integration matrix-login home matrix.example.org researcher
clawtilla integration matrix-rooms home
clawtilla integration set home rooms=!abc:example.org,!def:example.org
clawtilla integration scope home researcher
#+end_src

The password is read from stdin, used once, by the daemon, and never
stored -- there is deliberately no =--password= flag, because an argument
is in the shell history and in the process table.  What comes back is an
access token, written to a file under =secrets.dir= at 0600 and referred
to from the config by path.  *It is never returned to the client that
asked for the login*: a secret's value has no business in an IPC
response, and here it does not need to be in one.

The session appears on the account's device list as
=clawtilla (researcher)=, which is where you revoke it.

The =user_id= written into the config is the server's answer, not what
was typed: signing in as =researcher= gives =@researcher:example.org=,
and the short form authenticates perfectly and matches no mention.

An empty =rooms= list means every room the account is joined to,
including ones it is invited to later.  =require_mention= defaults to
*on*, unlike a clawtilla room: a Matrix room usually has people in it
talking to each other, and an agent that takes a turn on every line of it
is both expensive and unbearable.

Bridged rooms -- Discord, Signal, anything else with a Matrix bridge --
are just rooms, so an agent reaches them without knowing they are
bridged.  Its =TOOLS.org= says so, because an agent reasoning about
"Matrix users" will otherwise misjudge who it is talking to.

Health check: a TCP connection to the homeserver.

** email

#+begin_src yaml
integrations:
  - name: support
    type: email
    scope: selected
    agents: [triage]
    imap_host: "imap.example.com"
    imap_port: 993
    smtp_host: "smtp.example.com"
    smtp_port: 587
    username: "agent@example.com"
    password: {command: "pass show mail/agent"}
    folders: ["INBOX"]
#+end_src

The password is written to both ~imap_credentials.json~ and
~smtp_credentials.json~ at 0600.  libreclaw wants two files; making you
say the same password twice would be a worse answer than writing it
twice.

Health check: both directions.  An agent that can read mail but cannot
send looks like it is ignoring people.

** webhook

#+begin_src yaml
integrations:
  - name: alerts
    type: webhook
    scope: selected
    agents: [oncall]
    port: 9100
#+end_src

Health check: tries to *bind* the port rather than connect to it.  For a
listener the failure that matters is the port already being taken, and
binding then immediately closing is the only way to find that out without
starting the agent.

Give each agent a different port under =per_agent=.

*** Where it listens

=bind_address= is the loopback by default.  libreclaw's own default is
every interface --- which is the behaviour it has always had, and is why
the key exists here rather than only there: an endpoint in
=shell_command= mode runs a command, and bearer tokens are otherwise the
only thing between that and whoever can reach the port.  Widening it is
something you say:

#+begin_src yaml
integrations:
  - name: alerts
    type: webhook
    port: 9100
    bind_address: "0.0.0.0"     # or a private interface's address
#+end_src

An address that is not an IP address is refused at connect time rather
than falling back to every interface.  A listener that ignored where it
was told to bind and started anyway is running somewhere nobody knows
about.

*** The routing

clawtilla models the listener; libreclaw models what it *does* with a
request, at =channels.webhook.endpoints=.  That is a list of objects with
nested targets and has no sensible spelling as a flat schema key, so it
goes in the agent's ~libreclaw:~ block:

#+begin_src yaml
agents:
  - id: oncall
    integrations:
      webhook:
        enabled: true
        port: 9100
    libreclaw:
      channels:
        webhook:
          endpoints:
            - name: alerts
              path: /webhook/alerts
              mode: prompt
              prompt: "Summarize this alert: {{body}}"
              targets:
                - channel: clawtilla
#+end_src

**clawtilla merges that into the =webhook:= block it renders**, key by
key, rather than refusing it.  The whole-section refusal that used to
apply here was protecting against a real collision --- YAML keeps the
last of two identical top-level keys --- but the hazard is *per key*, and
refusing the section made the routing unexpressible: the listener could
be configured, scoped and health-checked, and could never receive
anything useful.

A key clawtilla writes itself is still refused, by name.  Setting
=listen_port= there would silently take the one the integration
configured, which is the collision, at the resolution it actually has.

The five sections clawtilla owns outright --- =agent:=, =ai:=,
=session:=, =database:= and =skills:= --- are still refused whole.  Those
are single blocks with no half to merge.

** mcp -- anything with an MCP server

This is the general one.  A hosted connector, somebody's stdio binary, a
service behind an HTTP endpoint: one entry reaches every agent in scope,
instead of the same block pasted into each agent's =.mcp.json= by hand.

#+begin_src yaml
integrations:
  - name: github
    type: mcp
    scope: all
    description: "GitHub issues and pull requests"
    command: npx
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_TOKEN: {env: GH_TOKEN}
#+end_src

Or over the network, instead of a command:

#+begin_src yaml
integrations:
  - name: connectors
    type: mcp
    scope: all
    url: "https://mcp.example.com/v1"
#+end_src

One or the other, never both: an entry naming a command *and* a URL is
two different servers and there is no way to tell which was meant, so it
is refused.

An =env= value may be a literal or a secret reference, told apart by
shape.  References are resolved when the agent's =.mcp.json= is written,
because the CLI that reads that file has never heard of clawtilla's
secret backends -- which is why the file is 0600 and already holds the
agent's own token.

Several =mcp= integrations on one agent is the ordinary case; each gets
its own entry.

Health check: that =command= is on the daemon's =PATH=, or that =url=
answers.  The command is *not* run.  Starting an MCP server to find out
whether it starts is a side effect nobody asked for -- it may log in
somewhere, or cost money -- and the failure people actually hit is a
binary that is not installed.

*** The =clawtilla-= prefix in =.mcp.json= is reserved

An integration called =github= becomes a server called =clawtilla-github=
in every agent in scope.  clawtilla owns =clawtilla= and every key
beginning =clawtilla-=: it rewrites them on every start and *removes* the
ones that should no longer be there, because an entry left behind after a
grant is withdrawn points the agent at a server the fleet has stopped
offering.

Everything else in that file is yours and is carried across untouched.
Do not name a server of your own =clawtilla-anything=.

** connector -- an account clawtilla holds the credential for

Same shape as =mcp= from the agent's side: tools appear in its
=.mcp.json= and it calls them.  Completely different on this side.  The
daemon obtains the credential, keeps it at 0600, renews it before it
expires and injects it into the tool server, so the value never reaches
the agent's config, its environment or its transcript.

#+begin_src bash
clawtilla connector catalog
clawtilla connector add gh --provider github --account work \
    --command github-mcp-server --scope all
clawtilla connector key gh
#+end_src

Use =connector= rather than =mcp= whenever the credential is one you
would mind an agent reading -- which is most of them.  Use =mcp= for a
server that needs no credential, or one whose key you are content to
hand over.

[[file:connectors.org][connectors.org]] covers the catalogue, the OAuth flows, renewal, revoking,
and exactly what the broker does and does not protect against.

** notify -- when an agent is blocked on you, or has broken

~clawtilla_message_user~ puts an agent's question where you will see it
*if you look*.  An agent that asked one and waited had, in practice,
stopped -- silently, until somebody next opened a client.  This is what
makes you look.

#+begin_src bash
clawtilla integration add phone notify scope=all \
    backend=ntfy url=https://ntfy.sh/your-topic
clawtilla integration test phone
#+end_src

*** The rule

| Event      | Default | What it is |
|------------+---------+------------|
| =question= | on      | An agent said something to you and is waiting |
| =error=    | on      | An agent stopped in a way nobody asked for |
| =done=     | off     | A task finished |
| =routine=  | off     | A scheduled run failed |

Blocked on you is worth a buzz.  Broken is worth a buzz.  Everything a
fleet does while it works is not -- a notifier that fires on every turn
is one people turn off, and then it is not there for the two that
mattered.

*** Backends

| =backend=  | Needs | Reaches |
|------------+-------+---------|
| =desktop=  | nothing | The machine the daemon runs on |
| =ntfy=     | =url=, optional =token= | A phone |
| =gotify=   | =url=, =token= | A phone |
| =matrix=   | =homeserver=, =room=, =token= | Wherever you read Matrix |
| =command=  | =command=, optional =args= | Whatever you point it at |

=desktop= is the wrong answer when the daemon is on a workstation and you
are not.  It is spoken over the session bus rather than by running
=notify-send=, which is a thin wrapper around the same call: spawning it
buys a process and a PATH dependency and nothing else, and a daemon
running as a systemd user service has a more certain session bus than it
has a PATH.

=matrix= on a bridged homeserver is often the best of these -- it arrives
wherever you already read messages, and a room with nobody else in it
keeps the fleet's noise out of one people are talking in.

=command= is the escape hatch and is meant to be used:

#+begin_src bash
clawtilla integration add desk notify scope=all \
    backend=command command=receipt-print
#+end_src

A program with no placeholders gets the title and the body as two
arguments, which is what makes that line work with nothing else written
down.  Otherwise ~{{title}}~, ~{{body}}~ and ~{{agent}}~ are substituted
wherever they appear:

#+begin_src yaml
integrations:
  - name: desk
    type: notify
    scope: all
    backend: command
    command: receipt-print
    args: ["--header", "{{agent}}", "--body", "{{title}}"]
#+end_src

*** Quiet hours

#+begin_src yaml
    quiet_hours: "23:00-07:00"
#+end_src

Local time, and it silences that instance *completely*.

To be woken for a broken agent but not for a question, make two
instances -- one with quiet hours and one without, each with its own
=events=.  That is why instances have names.

A range that cannot be parsed does *not* silence anything: the failure
nobody would ever find is a typo turning a notifier off for good.

*** Credentials

Resolved once when the configuration loads, not on every notification.  A
=command= reference to a locked password manager blocks until it times
out, and doing that each time something needed saying would make the
notifier the slowest thing in the daemon -- on the path that exists to be
fast.

A credential that cannot be resolved disables *that notifier* with a
warning naming the reference.  Being unable to buzz a phone is not a
reason to stop a fleet.

*** Testing one

#+begin_src bash
clawtilla integration test phone
#+end_src

A notifier is the one thing in a fleet you cannot tell is working by
looking at it: it is correct precisely when nothing happens.  The test
ignores the event list and the quiet hours, because a button that did
nothing at half past eleven would be indistinguishable from a broken one.

In the GTK editor the *Check* button becomes *Send a test* for a
notifier, for the same reason: there is nothing to connect to and check.

*** Reacting to more than this

A pod can call ~notify~ itself, which is how anything the fleet does can
be made to reach you without waiting for clawtilla to grow an event for
it.  See [[file:automation.org][automation.org]].

** local and cmacs

#+begin_src yaml
agents:
  - id: scratch
    integrations:
      local: true
#+end_src

=local= is stdin and stdout.  Only for an agent you run by hand -- it
owns fd 0 and 1, so two agents with it would fight over the terminal, and
an agent started by the daemon has no terminal at all.  At most one agent
in the fleet may have it, and clawtilla says so if two do.

=cmacs= is libreclaw's in-process Emacs integration.

** What the agent is told

An integration nobody told the agent about is an integration it does not
use.  A Matrix channel is invisible from inside a session -- messages
simply arrive -- and an MCP server's tools appear with no indication of
who they reach or whether a person is on the other end.

So clawtilla writes a section of the agent's =TOOLS.org=, between two
markers:

#+begin_example
# BEGIN clawtilla integrations -- rewritten on every start
...
# END clawtilla integrations
#+end_example

Everything outside the markers is yours and is never touched.  The
section is replaced on every start and skipped when nothing changed, so
an editor with the file open does not reload it for no reason.  A file
whose markers somebody removed gets them back, appended -- there is no
position in a file of somebody's prose that clawtilla could claim to know
is the right one.

The =description:= you write on an integration goes in beside it.  It is
the sentence the model reads when deciding whether this is the thing to
reach for, so it is worth filling in for anything whose name is not
self-explanatory.

** Health

#+begin_src bash
clawtilla integration health researcher            # everything it has
clawtilla integration health researcher home       # just one
#+end_src

A failing check is a non-zero exit, so this is usable in a pre-flight
script rather than only by eye.

Deliberately a connectivity check rather than a login: a check that
needed credentials could not run before they are resolved, and the
failure people actually hit is a typo in a hostname or a firewall.

What each type checks:

| Type       | What is checked                                        |
|------------+--------------------------------------------------------|
| =matrix=   | a TCP connection to the homeserver                     |
| =email=    | both directions -- IMAP, then SMTP                     |
| =webhook=  | *binds* the port and closes it; the failure that matters for a listener is the port already being taken |
| =mcp=      | a =command= is on the daemon's ~PATH~, or a =url= accepts a connection.  The server is never started |
| =connector= | from disk alone: a =provider=, a token file that loads, and either unexpired or renewable |
| =local=, =cmacs= | nothing outside the process, so nothing to check  |
| =notify=   | *nothing* -- see below                                 |

A =notify= instance reports healthy whatever it can reach.  There is no
check for it, and the reason is that a connectivity probe would answer a
different question from the one worth asking: a notifier is correct when
it *delivers*, and the only way to find that out is to send one.
~clawtilla integration test~ is the check for a notifier, and the GTK
editor swaps its *Check* button for *Send a test* for exactly this
reason.  Worth knowing before reading a green =health= line as an answer
about a phone.

Checks run one at a time rather than together.  A fleet-wide check
firing thirty simultaneous connects at one homeserver looks like
something it should not.

It runs *asynchronously* in the daemon.  A handler runs on the daemon's
main context while the client blocks, so one that waited on the network
would stall every other client for the length of the timeout -- ten
seconds in which no agent's message is routed.

** Validation

Checked when the config loads and again before an agent starts:

- an enabled integration missing a required key names the key
- a credential key with no secret reference names it, and says what a
  reference looks like
- an =mcp= entry with neither a command nor a URL, or with both
- two agents sharing an identity key on one instance
- two agents with =local=
- an instance naming an agent that is not there -- only under
  =scope: selected=, since that is the only scope that names anybody
- an instance that could not be read at all -- no name, or a type
  clawtilla cannot place -- which is reported as
  =integration 'x' is disabled: <why>= rather than dropped in silence
- an unknown =type=, which disables *that instance* and nothing else

The last one is the same treatment a shadow agent gets, and for the same
reason: a config written by a newer clawtilla must still load in an older
one.

A missing key is reported rather than tolerated because the failure it
causes is silent.  An agent whose Matrix block has no homeserver starts
perfectly cleanly and then never receives anything -- much worse than
being told which line to fix.

** From the GTK client

*Settings → Integrations* lists every instance with its type, who it
reaches, and any warning about two agents sharing one account.  The =+=
adds one; clicking a row opens the editor.

The editor shows only the fields that type has, a scope selector, and a
switch per agent.  Matrix gets a *Sign in* button beside the homeserver
and a *Choose…* button beside the rooms, which lists the account's rooms
by name rather than making anybody paste a room id.  *Check* runs the
health check.

An agent's own inspector has an *Integrations* group: a switch per shared
instance, plus a read-only row for anything configured inside that agent.
The switch edits the *instance's* scope rather than writing a copy into
the agent, because that is where the scope lives -- and an inline copy
per agent is the duplication shared instances exist to end.

** From the CLI

#+begin_src bash
clawtilla integration types                     # what kinds there are
clawtilla integration list                      # the instances
clawtilla integration list researcher           # and what one agent has
clawtilla integration show home                 # one in full
clawtilla integration add home matrix homeserver=matrix.example.org
clawtilla integration set home require_mention=false
clawtilla integration set home --agent scribe user_id=@scribe:example.org
clawtilla integration scope home researcher,scribe
clawtilla integration rm home
#+end_src

=key=value= arguments follow the schema: lists are comma-separated, and a
secret is =access_token=env:NAME= -- a *reference*, never a literal.

Removing an integration leaves any credential file it wrote where it is.
Removing one by mistake should cost a retype of the config, not another
sign-in.

** Adding a type

Most things do not need one.  If it speaks MCP, it is an =mcp= entry and
there is nothing to write.

If it genuinely needs behaviour, implement ~ClawtIntegrationProvider~ in
a plugin: ~get_id~ returns the =type:= value you answer to, ~validate~
checks the settings, ~render_config~ returns the YAML for the agent's
=channels:= block.  See [[file:plugins.org][plugins.org]].

The built-in eight are a declarative table rather than eight classes,
because each is the same shape: validate some keys, resolve some secrets,
emit a channel block, an MCP server entry or a notification.  One row per
type in =src/integration/clawt-integration.c=, carrying its id, its kind,
its required and credential keys, its identity keys, the ~channels:~ name
it renders as, and whether an agent may have more than one.
