* What a task is

A task is one unit of work with an origin (who asked), an assignee (who does it), a prompt, a state and a result. Agents make them with ~clawtilla_delegate~; the operator makes them from any client or ~clawtilla task create~; routines, triggers and (with VENTURE) tickets make them too.

This page is the reference for the work model. How tasks fit into delegation, cross-talk limits and the chief of staff is in [[file:orchestration.org][orchestration.org]]; tasks copied into VENTURE tickets are in [[file:venture.org][venture.org]].

* States

| State         | Means                                                         | Finished | Cancellable | Retryable |
|---------------+---------------------------------------------------------------+----------+-------------+-----------|
| ~unassigned~  | on the operator's backlog, with nobody                        | no       | yes         | no        |
| ~pending~     | with its assignee, no turn on it yet                          | no       | yes         | no        |
| ~running~     | its assignee has started a turn on it                         | no       | yes         | no        |
| ~blocked~     | held until the tasks it waits for complete, or until whoever its assignee said it waits on answers | no       | yes         | no        |
| ~review~      | finished by its assignee, waiting for the reviewer's verdict  | no       | yes         | no        |
| ~completed~   | done (accepted, when it had a reviewer)                       | yes      | no          | no        |
| ~failed~      | it broke, or the agent or daemon went away under it           | yes      | no          | yes       |
| ~stalled~     | a limit stopped it                                            | yes      | no          | yes       |
| ~cancelled~   | somebody cancelled it                                         | yes      | no          | no        |

Code asks the library instead of comparing states: =clawt_task_state_is_finished()=, =clawt_task_state_is_active()= (~pending~ and ~running~: what a turn timeout, an agent crash, the idle guard and the restart reconcile are about), =clawt_task_state_is_cancellable()= and =clawt_task_state_is_retryable()=. The three waiting states (~unassigned~, ~blocked~, ~review~) were appended to the enum in 0.36.0, so a stored or wire value means what it always did.

            task.create (no agent)          task.assign
  (made) ───────────────────────► unassigned ─────────┐
     │                                                 ▼
     │ after: unfinished blockers              ┌──► pending ──► running ──┬──► completed
     └──────────────────────► blocked ─────────┘      ▲                   │      ▲
                     every blocker completed           │ changes requested │      │ accept
                                                       └──── review ◄──────┘ (has a reviewer)
                     any unfinished state ──► cancelled        running ──► failed / stalled (retry: back to pending)
#+end_example

* Waiting on somebody

An assignee that cannot go on until somebody else acts says so with ~clawtilla_task_progress~: ~waiting_on~ is an agent id, =operator=, or =external:NAME= for a service (=external:venture=, =external:forge=), and ~question~ is the one line it needs answered (required for an agent or the operator).  The task goes to ~blocked~ with "waiting on NAME: QUESTION" as the reason; that reason is noted on the task, so a mirrored VENTURE ticket shows =blocked= with it as a comment.  The ~task.changed~ event carries ~waiting_on~ and ~question~, so a pod can tell the party (=on_task_changed=).

- An agent named is sent the question once, in its direct room with the assignee, so its reply reaches the assignee as an ordinary message.  Saying the same again sends nothing more.
- *Its answer ends the wait.*  The first message from that agent queued for the assignee in their direct room resumes every task of the assignee's waiting on it, and the assignee is woken in the task's room ("no longer waits on chief -- chief answered you in your direct room"), in a turn that is the task's, so that turn's end completes it as usual.  Before, only ~task unblock~, ~task_progress~ or ~task_complete~ ended a wait: an assignee that read the answer and ended its turn without a task tool left the task ~blocked~ for good.  Any message from the agent in that room counts, a clarifying question included; the assignee can say it waits again.
- *A question that cannot be sent does not block the task.*  If the router refuses it (a hop limit, a daily budget, a stalled room) or there is no room to send it in, the wait is undone, a note on the task says why, and the tool answers with an error saying the question was not sent.  The note is kept as ordinary progress, so the task stays open past the turn.
- *After a restart* a task restored ~blocked~ on an agent is not asked again: its question is already in that agent's mailbox, which is durable, or was already answered.  The answer, when it comes, resumes it the same way; nothing about the wait is kept in memory.  An answer queued in the instant before a crash, whose resume had not yet run, is not looked for again: ~task unblock~ ends that wait.
- The task stays its assignee's.  No turn end completes it and no turn timeout or idle guard is about it, but the assignee may still report progress on it or finish it, and either ends the wait.
- ~clawtilla task unblock TASK~ ends it from outside, and ~--on PARTY~ ends every wait on one party -- the move when a service that was down is back.  The assignee is told and the task is ~running~ again.
- Before this, ~blocked~ meant only "waits for other tasks", so a task held by a person or an outage stayed ~running~ with the block in a progress note, and looked silent rather than blocked.

* Tasks are kept, and survive a restart (since 0.35.0)

Every task is written to ~tasks.db~ in the state directory as it changes, by =ClawtTaskStore=.  A restart used to forget them all: a delegator could no longer ask what became of its work, a parent forgot the children it was waiting on, and the operator's Tasks list came back empty.

- *What is stored.* Each task whole, as =clawt_task_to_json()= writes it: every field, including the owner history, the completion hold, the retry count, the title, and when it was created, first started and finished. A few columns beside it (state, assignee, parent, created and finished times) are what lists filter and page on. A field added to a task later needs no migration: it is one more JSON member, read as its zero value from older rows.
- *The journal.* Every change also leaves a row in the task's history: when, the state it was left in, and what happened ("created by chief for scout", "retried by user", "cancelled by user: ...", "handed over to builder", or the failure reason). A save that changes nothing the state machine cares about, such as a model set right after creation, adds no row. ~task.show~ with ~journal: true~ returns it; ~clawtilla task show <id> --journal~ prints it.
- *Write-through.* =ClawtTaskManager= saves every transition before it emits ~task-changed~. A field set straight after creation by =tool_delegate= (room, model, consult, thread room), and an owner change from a handoff, are saved explicitly with =clawt_task_manager_save()=. A save that fails is logged and survived: the transition stands, because refusing work over a full disk would be worse than losing its history.
- *The live set and the history.* Memory holds what is live: every task that has not finished, and those that finished in the last day. That is what ~task.list~ returns and what every client's Tasks list shows. Older finished tasks leave memory on an hourly tick but stay in the store. They are still answerable by id (=clawt_task_manager_get()= reads them back without putting them on the live list), and ~task.list~ with ~history: true~ lists everything newest first, a page at a time (~before~ is the cursor, with ~state~, ~agent~ and ~limit~ to narrow it). On the command line that is ~clawtilla task list --history [--state failed] [--agent scout] [--before UNIX]~.
- *Retention.* A finished task is removed once it is older than ~orchestration.task_retention_days~ (180 by default, 0 keeps everything), with its journal. A task that has not finished is never removed, however old.
- *Spend.* What a task has already cost is read back on start from the agents' usage ledgers (the ~task_id~ tags on their turns), so ~orchestration.task_budget_usd~ keeps counting where it left off instead of resetting on every restart -- charged up each task's parent chain, finished subtasks included, as a live turn is.

** What a restart does with tasks that had not finished

They are restored silently: before anything listens to ~task-changed~, so a restored task sends no settle notice, raises no incident and reaches no client as news. A task with a room of its own (~thread: new~) gets its room back, transcript included.

Then, after turn recovery has turned every turn the restart cut short into either a queued item or an interrupted notice, each unfinished task is checked once for something still carrying it forward. A task is carried when any of these holds:

- its assignee armed a completion hold (~clawtilla_task_progress~: "not done yet");
- a task it handed on has not finished, so the child's settle notice will wake it;
- its assignee's mailbox holds a pending or leased item for it, which includes a cut-short turn handed back;
- its assignee has a wait pending;
- a handoff of it is still queued.

A task with none of these is failed with "the daemon restarted while this ran, and nothing was left to carry it on ... Retry it to run it again." Failed, not stalled: nothing stopped it on a limit, the daemon went away under it, which is the answer an agent crash gets too, and a failed task is retryable. Its delegator gets the usual settle notice (a delegator with several gets them folded into one turn by the router). The incident desk is kept quiet for this pass, as it is when an agent's tasks are orphaned: one restart is not a dozen problem reports.

** Incidents are kept with them

Incidents are written to the same file as they change, and restored as they were left: open or resolved, reported or still queued, with the log lines captured when the run broke. Nothing is published or flushed on restore, so a restart never reports an incident a second time, and a new failure of the same run counts up on the restored incident instead of opening another. The desk's bound (=INCIDENT_KEEP=) applies to the file too.

* The operator's own tasks, and a task's thread (since 0.36.0)

Tasks are not only what agents delegate.  The operator writes one down from any client (*New task*) or ~clawtilla task create~: what to do, optionally a title, and who does it -- or nobody yet, which puts it on the *backlog* as ~unassigned~.  A backlog task waits there; nothing that watches work with an assignee (a turn timeout, a crash, the restart reconcile) treats it as with anybody.  *Assign* (~task.assign~, ~clawtilla task assign~) takes it off the backlog and only off the backlog: a task somebody already has moves with a handoff, which tells the one losing it.

A task given to an agent this way, at creation or by assigning it, is sent as the operator's (=user=), with the task contract (=clawt_task_assignment_guidance()=) and the task's id on the delivery, into the conversation the two already share.  A send that is refused fails the task, so it is not left ~pending~ with nobody told.

Every task has a *thread*, kept in ~tasks.db~ beside the journal: notes, each with an author, a kind and a time.  The journal is what /happened/ to a task; the thread is what was /said/ about it.  The manager adds the assignee's progress reports (~progress~) and each result (~result~) itself; the operator adds *comments* (~task.comment~, the *Comment* box on a task's page, ~clawtilla task comment~).  A comment on a task that is with its assignee is also sent to them, from =user=, into the task's own room when it has one and the conversation the work is in otherwise -- the router then steers it into a running turn or queues it, as any message for a busy agent, so a comment never starts a turn of its own.  A comment on a backlog, blocked or finished task is only kept.  ~task.show~ carries the thread as ~notes~, and ~clawtilla_task_status~ shows the last five comments to an agent asking, the operator's named as "the operator".  A note emits ~task.noted~, not ~task.changed~: the settle notice and the incident desk hang off the latter, and a comment on a finished task must not send its delegator the result again.

Every client's task row shows the task's title with who it is between underneath ("user · on the backlog" for one with nobody), an *Assign…* control on backlog rows, and *Details*: the prompt, the result, the thread, a box to comment in, and the history.

* Work that waits for other work (since 0.37.0)

A task can wait for other tasks: it is *held* as ~blocked~ and handed over by itself once every task it waits for has *completed*.  An agent gives ~clawtilla_delegate~ an ~after~ (task ids, comma-separated); the operator gives ~task.create~ an ~after~ (*Wait for* on the New task form, ~clawtilla task create --after~), or links a backlog task with ~task.link~ (*Waits for* in a task's Details, ~clawtilla task link~).

- *What is kept.* The links are in ~tasks.db~ (~task_links~), and so is the held task's delivery (~held_deliveries~): everything it would have been sent with -- the sender, the target (the assignee or the task's own room), the body with the task contract, the hop depth, the priority and the conversation it was delegated from (=clawt_task_build_held_delivery()=).  A restart keeps both, and a held task whose blockers completed while the daemon was down goes when it comes back.
- *Release.* When a blocker completes, every task waiting for it with nothing else unfinished is released (=clawt_daemon_tasks_release_ready()=): ~blocked~ → ~pending~, and the delivery is taken out of the store (once -- a delivery released twice is work done twice) and sent exactly as it would have been: a delegation through the delegation path, as the delegator, at its hop depth, into the same conversation; an operator's task as a message from =user=.  The cross-talk limits are applied then, at the send; a send that is refused fails the task, so its delegator's settle notice says why.  An operator's backlog task with nothing to send goes back to ~unassigned~.
- *What holds.* Only ~completed~ releases (=clawt_task_manager_waiting_on()=).  A blocker that fails, stalls or is cancelled still holds the task -- its work was meant to come first -- and whoever is waiting is told once: the delegating agent as a system notice in the conversation it delegated from ("Retry it, cancel the waiting task, or stop waiting for it"), the operator as a note in the task's thread.  A retried blocker that then completes releases it as usual.  A blocker pruned long after it finished holds nothing.
- *Changing what it waits for.* ~clawtilla_task_link~ (an agent, on a task it delegated that is still ~blocked~) and ~task.link~ / ~task.unlink~ (the operator) add or take away blockers.  Taking the last one away hands the work over now (the manager's ~blockers-changed~ signal).  Work already handed over cannot be held back: linking is refused for a task that is not on the backlog or already waiting.
- *Refused.* An id naming no task, a task waiting for itself, a link that would close a cycle -- directly or further back -- and a task that has already ended.  Without a task store ~after~ is refused, because there would be nowhere to keep the delivery.
- *On the wire and in the clients.* A task object carries ~after~ (every blocker) and ~waiting_on~ (the ones still holding it); every client's row shows =clawt_task_waiting_caption()= ("waiting for task-a to complete"), and Details lists what it waits for with *Stop waiting* on each.

* Work that is checked before it counts (since 0.38.0)

A task can have a *reviewer*: finishing it sends the result to them as ~review~ instead of ~completed~, and only their accept completes it.

- *Who reviews.* ~agents.review_by~ on the assignee -- ~lead~ (its team's lead, or the chief of staff when the team has none), ~delegator~ (whoever handed it the task), ~operator~, an agent id, or empty for none -- or, for one task, ~review~ on ~clawtilla_delegate~ or on ~task.create~ (~clawtilla task create --review~).  It is resolved once, when the task is made (=clawt_task_resolve_reviewer()=), so "the lead" is the lead there was then.  Nobody reviews their own work: ~lead~ or ~delegator~ landing on the assignee means no review; naming the assignee outright, or an agent that does not exist, refuses the task.  When the operator delegated it, ~delegator~ is the operator.
- *Asking.* When the assignee finishes (=clawtilla_task_complete=, or its turn ending with the result), the task goes to ~review~ with the result kept and the manager's ~review-requested~ signal fires -- once per result, not on every comment made while it waits.  An agent reviewer is told in a system notice, in the task's room or the conversation it was delegated from, with the result and how to answer.  The operator gets a decision in the inbox, ~review-<task id>~: answer ~accept~, or write what to change.  The task's page in every client has *Accept* and *Request changes* too; either door settles the other.
- *Reading it.* The reviewer may read the task as its delegator and assignee may: ~clawtilla_task_status~, ~clawtilla_task_result~ (which, in ~review~, returns the result under review to the reviewer and the assignee; the delegator is still told "no result yet" until it is accepted, since a result in review may be sent back) and a task wait.  Every check takes the reviewer from the task itself, so the one that may give the verdict is the one that may read it -- a project's ~review_by~ only matters when the task is made, and only when the delegation named no ~review~.
- *Verdicts.* An agent answers with ~clawtilla_task_review~ (~task_id~, ~accept~, ~notes~); the operator with ~task.review~ or the inbox, and may decide whoever the reviewer is.  The assignee's own verdict is refused.  Accept completes the task -- a blocker held on it is released, and the delegator gets the usual settle notice unless the delegator was the reviewer, who already knows.  Changes need notes: the task goes back to ~pending~ with the notes in its thread and a notice to the assignee, and ~review_round~ counts up.  Each verdict and each request renews the tree's budget, as a settle does: a review round is owed work, not a runaway.
- *Bounded.* After ~orchestration.review_rounds~ (default 3) rounds of changes the task stays in ~review~ and becomes the operator's to decide, in the inbox, rather than the two agents going round again.  0 removes the limit.
- *On the wire and for the agent.* A task object carries ~reviewer~ (an agent id, or =user=) and ~review_round~; its thread has the verdicts as ~review~ notes.  TOOLS.org says how review works and, when an agent's work is reviewed, by whom.

* Work in a checkout of its own (since 0.39.0)

Two agents told to "work in ~/src/proj" work on top of each other, and nobody can tell whose change is whose.  A task given a *repository* -- ~repo~ (and optionally ~base~) on ~clawtilla_delegate~ or ~task.create~ (*Repository* on the New task form, ~clawtilla task create --repo~), or a routine or trigger with ~worktree: true~ -- gets a checkout of its own instead, and what it changed can be read as a diff.

- *Where.* In the assignee's workspace at =tasks/<task>= (the id without =task-=), on the branch =clawtilla/<task>=, started from ~base~ (its =HEAD= when left out) pinned to a commit -- so the diff never shows somebody else's later work as this task's.  The repository is named by its absolute *host* path; the CLI makes a relative one absolute.
- *Which shape* (=clawt_task_checkout_mode_for()=, ~checkout.mode~ on the wire).  A =git worktree= for an agent whose tools run on the host unconfined: cheap, and the branch is in the repository at once.  A hard-linked local clone for one confined by bwrap (~runtime.confine~) or working in a container, VM or distrobox: a worktree's =.git= points back into the repository, which a sandbox that binds only the workspace cannot follow.  An agent on an ssh host, or a container on another podman connection, has no workspace the host can write into its machine, and a task with a repository is refused for it, with that reason.
- *Telling the agent.* The assignment ends with a genuine =[clawtilla]= paragraph (=clawt_task_checkout_guidance()=): the path -- and the path inside its computer, for a container or VM with its workspace mounted -- the branch, the base, and the rules: work only there, commit on that branch, do not push, merge or touch the repository itself unless asked.  It is part of the contract the daemon recognises the assignment by (=clawt_task_assignment_guidance_for()=), so it survives a hold for blockers and a restart unchanged.  A routine's goes after its instructions; a trigger's goes *first*, above the payload's fence.
- *Refused.* A path that is not a directory, a base that names no commit, a destination that already exists, and a repository with no assignee (an operator's backlog task).  The delegation, the task or the run is refused or fails with git's own words; nothing is sent off to land on top of somebody else's work.
- *The diff* (~task.diff~, *Show changes*, ~clawtilla task diff~).  =git diff <base>= in the checkout -- committed and uncommitted changes together -- and the files git does not track yet, by name; taken off the main loop, and cut at 512 KiB on a line boundary with ~truncated~ said.  Once the checkout is gone the diff still works: =git diff <base> <branch>= in the repository, which kept the branch (~from_branch~).
- *Removal* (~task.checkout_remove~, *Remove checkout*, ~clawtilla task checkout-remove~).  Refused while the task is pending or running, and -- unless ~force~ -- while the checkout holds uncommitted work, which would go with it.  The branch is always kept: a worktree's is in the repository already, and a clone's is fetched back into it first (refused, with the clone left alone, if that fails).  It is said in the task's history.  Removal is confined to the workspace's =tasks/= directory (=clawt_remove_tree()=).
- *Clean-up.* Hourly, every agent's =tasks/= directory: a checkout whose task finished more than ~orchestration.checkout_keep_days~ (default 14) ago is removed as above, unless it is dirty.  A directory whose task is unknown is left alone -- there is no record of which repository to give its branch back to.
- *On the wire.* A task object carries ~checkout~: ~repo~, ~path~, ~branch~, ~base~, ~mode~ and ~present~.

* Projects: what work is for, and what it may spend (since 0.40.0)

A *project* (~projects:~) is a piece of work the fleet is pointed at: what it is for (~goal~), where it lives (~directory~, a host path), who reviews its work (~review_by~), who works in it (~agents~), and what it may spend in a calendar month (~monthly_budget_usd~, ~budget_warn_percent~, ~budget_hard_stop~).  Optional: a fleet with none works exactly as before.

- *Which project a task is in* (=clawt_project_resolve()=, decided once when the task is made): the one ~project~ names on ~clawtilla_delegate~ or ~task.create~ (an unknown id refuses the work rather than guessing); else its parent task's, since a piece of a project's work is the project's work; else the one whose ~directory~ its repository is -- its checkout's repository, or a worktree routine's or trigger's directory -- by path, then by a git remote the two share, compared as =host/owner/repo= (=clawt_git_remote_canonical()=), so a gitlab.com checkout and a self-hosted mirror of the same repository match.  Otherwise none.
- *What its assignee is told.* The assignment opens its closing =[clawtilla]= text with the project's name and goal (=clawt_project_spec_brief()=), kept on the task as it was when the task was made (~project_brief~), so the text the daemon recognises the assignment by never changes.
- *Who reviews it.* The project's ~review_by~ when the delegation names no ~review~ of its own -- between the delegation and the assignee's ~agents.review_by~: the project's rule beats the agent's habit.  Resolved like any other spelling, so never the assignee.
- *Its month.* Spend is summed, per task, from every agent's usage ledger (=clawt_usage_task_spend()=) over the project's tasks *made this calendar month*, local time (=clawt_task_store_project_tasks()=, the indexed ~tasks.project~ column).  A task made late last month that ran into this one counts towards last month: a month is the work started in it.  Read at most once a minute per project (=clawt_daemon_project_spend()=).
- *The budget.*  At ~budget_warn_percent~ (default 80) of ~monthly_budget_usd~ the operator gets one ~budget~ notification a month.  With ~budget_hard_stop~, once the month's spend reaches the budget, new work in the project is refused as the spending caps refuse (=LOOP_LIMIT=, with the reason): a delegation, a new task, a worktree routine's or trigger's run, and a held task's release (which fails, its delivery dropped).  Work already handed over is not stopped, and work outside the project is not held to its budget.
- *What every agent finds.* The =# BEGIN clawtilla projects= region of =PROJECTS.org= lists the projects it works in (every project whose ~agents~ is empty or names it): name, goal, directory, reviewer and budget -- not this month's spend, which changes every turn and would keep an identity file from ever settling.  It sits above the agent's own text (after the =#+= header lines), is capped at 4 KiB, is rewritten on start and whenever a project changes, and is written only when its text changed.  The agent keeps the rest of the file.
- *Managing them.* ~project.list~ (with ~month_spend_usd~ and ~stopped~), ~project.create~ / ~project.set~ / ~project.remove~; Settings → *Projects* in every client; ~clawtilla project list|create|set|rm~.  A removed project's tasks keep its name.  A task object carries ~project~; every client's task row shows it.

* The agent board (since 0.78.0)
:PROPERTIES:
:CUSTOM_ID: agent-board
:END:

One view that answers "where is oxpecker right now, and what is still in front of him?" for one agent, or a team's lead with the team beside it.  The task tree, the states, the progress notes, the streamed steps, the mailbox and the VENTURE tickets already say all of it between them; the board puts them in one reply, ~task.board~ ([[file:ipc-protocol.org::#task-board][ipc-protocol.org, "task.board"]]), which the CLI (~clawtilla task board~), the GTK client and the web client all draw.  The board changes nothing: it reads the task manager and what the daemon already knows, and is asked again on the events that move it.

** Cards

A card is one of the agent's *top-level* tasks: a task assigned to it, in the live set (what ~task.list {agent}~ lists: everything unfinished and what finished in the last day), whose parent is not also the agent's own -- typically one per VENTURE ticket it was handed.  A task of its own under another of its own is drawn as a chip on that card, not as a second card.  For a window longer than a day, the completed tasks the store still holds for the rest of it are read back too (at most 1000).

The tasks a card handed on -- its direct children, from the live set -- are its *chips*: worker, state, phase, elapsed time, and the ~after:~ links between siblings, so a client can draw "this waits for that" between chips.

The reply's ~totals~ make the board add up to the list: ~listed~ (the agent's tasks in the live set) = ~cards~ + ~hidden~ (cancelled, or finished before the window) + ~nested~ (under another of its own) − ~from_history~ (done cards read back from the store).

** Columns, and the rules that decide them

Every card is in exactly one column, decided by =clawt_board_classify()=: a pure function of the task, its children, its phase, a clock and three facts the daemon supplies (open operator decisions on it or its children, whether the agent has a clawtilla wait pending, and the quiet window).  The rules are tried in this order; the first that matches wins.

| # | Column       | When                                                                                                                                       |
|---+--------------+--------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | (hidden)     | not this agent's; on the operator's backlog (~unassigned~); ~cancelled~; or finished before the window                                       |
| 2 | ~done~       | ~completed~ inside the window                                                                                                               |
| 3 | ~blocked~    | any of the reasons below -- pinned first                                                                                                    |
| 4 | ~backlog~    | ~pending~ (not started, or sent back), or ~blocked~ on ~after:~ only (held until the tasks it waits for complete)                            |
| 5 | ~review~     | ~review~: its own result waits for its reviewer                                                                                             |
| 6 | (the phase)  | ~running~ with a reported phase: ~planning~ → planning, ~delegated~ → delegated, ~reviewing~ → review, ~gating~ and ~landing~ → gating      |
| 7 | ~review~     | ~running~, and a child's result is in ~review~ with this agent as its reviewer -- the bottleneck signal                                    |
| 8 | ~delegated~  | ~running~, with a child that has not finished                                                                                               |
| 9 | ~planning~   | ~running~, and nothing it handed on is still going                                                                                          |

The reasons for ~blocked~, any number at once, each with its wire spelling (=clawt_board_block_nick()=):

| Reason           | When                                                                                                                         |
|------------------+------------------------------------------------------------------------------------------------------------------------------|
| ~failed~         | the task itself ~failed~ inside the window                                                                                   |
| ~stalled~        | the task itself ~stalled~ (a limit stopped it) inside the window                                                             |
| ~child_failed~   | a child ~failed~, and the card's assignee has not reported progress or a phase since it did                                  |
| ~child_stalled~  | the same for a ~stalled~ child                                                                                               |
| ~decision~       | an operator decision is open on the card or one of its children, or a child waits on =operator=                             |
| ~waiting~        | the card itself waits on somebody it named (~clawtilla_task_progress~ ~waiting_on~: an agent, =operator= or =external:NAME=) |
| ~quiet~          | the card has gone quiet (below)                                                                                              |
| ~phase~          | its assignee reported the ~blocked~ phase                                                                                    |

Three choices worth knowing:

- *What needs somebody beats a phase.*  A card reported as ~gating~ whose child failed is under ~blocked~, not ~gating~: the phase is the agent's word about its own work, the failure is a fact about somebody else's.
- *A report after a child's failure unpins it.*  The agent saying anything -- a progress note or a phase -- after a child failed is taken as it having seen the failure and gone on (delegated the part again, done it itself).  Without this a fan-out that replaced one failed child would stay blocked until the day dropped the failure out of memory.  Retrying the child unpins it too, since it is no longer failed.
- *A card's own review is in the review column*, with ~review.waiting_for~ naming its reviewer, so the reader can tell "waits for oxpecker" (the bottleneck) from "oxpecker waits for chief".

Within a column: the backlog in the order the agent will take the work -- what it was handed (~pending~) before what is held, oldest first within each, numbered from 1 (~position~) -- done newest first, everything else by how long it has been going.

** Phase: what the agent says it is doing

An optional ~phase~ on ~clawtilla_task_progress~ and ~clawtilla_task_complete~: one of ~planning~, ~delegated~, ~reviewing~, ~gating~ (building or testing), ~landing~ (merging, tagging, releasing) or ~blocked~.  Case is forgiven as for every nickname clawtilla reads; anything else -- ~none~ included -- refuses the whole call with the six spelled out, and *nothing is recorded*: not the note, not the result, so the agent calls again rather than leaving half a report.  Without ~phase~ both tools are exactly what they were.

- *Stored on the task* (~phase~, ~phase_at~ in ~tasks.db~, no migration: one more JSON member), with every report kept as a bounded history (the last 32, ~phases~) that the timeline draws.  The same phase again is not a new report and does not move the time it began.
- *It overrides inference* for a ~running~ task (rule 6 above) but not the reasons for ~blocked~.  On a ~pending~, held or finished task it is shown, not used.
- *It lasts until the task goes back to ~pending~* -- a retry, a review asking for changes, a release from a hold -- which clears it with a =none= mark in the history: a phase describes one attempt.  A wait and its resumption keep it.
- *With ~waiting_on~* the phase is kept on the now-blocked task, where the work had got to when it stopped.  *With ~clawtilla_task_complete~* it is recorded before the state moves, so the timeline shows the phase the work ended in.
- Each report is journalled ("progress noted; phase gating", "phase landing") and announced with ~task.changed~, so the board's clients redraw.

The daemon-side calls are =clawt_task_manager_note_progress_in_phase()=, =clawt_task_manager_complete_in_phase()= and =clawt_task_manager_set_phase()=; validation is =clawt_task_phase_parse()=.

** Quiet: running, and nothing heard

A running card is *quiet* when nothing has been heard of it for ~orchestration.board_quiet_minutes~ (default 20; 0 turns the rule off).  Deliberately not called "stalled": ~stalled~ is a task state, a limit stopping the work, while a quiet task is still running and nobody has heard from it.

- *Heard* is the latest of: made, first started, a state change, a progress or phase report, or a streamed step its assignee took on it (=clawt_task_get_last_sign_of_life()=), on the card or on any running child.  Steps are counted in memory only (=clawt_task_manager_note_activity()=, from every step the daemon routes for a turn on that task), so just after a restart only the stored times count.
- *Never quiet:* a task that is not ~running~; one whose assignee has a clawtilla wait pending (it said why it will be silent); one with a child queued, held or in review, which is waiting on somebody else.
- A quiet card goes under ~blocked~ with the reason ~quiet~ and ~since~.  A card that is not quiet yet carries ~quiet_at~, when it would become so, and so does every chip: a client can flip it at that moment on a timer of its own, without asking the daemon again.

** Timeline: when each state started and ended

Each card and chip carries ~timeline~ (unless the request says ~timeline: false~): ~states~, each ~{state, from, to}~, and ~phases~, each ~{phase, from, to}~; the last span has no ~to~ (still going, or the state the task ended in).  =clawt_board_timeline()= builds it.

- *Where the history comes from.*  The journal in ~tasks.db~ (since 0.35.0) has a row for every state change, with its time -- that is the transition record, and nothing new was needed for it.  Rows that changed nothing (a progress note) extend the open span.  ~source~ says ~journal~.
- *Older tasks.*  A task saved before 0.35.0, or held by a daemon without a store, has no journal: its timeline is drawn from its own stamps -- created, first started, finished -- as pending, running and the state it ended in (~source: stamps~).  Coarse, never wrong about what it shows.
- *What 0.78.0 adds to every task.*  ~state_at~ (when the state last changed; read as the latest of the created, started and finished times for a task saved before it), ~progress_at~ (the last progress report) and the phase fields, all in the task's JSON.  ~state_at~ is what a review's wait is measured from.  Times are whole seconds.
- Phase spans come from the task's own phase history, which starts with 0.78.0: older tasks have none.

** Header and lanes

The ~header~ is the agent itself: its live state, the latest step of its running turn (text, tool, when) -- nothing between turns, since a step from an hour ago is not what it is doing now -- the task that turn is on (or its most recently active running task), how long the turn has run (~busy_since~), its mailbox depth, and counts per column with ~in_flight~ (planning + delegated + gating) and ~in_review~.

The ~lanes~ are the people the work is with: the team asked for (~team~), or the agent's own team, then every worker a chip names that is not on it -- never the board's own agent.  Each lane has the agent's live state and step, its current task, its queue (~queued~: pending and held; ~running~; ~review~; ~mailbox~) and ~idle~, the seconds since its last streamed step (0 while it is in a turn; absent when this daemon run has seen none).

** Live updates

There is no polling loop in the daemon.  A client asks ~task.board~ once and asks again (debounced) on the events that move it: ~task.changed~ (every transition, every progress or phase report), ~task.noted~, ~agent.state~, ~mailbox.queued~ / ~mailbox.delivered~, ~decision.asked~ / ~decision.settled~ / ~decision.deleted~ and ~wait.changed~; it may patch the header's step from ~turn.step~ (subject the agent) without asking.  Quiet is the one thing that changes by time alone, and ~quiet_at~ is there for it.

* What the lists say about themselves

~task.list~ carries ~kept~ (whether this daemon has a task store), ~retention_days~, and still ~since~, the daemon's start. Every client and the CLI put =clawt_task_list_caption()= over the Tasks and Problems lists: "Tasks still open, and those that finished in the last day. Every task is kept for 180 days with a record of what happened to it, across restarts; older ones are in the history (clawtilla task list --history)."  A daemon whose ~tasks.db~ would not open keeps working in memory, says so once in its log, and its lists carry the old caption instead (=clawt_held_since_caption()=): "Since the daemon started at 09:14. Tasks and problems are held in memory, so a daemon restart clears this list; ...".  Saying "kept" when they are not would be the lie that caption was written to stop.

* Work for another fleet (since 0.69.0)

A task can cross fleets: its assignee is =AGENT@ALIAS=, a linked fleet's agent.  Here it is a *proxy* that follows the real task there, reports to its delegator like any task, and is never failed by a restart; cancelling it cancels the work there.  Work another fleet hands this one is a real task whose origin is =fleet:ALIAS:AGENT=, capped by that fleet's grant.  Both carry =remote_peer=.  See [[file:federation.org::#delegation][federation.org, "Delegation"]].

* Worked examples

** A backlog, worked through by the operator

#+begin_src bash
# Write it down now, decide who does it later.
clawtilla task create --title "Release notes" "Write the release notes for 2.4 from the merged changes."
clawtilla task list --state unassigned

# Give it to scout, then add a detail while scout works on it.
clawtilla task assign task-01m0k5… scout
clawtilla task comment task-01m0k5… "Leave out the internal refactors."
#+end_src

The comment reaches scout in the running turn (or queues behind it); it never starts a turn of its own.

** One task after another, reviewed, in its own checkout

#+begin_src bash
# The migration first, in a checkout of ~/src/shop.
clawtilla task create --agent builder --repo ~/src/shop --project shop \
        "Add the orders.shipped_at column and its migration."
# → task-01m0aa…

# The API change waits for it, and the lead reviews it.
clawtilla task create --agent builder --repo ~/src/shop --project shop \
        --after task-01m0aa… --review lead \
        "Expose shipped_at in GET /orders."
# → task-01m0ab…, blocked

clawtilla task diff task-01m0aa…          # read what the first one changed
#+end_src

When ~task-01m0aa…~ completes, ~task-01m0ab…~ is released to builder as it would have been sent. When builder finishes it, it goes to ~review~ and the lead is asked. If the operator wants to decide instead: ~clawtilla task review task-01m0ab… changes "Return it as ISO 8601."~ sends it back with the notes, or ~accept~ completes it.

** An agent doing the same

A chief of staff calls ~clawtilla_delegate~ with ~agent: builder~, ~repo: /home/me/src/shop~ and ~prompt~, gets ~task-01m0aa…~, then calls it again with ~after: task-01m0aa…~ and ~review: delegator~. It does not poll: the second task starts by itself, and the chief is asked to review it when it is done.

* Troubleshooting

| What you see                                                     | Why, and what to do                                                                                  |
|------------------------------------------------------------------+------------------------------------------------------------------------------------------------------|
| A task failed with "the daemon restarted while this ran"         | Nothing was left to carry it on after a restart. Retry it (~clawtilla task retry~).                  |
| The Tasks list says tasks are "held in memory"                   | ~tasks.db~ would not open; the daemon's log says why. Fix the state directory and restart.          |
| ~after~ or ~task.link~ is refused                                | No task store (see above), a cycle, a self-link, or the task is already with its assignee.           |
| A ~blocked~ task never starts                                    | Only ~completed~ releases it. ~clawtilla task show --journal~ on each blocker: retry the failed one, or ~clawtilla task unlink~ it. |
| A task sits in ~review~                                          | Its reviewer has not answered, or ~review_rounds~ ran out and it is in the operator's inbox. Its reviewer is the task's own ~reviewer~ (on the wire, and in the journal's "with X for review"), not the project's. Decide it with ~clawtilla task review~. |
| A task with ~repo~ is refused                                    | Its assignee is on an ssh host or another podman connection, or the path, base or destination is wrong; the refusal quotes git. |
| ~checkout-remove~ is refused                                     | The task is still pending or running, or the checkout has uncommitted work: commit it, or ~--force~. |
| New work in a project is refused with =LOOP_LIMIT=               | The project's ~budget_hard_stop~ is on and its month's budget is spent. Raise the budget, or wait for the month. |
| A task's VENTURE state is ~skipped~ or ~dead~                    | See [[file:venture.org][venture.org]], "Troubleshooting".                                          |
| A board card is under ~blocked~ with ~quiet~                     | Nothing was heard of it for ~orchestration.board_quiet_minutes~. Its agent should report with ~clawtilla_task_progress~, or set a wait while it is waiting; a restart forgets streamed steps, so a long-running card can read quiet just after one. |
| A board card stays under ~blocked~ with ~child_failed~           | Retry the child, or have the agent report progress or a phase on the card: a report after the failure is taken as it having moved on. |
| ~clawtilla_task_progress~ is refused for its ~phase~             | Only ~planning~, ~delegated~, ~reviewing~, ~gating~, ~landing~ and ~blocked~; nothing was recorded, so call it again.  |
