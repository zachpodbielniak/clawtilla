* The web client

~clawtilla-web~ serves everything ~clawtilla-gtk~ does, over HTTP, from
the same daemon over the same socket.  A laptop on the tailnet reaches
the fleet on a workstation without a tunnel set up by hand, and without
GTK installed on either end.

#+begin_src bash
clawtilla-web
#+end_src

#+begin_example
clawtilla-web is listening on:
  http://127.0.0.1:8790/
  http://100.84.12.7:8790/

There is no login here: anything that can reach a listed
address can drive the whole fleet.
#+end_example

** Its own binary, on purpose

Not a mode of ~clawtillad~.  This page can start, stop, reconfigure and
delete every agent on the machine, and run commands inside their
computers.  A surface like that should exist because somebody decided
they wanted it, not because the daemon happened to start.

** Where it listens

The loopback, and this machine's tailnet address when there is one.

A tailnet is the one network where listening past the loopback is
defensible without a login of our own: every peer is a device the user
enrolled and WireGuard authenticated, and nothing off the tailnet can
route to a =100.64/10= address at all.  ~clawtillad~ binds its own
convenience listener on exactly that reasoning.

The address is found with ~getifaddrs()~ rather than by running
=tailscale ip=, and both the interface name and the address range are
checked -- =utun= is any tunnel on a BSD, and a container can hold a
=100.64/10= address for reasons of its own.

*** A machine with no tailnet gets the loopback alone

It does not fall back to every interface.  Widening the audience because
an address was missing is the opposite of what somebody would want, and
this client has no authentication to make that safe.

*** Naming an address yourself

#+begin_src bash
# This machine only
clawtilla-web --no-tailscale

# Somewhere else, on another port
clawtilla-web --bind 192.168.1.10 --port 9000

# Two addresses
clawtilla-web --bind 127.0.0.1 --bind 10.0.0.4
#+end_src

Using ~--bind~ at all replaces the defaults, so the tailnet address is
not quietly added to whatever was named.

An address a person named is never optional: failing to bind it exits
non-zero, because a client that ignored where it was told to listen and
started anyway is running somewhere nobody knows about.  The tailnet
address -- which clawtilla chose, not the person -- is a warning, and the
loopback still comes up.

*** What it reports is what it bound

The startup banner is built from the addresses the server is actually
listening on, not from the ones it was asked for.  A convenience address
whose bind failed is exactly the interesting case, and announcing the
request would say it was reachable there.

** It has no login

Anything that can reach a listed address drives the whole fleet.  On a
tailnet that is bounded by WireGuard.  Anywhere else, put it behind
something that can require a login.

There is deliberately no password flag: a password on the command line is
in the shell history and in the process table, and a real login for this
would need session handling, storage and a reset path -- which is a
reverse proxy's job, done properly, rather than ours done badly.

** The views

The same seven the GTK client's view switcher has, in the same order.

| View     | What is on it                                              |
|----------+------------------------------------------------------------|
| Chat     | transcript, composer, slash commands, attachments          |
| Agent    | every setting, the workspace files, the memory store       |
| Mailbox  | what is waiting, what died, purge and requeue              |
| Computer | exec console, mounts, the exchange, rebuild                |
| Routines | scheduled work, and running one now                        |
| Tasks    | delegated work, the budget, cancelling                     |
| Flow     | what the agents are saying to each other                   |

And seven settings pages: VM images, teams, spending, integrations,
connectors, appearance and connections.

*** On a phone

The same views, laid out for a screen 375 pixels wide rather than for a
narrow desktop.  Three things differ below 56rem, and each of them is a
response to something a phone has and a desktop does not.

**** The sidebar is a drawer, and it starts closed

Reached with the ☰ button in the topbar.  It was a 14rem band pinned
above every page --- on a 660px viewport that is a third of the screen
permanently spent on navigation, with the content starting below it on
every view.  Measured on a 375x812 phone: the first line of content began
at y=317 before, and begins at y=93 with the drawer closed.

It is a hidden checkbox and a ~<label for>~, not a ~<details>~ and not a
script.  The reason is specific: the sidebar carries
~hx-swap="outerHTML"~ on ~sse:fleet~, so anything remembered *inside* it
is thrown away every time an agent changes state --- which on a live
fleet is several times a minute.  The checkbox sits in front of the
sidebar, where the swap does not reach it.

**** Height is measured in ~dvh~

~100vh~ on a phone is the viewport with the URL bar retracted, so a box
measured that way is taller than what is visible and its bottom row ---
the composer --- starts below the fold.  Both units are declared, so a
browser that does not know ~dvh~ keeps the first.

**** Grid tracks can shrink

Every ~minmax()~ floor in the sheet either is ~0~ or goes through
~min()~.  A bare length there is a *hard* floor: the track refuses to go
under it and overflows its container instead of shrinking, which on a
320px screen is a page that scrolls sideways.

The two spellings mean different things and both are wanted.
~min(20rem,100%)~ keeps a preferred width and gives it up when there is
no room, which is what an auto-fit column wants.  Plain ~0~ is the
stronger form and is what a row holding a scrolling box wants, since
~1fr~'s own minimum is min-content --- a long transcript would otherwise
push the row past the bottom of the screen rather than scrolling inside
it.

*** The routes, and the one that has to be last

Around eighty, in families.  A ~GET~ renders; a ~POST~ does something and
answers with the page it did it on.

| Family                        | What is under it                        |
|-------------------------------+-----------------------------------------|
| =/=, =/fleet=                 | the fleet index                         |
| =/a/:id/:view=                | the seven agent views                   |
| =/a/:id/...=                  | everything done to one agent: send, start, stop, restart, reset, set, team, reorder, remove, exec, rebuild, attach, mount, mailbox, memories, file, files, compose, export, copy |
| =/f/...=                      | fragments htmx swaps in: the sidebar, a transcript, an attachment |
| =/settings=, =/settings/:page= | the seven settings pages               |
| =/settings/<page>/...=        | their actions: add, save, remove, health, test, authorize, revoke |
| =/new=, =/import=, =/design=  | making an agent                         |
| =/alerts=, =/decisions=, =/routines/...=, =/tasks/:task/cancel= | the standing surfaces |
| =/events=                     | the SSE stream                          |
| =/static=                     | the vendored scripts                    |

~/a/:id/:view~ is registered *last*, from its own
~clawt_web_register_views()~, and nothing may go after it.  A route
pattern compiles to an anchored regex where ~:param~ becomes ~([^/]+)~,
and the router answers with the *first* pattern that matches -- so
~/a/:id/:view~ claims every three-segment ~GET~ under an agent.
~/a/x/export~, ~/a/x/copy~ and ~/a/x/file~ were all quietly served by
the view handler.

The symptom is not an error.  An unrecognised view falls back to chat, so
a swallowed route renders the chat page and answers =200= -- the export
came back as ~text/html~, which reads as a formatting problem rather
than a routing one.

Depth is what bounds the hazard: because ~:param~ stops at a slash,
~/a/:id/:view~ cannot reach ~/a/:id/mount/add~, and ~/settings/:page~
does not swallow ~/settings/teams/add~ for the same reason.  The rule to
follow is still the simple one -- register the catch-all last -- because
counting segments is how somebody gets it wrong.

*** Slash commands

The same nineteen the GTK composer answers, typed into the message box.
Three mean something slightly different in a browser, and the help says
so rather than leaving anybody to find out.

| Command             | What it does                                        |
|---------------------+-----------------------------------------------------|
| =/help=             | list them                                           |
| =/start= =/stop= =/restart= | the agent's lifecycle                       |
| =/reset=            | start its AI session again, from nothing            |
| =/attach=           | send a file with the next message                   |
| =/compose=          | a full-page box, where GTK opens =$EDITOR=          |
| =/edit [file]=      | open a workspace file *in the page*                 |
| =/files=            | this agent's workspace files                        |
| =/memory <query>=   | search what it has remembered                       |
| =/agents=           | who is in the fleet                                 |
| =/flow= =/tasks=    | go to those views                                   |
| =/retry=            | send your last message again                        |
| =/export [org]=     | download the conversation                           |
| =/copy [org]=       | show it to copy, where GTK reaches the clipboard    |
| =/clear=            | hide the transcript *on screen only*                |
| =/new=              | create an agent                                     |

=/clear= sends nothing to the daemon.  The history is the daemon's, and a
command that tidied the view must not be one that destroyed it -- =/reset=
is the one that clears a session, and it says so.

=/export= and =/copy= go through =clawt_export_transcript()=, the same
function the GTK client uses, so the two produce the same bytes.  Three
formats: markdown, org, plain.

*** Editing workspace files

The GTK client opens them in =$EDITOR=, which is a program on the machine
somebody is sitting at.  A browser reached over the network has no such
thing, so the file comes over the wire: ~agent.file_read~ and
~agent.file_write~ exist for this and nothing else.

The name goes through ~clawt_workspace_file_path()~, which refuses
anything holding a separator or "..".  This is reached from an IPC
request, and a client that could name =../../secrets= would be reading
another agent's credentials.

*** The agent editor is built from the schema

Not from a list of rows.  ~agent.show~ reports every settable key with
this agent's value for it, walked from ~clawt_config_schema_get()~, and
the page renders a control per type.  An option added to the schema
appears here without anybody editing the client.

That is the same rule the daemon's integrations and its starter config
already follow, and for the same reason: a hand-written list of an
option's keys drifts silently, and the symptom is a setting that is
accepted, reported as saved, and then read from nowhere.

One key gets a control the schema cannot describe.  ~team~ is a plain
string there, so the generic path would draw a text box -- asking
somebody to know a team's id and to type it without a typo, when the
daemon can say what the ids are.  It is a select of the teams
~team.list~ reports, by name, which is the same control the GTK client's
agent editor has.  A team an agent names but the fleet does not declare
is *added to the list* rather than dropped, marked =(set by hand)=:
without that the control would open showing the first entry and saving
the page -- without touching that row -- would move the agent somewhere
nobody chose.

Nine keys are the exception, and the page says nothing about them because
it cannot: ~orchestration.mailbox.*~ and ~memories.*~ carry
=CLAWT_SCHEMA_FLAG_PER_AGENT=, and their spelling inside an agent block
lives in hand-written tables in =clawt-agent-manager.c= and
=clawt-config.c= rather than in the schema.  Guessing a name would
produce fields that are accepted and read from nowhere, which is the
failure the rule exists to prevent, arrived at from the other direction.

*** Only what changed is sent

Saving compares each field against what the daemon reported.  ~agent.set~
rewrites every agent's files on each call, so posting a hundred unchanged
keys would do that a hundred times for a form somebody opened and closed.

A permission changed under a running agent says so: an AI CLI lists its
tools once, when its session starts, so the change reaches the agent's
files and not its session.

** Appearance

Theme, interface font and size, code font and size, and the reading
measurements -- the same things the GTK client's appearance page has,
kept in this browser's cookies rather than in the fleet's own
configuration file.  A theme is about the screen you
are sitting at, not about the fleet, so it comes with you when this
server is pointed at a different daemon.

*** Three theme states, and only two of them are written down

A theme is not a boolean, and the stylesheet is built for all three.

| State           | On the root element    | What decides the colours       |
|-----------------+------------------------+--------------------------------|
| follow the browser | *no attribute at all* | ~prefers-color-scheme~       |
| light           | ~data-theme="light"~   | the explicit choice            |
| dark            | ~data-theme="dark"~    | the explicit choice            |

Every colour is a token defined on bare ~:root~, redefined under
~@media (prefers-color-scheme: dark)~ guarded as
~:root:not([data-theme="light"])~, and redefined again under
~:root[data-theme="dark"]~.  Both halves are needed: the media query is
what makes "follow" work, and the attribute block is what lets an
explicit choice win *in both directions* -- without it, choosing light
on a machine set to dark would change nothing.

A colour whose only definition is inside a media query has no value at
all for a reader whose browser does not match it, which is why the bare
~:root~ block is the complete palette rather than the light half of one.

The attribute is set by an inline script in the page head, before the
body paints -- done after paint it is a visible flash of the wrong
palette on every navigation.  The script reads the cookie and sets
nothing when it says =system=, because "follow" is the *absence* of the
attribute rather than a third value of it.

A palette read from a file is the exception: it is given its *base*
mode -- ~dark~ or ~light~ -- rather than its own nick.  The stylesheet
has a rule for ~dark~ and none for ~inkwell~, so setting the nick would
leave every colour the palette does not define falling back to the light
defaults: light chrome under dark colours, which is worse than either.
The palette's own sheet is emitted into the page and still wins on the
colours it does define.

*** Empty means follow, and keeps following

An unset field emits *no rule at all*, rather than a rule naming what the
browser currently uses.  The two look identical on screen and diverge for
ever afterwards: one keeps following the system, the other has quietly
frozen.  The GTK client's appearance page was fixed for exactly this.

"Follow the browser for everything" clears every cookie rather than
storing empty strings, so "unset" stays the *absence* of a setting.

*** Reading

Column width -- a unit and an amount -- and the gap between runs.  Left
alone, the conversation takes nine tenths of the window.

| Unit                | Amount   | What it does                        |
|---------------------+----------+-------------------------------------|
| Share of the window | 20--100  | grows with the window               |
| Characters a line   | 20--240  | grows with the font                 |
| Pixels              | 320--1600 | neither; exact                     |
| Follow the shipped column | --  | nine tenths of the window           |

The two fields are stored as *one* self-describing cookie (~90%~,
~80ch~, ~640px~), through the library's own formatter.  Two cookies
would let them arrive apart, and a browser that kept the amount and
dropped the unit would read 640 as a percentage and clamp it to the
whole window -- a setting nobody chose, and no error anywhere.

They reach the page as ~--chat-measure~ and ~--chat-run-gap~, which the
transcript, the composer and the run spacing all read -- so the shipped
design and a reader's override are one mechanism rather than two.  The
unit survives into the declaration: a percentage stays a percentage so
the column keeps following the window, and a character count stays ~ch~
so it keeps following the font.

The units, their labels and their bounds all come from
~clawt_measure_unit_count()~ and friends rather than from a list written
in this client, for the reason the colour schemes already record: two
hand-written lists is how a value came to be offered by one client and
not the other, with ~make parity~ reporting OK throughout.  A cookie is
edited as easily as a config file, and a spelling this build cannot
place -- ~80em~, say -- falls back to the shipped column rather than
failing.

*** A font family is sanitised, not escaped

It comes out of a cookie, which is a string anybody can set to anything,
and it is spliced into a CSS declaration.  The filter is an allowlist --
letters, digits, space, hyphen, underscore, full stop, comma -- because
CSS string escapes are their own small language and there is nothing in a
font name to preserve.

A denylist was the first attempt and was already wrong: it stopped a
quote closing the string and let a comment-opener through, which swallows
the rest of the sheet.

** Connections

Which daemon this server talks to, from the profiles in
=$XDG_CONFIG_HOME/clawtilla/connections.yaml= -- the same 0600 file
=clawtilla-gtk= and =clawtilla remote add= use.

*** Starting on one

The daemon this process serves is chosen at start, and it does not have
to be a local one:

#+begin_src bash
# a saved profile
clawtilla-web --profile workstation

# or an address, with the token that daemon expects
clawtilla-web --host 100.72.0.41 --token "$(ssh box clawtilla daemon token)"
#+end_src

~--host~ beats ~--profile~, which beats the local socket, exactly as in
the CLI and the GTK client.  ~--daemon-port~ is the port on the *daemon*
and defaults to 8792; ~--port~ is the one this server listens on and is a
different number for a different thing, which is why they are spelled
apart.

Without these, ~clawtilla-web~ could only ever serve the daemon on the
machine it runs on -- and on a laptop that is nothing at all.  A machine
serving a fleet over a tailnet need have no fleet of its own.

Unlike the desktop client, this one *refuses to start* when it cannot
reach its daemon, and says why on stderr.  The difference is who is
listening: a person at a window can read a banner and pick another
machine, and nobody is looking at this one yet.  Serving a page that says
"not connected" to a browser that may never arrive is worse than
answering the person who just ran the command.

*** Whether a saved daemon is up

Each row has a *Check* button, before *Connect*, because that is the
question somebody has before deciding whether to press Connect.  It
probes that daemon and draws one of four verdicts --- ~reachable~ (with
the version and agent count), ~refused~, ~unreachable~, or nothing at all
until somebody asks.  The words and the rule behind them are the
library's, shared with the GTK client, in
[[file:clients.org::*Another machine's fleet][clients.org]].

One at a time, and only when asked.  Probing the list while rendering the
page would multiply that page's latency by the number of saved daemons
and stall on every sleeping one for its full timeout --- which is the
same reason the GTK client probes on a worker thread rather than on its
main loop.

*** When the connection to the daemon goes

A banner appears under the topbar on every page, saying the connection
is gone and that what is shown is from before it went; it disappears
when the daemon comes back.  The GTK client draws the same sentence in
the same place relative to its own header, from the same rule --
~clawt_web_app_connection_notice()~ and ~update_connection_banner()~
apply one precedence between them.

Here it is the *server's* connection to the daemon, not the browser's,
which is the honest reading of it: this process holds one client and
every browser is looking through it.  A browser whose own connection to
this server has gone sees the page stop updating instead, which is a
different thing and not something the server can report.

Making it appear and disappear costs the same round trip a fleet event
already does: the daemon's ~connected~ and ~disconnected~ push a ~fleet~
event to every open page, which re-renders.  Nothing renders the banner
from two places.

A reconnect that could not resume -- the daemon's replay buffer had
dropped events past this client's cursor -- pushes the same nudge and
*drops the unread counts*.  They were counted from a stream with a hole
in it, and a count nobody can trust is worse than none.

*** Which version the daemon is

Asked once at connect with ~control.status~ and compared with this
build's own.  A mismatch is drawn in the same banner, saying which way
round it is: a newer daemon may offer things this client cannot ask for,
an older one may refuse something it sends, and the two need different
machines updated.  A version that cannot be read says nothing at all.

*** One connection, many browsers

This is the one place the web client differs in kind rather than in
mechanism.  The GTK client switches one window; here there is a single
=ClawtClient= behind however many browsers are looking, so switching
moves all of them.  The page says so before it asks, and the confirmation
repeats it.

The new client is connected *before* the old one is dropped: a daemon on
another machine that is not running is the ordinary case, and releasing
the working connection first would leave every open page connected to
nothing because of a typo in a port.

Afterwards every page is sent to the fleet index rather than left where
it was.  Agent ids, room ids and message ids are all per-daemon, so a
page still showing the previous fleet is showing another machine's.

** Live updates

One SSE stream per open page, at =/events=.  What goes down it is a name
and a subject, never the change itself -- a browser told "the fleet
changed" re-fetches the fragments it is showing, which against a daemon
on the same machine is one cheap round trip.  An event carrying the row
would mean this client rendering the same row two ways, once from a reply
and once from an event, and the two disagreeing the first time either
changed.

Every daemon event is also republished under the name ~fleet~, and that
is what the pages listen for.  Two reasons: the daemon's own kinds are
dotted (~mailbox.queued~, ~agent.changed~) and a dot in an ~hx-trigger~
is a class selector; and a client that enumerated them would quietly stop
updating for whichever kind was added last.

A comment goes down every idle stream twice a minute.  A quiet fleet can
go hours without an event, and anything in between -- a proxy, a NAT
holding a mapping -- times an idle connection out without saying so.

** Without JavaScript

Every action is a real form or a real link.  With scripting off the whole
client still works: each action posts and the page re-renders.  htmx is
what makes it feel live rather than what makes it work.

*** The colour schemes are the library's list, not this client's

Both clients build the scheme control by walking
~clawt_appearance_scheme_count()~ / ~_nth_nick()~ / ~_nth_label()~, so a
scheme appears in each without either being edited -- including a
palette dropped into ~$XDG_CONFIG_HOME/clawtilla/palettes/~, which
needs no code change at all.

That list is keyed by *nick* rather than by ~ClawtTheme~ because a
palette read from a file has no enum value. The nick was already what
the appearance file and this client's cookie stored, so nothing about
how a choice is remembered had to change.

A file palette's own stylesheet is emitted into the page, and the root
element is given the palette's *base* mode rather than its nick: the
stylesheet has a rule for ~dark~ and none for ~inkwell~, so setting the
nick would leave every colour the palette does not define falling back
to the light defaults -- light chrome under dark colours, which is
worse than either.

That is not tidiness.  Each client used to name the schemes itself, and
when Catppuccin Mocha was added only the GTK combo grew a fourth entry --
the palette was in the shared library, and a web reader could not select
it.  ~make parity~ saw nothing, because a colour scheme sends no IPC
frame and is no slash command.

The colours are shared; the mechanism cannot be.  In GTK the palette
redefines libadwaita's named colours; here the sheet is ours, so the same
Mocha values land on our own tokens in a
~:root[data-theme="catppuccin-mocha"]~ block.  That block sits *after*
the two dark blocks deliberately: a palette carries ~data-theme~ too, so
~:root:not([data-theme="light"])~ matches it as well, the specificity is
identical, and source order is the only thing that settles it.

What the form posts is round-tripped through
~clawt_appearance_theme_from_nick()~ before it reaches the cookie, so
only a nick the library knows is ever stored and anything else becomes
=system=.

*** Saying that something arrived while you were reading

When the reader has scrolled up, an arrival does not move the view --
and now it says so, with the same pair the GTK client uses: a rule in the
transcript where reading stopped, and a pill offering to go to the
newest message.  Both appear only when something actually arrived, never
merely because the reader scrolled up.

The state is the browser's scroll position rather than anything the
daemon holds, so it lives in an inline script in the page head -- inline
for the same reason the theme script is, and htmx is swapping the whole
transcript on every fleet event, so "what is new" is *counted* rather
than diffed: the number of messages before the swap is where the rule
goes after it.

Three things that had to be got right, each of which looked correct and
was not until it was run in a browser:

- The listeners are on ~document~, not ~document.body~.  The script runs
  in the head, where ~document.body~ is still ~null~ -- the first
  ~addEventListener~ threw and took every handler with it.
- The scroll position is restored after the swap.  The swap replaces the
  whole element, so the browser has nothing to restore from and a reader
  who had scrolled up was thrown to the top of the conversation on every
  fleet event, which is the opposite of what refusing to auto-scroll is
  for.
- The scroll listener is delegated, in the capture phase.  ~scroll~ does
  not bubble, and the transcript element is replaced on every arrival, so
  one bound directly to it survives exactly until the moment it is
  needed.

*** Ordering and teams are controls, not gestures

The GTK sidebar drags a row to reorder the fleet and drags it onto a team
heading to change its team.  Here both are buttons: *Move up* / *Move
down*, and a *Team* select with a *Move* beside it, shown under the agent
somebody is looking at so the sidebar stays a list of agents rather than
a list of controls.

Dragging is not the parity gap it looks like.  It needs JavaScript to be
worth anything, and this page has to work without it; the two write the
same ~agents.order~ and ~agents.team~, so an agent moved in either client
has moved in the other.

The sidebar also draws a heading for every team the fleet declares,
including one nobody is on yet -- a team created in Settings and then
nowhere in the sidebar reads as a team that was not created, and filling
it is the next thing somebody meant to do.  Teamless agents come first,
unlabelled, as they always have here.

*** The scripts are vendored

=data/web/htmx.min.js= and =data/web/htmx-ext-sse.js= are checked in and
served from the binary's own directory.  Never a CDN, for three reasons
in order of how much they matter: a fleet console must work without the
public internet, which is the whole point of binding the tailnet; a CDN
script that can change what runs on this page can change what runs on
every agent; and a build that reaches the network can produce different
output tomorrow.

They are found beside the binary first and in =$PREFIX/share/clawtilla=
second, so a fresh clone works before the first ~make install~.  When
neither has them the page still loads and says what is missing, naming
all three places it looked.

** Parity with the GTK client

The two answer for the same daemon, so they should reach the same parts
of it.  Two clients drifting apart is invisible -- nothing breaks,
nothing warns, and somebody finds out by reaching for the half that was
not built.

#+begin_src bash
make parity
#+end_src

#+begin_example
client parity: OK (81 kinds and 19 commands in gtk, 85 kinds and 27 commands in web;
4 enumeration(s), 2 vocabulary(ies), 40 affordance(s))
#+end_example

Layer one is the set of IPC frame kinds each client sends.  That is a
proxy for "feature" rather than a definition of one -- a client could
name a kind and do nothing useful with it -- but every real feature has
to talk to the daemon to do anything, so a kind one client sends and the
other never mentions is a capability that exists in one place only.  The
kinds themselves are read out of =src/core/clawt-daemon.c=, so one added
there is compared from the moment it exists, and each client's set is
intersected with it -- a client source is full of dotted strings that
are not frame kinds.

It runs from ~make parity~, from ~make docs-check~, and as a case in
~make test~.  A check that only runs in one target is one somebody can go
a long time without seeing.

*** Five layers are compared

| Layer | What it compares | Needs declaring |
|-------+------------------+-----------------|
| 1 | IPC frame kinds each client sends | no |
| 2 | slash commands each answers | no |
| 3 | library choice enumerations each walks | no |
| 4 | library vocabulary values either spells out | no |
| 5 | declared interface affordances | *yes* |

The command check exists because the frame-kind one missed them entirely:
thirteen of the eighteen then shipped were absent from the web client and
nothing said
so, since =/files=, =/agents= and =/export= are all built out of frames
both clients already sent.  A check that only looks at one layer will
keep finding nothing at the others.

*The =27 commands in web= in that line is not a command count.*  Layer
two greps each client for ~"/name"~ string literals, which is enough to
compare without either client declaring anything -- and in the web
client it also matches route paths and hrefs, so =/fleet=, =/settings=,
=/alerts=, =/events=, =/decisions=, =/design=, =/import= and =/static=
are counted alongside the real ones.  Both composers answer the same
nineteen; the eight extra are pages.

That over-count is harmless rather than fixed, and deliberately so.
Commands are compared *one way* -- a command the GTK composer answers
and the web one does not is a build failure, and the web client
answering something extra is a thing to notice by reading.  Anything the
grep adds to the web side therefore cannot produce a false failure.
Narrowing the pattern to the composer's own table would mean each client
declaring its commands for this script's benefit, which is the property
layers one to four exist to avoid.

Layers 3 to 5 exist because that sentence came true a second time.
Catppuccin Mocha went into libclawt, which both clients link, and was
selectable in one of them; the unread marker was built for the GTK
transcript and not the web one.  Neither sends a frame or answers a slash
command.

- *Layer 3* is the sharp one.  A ~_count()~/~_nth()~ pair in the public
  API is the library saying "here is a set, walk it", so if either client
  walks one, both must.  That is the Mocha shape exactly, and it needs
  nobody to declare anything.
- *Layer 4* catches the cause rather than the symptom.  A client that
  spells out a value the library enumerates is holding a copy of the
  list, and a copy is what drifts.  The values are read from the
  library's own table, so a palette added there is checked from the
  moment it exists -- the check fires on the copy whether or not the new
  value is missing from it yet.
- *Layer 5* is for the capabilities that are pure interface -- the unread
  marker is a rule and a pill, and touches no shared symbol.  Each is a
  row naming a marker per client.  It is honest about its limit: it
  catches one half being removed or never written, and cannot catch a
  feature nobody declared.

Two things learned building it, both of which made the check report the
opposite of the truth:

- It greps the sources with the comments stripped.  This codebase
  explains itself, so the comment saying why the stylesheet must spell
  =data-theme="light"= contains "light", and the one about the fallback
  contains "system" -- grepping the prose reported two hardcodings that
  were not there.  A check that cries wolf is one people learn to ignore.
- The stripped text goes to a file and is grepped there, never piped into
  ~grep -q~.  Under ~set -o pipefail~ that pipeline reports *failure on
  success*: grep exits the moment it matches, the upstream ~awk~ dies of
  SIGPIPE with 141, and the pipeline takes the worst status.  Every
  marker that was present reported missing.

*** Adding a feature

Build it in both.  If it sends a frame, answers a command, or walks a
~_count()~/~_nth()~ family, there is nothing to declare -- layers one to
four find it on their own.

If it is pure interface -- no frame, no command, no shared symbol -- add
a row to ~AFFORDANCES~ naming a marker per client:

#+begin_src bash
declare -A AFFORDANCES=(
    ["unread marker"]="unread_marker|unread-rule"
)
#+end_src

The key is the capability in words; the value is the GTK marker, a pipe,
and the web marker.  A marker must be something the feature *cannot work
without* -- a function name, a CSS class, a constant -- and never a
label somebody might reword, because then the check fails on a wording
change and passes when the feature is gone.  The two halves are usually
different spellings of the same idea (~adw_avatar_new~ against
~msg-avatar~); where the rule itself lives in libclawt they are the same
symbol on both sides, which is the strongest form the row can take.

Markers are matched against each client's sources with the comments
stripped, so a marker that also appears in prose is still safe.  Verify
a new row by *removing* the feature from one client and watching the
check fail -- a parity row that has never been shown to fail is a row
that reports OK.

When building it in both is genuinely not the right answer, add the
kind to the exception map at the top of
=tools/clawt-client-parity.sh= with the reason:

#+begin_src bash
declare -A GTK_MAY_LACK=(
    ["exchange.list"]="the GTK client offers drag-and-drop into the exchange rather than a listing"
)
#+end_src

An entry there is a decision, not a to-do.  Anything without a reason
somebody would agree with belongs in the client instead.

** Checking it by hand

=make test= covers the renderers; it cannot cover routing.  A route
registered after ~/a/:id/:view~ is unreachable, and the symptom is not an
error -- an unrecognised view falls back to chat, so a swallowed route
renders the chat page and answers =200=.  That is exactly how
=/a/x/export=, =/a/x/copy= and =/a/x/file= were all quietly serving the
chat page.

#+begin_src bash
make web-smoke WEB_SMOKE_URL=http://127.0.0.1:8790 WEB_SMOKE_AGENT=chief
#+end_src

It asks a running client for every page and checks the *content*, not the
status: a marker string per route, the =Content-Disposition= on each
download, and the daemon's own words on a refusal.

** Escaping

Every element is built with htmx-glib's typed classes -- ~HtmxDiv~,
~HtmxSpan~, ~htmx_node_set_text_content()~ -- rather than by appending to
a string.  That is htmx-glib's own house style, and here it is also the
security property: agent names, descriptions and message bodies were
written by a person or a model, and this client serves them back over
HTTP.

=tests/test-web-render.c= asserts it on the rendered markup rather than
on the code that produces it.  "We call the escaping function" is a claim
about the source; "no ~<~ reached the page" is a claim about what a
browser would receive.

*** The one place markup is set rather than escaped

Every element on every other page is built from htmx-glib's typed
classes, which escape.  A message body is the exception, and it is one
because rendering markdown *is* producing markup: there is no
typed-element route to bold text that an agent asked for.  ~set_body()~
in ~web-chat.c~ is the single call --- ~htmx_node_set_html_content()~ ---
and it is the line to look at first if anything ever goes wrong here.

What makes it safe is that the markup is not the agent's.
~clawt_markdown_to_html()~ emits tags only for the structure cmark
identified and puts every literal through ~g_markup_escape_text()~ on
the way out, so the parser never sees a character an agent wrote.  A
reply containing =<script>= --- a thing an agent can be talked into
writing --- arrives as those characters on the page.

It emits no =<a href>=, no =<img src>= and no =style= attribute.  The
link rule is the GTK client's and matters more in a browser: a
clickable link in model output is one keystroke between a prompt
injection and somewhere else, so the target is printed beside the text
instead.  A useful consequence is that no URL a model wrote is ever
parsed as one, so =javascript:= and =data:= are text like everything
else rather than a scheme to be filtered --- there is no filter to get
wrong.

~tests/test-markdown.c~ asserts it as an *allowlist* rather than by
hunting for =<script=: since a literal =<= from an agent is escaped
before it is emitted, every =<= that survives opens a tag the renderer
chose, so checking each one against the twenty-five it can emit checks
the whole property.  Attributes get the same treatment --- =class= with
one of five values and =start= with a number are the only two it can
produce, so an =href=, a =src=, a =style= or an =on*= reaching the page
fails whatever it is called.

That distinction cost a test its first draft.  Asserting that =src==
never appears anywhere fails on output that is exactly right, because
=&lt;img src=x&gt;= is the correct escaped rendering of what an agent
typed.  The property is not "this text is absent from the page", it is
"this text is not inside a tag" --- which is the difference between a
denylist and naming the safe set.

*** The stylesheet carries the blocks

~.msg-body~ lost its =white-space: pre-wrap= when the body stopped being
plain text.  A body was text with real newlines in it until the renderer
arrived; pre-wrap over block markup shows the newline between every pair
of tags as a blank line, so the markup's own formatting would become
visible gaps down the transcript.  The line breaks somebody typed
survive as =<br>=, which is what the renderer emits for them.  The
absence is asserted in ~tests/test-web-render.c~, because the rule would
otherwise still be there and still look right.

Every block the renderer can emit is styled, and that is checked rather
than remembered: a construct with no rule does not fail to render, it
renders in the browser's default --- a serif blockquote with no rule
beside it, a table with no borders --- which reads as the page being
broken rather than as a missing line of CSS.

Two things were found only by measuring the rendered page in a browser,
and neither is visible in the markup:

- *A message's table header was the fleet table's chrome.*  The bare
  =th= selector styles a column heading in the page furniture ---
  uppercase, letter-spaced, 11px, muted --- and it reaches into a
  message as well, so an agent writing =| Team |= got TEAM in the tone
  the page uses for labels.  Measured at 4.14:1 against its own
  background, which is the giveaway: nothing in a message should be
  quieter than the message.  It inherits the body now, which also
  carries it into the operator's bubble where the colour is not the
  page's at all.  17.47:1 after.

- *The header tint made the bubble's boldest row its least readable.*
  A tint separates a header from its body on the page; over the accent
  it lightens the ground under the one row drawn in bold, and that row
  measured 3.94:1 against 5.67 for every other line in the same bubble.
  A firmer rule under the row separates it for nothing.  5.67:1 after,
  in both schemes.

A table scrolls inside its own box, which was measured too rather than
assumed: a table whose header cells cannot shrink laid out at 692px
inside a 390px message, scrolled within the wrapper, and the page did
not scroll sideways.  That is the whole reason this client needs
neither the width threshold nor the record layout the GTK one does.

Every colour is an existing token, so a colour scheme recolours a
rendered message with everything else.

*** Every text colour clears WCAG AA

Measuring the rendered page for the table header turned up a second
number: =.md-url= was 4.32:1 in light, under AA's 4.5 for text.  It
uses =--muted=, and so does every timestamp, day divider and =.muted=
span in the client --- so the fault was the token's rather than this
feature's, and giving the URL a colour of its own would have made a
link's target louder than the message's own metadata while leaving
everything else where it was.

So the token moved.  =--muted= went from =#787774= to =#6E6D6B=, eight
percent darker along the same warm grey: 4.99 on the canvas, 5.17 on a
surface and 4.78 on =--surface-2=, all with room, and still the
lightest text token so nothing about the hierarchy under =--ink= and
=--ink-2= changed.  Confirmed in a browser at 4.99:1 rather than only
on paper.

An audit of all four palettes --- light, the two dark blocks and
Catppuccin --- against all three grounds, plus every semantic
foreground on its own tint and bare, found that one value and nothing
else.  The GTK palette in ~clawt-appearance.c~ was clean throughout,
its worst pair 6.31:1.

Both are checked now rather than remembered.
~tests/test-web-render.c~ parses the palettes out of the stylesheet and
~tests/test-appearance.c~ parses the =@define-color= pairs, and each
fails naming the palette, the token, both colours and the ratio.  A
palette added later cannot ship under the line quietly, which is what
this one did.

Two things that check cannot do, said plainly.  It reads the palettes
clawtilla ships, so stock GNOME's colours --- which are libadwaita's
and not in this tree --- are outside it.  And it compares tokens rather
than rendered pixels, so a colour composited over another, such as the
white tint on the operator's bubble, is not among them; that one was
measured in the browser instead.

The web check passed on its first run for the wrong reason, which is
worth recording.  It bounded each palette block at the ="}= sequence
that separates two adjacent C string literals in ~web-style.c~ --- and
by the time ~clawt_web_stylesheet()~ returns, the quotes are gone and
there is no such pair.  The scan ran to the end of the sheet, a later
definition replaced an earlier one in the hash table, and all four
palettes reported Catppuccin's colours: four dark schemes, nothing
under the line, a green check.  **A test written against the shape of
the code rather than the shape of its output.**  It compares the ground
each block reports against the light one's now, so a scan that reads
past its own block fails on that instead.

** Troubleshooting

*** The page loads but nothing updates by itself

The scripts are missing.  Check the startup output: it names every
directory it looked in.  Running out of a checkout they are in
=data/web=; after ~make install~ they are in
=$PREFIX/share/clawtilla/web=.  =CLAWT_WEB_STATIC_DIR= overrides both.

Everything still works without them -- each action posts and the page
re-renders -- so this looks like a slow client rather than a broken one.

*** It is not reachable from the tailnet

#+begin_src bash
ss -ltn | grep 8790
#+end_src

If only =127.0.0.1= is bound, either there is no tailnet address on this
machine (Tailscale in userspace-networking mode has none, correctly:
there is no address to bind either), or the bind failed and said so.

*** It cannot reach the daemon

#+begin_src bash
clawtilla-web --socket "$XDG_RUNTIME_DIR/clawtilla/daemon.sock"
#+end_src

The sidebar says "The daemon is not answering" with the reason, rather
than drawing an empty fleet -- a fleet with no agents in it is a
different problem with a different fix.
