* The web client

~clawtilla-web~ serves everything ~clawtilla-gtk~ does, over HTTP, from
the same daemon over the same socket.  A laptop on the tailnet reaches
the fleet on a workstation without a tunnel set up by hand, and without
GTK installed on either end.

#+begin_src bash
clawtilla-web
#+end_src

#+begin_example
clawtilla-web is listening on:
  http://127.0.0.1:8790/
  http://100.84.12.7:8790/

There is no login here: anything that can reach a listed
address can drive the whole fleet.
#+end_example

** Its own binary, on purpose

Not a mode of ~clawtillad~.  This page can start, stop, reconfigure and
delete every agent on the machine, and run commands inside their
computers.  A surface like that should exist because somebody decided
they wanted it, not because the daemon happened to start.

** Where it listens

The loopback, and this machine's tailnet address when there is one.

A tailnet is the one network where listening past the loopback is
defensible without a login of our own: every peer is a device the user
enrolled and WireGuard authenticated, and nothing off the tailnet can
route to a =100.64/10= address at all.  ~clawtillad~ binds its own
convenience listener on exactly that reasoning.

The address is found with ~getifaddrs()~ rather than by running
=tailscale ip=, and both the interface name and the address range are
checked -- =utun= is any tunnel on a BSD, and a container can hold a
=100.64/10= address for reasons of its own.

*** A machine with no tailnet gets the loopback alone

It does not fall back to every interface.  Widening the audience because
an address was missing is the opposite of what somebody would want, and
this client has no authentication to make that safe.

*** Naming an address yourself

#+begin_src bash
# This machine only
clawtilla-web --no-tailscale

# Somewhere else, on another port
clawtilla-web --bind 192.168.1.10 --port 9000

# Two addresses
clawtilla-web --bind 127.0.0.1 --bind 10.0.0.4
#+end_src

Using ~--bind~ at all replaces the defaults, so the tailnet address is
not quietly added to whatever was named.

An address a person named is never optional: failing to bind it exits
non-zero, because a client that ignored where it was told to listen and
started anyway is running somewhere nobody knows about.  The tailnet
address -- which clawtilla chose, not the person -- is a warning, and the
loopback still comes up.

*** What it reports is what it bound

The startup banner is built from the addresses the server is actually
listening on, not from the ones it was asked for.  A convenience address
whose bind failed is exactly the interesting case, and announcing the
request would say it was reachable there.

** It has no login

Anything that can reach a listed address drives the whole fleet.  On a
tailnet that is bounded by WireGuard.  Anywhere else, put it behind
something that can require a login.

There is deliberately no password flag: a password on the command line is
in the shell history and in the process table, and a real login for this
would need session handling, storage and a reset path -- which is a
reverse proxy's job, done properly, rather than ours done badly.

** The views

The same seven the GTK client's view switcher has, in the same order.

| View     | What is on it                                              |
|----------+------------------------------------------------------------|
| Chat     | transcript, composer, slash commands, attachments          |
| Agent    | every setting, the workspace files, the memory store       |
| Mailbox  | what is waiting, what died, purge and requeue              |
| Computer | exec console, mounts, the exchange, rebuild                |
| Routines | scheduled work, and running one now                        |
| Tasks    | delegated work, the budget, cancelling                     |
| Flow     | what the agents are saying to each other                   |

And seven settings pages: VM images, teams, spending, integrations,
connectors, appearance and connections.

*** Slash commands

The same eighteen the GTK composer answers, typed into the message box.
Three mean something slightly different in a browser, and the help says
so rather than leaving anybody to find out.

| Command             | What it does                                        |
|---------------------+-----------------------------------------------------|
| =/help=             | list them                                           |
| =/start= =/stop= =/restart= | the agent's lifecycle                       |
| =/reset=            | start its AI session again, from nothing            |
| =/attach=           | send a file with the next message                   |
| =/compose=          | a full-page box, where GTK opens =$EDITOR=          |
| =/edit [file]=      | open a workspace file *in the page*                 |
| =/files=            | this agent's workspace files                        |
| =/memory <query>=   | search what it has remembered                       |
| =/agents=           | who is in the fleet                                 |
| =/flow= =/tasks=    | go to those views                                   |
| =/retry=            | send your last message again                        |
| =/export [org]=     | download the conversation                           |
| =/copy [org]=       | show it to copy, where GTK reaches the clipboard    |
| =/clear=            | hide the transcript *on screen only*                |
| =/new=              | create an agent                                     |

=/clear= sends nothing to the daemon.  The history is the daemon's, and a
command that tidied the view must not be one that destroyed it -- =/reset=
is the one that clears a session, and it says so.

=/export= and =/copy= go through =clawt_export_transcript()=, the same
function the GTK client uses, so the two produce the same bytes.  Three
formats: markdown, org, plain.

*** Editing workspace files

The GTK client opens them in =$EDITOR=, which is a program on the machine
somebody is sitting at.  A browser reached over the network has no such
thing, so the file comes over the wire: ~agent.file_read~ and
~agent.file_write~ exist for this and nothing else.

The name goes through ~clawt_workspace_file_path()~, which refuses
anything holding a separator or "..".  This is reached from an IPC
request, and a client that could name =../../secrets= would be reading
another agent's credentials.

*** The agent editor is built from the schema

Not from a list of rows.  ~agent.show~ reports every settable key with
this agent's value for it, walked from ~clawt_config_schema_get()~, and
the page renders a control per type.  An option added to the schema
appears here without anybody editing the client.

That is the same rule the daemon's integrations and its starter config
already follow, and for the same reason: a hand-written list of an
option's keys drifts silently, and the symptom is a setting that is
accepted, reported as saved, and then read from nowhere.

One key gets a control the schema cannot describe.  ~team~ is a plain
string there, so the generic path would draw a text box -- asking
somebody to know a team's id and to type it without a typo, when the
daemon can say what the ids are.  It is a select of the teams
~team.list~ reports, by name, which is the same control the GTK client's
agent editor has.  A team an agent names but the fleet does not declare
is *added to the list* rather than dropped, marked =(set by hand)=:
without that the control would open showing the first entry and saving
the page -- without touching that row -- would move the agent somewhere
nobody chose.

Nine keys are the exception, and the page says nothing about them because
it cannot: ~orchestration.mailbox.*~ and ~memories.*~ carry
=CLAWT_SCHEMA_FLAG_PER_AGENT=, and their spelling inside an agent block
lives in hand-written tables in =clawt-agent-manager.c= and
=clawt-config.c= rather than in the schema.  Guessing a name would
produce fields that are accepted and read from nowhere, which is the
failure the rule exists to prevent, arrived at from the other direction.

*** Only what changed is sent

Saving compares each field against what the daemon reported.  ~agent.set~
rewrites every agent's files on each call, so posting a hundred unchanged
keys would do that a hundred times for a form somebody opened and closed.

A permission changed under a running agent says so: an AI CLI lists its
tools once, when its session starts, so the change reaches the agent's
files and not its session.

** Appearance

Theme, interface font and size, code font and size -- the same four
things the GTK client's appearance page has, kept in this browser's
cookies rather than in the fleet's own configuration file.  A theme is about the screen you
are sitting at, not about the fleet, so it comes with you when this
server is pointed at a different daemon.

*** Empty means follow, and keeps following

An unset field emits *no rule at all*, rather than a rule naming what the
browser currently uses.  The two look identical on screen and diverge for
ever afterwards: one keeps following the system, the other has quietly
frozen.  The GTK client's appearance page was fixed for exactly this.

"Follow the browser for everything" clears all five cookies rather than
storing empty strings, so "unset" stays the *absence* of a setting.

*** A font family is sanitised, not escaped

It comes out of a cookie, which is a string anybody can set to anything,
and it is spliced into a CSS declaration.  The filter is an allowlist --
letters, digits, space, hyphen, underscore, full stop, comma -- because
CSS string escapes are their own small language and there is nothing in a
font name to preserve.

A denylist was the first attempt and was already wrong: it stopped a
quote closing the string and let a comment-opener through, which swallows
the rest of the sheet.

** Connections

Which daemon this server talks to, from the profiles in
=$XDG_CONFIG_HOME/clawtilla/connections.yaml= -- the same 0600 file
=clawtilla-gtk= and =clawtilla remote add= use.

*** One connection, many browsers

This is the one place the web client differs in kind rather than in
mechanism.  The GTK client switches one window; here there is a single
=ClawtClient= behind however many browsers are looking, so switching
moves all of them.  The page says so before it asks, and the confirmation
repeats it.

The new client is connected *before* the old one is dropped: a daemon on
another machine that is not running is the ordinary case, and releasing
the working connection first would leave every open page connected to
nothing because of a typo in a port.

Afterwards every page is sent to the fleet index rather than left where
it was.  Agent ids, room ids and message ids are all per-daemon, so a
page still showing the previous fleet is showing another machine's.

** Live updates

One SSE stream per open page, at =/events=.  What goes down it is a name
and a subject, never the change itself -- a browser told "the fleet
changed" re-fetches the fragments it is showing, which against a daemon
on the same machine is one cheap round trip.  An event carrying the row
would mean this client rendering the same row two ways, once from a reply
and once from an event, and the two disagreeing the first time either
changed.

Every daemon event is also republished under the name ~fleet~, and that
is what the pages listen for.  Two reasons: the daemon's own kinds are
dotted (~mailbox.queued~, ~agent.changed~) and a dot in an ~hx-trigger~
is a class selector; and a client that enumerated them would quietly stop
updating for whichever kind was added last.

A comment goes down every idle stream twice a minute.  A quiet fleet can
go hours without an event, and anything in between -- a proxy, a NAT
holding a mapping -- times an idle connection out without saying so.

** Without JavaScript

Every action is a real form or a real link.  With scripting off the whole
client still works: each action posts and the page re-renders.  htmx is
what makes it feel live rather than what makes it work.

*** The colour schemes are the library's list, not this client's

Both clients build the scheme control by walking
~clawt_appearance_theme_count()~ / ~_nth()~ / ~_label()~, so a palette
added to =clawt-appearance.c= appears in each without either being
edited.

That is not tidiness.  Each client used to name the schemes itself, and
when Catppuccin Mocha was added only the GTK combo grew a fourth entry --
the palette was in the shared library, and a web reader could not select
it.  ~make parity~ saw nothing, because a colour scheme sends no IPC
frame and is no slash command.

The colours are shared; the mechanism cannot be.  In GTK the palette
redefines libadwaita's named colours; here the sheet is ours, so the same
Mocha values land on our own tokens in a
~:root[data-theme="catppuccin-mocha"]~ block.  That block sits *after*
the two dark blocks deliberately: a palette carries ~data-theme~ too, so
~:root:not([data-theme="light"])~ matches it as well, the specificity is
identical, and source order is the only thing that settles it.

What the form posts is round-tripped through
~clawt_appearance_theme_from_nick()~ before it reaches the cookie, so
only a nick the library knows is ever stored and anything else becomes
=system=.

*** Saying that something arrived while you were reading

When the reader has scrolled up, an arrival does not move the view --
and now it says so, with the same pair the GTK client uses: a rule in the
transcript where reading stopped, and a pill offering to go to the
newest message.  Both appear only when something actually arrived, never
merely because the reader scrolled up.

The state is the browser's scroll position rather than anything the
daemon holds, so it lives in an inline script in the page head -- inline
for the same reason the theme script is, and htmx is swapping the whole
transcript on every fleet event, so "what is new" is *counted* rather
than diffed: the number of messages before the swap is where the rule
goes after it.

Three things that had to be got right, each of which looked correct and
was not until it was run in a browser:

- The listeners are on ~document~, not ~document.body~.  The script runs
  in the head, where ~document.body~ is still ~null~ -- the first
  ~addEventListener~ threw and took every handler with it.
- The scroll position is restored after the swap.  The swap replaces the
  whole element, so the browser has nothing to restore from and a reader
  who had scrolled up was thrown to the top of the conversation on every
  fleet event, which is the opposite of what refusing to auto-scroll is
  for.
- The scroll listener is delegated, in the capture phase.  ~scroll~ does
  not bubble, and the transcript element is replaced on every arrival, so
  one bound directly to it survives exactly until the moment it is
  needed.

*** Ordering and teams are controls, not gestures

The GTK sidebar drags a row to reorder the fleet and drags it onto a team
heading to change its team.  Here both are buttons: *Move up* / *Move
down*, and a *Team* select with a *Move* beside it, shown under the agent
somebody is looking at so the sidebar stays a list of agents rather than
a list of controls.

Dragging is not the parity gap it looks like.  It needs JavaScript to be
worth anything, and this page has to work without it; the two write the
same ~agents.order~ and ~agents.team~, so an agent moved in either client
has moved in the other.

The sidebar also draws a heading for every team the fleet declares,
including one nobody is on yet -- a team created in Settings and then
nowhere in the sidebar reads as a team that was not created, and filling
it is the next thing somebody meant to do.  Teamless agents come first,
unlabelled, as they always have here.

*** The scripts are vendored

=data/web/htmx.min.js= and =data/web/htmx-ext-sse.js= are checked in and
served from the binary's own directory.  Never a CDN, for three reasons
in order of how much they matter: a fleet console must work without the
public internet, which is the whole point of binding the tailnet; a CDN
script that can change what runs on this page can change what runs on
every agent; and a build that reaches the network can produce different
output tomorrow.

They are found beside the binary first and in =$PREFIX/share/clawtilla=
second, so a fresh clone works before the first ~make install~.  When
neither has them the page still loads and says what is missing, naming
all three places it looked.

** Parity with the GTK client

The two answer for the same daemon, so they should reach the same parts
of it.  Two clients drifting apart is invisible -- nothing breaks,
nothing warns, and somebody finds out by reaching for the half that was
not built.

#+begin_src bash
make parity
#+end_src

#+begin_example
client parity: OK (68 kinds in gtk, 70 in web)
#+end_example

What is compared is the set of IPC frame kinds each client sends.  That
is a proxy for "feature" rather than a definition of one -- a client
could name a kind and do nothing useful with it -- but every real feature
has to talk to the daemon to do anything, so a kind one client sends and
the other never mentions is a capability that exists in one place only.

It runs from ~make parity~, from ~make docs-check~, and as a case in
~make test~.  A check that only runs in one target is one somebody can go
a long time without seeing.

*** Five layers are compared

| Layer | What it compares | Needs declaring |
|-------+------------------+-----------------|
| 1 | IPC frame kinds each client sends | no |
| 2 | slash commands each answers | no |
| 3 | library choice enumerations each walks | no |
| 4 | library vocabulary values either spells out | no |
| 5 | declared interface affordances | *yes* |

The command check exists because the frame-kind one missed them entirely:
thirteen of the eighteen were absent from the web client and nothing said
so, since =/files=, =/agents= and =/export= are all built out of frames
both clients already sent.  A check that only looks at one layer will
keep finding nothing at the others.

Layers 3 to 5 exist because that sentence came true a second time.
Catppuccin Mocha went into libclawt, which both clients link, and was
selectable in one of them; the unread marker was built for the GTK
transcript and not the web one.  Neither sends a frame or answers a slash
command.

- *Layer 3* is the sharp one.  A ~_count()~/~_nth()~ pair in the public
  API is the library saying "here is a set, walk it", so if either client
  walks one, both must.  That is the Mocha shape exactly, and it needs
  nobody to declare anything.
- *Layer 4* catches the cause rather than the symptom.  A client that
  spells out a value the library enumerates is holding a copy of the
  list, and a copy is what drifts.  The values are read from the
  library's own table, so a palette added there is checked from the
  moment it exists -- the check fires on the copy whether or not the new
  value is missing from it yet.
- *Layer 5* is for the capabilities that are pure interface -- the unread
  marker is a rule and a pill, and touches no shared symbol.  Each is a
  row naming a marker per client.  It is honest about its limit: it
  catches one half being removed or never written, and cannot catch a
  feature nobody declared.

Two things learned building it, both of which made the check report the
opposite of the truth:

- It greps the sources with the comments stripped.  This codebase
  explains itself, so the comment saying why the stylesheet must spell
  =data-theme="light"= contains "light", and the one about the fallback
  contains "system" -- grepping the prose reported two hardcodings that
  were not there.  A check that cries wolf is one people learn to ignore.
- The stripped text goes to a file and is grepped there, never piped into
  ~grep -q~.  Under ~set -o pipefail~ that pipeline reports *failure on
  success*: grep exits the moment it matches, the upstream ~awk~ dies of
  SIGPIPE with 141, and the pipeline takes the worst status.  Every
  marker that was present reported missing.

*** Adding a feature

Build it in both.  If it is pure interface -- something with no frame, no
command and no shared symbol -- add a row to ~AFFORDANCES~ naming a
marker in each client, so its removal from either is a build failure.

When building it in both is genuinely not the right answer, add the
kind to the exception map at the top of
=tools/clawt-client-parity.sh= with the reason:

#+begin_src bash
declare -A GTK_MAY_LACK=(
    ["exchange.list"]="the GTK client offers drag-and-drop into the exchange rather than a listing"
)
#+end_src

An entry there is a decision, not a to-do.  Anything without a reason
somebody would agree with belongs in the client instead.

** Checking it by hand

=make test= covers the renderers; it cannot cover routing.  A route
registered after ~/a/:id/:view~ is unreachable, and the symptom is not an
error -- an unrecognised view falls back to chat, so a swallowed route
renders the chat page and answers =200=.  That is exactly how
=/a/x/export=, =/a/x/copy= and =/a/x/file= were all quietly serving the
chat page.

#+begin_src bash
make web-smoke WEB_SMOKE_URL=http://127.0.0.1:8790 WEB_SMOKE_AGENT=chief
#+end_src

It asks a running client for every page and checks the *content*, not the
status: a marker string per route, the =Content-Disposition= on each
download, and the daemon's own words on a refusal.

** Escaping

Every element is built with htmx-glib's typed classes -- ~HtmxDiv~,
~HtmxSpan~, ~htmx_node_set_text_content()~ -- rather than by appending to
a string.  That is htmx-glib's own house style, and here it is also the
security property: agent names, descriptions and message bodies were
written by a person or a model, and this client serves them back over
HTTP.

=tests/test-web-render.c= asserts it on the rendered markup rather than
on the code that produces it.  "We call the escaping function" is a claim
about the source; "no ~<~ reached the page" is a claim about what a
browser would receive.

** Troubleshooting

*** The page loads but nothing updates by itself

The scripts are missing.  Check the startup output: it names every
directory it looked in.  Running out of a checkout they are in
=data/web=; after ~make install~ they are in
=$PREFIX/share/clawtilla/web=.  =CLAWT_WEB_STATIC_DIR= overrides both.

Everything still works without them -- each action posts and the page
re-renders -- so this looks like a slow client rather than a broken one.

*** It is not reachable from the tailnet

#+begin_src bash
ss -ltn | grep 8790
#+end_src

If only =127.0.0.1= is bound, either there is no tailnet address on this
machine (Tailscale in userspace-networking mode has none, correctly:
there is no address to bind either), or the bind failed and said so.

*** It cannot reach the daemon

#+begin_src bash
clawtilla-web --socket "$XDG_RUNTIME_DIR/clawtilla/daemon.sock"
#+end_src

The sidebar says "The daemon is not answering" with the reason, rather
than drawing an empty fleet -- a fleet with no agents in it is a
different problem with a different fix.
