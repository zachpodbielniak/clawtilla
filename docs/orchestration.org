* Orchestration

** Rooms

Agents are managed as chats, so a room is the only mechanism: a direct
exchange between two agents is a room with two members, and a standup is a
room with five.  There is no separate "DM" code path to keep in step.

#+begin_src yaml
rooms:
  - id: standup
    name: "Standup"
    members: [chief-of-staff, researcher, writer]
    require_mention: false
#+end_src

~rooms.max_hops~ overrides ~orchestration.max_hops~ for messages landing
in that room, and it may *loosen* the fleet limit as well as tighten it.
That is deliberate and is the case the key exists for: in a conversation
three agents each reply one hop deeper, so an ordinary standup reaches
the fleet ceiling on its own, and the only other remedy is raising the
fleet value for every delegation chain to fix one room.

It is not an escalation.  ~rooms:~ is the same file set by the same
hand, and the room value reaches the hop count and nothing else -- the
rate limit, the task budget and the cycle detector are untouched, so a
loop that costs money still has three limits on it.

For a long time it was parsed, stored, and read by nothing, so a
per-room ceiling was accepted and never applied.

Posting into a room appends to its transcript and enqueues into every
member's mailbox except the sender's.

~require_mention: true~ means an agent only receives messages that name
it -- worth having in a busy room, so five agents do not each take a turn
on every remark.

Transcripts persist to ~<state_dir>/transcripts/<room>.ndjson~, written
on every message rather than at shutdown.  A daemon that is killed rather
than stopped is the ordinary case for a service, and a transcript that
only survives a clean exit is not a transcript.

Removing a room leaves its transcript on disk.  Removing a room from the
fleet is a configuration change; destroying the record of what was said
in it is not, and is not recoverable.

*** Direct rooms, and where a reply goes

A message addressed to an agent rather than a room goes into the direct
room between the two, named ~dm:<a>:<b>~ with the pair sorted so that
"a to b" and "b to a" are the same room.  That is what makes a reply
land in the conversation it answers instead of starting a parallel one:
the room travels out to the agent with the message, libreclaw builds its
reply against the same room, and it comes back into it.

So a conversation between two agents is between those two agents, and
does not appear in your own chat with either of them.  You read it on
the GTK client's Flow tab, or with ~clawtilla room history dm:a:b~.

These rooms are made on demand and nothing in the config names them, so
the daemon scans the transcript directory at start and re-creates the
ones that have a file.  Without that, every conversation the fleet had
ever had was missing from a listing after a restart until the same two
agents happened to speak again -- the transcripts were there, nothing
had asked for them.

** Tasks

A task is a delegated unit of work with an origin, an assignee, a prompt,
a state and a result.

#+begin_src bash
clawtilla task list
clawtilla task show task-01m0k5…
clawtilla task cancel task-01m0k5…
#+end_src

States: ~pending~ → ~running~ → ~completed~ / ~failed~ / ~cancelled~ /
~stalled~.  There is no ~orphaned~ state: stopping an agent moves its
tasks to ~failed~ with the reason "the agent handling this stopped before
finishing", rather than leaving them assigned to nobody and looking like
work in progress for ever.

Both clients colour the badge from ~clawt_task_state_tone()~ ---
~completed~ green, ~failed~ and ~cancelled~ red, ~stalled~ amber,
~running~ blue, ~pending~ grey.  It is in the library rather than in each
client because the two got it wrong in different ways: the web client
compared the state against ~done~ and ~complete~, neither of which is a
state, so a finished task was never once drawn green; the GTK client drew
every badge the same grey whatever the state.  A colour that is merely
wrong reads as somebody's design choice, so neither was reported.

*~running~ means the assignee has started a turn on it.*  Not that the
task was created, and not that the message reached a mailbox -- a stopped
agent has a full mailbox and does nothing.  The moment is
~clawt_agent_begin_turn()~, which is the first point at which anybody
knows, and every path reaches it the same way.

That was not always true.  ~clawtilla_delegate~ marked nothing started,
so work an agent handed out read ~pending~ from creation until it went
straight to ~completed~, and ~clawtilla_task_list~ carried a paragraph
apologising for the column.  A chief reading ~pending~ as "nobody picked
it up" delegates the work a second time, and then there are two of it.

Tasks are held in memory only.  A daemon restart loses the list; what the
work produced is in the room transcript and the event log.

**** A task knows what it came out of

Every task records a ~parent_id~ and a depth.  A chief's task that
reaches a lead who fans out to two specialists is three levels deep and
says so, which is what makes two other things work at all:

- ~orchestration.max_hops~ bounds the *chain of delegations* as well as
  the chain of messages.  ~clawt_task_manager_create()~ measures depth
  from the parent and refuses past the ceiling, with a sentence that says
  to do the work rather than hand it on again.
- ~clawtilla_task_cancel~ takes the whole subtree, which is what its own
  description promises.

Neither worked before, and neither said so.  ~clawtilla_delegate~ passed
no parent, so every task an agent created was a root: the depth limit
compared 0 against the ceiling however long the real chain was, and the
cancel walk -- which matches on ~parent_id~ -- found no children and
cancelled exactly one task while the fan-out under it carried on
reporting into something nobody was waiting for.  Both were correct code
that nothing had wired up, and this page recorded the second as intended
behaviour.

The parent comes from the delegating agent's own turn:
~clawt_agent_get_turn_task_id()~ says which task the running turn is
answering, set per delivery beside the hop depth and the turn origin.
Per delivery, because libreclaw runs one turn per message -- a burst of
[task delivery, ordinary message] must not hang the second turn's work
off the first turn's task.  It is checked against the task manager rather
than trusted: a finished or forgotten id parents nothing, since a closed
task acquiring children is a tree nobody can read.

**** A turn ending is not the work finishing

An AI CLI cannot end a turn without writing something, so the daemon
takes the last thing an assignee wrote in a task's thread as that task's
result.  That inference is right for the ordinary shape -- do the work,
answer, done -- and wrong for the assignee that does the sensible thing:
finish its own share, hand the rest on, schedule a wakeup, and report
once at the end rather than narrating.

Such a turn ends with a status note and the task used to close under it.
On a real fleet the stored result said, in so many words, that the
consolidated report had not been sent yet; the delegator, holding a
terminal state, stopped polling, and the real answer arrived against a
task nothing was waiting on.  The lifecycle rewarded chatter, which is
the opposite of what the rest of this page asks for.

Four things now veto that completion, and they are checked in
~clawt_task_manager_complete_on_turn_end()~ rather than at the call site,
so there is one rule instead of one per caller who noticed:

| Veto | Why |
|------+-----|
| the turn was not the assignee's | everyone in a task's thread ends turns there, and the delegator's "thanks, carry on" was being recorded as the result of work that was still running |
| the assignee is still marked busy | libreclaw drops its typing indicator before posting the answer, so anything arriving while it is up is by construction not the answer |
| the assignee called ~clawtilla_task_progress~ this turn | it said the work is not finished, which is the only thing that actually knows |
| the task has children of its own still running | it cannot be finished while the work it handed on is not |

The first is checked before the progress hold, because the hold is
consumed by being checked: a delegator's turn ending in the thread must
not spend the hold the assignee armed against its own next one.  The
last could not fire at all until delegation started recording a
parent.  It is the one that would have held the reported case open.

A task that *does* end this way is marked as inferred, and
~clawtilla_task_status~ and ~clawtilla_task_result~ say so when they are
read: "nobody reported this task complete; that is the last thing they
wrote before the turn ended".  "They said it was done" and "they stopped
talking" are different facts, and a delegator that cannot tell them apart
either waits on finished work or does it again.

**** Reporting progress without finishing

#+begin_example
clawtilla_task_progress(task_id, note)
#+end_example

For an assignee that is stopping for now and coming back.  It records the
note, holds the task open past the end of this turn, and marks it
~running~.

The hold is *one turn*.  A hold that outlived its turn would mean the
task could never finish by inference again, and the next turn ending is
usually exactly when the work is done -- so an assignee still going says
so each time.  The note it carries is the one the assignee chose for the
purpose: a vetoed turn-end does not overwrite it with whatever the AI CLI
wrote to close the turn, which is often "I will check back shortly".

The delegator reads it through ~clawtilla_task_status~, without waiting
for a result.

*** Seeing all of it at once

~clawtilla_task_status~ answers about *one* task, and only if the agent
still has its id.  An agent that has handed out five pieces of work and
wants to know how they are going had to have kept five ids and make five
calls -- and a chief that had lost them, or had been restarted, could not
ask at all.  ~clawtilla_list_agents~ was no help either: it reports who
is *running*, which is not the same question as what they are running.

~clawtilla_task_list~ is the one call:

#+begin_example
Delegated by you (3):
  tsk_01JQ...  oryx    running    4m ago   Validate the Fedora 44 image boots to a desktop
  tsk_01JQ...  kudu    running    6m ago   Check the Ubuntu LTS guest reaches a login prompt
  tsk_01JQ...  mamba   failed     2h ago   Boot the Arch cloudimg and report the console

Assigned to you (1):
  tsk_01JQ...  from operator  running  12m ago  Report on the qa team's progress

Handed on further, under work you started (2):
  tsk_01JQ...  oryx -> kudu   running  3m ago   Run the same mount checks on yours
  tsk_01JQ...  oryx -> mamba  pending  3m ago   Run the same mount checks on yours

Finished tasks are omitted; pass include_finished to see them.
#+end_example

Three sections, and they are three different claims.

*Delegated by you* and *Assigned to you* are what the caller is a party
to.  Both directions, because "my tasks" means both to whoever is asking,
and because an agent that delegated everything is the assignee of none of
it -- the assignee filter that already existed answered the delegating
agent with an empty list, which is the case the tool is for.

*Handed on further* is everything below a task the caller started, with
both sides named because neither of them is the caller.  Without it a
delegator could see one level and no further: a chief that gave a lead a
job could not list what the lead gave anybody, so a fan-out was
unobservable from the one place that was watching it.  Combined with a
parent that closed early, nothing distinguished finished from evaporated
from still-running.

A task in a chain the caller did not start still does not appear.  That
is what lets the tool need no permission, rather than being a window onto
the whole fleet's work.

**** ~agent_id~ narrows, it does not search the fleet

~agent_id~ means *this agent on the other side of something of mine* --
your task to them, theirs to you, or one of them on either side of
something below a chain you started.  It is not "every task involving this
agent", and the parameter used to say that it was, which produced a
confident wrong answer: asking about a worker two levels down came back
"No tasks involving kudu" while kudu's task was running, and then blamed a
daemon restart for it.  A plausible wrong cause is worse than no cause,
because it sends the reader to a different layer.

The empty case now says what it looked at and what it did not.

**** An empty list is not "nothing happened"

Tasks are held in memory, so a daemon restart clears them.  The empty
case says so, and points at the event log, rather than returning nothing
and letting an agent conclude that work it remembers delegating was never
delegated.  The same shape as ~clawtilla_mailbox_list~ being empty for a
running agent.

*** A task does not get a session of its own

This page and ~clawt-task.h~ both used to say it did.  It has never been
true, and the reason is in libreclaw and is deliberate:
~lc_router_resolve_session_key()~ keys a session on channel, room and
sender, and its own note says the thread is *intentionally* excluded --
there a thread anchors a Matrix reply rather than dividing a
conversation.

~clawtilla_delegate~ routes into the direct room the two agents already
share, so every task between one delegator and one assignee lands in one
session.  Three consequences, all real:

- *Tasks share context.* Yesterday's assignment is in today's session,
  and so is anything the operator said to that agent in between.
- *A task waits its turn.* Queued behind whatever that pair is already
  doing, and behind the operator's conversation if the agent is one
  somebody talks to.
- *It happens in that room's transcript*, because that is the room it
  went to.

For delegation between two workers that is usually fine and sometimes
desirable -- continuity between assignments is worth having.  For a
*routine* it is not, which is why ~docs/routines.org~ says to point
routines at an agent that is not also a conversational surface, and why
~routines.isolate~ exists.  Delivering the same isolation for an ordinary
delegated task would mean routing it into a room of its own, which takes
its output out of the transcript somebody is reading.  That is a product
decision rather than a repair, and it has not been made.

** The chief-of-staff pattern, worked through

Name one agent as the chief:

#+begin_src yaml
orchestration:
  chief_of_staff: chief-of-staff

agents:
  - id: chief-of-staff
    chief_of_staff: true
    description: "hands work to the others and reports back"
    model:
      model: opus
  - id: researcher
    description: "reads code and summarises it"
    computer:
      type: container
  - id: writer
    description: "turns notes into prose"
#+end_src

The descriptions are load-bearing.  They are what the chief reads when
deciding who to delegate to, so they should say what an agent is *for*,
not what it is called.

Now:

#+begin_src bash
clawtilla send chief-of-staff "summarise this week's commits and write it up"
#+end_src

What happens:

1. The message is queued into the chief's mailbox and delivered.
2. The chief calls ~clawtilla_list_agents~ and sees the researcher and
   the writer, with their descriptions and states.
3. It calls ~clawtilla_delegate(agent_id: "researcher", task: "…")~ and
   gets a task id back immediately.
4. The router enqueues that work into the researcher's mailbox, carrying
   the task id and one hop beyond whatever the chief was handling.  From
   a message you typed that is a depth of 1; from a chain it is deeper.
5. The researcher works, then calls ~clawtilla_task_complete~ with its
   result -- or simply replies, in which case the daemon completes the
   task from the reply, because an agent that only replied would
   otherwise leave the chief waiting for ever.  If it is *not* done --
   it has handed part of the work on, or scheduled a wakeup -- it calls
   ~clawtilla_task_progress~ instead, and the task stays open.
6. The chief polls ~clawtilla_task_status~, gets the result with
   ~clawtilla_task_result~, and delegates the write-up.  With more than
   one piece of work out, ~clawtilla_task_list~ answers for all of them
   at once and does not need the ids kept.

Step 6 is where a fan-out shows up.  If the researcher hands part of the
job to a specialist, that task is parented on the chief's, so the chief
sees it under *Handed on further* and its own task cannot report
~completed~ while the specialist is still going.

At every step:

#+begin_src bash
clawtilla task list                # what is in flight
clawtilla room history standup     # what was said
clawtilla mailbox list writer      # what is waiting (usually nothing)
clawtilla cost                     # what it has cost so far
#+end_src

A reply that carries a task id completes it *only* on the last message of
the turn, while the agent is no longer busy, with nothing it handed on
still running, and with no progress note held against it this turn.  The
busy check is what stops libreclaw's own progress notes -- "Still
working... (5m elapsed)" -- from completing a task seconds after it
started and reporting the note as the result; the other two stop a turn
that ended for other reasons from doing the same thing more quietly.

** The tools agents get

Served over each agent's link as an MCP endpoint.

| Tool | What it does |
|------+--------------|
| ~clawtilla_list_agents~ | who else is here, what for, and whether they are running |
| ~clawtilla_get_agent~ | one agent in detail |
| ~clawtilla_message_agent~ | queue a message; returns without waiting |
| ~clawtilla_ask_agent~ | ask a question; the answer arrives in your mailbox |
| ~clawtilla_delegate~ | hand over work, get a task id |
| ~clawtilla_handoff~ | give a task you own to somebody else, and stop owning it |
| ~clawtilla_task_list~ | everything you delegated, were delegated, and what those turned into |
| ~clawtilla_task_status~ / ~clawtilla_task_result~ / ~clawtilla_task_cancel~ | follow it |
| ~clawtilla_task_complete~ | report your own assigned task done |
| ~clawtilla_task_progress~ | say it is still going, so ending your turn does not close it |
| ~clawtilla_post_room~, ~clawtilla_create_room~, ~clawtilla_room_history~ | rooms |
| ~clawtilla_mailbox_list~ / ~clawtilla_mailbox_read~ / ~clawtilla_mailbox_ack~ / ~clawtilla_mailbox_reply~ | your own mail |
| ~clawtilla_computer_exec~, ~clawtilla_computer_state~ | your computer |
| ~clawtilla_memory_*~ | six tools over your own searchable memories |
| ~clawtilla_message_user~ | reach the operator; replying does not |
| ~clawtilla_ask_decision~ | put a choice in the operator's decision inbox |
| ~clawtilla_list_teams~ | who is on which team, and who leads it |
| ~clawtilla_fleet_cost~ | what the fleet has spent, and one task's budget |
| ~clawtilla_create_agent~, ~_agent_options~ | grow the fleet |
| plugin tools | whatever a ~ClawtToolProvider~ registers |

That is the whole registered set.  Which of them an agent is actually
offered depends on a gate per tool:

| Requirement | Gated on |
|-------------+----------|
| peer comms | a capability every agent has, so it gates nothing today |
| assigning (~clawtilla_delegate~) | ~agents.chief_of_staff~, or ~team_role: lead~ |
| handing over (~clawtilla_handoff~) | the same, *and* the daemon offering the hook |
| fleet admin (create agent, options) | ~agents.tools.manage_fleet~, *and* the daemon offering the hook |
| a computer | ~computer.type~ not ~none~ |
| memories | ~memories.enabled~ |
| the decision inbox | the daemon offering the hook; no config key |

There is no ~tools.delegate~ key.  Turning delegation off for one agent
is ~deny: [clawtilla_delegate]~.

There is also no ~clawtilla_spawn_~* tool, whatever an older copy of
these docs said: the two that create agents are ~clawtilla_create_agent~
and ~clawtilla_agent_options~, and the permission is
~tools.manage_fleet~.  ~make docs-check~ fails on any ~clawtilla_*~ name
in ~docs/~ that is not registered, which is what stopped that particular
fiction coming back.

*A tool an agent cannot use is not offered at all.*  Listing it and then
refusing costs the agent a turn to discover something it could have been
told up front, and teaches it to keep trying.  An agent with no computer
never sees ~clawtilla_computer_exec~.

Per-agent narrowing:

#+begin_src yaml
tools:
  allow: [clawtilla_list_agents, clawtilla_message_agent]
  deny:  [clawtilla_delegate]
#+end_src

Deny is applied after allow and wins, so a broad allow cannot quietly
re-enable something specifically turned off.  Plugin tools obey the same
lists -- a plugin must not be able to hand an agent something its
operator turned off.

** Teams

A handful of agents needs no structure. A fleet does, and teams are it:
an agent names its team in ~agents.team~ and its standing there in
~agents.team_role~.

#+begin_src yaml
teams:
  - id: research
    name: Research
    description: Reads sources and answers questions about what is in them.
                 Not for anything that writes code.

agents:
  - id: chief
    chief_of_staff: true
  - id: lead-r
    team: research
    team_role: lead
  - id: reader
    team: research
#+end_src

*** Who may assign to whom

Three rules, and no more:

- the *chief of staff* may assign to anybody. It is the lead of every
  team, and dividing work between them is the whole of the role
- a *lead* may assign within its own team and nowhere else
- a *member* may assign to nobody

That is about *assigning*, not about talking. Every agent may message,
ask and share a room with every other agent, on its team or not. Handing
something over in conversation, asking somebody who knows, working on
something together -- none of that is restricted, and a fleet where it
was would be much less useful than one where it is not.

So ~clawtilla_delegate~ is offered only to the chief and to leads, and a
lead calling it on another team's agent is refused with somewhere to send
it instead:

#+begin_example
builder is not on your team (research), and a lead assigns only within
their own. Send it to the chief of staff, who can hand it to the right
team's lead -- or message builder directly if it is a question rather
than a task.
#+end_example

*** Descriptions are what the chief reads

~clawtilla_list_teams~ leads with the description, because that is the
only part that says what a team *handles*. The names on it do not, and a
chief-of-staff choosing between four teams by their members is guessing.

A team with no description says so, in the tool output and in the client,
rather than appearing as an option nothing is ever sent to.

*** What only the whole fleet shows

~clawtilla team list~ prints these to stderr, and the Teams page shows
them:

- a team with *two leads* -- not picked between, because which of them
  may assign is exactly the question
- an agent on a team *nobody declared*, which is almost always a typo
- a team with members and *no lead*, which works (the chief assigns into
  it directly) and is usually not what somebody meant

Warnings rather than errors. A fleet is edited by hand and half-built
states are ordinary; refusing to start over one would be far worse than
saying so.

*** Teams are optional

A fleet that declares none behaves exactly as it did before there were
any: one group, and only the chief of staff assigns.

** Growing the fleet from a conversation

A chief-of-staff can create agents, which is off by default:

#+begin_src yaml
agents:
  - id: chief-of-staff
    chief_of_staff: true
    tools:
      manage_fleet: true
#+end_src

Worth a moment before turning on.  An agent that can create agents can
give one a computer, and a container or a VM is a machine that runs
code.  It cannot exceed what you could create yourself -- every agent it
makes goes through the same validation, the same refusal of a VM with no
disk, and the same start -- but it can do it without being asked twice.

Two settings, not one, and the obvious-sounding name is not the one that
grants it: ~chief_of_staff~ marks who receives work addressed to the
fleet, ~tools.manage_fleet~ is what adds the tool.  Enabling the first
and asking for an agent gets you an agent that says, correctly, that it
has no such tool.  Both are switches in the agent editor.

Two tools come with it:

| Tool                       | What it does                                     |
|----------------------------+--------------------------------------------------|
| ~clawtilla_agent_options~  | What can actually be chosen                      |
| ~clawtilla_create_agent~   | Adds one and starts it                           |

The first exists because the second is otherwise a guessing game.  An
agent asked to create another will invent a provider, a model name and a
disk image path, and each of those produces an agent that looks created
and does not work -- an image most of all, since the ones that exist are
the ones somebody fetched.  So ~clawtilla_agent_options~ reports the
providers that can *run* an agent (not the ones that only do tool
calls), their models, the images actually on disk, and every settable
key straight from the schema.

~settings~ takes ~key=value~ lines using those keys, so anything in the
schema is reachable without a list in the tool that would drift from it
the first time somebody added an option.

Creating goes through the same path a person's ~agent create~ does --
one implementation, because the last time there were two, one of them
skipped the check that refuses a VM with no disk.

** How the tools reach an agent

An agent runs an AI CLI, and the only way such a CLI can be given tools
is a config naming an MCP server to talk to.  clawtilla writes one into
the agent's workspace as ~.mcp.json~, naming ~clawtilla-mcp-server~ with
the agent's id, the daemon's socket, and the path to the agent's token.

The CLI finds it in its working directory by itself, the same way it
finds ~CLAUDE.md~ -- so this needs no cooperation from libreclaw and
works for any CLI that follows the convention.

~clawtilla-mcp-server~ speaks MCP on stdin and stdout and answers by
asking the daemon over ~tool.rpc~.  It is almost entirely a
pass-through: ~clawt_mcp_tools_call()~ already takes a JSON-RPC request
and returns a JSON-RPC response, so the tools have one implementation
and the server cannot drift from it.  It answers ~initialize~, ~ping~
and the empty ~resources/~ and ~prompts/~ lists itself, because those
are transport boilerplate the daemon has no opinion about.

It authenticates with the agent's own token -- the same one the link
uses -- so one agent on this machine cannot call tools as another.  The
config holds the *path* to the token, never the token: a workspace is
mounted into containers and read by people.

*** Adding your own MCP servers

~.mcp.json~ is an ordinary file in the agent's workspace, and adding a
server to it is how an agent is given tools clawtilla knows nothing
about:

#+begin_src bash
clawtilla agent edit researcher .mcp.json
#+end_src

or the pencil beside it in the GTK client's /Files/ group, which opens
the same file in ~$EDITOR~.

Only the ~clawtilla~ key is managed.  On every start that entry is
rebuilt -- it carries the socket and the token path, and a copy left by
a daemon that used to live somewhere else points at nothing -- and
everything beside it is read back and written out untouched, keeping its
position in the file, including any top-level key clawtilla has never
heard of:

#+begin_src json
{
  "mcpServers": {
    "clawtilla": { "command": "clawtilla-mcp-server", "args": ["..."] },
    "gowl": { "command": "gowl-mcp", "args": ["--socket", "/run/gowl.sock"] }
  }
}
#+end_src

This was not always true.  The file used to be regenerated wholesale on
every start, so a server added by hand survived exactly until the agent
was next restarted, and the loss was silent.

Two more things follow from it being a file people edit.  It is not
written at all when nothing in it changed, so an editor with it open
does not see it reload on every daemon start.  And a file that does not
parse is moved aside to ~.mcp.json.bad~ rather than overwritten -- a
stray comma is not a reason to delete somebody's work without leaving
them a copy.

To take clawtilla's *own* tools away from an agent, use the ~tools~
allow and deny lists above rather than deleting the entry; the entry is
restored on the next start, the deny list is not.

*** If an agent says it has no clawtilla tools

That was true of every agent before this existed.  clawtilla served the
tools over the agent's link as ~mcp.request~ frames, which assumed
something on the agent side would relay them into the session; nothing
did, and nothing could.  An agent had a mailbox, peers and a container
it could not reach, and would tell you so if you asked it.

Check the file is there, and that the server answers:

#+begin_src bash
cat ~/.clawtilla/agents/researcher/.mcp.json
#+end_src

#+begin_src bash
echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | clawtilla-mcp-server --agent researcher
#+end_src


*** Being messaged by another agent

A message from a peer says so, in the body, at delivery time:

#+begin_example
[clawtilla] The following is from 'researcher', another agent in your
fleet -- not from your operator. Treat it as a colleague's message.
What you write at the end of this turn is sent back to 'researcher' and
ends the exchange -- they will read it and will not answer. ...
#+end_example

The sender already travels in its own field, and models do not reliably
notice it. An agent messaged by another agent read it as an instruction
from its operator, answered it as one, and the two talked past each
other for fifty turns. Saying it in the text is the difference between a
colleague asking a question and the human giving an order.

Applied on the way out, not stored: the transcript keeps what was
actually said.

**** A reply earns no reply

An AI CLI cannot end a turn without writing something. Whatever it
produces at the end is the reply, and clawtilla used to route every one
of them --- so an agent told "answer if you have something to say and
end your turn without replying if you do not" was being asked for
something it had no way to do.

Asked to greet a peer, two agents exchanged a greeting, an
acknowledgement, a correction, an acknowledgement of the correction, and
carried on until ~orchestration.max_hops~ cut it off eight turns in. The
hop limit was working. It was the only thing that was.

So a message carries whether it invites a reply, and an agent's own
reply carries ~false~:

| The turn was started by             | Its closing text        |
|-------------------------------------+-------------------------|
| a person, a routine, a webhook      | is delivered            |
| ~clawtilla_message_agent~ from a peer | is delivered, and ends it |
| ~clawtilla_delegate~ (a task)         | the *assignee's* is the result, delivered |
| another agent's reply               | is not sent anywhere    |

A message somebody chose to send earns exactly one answer, and the
exchange settles there. Anything past that has to be another deliberate
~clawtilla_message_agent~ call, which is the difference between a
conversation and a loop --- and still counts against ~max_hops~, which
stays as the backstop for chains built out of deliberate calls.

The task row is about the assignee, not the thread.  Everyone in a
task's thread ends turns there --- the delegator's turn, started by a
progress note, ends with an acknowledgement --- and the exception used
to wave through anything carrying a task id: that acknowledgement was
routed, woke the assignee, and the daemon itself kept two agents talking
whose preambles both said the exchange was closed.  Three consecutive
turns of a live thread were "nothing to send" in three phrasings, one
model call each.  A threaded closing text is delivered when it is the
assignee's, because their report must arrive whatever the room's flag
says, and judged like any other reply when it is not.  An id naming no
task routes --- tasks live in memory, so after a daemon restart the
choice is between a swallowed result and one delivered acknowledgement,
and the acknowledgement is the cheap mistake.

The agent is told which of the two it is holding, because the rule is
useless as a secret: an agent whose closing text goes nowhere has to
know that, and has to be told what to call instead.

#+begin_example
[clawtilla] The following is 'oryx' answering you, which closes the
exchange.
What you write at the end of this turn will NOT be sent to anybody --
read this, act on it, and end your turn. Do not write a reply or an
acknowledgement; there is nowhere for one to go. If something genuinely
has to reach 'oryx' -- an answer to a question they asked, or a
correction that changes what they will do -- call
clawtilla_message_agent, which starts a fresh exchange they may answer
once.
#+end_example

The operator is never on the receiving end of this. Their message is a
request whose whole point is the reply, and a reply into their own room
is delivered whatever the flag says --- a fleet that went quiet on its
human would be a worse bug than the one this fixes.

***** It is on the message, and it is stored

The flag rides on the ~ClawtMailboxItem~ and is written to the mailbox
database, because a mailbox is durable precisely so a stopped agent
still gets its post. Holding it in memory would mean a reply queued
before a daemon restart was delivered afterwards as though somebody had
chosen to send it, reopening the exchange it closed.

An existing mailbox is migrated on open. ~CREATE TABLE IF NOT EXISTS~
does nothing to a file that already has the table, so without the
migration every mailbox in a live fleet would fail its first read and be
quarantined as corrupt --- a fleet's queued work moved aside on upgrade.
Rows written by an older build read as inviting a reply, which is what
they meant.

*** Reaching the operator is not the same as replying

An agent's reply goes back into the room the message came from. So an
agent asked by its operator to find something out from a peer asks the
peer, the peer answers, and the agent *replies to the peer* -- the
operator hears nothing and ends up asking "did you get a reply?" every
time.

~clawtilla_message_user~ posts into the room between that agent and the
user, which is the room the client is already watching.

**** It is refused during a turn another agent started

Work handed down a chain comes back up the same one.  A chief of staff
delegates to a lead, the lead delegates to a member; if each of them
reports to the operator directly, the operator gets three separate
answers arriving in the middle of a conversation they were not part of
--- and whoever asked the question gets no answer at all.

So an agent whose current turn was started by a peer is refused, and the
refusal names who is waiting and how to reach them.  Answer that agent;
they will pass it on.  The chief of staff is not a special case: its
turns come from the operator, so it never meets this.

Refused rather than redirected on purpose.  A redirect would deliver a
message written for the operator to somebody else --- addressed to the
wrong reader, in the wrong register --- while the refusal makes the next
attempt be written for the person who is actually waiting.

Which turn an agent is on comes from the delivery that started it, held
beside the hop depth and dropped by the same turn boundary: a turn no
delivery preceded (Matrix, a webhook, the person typing into libreclaw)
has no origin the daemon can name, so the tool works as it always did.

***** A message is a turn, and a burst is that many turns

Delivery acknowledges at the socket, so an agent's mailbox is empty
while it is running and a peer that sends five messages has all five
handed over long before any of them is answered.  libreclaw then runs
*five turns*: ~LcSession~ keeps its own queue and takes one message off
it per turn.  It never merges them.

That matters because everything above --- the hop depth, whether the
closing text is delivered, and who is waiting for it --- describes a
message, and there are five of them.  clawtilla used to describe them
with one set of fields plus a flag saying "a delivery set the next turn
up", which the first turn spent.  Turns two through five then looked
exactly like turns nothing had delivered into:

- the depth went back to zero, so ~max_hops~ could not be reached;
- the closing text became deliverable, so an acknowledgement carrying
  ~invites_reply: false~ was answered anyway;
- and the origin was gone, so the refusal above did not fire.

On a live fleet one operator question produced three messages in their
chat: the answer, and two reports written for another agent, pushed into
a conversation that agent was not part of.  Both tool calls returned
success.  Nothing said the guard had been skipped, because from inside
the turn nothing had been --- there was simply no peer on record.

So the daemon keeps one queued description per delivery and
~clawt_agent_begin_turn()~ takes exactly one of them.  The queue is
bounded; past the bound the oldest is *folded into* the one behind it
rather than dropped, keeping the deeper hop count and the more
restrictive reply flag.  Dropping would lose a close signal, and an
agent that never learns it has been answered answers back --- which is
the loop the flag exists to end.

The same correction applies one layer down.  The reply flag used to be
accumulated across a drain, so that a bare "thanks, got it" queued
behind a question could not close the turn the question opened.  With
one turn per message the question gets its own turn and its own answer,
and the accumulation only made the acknowledgement's turn reply to an
acknowledgement.

*** Sending a file

~clawtilla_message_user~ takes an optional ~attachments~ array: paths the
agent can read.  Agents produce non-text artefacts routinely ---
screenshots, rendered diagrams, exported logs --- and without this the
only way to get one in front of a person was a separate channel with its
own credentials, which arrives detached from the conversation that
produced it.

**The daemon reads the bytes at send time.**  Passing the path through
would work for a client on the same host and show nothing for a remote
one, and that failure looks like a broken image rather than an
unsupported configuration.  It also means the agent may delete or rewrite
its own copy afterwards without changing what was sent.

The copy is kept under the daemon's state directory, not in the exchange:
the exchange is mounted into computers and readable by every agent that
shares one, and a message's attachment belongs to the conversation.  A
client fetches it with ~attachment.get~ --- the GTK client caches it and
shows a thumbnail, the web client serves it from ~/f/attachment/<id>~.

A file that cannot be read is *reported* rather than dropped.  An
attachment that silently did not arrive is worse than one that was
refused, because the agent goes on believing it sent it.

There is deliberately **no** attachments argument on the agent-to-agent
verbs.  The receiving side is an agent whose ~read~ and ~bash~ run on the
host, and the daemon's copy is not somewhere it can open --- so it would
receive an id it can do nothing with, which is exactly the shape of
missing feature an agent invents a workaround for.  Put the file in the
exchange and name its path.


** The decision inbox

An agent that reaches a point where a human choice would change what it
does next has, without this, two options and both are bad: block on the
operator, which stalls autonomous work, or decide unilaterally, which
commits somebody to something they never saw.

~clawtilla_ask_decision~ is the third. The agent files the choice and
*keeps going*.

*** The rule that makes it work

**Every item carries the default the agent will act on if nobody
answers, and the point at which that default stops being cheap to
reverse.**

Without those it is a queue of stalled work with a nicer name. With
them an agent can say "going right unless you say otherwise, reversible
until this ships" and keep moving honestly --- the operator's answer
*redirects* rather than unblocks.

The default is therefore required, and filing without one is refused in
those words. The reversibility window is not required, because an agent
that does not know must not invent urgency: a fabricated deadline
reorders somebody else's list.

Hours rather than a timestamp, because "how long until this is hard to
undo" is the thing a model actually knows, and one asked for an
absolute time writes a plausible one in the wrong year often enough to
matter.

*** The threshold

A decision list that collects every small choice stops being read, and
then it is worse than nothing, because it looks as though the operator
has seen things they have not.

The bar: it goes in the inbox only if the branches produce *materially
different work*, or the choice is *not cheaply reversible*. Everything
else the agent simply decides.

That is stated in the tool's own parameter descriptions rather than
only here, because the failure mode is agents being polite rather than
selective --- and an agent reads the description at the moment it is
deciding whether to file.

*** It closes the loop

An answer is routed back to the agent that asked, as an ordinary
message carrying the task id, so it costs a turn and changes what the
agent does next. Without that this would be a suggestion box: the
operator answers into the void and the agent never learns.

The message repeats the question and names the default it replaces. An
agent may have handled a hundred messages since it asked, and an answer
of "after the release" with nothing around it is unattributable.

*** Answered, defaulted, dismissed

Three different outcomes and they stay different. All of them mean the
work went a particular way; only one means somebody chose. Collapsing
them would make the inbox unable to answer the question it exists for
--- what did I actually decide, and what merely happened.

Answering twice is refused rather than allowed to overwrite: the first
answer has already reached the agent and may already have changed what
it did, so a second would be a change of mind nothing downstream ever
hears about.

*** Where it appears

Its own surface in both clients --- a *Decisions* page with a badge in
the GTK client, ~/decisions~ in the web one --- and ~clawtilla decision~
from a terminal, because a decision an operator cannot see over ssh is
one that silently takes its default.

Beside the alerts rather than inside them. An alert is something that
happened; a decision is something that needs you, and one badge meaning
both is a badge nobody can act on.

The store is sqlite under the state directory, durable for the same
reason the mailbox is: an agent that asked and got no answer carried on
with its default, and an operator who never saw the question has no way
to know that happened.

**** How it is laid out, and why it had to be fixed

A decision is three pieces of prose and a list of choices: the question,
what happens if you say nothing, and the options. All four are sentences
an agent wrote, and none of them has a length anybody controls.

Both clients now give them a reading column, wrap every one of them, and
stack the options one per line, left-aligned. That last part is not
decoration --- an option like "Re-provision clawt-oryx from a proper
Fedora cloud image, so the exchange mounts and the default-user config
land too" is a sentence, and two of those side by side is wider than any
window.

The GTK page was unreadable before that, and the cause is worth knowing
because it will happen again. *A wrapping ~GtkLabel~ still reports the
unwrapped string as its natural width*, and a ~GtkScrolledWindow~ left
at the default ~GTK_POLICY_AUTOMATIC~ gives its child exactly that. So
the row became as wide as the question, ran off the right edge of the
window, and took the default line, the answer box and every option
button with it. Nothing was ellipsised and no warning was logged --- the
page had simply become wider than the screen, so all anybody saw was the
first screenful of each line, and it read as text that had been cut off
rather than as a page that was scrolled.

Refusing the horizontal scroll is what makes the wrap that libadwaita
already asks for actually happen. The clamp then comes from the same
resolver the chat uses, so a reader who widened their conversation gets
the same column here.

** Your mailbox is empty while you are running

This trips up agents, so it is worth stating plainly: a message is
acknowledged the moment it reaches the agent's socket and is delivered
as an ordinary turn.  The mailbox holds what queued up while the agent
was *stopped*.  For a running agent it is almost always empty, and that
fact carries no information.

An agent asked to "message test and see what they say back" therefore
checked ~clawtilla_mailbox_list~, found nothing, and reported that no
reply had come -- while the reply was in the turn it had just been
handed.  Both agents then settled into acknowledging each other
indefinitely.

The answer is ~clawtilla_room_history~, which takes *either* a room id
*or* an agent id and, given an agent id, returns the conversation
between the caller and that agent.  It has to accept an agent id: every
exchange between two agents is a room named ~dm:<sorted>:<pair>~, and
that naming is internal -- an agent should no more be typing it than a
client should.  The scaffolded ~TOOLS.org~ says all of this, and
~clawtilla_mailbox_list~ says it again in the empty case rather than
answering a bare "your mailbox is empty".

** Loop safety

Four limits, each answering a different failure.  The defaults:

#+begin_src yaml
orchestration:
  max_hops: 8
  rate_limit_per_minute: 30
  task_budget_usd: 5.0
  cycle_window: 10
  cycle_seconds: 300
#+end_src

Every one of them takes ~0~ to mean *disabled*, not "zero allowed".

The cycle check is the one with two keys: ~cycle_window~ bounds how much
it remembers and ~cycle_seconds~ bounds how long it remembers it for.
Either at ~0~ turns it off.

They are checked in one place, ~clawt_loop_guard_check()~, in a fixed
order: hops, budget, rate, cycle.  The order is load-bearing twice over.
The two checks with no side effects run first, so a message refused on
hops has not consumed part of its sender's rate allowance -- and rate
runs before cycle, because the cycle check *records* the fingerprint it
was handed.  A message refused on rate used to have its text written into
the cycle window anyway, so re-sending it later, legitimately, after the
throttle cleared, was flagged as going in circles.

*** max_hops

Every message carries a depth.  An agent's outbound messages are stamped
one hop beyond whatever it is currently handling, so a chain genuinely
accumulates depth rather than every message looking like the first.  Past
~max_hops~ the send is refused with an error the agent can read.

This is what stops A → B → A → B running until somebody notices.

It applies to an agent's *ordinary reply* as well as to the
orchestration tools, which was not always true and is the whole point.
The router records how far each delivery had come and the tools read it
back, but a reply arrives over the agent's link, and that path stamped a
flat depth of 1 -- so every reply looked like the start of a fresh
conversation and the one limit built for two agents answering each other
for ever could never be reached on the path where that actually happens.
Two agents traded fifty messages of "Idle." and nothing stopped them.

A *turn* is counted, not a message.  Every message an agent sends in one
turn is stamped from the same depth --- because a turn is not one
message: a chief-of-staff answers its operator and hands work to a peer
in the same breath, and a lead reports upwards while asking downwards.

The depth used to be dropped as soon as the first of those went out, on
the reasoning that the reply is the last thing that needs it.  That is
true of a turn that sends one message and false of every other kind: the
second message started a fresh chain at depth 1, so two agents signing
off at each other never reached ~max_hops~ however long they kept it up.
Six rounds of "nothing further, ending turn" on a real fleet is what
found it.

What drops the depth now is the *start* of a turn that no delivery
preceded.  Matrix, webhook, local and cmacs belong to libreclaw and the
daemon never sees those messages, so an agent answering a person there
must not inherit nine hops from the last peer conversation and be
refused a delegation one hop deep.

A hop count is shown against each message on the GTK client's Flow tab
from the second hop on, because a number climbing towards the limit is
the only thing on screen that distinguishes a loop from a conversation:
two agents politely agreeing to do nothing look the same on the tenth
exchange as on the first.

**** Past the limit the tools are not there at all

The limit is enforced twice, and the two are not the same strength.

**The gate that matters is structural**: for a turn that began at
~orchestration.max_hops~ or deeper, ~clawtilla_message_agent~,
~clawtilla_ask_agent~, ~clawtilla_delegate~ and ~clawtilla_handoff~ are
**not offered**.  A → B is allowed; B → C never starts, because B was
never handed the tool.

That is stronger than refusing the call, and the difference is money: a
refusal arrives after the model has decided to make the call and after
the tokens that decided it were paid for, and this tree already knows
what an agent does with a refusal --- it tries the same thing in a
different shape.  ~tests/test-routing.c~ therefore asserts on the *tool
list* and never on a refusal; a test phrased the other way would pass
against the version this replaces.

The other four tools that need peer comms --- ~clawtilla_post_room~,
~clawtilla_create_room~, ~clawtilla_room_history~,
~clawtilla_list_teams~, ~clawtilla_mailbox_reply~ --- stay.  An agent out
of hops has run out of hops; it has not been cut off from its
colleagues, and telling it otherwise is the refusal-shaped mistake
again.

~max_hops: 0~ means no limit, so it withholds nothing.

The call-time check stays as the backstop, because the tool list is read
once at session start and there are ways to reach a tool that did not go
through it --- an allow list, a plugin, a session that outlived the gate.
A limit enforced only where it is convenient is a limit about that call
site.

**** A room reaches it on its own, and the refusal says so

Every reply in a room counts as a hop, because it is one --- so three
agents in a standup do not need to be looping to reach the ceiling.
They just need to have been talking.

That is correct as a limit and was wrong as a *message*. It used to say
"Delegation has gone deeper than intended; answer directly rather than
passing it on again", which is exactly right for a chain of handoffs
and useless in a room: every one of those agents *was* answering
directly, and an agent told to do the thing it is already doing has
nothing to act on. This tree already has the rule --- a refusal that
only says no gets retried in a different shape.

A room refusal now says it is a room, that a long exchange reaches the
ceiling by itself, that nobody did anything wrong, and names
~orchestration.max_hops~ for somebody who wants longer conversations. A
delegation chain still gets the advice that fits a delegation chain, and
there is a test asserting both --- a fix that gave one wrong answer
instead of another would be no better.

Found by running a real three-agent fleet with ~max_hops: 4~ and reading
the event log: 111 refusals in a session, every one of them a room.

*** When a limit fires

The sender gets the error, and the daemon publishes ~message.refused~
naming both agents and the reason.  Without that a refusal on the link
path went only to the log: the two agents simply stopped, and the
conversation appeared to trail off for no reason at all.  The GTK client
raises it as a toast.

*** rate_limit_per_minute

A sliding sixty-second window keyed on the *sender alone* -- not per
peer, not per room.  Thirty messages a minute is thirty messages a
minute wherever they went, which is the right shape: an agent that is
stuck is stuck regardless of who it is talking at.

Sliding rather than a per-minute bucket, because a bucket lets an agent
send its whole allowance twice across a boundary.

When it fires:

#+begin_example
'researcher' has sent 30 messages in the last minute, which is its limit.
Something is looping; wait before sending more.
#+end_example

Nothing waits and nothing queues.  The send fails, and it is the agent's
turn that absorbs it.

*** task_budget_usd

Charged against the *task* by its id.  Past the cap -- at it, in fact:
the test is spend >= budget -- every further message carrying that task
id is refused:

#+begin_example
this task has spent $5.40, which is its budget of $5.00. Stop and report
what you have.
#+end_example

The second sentence is the half that matters.  A refusal that only says
no gets retried in a different shape; this one tells the agent to finish.

The spend is real money: each reply drains what that agent has been
billed since its previous turn -- the figure the provider itself
reported -- and books it against the task the reply is about.  The first
turn after a daemon restart charges nothing, so a restart mid-task does
not bill it for everything the agent has ever done.  See [[file:spending.org][Spending]].

Ordinary conversation is deliberately uncapped: spend is booked against a
task id, and a chat has none.

**** It is per task, not per tree of tasks

The schema calls this a cap on "one delegated task and everything it
spawns", and that is not what happens.  Spend is a flat table keyed on
task id with no walk to a parent -- and no task in production *has* a
parent, since every creation path passes NULL.  So a chief that delegates
ten subtasks creates ten tasks each with its own full $5.00, and the
$5.00 it was itself given bounds only its own turns.

The practical reading: ~task_budget_usd~ bounds *one agent's work on one
assignment*, which is still the runaway case it was built for.  It does
not bound a fan-out.  Bound that with ~max_hops~ and by watching
~clawtilla cost~.

*** cycle_window and cycle_seconds

A SHA-256 fingerprint of (sender, room, body), with the last ten per room
remembered for five minutes.  Catches the case the other three miss: two
agents politely agreeing with each other for ever, each message fresh
enough to pass the hop count and slow enough to pass the rate limit.

It fires on a *byte-identical* repeat and nothing else.  Two agents
varying their wording at all -- which a model does readily -- go straight
past it, so this is a backstop against a genuinely stuck exchange rather
than a general loop detector.  A message with no room is skipped
entirely.

#+begin_example
this exact message has already been sent to 'standup' within the last
300 seconds. The conversation is going in circles; say something
different, or wait for the window to pass if the repetition is genuinely
what you mean.
#+end_example

**** Two bounds, and only one of them used to exist

~cycle_window~ is a count and ~cycle_seconds~ is a duration, and the
check needs both: the count is what stops a busy room accumulating a
fingerprint per message for the whole window, and the duration is what
makes the refusal's "recently" mean anything.

For a long time only the count existed.  The queue held bare
fingerprints and was trimmed by length alone, so how far back the check
looked was *however long the room's last ten messages had taken* --- in a
quiet room, hours.  ~check_rate()~ a few lines above it had kept a
timestamp per entry and slid a real sixty-second window since it was
written, so the file contained its own counter-example: the check that
is time-bounded never claimed to be, and the check that claimed to be
was not.

What it cost is the reason this section is long.  An agent hit an
unrelated spawn failure and emitted a byte-identical error string every
turn.  The first reached the operator; every one after it was refused as
a cycle.  Two routines produced no output at all, and the agent looked
*idle* rather than wedged for ten hours.  Identical repeated output is
the signature of a stuck system, and the guard's answer to a stuck
system was to hide its only symptom.

The expiry sweep runs *before* the search rather than being skipped
inside it, which also closes a leak: a queue nothing drops from grows
without bound in a room that never reaches its count.

**** Choosing cycle_seconds

The default of 300 suits the runaway this check exists for --- two
agents alternating the same two replies with nothing pacing them, where
a turn is seconds.  A repeat is only caught if it lands *inside* the
window, so a fleet whose turns are minutes wants a larger one; a fleet
where an agent legitimately reports the same line each time it runs
wants a smaller one, or ~0~.

The refusal names the number, so an agent that is repeating itself on
purpose is told how long to wait rather than only that it may not.  A
refusal that cannot be waited out is a refusal that gets retried.

*** What happens when one is hit

The send is refused *before* anything is enqueued, and the refusing agent
gets an error saying which limit and why.  Refusing at the source is what
stops a runaway fan-out; checking at delivery time would mean the
messages already exist and cleaning up rather than preventing.

** Turn hygiene

Loop safety above answers "may this message be sent".  Turn hygiene
answers the question it does not: *what ends the exchange*.

The four limits refuse a message.  They do not stop anything, so a stuck
pair kept taking turns --- each turn produced a message, each message was
refused, and the turn had already been paid for before the refusal
arrived.  The limits were being billed for the runaway they exist to
prevent.

*** Which loops clawtilla can actually stop

This distinction is the important one, because a check that implies more
reach than it has sends you to the wrong layer when something goes wrong.

| Loop | Owned by | What happens |
|---+---+---|
| Two agents sending the same thing | clawtilla --- it owns the mailbox router | The *exchange ends*.  The room is stalled, the tasks move to ~stalled~, one alert names both agents and the repeated text. |
| A turn that produces nothing | clawtilla --- it owns the runtime | The turn is *interrupted*, the reason goes into the thread, and anything waiting on it is failed. |
| A member holding a room's turn | clawtilla --- it owns the room | The turn is *yielded* and the room is stalled. |
| One turn calling the same tool over and over | *Nobody on this side of the socket.*  The loop lives in the model's own CLI. | Counted and *reported* in the thread; at the last threshold, escalated to an interrupt.  That is the whole of its reach. |

*** A stalled exchange, and how it restarts

A stalled room refuses every message an agent sends into it, immediately
and without a turn.  That is the point: the refusal an agent would
otherwise get arrives *after* it has written the message, so a pair that
will not stop is billed for every refusal.

**A person saying something in the room clears it.**  Nothing else does,
deliberately --- the stall was raised for somebody to look at, and an
exchange that reopened on its own would reopen into the same loop.

Only an agent's exact repeat stalls a room.  A person repeating
themselves is refused exactly as before and the room stays open;
clawtilla does not end a person's conversation.

*** Counting up is not progress

An exact-match detector is blind to a loop that renumbers itself:
"finished run 41", "finished run 42", "finished run 43" is three
distinct messages and runs for ever.

So the cycle check also compares each message with the numbers taken out
of it, and refuses the sixth near-identical one inside the window.  Two
things keep that from silencing real work:

- it takes *six*, not two, so an agent reporting "step 1 done" through
  "step 4 done" gets through;
- a near match never stalls a room.  It is a refusal that can be waited
  out, because being wrong about a stall means somebody has to come and
  restart the conversation.

An hourly status line is not caught at all, and what protects it is the
*window*: the previous one fell out of ~orchestration.cycle_seconds~
fifty-five minutes ago.

*** A typing frame is a level, not an edge

Everything below this heading, and every field
[[*A task knows what it came out of][the turn state]] holds, depends on
the daemon knowing when a turn *starts*.  The only signal it has is
libreclaw's typing indicator, and that indicator is not an edge:

- it is raised for the whole of a turn, from pickup to reply;
- it is **re-sent every 25 seconds** (~TYPING_REFRESH_MS~) so that Matrix
  does not drop it;
- it is per *room*, and one agent talking to three peers raises three of
  them independently, while the turn state it gates is per *agent*.

Read as a turn start, each of those restarted the turn.  Every 25 seconds
of a running turn:

| Field | Went to | So |
|-------+---------+----|
| ~hop_depth~ | 0 | ~orchestration.max_hops~ could never climb; raising it could not help |
| ~turn_replies~ | %TRUE | a sign-off was routed, and cost the other agent a whole model turn |
| ~turn_origin~ | %NULL | ~clawtilla_message_user~'s guard was not misled, it was *off* |
| ~turn_task_id~ | %NULL | a delegation after the first 25 seconds was created parentless |

And ~clawt_turn_watch_begin()~ installs a *fresh* deadline, so the same
frame moved the watchdog's deadline every 25 seconds:
~agents.runtime.turn_timeout_seconds~ and ~rooms.turn_timeout_seconds~
could not be reached by any turn that ran longer than the refresh
interval -- which is every turn they were written for.  A keepalive is a
timer firing, not a sign of life; ~clawt_daemon_turn_activity()~ is what
an agent doing something actually calls.

A live fleet produced **11,869 ~typing=true~ frames against 549 turns**,
with 22% of its peer messages being sign-offs that had been delivered.

~clawt_agent_note_typing()~ answers the question the frame cannot: it
holds the set of rooms an agent is currently typing in and reports
whether this frame changed whether the agent is in a turn at all.  A turn
begins on empty → non-empty and settles on non-empty → empty.  A set
rather than a counter, because the frames are neither unique nor
guaranteed to pair: a repeated ~true~ or an unmatched ~false~ drifts a
counter and is idempotent against a set.

**Whatever settles a turn must clear the set.**  An interrupt and the
grace timer both end turns the runtime will never send a ~false~ for, so
~clawt_daemon_turn_settle()~ clears it.  Without that the next real frame
is not a rising edge, the turn state is not refreshed, and the new turn
runs holding the abandoned one's depth, origin and task -- the same wrong
answer, reached from the other side.

*** One turn per room, because an agent runs one

An agent can be mid-turn in several rooms at once.  ~LcSession~'s
~processing~ flag is per session and ~lc_router_resolve_session_key()~
keys a session on channel, room and sender, so an agent talking to three
peers has three sessions that can each be running.  The same fleet showed
it: one agent with three rooms' typing frames overlapping and three
separate ~false~ frames, one per room.

Every field above was a scalar on the agent, so those three turns shared
one description and each was judged by whichever room wrote last.  The
reply flag is the severe one, and it is wrong in *both* directions:

- a real answer **swallowed** because another room's turn was a closed
  exchange -- silent, and the peer waits for ever;
- a sign-off **delivered** because another room's was not, costing the
  recipient a whole model turn.

So the turn is filed under its room.  ~clawt_agent_deliver_turn()~ tags
each delivery with the room it was delivered into, and a turn starting in
a room takes the oldest entry waiting for *that* room.  Arrival order and
turn-start order are independent -- libreclaw picks up each session on
its own -- so a queue drained in arrival order handed one room's turn
another room's message.

This works because the room round-trips.  The router puts
~clawt_room_get_id(room)~ on the mailbox item, ~clawt_link_deliver()~
sends it as ~room_id~, and libreclaw's clawtilla channel echoes the same
string back on both the typing frame and the reply -- so the room on a
frame is the room clawtilla delivered into.

**A tool call is told which room it is part of.**  Nothing about the
*transport* carries one -- ~.mcp.json~ is written per workspace and a
workspace is per agent -- so it is carried alongside, from two sources
that ~call_room()~ resolves in this order:

1. **The runtime.**  libreclaw sets ~CLAWTILLA_ROOM_ID~ on the CLI client
   for the session, in ~lc_session_process_message_async()~.  ai-glib
   applies a client's environment at spawn and ~ai_cli_client_chat_sync()~
   spawns per turn, so it is refreshed before each one.  The CLI passes it
   to the ~clawtilla-mcp-server~ it starts from ~.mcp.json~, which puts it
   in the ~tool.rpc~ frame beside the agent and the token.  One room per
   session, and nothing the model touches.
2. **The agent.**  A peer delivery's preamble names the room and asks for
   it back as ~turn_room~ -- named that, not ~room_id~, because several
   tools already take a room to act *on* and the two are different
   questions.  Believed only while the agent has a turn running there: a
   turn's description outlives its turn, so a *finished* room would still
   answer, and naming an old shallow conversation would buy a lower hop
   depth in the one the agent is really in.

Neither being available is not a failure.  With no room the agent-wide
getters *fold* across the running turns, each picking the safe direction
rather than a plausible one:

| Field | Folded as | Because |
|-------+-----------+---------|
| ~hop_depth~ | the **deepest** running turn | ~max_hops~ firing a hop early costs a delegation; firing late costs the runaway |
| ~turn_task_id~ | only when the running turns **agree**, else none | a wrong parent hangs work under somebody else's job, where the depth limit measures from the wrong place and cancellation reaches into a tree it does not belong to. No parent is what the behaviour was before any of this existed |
| ~turn_origin~ | any peer origin among them | the guard is really asking "did a peer start what I am doing", and with one peer turn running the answer is yes. The name may be the wrong peer, which is why the refusal points at ~clawtilla_message_agent~ rather than claiming certainty |
| ~turn_replies~ | the most recent | there is no safe direction, so nothing pretends otherwise -- routing is decided by ~clawt_agent_get_turn_replies_in()~, which has the room |

The fold is still what answers on the agent's bridge link, which is per
agent rather than per session -- and that is not the production route,
because ai-glib's CLI clients drop a tool list handed to them and
~.mcp.json~ is how an agent gets tools at all.  Peer deliveries are also
the only ones whose preamble names the room: an operator's chat is the
common case, and a routing footer on every message in it is noise the
environment already makes unnecessary.

A turn's description **outlives the turn**.  libreclaw lowers the
indicator in ~on_process_message_finish()~ and posts the answer
afterwards, so a table that forgot the room on the falling edge would
have nothing left to judge that answer by.  The entry is replaced on that
room's next rising edge, and the table is bounded so an agent moved
between rooms for months does not grow one.

*** The turn watchdog

~agents.runtime.turn_timeout_seconds~ (default 1200) bounds a turn that
has stopped producing anything.

**Activity, not duration.**  A turn may legitimately run for an hour
while things keep happening; a turn that has emitted nothing at all for
the whole budget is wedged.  What counts as activity is a message the
agent sent or a ~clawtilla_*~ tool call it made --- an agent's own
~bash~ and ~read~ belong to the CLI and never reach the daemon, so those
two are the whole of what the daemon can honestly observe.

**A turn parked on an open decision is exempt.**  Waiting for a person is
not a stall, and stopping a turn under an unanswered question
manufactures a stranded decision the daemon then has to repair.  The
clock resumes when the decision is answered or dismissed.

When it fires: the repeat counters are dropped, the turn is interrupted,
the reason is written into the thread, anything waiting on it is moved to
~stalled~, and a short grace timer force-releases the agent if the
runtime never reports the end.  That last step is the lesson
~agent.restart~ already learned --- a stop that only signals is not a
stop, and without it a second turn overlaps the one being stopped.

The same number is also rendered into the agent's own libreclaw config as
~session.watchdog_timeout_seconds~, so a turn wedged somewhere the daemon
cannot see is still unwound from inside.  Two watchers on purpose: this
one ends the exchange and tells the clients, that one unwinds the worker.

*** The room's turn

~rooms.turn_timeout_seconds~ (default 300, floored at 60) bounds how long
one member may hold a room's turn.

Counted in *work*, not wall time: the clock holds while the turn is
parked on an open decision and resumes with **the remainder**, not with a
fresh budget.  A turn credited the whole budget on every release could
hold a room for ever by asking a question every four minutes.

Different from the runtime's turn timeout: that one catches a wedged
worker, this one catches a wedged conversation.

*** Repeated tool calls

~orchestration.repeat_thresholds~ (default ~5,10,20~) and
~orchestration.repeat_max_keys~ (default 256).

The key is the tool name and its arguments with runs of whitespace
collapsed.  **A bare tool name is not a call worth counting** --- five
~bash~ calls may be five different commands, and a report that says
otherwise is what teaches somebody to stop reading these.

Counts are cumulative for the whole turn rather than a sliding window,
because "the same thing over and over" is a total and a window lets a
slow loop pass for ever.  A threshold fires only when the count lands
*exactly* on it, so the fifth identical call reports and the sixth says
nothing.  The table is an LRU bounded by ~repeat_max_keys~, so one
pathological turn cannot grow the daemon; a call it dropped starts
counting again from one.  Everything is forgotten when the turn ends.

At the highest threshold the turn is interrupted.  Below it, the note in
the thread is all there is --- see the table above for why.

*** Steering an agent that is already working

A message typed at an agent mid-turn is **held, not routed**, and does
not enter the transcript until the turn ends.

Appending it straight away would make the queued line the active leaf, so
the rest of the turn already in flight would hang off a line the model
was never shown --- and the transcript would read as though the agent had
answered something nobody had said.  Both clients say where it went,
because a message that leaves the composer and appears nowhere reads
exactly like a message that was lost.

On settle every held message for that conversation is delivered as one
follow-up turn, joined by newlines.  Two sentences typed three seconds
apart are one turn, not two.

**It survives an interrupt.**  Queue a correction, press stop, the
correction runs --- that is the feature.  Pressing stop is how somebody
says "not that, this", and dropping the "this" would leave them having
only cancelled.

Only a person steers.  A message from one agent to another is ordinary
traffic and goes to the mailbox, which is durable and ordered precisely
so a busy recipient is not a special case; and a message to an agent that
is *not* working goes to the mailbox too, because nothing settles a turn
that never started.

*** Drafts

Composer text that has not been sent lives in the *client's* own config
--- ~$XDG_CONFIG_HOME/clawtilla/drafts.yaml~, mode 0600, beside
~connections.yaml~ --- and never in ~clawtilla.yaml~.  A half-typed
message belongs to the person rather than to the fleet, and a laptop
reaching a workstation may have no fleet at all.

The key carries the connection profile as well as the agent, so two
daemons that each have an agent called ~chief~ do not share one composer.

** Handing work over

~clawtilla_handoff(task_id, agent_id, reason)~ moves a task onto somebody
else's list and takes it off yours.

*** It is not delegation, and the difference is who is responsible

Delegating creates *new* work and keeps the delegator responsible for it;
handing off moves work that already exists and stops it being yours.
Sharing one verb is why a chief of staff kept re-delegating things it had
already passed on --- the task came back with its original origin, so it
read as work it still owed.

The ~reason~ is required, where ~clawtilla_delegate~'s is optional.  A
delegation arrives with the work itself, which explains it; a handoff
arrives as somebody else's half-finished task, and "why has this landed
on me" is the first thing its new owner needs.  They cannot see the
conversation it was decided in, so the reason is the only context they
get.

*** It runs when your turn ends, not when you call it

The call queues and answers immediately.  Waiting for the recipient would
mean waiting for a whole turn, because an agent that is mid-turn will not
look at anything until it finishes.

So a handoff is drained by ~clawt_daemon_turn_settle()~, which is also
what makes it safe: the source has finished writing whatever it was
writing before the task moves out from under it.

**Everything is re-read before it runs.**  Between the call and the turn
boundary --- and on the restart path, across whatever the downtime was
--- an agent can be removed, a team can be re-arranged, and the task can
be finished by somebody else.  A handoff that trusted its arguments would
start a turn on an agent that is now busy, or move a task onto a list
nobody owns.  So the task, both agents and the team rule are all looked
up again, and the ownership transfer is written only once the delivery
has been *accepted* --- the other order leaves a task whose assignee has
never heard of it.

*** Receipts, and why they are durable

~ClawtTaskManager~ is in memory and says so.  After a restart it has
nothing to say about a task, and "there is no task X" to an agent that
handed one over reads as "your handoff never happened" --- which is how
you get two of everything.

So ~<state_dir>/handoffs.db~ keeps a terminal receipt per handoff, and
~clawtilla_task_status~ answers from it when the task itself has gone.

| Receipt | What it means | What to do |
|---+---+---|
| ~done~ | the new owner has it and has been told | nothing; it is theirs |
| ~busy_gave_up~ | they stayed mid-turn for every retry | it is *still yours* --- do it, or find somebody else |
| ~denied~ | the team rule refused it when it came to run | it was never yours to assign there |
| ~dropped~ | the turn was interrupted, or the task or agent went away | re-read the task before doing anything |
| ~failed~ | the delivery itself was refused, usually by a hop limit | answer directly rather than passing it on |
| ~error~ | something else, with a message | read the message |

Six answers rather than "worked" and "did not", because three of them are
not failures and sending somebody to look for a bug in those three wastes
the day.  Each receipt carries a **sentence** as well as its state ---
~too_deep~ gives a model nothing to do, where "delegation chains are
limited to one hop, do this one yourself" gives it the next action.  A
tool's output is part of its behaviour, and one sentence in
~clawtilla_message_user~'s description has already cost this project a
fleet-wide misbehaviour.

The queue is durable for a different reason: a handoff an agent was told
was on its way stopped being that agent's problem the instant the tool
answered, and the turn that could have been asked again is over.  So one
queued just before a restart runs after it.  ~orchestration.handoff_receipt_days~
(default 2) and a row bound retire the *receipts*; a queued handoff is
never pruned however old it is, because age means "finished a while ago"
for one and "nothing has drained this" for the other.

*** The two limits

~orchestration.handoff_max_per_turn~ (default 4) bounds fan-out.  A
blocking ask gets backpressure for free because the caller waits; an
asynchronous handoff does not, so this is the only thing between a
confused chief of staff and a fan-out of real turns that each cost money.
It counts what is *queued* rather than keeping a per-turn tally.  Usually
the same number, since the queue drains when the turn that filled it
ends --- and deliberately not the same when it does not: a transfer still
waiting for a busy recipient goes on counting, so an agent with three
stuck cannot queue four more on top of them.  It also means there is no
counter to forget to clear, which is the shape that produces a limit
nothing ever reaches.

~orchestration.handoff_busy_retries~ (default 3) bounds waiting for a
recipient that is mid-turn.  **These are tries, not seconds**: a queued
handoff is looked at every time any turn in the fleet ends, so three
tries means three turn boundaries went by with the recipient still busy.
Then it is *reported*, never dropped --- "nobody was free" is a different
instruction from "it went wrong".

*** An interrupt drops the queue

A turn somebody stopped did not finish deciding, so the transfers it had
queued would be acting on half a decision.  Each gets a ~dropped~ receipt
saying so, and the task stays where it was.

This is deliberately the opposite of the steer queue, which survives an
interrupt: a steer is what somebody typed *instead*, and a handoff is
part of what was stopped.

*** You can see all of it

Every outcome is written into the pair's room and into both agents' own
threads, through ~clawt_mailbox_router_note()~ --- which appends and
delivers to nobody, so reporting a handoff never starts a turn of its
own.  Agent-to-agent turns cost real money, and a hidden exchange is the
mistake peer coordination exists to prevent.

~handoff.queued~ and ~handoff.settled~ go on the event bus with both
agents, the state and the verdict.

** Who is here, and how an agent chooses

There is **no scorer, no embedding and no description matcher**, and
there is not going to be one.  Which agent should do a piece of work is a
judgement about the work; a matcher in the daemon would be a second and
worse opinion about it, one that needs tuning for ever and that an agent
cannot argue with.

What clawtilla owes is the facts, in two places that are read at
different moments.

*** ~clawtilla_list_agents~, for when it has decided to look

One line per agent, carrying the id and name, the team and standing, the
description, the state, whether the agent is *mid-turn*, and the
configured computer type.  So "who can run a container" needs no second
call.

~running~ is not ~available~: an agent mid-turn will not look at anything
new until it finishes, and a chief that reads the two as the same thing
hands three pieces of work to the one agent that is already working.

The computer type is the **configured** one, not a live object.  A
stopped agent has no computer built yet, and the question is usually
being asked in order to decide whether to start it.

Everything here is clipped --- the description to 200 characters, the
name to 80 --- and the listing stops at 40 agents and says how many it
left out.  This lands in context on *every* call an agent makes, so an
unclipped fleet is a fixed cost paid for ever.

*** The roster in ~TOOLS.org~, for when it is deciding whether to look

An agent that can assign to somebody gets a *Who is here* table in the
managed region of its own ~TOOLS.org~, through the same permission gate
as everything else in that file.  A chief that has to call a tool to find
out a fleet exists mostly does not call it.

It is written when the agent starts and does not move, so it says so and
points at ~clawtilla_list_agents~ for anything about availability.

**These fields are operator-written, and through an imported team
third-party-written, and they are being interpolated into a file the
agent treats as its own instructions.**  So: 40 agents, then "...and N
more"; 80 characters of name, 120 of role, 200 of description; one line
each, with a newline in a description clipped away rather than forging a
second row; and a vertical bar replaced, because org has no escape for
one inside a table cell and three columns of somebody else's choosing is
a place to smuggle in a heading.

An agent that cannot assign gets no roster.  A list of candidates it has
no way to use is an invitation to try, be refused, and try again in a
different shape.

** Rooms, transcripts and branching

~ClawtMessage~ carries a ~parent_id~, so an edit forks a branch rather
than destroying history.  The transcript keeps both.

** Creating agents from a tool

Covered above under *Growing the fleet from a conversation*:
~clawtilla_create_agent~ and ~clawtilla_agent_options~, behind
~tools.manage_fleet~, which is *off by default*.  An agent that can
create agents can create agents that create agents, and the hop limit
