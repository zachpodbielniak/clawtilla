* The client protocol

What ~clawtilla~, ~clawtilla-gtk~, ~clawtilla-web~ and any other client
speak to the daemon.

** Framing

Newline-delimited JSON.  One object per line, UTF-8.

A frame is capped at 8 MiB.  The bound is not optional: without it a peer
that never sends a newline makes the daemon buy memory until it is killed.

** The envelope

#+begin_src json
{"v": 1, "kind": "agent.list", "id": "r1", "payload": {}}
#+end_src

| Field | Meaning |
|-------+---------|
| ~v~ | protocol version; must match, and both are named when it does not |
| ~kind~ | what this is |
| ~id~ | a correlation id the reply repeats back |
| ~payload~ | the body |

A reply adds ~ok~, and on failure ~code~ (a ~ClawtErrorCode~) and
~error~ (text a person can act on, with secrets redacted).

#+begin_src json
{"v":1,"kind":"agent.list","id":"r1","ok":true,"payload":{"agents":[…]}}
{"v":1,"kind":"agent.start","id":"r2","ok":false,"code":2,
 "error":"there is no agent called 'ghost'"}
#+end_src

*A version mismatch names both versions.*  "Protocol error" alone sends
people looking for a bug when the answer is that one half of the install
was upgraded and the other was not.

*An unknown kind names itself.*  A client from a newer build should learn
what is missing, not merely that something failed.

** Kinds

*** control.*

| Kind | Payload | Reply |
|------+---------+-------|
| ~control.hello~ | ~token~ (TCP only) | ~version~, ~daemon~ |
| ~control.status~ | | ~version~, ~config~, ~agents~, ~connected~, ~clients~, ~cursor~ |
| ~control.subscribe~ | ~cursor~ | ~cursor~, ~resumed~, then a replay |
| ~control.reload~ | | ~refused~ -- see below |
| ~control.shutdown~ | | answered before the daemon quits |

~control.status~ answers with two counts of agents and they mean
different things: ~agents~ is how many the configuration declares,
~connected~ is how many have a link dialled in right now.  An agent that
is configured and not connected is the ordinary case -- it is stopped, or
it is starting -- so a client showing only one of them would report
either a fleet that is always broken or a fleet that is always fine.

**** refused

Seven handlers rewrite every agent's files, and every one of them answers
with ~refused~, an array of ~{agent, message}~.  It is empty when every
agent was rendered.

| Kind | Also carries |
|------+--------------|
| ~control.reload~ | |
| ~agent.set~ | ~agent~, ~restart_required~ |
| ~agent.mount.add~ / ~agent.mount.remove~ | ~target~ |
| ~defaults.mount.add~ / ~defaults.mount.remove~ | ~target~, ~restart_required~ |
| ~team.set~ | |
| ~team.remove~ | ~orphaned~ |
| ~design.commit~ | ~id~, ~committed~, ~started~ |

A call can succeed and still leave an agent behind -- the renderer turns
down a ~libreclaw:~ passthrough that redeclares a section clawtilla
renders itself -- and that agent goes on running against the
~config.yaml~ it already had.  Reporting it as a plain success made an
edit that was *rejected* look like an edit that was *ignored*, with the
reason only in the daemon's journal.

It is not an error reply: the call did what it was asked, and every other
agent is on the new configuration.  The array is always present so a
client can tell "nothing was refused" from "this daemon does not report
refusals".

~agent.set~ is the one that matters most day to day.  Rendering is the
whole point of the call there -- without it the setting reaches
~clawtilla.yaml~ and nothing the agent reads -- so a refusal means the
call accomplished nothing at all for that agent while answering
successfully.

~clawt_ipc_reply_refusal_text()~ turns the array into the sentence a
person is shown, so the CLI, the GTK client and the web client all say
the same thing about it.  ~clawtilla~ prints it and exits non-zero, the
GTK client raises it as a toast from its one request wrapper, and the web
client turns the banner it was about to draw.

~clawtillad~ itself is the one caller with nobody to answer: a start
warns once per refused agent and once more in summary, naming them.  It
does not refuse to come up.  A fleet that would not start because one
operator-typed block is wrong is a far worse failure than one that starts
and says which agents are stale.

*** attachment.*

~attachment.put~ carries a file from a client *into* an agent's exchange
directory --- what somebody drags into the composer.  ~attachment.get~ is
the other direction: it takes an ~id~ and answers with ~name~, ~bytes~
and ~base64~, which is how a client gets at a file an agent sent.

The bytes travel rather than the path because a client may be on another
machine, and an id is checked rather than trusted: anything outside the
character set an id is made of is refused, which is what stops a request
of somebody's choosing reading a file the daemon was never asked to
serve.

~attachment.remove~ (~agent~, ~name~) deletes one from that agent's
drop-box and answers with ~removed~, the host path it unlinked.  The name
is rebuilt from its own basename and resolved through the exchange, the
same way ~attachment.put~ does, so a client asking to delete
~../../../etc/passwd~ gets a refusal about a file in its own drop-box
that does not exist.

*** decision.*

~decision.list~ takes ~open~ (default true) and answers with
~decisions~ and an ~open~ count. ~decision.answer~ takes ~decision~ and
a free-text ~answer~; ~decision.dismiss~ takes ~decision~.

Two fields on each item are *derived by the daemon* rather than left to
each client: ~urgent~ (the deadline is inside a day) and
~settled_by_default~ (it has passed while the item was still open).
Both are the same rule about the same clock, and two clients deriving
them would differ exactly once --- on the item whose deadline had just
gone, which is the one that matters. The raw ~reversible_until~ goes
too, so a client can still say *when*.

~decision.answer~ has a side effect the other two do not: it routes the
answer back to the agent that asked, as an ordinary message carrying
the task id. That is what makes the inbox a loop rather than a
suggestion box, and it is why answering twice is refused --- the first
answer has already reached the agent.

*** event.*

~event.list~ takes an optional ~subject~ (an agent, room or task) and a
~limit~, and answers with ~events~ --- each one the same payload a
subscriber receives, so a client reading history and a client receiving
live events parse one shape rather than two.

It reads ~ClawtEventLog~, which has written every published event to
NDJSON under the daemon's state directory since the daemon was first
built, sweeps on ~daemon.event_log_days~, and had been read back by
nobody.  It is fleet-wide unless a subject is named, because the case
that sends somebody to ~sqlite3~ and ~grep~ on the host is watching
several agents at once.

*** agent.*

~agent.list~, ~agent.show~, ~agent.start~, ~agent.stop~, ~agent.restart~,
~agent.reset~, ~agent.logs~, ~agent.create~, ~agent.import~,
~agent.remove~, ~agent.set~, ~agent.reorder~, ~agent.discover~,
~agent.forget~, ~agent.files~, ~agent.file_read~, ~agent.file_write~,
~agent.mount.list~, ~agent.mount.add~, ~agent.mount.remove~.

~team.list~, ~team.create~, ~team.set~ and ~team.remove~ manage teams.
~team.list~ answers with each team's members, its lead, and how many are
running -- counted in the daemon, because three clients counting the same
thing is three chances to disagree about what "active" means -- plus
~warnings~ for what only the whole fleet shows. ~team.set~ refuses ~id~:
everything refers to a team by it. ~team.remove~ answers with
~orphaned~, the number of agents still naming it.

~agent.list~ carries ~team~ and ~team_role~ per agent, and returns the
fleet grouped by team so a client can emit a header when the team
changes rather than gathering the fleet itself.

It also carries ~dm_room~: the id of the room the operator's conversation
with that agent is in.  Reported rather than derived, because how a
direct room is named is the daemon's business -- a client that takes
=dm:a:b= apart is a client that breaks when that changes.  It is what
lets a client tell a message meant for the person from the fleet's own
peer traffic, and it is answered for agents whose room does not exist
yet, which is exactly the agent an unread count is for.

~agent.reorder~ takes ~agents~, the ids comma separated in the order
wanted, and numbers them in tens.  An id it does not know is skipped
rather than refused: the list comes from a client's view, which may be a
moment behind a removal, and failing the whole reorder over that would
lose the arrangement somebody had just made.

~agent.remove~ takes ~remove_files~ beside ~remove_computer~ and answers
with ~files~, which is ~removed~ or the reason it was not.

~agent.create~ and ~design.commit~ take an optional ~start~ (default
true) and answer with ~started~, plus ~start_error~ when it did not.  A
computer is built at start, so an agent created and not started is a
configuration file and no machine; a failure to start is reported and
never undoes the creation.

~agent.mount.add~ (~agent~, ~source~, ~target~, ~mode~, ~type~,
~relabel~, ~size~) validates before writing, so a mount that could never
work is refused here rather than at the agent's next start -- by which
time the config has been saved and the failure mentions neither the path
nor the reason. ~agent.mount.remove~ takes ~target~, which is what has
to be unique.

~defaults.mount.list~, ~defaults.mount.add~ and ~defaults.mount.remove~
are the same three frames for the fleet-wide list every agent inherits,
with the same payload and no ~agent~.  They re-render *every* agent,
because that is what changed, and they answer ~restart_required: true~
without asking: a mount reaches a computer when it is next built, and a
container or a domain that already exists had its devices decided when it
was created.

An agent object carries ~vm_cpus~ and ~vm_memory_mb~ for a VM agent, and
~image~ for a container one.

~agent.remove~ takes ~remove_computer~: %TRUE tears the agent's
container or VM down before removing it, forcing it if it is running.
Off by default. The reply carries ~computer~ saying what happened, or
omits it when there was nothing to remove.

Booleans in a payload may be sent as real JSON booleans or as the
strings "true"/"false" -- both bundled clients build payloads from
string pairs, and a flag sent as a string used to read as the default,
which is the worst failure a boolean can have: the request succeeds and
does the other thing.

~agent.files~ (~agent~) → ~workspace~ and a ~files~ array of
{~name~, ~path~, ~title~, ~identity~, ~generated~, ~exists~}.  ~identity~
says whether the file reaches the system prompt; ~generated~ says
clawtilla writes into it as well as you, which today means ~.mcp.json~
and nothing else.  Missing files are scaffolded before the reply, and
~.mcp.json~ is written too, so a client can offer to edit an agent that
has never been started.

~agent.files~ answers with paths and not contents, because a terminal
client wants to hand the path to ~$EDITOR~ rather than round-trip the
bytes.  A client with nowhere to spawn an editor reads and writes them
instead: ~agent.file_read~ (~agent~, ~name~) → ~name~, ~path~,
~content~, and ~agent.file_write~ (~agent~, ~name~, ~content~) →
~path~, ~bytes~, which also publishes ~agent.changed~.

A file that is not there yet reads as empty rather than as an error.  The
standard set is scaffolded at first start, so asking for one before then
is an ordinary thing to do, and an editor that refused to open a file it
is about to create would be a strange editor.

The ~name~ is a plain file name and the daemon checks that it is: no
separator, no ~..~, not empty and not ~.~.  It is reached from an IPC
request, so the name is whatever the client sent, and
~../../agents/other/credentials~ is a perfectly good relative path that
would hand one client another agent's secrets.  ~g_path_is_absolute()~
alone does not stop it.

~agent.reset~ (~agent~) clears the agent's AI session and answers with
~sessions_cleared~, ~moved~ and ~restarted~.  It stops the agent if it
was running, moves its ~sessions~ directory aside with a timestamp rather
than deleting it -- a reset is what you reach for when something is
wedged, which is exactly when you might want to look at what it was
doing -- clears the session rows from libreclaw's own database, forgets
the usage watermark, and starts the agent again if it had been running.
Both places have to be cleared: libreclaw restores a session from the
persist directory *or* from sqlite, so clearing one leaves the agent
resuming from the other and looking like the reset did nothing.

This is also the only thing that applies an identity change.  An AI CLI
is not handed a system prompt when it *resumes* a session, so editing
~SOUL.org~ or repointing ~persona.identity_files~ reaches a running
agent's files and not its prompt.  Restarting is not enough.

~agent.discover~ takes no payload and answers with ~found~: directories
under the state root and the workspace root that look like an agent and
are not in the configuration, each with ~id~, ~path~, ~kind~ (~state~ or
~workspace~), ~holds~ (which of ~mailbox.db~, ~memory.db~,
~config.yaml~, ~SOUL.org~, ~IDENTITY.org~ and ~AGENTS.md~ are in there)
and ~modified~.  They accumulate: an agent removed from the config keeps
its state, a design that was never committed leaves a workspace, and a
config restored from a backup leaves everything it did not mention.
None of that was visible anywhere.

~agent.forget~ (~id~) is what answers a discovery.  It renames both
directories to ~<path>.discarded~ and answers with ~moved~, and
~agent.discover~ skips a ~.discarded~ suffix so the same question is not
asked twice.  Moved rather than deleted: this is somebody's agent, and "I
never created this" is a thing people say about directories they later
want back.  It refuses an id the configuration still has, naming
~agent.remove~ instead.

~agent.import~ (~id~, ~from~, ~mode~, ~keep_git~) adopts an existing
workspace and answers with ~id~, ~workspace~, ~files~, ~mode~ and
sometimes ~detail~.  ~mode~ is ~copy~, ~link~ or ~git~ and an
unrecognised one is *refused* rather than defaulted -- somebody who typed
~--lnik~ would otherwise get a fork of their workspace instead of a link
to it, and find out only when their edits stopped reaching the agent.  A
git import names a URL rather than a directory, which is why ~detail~
exists: whether it became a submodule depends on where the workspace root
is, and a workspace somebody's ~git status~ tracks is different enough
from one it does not to be worth saying.

An import adopts what the source already said about itself.  Its
~config.yaml~ carries a provider and a model, and dropping them would
quietly move the agent onto the fleet defaults; its persona is in
markdown where clawtilla's is in org, and the two sets do not collide --
so the copy brought a complete persona across and the scaffolder then
wrote a blank ~.org~ beside every file of it.  The agent loaded the
blanks.  ~persona.identity_files~ is set from what is actually there, and
only when nothing was configured on the frame.

An agent object carries id, name, description, state, detail, caps,
whether it is the chief, whether it is connected, its computer type,
model, mailbox depth, and its credentials *by reference*.

*** memory.*

~memory.list~ and ~memory.search~ both take an ~agent~, a ~category~ and
a ~limit~ (20 by default); ~memory.search~ takes a ~query~ as well.  They
answer with ~total~ -- the whole store, not the page -- and ~memories~,
each carrying ~id~, ~content~, ~summary~, ~category~, ~importance~,
~tags~, ~pinned~, ~created_at~ and ~access_count~.  ~memory.list~ also
takes ~pinned~ to show only those.

An agent with ~memories.enabled~ off has no store, and that is answered
as ~CLAWT_ERROR_NOT_SUPPORTED~ naming the key rather than as an empty
list -- an empty result and a feature that is switched off look identical
from a client, and only one of them is worth acting on.

This is ~memories.*~, the searchable per-agent sqlite store, and not
~agents.memory~, which is libreclaw's ~MEMORY.md~ size budget.  The two
are unrelated and the plural is the whole distinction.

*** tool.*

~tool.rpc~ (~agent~, ~token~, ~request~) → ~response~.  Takes one MCP
JSON-RPC request and returns the JSON-RPC response, so the orchestration
tools have one implementation and ~clawtilla-mcp-server~ cannot drift
from it.

The agent's own token is required -- the same one the link uses.  The
socket's permissions are the first line; this stops one agent on this
machine calling tools as another.

*** msg.* and room.*

~msg.send~ (~target~, ~body~, ~from~) → ~queued~, the number of mailboxes
it went into, and ~target_state~ when ~target~ names an agent.

~target_state~ is the agent's state at the moment the message was
enqueued.  A stopped agent accepts mail -- that is what makes the
mailbox worth having -- but nothing is going to read it until the agent
starts, and a client that cannot tell the two apart shows a progress
indicator that never resolves.  Both bundled clients say so instead: the
CLI prints "held in the mailbox until the agent starts", and the GTK
client raises a toast and leaves the activity line clear.

A room has one state per member, so there is no single honest answer and
the key is omitted rather than guessed at.

~room.list~, ~room.create~, ~room.add~, ~room.history~.

~room.history~ accepts an agent id as well as a room id: an agent id
means the direct room with that agent, the same way it does for
~msg.send~.  Pass ~as~ to say who is asking; it defaults to ~user~.

*** mailbox.*

~mailbox.list~, ~mailbox.dead~, ~mailbox.ack~, ~mailbox.requeue~,
~mailbox.purge~.

*** task.*

~task.list~, ~task.show~, ~task.cancel~.

*** usage.*

~usage.summary~ (~since~, unix seconds, 0 for everything) → ~agents~, one
object per agent with ~id~, ~name~, ~turns~, ~input_tokens~,
~output_tokens~ and ~cost_micros~; plus a ~total~ of the same shape,
the ~since~ it was answered for, and ~task_budget_usd~ so a client can
show the cap beside the spend.

Cost crosses the wire in *micro-dollars as an integer*, not as a float.
It is summed across every agent, and a running total of floats disagrees
with itself depending on the order the agents happened to be visited in.

One unreadable database does not fail the summary -- a fleet report that
refused because one agent's file was mid-write would say nothing about
the other nine.

*** computer.*

~computer.exec~ (~agent~, ~command~, ~cwd~, ~timeout~ -- 120 seconds by
default) → ~exit~, ~stdout~, ~stderr~.  ~computer.status~ (~agent~) →
~state~ and ~description~.  ~computer.copy~ (~src~, ~dst~, one side being
~<agent>:<path>~).  ~exchange.list~ (~agent~) → ~entries~.

~computer.rebuild~ (~agent~) tears the agent's computer down and
provisions it again, answering ~rebuilt~, ~agent~ and sometimes ~note~.
It is *refused while the agent runs*, rather than done carefully:
rebuilding is destroying the machine the agent is working on, and there
is no version of that which is safe to do underneath it.  A teardown that
fails is reported in ~note~ and is not fatal -- the common reason to
reach for this is that the guest is already gone, deleted by hand in
virt-manager, and refusing to rebuild because there was nothing to tear
down would be absurd.

This is the frame for every VM setting cloud-init reads once.  The login,
the desktop, the flavour and the package list are fixed for the life of
an overlay, so changing one and restarting the agent does nothing
visible -- which reads as the setting not working rather than as the
setting arriving too late.  cpus, memory, disk size and the screen
resolution are *not* in that group: they reach the domain definition and
apply at its next boot.

~computer.desktop~ (~agent~) answers ~backend~, ~argv~ and ~tools~ -- the
command that reaches a guest desktop's MCP server, and the tool names the
agent's grant permits.  The command is built here rather than written
into the agent's ~.mcp.json~ because the port that reaches the guest is
chosen when the VM is provisioned, which is after the workspace files are
written; a command line captured at render time names a port nothing is
listening on.  The permitted tools travel with it so the relay needs no
copy of the policy, and so revoking ~computer.desktop.allow_input~ takes
effect at the next daemon reload rather than whenever the agent's MCP
client is next restarted.

Its refusals are deliberately four different sentences, because the four
causes want four different actions: no desktop configured names
~computer.desktop.enabled~; a desktop that is not in a VM says there is
nothing to relay to; a VM agent that is stopped says to start it, since a
stopped agent's VM has no address yet; and a running VM with no forwarded
port says so rather than reporting a missing desktop.  The policy is a
pure function of the config, so a stopped agent is answered from the
config rather than told it has no desktop -- which is what it used to be
told, naming a key that was already set.

*** image.* and state.*

~image.list~ is container images and is described below.  The ~vm_~
frames are cloud images, which are several hundred megabytes each: a VM
needs one, clawtilla ships none, and they are fetched deliberately ahead
of any agent needing one.

| Kind | Payload | Reply |
|------+---------+-------|
| ~image.vm_catalog~ | | ~sources~: ~id~, ~name~, ~group~, ~url~, ~note~ |
| ~image.vm_list~ | | ~images~: ~name~, ~path~, ~bytes~, ~total~, ~downloading~, ~url~ |
| ~image.vm_download~ | ~url~ | ~name~ |
| ~image.vm_cancel~ | ~name~ | ~cancelled~ |
| ~image.vm_remove~ | ~name~, ~force~ | ~removed~ |

~image.vm_list~ reports ~bytes~ against ~total~ and ~downloading~ so one
listing covers both what is on disk and what is arriving; progress
between listings is the ~image.progress~ and ~image.finished~ events.

~image.vm_remove~ refuses an image an agent's overlay is built on, naming
the agents, unless ~force~ is set.  A qcow2 overlay records the base it
was made from, so deleting the base breaks that VM at its next start --
with an error from qemu about a missing backing file, a long way from the
button that caused it.

~state.git_init~ takes no payload and answers ~path~, ~created~ and
~gitignore~.  It makes the daemon's state directory a git repository, so
the fleet's configuration and transcripts can be versioned; it is
idempotent, and ~created~ says whether this call is the one that made it.

*** config.*, plugin.*, integration.*, model.*, design.*

~config.show~, ~config.render~, ~config.validate~; ~plugin.list~;
~model.list~; ~image.list~; ~design.agent~, ~design.commit~,
~design.discard~.

Integrations: ~integration.types~ (the kinds, with the keys each needs);
~integration.list~ (~agent~ optional -- with it, the reply also carries
~bindings~, what that one agent actually has, and every instance gains a
~covers~ flag); ~integration.add~, ~integration.update~,
~integration.remove~; ~integration.health~; ~integration.matrix_login~,
~integration.matrix_rooms~.

Connectors: ~connector.catalog~ (the services clawtilla knows how to
connect, with the auth kind each uses); ~connector.list~ (the ones you
have, with whether each is live, when it expires and whether it can renew
itself -- never the credential); ~connector.begin~ and ~connector.await~;
~connector.key~; ~connector.refresh~; ~connector.revoke~.  Adding and
removing a connector go through ~integration.add~ and
~integration.remove~ like any other integration.

A secret is written by naming its *reference*: ~secret_key~,
~secret_backend~ (~file~, ~env~ or ~command~) and ~secret_locator~.  A
reply carries the reference back, never the value.

~integration.matrix_login~ takes ~integration~, ~homeserver~, ~user~ and
~password~, and optionally ~agent~ to write the result under
~per_agent~.  It returns ~user_id~, ~device_id~ and ~token_file~ -- the
token itself stays in the daemon.

*** routine.*

~routine.list~ returns every routine with its own fields plus three the
daemon works out: ~expression~ (what the schedule *means* as cron),
~next_run~ (ISO 8601) and ~last_run~ / ~last_state~ / ~last_detail~.  A
client that had to turn "weekdays at 09:00" into an expression itself
would be a second implementation of the schedule.

~routine.add~ and ~routine.update~ take the schema's own keys and refuse
a schedule that does not parse, so a bad expression is rejected while
somebody is still looking at what they typed rather than at the next tick.
~routine.remove~ and ~routine.run~ take an ~id~; ~routine.run~ ignores
both the schedule and ~enabled~ and returns the ~task~ it started.

~routine.ran~ and ~routine.changed~ are published as events.

*** connector.begin, then connector.await

Authorising takes as long as a person takes, which is far longer than a
request may block -- so it is two frames rather than one.

~connector.begin~ is deferred only as long as the provider takes to hand
over a code, and its reply carries the ~user_code~ and
~verification_uri~ (or, for the authorization-code flow, an
~authorize_url~) plus a ~flow~ id.  That is what a client shows
immediately; waiting for the whole thing before showing anything would
be no use to anybody.

~connector.await~ takes the ~flow~ and is deferred until the person has
approved, refused, or run out of time.  Clients must ask for a longer
timeout than the default -- ~clawt_client_request_full()~ exists for
this, and 900 seconds matches a device code's usual life.

A flow that finishes before anybody asks keeps its answer, so ~await~
gets the same reply whether it arrives before or after: somebody who
started an authorization, walked away and came back should not find the
result was delivered to nobody.

The ~device_code~ is deliberately absent from every reply.  It is the
secret half of the pair -- it authorises the exchange -- while the user
code is the half meant to be read aloud.

*** connector.key

Takes a token and stores it 0600 under ~secrets.dir~.  The reply names
the *file*, never the value: handing the credential back to the client
that sent it would put a live secret into every client's memory.  Same
rule as ~integration.matrix_login~.

*** integration.notify_test

Takes ~integration~ and sends one notification through it, ignoring its
event list and its quiet hours.  A notifier is correct precisely when
nothing happens, so this is the only honest way to check one.

*** Some replies arrive later

~integration.health~, ~integration.matrix_login~,
~integration.matrix_rooms~, ~integration.notify_test~,
~connector.begin~, ~connector.await~, ~connector.refresh~ and
~connector.revoke~ all wait on the
network, so their handlers
*defer*: the request is answered when the work finishes rather than
before the handler returns.  A client sees nothing different -- the reply
carries the request's id as always -- but the daemon keeps answering
everybody else in the meantime.

This matters because a handler runs on the daemon's main context while
the client blocks.  Waiting there for a ten-second connect timeout is ten
seconds in which no agent's message is routed and no other client is
answered.

~design.agent~ takes the questionnaire -- ~purpose~ (required),
~boundaries~, ~needs~, ~personality~, ~projects~, ~notes~ -- plus
~provider~ and ~model~ naming which model does the designing.  A single
~description~ is still accepted, so an older client keeps working.  It
returns ~draft~ (a token), ~yaml~, ~id~, ~files~ (the org files the model
wrote) and ~notes~.

~design.commit~ (~draft~) creates exactly what was reviewed.  The
designer is held on the daemon between the two calls rather than the
model being asked again: a second run is a fresh conversation producing
something else, which would make the preview a demonstration rather than
a decision.  ~design.discard~ drops one.  At most eight may be pending.

~model.list~ takes ~refresh~: %TRUE serves the providers' own lists from
a cache, marking those entries ~live~, and refreshes that cache in the
background when it is more than six hours old.  The request never waits
on a provider.

That is not a detail. Asking during the request made it take as long as
the slowest provider, and both the new-agent dialog and the agent
inspector ask on every build -- so pressing + or clicking an agent
appeared to hang for tens of seconds.

The cache is *not* warmed at daemon start.  It was, so that the first
list a client opened was already the real one, but that made every start
call five provider APIs whether or not anybody would ever look -- and it
made ~make test~ reach the network from every daemon fixture, which the
suite is not allowed to do.  The first ~refresh~ request warms it
instead, and is answered from the built-in table while that runs.
The built-in table goes stale -- it offered grok-3 and grok-4 well after
4.5 and 4.6 had shipped -- so anywhere a list is shown to a person should
ask for this. A provider with no key, or no network, falls back to the
table rather than returning nothing, and the call is bounded so a
provider that never answers cannot hang the daemon.

~design.agent~ takes ~id~ and ~name~: when present they are pinned and
the model cannot change them.

~model.list~ returns the providers clawtilla knows about, each with its
models, ~open_ended~, ~agent~ and ~tools~.  It comes from the daemon
rather than being built into each client so the CLI, the GTK app and the
web client cannot disagree about what exists.

~agent~ and ~tools~ are what a client filters on, and they answer two
different questions.  ~agent~ is whether libreclaw can run an agent on
it -- four CLI backends, and anything else is silently rewritten to
~claude-code~, so offering the rest let a person pick OpenAI and get
Claude Code with ~gpt-4o~ in the model field.  ~tools~ is whether it can
be given tool definitions, which is what the agent designer needs.  A
client that filters on neither is offering both lists at once, and
roughly half of what it shows will not work.

~image.list~ returns ~default~, ~open_ended~ (always true) and an
~images~ array of {~reference~, ~label~, ~note~, ~group~}.  The user's
own entries from ~defaults.container_images~ come first, under the group
"Yours", followed by the built-in suggestions.  Nothing validates
~computer.container.image~ against it.

Each provider carries ~tools~: %TRUE when it can be given tool
definitions, which is what decides whether it can design an agent.  The
CLI-backed providers cannot.  A client filtering on it should treat a
missing member as "yes" -- an older daemon does not report it, and
filtering on absence empties the list.

Each provider carries ~open_ended~.  When it is true the list is a
starting point rather than the whole truth -- Ollama runs whatever you
have pulled -- and a client must offer a way to type a name that is not
listed.  Nothing validates ~model.model~ against the catalogue.

** Events

Subscribers receive:

#+begin_src json
{"v":1,"kind":"event","payload":{
   "kind":"agent.started","subject":"researcher",
   "ts":1755792000000000,"cursor":42,
   "detail":{"from":"chief-of-staff"}}}
#+end_src

Every kind published, by subject:

| Subject | Kinds |
|---------+-------|
| the daemon | ~daemon.started~, ~daemon.stopped~, ~daemon.reloaded~, ~config.changed~ |
| an agent | ~agent.created~, ~agent.removed~, ~agent.changed~, ~agent.started~, ~agent.stopped~, ~agent.state~, ~agent.connected~, ~agent.disconnected~, ~agent.typing~ |
| a room | ~message~, ~message.refused~, ~room.created~, ~room.changed~ |
| an agent's mailbox | ~mailbox.queued~, ~mailbox.delivered~ |
| a team | ~team.changed~ |
| an agent | ~decision.asked~ |
| a routine | ~routine.ran~, ~routine.changed~ |
| an integration | ~integration.changed~ |
| a cloud image | ~image.progress~ (~done~, ~total~), ~image.finished~ (~path~ or ~error~) |
| an agent | ~computer.exec~ |

~agent.state~ is published for *every* state and carries the state's nick
plus a ~detail~ saying why.  ~agent.started~ and ~agent.stopped~ are
published by the frames that asked for them, so an agent that crashed
raises ~agent.state~ and nothing else -- a client that watched only the
pair would show a running agent that is not.

~task.changed~ is published for every state a task passes through, and
its *subject is the task id* -- which is what ~event.list~ filters on.
Details: ~state~, the enum nickname, matching ~agent.state~; and ~agent~,
the assignee.

The ~agent~ detail is load-bearing rather than decoration.  A pod's
scope is matched against it, so without it a pod built as
~clawtilla->new("researcher")~ would hear about every task in the fleet.

This event did not exist for a long time: the manager's signal was
emitted and connected, but only to decide whether to send a
notification, so a client following a task had to poll ~task.list~ and
podomation's ~on_task_changed~ binding named an event nothing published.

~message~ is published once for every message the daemon routes,
whoever sent it, and its *subject is the room*.  Details: ~id~, ~from~,
~to~ and ~body~, plus ~task~ when the message belongs to one.

The subject matters more than it looks.  It used to be published from
the link handler and named the sender and the body but not the room, so
a client had nothing to match a transcript against; the GTK client fell
back to "is this from the agent I am looking at", and a reply from that
agent to one of its *peers* matched -- so two agents talking to each
other appeared in the user's own chat with one of them.  The message had
been routed correctly the whole time.  Match on the room, which
~room.history~ hands back for exactly this purpose, and on nothing else.

Because every message publishes one, a client must also expect to see a
message it already has: a client that has just connected loads history
*and* is replayed the recent events that history already contains.
Deduplicate on ~id~.

~message.refused~ is published when a loop limit rejects a message,
subject the room, with ~from~, ~to~ and ~reason~.  A refusal on the link
path went only to the log before this, so from outside the two agents
just stopped talking and nothing said why.

~room.history~ entries carry ~depth~ -- how far agent-to-agent that
message had travelled -- which is what lets a client show a chain
climbing towards ~max_hops~ instead of an inexplicable wall of polite
agreement.

~agent.typing~ carries ~typing~ ("true" or "false") and, when the agent
named one, ~room~.  It originates in libreclaw, which raises the
indicator for the whole turn -- from picking the message up to posting
the reply -- so it is what separates an agent that is working from one
that is never going to answer.  It is deliberately not persisted: it
describes right now, and a client that connects late learns the state
from the next transition.

Treat the reply as the end of the turn as well as the indicator
dropping.  The two race, and the message wins often enough that a client
waiting only for ~typing:false~ leaves a spinner running underneath an
answer that has already arrived.

** Cursors and resume

Every event has a sequence number.  A client subscribes with the last one
it saw:

#+begin_src json
{"v":1,"kind":"control.subscribe","id":"r1","payload":{"cursor":41}}
{"v":1,"kind":"control.subscribe","id":"r1","ok":true,
 "payload":{"cursor":57,"resumed":true}}
#+end_src

~resumed: false~ means the cursor had already fallen out of the daemon's
buffer and events are missing.  *A client that gets that must re-fetch
rather than assume it is up to date* -- one that silently accepts a
partial replay carries the hole for the rest of its life and shows stale
state it has no way to notice.

Sequence numbers rather than timestamps, because two events in the same
microsecond are ordinary and a client must not have to guess which of
them it already has.

** Authentication

Over the unix socket: none.  The socket is 0600, so connecting at all
proves you are the owner.

Over TCP: ~control.hello~ with a token, before anything else.  The daemon
refuses to open a TCP listener without a token configured.

** Noticing that the other end has gone

A unix peer cannot leave quietly.  Its exit closes the socket and the
reader is told on the next turn of the loop, which is why the local
socket needs nothing here.

A TCP peer can, and does.  A laptop suspends, a tailnet comes back on a
different path, a firewall forgets the flow --- and if neither end
happens to be sending at that moment, *neither end is told anything*.
The connection is not closed and not reset; it simply stops carrying
packets.  Both sides go on believing in it.

That failure is worse than a disconnection in every way that matters.
The daemon writes events into a socket nobody is on the other end of.
The client's read never completes, so nothing fails, so
~clawt_client_set_auto_reconnect()~ never fires --- the window stays
"connected", shows no new message for the rest of the day, and the next
thing typed into it waits out the 120-second request timeout and is
lost.  A client that had *disconnected* would have reconnected,
resumed from its cursor and been handed everything it missed.

So every TCP connection --- both the one the client dials and the one
the daemon accepts --- is armed with keepalive when it is opened:

| ~CLAWT_IPC_KEEPALIVE_IDLE_SECONDS~ | 30 | silence before the kernel starts probing |
| ~CLAWT_IPC_KEEPALIVE_INTERVAL_SECONDS~ | 10 | between probes once one goes unanswered |
| ~CLAWT_IPC_KEEPALIVE_COUNT~ | 3 | unanswered probes that end it |

~SO_KEEPALIVE~ on its own is not the fix, which is why the three timers
are set as well.  The kernel's default idle is *two hours*: a connection
armed and left at the default is reported broken long after the person
watching has given up on the fleet, and long after the message they
typed was lost.  Sixty seconds is short enough that the reconnect
happens before a request times out, and long enough that an ordinary
pause between messages is not mistaken for a failure.  It also keeps a
NAT or a tailnet from forgetting the flow in the first place, since an
idle conversation now sends a packet every thirty seconds.

Recovery is the machinery that already existed: the read fails, the
client disconnects, reconnects, and re-subscribes from the cursor it had
reached, so the events it missed are replayed.  Nothing about that is
new --- it was simply unreachable, because the disconnection it starts
from never happened.

** Backpressure

A client that stops reading has its outbound queue capped and is then
disconnected.  Otherwise a paused GUI or a suspended terminal grows the
daemon's memory without bound while looking healthy.  Dropping a client
is recoverable; running the daemon out of memory is not.

The cap is deliberately *above* the largest legal frame -- twice
~CLAWT_IPC_MAX_FRAME_BYTES~ plus a megabyte, so 17 MiB against a frame
limit of 8.  A single reply may legitimately be 8 MiB, and a cap below
that disconnects a client that is reading perfectly well and blames it
for not reading.

** Robustness

A malformed frame is answered with an error and the connection *stays
open*.  A client that sent something malformed usually recovers, and
dropping it would turn a message-level mistake into a session-level one.

An oversized frame does close the connection: at that point the stream is
no longer trustworthy.

** Versioning

~CLAWT_IPC_VERSION~ increments when the meaning of an existing frame
changes.  Adding a new kind, or a new optional payload member, does not:
an older daemon answers an unknown kind with an error naming it, and an
older client ignores payload members it does not know.

** In code

#+begin_src c
g_autoptr(ClawtClient) client = clawt_client_new(NULL);

if (!clawt_client_connect(client, &error))
    return;

clawt_client_set_auto_reconnect(client, TRUE);
g_signal_connect(client, "event", G_CALLBACK(on_event), self);
clawt_client_subscribe(client, cursor, &resumed, &error);

reply = clawt_client_request(client, "agent.list", NULL, &error);
#+end_src

~clawt_client_request()~ is synchronous: it iterates the caller's main
context until the reply arrives, rather than reading the socket itself.
One reader owns the connection for its whole life, so a request made from
inside an event handler works like any other -- the reader is always
armed, and events reach handlers from an idle rather than from inside the
reader's own callback.

~clawt_client_request_async()~ takes no thread; the same reader completes
its ~GTask~.

Auto-reconnect re-subscribes for you, from the cursor the client had
actually reached -- and the ~resumed~ answer to *that* subscription is
not reported anywhere, in this version.  An embedder should therefore
treat a reconnect as a reason to re-fetch whatever it is showing rather
than as a promise of a complete replay.  ~ClawtClient::disconnected~ is
the signal that says one happened; none of the three shipped clients
connects to it, so there is no example of that in the tree to copy.

An embedding host can skip the socket entirely and call
~clawt_daemon_handle_request()~ with the same frames.
