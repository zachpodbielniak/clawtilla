* The client protocol

What ~clawtilla~, ~clawtilla-gtk~, ~clawtilla-web~ and any other client speak to the daemon.

** Stored trigger replay

~trigger.replay~ accepts ~id~, optional positive integer ~receipt~ (zero or absent previews the latest snapshot), and boolean ~run~ (default false). Execution requires a positive explicit receipt. It returns integer ~receipt~, booleans ~matches~, ~eligible~, ~duplicate~, strings ~prompt~ and ~report~, optional ~reason~, and ~task~ only after an explicit successful execution. ~trigger.deliveries~ now includes each row's ~receipt~ as a decimal string. The request uses current filters and normal task delivery; see [[file:triggers.org][triggers.org]] for durable reservation semantics and retention.

With trigger fan-out, ~trigger.replay~ and ~trigger.test~ include a ~recipients~ array in stable execution order. Explicit execution adds a ~results~ array of objects, each with ~agent~ and either ~task~ or ~error~, plus integer ~failed~. The legacy top-level ~task~ remains the primary recipient's successful task only. A successful IPC envelope means the batch outcomes were recorded; callers must inspect ~failed~ and all ~results~ to detect partial failure. Reservations or persistence failures return an IPC error, which can represent an uncertain result requiring inspection before further action. Delivery rows additionally expose ~agent~ and ~parent~ strings, with child rows pointing at the primary delivery key. Only source-event rows carry replay snapshots; child and replay-result rows cannot be replayed as fresh source events. Rate counting treats a whole batch as one delivery, while unfinished-run accounting counts each reserved or running recipient.

** Framing

Newline-delimited JSON.  One object per line, UTF-8.

A frame is capped at 8 MiB.  The bound is not optional: without it a peer
that never sends a newline makes the daemon buy memory until it is killed.

** The envelope

#+begin_src json
{"v": 1, "kind": "agent.list", "id": "r1", "payload": {}}
#+end_src

| Field | Meaning |
|-------+---------|
| ~v~ | protocol version; must match, and both are named when it does not |
| ~kind~ | what this is |
| ~id~ | a correlation id the reply repeats back |
| ~payload~ | the body |

A reply adds ~ok~, and on failure ~code~ (a ~ClawtErrorCode~) and
~error~ (text a person can act on, with secrets redacted).

#+begin_src json
{"v":1,"kind":"agent.list","id":"r1","ok":true,"payload":{"agents":[…]}}
{"v":1,"kind":"agent.start","id":"r2","ok":false,"code":2,
 "error":"there is no agent called 'ghost'"}
#+end_src

*A version mismatch names both versions.*  "Protocol error" alone sends
people looking for a bug when the answer is that one half of the install
was upgraded and the other was not.

*An unknown kind names itself.*  A client from a newer build should learn
what is missing, not merely that something failed.

*A reply with nothing to say still carries an object.*  Eleven handlers
answer with ~ok~ and no ~payload~ --- ~agent.start~ and ~agent.restart~
among them, because there is nothing to report beyond that it worked ---
and ~clawt_client_request()~ hands those back as an *empty* object rather
than as nothing.  A caller may always take the object and ask it for a
member; the answer is simply that it has none.

This is a contract about the node, not about any one reader.  A
=JsonNode= built with ~json_node_new(JSON_NODE_OBJECT)~ and left there
answers ~JSON_NODE_HOLDS_OBJECT()~ with =TRUE= and
~json_node_get_object()~ with =NULL=: a node that lies about what is in
it.  Every reply used to arrive that way when it had no payload, and the
first reader to check the type and then take the pointer got a json-glib
CRITICAL and its fallback answer.  In ~clawtilla-gtk~ that reader runs on
*every* reply, so pressing Start printed a critical and started the agent
anyway.

** Kinds

*** control.*

| Kind | Payload | Reply |
|------+---------+-------|
| ~control.hello~ | ~token~ (TCP only): the owner token or a paired device's | ~version~, ~daemon~ |
| ~control.status~ | | ~version~, ~config~, ~agents~, ~connected~, ~clients~, ~cursor~ |
| ~control.subscribe~ | ~cursor~ | ~cursor~, ~resumed~, then a replay |
| ~control.reload~ | | ~refused~ -- see below |
| ~control.pause~ | ~agent~ (optional) | ~hold~ |
| ~control.resume~ | ~agent~ (optional) | ~hold~ |
| ~control.shutdown~ | | answered before the daemon quits |

~control.status~ answers with two counts of agents and they mean
different things: ~agents~ is how many the configuration declares,
~connected~ is how many have a link dialled in right now.  An agent that
is configured and not connected is the ordinary case -- it is stopped, or
it is starting -- so a client showing only one of them would report
either a fleet that is always broken or a fleet that is always fine.

**** hold

~control.status~ also carries a ~hold~ object, and ~control.pause~ and
~control.resume~ answer with the same one: ~held~, ~fleet~, ~draining~,
~since~ and ~agents~.

It is present whether or not anything is held, because it is the answer
to "is it safe to restart" -- a client inferring that from an absent
member cannot tell a daemon that is not held from one too old to say.
~draining~ is written even at zero for the same reason: "held, nothing
in flight" is the answer somebody is waiting for.

Neither verb waits.  ~control.pause~ answers immediately with the number
of turns still in flight, and the count falls as they finish.  Agents
report ~held~ and ~draining~ of their own beside ~busy~ -- not as a
~state~, because a held agent is running and only delivery has stopped.

Omitting ~agent~ means the whole fleet.  ~control.resume~ *refuses* a
named agent while the fleet is held, rather than accepting it and
changing nothing: the fleet hold would still cover it, so a caller told
it worked would sit watching an agent that never moves.

**** refused

Seven handlers rewrite every agent's files, and every one of them answers
with ~refused~, an array of ~{agent, message}~.  It is empty when every
agent was rendered.

| Kind | Also carries |
|------+--------------|
| ~control.reload~ | ~restart_required~, ~recreate~ |
| ~agent.set~ | ~agent~, ~restart_required~, ~recreate~ (when it applies) |
| ~agent.mount.add~ / ~agent.mount.remove~ | ~target~ |
| ~defaults.mount.add~ / ~defaults.mount.remove~ | ~target~, ~restart_required~ |
| ~team.set~ | |
| ~team.remove~ | ~orphaned~ |
| ~design.commit~ | ~id~, ~committed~, ~started~ |

A call can succeed and still leave an agent behind -- the renderer turns
down a ~libreclaw:~ passthrough that redeclares a section clawtilla
renders itself -- and that agent goes on running against the
~config.yaml~ it already had.  Reporting it as a plain success made an
edit that was *rejected* look like an edit that was *ignored*, with the
reason only in the daemon's journal.

~recreate~ (0.78.0) is about a container's SELinux level, which podman sets when it creates a container and never after: when a call moved an agent's effective ~computer.container.selinux_level~ -- the key itself, or its ~team~ or ~computer.use~ under ~auto~ -- it says which agent, from which level to which, and how to recreate the container.  ~control.reload~ always carries it, as an array of those sentences (empty when nothing moved), with ~restart_required~ true when it is not empty; ~agent.set~ carries it as one string only when the level moved, and then sets ~restart_required~ for a running agent.  See [[file:computers.org::#selinux-level][computers.org]].

It is not an error reply: the call did what it was asked, and every other
agent is on the new configuration.  The array is always present so a
client can tell "nothing was refused" from "this daemon does not report
refusals".

~agent.set~ is the one that matters most day to day.  Rendering is the
whole point of the call there -- without it the setting reaches
~clawtilla.yaml~ and nothing the agent reads -- so a refusal means the
call accomplished nothing at all for that agent while answering
successfully.

~clawt_ipc_reply_refusal_text()~ turns the array into the sentence a
person is shown, so the CLI, the GTK client and the web client all say
the same thing about it.  ~clawtilla~ prints it and exits non-zero, the
GTK client raises it as a toast from its one request wrapper, and the web
client turns the banner it was about to draw.

~clawtillad~ itself is the one caller with nobody to answer: a start
warns once per refused agent and once more in summary, naming them.  It
does not refuse to come up.  A fleet that would not start because one
operator-typed block is wrong is a far worse failure than one that starts
and says which agents are stale.

*** device.*

Per-device client tokens.  See [[file:security.org::*Paired devices][security.org]] for
why each rule is the shape it is.

| Kind | Who | Payload | Reply |
|------+-----+---------+-------|
| ~device.pair~ | owner | ~name~ (optional) | ~code~, ~display~ ("123 456"), ~expires_in~, ~expires_at~, ~addresses~, ~uri~ (when an address is dialable) |
| ~device.pair_cancel~ | owner | | ~{}~ |
| ~device.redeem~ | anyone, *before* ~control.hello~ | ~code~, ~name~ (optional) | ~version~, ~daemon~, ~id~, ~name~, ~token~ |
| ~device.list~ | any authenticated client | | ~owner~, ~idle_days~, ~pairing_expires_in~, ~devices~ |
| ~device.revoke~ | the owner; a paired device for its own ~id~ only | ~id~ | ~id~, ~closed~ |

"Owner" is a unix-socket client or a network client that said
~control.hello~ with the daemon's own token.  A paired device asking for
~device.pair~ or ~device.pair_cancel~ is refused with
~PERMISSION_DENIED~, naming the device and where the owner credential is.

~device.redeem~ is the one frame a network client may send before
~control.hello~, because a device being paired has nothing to say hello
with yet.  It *is* the handshake: a success authenticates the connection
as the new device -- on any socket, a unix one included -- and its
~token~ is the only token any reply ever carries.  ~ClawtClient~ sends it
in place of ~control.hello~ when ~clawt_client_set_pairing_code()~ was
called, and says an ordinary hello with the token on every reconnect.  A
wrong code is ~AUTH~ and says how many tries are left; the daemon-wide
rate limit is ~LOOP_LIMIT~.

~expires_in~ is what a client counts down from, against its own clock.
~expires_at~ is the daemon's clock and is right only where the two agree.
~addresses~ is every network listener that actually bound, as
~host:port~, or ~[address]:port~ for IPv6 -- empty when the daemon is
on its unix socket alone, in which case no other device can reach it to
redeem the code.

Each entry of ~devices~ is ~id~, ~name~, ~created~ and ~last_seen~
(seconds since the epoch), ~connected~ (a connection is open now) and
~current~ (it is the connection asking).  Never a token and never a
hash.  ~owner~ says whether the asking client may pair, so a client can
offer the button only where it would work; ~pairing_expires_in~ says a
code is outstanding without saying which.

~device.revoke~ closes every connection the device has open -- including
the one asking, when a device revokes itself, which then never sees the
reply.  ~closed~ counts them.  A paired device naming any id but its own
is refused with =PERMISSION_DENIED= before the id is looked up; the
clients ask =clawt_device_row_action()= which button a row gets, so a
paired device's list offers *Sign out this device* on its own row and
nothing on the others.

**** The pairing URI

~uri~ (since 0.34.3) is the code and the addresses as one link, for a client to draw
as a QR code that a phone scans instead of somebody typing both:

#+begin_example
clawtilla://pair?v=1&code=123456&port=8792&host=100.101.102.103&host=fd7a%3A115c%3Aa1e0%3A%3A1&name=phone
#+end_example

| Parameter | Meaning |
|-----------+---------|
| ~v~ | the format's version, ~1~; a reader refuses any other rather than guessing |
| ~code~ | the six digits, no space or dash |
| ~port~ | the port every ~host~ listens on (default 8792 when absent) |
| ~host~ | an address to dial, repeated, in the daemon's order of preference; bare, so an IPv6 address has no brackets |
| ~name~ | the ~name~ the code was asked for with; the daemon files the device under it, whatever ~device.redeem~ says, so a phone can show it as its own name; absent when none was given |

Every value is percent-encoded with nothing reserved left bare, so an
IPv6 address's colons travel as ~%3A~ and a name cannot break the query.
A reader ignores parameters it does not know, so a later version can add
one.  The phone redeems it exactly as a typed code: a fresh TCP
connection to one ~host~ on ~port~, and ~device.redeem~ with ~code~ and
~name~ as the first frame.

The daemon builds it (~clawt_pair_uri_build_from_addresses()~) rather
than each client, so every client agrees on what a phone is told to
dial.  From ~addresses~ it leaves out a wildcard (~0.0.0.0~, ~::~) and a
loopback address -- a phone dialling either reaches itself -- and any
address on a port other than the first remaining one's, since the link
has room for one port.  When nothing is left, ~uri~ is absent: a QR code
nobody can redeem is not drawn at all.  ~clawt_pair_uri_parse()~ reads
one back.

The link carries nothing ~code~ and ~addresses~ did not already: the
code is short-lived, single use and guess-limited, and never a token.

*** attachment.*

~attachment.put~ carries a file from a client *into* an agent's exchange
directory --- what somebody drags into the composer.  It answers ~name~,
~host_path~, ~path~ (where the agent sees it), ~bytes~ and, since 0.51.5,
~id~: a copy kept in the daemon's attachment store, as an agent's file
is.  A client names the file in its message by both -- the host path for
the agent, an indented ~clawt:<id>~ line for every client -- so the
operator's own image is previewed through ~attachment.get~ wherever the
client runs.  Before, the preview was drawn only by a client that could
open the host path itself.  ~attachment.get~ is
the other direction: it takes an ~id~ and answers with ~name~, ~bytes~
and ~base64~, which is how a client gets at a file an agent sent.

The bytes travel rather than the path because a client may be on another
machine, and an id is checked rather than trusted: anything outside the
character set an id is made of is refused, which is what stops a request
of somebody's choosing reading a file the daemon was never asked to
serve.

~attachment.remove~ (~agent~, ~name~) deletes one from that agent's
drop-box and answers with ~removed~, the host path it unlinked.  The name
is rebuilt from its own basename and resolved through the exchange, the
same way ~attachment.put~ does, so a client asking to delete
~../../../etc/passwd~ gets a refusal about a file in its own drop-box
that does not exist.

**** attachment.list and attachment.thumbnail: a conversation's files

Since 0.52.0 the clients draw a *Files* gallery for each conversation from two frames.

~attachment.list~ takes ~room~ (a room id, or an agent id, which resolves to the operator's direct room with that agent as ~room.history~ resolves it) or ~agent~ (an agent id only).  It reads the room's whole history -- every room keeps all of its messages in memory -- for attachment blocks, with the same parser every client previews from (=clawt_attachment_refs_parse()=), and answers the room it read and ~items~, newest message first and in block order within a message:

| Member    | What it is |
|-----------+------------|
| ~id~      | the daemon's copy (=clawt:<id>=), when the block named one; absent otherwise |
| ~path~    | the host path, when the block named no id (a message from before 0.51.5) |
| ~name~    | the item's name |
| ~kind~    | ~image~, ~pdf~, ~text~ or ~other~, from the name (=clawt_attachment_kind()=) |
| ~bytes~   | the size now, or 0 when it is gone |
| ~exists~  | whether the file is still there |
| ~message~ | the id of the message that carried it |
| ~sender~  | who sent that message (~user~ for the operator) |
| ~ts~      | when, in seconds |

#+begin_example
→ {"type":"request","id":"7","kind":"attachment.list","payload":{"agent":"scout"}}
← {"type":"response","id":"7","payload":{"room":"dm:user:scout","items":[
     {"id":"0f3c9a1b2c3d-report.pdf","name":"report.pdf","kind":"pdf","bytes":48211,
      "exists":true,"message":"0f3c9a1b2c40","sender":"scout","ts":1763475600},
     {"path":"/home/you/.local/share/clawtilla/exchange/scout/old.png","name":"old.png",
      "kind":"image","bytes":0,"exists":false,"message":"0f3c8e7d6a10","sender":"user",
      "ts":1763389200}]}}
#+end_example

The list is built from the transcript rather than from the attachment directory because that directory is shared by every conversation and records nothing about which one a file came from.  An id in a message body -- text any agent can write -- is resolved through =clawt_attachment_path()=, so one that is not ours is listed as gone rather than turned into a path.  Neither ~room~ nor ~agent~ is ~INVALID_ARGUMENT~; one that names nothing is ~NOT_FOUND~.

~attachment.thumbnail~ takes ~id~ and an optional integer ~size~ (the longer edge in pixels, clamped to 16..512, default 256) and answers ~id~, ~kind~ and, by kind:

- *pdf*: ~mime~ (~image/png~), ~width~, ~height~ and ~base64~ -- page 1 only, drawn with poppler-glib onto white so its longer edge is ~size~.  Cached as ~<state_dir>/attachments/.thumbs/<id>.<size>.png~; an id names bytes that never change, so the cache never goes stale.  A build without poppler (~POPPLER=0~, or no ~poppler-glib-devel~) answers ~NOT_SUPPORTED~, "no PDF renderer in this build".
- *text*: ~text~, the first twelve lines (at most 8 KiB read, each line cut at 160 characters, always valid UTF-8).  Not cached; it is cheaper to read than to look up.
- *image*: ~NOT_SUPPORTED~ -- a picture is its own thumbnail, and every client already decodes images at thumbnail size from ~attachment.get~.
- *other*: ~NOT_SUPPORTED~.

#+begin_example
→ {"type":"request","id":"8","kind":"attachment.thumbnail","payload":{"id":"0f3c9a1b2c3d-report.pdf","size":160}}
← {"type":"response","id":"8","payload":{"id":"0f3c9a1b2c3d-report.pdf","kind":"pdf",
     "mime":"image/png","width":124,"height":160,"base64":"iVBORw0KGgo..."}}
#+end_example

The id is checked by =clawt_attachment_path()= before any file is opened: ~../x.pdf~ is ~INVALID_ARGUMENT~, an id with no file behind it ~NOT_FOUND~.

*** decision.*

~decision.list~ takes ~open~ (default true) and answers with
~decisions~ and an ~open~ count. ~decision.answer~ takes ~decision~ and
a free-text ~answer~; ~decision.dismiss~ takes ~decision~.
~decision.delete~ takes ~decision~ and answers with ~deleted~ (the id):
the row leaves the store whatever its state, and an unknown id is
~NOT_FOUND~.  Dismissing keeps the record and says the operator passed;
deleting is for an entry nobody wants to see again -- a stale ask, one
raised by mistake, or one a daemon from before 0.3.0 left open past its
deadline.  An open decision is withdrawn on the way out exactly as a
dismissal would be: a turn it held is released, and a policy call
waiting on it is refused with "The operator deleted the request".

Two more members, present only when set (since 0.22.0): ~routed_to~,
the agent a decision raised inside delegated work was put to before the
operator (the delegator), and ~answered_by~, the agent that answered it
when an agent did.  A client draws ~clawt_decision_routed_label()~ from
the pair and the open state; the operator may still answer a routed
decision, and the first answer wins.

Two fields on each item are *derived by the daemon* rather than left to
each client: ~urgent~ (the deadline is inside a day) and
~settled_by_default~ (it has passed while the item was still open).
Both are the same rule about the same clock, and two clients deriving
them would differ exactly once --- on the item whose deadline had just
gone, which is the one that matters. The raw ~reversible_until~ goes
too, so a client can still say *when*.

A rebuild request (~clawtilla_request_rebuild~, ids ~rebuild-<uuid>~)
carries two more: ~kind: "rebuild"~ and ~loses~, the sentence saying what
a rebuild destroys, which is also the question's last paragraph.  Only
the answer ~approve~ rebuilds; the daemon answers a rebuild request by
doing it or by telling the agent it was not done, never by quoting the
answer back.  See ~docs/computers.org~, "An agent asking for a rebuild".

~decision.answer~ has a side effect the other two do not: it routes the
answer back to the agent that asked, as an ordinary message carrying
the task id. That is what makes the inbox a loop rather than a
suggestion box, and it is why answering twice is refused --- the first
answer has already reached the agent.

**** The room, and the inline view

A decision remembers the room it was asked from, so a chat can draw it
inline as a second view of the same record (see [[file:clients.org][clients.org]]).  Members
added for that:

| Where | Member | What it is |
|-------+--------+------------|
| each item (~decision.list~, ~decision.answer~'s ~decision~) | ~room~ | the room it was asked from, or null when nobody could say |
| each item | ~settled_via~ | where a person settled it: ~chat~, ~inbox~, ~cli~, or null (an older client, the venture bridge, the clock) |
| each item | ~answered_at~ | when it was settled, Unix seconds; 0 while open |
| ~decision.list~ request | ~room~ | narrows the list to that room: every state, oldest first, ~open~ ignored -- a settled question stays in the transcript where it was asked |
| ~decision.answer~ request | ~via~ | ~chat~, ~inbox~ or ~cli~; anything else is ~INVALID_ARGUMENT~, refused where it arrives rather than stored as a word no view can draw |

The room is set from the tool call's turn room (~CLAWTILLA_ROOM_ID~ from
libreclaw, or a ~turn_room~ the agent repeats); with neither, and for a
policy ask or hand-back, it is the agent's one running room when it has
exactly one, and unset otherwise.  A question drawn in the wrong
conversation is worse than one that only reaches the inbox, so there is
no guess beyond that.  A venture staging has no room.

A press on a decision that is no longer open -- a stale view, or a
double tap's second press -- is refused with a message that says what
happened: ~Already settled: You answered "now" in the chat. Your press
changed nothing; if you have changed your mind, say so in a message to
chief.~ (~clawt_decision_refusal_text()~).  The check and the write run
in one call on the daemon's main context, so two presses are ordered
there and only the first settles.  A press on a deleted decision is
~NOT_FOUND~.

*** event.*

~event.list~ takes an optional ~subject~ (an agent, room or task) and a
~limit~, and answers with ~events~ --- each one the same payload a
subscriber receives, so a client reading history and a client receiving
live events parse one shape rather than two.

It reads ~ClawtEventLog~, which has written every published event to
NDJSON under the daemon's state directory since the daemon was first
built, sweeps on ~daemon.event_log_days~, and had been read back by
nobody.  It is fleet-wide unless a subject is named, because the case
that sends somebody to ~sqlite3~ and ~grep~ on the host is watching
several agents at once.

*** agent.*

~agent.list~, ~agent.show~, ~agent.start~, ~agent.stop~, ~agent.restart~,
~agent.interrupt~, ~agent.reset~, ~agent.logs~, ~agent.create~,
~agent.import~,
~agent.remove~, ~agent.reap~, ~agent.set~, ~agent.reorder~, ~fleet.reorder~,
~agent.discover~,
~agent.forget~, ~agent.files~, ~agent.file_read~, ~agent.file_write~,
~agent.avatar~, ~agent.avatar_set~, ~agent.avatar_clear~,
~agent.mount.list~, ~agent.mount.add~, ~agent.mount.remove~.

~team.list~, ~team.create~, ~team.set~ and ~team.remove~ manage teams.
~team.list~ answers with each team's members, its lead, and how many are
running -- counted in the daemon, because three clients counting the same
thing is three chances to disagree about what "active" means -- plus
~warnings~ for what only the whole fleet shows -- since 0.78.0 including
container computers that share a writable folder at different SELinux
levels, compared with the teams' stored pairs (see
[[file:computers.org::#selinux-level][computers.org]]), and one line per
agent whose kept container was adopted after a restart and then removed
and made again because it no longer matched its config, naming the
container, when and why (see
[[file:computers.org::#container-restarts][computers.org]]), and the
VENTURE task mirror's warnings (VENTURE #30): an agent whose token cannot
reach the organization its tickets are in, a ticket write VENTURE's
install-wide role gate refused, or a 404 the ticket's own read-back
contradicts -- each naming the agent, the organization and the fix, until
a write by that agent succeeds again (see
[[file:venture.org::*A 404 is confirmed before it is believed (VENTURE #30)][venture.org]]); the web Fleet
page shows these. ~team.set~ refuses ~id~:
everything refers to a team by it. ~team.remove~ answers with
~orphaned~, the number of agents still naming it.

Since 0.55.0 every team in ~team.list~ carries ~tags~, an array as
written in =teams.tags=; ~team.create~ takes ~tags~ (an array); and
~team.set~ dispatches on the schema's type for the key, so a list key
(~tags~, ~skills~) takes ~values~ (an array) or ~value~ split on commas,
and is never written as a single string.  A malformed tag is refused
there.  See [[file:team-tags.org][team-tags.org]].

~agent.list~ carries ~team~ and ~team_role~ per agent, and returns the
fleet grouped by team so a client can emit a header when the team
changes rather than gathering the fleet itself.

It carries ~crosstalk_summary_to~ (since 0.33.0), =source= or =chat=, resolved the same way.

It carries ~crosstalk_summary~ too (since 0.30.0): =chief=, =on= or =off=,
the agent's own value or, when it has none, the fleet's
~orchestration.crosstalk_summary~.  It is what an agent-settings control
shows, and a client writes it back with ~agent.set~ only when the person
changed it -- writing the resolved value on every save would pin the
agent to what the fleet happened to say that day.

It also carries ~dm_room~: the id of the room the operator's conversation
with that agent is in.  Reported rather than derived, because how a
direct room is named is the daemon's business -- a client that takes
=dm:a:b= apart is a client that breaks when that changes.  It is what
lets a client tell a message meant for the person from the fleet's own
peer traffic, and it is answered for agents whose room does not exist
yet, which is exactly the agent an unread count is for.

Each agent also carries what it is *doing* and what is doing it.  ~busy~
and ~peer~ describe the current turn; ~pid~, ~uptime~ (seconds) and
~restarts~ describe the process serving the agent.

~pid~ and ~uptime~ are present only when there is a process, because a
~pid: 0~ invites a client to render it as one and 0 is a pid a caller
could hand to ~kill(2)~ meaning its own process group.  ~restarts~ is
present whenever there is a runtime, including at zero: "this child has
never been replaced" is the answer that makes the other two worth
trusting, and an absent member cannot say it.

An agent running on a fallback backend also carries ~failover~ and ~failover_message~, and only while that lasts.  ~failover~ is the state its libreclaw reported (~state~, ~primary~ and ~active~ each with ~provider~ and ~model~, ~reason~, ~reset_at~, ~retry_at~, ~context_lost~) plus ~since~, in microseconds, when it first left its primary.  ~failover_message~ is the sentence the ~agent.failover~ alert carried.  Clients badge it through ~clawt_failover_badge()~.  ~agent.show~'s ~settings~ carries ~model.fallbacks~ in the one text spelling, =provider:model@account= comma separated, which ~agent.set~ takes back.

Every client renders ~busy~ and ~peer~ through
~clawt_agent_activity_label()~ rather than its own sentence -- the CLI
read neither field for as long as they existed, and the web client drew
a bare "busy" badge that dropped ~peer~ on the floor.

None of these three reach ~clawtilla_list_agents~.  An agent's own
~bash~ runs on the daemon's host whatever computer it has, so a
sibling's pid there is a signal number away from being an action.

~agent.reorder~ takes ~agents~, the ids comma separated in the order
wanted, and numbers them in tens.  An id it does not know is skipped
rather than refused: the list comes from a client's view, which may be a
moment behind a removal, and failing the whole reorder over that would
lose the arrangement somebody had just made.

~fleet.reorder~ takes ~entries~ instead: the same list, in the same
order, with each one written ~a:<agent>~ or ~r:<room>~.  The sidebar
holds both kinds since a group room sits beside the agents it concerns,
and what a reorder actually sends is a *renumbering* of the whole
list --- so a frame carrying only the agents would number them from ten
while the rooms kept whatever they had, and the two scales would
interleave in a way nobody asked for.  Both graphical clients send this
one; ~agent.reorder~ remains for the CLI and is the same renumbering
with every entry read as an agent, so the two cannot drift.

The gap of ten is not decoration: it leaves room to place something
between two others by setting a single number, which is the only way to
do it in a text editor without renumbering the whole file.

~agent.remove~ takes ~remove_files~ beside ~remove_computer~ and answers
with ~files~, which is ~removed~ or the reason it was not.

**** Ephemeral agents (since 0.55.0)

Every agent in ~agent.list~ and ~agent.show~ carries ~ephemeral~
(boolean).  An ephemeral agent also carries ~parent~ (the agent that
spawned it and may reap it), ~ephemeral_since~ (unix seconds) and
~awaiting_reap~ (boolean: it has finished work and nothing open).
=clawt_ephemeral_badge_for()= turns the three into the HELPER badge.

~agent.reap~ (~agent~, optional ~force~) ends an ephemeral agent as the
operator, who may reap anybody's: it is stopped, its workspace and
state are removed, and ~agent.removed~ is published.  Without ~force~ it
is refused while the agent has a task that is not finished, naming the
tasks.  It answers an empty object.  ~agent.remove~ on an ephemeral
agent reaps it (with ~force~, since Remove was pressed on purpose), and
~agent.remove~ on an agent that has helpers hands them to the chief of
staff with a notice.  See [[file:ephemeral-agents.org][ephemeral-agents.org]].

~agent.create~ and ~design.commit~ take an optional ~start~ (default
true) and answer with ~started~, plus ~start_error~ when it did not.  A
computer is built at start, so an agent created and not started is a
configuration file and no machine; a failure to start is reported and
never undoes the creation.

**** Faces: ~face~, ~face_configured~, ~color_resolved~ (since 0.53.0)

Every agent in ~agent.list~ and ~agent.show~ carries three members for its generated face (see "Generated faces" in [[file:agents.org][agents.org]]):

| Member           | Holds                                                                                          |
|------------------+------------------------------------------------------------------------------------------------|
| ~face~           | the face to draw, already resolved: a shape name such as ~cloud~, or ~initials~               |
| ~face_configured~ | the raw ~agents.face~, or ~null~ when unset -- what a picker shows as selected ("automatic") |
| ~color_resolved~ | the colour the face is painted in: ~agents.color~ when valid, otherwise the id's derived tone |

~face~ is resolved by the daemon rather than by each client, so a client built against an older or newer shape table still draws what this daemon decided. A client that does not know the name it is sent draws the letter disc. ~has_avatar~ still wins: a picture is drawn instead of any face.

~agent.create~ takes ~face~ and ~color~ beside its other fields. A request that leaves either out gets a random one, written to the config (~design.commit~ too): a new agent is born with a random shape and palette colour. Send ~""~ to ask for the automatic one instead. ~agent.set~ takes them as the keys ~face~ and ~color~. Both are checked where they arrive, and a refused value writes nothing (and creates no agent):

- ~face~ must be a shape name, ~initials~, or empty for the automatic face. The refusal lists every shape.
- ~color~ must be ~#rgb~ or ~#rrggbb~, or empty for the derived tone. It is written into the web client's markup, so nothing else is stored.

#+begin_src json
{"v":1,"kind":"agent.create","id":"7","payload":{"id":"scout","face":"cloud","color":"#22b573"}}
{"v":1,"kind":"agent.set","id":"8","payload":{"agent":"scout","key":"face","value":"hexagon"}}
{"v":1,"kind":"error","id":"8","code":"invalid-argument","error":"'hexagon' is not a face: it takes one of pebble, cloud, ..., bloom, initials, or empty for one picked automatically"}
#+end_src

~agent.mount.add~ (~agent~, ~source~, ~target~, ~mode~, ~type~,
~relabel~, ~size~, ~create~, ~required~) validates before writing, so a
mount that could never work is refused here rather than at the agent's
next start -- by which
time the config has been saved and the failure mentions neither the path
nor the reason. ~agent.mount.remove~ takes ~target~, which is what has
to be unique.

~defaults.mount.list~, ~defaults.mount.add~ and ~defaults.mount.remove~
are the same three frames for the fleet-wide list every agent inherits,
with the same payload and no ~agent~.  They re-render *every* agent,
because that is what changed, and they answer ~restart_required: true~
without asking: a mount reaches a computer when it is next built, and a
container or a domain that already exists had its devices decided when it
was created.

~egress.allow.list~, ~egress.allow.add~ and ~egress.allow.remove~ edit
=egress.allow=, the private addresses a gated agent may reach (see
=docs/security.org=, "Egress").  The two writes take ~entry~ -- one
address, network or host name, with an optional port -- and all three
answer ~entries~, the list as it now stands (always present, possibly
empty), plus ~problem~ when the list as written does not parse and so
opens nothing.  ~.add~ checks the entry where it arrives: a metadata
address, a multicast range or a typo is refused rather than saved.  The
running gate reads the list per connection, so neither answers
~restart_required~.

agent.show carries an ~egress~ member beside ~agent~: ~network~ (the
agent's ~runtime.network~ nickname), ~refused_today~ (connections the
gate refused it since local midnight), ~refusals~ (the last twenty,
newest first, each ~at~ in microseconds, ~host~, ~port~, ~reason~ and,
when there was one, the refused ~address~) and ~keys~ (every
credential-looking variable in its environment by ~name~, with
~brokered~ and, when it is not, a ~reason~).  No key's value is in it.
The agent object itself carries ~network~ as well, beside ~confine~.

~defaults.mount.add~ takes ~agents~ and ~teams~ separately, and also
takes ~who~: one list of names that the *daemon* sorts into the two.
Both graphical clients send ~who~, because a name is a team or an agent
and the fleet already knows which --- asking somebody to classify it is
asking them to know something the daemon does.

Sorted there rather than in a client because a client can only ask
~team.list~, which reports the teams somebody *declared*, while an agent
may perfectly well be on a team nobody declared.  The GTK dialog did
exactly that and filed every such name under ~agents:~, where it matches
nothing: the folder reached nobody, the agents meant to have it started
perfectly, and the field promising "teams or agents" was the thing that
had caused it.  ~clawt_mount_sort_scope()~ answers the same question
~clawt_mount_covers()~ does, which is the only version that cannot
disagree with what the mount then does.

A name that is neither an agent nor a team goes into ~agents~, where
~clawt_mount_validate_fleet()~ names it; guessing "team" would silently
widen a folder to a group somebody may be about to create.

An agent object carries ~vm_cpus~ and ~vm_memory_mb~ for a VM agent, and
~image~ for a container one.  It also carries ~computer~ (the type),
~computer_machine~ (whether it has a machine to power on and off) and
~computer_stop_removes~ (whether stopping that machine destroys it), so
no client has to work any of the three out from the type.  A container agent
whose kept container this daemon removed and made again -- because it no
longer matched the config when it was adopted -- also carries
~computer_recreated~, the sentence the Fleet page shows; it is absent
otherwise.

~agent.stop~ and ~agent.restart~ stop the agent's *machine* as well ---
those two verbs mean "this agent is finished for now", and a container
left running under a stopped agent is a resource nobody can see.
~agent.reset~ and ~agent.remove~ stop only the process: both stop it as a
step in something larger, and reset in particular needs the sqlite
connection closed rather than the machine powered off.  Blocking, in the
same way ~agent.start~ is and for the reason written there --- every
caller has somebody waiting on the answer, and the wait is bounded by
podomation's socket timeout.

**** activity.list

~activity.list~ (no payload) → ~now~ (the daemon's clock, microseconds) and ~turns~: one object per turn running anywhere in the fleet, an agent's oldest turn first. Each has ~agent~, ~agent_name~, ~room~ and ~room_name~ when the room has one, ~started~ (microseconds, taken on the typing indicator's rising edge and not moved by its keepalives), ~origin~ and ~task~ when the turn has them, ~steerable~, ~running_turns~ (how many the agent has, which is what Stop ends), ~step_count~ and ~steps~ -- that agent's most recent steps in that room since the turn began, at most =CLAWT_ACTIVITY_STEPS=, in the shape ~room.steps~ uses.

Nothing in it is kept for the purpose. Which turns are running is each agent's typing set, already cleared wherever a turn can end, the runtime exiting included; the steps are the rooms' bounded history. A turn with no room named is listed with an empty ~room~.

~steerable~ is TRUE only for the agent's direct room with the operator, which is where ~msg.send~ folds a correction into a running turn. Stop is ~agent.interrupt~, below, and ends every turn the agent has.

**** agent.interrupt

~agent.interrupt~ (~agent~) → ~interrupted~, ~killed~.

Ends what the agent is doing *now* and leaves the agent up. It is not a
smaller ~agent.stop~ --- it is a different thing entirely:

| | ~agent.interrupt~ | ~agent.stop~ |
|---+---+---|
| the AI CLI mid-turn | killed | killed with everything else |
| the libreclaw process | keeps running | stopped |
| its container or VM | untouched | stopped |
| its link, session, mailbox | kept | dropped, and the session resumes on start |
| afterwards | it is idle, message it | it needs ~agent.start~ |

A turn is carried out by an AI CLI that the agent's libreclaw spawned,
and that CLI spawns whatever the model asked for --- a build, a test run,
a search. All of it sits below the agent's own process in the process
tree and none of it is clawtilla's child, so the daemon walks ~/proc~ for
the descendants of the agent's pid rather than using ~GSubprocess~, which
knows only about the one process it started.

Killing the CLI is what actually ends the work. Cancelling libreclaw's
own ~GCancellable~ --- which is what its ~!stop~ command does --- makes
~g_subprocess_communicate_async()~ abandon the read and leaves the
process running, so the model goes on burning tokens against a wait
nobody is holding. Coming at it from the process side is the half that
ends it; libreclaw then sees its child exit and finishes the turn on its
own.

~killed~ is the number of processes signalled, and it is in the reply
because zero and several mean different things to whoever pressed the
button: nothing was running, or that much was. Zero is not a failure ---
an agent between turns has no CLI --- so the frame answers ~interrupted:
true~ either way and the clients say which happened rather than reporting
"stopped" over an agent that was already idle.

A zombie is not counted. The CLI that has just exited stays in ~/proc~
until libreclaw reaps it, and ~kill()~ on a zombie succeeds while doing
nothing, so a count that trusted it answered ~killed: 1~ for an agent
that was already between turns. ~clawt_process_has_exited()~ reads the
~State:~ line and the interrupt skips ~Z~ and ~X~.

Every pid is re-checked against the agent's process tree immediately
before it is signalled. A pid read a moment earlier may have exited and
been reused by then, and what inherits a recycled pid belongs to somebody
else; on a busy machine that is the difference between stopping an agent
and killing the operator's editor. SIGTERM first, then SIGKILL after a
short grace period, deepest process first --- a parent killed before its
children hands them to init, where they are no longer reachable from the
agent at all.

The daemon marks the agent idle itself rather than waiting for
libreclaw's typing indicator to drop. Killing a turn mid-flight is the
one case where that frame may never arrive, since the code that sends it
runs when the turn finishes and the turn was just taken out from under
it. An agent that shows as working for ever after somebody pressed stop
is precisely the state the button exists to get out of.

It is refused, naming the runtime type, for an agent that has no such
tree: an embedded agent takes its turn inside the daemon, where the only
process to signal is the daemon itself. That is a capability
(~interrupt~ in ~caps~), so a client can tell before it offers the
button, and the refusal exists for the client that does not ask.

~agent.remove~ takes ~remove_computer~: %TRUE tears the agent's
container or VM down before removing it, forcing it if it is running.
Off by default. The reply carries ~computer~ saying what happened, or
omits it when there was nothing to remove.

Booleans in a payload may be sent as real JSON booleans or as the
strings "true"/"false" -- both bundled clients build payloads from
string pairs, and a flag sent as a string used to read as the default,
which is the worst failure a boolean can have: the request succeeds and
does the other thing.

~agent.files~ (~agent~) → ~workspace~ and a ~files~ array of
{~name~, ~path~, ~title~, ~identity~, ~generated~, ~exists~}.  ~identity~
says whether the file reaches the system prompt; ~generated~ says
clawtilla writes into it as well as you, which today means ~.mcp.json~
and nothing else.  Missing files are scaffolded before the reply, and
~.mcp.json~ is written too, so a client can offer to edit an agent that
has never been started.

~agent.files~ answers with paths and not contents, because a terminal
client wants to hand the path to ~$EDITOR~ rather than round-trip the
bytes.  A client with nowhere to spawn an editor reads and writes them
instead: ~agent.file_read~ (~agent~, ~name~) → ~name~, ~path~,
~content~, and ~agent.file_write~ (~agent~, ~name~, ~content~) →
~path~, ~bytes~, which also publishes ~agent.changed~.

A file that is not there yet reads as empty rather than as an error.  The
standard set is scaffolded at first start, so asking for one before then
is an ordinary thing to do, and an editor that refused to open a file it
is about to create would be a strange editor.

The ~name~ is a plain file name and the daemon checks that it is: no
separator, no ~..~, not empty and not ~.~.  It is reached from an IPC
request, so the name is whatever the client sent, and
~../../agents/other/credentials~ is a perfectly good relative path that
would hand one client another agent's secrets.  ~g_path_is_absolute()~
alone does not stop it.

~agent.avatar~ (~agent~) → ~mime~, ~bytes~, ~base64~ and ~etag~ --- the
profile picture, as bytes and never as a path, for the same reason
~attachment.get~ already gives: a client may be on another machine
entirely, so a filename would work on this host and show nothing
anywhere else.  It resolves ~agents.avatar~ against the workspace when
set, falls back to a ~profile-picture.png~/~.jpg~/~.jpeg~/~.webp~
found directly in the agent's own directory, and refuses with
~NOT_FOUND~ when there is neither.  The type comes from sniffing the
bytes' own magic numbers, never from the file's name, and a file over
~defaults.avatar_max_bytes~ is refused by name rather than served
truncated.  ~etag~ is a SHA-256 of the bytes, so a client can cache the
decoded texture per (agent, etag) and know when to throw it away.

~agent.avatar_set~ (~agent~, ~data~) writes a new picture from
base64-encoded bytes --- there is deliberately no path parameter, so a
client cannot ask the daemon to read an arbitrary file off its own disk
and hand the bytes back as this agent's face.  The stored extension
comes from sniffing ~data~, never from anything the client claims, and
a payload that is not a recognised image is refused before anything is
written.  ~agents.avatar~ is left unset, so the picture is found through
the same auto-detection as one dropped in by hand.  Publishes
~agent.changed~.

~agent.avatar_clear~ (~agent~) removes the auto-detected picture and
answers with ~removed~ --- %TRUE if a file was actually there to take
away.  Publishes ~agent.changed~ only when it removed something.

~agent.reset~ (~agent~) clears the agent's AI session and answers with
~sessions_cleared~, ~moved~ and ~restarted~.  It stops the agent if it
was running, moves its ~sessions~ directory aside with a timestamp rather
than deleting it -- a reset is what you reach for when something is
wedged, which is exactly when you might want to look at what it was
doing -- clears the session rows from libreclaw's own database, forgets
the usage watermark, and starts the agent again if it had been running.
Both places have to be cleared: libreclaw restores a session from the
persist directory *or* from sqlite, so clearing one leaves the agent
resuming from the other and looking like the reset did nothing.

This is also the only thing that applies an identity change.  An AI CLI
is not handed a system prompt when it *resumes* a session, so editing
~SOUL.org~ or repointing ~persona.identity_files~ reaches a running
agent's files and not its prompt.  Restarting is not enough.

~agent.discover~ takes no payload and answers with ~found~: directories
under the state root and the workspace root that look like an agent and
are not in the configuration, each with ~id~, ~path~, ~kind~ (~state~ or
~workspace~), ~holds~ (which of ~mailbox.db~, ~memory.db~,
~config.yaml~, ~SOUL.org~, ~IDENTITY.org~ and ~AGENTS.md~ are in there)
and ~modified~.  They accumulate: an agent removed from the config keeps
its state, a design that was never committed leaves a workspace, and a
config restored from a backup leaves everything it did not mention.
None of that was visible anywhere.

~agent.forget~ (~id~) is what answers a discovery.  It renames both
directories to ~<path>.discarded~ and answers with ~moved~, and
~agent.discover~ skips a ~.discarded~ suffix so the same question is not
asked twice.  Moved rather than deleted: this is somebody's agent, and "I
never created this" is a thing people say about directories they later
want back.  It refuses an id the configuration still has, naming
~agent.remove~ instead.

~agent.import~ (~id~, ~from~, ~mode~, ~keep_git~) adopts an existing
workspace and answers with ~id~, ~workspace~, ~files~, ~mode~ and
sometimes ~detail~.  ~mode~ is ~copy~, ~link~ or ~git~ and an
unrecognised one is *refused* rather than defaulted -- somebody who typed
~--lnik~ would otherwise get a fork of their workspace instead of a link
to it, and find out only when their edits stopped reaching the agent.  A
git import names a URL rather than a directory, which is why ~detail~
exists: whether it became a submodule depends on where the workspace root
is, and a workspace somebody's ~git status~ tracks is different enough
from one it does not to be worth saying.

An import adopts what the source already said about itself.  Its
~config.yaml~ carries a provider and a model, and dropping them would
quietly move the agent onto the fleet defaults; its persona is in
markdown where clawtilla's is in org, and the two sets do not collide --
so the copy brought a complete persona across and the scaffolder then
wrote a blank ~.org~ beside every file of it.  The agent loaded the
blanks.  ~persona.identity_files~ is set from what is actually there, and
only when nothing was configured on the frame.

An agent object carries id, name, description, state, detail, caps,
whether it is the chief, whether it is connected, its computer type,
model, mailbox depth, and its credentials *by reference*.

*** memory.*

~memory.list~ and ~memory.search~ both take an ~agent~, a ~category~ and
a ~limit~ (20 by default); ~memory.search~ takes a ~query~ as well.  They
answer with ~total~ -- the whole store, not the page -- and ~memories~,
each carrying ~id~, ~content~, ~summary~, ~category~, ~importance~,
~tags~, ~pinned~, ~created_at~ and ~access_count~.  ~memory.list~ also
takes ~pinned~ to show only those.

An agent with ~memories.enabled~ off has no store, and that is answered
as ~CLAWT_ERROR_NOT_SUPPORTED~ naming the key rather than as an empty
list -- an empty result and a feature that is switched off look identical
from a client, and only one of them is worth acting on.

Each memory also carries ~scope~ -- ~agent~, ~team~ or ~fleet~ -- saying
which database it was read out of.  A listing that mixed an agent's own
conclusion with something the whole fleet believes and did not say which
was which would have turned two different claims into the same row.

This is ~memories.*~, the searchable per-agent sqlite store, and not
~agents.memory~, which is libreclaw's ~MEMORY.md~ size budget.  The two
are unrelated and the plural is the whole distinction.

~memory.journal~ (~agent~, optional ~limit~, default 50, at most 500) →
~agent~, ~keep~ (~memories.journal_keep~) and ~entries~, newest first
across the agent's own database and its own changes in its team's and the
fleet's.  Each entry carries ~id~ (the row, unique within its database),
~scope~, ~at~ (unix seconds), ~action~ (~add~, ~forget~, ~pin~, ~unpin~,
~undo~), ~memory_id~, ~actor~, ~excerpt~, ~line~ (the sentence from
=clawt_memory_journal_describe()=), ~undoes~ on an undo row, ~undone_at~,
~undone_by~, ~undoable~ (a JSON boolean) and ~why_not~ when it is not.
An agent with ~memories.enabled~ off is ~CLAWT_ERROR_NOT_SUPPORTED~.

~memory.undo~ (~agent~, ~scope~ -- ~agent~ by default -- and ~id~) →
~undone~.  Refused with the store's sentence for a row that cannot be
undone, ~CLAWT_ERROR_NOT_FOUND~ for one older than the journal keeps, and
~CLAWT_ERROR_PERMISSION_DENIED~ for a row in a shared database that this
agent did not make.  Publishes ~memory.changed~.

~memory.proposals~ (~agent~) → the periodic review's state and open
proposals (~memories.review.*~): ~agent~, ~enabled~ (a JSON boolean: a
model is named), ~model~ (the stored ~provider/model~, ~""~ for off),
~model_label~ (=clawt_ack_check_model_label()=), ~interval_hours~,
~last_run_at~ (unix seconds, 0 never), ~running~ (a pass for this agent
is in flight), ~last_error~ when the last pass proposed nothing because
it failed, timed out or answered something unreadable, and ~proposals~.
Each proposal carries ~id~ (~p~ and sixteen hex digits), ~kind~
(~merge~, ~forget~, ~pin~, ~unpin~), ~kind_label~
(=clawt_memory_proposal_kind_label()=), ~line~
(=clawt_memory_proposal_describe()=), ~content~ (a merge's text),
~reason~ (the model's, clipped to one line), ~created_at~, and
~memories~: each named memory's ~id~, its ~excerpt~ as it is now, and
~present~ (a JSON boolean; false once it was forgotten since).

~memory.proposal_accept~ (~agent~, ~id~) → ~accepted~.  Applies the
proposal through the journaled store as ~operator~
(=clawt_memory_proposal_apply()=) and takes it off the list; a proposal
naming a memory that was forgotten since is refused with
~CLAWT_ERROR_NOT_FOUND~ and stays listed, so it can be read and
rejected.  ~memory.proposal_reject~ (~agent~, ~id~) → ~rejected~,
changing nothing.  Both publish ~memory.changed~.

~memory.review~ (~agent~) → ~started~: one pass now, refused while the
review is off, while any pass is running, or for an agent with fewer
than two memories.  ~memory.review_set~ (~model~ and/or
~interval_hours~) → both as saved: the fleet's ~memories.review.model~
(~provider/model~ or ~""~) and ~memories.review.interval_hours~ (1 to
720), validated and saved like ~orchestration.set~.

~memory.recall~ (~query~, and optionally ~agent~, ~days~ and ~limit~) →
~hits~, ~full_text~ and ~indexed~.  This searches the *transcript*, not
the memories: every message the fleet has routed, across every room and
every session, out of ~<state_dir>/transcripts.db~.  Each hit carries
~id~, ~room~, ~from~, ~from_name~, ~body~ and ~at~ (unix seconds).

A client's recall is not room-filtered, because a person can already open
any transcript in the state directory.  An *agent* asking through
~clawtilla_recall~ is held to the rooms it is a member of, and that is a
filter on the query rather than on the result -- a hit fetched and then
dropped would still have spent the caller's limit.

~full_text~ says whether the search was FTS5-ranked or a substring scan,
so a thin result can be told apart from a sqlite built without FTS5;
~indexed~ says how many messages there are at all, so "nothing matched"
can be told apart from "nothing has been said yet".  A query with no
letters or digits in it is refused with ~CLAWT_ERROR_INVALID_ARGUMENT~
rather than answered with an empty list: quoted as an FTS5 phrase it
would match nothing anywhere, and "no matches" is what an empty store
says too.

*** operator.*

~operator.get~ → ~text~, ~path~, ~enabled~ and ~learned~.  The model of
the person the fleet works for, in two halves: ~text~ is the file at
~<state_dir>/OPERATOR.org~, which a person writes, and ~learned~ is the
fleet-scope memories filed under the ~operator~ category, which agents
write.  Each learned entry carries ~id~, ~content~, ~source~ and
~created_at~.

They are returned separately rather than merged, because only one of them
is editable and a client that could see only the merged text would have
to guess which lines it may offer to change.  ~enabled~ is
~memories.operator_profile~: off means no agent is told any of it, which
a client has to be able to say rather than showing an editor for a file
nothing reads.

~operator.set~ (~text~) → ~path~ and ~refused~.  Replaces the written
half and re-renders every agent's ~USER.org~ at once -- a correction that
reached no agent until the next daemon start is a correction somebody
makes twice.

*** tool.*

~tool.rpc~ (~agent~, ~token~, ~request~) → ~response~.  Takes one MCP
JSON-RPC request and returns the JSON-RPC response, so the orchestration
tools have one implementation and ~clawtilla-mcp-server~ cannot drift
from it.

The agent's own token is required -- the same one the link uses.  The
socket's permissions are the first line; this stops one agent on this
machine calling tools as another.

*** msg.* and room.*

~msg.send~ (~target~, ~body~, ~from~) → ~queued~, the number of mailboxes
it went into, and ~target_state~ when ~target~ names an agent.

~target_state~ is the agent's state at the moment the message was
enqueued.  A stopped agent accepts mail -- that is what makes the
mailbox worth having -- but nothing is going to read it until the agent
starts, and a client that cannot tell the two apart shows a progress
indicator that never resolves.  Both bundled clients say so instead: the
CLI prints "held in the mailbox until the agent starts", and the GTK
client raises a toast and leaves the activity line clear.

A room has one state per member, so there is no single honest answer and
the key is omitted rather than guessed at.

~room.list~, ~room.create~, ~room.set~, ~room.add~, ~room.remove~,
~room.history~, ~room.steps~, ~room.read~.

Each room in ~room.list~ carries ~declared~ (somebody made it) and, since incidents, ~incidents~ (a JSON boolean: it is a team's *Problems to look at* room, ~incidents:<team>~ or ~incidents:+fleet~).  Which rooms get a sidebar row is =clawt_room_is_listed()=, the same in every client: the declared ones and the incidents ones.

~room.create~ takes ~room~, an optional ~name~, comma-separated
~members~ and an optional ~require_mention~.  It writes a ~rooms:~ entry
*and* makes the room, because writing the config is not creating the
room --- and a room that lived only in the running daemon was one
somebody made in a client, used, restarted, and could not find, with its
transcript still on disk and nothing that would ever reopen it.

Omitting ~require_mention~ is the ordinary case: the room then resolves
it from its own shape, which is what somebody editing ~clawtilla.yaml~
by hand gets too.

~room.set~ takes ~room~ and any of ~name~, ~members~,
~require_mention~ and ~max_chain~.  A ~members~ list *replaces* the
membership rather than adding to it, so it is how somebody is taken out
of a room as well as put in.  ~max_chain~ is an *integer*, 0 (no cap) to
100 --- how many replies one thread of a round may run to
(=rooms.max_chain=); anything else is refused with
~CLAWT_ERROR_INVALID_ARGUMENT~ rather than wrapped.

~room.list~ entries carry ~round~ (the round the room is in, 0 before
the first) and ~max_chain~ beside ~require_mention~.

~room.remove~ takes ~room~ and answers ~transcript_kept: true~.
Removing a room is a configuration change; destroying the record of what
was said in it is not, and is not recoverable.  It is reported because
nothing will reopen that file on its own --- only ~dm:~ transcripts are
restored at start.

*~room.set~, ~room.add~ and ~room.remove~ refuse a derived
conversation* --- anything named ~dm:~, ~routine:~ or ~trigger:~.  Those
have no config entry: their members follow from who exists, so removing
one deletes nothing and it returns the moment the pair speaks again.
More sharply, ~room.add~ would otherwise put a third member into
~dm:oryx:user~, and membership *is* permission --- that agent could then
read and post into the operator's private conversation with another.

~room.history~ accepts an agent id as well as a room id: an agent id
means the direct room with that agent, the same way it does for
~msg.send~.  Pass ~as~ to say who is asking; it defaults to ~user~.

**** Read marks: ~room.read~, and ~unread~ / ~read_upto~ (since 0.52.0)

The daemon holds one *read mark* per room -- the last message the operator has read in it -- in ~<state_dir>/reads.db~, and every unread count is derived from the room's history and that mark when it is asked for.  The counts every client draws come from here, so reading in one client clears the count in all of them and a restart forgets nothing.  See "Unread" in [[file:clients.org][clients.org]].

Each ~room.list~ entry gains:

| member | what it is |
|--------+------------|
| ~unread~ | messages after the mark sent by anybody but ~user~ (an integer) |
| ~read_upto~ | the id of the last message read, or ~""~ for a room nobody has read |

~room.history~ gains ~read_upto~, the same value, read *before* the client marks the room read on opening it -- it is where the "New messages" rule goes (=clawt_unread_rule_index()=).  Both members are absent when the store could not be opened; a client takes that as "keep counting from events", which is what every client did before 0.52.0.

~room.read~ moves a mark:

#+begin_src json
{"v":1,"id":"7","kind":"room.read","payload":{"agent":"zed"}}
{"v":1,"id":"7","kind":"response","payload":{"room":"dm:user:zed","read_upto":"01jc8w4m5ae7qz3t9hxk","unread":0}}

{"v":1,"id":"8","kind":"room.read","payload":{"room":"standup","upto":"01jc8w4m5ae7qz3t9hxk"}}
{"v":1,"id":"9","kind":"room.read","payload":{"all":true}}
{"v":1,"id":"9","kind":"response","payload":{"marked":3}}
#+end_src

- ~room~ names a room, or an agent id meaning the operator's direct room with it (the ~room.history~ resolver).  ~agent~ names an agent explicitly; its direct room is named by =clawt_room_manager_direct_id()= -- ~dm:user:zed~ for an agent ~zed~, ~dm:alice:user~ for ~alice~, because the two ids are sorted -- so no client ever spells one.  An unknown agent is ~not_found~.
- ~upto~ is the id of the last message read; without it, the newest message.  It must be a message the room holds, or the request is ~not_found~: a mark that named nothing would fall back to a timestamp a client could set to any second, swallowing every message until then.
- *A mark never moves backwards.*  Two clients reading the same room can report in either order; a mark behind the one held -- by position in the history, or by timestamp when the held message is gone -- is not written.  The reply and the event still go out, carrying the room's real count.  Not by id: ids sort by time only to the millisecond.
- ~all: true~ marks every room that has anything unread, up to its newest message, and answers ~marked~, how many it touched.
- An empty room has nothing to mark; the request succeeds and nothing is written.
- ~not_supported~ when the store could not be opened.

The reply carries ~room~ (what was resolved), ~read_upto~ and ~unread~ (what is left after the mark, 0 unless ~upto~ stopped short of the newest message).

Every room marked publishes a ~room.read~ event whose subject is the room, with ~room~, ~upto~ (the mark as it now stands) and ~unread~ (an integer).  Every client zeroes -- or sets -- that room's pill on it, which is how a read in one client clears the badge in every other one.

The count itself (=clawt_room_count_unread()=): walk back from the newest message to the marked one and count the messages not sent by ~user~; when the marked message is no longer in the history, count those stamped after the mark's second.  A room with no mark counts all of them.  The first time ~reads.db~ is created the daemon marks every existing room read at its newest message, so an upgrade does not light up the fleet's whole history.

~room.steps~ takes the same ~room~ and ~as~ pair, through the same
resolver, and answers with the steps that room has seen: an array of
~steps~, oldest first, plus the ~room~ it resolved.  Pass ~live: true~
to narrow it to the turn currently running --- the steps taken since the
room's last message.  A client that draws steps both interleaved through
a transcript and again as a live tail needs that boundary decided in one
place, or the turn that just finished is drawn twice.

Each entry carries ~step_kind~ (~text~, ~thinking~, ~tool~ or
~status~), ~room_id~, the ~agent~ whose turn it is, and then whichever
of ~text~, ~tool~ and ~detail~ apply.

~status~ is for notices libreclaw writes itself -- that steps were
dropped, say.  A provider's own status lines are *not* forwarded: the
kind is documented as having no fixed vocabulary, and Claude Code
emits one per protocol line, so a four-tool turn put ~claude: init~,
~claude: task_started~ and ~claude: task_notification~ into the
conversation seven times.  There is no filter to write for that either,
since the vocabulary is per provider and undeclared.  ~failed~ is a *JSON boolean* and
is present on every entry.

An empty array is the ordinary answer, not a failure.  A room with no
turn running has no steps, and neither does one whose agent has not
reached a tool yet -- so this is safe to call on every refresh.  A room
that does not resolve answers the same way rather than refusing, because
a handler that calls an ordinary condition an error stacks one toast per
refresh over whatever is underneath it.

The list outlives the turn: steps stay in the conversation where they
happened, so a client rebuilding a room merges them back in on ~ts~.
It is *not* the transcript, though --- steps are never messages, because
the last thing in a thread is what a finished turn's task result is
inferred from.  It is held in memory, bounded per room, and gone when
the daemon stops.

*** notice.* (since 0.52.0)

The fleet's notification list, held by the daemon (=src/core/daemon-notice.c=, =core/clawt-notice-store.h=) in ~<state_dir>/notices.db~, which every client draws its bell and its notifications panel from.  The daemon listens to its own bus: each event ~clawt_alert_tier_for_event()~ rates an error or a notice becomes a row, worded by ~clawt_alert_text_for_event()~.  Routine events are not recorded -- they are the event log's (~event.list~).  See docs/clients.org, "Notifications".

| kind | payload | reply |
|------+---------+-------|
| ~notice.list~ | ~agent~?, ~include_dismissed~? (false), ~limit~? (200) | the list, below |
| ~notice.read~ | ~id~, or ~all: true~ | ~read~: how many changed |
| ~notice.dismiss~ | ~id~ | ~dismissed: 1~; ~not-found~ for an id not showing |
| ~notice.clear~ | ~agent~? | ~cleared~: how many were dismissed |
| ~notice.mute~ | ~agent~, ~until~? (Unix seconds; absent or 0 for "until unmuted") | ~agent~, ~muted~ |
| ~notice.unmute~ | ~agent~ | ~agent~, ~muted~ |

An ~id~ or ~until~ may be a JSON number or a numeric string: the GTK and libregnum clients build payloads of strings.  ~notice.mute~ refuses an agent the config does not have (~not-found~) and an ~until~ already past (~invalid-argument~).  A daemon whose ~notices.db~ would not open answers every verb but ~notice.list~ with ~not-supported~, and ~notice.list~ with ~kept: false~.

#+begin_src json
{"v":1,"id":"4","kind":"notice.list","payload":{}}
{"v":1,"id":"4","kind":"response","payload":{
  "kept":true,
  "notices":[{"id":42,"agent":"scout","tier":"error","kind":"turn.timed_out",
              "source":"turn.timed_out","subject":"scout",
              "title":"turn.timed_out · scout","created_at":1763532000,
              "read":false,"dismissed":false,"muted":false}],
  "mutes":[{"agent":"zed","until":1763539200}],
  "chats":[{"room":"dm:scout:user","agent":"scout","name":null,"unread":2}],
  "decisions":[{"id":"8c1e…","agent":"lead","question":"Ship it tonight?"}],
  "grok":[{"id":"job-3","agent":"scout","bot":"research","state":"Failed",
           "note":"the page would not load","remove_question":"…"}],
  "sources":{"chats_unread":2,"decisions_pending":1,"grok_attention":1},
  "unread":1,"total":5}}
{"v":1,"id":"5","kind":"notice.mute","payload":{"agent":"zed","until":"1763539200"}}
{"v":1,"id":"6","kind":"notice.read","payload":{"all":true}}
{"v":1,"id":"7","kind":"notice.dismiss","payload":{"id":42}}
#+end_src

The reply's members:

- ~notices~: newest first; ~tier~ is ~error~ or ~notice~; ~source~ is where to look (the event kind, or ~download~ / ~message~ for the two said in a sentence of their own); ~agent~ is who a row narrows to and is muted by; ~created_at~ is when the event happened, in seconds.  Narrowed by ~agent~ when one is given.
- ~mutes~: every mute in force -- a timed one whose ~until~ has passed is gone from here at once, whether or not a prune has removed it.
- ~chats~, ~decisions~, ~grok~: the three other things that want somebody -- the operator's conversations and group rooms with unread messages (from the read marks), open decisions, and Grok jobs needing attention by the rule the Grok badge uses (=grok.attention_days=).  A muted agent's are left out of all three; ~grok~ entries carry ~remove_question~, the confirmation to ask before ~grok.remove~ (=clawt_grok_job_remove_question()=).
- ~sources~: the three counts; ~unread~: alerts neither read nor dismissed, less the muted agents'; ~total~: their sum, which is the bell (=clawt_notice_list_badge()= adds the same four).

Every verb that changes something publishes ~notice.changed~ (subject the agent, when there is one; details ~reason~ -- ~added~, ~read~, ~dismissed~, ~cleared~, ~muted~ or ~unmuted~ -- and ~id~).  A recorded notice publishes it too (~added~), and so does a timed mute lapsing (~unmuted~, from a timer the daemon arms for the soonest ~until~).  Every client asks for ~notice.list~ again on it.

A mute also stops the push and desktop notifiers for that agent: every notification the daemon raises goes through ~clawt_daemon_notify()~, which skips a muted agent.

Pruned at start and hourly to =notices.keep= (500 newest) and =notices.keep_days= (30), and lapsed mutes dropped.

*** orchestration.*

~orchestration.get~ → ~ack_check_model~ (the stored
~orchestration.ack_check_model~, ~""~ for off) and
~ack_check_model_label~ (how to show it: "Off", a catalogue label, or a
value typed into the file shown as itself).

Since 0.18.0 the reply also carries ~tree_message_budget~ (an integer,
=orchestration.tree_message_budget=), ~max_hops~ (the fleet's, for a page
that explains one limit beside the other), and ~rooms~: one object per
group room with an entry in ~rooms:~ --- ~id~, ~name~, ~max_chain~,
~max_hops~ (the room's override, 0 for none) and ~round~ --- so the
Orchestration page is one request.  A pair has no rounds and a derived
room has no entry to write to, so neither is listed.

~orchestration.set~ takes ~ack_check_model~, ~tree_message_budget~, or
both; at least one.  It writes what it was given, saves the file,
publishes ~config.changed~ and answers as ~orchestration.get~ does.
~tree_message_budget~ is an *integer* from 0 (off) to 10000 and reaches
the loop guard at once, not at the next reload.
~""~ turns the acknowledgement check off.  A value that is not ~provider/model~ is
refused with ~CLAWT_ERROR_INVALID_ARGUMENT~, so a client cannot save
something the daemon would then warn about and ignore; a model the
catalogue does not list is accepted, because the catalogue goes stale.
A client offers the choices by walking ~clawt_ack_check_model_count()~
/ ~_nth_value()~ / ~_nth_label()~, never a copy of the list.

*** task.*

~task.list~, ~task.show~, ~task.cancel~, ~task.retry~.

Tasks and incidents are kept in ~tasks.db~ across restarts (since 0.35.0; docs/tasks.org, "Tasks are kept, and survive a restart").

~task.list~ with no options is the live set: every task that has not finished and those that finished in the last day, oldest first.  With ~history: true~ it is every task the store still holds, *newest* first, one page: ~limit~ (default 100, at most 1000), ~before~ (a Unix time; only tasks created before it -- pass the last task's ~created_at~ for the next page), ~state~ (a task state nickname; anything else is =INVALID_ARGUMENT=) and ~agent~ (the assignee).

Both forms answer:
- ~since~ (since 0.29.0): when this daemon started, as a Unix time.  ~incident.list~ carries it too.
- ~kept~ (since 0.35.0): whether this daemon keeps tasks on disk.  False for a daemon whose ~tasks.db~ would not open, which then holds them in memory only.
- ~retention_days~ (since 0.35.0): ~orchestration.task_retention_days~.

Every client words the three through =clawt_task_list_caption()=: with ~kept~, "Tasks still open, and those that finished in the last day. Every task is kept for 180 days ...", and without it the older in-memory sentence (=clawt_held_since_caption()=).  A reply without ~kept~ (an older daemon) is read as false.

~task.show~ takes ~task~ and, optionally, ~journal: true~, which adds ~journal~: the task's history, oldest first, each entry ~at~ (Unix time), ~state~ (nickname) and, when one was recorded, ~what~.  It answers for a task that has left the live set too, read back from the store.

A task object carries (since 0.35.0) ~title~ (the given title or the first line of the prompt), ~created_at~, ~started_at~ and ~finished_at~ (Unix times; the last two only once they happened), ~room~ (the conversation it was delegated from) and ~cancelled_by~.

A task object carries ~retries~ and ~retried_by~ once it has been retried, and not before.

~task.create~ (since 0.36.0) takes ~prompt~ (required), ~title~ and ~agent~.  Without ~agent~ the task goes on the backlog as ~unassigned~; with one it is created ~pending~ and sent to that agent as the operator's.  An unknown agent is =NOT_FOUND=; no prompt is =INVALID_ARGUMENT=.  It answers ~task~, the task object.

~task.assign~ (since 0.36.0) takes ~task~ and ~agent~: an ~unassigned~ task becomes ~pending~ with that assignee and is sent to them.  Any other state is =INVALID_ARGUMENT= (a task somebody has moves with a handoff).  It answers ~task~.

~task.create~ also takes ~after~ (since 0.37.0): task ids, comma- or space-separated, that the new task waits for.  While any of them has not completed it is ~blocked~; with an ~agent~, its delivery is kept and sent as the operator's when the last one completes.

~task.create~ takes ~review~ (since 0.38.0): ~lead~, ~delegator~ (the operator), ~operator~, an agent id or ~none~; without it the assignee's ~agents.review_by~ applies.  A spelling that names nobody, or names the assignee, is =NOT_FOUND= / =INVALID_ARGUMENT= and makes no task.

~fleet.export~ (since 0.42.0) takes ~dir~ (absolute, on the daemon's machine; absent or empty) and answers counts of ~agents~, ~teams~, ~routines~, ~triggers~, ~projects~, ~skills~ and ~files~ written, and ~to_fill~.  ~fleet.import_preview~ takes ~dir~ and answers ~items~ (each ~kind~, ~id~, ~exists~ and ~dangerous~, the dangerous settings it turns on) and ~to_fill~.  ~fleet.import~ takes ~dir~, ~resolutions~ -- an object, or the string =kind:id=what,...=, each ~skip~, ~replace~ or ~rename:<id>~; an existing item is skipped unless told -- and ~allow_dangerous~, and answers ~taken~ (=kind:id= as each now is).  An item that turns on a dangerous setting without ~allow_dangerous~ is =PERMISSION_DENIED= and nothing is taken.

~revision.list~ (since 0.41.0) takes optional ~kind~ (~config~, ~persona~, ~skill~), ~subject~ and ~limit~ (default 100), and answers ~revisions~: each with ~id~, ~kind~, ~subject~, ~at~, ~author~, ~note~ and ~bytes~, newest first, without the text.  ~revision.show~ takes ~id~ and answers it with ~text~.  ~revision.diff~ takes ~from~ and, optionally, ~to~ (another revision of the same thing; =INVALID_ARGUMENT= otherwise), and answers ~diff~, a unified diff -- against how the thing reads now when ~to~ is absent.  ~revision.restore~ takes ~id~, puts that version back through the path an edit takes (the config is parsed first and reloaded after), and answers ~restored~.  Ids may be sent as numbers or strings.

~skill.tests~ (since 0.41.0) takes ~skill~ and answers ~tests~ (each ~name~, ~input~, ~agent~ and ~last~: ~at~, ~state~ -- ~running~, ~passed~, ~failed~, ~error~ -- ~detail~, ~revision~, ~agent~, ~task~) and ~problems~ (test files that could not be used).  ~skill.test_run~ takes ~skill~, optionally ~test~ (one by name) and ~agent~ (else each test's own), and answers ~runs~: each ~test~, ~task~, ~agent~ (since 0.50.0 the scratch agent the run is on) and ~as~ (the agent it copies).  No agent named is =INVALID_ARGUMENT=, as are an agent in a VM and a skill not in effect even for a copy given it alone; an unknown agent is =NOT_FOUND=.  See docs/skills.org.

~project.list~ (since 0.40.0) answers ~projects~: each with ~id~, ~name~, ~directory~, ~goal~, ~review_by~, ~agents~, ~monthly_budget_usd~, ~budget_warn_percent~, ~budget_hard_stop~, ~month_spend_usd~ (its tasks made this calendar month) and ~stopped~ (a hard stop that has been reached).  ~project.create~ takes ~project~ (the id) and any of those fields, as strings; ~project.set~ takes ~project~, ~key~ and ~value~ (empty removes the key; a bad number is =INVALID_ARGUMENT=; the id cannot be changed); ~project.remove~ takes ~project~.  All three save the config, rewrite every agent's =PROJECTS.org= region, publish ~project.changed~ and answer ~project~ with any render refusals.

~task.create~ takes ~project~ (since 0.40.0): an id, or left out for the one the task's repository matches.  An unknown one is =NOT_FOUND=; a project whose ~budget_hard_stop~ has been reached is =LOOP_LIMIT=; either way no task is made.  A task object carries ~project~ when it has one.

~task.create~ takes ~repo~ and ~base~ (since 0.39.0): an absolute host path to a git repository, and the ref to start from (its =HEAD= when left out).  The task gets a checkout of its own in its assignee's workspace; without an ~agent~ that is =INVALID_ARGUMENT=, and a path or ref that cannot be checked out refuses the task with git's words.  A task object then carries ~checkout~: ~repo~, ~path~, ~branch~, ~base~, ~mode~ (~worktree~ or ~clone~) and ~present~.

~task.diff~ (since 0.39.0) takes ~task~ and answers later (deferred): ~diff~ (=git diff= against the base, committed and uncommitted together), ~untracked~ (new files, by name), ~truncated~ (cut at 512 KiB) and ~from_branch~ (the checkout is gone, so this is the branch the repository kept).  A task without a checkout is =NOT_FOUND=.

~task.checkout_remove~ (since 0.39.0) takes ~task~ and ~force~: removes the checkout and keeps its branch.  =INVALID_ARGUMENT= while the task is pending or running, and without ~force~ while the checkout has uncommitted changes.  It answers ~task~.

With the VENTURE mirror on (since 0.44.0), ~task.show~ also answers ~venture~ once the mirror has looked at the task: ~state~ (~synced~, ~queued~, ~skipped~ or ~dead~), and as known ~ticket~ (its id), ~url~ (its page), ~instance~ (the connector) and ~reason~ (why it was skipped or given up on, or the last error while queued).  ~task.venture_retry~ takes ~task~: the task's given-up rows are queued again and a skipped task is looked at afresh; it answers ~task~ and ~queued~ (rows queued).  =NOT_FOUND= for no such task, =INVALID_ARGUMENT= when no venture connector has ~mirror_tasks~ on.  See [[file:venture.org][venture.org]].

~task.review~ (since 0.38.0) takes ~task~, ~verdict~ (~accept~ or ~changes~) and ~notes~ (required for ~changes~): the operator's verdict on a task in ~review~, whoever its reviewer is.  It answers ~said~ (what happened, in a sentence) and ~task~.  A task not in review is =INVALID_ARGUMENT=.  A task object carries ~reviewer~ and ~review_round~ when it has a reviewer.

~task.link~ and ~task.unlink~ (since 0.37.0) take ~task~ and ~after~ (one task id).  Linking holds a task on the backlog or adds to what a held task waits for; any other state is =INVALID_ARGUMENT=, as are a self-link and a link that would close a cycle.  Unlinking the last blocker releases the task.  Both answer ~task~.  A task object carries ~after~ and ~waiting_on~ (arrays of task ids) when it waits for anything.

~task.comment~ (since 0.36.0) takes ~task~ and ~text~ and adds an operator comment to the task's thread.  It answers ~note~ (the note's id) and ~delivered~ (a JSON boolean: whether the assignee was sent it -- true only for a ~pending~ or ~running~ task).  It publishes ~task.noted~ (subject the task id, details ~author~ and ~agent~), not ~task.changed~.

~task.show~ also carries ~notes~ (since 0.36.0): the thread, oldest first, each ~id~, ~at~, ~kind~ (~comment~, ~progress~, ~result~), ~body~ and, unless clawtilla wrote it, ~author~.

A task's ~state~ may also be ~unassigned~, ~blocked~ or ~review~ (since 0.36.0); a client classifies a state with =clawt_task_state_nick_is_cancellable()= and the other predicates rather than by name.  A backlog task has no ~assignee~ member.

~task.retry~ takes ~task~ (a task id) *or* ~incident~ (an incident id), and an optional ~reason~ the assignee sees with the work.  It is the operator's Retry: a ~failed~ or ~stalled~ task is re-queued for its assignee with its original work and ~retried_by: "user"~; a routine's run is run again.  It answers ~task~ (the task now carrying the work -- the same id for a re-queue, the new run's for a routine) and ~rerun~ (a JSON boolean, true for a routine).  Any other task state is =INVALID_ARGUMENT= with the reason, as is an incident whose agent could not start (its work is still queued); an unknown id is =NOT_FOUND=.  See docs/orchestration.org, "Incidents: broken runs reach the lead".

*** incident.*

~incident.list~ answers ~enabled~ (a JSON boolean, =orchestration.incidents.enabled=), ~to~ (=orchestration.incidents.to=, a nickname a client offers by walking =clawt_incident_recipient_count()= / =clawt_incident_recipient_nth()=) and ~incidents~, newest first: the open ones, or every one the daemon still holds with ~all: true~.  Each has ~id~, ~kind~ (~failed~, ~stalled~, ~unstartable~ or ~routine-failed~) and ~kind_label~ (=clawt_incident_kind_label()=), ~agent~, ~team~, ~room~ (its incidents room), ~run_room~, ~task~, ~routine~, ~reason~, ~log_lines~ (an array), ~recipient~ (absent when nobody was given it), ~note~ (why not), ~retried_by~, ~occurrences~, ~retries~, ~opened_at~, ~updated_at~ and ~delivered_at~ (microseconds; 0 for never), and three JSON booleans: ~queued~ (waiting for its recipient's turn to end, or for the router), ~resolved~, and ~retryable~ -- whether ~task.retry~ would be accepted now, decided by the daemon so no client guesses from state names.

~incident.configure~ takes ~enabled~ (a JSON boolean) and ~to~ (~lead~, ~chief~ or ~none~; anything else is =INVALID_ARGUMENT= rather than saved and read back as the default), writes them to ~clawtilla.yaml~, publishes ~incident.configured~, and answers both as they now stand.

Events: ~incident.opened~ and ~incident.updated~ (a repeat, a delivery, a retry) and ~incident.resolved~, each with the incident id as subject and details ~agent~ (the agent whose run broke, which is what a pod's scope is matched against), ~kind~, ~room~, ~occurrences~, and ~team~, ~task~, ~routine~ and ~recipient~ when there is one.  All three are routine-tier: the report is in the room, and a badge would be the same news twice.

Each task object carries, besides its id, parties, state and prompt,
two members present only when set (since 0.22.0):

- ~thread_room~ --- the room the work runs in when it was delegated with
  ~thread: new~ (~task:<id>~, a libreclaw session of its own).  A client
  offers to open it, beside ~clawt_task_thread_summary()~'s line.  The
  settle notice does not go there; it goes back to the room the
  delegation was made in.
- ~consult: true~ --- delegated with ~mode: consult~: the assignee's turn
  was offered no tool that acts, so the result is an answer.  Draw
  ~clawt_task_consult_label()~.

*** turn.rescue

~turn.rescue~ takes ~action~:

- ~list~ (the default; ~agent~ optional) → ~offers~, one per turn the
  daemon has offered to rescue: ~agent~, ~room~, ~seconds~ (silent for),

  room's running turn back to the queue with ~model~ on it, then
  interrupts the agent, whose settle delivers it again.  Refused when
  ~model~ is not one of the choices, when there is no running turn in
  ~room~, and when the turn has already acted outside the fleet.

Events, subject the agent: ~turn.no_reply~ (~room~, ~seconds~,

*** usage.*

~usage.summary~ (~since~, unix seconds, 0 for everything) → ~agents~, one
object per agent with ~id~, ~name~, ~turns~, ~input_tokens~,
~output_tokens~ and ~cost_micros~; plus a ~total~ of the same shape,
the ~since~ it was answered for, and ~task_budget_usd~ so a client can
show the cap beside the spend.

Cost crosses the wire in *micro-dollars as an integer*, not as a float.
It is summed across every agent, and a running total of floats disagrees
with itself depending on the order the agents happened to be visited in.

Since 0.8.0 it also takes ~days~ (1 to 92) and ~sort~ (~"cost"~, most first; otherwise the fleet's own order), and every agent carries ~last_turn_at~ (unix seconds, 0 for never), ~idle~ and ~idle_tone~ (=clawt_usage_idle_label()= and =clawt_usage_idle_tone()=, so a client does not decide what idle means), ~state~, ~idle_stop_hours~ and ~asleep~ (stopped by the daemon for being idle, and woken by the next message). An agent running on one of its fallbacks also carries ~failover~ and ~failover_message~, exactly as in ~agent.list~ (one daemon function writes both), so the Fleet page can badge it.  With ~days~, each agent has a ~daily~ array of cost per day and the reply a ~days~ array of ~{start, cost_micros}~, oldest first, the last being today from local midnight. The reply also carries ~now~ (the daemon's clock, for ages), ~idle_hours~ and ~daily_fleet_budget_micros~. A client older than this reads none of them and loses nothing.

~usage.providers~ (since 0.54.0; ~refresh~, boolean) → ~now~ (the
daemon's clock, unix seconds) and ~logins~, one object per login the
fleet uses: ~id~ (=<cli>:<account>= or =<cli>:default=), ~provider~
(the libreclaw CLI type), ~account~ (absent for a CLI's default login),
~description~, ~pay_per_use~, ~state~ (~idle~ for never asked,
~pending~, ~ok~, ~unsupported~, ~error~), ~message~ (why, for the last
two), ~read_at~ (unix seconds of the last answer, absent for none), and
from the last good report ~plan~, ~source~, ~detail~, ~partial~,
~collected_at~ and ~windows~.  Each window has ~label~ (a name; a raw key such as ~USAGE_PERIOD~ is already rewritten), ~key~ (that raw label, when the provider sent one), ~kind~ (~meter~ or ~balance~; a balance is a currency or credit figure with no percentage, drawn with no meter and never as a warning) and ~unit~
(~percent~, ~tokens~ or ~USD~) and only the members the provider
reported: ~remaining_percent~ (when the source gave a direction),
~percent~ (a figure with no direction), ~used~, ~limit~, ~remaining~,
~window_minutes~, ~cost_usd~, ~model~, ~reset_at~ (unix seconds, an
exact instant only) and ~reset_text~ (the source's own words, or a date
with no time).  An unknown value is absent, never zero.  The handler
never waits on a provider: ~refresh~ starts a read of each login
*behind* the reply (at most once a minute per login), and each answer
is announced as ~usage.providers_changed~ (subject the login's id;
detail ~state~), which is ephemeral like ~turn.step~.  Re-read without
~refresh~ on it, or a login that keeps failing loops.  See
[[file:provider-usage.org][provider-usage.org]].

~task.tree_budget~ (since 0.18.0) is published once when a task tree
uses =orchestration.tree_message_budget=, and not again until a task in
it settles.  Subject the root task's id; details ~tree~ (what to call
it: the root's brief, its id and its assignee), ~count~ and ~limit~
(integers), ~agent~ (the root's assignee, for a pod's scope) and
~message~, the sentence ~clawt_loop_guard_tree_alert_text()~ writes.

~crosstalk.pair_budget~ (since 0.34.0) is published once when two agents
use =orchestration.pair_message_budget=, and not again until the pair's
count has started over.  Subject the agent whose request was the last one
allowed; details ~agent~ (the same, for a pod's scope), ~peer~ (the
other), ~count~ and ~limit~ (integers) and ~message~, the sentence
~clawt_loop_guard_pair_alert_text()~ writes.
It is a notice.

Two events go with it: ~agent.idle_stopped~ (subject the agent, detail ~hours~) when =agents.runtime.idle_stop_hours= stops one -- a routine alert -- and ~spending.limit-reached~ (subject ~fleet~ or ~agent:<id>~, details ~cost_micros~ and ~limit_micros~), published by the router since 0.7.x and tiered as a notice from 0.8.0.

One unreadable database does not fail the summary -- a fleet report that
refused because one agent's file was mid-write would say nothing about
the other nine.

~usage.ledger~ (new in v0.15.0) is the same turns grouped another way.  It takes ~since~ (unix seconds, 0 for everything), ~by~ (~agent~, ~model~, ~origin~ or ~day~; absent is ~agent~, anything else is refused with =INVALID_ARGUMENT= rather than answered under the wrong heading) and optionally ~agent~ (one agent; an unknown one is =NOT_FOUND=).  It answers ~by~, ~since~, ~now~, ~agent~ when one was asked for, ~groups~ -- each ~{key, turns, unpriced_turns, input_tokens, output_tokens, cost_micros}~ -- and a ~total~ of the same shape without ~key~.  Days are local dates (~YYYY-MM-DD~), oldest first; every other grouping is most expensive first.  An origin key is ~operator~, ~agent:<id>~, ~routine:<id>~, ~trigger:<id>~, ~task:<id>~, ~channel:<name>~, ~other:<sender>~ or ~untagged~ (=clawt_usage_origin_label()=).

~unpriced_turns~ counts turns whose recorded cost is not a price -- negative, or zero against tokens (=clawt_usage_turn_is_priced()=) -- and ~cost_micros~ never includes them: unknown is not free, and a ~-1~ summed in would quietly refund a micro-dollar per turn.  A client builds the request with =clawt_usage_ledger_payload()= and draws the reply with =clawt_usage_ledger_cost_label()=, =clawt_usage_ledger_row_subtitle()=, =clawt_usage_ledger_unpriced_line()= and =clawt_usage_ledger_csv()=, so the words and the export are the same everywhere.  A new frame kind, so an older daemon answers it as an unknown kind; ~usage.summary~ is unchanged apart from no longer letting a negative cost reduce a total.

*** browser.*

Since 0.9.0. Every verb but ~browser.list~ takes ~agent~ and acts on the session that agent drives -- its own, or the shared one its =agents.browser.use= names -- and every verb but ~browser.list~ is deferred: a frame waits on a page and a start waits seconds for an X server.

- ~browser.list~ → ~available~ (whether this daemon was built with =GSURF=1=) and ~sessions~: every shared session declared under =browsers:=, used or not, then each agent's own. Each has ~key~ (~agent:<id>~ or ~shared:<id>~), ~id~, ~kind~ (~own~ or ~shared~), ~agents~ (who drives it), ~running~, ~uri~, ~title~, ~driver~ (the agent holding a shared session's wheel, or empty) and ~last_used~. Read from the daemon's record; it touches no browser, so ~uri~ and ~title~ are the last ones read.
- ~browser.frame~ → the same members for one session plus ~png_base64~, a picture of the visible page. A session that is not running answers at once with ~running: false~ and no picture -- a frame never starts one.
- ~browser.open~ (~url~; ~https://~ is assumed without a scheme) starts the session if it must, navigates, and waits up to twenty seconds for the load.
- ~browser.click~ (~x~, ~y~, in the page's CSS pixels) is a person's click. It does not take a shared session's driver lease, since a person at the Computer page outranks an agent.
- ~browser.stop~ stops it. The profile and its logins stay; the open page does not.

Since 0.25.0 every session object -- in ~browser.list~ and in each ~browser.*~ reply -- also carries ~secret_hold~ (a secret was filled on the page and it has not been seen to navigate away) and ~last_fill~ (~{name, host, at}~: the vault entry's name, the host it was typed on and unix seconds, or ~null~). Never a value. While ~secret_hold~ is true ~browser.frame~ answers without ~png_base64~ rather than with an error: the daemon takes no picture of a page a secret is on. Clients draw both through =clawt_browser_session_line()=, whose second line is =clawt_browser_fill_line()=.

*** vault.list

Since 0.25.0. The =vault:= entries, for a client choosing which ones an agent may have filled. Takes an optional ~agent~ (an unknown one is =NOT_FOUND=). Answers ~entries~, each ~{name, kind, description, sites}~ (~kind~ is ~password~ or ~totp~), and with ~agent~ also ~agent~, ~browser~ (whether its =agents.browser.mode= is not =none=) and a ~granted~ boolean per entry. Names only: neither the value nor the reference it is resolved through crosses the socket. An entry missing its secret or its sites is not listed, since it is never filled.

*** computer.*

~computer.exec~ (~agent~, ~command~, ~cwd~, ~timeout~ -- 120 seconds by
default) → ~exit~, ~stdout~, ~stderr~, and ~wake_ms~: how long this
command waited for an ~ssh~ machine's [[file:computers.org::#ssh-wake][wake
command]] before it ran, outside its timeout (0 when it did not).  A
computer with ~computer.start: on_first_use~ is started by the command,
once for every command that arrives while it starts.
~computer.desktop~ (~agent~) defers the same way while a VM that starts on
first use boots.  ~computer.status~ (~agent~) →
~state~ and ~description~.  ~computer.copy~ (~src~, ~dst~, one side being
~<agent>:<path>~).  ~exchange.list~ (~agent~) → ~entries~.

~computer.start~, ~computer.stop~ and ~computer.restart~ (~agent~,
~remove~) power the machine itself, separately from the agent → ~agent~,
~action~, ~state~ and ~removes~.  All three *defer*: starting a container
is a blocking request to podman and stopping a VM waits up to thirty
seconds for the guest to flush, and either held on the daemon's main
context is that long in which nothing else is routed.

They are refused for a computer type with no machine of its own ---
~none~ has nothing, and a ~host~ agent's machine is the one clawtilla is
running on.  Which types have one is
~clawt_computer_type_has_machine()~, so a backend added later reaches
every surface without any of them being edited; the listing reports it
per agent as ~computer_machine~.

~computer.stop~ and ~computer.restart~ are also refused, without
~remove~, when stopping would *destroy* the machine.  That is a
~computer.container.keep~ is off: the backend then removes the container
when it stops one, and the contents are gone rather than offline.  It is
on by default, so this is the case somebody chose.  The listing says so in advance as
~computer_stop_removes~, both graphical clients warn before they send,
and the fence is what protects a client that does not.  ~removes~ in the
reply is that same policy rather than an observed destruction --- a
computer object built from the config knows nothing about a machine it
did not start, so claiming one had been destroyed would sometimes be
untrue.

Each one publishes a ~computer.power~ event carrying ~action~ and
~result~, recorded whichever way it went: a trail holding only the
successes reads as "it did not happen" rather than as "we do not know
what it did".

~computer.shared~ (no payload) → ~computers~, one object per machine declared under ~computers:~, in file order: ~id~, ~type~, ~description~ when there is one, ~shareable~ (FALSE for a host computer), ~state~ (~unbuilt~ until a user has started it), ~users~ (every agent naming it) and ~running~ (those of them running). Read from the config rather than from the machines built, so a machine nobody has started can still be chosen.

For an agent on a shared machine, ~computer.start~, ~computer.stop~ and ~computer.restart~ are refused while another user is running, and ~computer.rebuild~ while any user is. ~agent.set~ refuses ~computer.use~ naming an undeclared or host computer, and any other ~computer.*~ key of an agent that names a machine. ~computer.control~ answers ~allowed: false~ with the holder in ~refusal~ when another user is driving the shared screen.

~computer.rebuild~ (~agent~) tears the agent's computer down and
provisions it again, answering ~rebuilt~, ~agent~ and sometimes ~note~.
It is *refused while the agent runs*, rather than done carefully:
rebuilding is destroying the machine the agent is working on, and there
is no version of that which is safe to do underneath it.  A teardown that
fails is reported in ~note~ and is not fatal -- the common reason to
reach for this is that the guest is already gone, deleted by hand in
virt-manager, and refusing to rebuild because there was nothing to tear
down would be absurd.

This is the frame for every VM setting cloud-init reads once.  The login,
the desktop, the flavour and the package list are fixed for the life of
an overlay, so changing one and restarting the agent does nothing
visible -- which reads as the setting not working rather than as the
setting arriving too late.  cpus, memory, disk size and the screen
resolution are *not* in that group: they reach the domain definition and
apply at its next boot.

~computer.desktop~ (~agent~) answers ~backend~, ~argv~ and ~tools~ -- the
command that reaches a guest desktop's MCP server, and the tool names the
agent's grant permits.  The command is built here rather than written
into the agent's ~.mcp.json~ because the port that reaches the guest is
chosen when the VM is provisioned, which is after the workspace files are
written; a command line captured at render time names a port nothing is
listening on.  The permitted tools travel with it so the relay needs no
copy of the policy, and so revoking ~computer.desktop.allow_input~ takes
effect at the next daemon reload rather than whenever the agent's MCP
client is next restarted.

Its refusals are deliberately four different sentences, because the four
causes want four different actions: no desktop configured names
~computer.desktop.enabled~; a desktop that is not in a VM says there is
nothing to relay to; a VM agent that is stopped says to start it, since a
stopped agent's VM has no address yet; and a running VM with no forwarded
port says so rather than reporting a missing desktop.  The policy is a
pure function of the config, so a stopped agent is answered from the
config rather than told it has no desktop -- which is what it used to be
told, naming a key that was already set.

For a ~display~ computer on gowl (since 0.51.0) it answers ~backend:
gowl~ and an ~argv~ of ~gowl-mcp --socket <the display's run
directory>/gowl-mcp.sock~ -- gowl's own stdio bridge to the private
compositor -- with ~tools~ filtered by ~computer.display.allow_input~ and
~allow_spawn~ (recording tools never).  It starts the display first when
it is not running.  A display on an X server is =NOT_SUPPORTED= with a
sentence saying the ~clawtilla_display_*~ tools cover it; no ~gowl-mcp~
installed is =NOT_FOUND=.

*** computer.screen and the takeover

~computer.screen~ (~agent~) answers everything a client needs to draw the
Screen tab in one frame: ~type~, ~has_screen~, ~observable~, ~watchers~,
~fps~, ~stamp~, ~stale~, ~frame_width~, ~frame_height~, ~screen_width~,
~screen_height~, ~held~, ~holder~, ~expires_at~, ~lease_seconds~,
~request~, ~can_input~, ~allow_input~, and ~viewer~ and ~error~ when
there are any.

For a ~display~ computer (since 0.51.0) it also carries
~display_backend~ (~gowl~, ~xvnc~ or ~xvfb~ once started, or what was
asked for before), ~display_running~, and when there are any
~display_notes~ -- what ~auto~ skipped and why, one line each -- and
~display_failure~, the last lines a server that died wrote.  See
docs/computers.org, "display".

~has_screen~ and ~observable~ are two different questions and both are
needed.  The first is about the *type* -- ~clawt_computer_type_has_screen()~
-- and decides whether the tab is drawn at all; the second is about this
agent right now, and decides whether the tab holds a picture or an
explanation.  A client with only the first shows an empty panel on a
stopped agent; one with only the second silently drops the tab whenever
the agent is off, which reads as the feature not existing.

~stale~ is the daemon's answer to "is this picture old enough to be
labelled rather than shown as current", so both clients agree about it.
~viewer~ is *absent* rather than empty when there is nothing to open: an
address for a VM that is off sends whoever clicks it to debug their
viewer.

~computer.observe~ (~agent~, ~watcher~, ~fps~) starts watching and
~computer.observe_stop~ (~agent~, ~watcher~) lets go.  Nothing is
captured unless somebody is subscribed, because a frame comes out of the
same channel the agent is using for its own work.  A subscription is a
**lease** keyed by ~watcher~: asking twice under one name is one watcher
whose lease moves forward, and a client that stops asking stops being
one.  That is the only way a browser can say goodbye -- a closed tab
sends nothing, and a count nobody decremented would leave a screen
grabbed for ever.

~computer.frame~ (~agent~, ~refresh~) answers ~mime~, ~bytes~, ~base64~,
~stamp~ and ~stale~.  Bytes and never a path, for the reason
~attachment.get~ already records: a client may be on another machine, so
a filename would work on this host and show nothing anywhere else.

*A screen with nothing captured yet answers rather than failing*: the
reply is ~pending: true~ with ~watchers~, ~stamp: 0~, ~stale: false~ and
no ~base64~.  That is the ordinary state of a screen for the first second
of watching it, and for as long as a VM takes to boot or to be rebuilt.
It used to be a ~NOT_FOUND~ error, and both clients poll this verb --- the
GTK client toasts every failed request, so a booting VM raised one toast
per refresh, saying what the panel underneath was already showing in
place.  ~pending~ is a stated absence rather than an implied one, so a
client can tell "there is no picture" from "this build does not send
one"; ~watchers~ distinguishes the two reasons there is no frame, and
only one of them is something a person can act on.

A frame whose file has since gone *is* an error, and stays one.

~computer.takeover~ (~agent~, ~holder~) and ~computer.release~ (~agent~)
are how a *person* takes the screen, and only a person: while it is held
the agent's actions on that screen are refused rather than queued, since
a queued click lands after somebody has moved on.  Releasing also settles
an open request for hands, so there is no separate "done helping" step to
forget.  Taking a screen somebody else holds is refused and names them;
taking one you already hold extends the lease.

~computer.input~ (~agent~, ~kind~, ~text~, ~x~, ~y~, ~button~, ~dx~,
~dy~) sends one event, and is refused unless you are holding the screen.
It *defers*: a keystroke into a guest is an SSH round trip, and waiting
for it on the daemon's context would be every agent's messages stopped
once per key.

~computer.act~ (since 0.51.0; ~agent~, ~action~ and the action's own
fields) is an *agent's* hands on its virtual display, where
~computer.input~ is a person's during a takeover.  ~action~ is
~screenshot~, ~windows~, ~launch~ (~command~), ~click~ (~x~, ~y~,
~button~), ~move~ (~x~, ~y~), ~type~ (~text~), ~key~ (~text~, an XKB
combo) or ~scroll~ (~x~, ~y~, ~dx~, ~dy~).  It *defers*, since each runs
a process or a socket call, and answers: ~png~ (base64), ~width~ and
~height~ for a screenshot; ~windows~ (an array); ~started~ and, when the
display knows it, ~pid~; or ~sent~.  Refusals: no such agent
=NOT_FOUND=; an agent whose computer is not a display
=NOT_SUPPORTED=; an unknown action, or ~type~/~key~ without ~text~, or
~launch~ without ~command~ =INVALID_ARGUMENT=;
~computer.display.allow_input~ off for an acting action, or
~allow_spawn~ off for ~launch~, =PERMISSION_DENIED=.  While a person
holds the screen an acting action answers ~allowed: false~ with the
takeover's ~refusal~ sentence -- an answer, not an error, so a tool can
pass the reason on; ~screenshot~ and ~windows~ are never refused for
it.  The agent's own ~clawtilla_display_*~ tools do the same work over
its link (docs/computers.org, "The agent's tools").

~computer.control~ (~agent~, ~tool~) → ~allowed~ and ~refusal~ is not a
client frame.  It is what the desktop relay asks before forwarding an
acting tool, and it is the only place a takeover reaches an agent that is
already running -- the permitted tool list is fixed when the relay starts
and cannot know that somebody has since taken the screen.  **The caller
fails open**: a gate that cannot reach the daemon allows the call, because
this is cooperation between an operator and their own agent rather than a
boundary against a hostile one, and a daemon hiccup bricking every
desktop tool mid-turn costs more than the race.  ~computer.desktop.allow_input~
is the permission that is *not* like this, and it is enforced through the
tool list rather than here.

Three events go with these.  ~computer.frame~ carries ~stamp~ and names
the agent, never the path -- a client fetches the bytes.
~computer.frame_failed~ carries the backend's own ~error~, because a
preview that stops updating in silence reads as a machine doing nothing.
~computer.takeover~ carries ~held~, ~holder~ and ~request~.

~image.list~ is container images and is described below.  The ~vm_~

~oom_killed~ when the container module reported them, ~failure~ in
~broker.restart: on-failure~'s sense and ~restarted~), ~refusal~ when
Jentic One is refused for an unconfined agent, ~assignments~ (each with
~target~, ~server~, ~connector~, ~agents~ and ~key_stored~ -- whether, never
what) and ~warnings~.  ~broker.start~, ~broker.stop~ and ~broker.restart~
answer at once with the same members, saying ~starting~ or ~stopping~:
the work is on worker threads and ~broker.changed~ follows it.  A start
is refused with ~CLAWT_ERROR_NOT_SUPPORTED~ while ~broker.enabled~ is off
and ~CLAWT_ERROR_CONFINEMENT~ for Jentic One with an unconfined agent.
~broker.logs~ is deferred and answers ~logs~.  ~broker.key~ takes
~target~ (an agent id, or ~team:<id>~) and ~key~, writes it 0600 and
answers ~key_file~ -- the path, never the key.  ~integration.update~,
~integration.remove~, ~connector.begin~, ~connector.discover~,
~connector.key~ and ~connector.revoke~ aimed at one of the broker's own
connectors (~broker-agent-*~, ~broker-team-*~) are refused with
~CLAWT_ERROR_INVALID_ARGUMENT~, naming the settings that change it.

~integration.add~ for a ~connector~ given a ~url~ and no ~provider~ is the
built-in ~remote~ entry.  A second connector on a ~provider~ that already
has one is refused (~CLAWT_ERROR_INVALID_ARGUMENT~) without an ~account~,
and with one another account on that provider already folds to
(~CLAWT_ERROR_ALREADY_EXISTS~); nothing is written either way.

A secret is written by naming its *reference*: ~secret_key~,
~secret_backend~ (~file~, ~env~ or ~command~) and ~secret_locator~.  A
reply carries the reference back, never the value.

~integration.matrix_login~ takes ~integration~, ~homeserver~, ~user~ and
~password~, and optionally ~agent~ to write the result under
~per_agent~.  It returns ~user_id~, ~device_id~ and ~token_file~ -- the
token itself stays in the daemon.

~agent~ is checked before the sign-in is attempted: it has to be a
well-formed id and it has to name an agent that exists.  It becomes part
of the token's filename, and it was taken raw -- so a separator in it put
a live access token outside the 0700 secrets directory and on top of
whatever it named, and the resulting name was written back into
~clawtilla.yaml~ as a ~{file: ...}~ reference, so the traversal outlived
a restart.  The integration name is folded rather than refused, the way
~clawt_connector_token_path()~ folds an instance name, because that one
arrives from a file somebody edits by hand.

*** routine.*

~routine.list~ returns every routine with its own fields plus three the
daemon works out: ~expression~ (what the schedule *means* as cron),
~next_run~ (ISO 8601) and ~last_run~ / ~last_state~ / ~last_detail~.  A
client that had to turn "weekdays at 09:00" into an expression itself
would be a second implementation of the schedule.

From the start-failure guard (=routines.max_start_failures=): ~start_failures~,
the runs in a row whose computer did not start, and -- only while the
routine is off for that reason -- ~turned_off_after~ (how many turned it
off) and ~turned_off_error~ (the computer's error).  Numbers and the raw
error, not a sentence: each client words them with
~clawt_routine_turned_off_note()~.  Turning it back on is ~routine.update~
with =enabled: true=, which clears both.

~routine.add~ and ~routine.update~ take the schema's own keys and refuse
a schedule that does not parse, so a bad expression is rejected while
somebody is still looking at what they typed rather than at the next tick.
~routine.remove~ and ~routine.run~ take an ~id~; ~routine.run~ ignores
both the schedule and ~enabled~ and returns the ~task~ it started.
~routine.run~ is a person's Run now: the loop guard's cycle detector
does not measure it (a second press inside ~orchestration.cycle_seconds~
runs again), and a refusal -- the rate limit, a spending cap, an agent
that is gone -- is the error this request returns and is never filed as
an incident; the task it had created is cancelled with the reason.

~routine.ran~, ~routine.changed~ and ~routine.turned_off~ are published
as events; the last carries ~agent~, ~failures~ and ~error~ and is an
error in every client's alerts panel.

**** routine.occurrences and routine.upcoming: the Schedule calendar (since 0.78.0)

The fleet's routines laid out in time, for the Schedule page (Day, Week
and Month views and the Upcoming runs panel; VENTURE #35).  Both replies
are built by =ClawtRoutineCalendar= in libclawt, so every client draws
the same answer and none of them expands a cron expression itself.

Times on the wire are UTC, written =2026-11-24T14:00:00Z=.  Every reply
also carries ~time_zone~, the daemon's zone name (=America/Detroit=):
schedules fire in the daemon's local time, so a client converts to that
zone for display and says so ("Times in America/Detroit").  A client in
another zone that converts to its own will put a 09:00 routine at the
wrong hour on its grid.

~routine.occurrences~ request:

| Field              | Type    | Default                   | Meaning |
|--------------------+---------+---------------------------+---------|
| ~from~             | string  | start of today, local     | window start, inclusive: ISO 8601 (no offset means UTC) or a bare =YYYY-MM-DD=, which is local midnight |
| ~to~               | string  | ~from~ + 7 days           | window end, exclusive, same forms |
| ~agent~            | string  | all                       | only this agent's routines and crons |
| ~team~             | string  | all                       | only agents whose =agents.team= is this |
| ~include_disabled~ | boolean | false                     | include routines and libreclaw crons that are off, and the crons of disabled agents |
| ~collapse~         | boolean | false                     | fold a routine's runs on one local day into a group when there are three or more |

Refused with =INVALID_ARGUMENT= -- and a message saying which bound --
for a time that does not parse, a window that is empty or backwards, one
longer than =daemon.calendar_max_days= (62), and one holding more than
=daemon.calendar_max_occurrences= (5000) occurrences, which names the
routine that holds most.  Nothing is silently cut short.

Reply:

| Field         | Meaning |
|---------------+---------|
| ~from~, ~to~, ~now~ | the window as answered, and the daemon's now, UTC |
| ~time_zone~   | the daemon's zone name |
| ~count~       | every occurrence in the window, folded or not |
| ~routines~    | an index of every routine and scheduled libreclaw cron that passed the filters, with or without occurrences: ~source~, ~id~, ~agent~, ~title~, ~enabled~, ~schedule~ (the preset, =custom= for a cron), ~expression~, ~jitter_seconds~, ~every_seconds~ (the shortest gap between runs -- 3600 for hourly; absent for a manual routine), ~problem~ when the schedule cannot be read |
| ~unscheduled~ | libreclaw crons that cannot go on a calendar: an =interval_seconds= job (counted from when the agent's process started) with ~interval_seconds~, or a schedule clawtilla cannot parse with ~problem~.  Same fields as ~routines~ |
| ~occurrences~ | the occurrences, soonest first; with ~collapse~, only those not in a group |
| ~groups~      | with ~collapse~ only: one per routine per local day with three or more runs |

An occurrence:

| Field          | Present        | Meaning |
|----------------+----------------+---------|
| ~source~       | always         | =routine= or =libreclaw-cron= -- label the second so it is not mistaken for a routine |
| ~routine~      | always         | the routine id, or the libreclaw job's name |
| ~agent~        | always         | the agent, for its avatar |
| ~title~        | always         | the routine's =description=, else its id; a job's name |
| ~at~           | always         | the scheduled time; for a run by hand, when it started |
| ~earliest~, ~latest~ | always   | the jitter window: =at= to =at= + =jitter_seconds= (equal without jitter) |
| ~kind~         | always         | =scheduled=, or =manual= for a run nothing scheduled (Run now, an automation) |
| ~repeat~       | always         | the preset: =hourly=, =daily=, =weekdays=, =weekly=, =custom=, =manual= -- the hint for folding client-side |
| ~status~       | always         | =upcoming=, =due=, =running=, =ok=, =failed=, =skipped= or =unknown= (=ClawtOccurrenceStatus= nicks) |
| ~reason~       | when it helps  | with =skipped=: =daemon_down=, =catch_up=, =agent_stopped=, =refused=, =cancelled=; with =due=: =next_tick=, =jitter=; with =unknown=: =no_record=, =not_tracked= |
| ~detail~       | when known     | why: the failure, the refusal, the task's own reason |
| ~started_at~   | it started     | when the run actually began |
| ~task~         | a task was made | the task to open: its result, its transcript |
| ~task_state~   | the task is known | the task's state nick, for a client that wants more than ~status~ |
| ~room~         | the task is known | the room the run is in -- a routine's own room when it is isolated |
| ~by_hand~      | true only      | a person started it |
| ~queued~       | true only      | with =agent_stopped=: still in the agent's mailbox, and runs when the agent starts |

How a past time gets its status.  The runner keeps a history of every
scheduled time (=ClawtRunEntry=, =daemon.routine_history_days=): started
with which task, failed to start, refused by a guard, missed while the
daemon was down or the machine asleep, or folded into a =catch_up= run.
A started run is then judged by its task: completed is =ok=; failed or
stalled is =failed=; cancelled is =skipped= / =cancelled=; pending or
running on an agent that is not up is =skipped= / =agent_stopped= with
~queued~ (the daemon marks a routine's task running before it delivers
the prompt, so a run held in a stopped agent's mailbox reads as running);
any other open state is =running=.  A task the daemon no longer knows counts
as =ok= -- it started, which is what the runner can vouch for.  A past
time with nothing recorded is =due= for two minutes (the tick may not have
come) or while a jitter is pending, and =unknown= / =no_record= after
that: before the history was kept, pruned from it, or while the routine
was off.  Runs the current schedule would not produce -- a Run now, a
time from before the schedule was edited -- are included as they
happened.  A libreclaw cron in the past is always =unknown= /
=not_tracked=: clawtilla lays them out from the agent's =libreclaw:=
block and does not run them.

A group (~collapse~):

| Field          | Meaning |
|----------------+---------|
| ~source~, ~routine~, ~agent~, ~title~ | as an occurrence |
| ~day~          | the local date, =2026-11-24= |
| ~first~, ~last~ | the first and last run that day, UTC |
| ~count~        | how many runs |
| ~every_seconds~ | the gap when every gap is the same |
| ~label~        | the card's text, in the daemon's zone: =every hour, 08:00-18:00=, =every 15 minutes, ...=, or =12 runs, ...= |
| ~status~       | the worst in it, so a failure is not hidden: failed, running, due, skipped, unknown, ok, upcoming in that order |
| ~statuses~     | how many of each status, ={"ok": 5, "upcoming": 6}= |
| ~occurrences~  | every run in it, for the expand control |

~routine.upcoming~ takes ~limit~ (default 10, at most 200; a number or a
numeric string), ~agent~ and ~team~, and returns ~now~, ~time_zone~ and
~runs~: the next ~limit~ runs of every enabled routine and scheduled
libreclaw cron, soonest first, each an occurrence with =status: upcoming=.
A routine's first run in ~runs~ is exactly its ~next_run~ in
~routine.list~: both come from =clawt_routine_runner_next_run_after()=.

Neither request changes anything, and neither publishes an event.  A
client refreshes on ~routine.ran~ and ~routine.changed~, and on a task
event for a task it is showing.

*** wait.*

Conditions an agent asked to be told about with ~clawtilla_wait_until~, checked by the daemon rather than by the model.  See [[file:orchestration.org::*Waits: a condition checked by code][orchestration.org]].

~wait.list~ takes an optional ~agent~ and returns ~{"waits": [...]}~, the pending ones only, oldest first.  Each carries ~id~, ~agent~, ~room~ (where its notice goes), ~label~ (the agent's words), ~note~ when there is one, ~kind~ (~url~, ~file~, ~task~, ~computer~ or ~command~), ~condition~ (the daemon's phrase for it, so a client does not rebuild one per kind), ~state~ (always ~pending~ here), ~created_at~, ~last_check_at~ (0 before the first look), ~next_check_at~ and ~expires_at~ in microseconds since the epoch, ~checks~, ~failures~ (looks in a row that went unanswered, which is what the backoff counts) and ~last_result~ when a look has seen something.  A client draws the schedule with ~clawt_wait_schedule_label()~ from the three timestamps, at render time.

~wait.cancel~ takes ~wait~ (the id) and ends it as the operator: any agent's wait, and the agent is sent a notice saying so, because it would otherwise go on believing it was waiting.  The reply is ~{"cancelled": "<id>"}~; an id that is not pending is ~NOT_FOUND~.

Both answer ~NOT_SUPPORTED~ from a daemon with no state directory, which keeps no waits.

~wait.changed~ is published, with the agent as subject and ~wait~ and ~state~ (~pending~, or ~ended~ once it has gone) as detail, when a wait is set, when it ends, and when a look sees something different from the last one -- not on every look.

*** trigger.*

~trigger.list~ returns every trigger with its own schema fields plus
four the daemon works out: ~endpoint~ (the address it answers on),
~pending_verification~, ~unfinished~ (runs in flight), and ~has_secret~.
~mode~ is the nick; ~max_pending~ is the cap the daemon *applies*, so a
hand-written value outside 1 to 50 is reported as the default it reads
as; ~match~ is an array of ~{path, value}~ objects.  A ~match~ the
daemon cannot read is reported as ~match_error~ (the reason) in place
of ~match~, so an editor can say so rather than draw an empty filter a
save would write over it.
The reply also carries ~receiving~ -- whether the receiver is listening
at all -- and ~listening~, the base URLs it bound, so a client can print
a whole address rather than asking somebody to assemble one.

*The secret is never in a reply except the two that mint it.*
~trigger.add~ and ~trigger.rotate~ return ~secret~ with
~secret_shown_once~ beside it, and nothing else ever does.  The
~CLAWT_SCHEMA_SECRET~ field is skipped outright when a trigger is
serialised, so not even the *reference* is listed: ~{command: pass show
fleet/trigger-x}~ names where the credential lives, to every client on
the tailnet.  There is correspondingly no way to *post* a secret.

~trigger.add~ and ~trigger.update~ take the schema's own keys and
dispatch on each key's type; a list may be an array or a
comma-separated string, because a command line and an HTML form both
produce the latter.  ~trigger.add~ forces ~enabled~ false whatever was
posted: the first authenticated delivery is captured rather than run,
and an enabled trigger can never be pending.

~match~ is accepted as an array of ~{path, value}~ objects, an array of
~"path=value"~ strings, or one string with a pair per line; JSON null,
~""~ and ~[]~ clear it.  ~trigger.add~ and ~trigger.update~ refuse,
before anything is written, more than ten pairs, a pair
=clawt_trigger_match_check()= rejects, a ~max_pending~ outside 1 to 50,
a ~mode~ the enum does not have, and ~mode: post~ with no ~room~ (taking
whichever of the two the payload does not carry from the saved trigger).

~trigger.match_test~ takes an ~id~, an optional ~match~ (in any of the
spellings above; the saved filter when absent) and an optional
~receipt~, and checks those pairs against the newest stored delivery
body -- or the handshake capture when there is none -- without saving or
running anything.  It returns ~payload~ (the body checked), ~receipt~
when it came from one, ~matches~, ~reason~ when it would have been
ignored, ~results~ (one object per pair: ~path~, ~value~, ~found~,
~matched~ and, when found, ~actual~ cut short) and ~paths~ (every scalar
in the body as ~{path, value}~, at most 200, for an editor to offer).
With nothing stored it returns a ~note~ and no ~payload~.

~trigger.remove~, ~trigger.rotate~ and ~trigger.capture~ take an ~id~.
~trigger.rotate~ replaces the secret *and* the endpoint and puts the
trigger back to pending.  ~trigger.capture~ returns the held delivery
as ~payload~, with ~pending_verification~ saying whether the handshake
is still open.

~trigger.test~ takes an ~id~, an optional ~event~ name and ~run~.  With
~run~ false it returns the ~prompt~ the agent would be asked; with it
true it starts the run and returns the ~task~.  For a ~mode: post~
trigger ~prompt~ is the message it would post and ~report~ begins
=Posts into: <room>=; with ~run~ true it posts, and the reply carries
~posted~ (the room) instead of ~results~.  ~trigger.replay~ treats a
post trigger the same way.  It builds a synthetic
event rather than making a loopback request against the real endpoint,
which would need the secret in a process listing.

~trigger.deliveries~ takes an optional ~id~ and a ~limit~ (50 by
default) and returns receipts newest first, each with ~trigger~,
~delivery~, ~event~, ~repo~, ~branch~, ~actor~, ~outcome~, ~detail~,
~task~ and ~at~.  An empty list carries a ~note~ saying *why* it is
empty, because "nothing has been delivered" and "the receiver is not
running" are different facts and only one is about the sender.

~trigger.fired~, ~trigger.posted~, ~trigger.changed~, ~trigger.refused~
and ~trigger.verified~ are published as events.  ~trigger.posted~ is a
~mode: post~ delivery written into its room.  ~trigger.refused~ is an
authentication failure and nothing else: a delivery turned away by the
rate limit or dropped at ~max_pending~ is in the receipts and publishes
*nothing*, since an event per refusal is a way to make the daemon
publish as fast as somebody can POST.  A receipt's ~outcome~ is one of
=ran=, =duplicate=, =ignored=, =captured=, =refused=, =failed=, =dropped=
and =posted=.
*** grok.*

~grok.bots~ takes nothing and returns ~bots~ -- each bot once, by ~name~, with ~description~, ~key_configured~ (the integration names a routine key), ~mcp_key~ (a key has been minted for the MCP endpoint) and ~agents~ (who it is shared with, walked from each agent's resolved bindings) -- and ~reachable~: whether a job could be sent right now.  When it could, ~callback_host~ names where bots report; when it could not, ~unreachable_reason~ says why, in the same words a send's refusal uses.  ~mcp_url~ is present when the endpoint can be reached.

~grok.jobs~ takes optional ~bot~, ~agent~, ~open~ (unsettled only) and ~limit~ (50, at most 500), and returns ~jobs~ newest first -- each with ~id~, ~bot~, ~agent~, ~room~, ~task~, ~run_uuid~, ~instructions~, ~result~, ~note~, ~state~ (a =ClawtGrokJobState= nick), ~settled~, ~needs_attention~ and ~created_at~, ~updated_at~, ~expires_at~ in microseconds -- and ~attention~, the number of listed jobs that need somebody, which is the page badge.  Never a token.  A job counts toward ~attention~ for =grok.attention_days= (3) after it last changed -- for ever, until removed, when that is 0 -- and stays listed until it is pruned =grok.retention_days= (30) after it settled; the prune runs at start and then hourly (since 0.52.0; the windows were fixed at three and thirty days before).

~grok.remove~ takes ~job~ (its id) and answers ~job~, ~removed~ and ~cancelled~.  A settled job is deleted and nobody is told.  An open one is first settled as ~expired~ -- the same one-statement settle a report races, so the bot's late report is refused -- and its agent is sent a message from ~grok:<bot>~ saying the operator cancelled it and it should stop waiting; then it is deleted.  ~cancelled~ says which happened.  Publishes ~grok.job_updated~.  An unknown id is ~not_found~.

~grok.send~ takes ~agent~ (whose job it is; its answer goes to that agent's conversation with its operator), ~bot~ (resolved by name, case or unique prefix among the bots shared with that agent), ~instructions~, and optional ~context~ and ~timeout_minutes~.  It is answered later: after Grok has said whether it started a run, with ~job~ -- or with an error whose message says why it was not started.

~grok.routine_prompt~ takes ~bot~ and returns ~text~, the standing instructions for the bot's routine.  ~grok.mcp_key~ takes ~bot~, mints a key for the MCP endpoint and returns ~key~ with ~secret_shown_once~, and ~mcp_url~ when reachable.  Only the digest is kept; minting again replaces it.

~grok.job_updated~ is published whenever a job changes -- sent, accepted, a progress note, settled or expired -- with ~bot~, ~agent~ and ~state~, so a client's count goes down as well as up.  ~grok.bots_changed~ is published when an MCP key is minted.  See [[file:grok.org][grok.org]].

*** skill.*

~skill.list~ returns every skill in the library, each with its
~description~, ~source~, ~enabled~, ~origin~, ~sha256~, the ~warnings~
the scan produced and the ~skipped~ files an import left behind.  The
warnings are in the *listing* rather than only in ~skill.show~, because
the person reading it is deciding whether to enable something and a
warning behind a second click is a warning that gets enabled around.

An empty list has two causes and the reply says which: ~enabled~ is
false when ~skills.enabled~ is off, and ~directory~ names where it did
look.  ~problems~ carries a line per directory that looks like a skill
and could not be read -- a skill that fails to parse is otherwise
invisible, and assigning it reports that no skill of that name exists,
which sends somebody to look at the assignment rather than at the file.

~skill.show~ adds the ~body~.  ~skill.create~ takes ~name~,
~description~ and an optional ~body~ and lands *enabled*, because
somebody sat there and wrote it.  ~skill.import~ takes a local ~source~
directory and an optional ~origin~, and lands **disabled**: nothing an
import brings in reaches any prompt until a person has read it.  It
copies markdown only and reports what it left behind.

~skill.enable~ takes ~name~ and ~enabled~; ~skill.remove~ takes ~name~.
Both re-render every agent's workspace, so the reply carries ~refused~
the way ~agent.set~ does.

~skill.assign~ and ~skill.unassign~ take ~name~ plus *exactly one* of
~agent~, ~team~ or ~fleet~, and answer with ~changed~ -- false when the
skill was already there, so a client can say "it already had that"
rather than claiming to have done something.

~skill.reload~ rescans.  The library follows its directory with a
~GFileMonitor~, so this is rarely needed -- but a filesystem with no
inotify silently has no watch at all, and without this the only remedy
would be restarting the daemon.

~skill.commands~ takes an ~agent~ and returns the ~/name~ commands that
agent's workspace offers: ~name~, ~description~, ~argument_hint~ and the
~origin~ harness.  ~skill.expand~ takes ~agent~, ~name~ and optional
~arguments~ and returns the ~prompt~ to send: for a skill (since
0.51.1) ~Use skill: <name>~, then a blank line and the arguments when
there are any -- never the skill's body; for a command file, its text
with the arguments substituted.

Expansion is **daemon-side on purpose**.  Both graphical clients send
byte-identical text for the same ~/name args~ because there is one
implementation of the argument substitution rather than two that agree
until somebody types a ~$~.  Nothing in that path can start a process:
the command set's shell policy is pinned off, so a skill file declaring
~shell: true~ cannot run code on the daemon's host, and no ~skill.*~
frame waits on anything.

A skill name arriving on any of these frames is **percent-decoded before
it is validated**, because an encoded traversal has to be judged by what
it decodes to: ~%2e%2e%2f~ contains no dot and no slash and is ~../~ the
moment it is unescaped.

~skill.changed~ is published as an event.

*** Skill proposals

What agents proposed with ~clawtilla_skill_propose~.  Each proposal
raises a decision whose id *is* the proposal's id (=skill-proposal-= and
a UUID); a client recognises one with
~clawt_skill_proposal_id_is_valid()~ rather than its own copy of the
rule.

~skill.proposals~ takes an optional ~pending~ (a JSON boolean, default
true; false includes the ones settled in the last week) and returns
~proposals~, oldest first, each with ~id~, ~decision~ (the same id),
~agent~, ~name~, ~kind~ (~create~ or ~update~), ~state~ (~pending~,
~approved~, ~edited~ or ~rejected~), ~reason~, ~description~, ~body~,
~text~ (the whole proposed ~SKILL.md~), ~diff~ (an update's unified diff
against the skill as it is *now*, else null), ~created_at~ and
~settled_at~ (microseconds), ~stale~ (a JSON boolean: the file changed
since the proposal, so approving is refused) and ~warnings~ (the scan's).
Beside them, ~max_per_day~ and ~skills_enabled~ say why a list is empty.

Every member an agent wrote -- ~reason~, ~description~, ~body~, ~text~,
~diff~ -- has been through ~clawt_preamble_escape()~, so render it as
text.  The raw text never crosses: the edit form is prefilled with the
escaped form, so a forged ~[clawtilla]~ line cannot be saved back in
without the person seeing it rewritten.

~skill.proposal_resolve~ takes ~proposal~, ~action~ (~approve~, ~reject~
or ~edit~), an optional ~note~ that is passed to the agent, and for
~edit~ the new ~description~ and ~body~.  It answers the decision too
(with ~approved~, ~edited~ or ~rejected~), publishes ~decision.settled~
and ~skill.changed~, tells the agent, and returns ~proposal~.  Approve is
refused -- and the proposal stays pending -- when the bytes on disk are
not the ones that were reviewed.

~decision.answer~ on a proposal's decision carries it out the same way:
~approve~ approves, ~edit~ is refused (it needs text), and anything else
is a rejection with the answer passed on as the note.  ~decision.dismiss~
and ~decision.delete~ on an open one reject the draft.

*** teach.*

Recording a task, and turning the recording into a skill.

~teach.list~ returns every recording under ~<state_dir>/teach/~, each
with its kind, its agent, how many steps it holds and whether it is
running now.  It carries the *caveats* too, and does so whether or not
the steps are included: a listing that showed a demonstration without
saying what its guard does not cover would be the place somebody decided
it was safe to share.  ~teach.show~ adds the steps, which the listing
deliberately omits -- a demonstration can be twenty thousand of them.

~teach.start~ takes an ~agent~, a ~source~ (~agent~, ~host-demo~ or
~guest-demo~) and an optional ~goal~.  The two demonstration kinds are
refused unless that agent has ~computer.desktop.allow_recording~, which
is a separate grant from ~allow_input~ on purpose.  ~teach.stop~ takes
the ~id~.

Both **defer**: starting and stopping a demonstration is a round trip to
a compositor, over a unix socket on this machine or over SSH into a
guest.  ~teach.synthesize~ defers too, because it is a model call.  A
stop that the backend refused still answers with the trace: the
recording has ended either way, and answering with only an error would
leave somebody thinking their demonstration was lost when it is on disk.

~teach.synthesize~ takes an ~id~ and optional ~provider~ and ~model~, and
returns the ~preview~ -- the whole ~SKILL.md~ the draft would become,
not a summary of it, because that is what the reviewer has to read.  The
draft is kept so that ~teach.commit~ writes exactly what was previewed;
running the model again would create something nobody reviewed.

~teach.commit~ takes the ~id~ and writes the skill **disabled**, through
the same path manual creation uses.  ~teach.remove~ deletes a recording
and its frames, and refuses while it is still running.

~teach.changed~ is published as an event.

*** connector.begin, then connector.await

Authorising takes as long as a person takes, which is far longer than a
request may block -- so it is two frames rather than one.

~connector.begin~ is deferred only as long as the provider takes to hand
over a code, and its reply carries the ~user_code~ and
~verification_uri~ (or, for the authorization-code flow, an
~authorize_url~) plus a ~flow~ id.  That is what a client shows
immediately; waiting for the whole thing before showing anything would
be no use to anybody.

~connector.await~ takes the ~flow~ and is deferred until the person has
approved, refused, or run out of time.  Clients must ask for a longer
timeout than the default -- ~clawt_client_request_full()~ exists for
this, and 900 seconds matches a device code's usual life.

A flow that finishes before anybody asks keeps its answer, so ~await~
gets the same reply whether it arrives before or after: somebody who
started an authorization, walked away and came back should not find the
result was delivered to nobody.

The ~device_code~ is deliberately absent from every reply.  It is the
secret half of the pair -- it authorises the exchange -- while the user
code is the half meant to be read aloud.

~connector.begin~ on a remote connector whose catalogue entry names no
endpoints is deferred through discovery and, with no ~client_id~,
dynamic client registration before it answers; its reply then carries
~auth_server~ too, for the client to show beside the link.

*** connector.discover

Takes ~name~ and asks the connector's server how to sign in to it (RFC
9728 then RFC 8414), keeping what it finds in the connector's 0600 auth
file.  Deferred.  Answers ~sign_in~ (a boolean), and when it is true
~auth_server~, ~source~ (~protected-resource~ or ~origin~) and
~registration~ (whether clawtilla can register itself there).  Finding
nothing is an *answer* -- ~sign_in: false~ with a ~reason~ -- not an
error: most MCP servers take a key, and a client asking straight after an
add must not toast a failure for something that is not wrong.  A
connector with no URL, or whose catalogue entry names its endpoints,
answers the same way at once, with no request made.

*** connector.unauthorized

Sent by a connector's relay when its remote server answers 401.  Takes
~name~ and, optionally, ~challenge~ (the ~WWW-Authenticate~ header).
Records that a sign-in is wanted and the challenge's ~resource_metadata~
hint for the next discovery, publishes ~integration.changed~ the first
time, and answers an empty object at once: the relay is in the middle of
a tool call, and nothing here goes to the network.  Kept in memory only
-- a restarted daemon learns it again on the next refused call.

*** connector.key

Takes a token and stores it 0600 under ~secrets.dir~.  The reply names
the *file*, never the value: handing the credential back to the client
that sent it would put a live secret into every client's memory.  Same
rule as ~integration.matrix_login~.

*** connector.settings

The two thresholds that make a connector's server a directory.  Takes
~directory_min_tools~ and ~directory_min_chars~, each optional; a member
that is absent is left alone.  Both are checked before either is
written, and a negative one is refused with
~CLAWT_ERROR_INVALID_ARGUMENT~.  Replies with both current values, so an
empty request reads them.

*** connector.tools_seen

Sent by a connector relay (=clawtilla connector relay=) when a whole tool
list has arrived: ~name~, ~agent~, ~tools~, ~chars~, ~areas~ and
~directory~.  The daemon keeps the last report per connector in
=<state_dir>/connector-tools.yaml=; it is what ~connector.list~'s
~tool_count~ and the agent's =TOOLS.org= are made from.  Refused with
~CLAWT_ERROR_NOT_FOUND~ for a name that is not a connector, so a relay
for one since removed does not bring its row back.  No client sends it.

*** connector.result_trimmed

Sent by a connector relay when it trimmed a result to the connector's
budget: ~name~, ~agent~, ~room~ (from ~CLAWTILLA_ROOM_ID~, absent for a
relay run by hand), ~tool~, ~original_bytes~, ~kept_bytes~ and
~result_id~.  The daemon checks the agent holds that connector and puts a
status step in the room whose text is =clawt_mcp_result_notice()='s --
every client draws it as a warning (=clawt_mcp_result_is_notice()=).
With no room it records nothing and answers ~{}~.  No client sends it.

*** connector.app

Sent by a connector relay with *Show its apps in chat* on, when a tool
that ships a view was called: ~agent~, ~room~, and ~app~ -- ~connector~,
~tool~, ~title~, ~resource_uri~, ~html~ (or ~blocked~, why there is none),
~csp~, ~refused~, ~input~ and ~result~.  Refused with
~CLAWT_ERROR_NOT_FOUND~ when the agent holds no such connector and
~CLAWT_ERROR_PERMISSION_DENIED~ when the connector's ~show_apps~ is off --
asked again here, because the relay may predate the switch.  The daemon
gives it an id (~a~ and sixteen hex digits), keeps it 0600 under
=<state_dir>/agents/<agent>/mcp-apps/=, and puts a status step in the
room carrying ~app_id~, ~app_url~ (=clawt_mcp_app_web_url()= of
~connectors.apps_web_url~) and ~app_title~.  Answers ~id~.  No client
sends it.

*** connector.app_get

Takes ~agent~ and ~app~ and answers one app: ~id~, ~agent~, ~connector~,
~tool~, ~title~, ~resource_uri~, ~room~, ~blocked~, ~document~ (the whole
~srcdoc~, the Content-Security-Policy ~<meta>~ first --
=clawt_mcp_app_build_document()=), ~csp~, ~sandbox~ (=allow-scripts=),
~url~, ~created_at~, ~refused~, ~input~ and ~result~.  An app is looked up
under the agent named and nowhere else; an id that is not there is
~CLAWT_ERROR_NOT_FOUND~ whatever the reason.  The web client sets
~document~ verbatim; GTK and lrg ask it before opening ~url~, so a swept
app is a toast rather than a browser on a missing page.

*** connector.app_call

Takes ~agent~, ~app~, ~tool~ (the server's own name) and optionally
~arguments~ (an object, at most 256 KiB as JSON) and runs that tool for
the app's view through =clawtilla connector relay <name> --agent <id>
--app-call= (see [[file:connectors.org::*A view calling its own server's tools][connectors.org]]).  Deferred; the reply is ~result~, the
~tools/call~ result object, which may itself say ~isError~ (the tool
failed, or an action rule refused it).  Refused with
~CLAWT_ERROR_NOT_FOUND~ for an app or connector that is not this agent's,
~CLAWT_ERROR_PERMISSION_DENIED~ when *Show its apps in chat* is off or
the tool is not visible to apps, ~CLAWT_ERROR_NOT_SUPPORTED~ for a
confined agent, and ~CLAWT_ERROR_TIMEOUT~ past ten minutes.  Every call
is recorded in the app's room as the app's (=clawt_mcp_app_call_note()=)
and published as ~connector.app_called~ (subject the agent; ~app~,
~connector~, ~tool~, ~ok~).

A ~turn.step~ event and a ~room.steps~ element may carry ~app_id~,
~app_url~ and ~app_title~ (=CLAWT_STEP_MEMBER_APP=, =_APP_URL=,
=_APP_TITLE=) for a step that shows an app.

*** connector.registry_refresh

Imports the open MCP registry into the connector catalogue, right now
rather than on ~connectors.registry_refresh_hours~'s own timer.  Refused
with ~CLAWT_ERROR_NOT_SUPPORTED~ while ~connectors.registry_enabled~ is
off, and with a plain failure if an import -- from either this verb or
the periodic timer -- is already running.

The fetch itself happens after this handler returns, exactly like
~connector.refresh~: the request is deferred and answered with
~imported~, a count, once the whole paginated walk completes.  A page
partway through when the daemon is asked to stop, or when the request
times out and the client gives up, is not lost -- the walk itself is
unaffected, and the cache is only written once, at the end, so a client
that stopped waiting never sees a half-imported catalogue either.

An entry the registry has never fills a gap; it never replaces a
built-in connector or one from ~connectors.dir~, both of which are a
choice somebody already made on purpose.

*** integration.notify_test

Takes ~integration~ and sends one notification through it, ignoring its
event list and its quiet hours.  A notifier is correct precisely when
nothing happens, so this is the only honest way to check one.

*** Some replies arrive later

~integration.health~, ~integration.matrix_login~,
~integration.matrix_rooms~, ~integration.notify_test~,
~connector.begin~, ~connector.await~, ~connector.discover~,
~connector.refresh~, ~connector.revoke~ and ~connector.registry_refresh~
all wait on the
network, so their handlers
*defer*: the request is answered when the work finishes rather than
before the handler returns.  A client sees nothing different -- the reply
carries the request's id as always -- but the daemon keeps answering
everybody else in the meantime.

This matters because a handler runs on the daemon's main context while
the client blocks.  Waiting there for a ten-second connect timeout is ten
seconds in which no agent's message is routed and no other client is
answered.

~control.status~ is the read-only "what are you" frame, answered from
what the daemon already holds.  Both graphical clients send it once at
connect to compare the daemon's version with their own, and the GTK
client sends it again per saved connection when probing reachability.
For a long time its only caller in the tree was the CLI, which is how a
client talking to a different build came to find out by a frame kind
being refused in whichever feature the person happened to open.

~control.subscribe~ answers ~resumed~, and a client must act on it.  The
daemon replays from a bounded ring of 1024 events, so a cursor that fell
off it comes back ~resumed: false~ -- meaning that client has a hole
nothing will fill.  ~ClawtClient~ emits ~::resync~ for it and both
graphical clients answer by re-reading; before that the only consequence
was a warning in the journal, and the window went on showing state from
before the outage indefinitely.

~computer.exec~ defers for the same reason, with the number rather larger.
It runs whatever command it was given, on the machine, and its advertised
default deadline is 120 seconds -- so answering it inline was two minutes
in which the whole fleet could be silent.  The person at the terminal is
the caller most likely to run something long on purpose, which is what
makes this the sharper of the two exec paths: they can see their own
command still running, so a fleet that has gone quiet reads as the fleet
being broken.

Its ~computer.exec~ event on the stream is published when the command
*ends*, carrying the exit status -- ~-1~ when the command could not be
run at all, which reads as "we do not know what it did" where an absent
entry would read as "it did not happen".

~design.agent~ takes the questionnaire -- ~purpose~ (required),
~boundaries~, ~needs~, ~personality~, ~projects~, ~notes~ -- plus
~provider~ and ~model~ naming which model does the designing.  A single
~description~ is still accepted, so an older client keeps working.  It
returns ~draft~ (a token), ~yaml~, ~id~, ~files~ (the org files the model
wrote) and ~notes~.

~design.commit~ (~draft~) creates exactly what was reviewed.  The
designer is held on the daemon between the two calls rather than the
model being asked again: a second run is a fresh conversation producing
something else, which would make the preview a demonstration rather than
a decision.  ~design.discard~ drops one.  At most eight may be pending.

~model.list~ takes ~refresh~: %TRUE serves the providers' own lists from
a cache, marking those entries ~live~, and refreshes that cache in the
background when it is more than six hours old.  The request never waits
on a provider.

That is not a detail. Asking during the request made it take as long as
the slowest provider, and both the new-agent dialog and the agent
inspector ask on every build -- so pressing + or clicking an agent
appeared to hang for tens of seconds.

The cache is *not* warmed at daemon start.  It was, so that the first
list a client opened was already the real one, but that made every start
call five provider APIs whether or not anybody would ever look -- and it
made ~make test~ reach the network from every daemon fixture, which the
suite is not allowed to do.  The first ~refresh~ request warms it
instead, and is answered from the built-in table while that runs.
The built-in table goes stale -- it offered grok-3 and grok-4 well after
4.5 and 4.6 had shipped -- so anywhere a list is shown to a person should
ask for this. A provider with no key, or no network, falls back to the
table rather than returning nothing, and the call is bounded so a
provider that never answers cannot hang the daemon.

~design.agent~ takes ~id~ and ~name~: when present they are pinned and
the model cannot change them.

~model.list~ returns the providers clawtilla knows about, each with its
models, ~open_ended~, ~agent~ and ~tools~.  It comes from the daemon
rather than being built into each client so the CLI, the GTK app and the
web client cannot disagree about what exists.

~agent~ and ~tools~ are what a client filters on, and they answer two
different questions.  ~agent~ is whether libreclaw can run an agent on
it -- the CLI backends libreclaw's ~lc_provider_type_normalize()~ names
(eight today), and libreclaw refuses anything else, so offering the rest
let a person pick OpenAI and get an agent that cannot run a turn.  (It
used to be rewritten to ~claude-code~ instead, which ran Claude Code with
~gpt-4o~ in the model field.)  ~tools~ is whether it can
be given tool definitions, which is what the agent designer needs.  A
client that filters on neither is offering both lists at once, and
roughly half of what it shows will not work.

~image.list~ returns ~default~, ~open_ended~ (always true) and an
~images~ array of {~reference~, ~label~, ~note~, ~group~}.  The user's
own entries from ~defaults.container_images~ come first, under the group
"Yours", followed by the built-in suggestions.  Nothing validates
~computer.container.image~ against it.

Each provider carries ~tools~: %TRUE when it can be given tool
definitions, which is what decides whether it can design an agent.  The
CLI-backed providers cannot.  A client filtering on it should treat a
missing member as "yes" -- an older daemon does not report it, and
filtering on absence empties the list.

Each provider carries ~open_ended~.  When it is true the list is a
starting point rather than the whole truth -- Ollama runs whatever you
have pulled -- and a client must offer a way to type a name that is not
listed.  Nothing validates ~model.model~ against the catalogue.

they are about can file both the same way.

Both ends carry the room -- ~decision.asked~ and ~decision.settled~ alike,
and ~decision.deleted~ too -- because the chat's inline view is a fold
over them: asked tells the chat on screen to draw the question, settled
lets it redraw the card with the outcome (~answer~, ~via~) without asking
again, whichever surface or clock settled it.  ~room~ is absent for a
decision nobody could place.  Every door a decision comes in by
publishes through ~clawt_daemon_publish_decision_asked()~.

~decision.deleted~ is published for every deletion; ~decision.settled~
with ~how: deleted~ only when the row was still open.  A list holding
the row must drop it either way, while a count of open questions may
come down only once -- a second ~settled~ for an already-answered row
would take it below the truth.

~agent.state~ is published for *every* state and carries the state's nick
plus a ~detail~ saying why.  ~agent.started~ and ~agent.stopped~ are
published by the frames that asked for them, so an agent that crashed
raises ~agent.state~ and nothing else -- a client that watched only the
pair would show a running agent that is not.

~agent.interrupted~ carries ~killed~, the number of processes signalled.
It is *not* an ~agent.state~ change: the agent is still running, and a
client that redrew its state from this would show it as stopped. What
changes is that it is no longer busy, which is why the daemon lowers the
activity itself rather than waiting for a ~agent.typing~ frame that a
killed turn may never send.

~agent.identity~ is published when an agent is started whose identity
files have reached 80% of what a single command-line argument may hold.
Details: ~verdict~ (the sentence, naming the largest files and what to do
about it), ~bytes~, ~limit~, and ~over~ (~"true"~ once the limit is
passed).  It is a %CLAWT_ALERT_NOTICE, so it reaches both clients' alert
panels rather than only a warning in the journal -- the failure it warns
about is silent right up to the cliff and then presents as a broken CLI.

Nothing is published below the threshold: an event on every start of
every agent is one nobody reads on the agent it matters for.  The numbers
are always available on ~agent.show~, under ~identity~, with a per-file
breakdown.

~task.changed~ is published for every state a task passes through, and
its *subject is the task id* -- which is what ~event.list~ filters on.
Details: ~state~, the enum nickname, matching ~agent.state~; and ~agent~,
the assignee.

The ~agent~ detail is load-bearing rather than decoration.  A pod's
scope is matched against it, so without it a pod built as
~clawtilla->new("researcher")~ would hear about every task in the fleet.

This event did not exist for a long time: the manager's signal was
emitted and connected, but only to decide whether to send a
notification, so a client following a task had to poll ~task.list~ and
podomation's ~on_task_changed~ binding named an event nothing published.

~message~ is published once for every message the daemon routes,
whoever sent it, and its *subject is the room*.  Details: ~id~, ~from~,
~to~ and ~body~, plus ~task~ when the message belongs to one.

The subject matters more than it looks.  It used to be published from
the link handler and named the sender and the body but not the room, so
a client had nothing to match a transcript against; the GTK client fell
back to "is this from the agent I am looking at", and a reply from that
agent to one of its *peers* matched -- so two agents talking to each
other appeared in the user's own chat with one of them.  The message had
been routed correctly the whole time.  Match on the room, which
~room.history~ hands back for exactly this purpose, and on nothing else.

Because every message publishes one, a client must also expect to see a
message it already has: a client that has just connected loads history
*and* is replayed the recent events that history already contains.
Deduplicate on ~id~.

~message.refused~ is published when a loop limit rejects a message,
subject the room, with ~from~, ~to~ and ~reason~.  A refusal on the link
path went only to the log before this, so from outside the two agents
just stopped talking and nothing said why.

~exchange.stalled~ is published when the daemon *ends* an exchange rather
than refusing one more message, subject the room, with ~reason~ (a
#ClawtStallReason nickname) and ~detail~ (what was going round).  A
stalled room refuses everything an agent sends into it, without a turn,
until a person says something there.

The difference from ~message.refused~ is the whole point: a refusal
arrives after the sender has already written the message, so a pair that
will not stop is billed for every refusal.  A client should draw a
stalled room as needing attention rather than as one more rejection.

~turn.timed_out~ is published when a turn is stopped for producing
nothing within ~agents.runtime.turn_timeout_seconds~, or when a member
spends a room's whole ~rooms.turn_timeout_seconds~.  Subject the agent,
with ~reason~ and ~detail~ carrying the sentence written into the thread.

~turn.repeating~ is published when one turn makes the same tool call a
number of times that lands on ~orchestration.repeat_thresholds~.  Subject
the agent, ~detail~ the repeated call.  It is a notice rather than an
error, because at every threshold but the last **nothing has been
stopped** -- clawtilla does not own the model's own tool-call loop and
cannot steer a turn that is already running.  At the last threshold the
turn is interrupted and a ~turn.timed_out~ follows.

~agent.failover~ is published when an agent's libreclaw reports, over its link, that it moved to a fallback backend (~state~ =fallback=) or came back to its own (~state~ =primary=); see ~model.fallbacks~ in [[file:agents.org][agents.org]].  ~provider~ and ~model~ are the backend turns now run on, ~reason~ is =usage-limit=, =rate-limit=, =signed-out= or =unavailable=, ~reset_at~ is the reset the provider named and ~retry_at~ when the primary is tried again (Unix seconds, =0= when unknown), and ~context_lost~ is =true= when the fallback is another CLI or login, so the conversation did not come along.  ~message~ is the sentence from ~clawt_failover_describe()~, which every client shows rather than writing its own.  It is a notice while the agent is away and routine when it is back (~clawt_alert_tier_for_event()~), and ~agent.changed~ follows it.

~agent.contested~ is published when connections claiming one agent id
have taken the link from each other often enough, and fast enough, to be
two live processes rather than one reconnecting.  Subject the agent, with
~evictions~ carrying how many displacements stand against it.  The link
server fences the id at that point: the incumbent keeps the link and
further connections claiming it are refused, whether or not anybody is
listening to this.

The fence is a rate limit rather than a ban, so a rival that never gives
up still takes the link twice per window -- delivery goes from
alternating every few seconds to twice a minute, and the event repeats
once per window while it lasts.  That is deliberate: an incumbent whose
process died without closing its socket must not be able to lock out its
own replacement.  It bounds the damage; ending it is still a person's
job.

It is published rather than moving the agent to ~error~, because the
agent is not the broken part.  On the link that survived the fence it
answers normally, and marking it broken would stop the daemon routing to
something that works; what has to end is a second process outside it.

Clients draw it as an error for a reason that inverts the usual one:
**nothing else about such an agent looks wrong.**  It is running, it has
a link, and its mailbox items read delivered -- so there is no panel
somebody would come across this in, and a routine tier would file the one
event that says so where nobody looks.

~handoff.queued~ is published when an agent asks to give a task away,
subject the *task*, with ~handoff~ (the transfer's own id), ~from~, ~to~
and ~state~ (~queued~).  Nothing has moved yet: a handoff runs when the
turn that asked for it ends, so this says a promise was made rather than
kept.

~handoff.settled~ is published when it finishes one way or another, with
the same members plus ~verdict~ -- a sentence rather than a code, because
it is what an agent reads back out of ~clawtilla_task_status~ and a code
gives it nothing to do.  ~state~ is a #ClawtHandoffState nickname:
~done~, ~failed~, ~denied~, ~busy-gave-up~, ~dropped~ or ~error~.

Only ~done~ is routine.  The other five mean the work did not move and is
still where it was, and they arrived on their own while nobody was
watching that pair, so ~clawt_alert_tier_for_event()~ makes them notices
-- classified on ~state~ rather than on the kind, since a kind-only rule
would put every successful handoff in the loud list and teach somebody to
stop reading it.

~turn.steered~ (since 0.28.0) is published when an agent says a delivery
was steered into the turn it was running (libreclaw's ~chat.steered~ with
~delivered~ or ~indeterminate~), subject the agent, with ~room~,
~message~ (the room message, now carrying ~steered~ in ~room.history~),
~item~ (the mailbox item), ~outcome~ and ~from~.  Clients redraw the room
on it.  ~msg.send~'s reply carries ~steering: true~ when the person's
message goes straight into the running turn under ~agents.steer: all~
instead of being held.  A room history message carries ~steered~ (the
outcome) when it was steered.

~message.steered~ is published when a message to a busy agent is held
rather than routed, subject the agent, with ~room~ and ~held~ (how many
are waiting).  There is no ~message~ event for it yet and nothing in the
transcript: appending it now would make the queued line the active leaf,
so the rest of the turn in flight would hang off a line the model was
never shown.  The ~message~ event arrives when the turn settles and the
held text is delivered.

~room.history~ entries carry ~depth~ -- how far agent-to-agent that
message had travelled -- which is what lets a client show a chain
climbing towards ~max_hops~ instead of an inexplicable wall of polite
agreement.

Two more members, present only when set, on ~room.history~ entries and
on the ~message~ event's detail alike, and integers in both so one
reader serves either source:

- ~acknowledged: 1~ --- an answer the acknowledgement check recorded
  instead of delivering (~orchestration.ack_check_model~).  Draw
  ~clawt_message_ack_label()~ beside it.
- ~merged: N~ --- clawtilla's note that N results were delivered to an
  agent as one turn.  The body is sectioned; read it with
  ~clawt_merge_split()~ and draw the sections.
- ~consult: 1|2~ --- part of a consultation (since 0.22.0): ~1~ is the
  question or the consulted task's assignment, ~2~ the answer the
  consulted turn wrote.  Draw ~clawt_message_consult_label()~, which
  returns nothing for a value it does not know.
- ~interrupted: 1~ --- the daemon's notice that a turn was cut short and
  will not be resumed (it had acted outside the fleet, it was already a
  rerun, or somebody stopped it).  Draw
  ~clawt_message_interrupted_label()~ beside it, apart from ordinary
  talk.  See ~docs/mailboxes.org~, "A turn a restart cut short".
- ~round: N~ --- the round of a group room the message belongs to
  (since 0.18.0).  Draw ~clawt_round_label()~ where it changes.
- ~skipped~ and ~skip_reason~ --- strings: the members a message named
  and was *not* delivered to (comma-separated), because they had already
  answered in its thread of replies or the thread had reached
  =rooms.max_chain=, and why.  Draw ~clawt_round_skip_note()~ under the
  message.  The message itself is in the room for everyone either way.
- ~answer_from~ --- string (since 0.34.2): the message is the daemon's
  notice handing a teammate's answer back to the conversation that asked
  for it (~orchestration.answer_in_request_room~); the value is the
  answering agent.  It also carries ~crosstalk_room~ and
  ~crosstalk_message~, naming the exchange and the answer in it.  Draw
  ~clawt_message_answer_label()~ on it *in place of*
  ~clawt_crosstalk_mark_label()~, with the same Flow action.
- ~waiting_on~ --- string (since 0.34.2): what an agent wrote at the end
  of a turn that asked a teammate something; the value is who it asked.
  Draw the message quietly, with ~clawt_message_waiting_note()~ under it
  (~clawt_message_waiting_tooltip()~ says what it means).
- ~crosstalk_room~ and ~crosstalk_message~ --- strings (since 0.30.0):
  the message is the daemon's summary of agent-to-agent exchanges that
  ended (~orchestration.crosstalk_summary~).  ~crosstalk_room~ names the
  Flow conversation each exchange happened in, space-separated, in the
  order the note numbers its sections; ~crosstalk_message~ is the first
  message of each, paired by position (~-~ where there was none).  Draw
  ~clawt_crosstalk_mark_label()~ on it and one action per room labelled
  ~clawt_crosstalk_flow_label()~ that opens that room on the Flow page;
  split either list with ~clawt_crosstalk_split_targets()~.  The note is
  from ~clawtilla~, is never delivered to the agent, and invites no
  reply.  See "Telling you about cross-talk" in
  [[file:orchestration.org][orchestration.org]].

- ~change~ and ~change_actor~ --- strings (since 0.74.0): the message is
  the daemon's note that the agent's configuration was changed
  (~orchestration.config_notes~).  ~change~ is a ~ClawtChangeKind~ nick
  (~setting~, ~routine~, ~trigger~, ~mount~, ~integration~, ~skill~,
  ~persona~, ~team~, ~created~, ~removed~) for the note's first line;
  ~change_actor~ is who made the change (an agent id, ~user~, ~system~ or
  ~fleet:ALIAS:AGENT~).  Draw it as one compact row -- the kind's icon
  from ~clawt_change_kind_icon()~ (~clawt_change_kind_from_nick()~), then
  the body -- not as a message with a face and a name.  It is from
  ~clawtilla~, never delivered to the agent, and never counted as unread:
  count with ~clawt_unread_should_count_message()~.  See "Telling an
  agent's chat that it was changed" in [[file:orchestration.org][orchestration.org]].

A request frame may carry a top-level ~acting_agent~ (since 0.74.0): the
CLI sets it from ~CLAWTILLA_AGENT_ID~, which every agent's process has,
so a change made from an agent's shell is attributed to that agent in
the change notes and the revision history.  It is a name, never a
credential: the request is judged on the connection's credential, and a
name that is not one of the fleet's agents is ignored.

~turn.step~ is one step of a turn that is still running: a tool the
agent reached for, or a paragraph it wrote between two of them.  It
carries the same members ~room.steps~ does.

It is *ephemeral*.  Unlike every other kind in the table it is delivered
live and then forgotten -- not held in the replay ring, and not written
to the ndjson event log.  Two separate reasons.  The ring is small and
shared, and a turn makes tens of tool calls, so retaining steps would
evict real events within one busy turn and a client resuming from a
cursor would be told its replay was incomplete precisely because an
agent had been working.  The log is the record, and a step is not part
of one: the last thing in a thread is what a finished turn's task result
is inferred from, so a retained step would make "Ran 6 commands" the
recorded outcome of somebody's delegated work.

A step is *not a message*.  It has no id, no sender and no thread, so
there is nothing about it a router could deliver or a reader could reply
to.  That is structural rather than a flag: there is no code path from a
step to a mailbox.  It matters because delivery is what starts a turn --
an agent that took a turn over each step of a peer's turn would answer
its own answers for ever, which is a faster version of what the
five-minute "Still working..." notes used to do.

A client that missed steps catches up with ~room.steps~, not by
replaying the event stream.

~agent.typing~ carries ~typing~ ("true" or "false") and, when the agent
named one, ~room~.  It originates in libreclaw, which raises the
indicator for the whole turn -- from picking the message up to posting
the reply -- so it is what separates an agent that is working from one
that is never going to answer.  It is deliberately not persisted: it
describes right now, and a client that connects late learns the state
from the next transition.

Treat the reply as the end of the turn as well as the indicator
dropping.  The two race, and the message wins often enough that a client
waiting only for ~typing:false~ leaves a spinner running underneath an
answer that has already arrived.

** Cursors and resume

Every event has a sequence number.  A client subscribes with the last one
it saw:

#+begin_src json
{"v":1,"kind":"control.subscribe","id":"r1","payload":{"cursor":41}}
{"v":1,"kind":"control.subscribe","id":"r1","ok":true,
 "payload":{"cursor":57,"resumed":true}}
#+end_src

~resumed: false~ means the cursor had already fallen out of the daemon's
buffer and events are missing.  *A client that gets that must re-fetch
rather than assume it is up to date* -- one that silently accepts a
partial replay carries the hole for the rest of its life and shows stale
state it has no way to notice.

Sequence numbers rather than timestamps, because two events in the same
microsecond are ordinary and a client must not have to guess which of
them it already has.

** Authentication

Over the unix socket: none.  The socket is 0600, so connecting at all
proves you are the owner.

Over TCP: ~control.hello~ with a token, before anything else.  The daemon
refuses to open a TCP listener without a token configured.

A third hello is another fleet's: ~fed.hello~ with a signed stamp (see
[[file:federation.org::#ipc][federation.org]]).  A connection that says it becomes a fleet connection:
~fed.envelope~ and ~fed.invite~ frames only, answered with a signed
envelope, and pushed ~fed.push~ frames from this daemon; every other kind
is refused with =auth=, and it never receives events.  ~fed.*~ frames are
accepted before the token check because each carries its own signature.

The token is either the daemon's own -- the owner credential, from
~daemon.token_file~ or ~<state_dir>/tcp-token~ -- or a paired device's,
from ~device.redeem~.  The owner token is checked first and by itself, so
nothing that happens to devices changes what it opens.  The one frame
allowed before the hello is ~device.redeem~, which is a hello of its own
(see ~device.*~ above).

** Noticing that the other end has gone

A unix peer cannot leave quietly.  Its exit closes the socket and the
reader is told on the next turn of the loop, which is why the local
socket needs nothing here.

A TCP peer can, and does.  A laptop suspends, a tailnet comes back on a
different path, a firewall forgets the flow --- and if neither end
happens to be sending at that moment, *neither end is told anything*.
The connection is not closed and not reset; it simply stops carrying
packets.  Both sides go on believing in it.

That failure is worse than a disconnection in every way that matters.
The daemon writes events into a socket nobody is on the other end of.
The client's read never completes, so nothing fails, so
~clawt_client_set_auto_reconnect()~ never fires --- the window stays
"connected", shows no new message for the rest of the day, and the next
thing typed into it waits out the 120-second request timeout and is
lost.  A client that had *disconnected* would have reconnected,
resumed from its cursor and been handed everything it missed.

So every TCP connection --- both the one the client dials and the one
the daemon accepts --- is armed with keepalive when it is opened:

| ~CLAWT_IPC_KEEPALIVE_IDLE_SECONDS~ | 30 | silence before the kernel starts probing |
| ~CLAWT_IPC_KEEPALIVE_INTERVAL_SECONDS~ | 10 | between probes once one goes unanswered |
| ~CLAWT_IPC_KEEPALIVE_COUNT~ | 3 | unanswered probes that end it |

~SO_KEEPALIVE~ on its own is not the fix, which is why the three timers
are set as well.  The kernel's default idle is *two hours*: a connection
armed and left at the default is reported broken long after the person
watching has given up on the fleet, and long after the message they
typed was lost.  Sixty seconds is short enough that the reconnect
happens before a request times out, and long enough that an ordinary
pause between messages is not mistaken for a failure.  It also keeps a
NAT or a tailnet from forgetting the flow in the first place, since an
idle conversation now sends a packet every thirty seconds.

Recovery is the machinery that already existed: the read fails, the
client disconnects, reconnects, and re-subscribes from the cursor it had
reached, so the events it missed are replayed.  Nothing about that is
new --- it was simply unreachable, because the disconnection it starts
from never happened.

** Backpressure

A client that stops reading has its outbound queue capped and is then
disconnected.  Otherwise a paused GUI or a suspended terminal grows the
daemon's memory without bound while looking healthy.  Dropping a client
is recoverable; running the daemon out of memory is not.

The cap is deliberately *above* the largest legal frame -- twice
~CLAWT_IPC_MAX_FRAME_BYTES~ plus a megabyte, so 17 MiB against a frame
limit of 8.  A single reply may legitimately be 8 MiB, and a cap below
that disconnects a client that is reading perfectly well and blames it
for not reading.

** Robustness

A malformed frame is answered with an error and the connection *stays
open*.  A client that sent something malformed usually recovers, and
dropping it would turn a message-level mistake into a session-level one.

An oversized frame does close the connection: at that point the stream is
no longer trustworthy.

** Versioning

~CLAWT_IPC_VERSION~ increments when the meaning of an existing frame
changes.  Adding a new kind, or a new optional payload member, does not:
an older daemon answers an unknown kind with an error naming it, and an
older client ignores payload members it does not know.

** In code

#+begin_src c
g_autoptr(ClawtClient) client = clawt_client_new(NULL);

if (!clawt_client_connect(client, &error))
    return;

clawt_client_set_auto_reconnect(client, TRUE);
g_signal_connect(client, "event", G_CALLBACK(on_event), self);
clawt_client_subscribe(client, cursor, &resumed, &error);

reply = clawt_client_request(client, "agent.list", NULL, &error);
#+end_src

~clawt_client_request()~ is synchronous: it iterates the caller's main
context until the reply arrives, rather than reading the socket itself.
One reader owns the connection for its whole life, so a request made from
inside an event handler works like any other -- the reader is always
armed, and events reach handlers from an idle rather than from inside the
reader's own callback.

~clawt_client_request_async()~ takes no thread; the same reader completes
its ~GTask~.

Auto-reconnect re-subscribes for you, from the cursor the client had
actually reached -- and the ~resumed~ answer to *that* subscription is
not reported anywhere, in this version.  An embedder should therefore
treat a reconnect as a reason to re-fetch whatever it is showing rather
than as a promise of a complete replay.  ~ClawtClient::disconnected~ is
the signal that says one happened; none of the three shipped clients
connects to it, so there is no example of that in the tree to copy.

An embedding host can skip the socket entirely and call
~clawt_daemon_handle_request()~ with the same frames.
