* What it is

With a VENTURE connector's ~mirror_tasks~ on (since 0.44.0), clawtilla copies the tasks of the agents that connector covers into VENTURE tickets and keeps them current: status, assignee, title, results and notes. VENTURE then shows the fleet's work beside everything else it tracks -- on the ticket board, against the repository, in the activity log under each agent's own account.

VENTURE is never required. With no mirroring connector nothing here runs, and with one, nothing an agent does waits on VENTURE: every change is queued in ~tasks.db~ and sent behind, so a VENTURE that is down only means the queue grows until it is back.

It needs VENTURE 0.10.0 or later (=whoami=, =external_ref=, =Idempotency-Key=, =forge_repo/resolve=). Setting up VENTURE's side -- one account per agent, forges and repositories -- is VENTURE's =docs/clawtilla.org=; the connector itself is [[file:venture-setup.org][venture-setup.org]].

* Turning it on

On each agent's venture connector:

#+begin_src yaml
integrations:
  - name: books-scout
    type: connector
    provider: venture
    instance: https://venture.example
    token_file: ~/.local/share/clawtilla/secrets/connectors/books-scout.json
    scope: selected
    agents: [scout]
    mirror_tasks: true
#+end_src

Or *Mirror tasks as tickets (VENTURE)* in any client's integration form.  An agent's account is the first venture connector it has with ~mirror_tasks~ on.

* Which tasks become tickets

Both of these, or nothing:

1. *An agent with a mirroring account is involved*: the delegator or the assignee.
2. *Its repository is one VENTURE knows*, as that agent's account sees it:
   - the task's project pins one -- ~projects.venture_repo_id~, a VENTURE ~forge_repo~ id -- or else
   - a git remote of the task's checkout (or, without one, of its project's directory) is answered by =GET /api/v1/forge_repo/resolve?url=<remote>=.  Remotes are tried in order, origin first, so a repository with both a public and a self-hosted remote matches whichever VENTURE has.

A task that does not qualify is *skipped*, and its task says why (see [[*Seeing it][Seeing it]]); it is looked at again on its next change, so giving it a checkout or a project later is enough.

* Who writes what

Every write is made with the token of the agent it is about, so VENTURE's activity log and webhooks name the right one:

| What | Written by |
|------+------------|
| the ticket, when the task is first mirrored | the delegator's account (or the assignee's, if the delegator has none) |
| every later change -- status, assignee, title | the assignee's account (or the delegator's) |
| a note's comment | its author's account, when the author has one on the same server; else the assignee's |

*The operator's own account* (since 0.46.0): give one mirroring connector ~service_token_file~ -- a token file for the operator's VENTURE account, kept outside =secrets.dir/connectors/= so no agent's box mounts it -- and that account files the operator's own tasks (the delegator is the operator) and any task where neither agent has an account, which are otherwise not mirrored.  The assignee's account still keeps it current when it has one.

The ticket's =assignee= is the assignee's VENTURE username, learned from =GET /api/v1/whoami= on its own token -- never a guess from its agent id.  An assignee without an account leaves it empty.  When the delegator's and the assignee's connectors point at different VENTURE servers, the delegator's account writes everything, on its own server.

* What the ticket holds

| Ticket field | From the task |
|--------------+---------------|
| =title= | its title, or its id -- only on a ticket clawtilla filed; a ticket taken in through intake keeps the title its author gave it, since the task's own ("#<ticket> <title>", cut at 120 characters) is never written back |
| =description= | the work it was given, up to 8 KiB, with "mirrored from clawtilla task …" |
| =status= | its state, below |
| =assignee= | the assignee's VENTURE username |
| =kind= | =internal= |
| =issue_type= | =task=, or =subtask= under its parent's ticket |
| =parent_id= | its parent's ticket; VENTURE allows no subtask under a subtask, so a grandchild goes under the nearest ticket that is not one |
| =repo_id=, organization | the matched repository and its organization |
| =external_ref= | =clawtilla:<host>:<task id>= |
| =milestone_id=, =goal_id= | its project's ~venture_milestone_id~ and ~venture_goal_id~ (since 0.46.0) |

*The branch* (since 0.46.0): a task with a checkout gets one =ticket_link= on its ticket, written by the assignee: the matched repository, the task's branch, and =origin= =venture= -- so VENTURE's forge loop guard never reads it as an issue raised upstream.  *The pull request* (since 0.48.0): clawtilla opens none itself, but an agent may, and says so.  When a task with a linked branch has a result naming a pull or merge request -- =…/pull/N= (GitHub), =…/pulls/N= (Forgejo, Gitea), =…/-/merge_requests/N= (GitLab) -- the link gets its number and URL, once, and the task's run its number.

| Task state | Ticket status |
|------------+---------------|
| unassigned | =triage= |
| pending | =todo= |
| running | =in_progress= |
| blocked, failed, stalled | =blocked= |
| review | =review= |
| completed | =done= |
| cancelled | =cancelled= |

*Notes become internal comments* -- results, review notes and comments always; progress at most once per ten minutes per task -- each prefixed with its kind and author and carrying =external_ref= =clawtilla:<host>:note:<id>=.

*Only what changed is written.* The mirror keeps a receipt of what it last wrote to each ticket; a later change sends only the fields that differ from it, with the ticket's =version=, so a person's edit to anything else on the ticket is never overwritten.

* The outbox

Every task save and every note queues a row in ~tasks.db~'s =venture_outbox=, in the same transaction as the change itself.  A task's saves coalesce into one row; its notes are a row each, in order.  The mirror drains it every 15 seconds and at once after a change, one request at a time, a task's rows strictly in order.

| VENTURE answers | The mirror |
|-----------------+------------|
| 2xx | records the ticket, version and receipt; done |
| 409 to a create | the ticket exists from an earlier attempt (the same =external_ref=): finds it, in the organization it was filed in, and adopts it |
| 409 to an update | somebody changed the ticket: re-reads its version and sends the same change, twice at most |
| 404 to an update | the ticket was deleted: gives up on the task |
| nothing, 408, 429, 5xx | waits and retries: 30 seconds, doubling, to half an hour |
| 202 | the token's role stages writes (a viewer): gives up -- the account needs an editor membership |
| 401 | the token was refused: gives up, naming the agent and the connector to reconnect |
| any other 4xx | gives up, with VENTURE's own message |

Creates carry =Idempotency-Key=, so a create that timed out and is sent again is answered with the first ticket, not a second.

A row given up on is kept, with its reason, and the task's later rows wait behind it until the operator retries.  One agent's bad token stops only its own tasks.

* Seeing it

A task's details show a *VENTURE* section in every client: the ticket and *Open in VENTURE* when it is kept current; "Waiting to be sent" with the last error while a retry is pending; "Not mirrored" with the reason when it was skipped; "The mirror gave up" with the reason when it did -- and *Retry* for those two.

*The link* (=url=, *Open in VENTURE*) is built by =clawt_venture_record_url()=.  VENTURE is multi-organization and keeps the page scope in a cookie, set by =GET /entity/<organization_id>?back=<path>=, so the link is =<base>/entity/<organization_id>?back=%2Fe%2Fticket%2F<id>=: opening it switches the browser's VENTURE organization to the ticket's (VENTURE remembers the selection, for a year) and lands on the ticket's page, =/e/ticket/<id>=.  When the organization is not known it is the bare page, =<base>/e/ticket/<id>=, which opens in whatever organization the browser last chose.  The organization comes from VENTURE's answer to the create, or from the ticket on intake, else the repository's, and is kept with the ref.  Links stored before this change pointed at the board (=/tickets/<id>=); the store rewrites them to the bare page once, when it opens.  The same link is the URL in an intake task's text.

#+begin_src sh
clawtilla task show task-01m0k6
# venture:  #12 (synced)  https://venture.example/entity/2?back=%2Fe%2Fticket%2F12
clawtilla task venture-retry task-01m0k6
#+end_src

Over IPC, ~task.show~ answers a ~venture~ object (~state~: ~synced~, ~queued~, ~skipped~ or ~dead~; ~ticket~, ~url~, ~instance~, ~reason~), and ~task.venture_retry~ queues the task's dead rows again and looks at a skipped task afresh ([[file:ipc-protocol.org][ipc-protocol.org]]).

* The other direction: changes made in VENTURE (since 0.45.0)

Every minute the mirror reads VENTURE back, with each agent's own token, from a cursor kept in ~tasks.db~ (so a restart picks up where it left off), in *every organization that token reaches* -- the =memberships= its =whoami= lists, each asked for with =organization_id=.  VENTURE answers a list that names no organization from the token's default organization alone, so without this a ticket in an agent's second organization was never read.  Each organization has its own cursors, and one read for the first time is read as a first pass is: changes from a day back, comments from where they stood when the mirror started.  The account's cursor from before is not carried over -- it said where the default organization was up to, nothing about another -- so a comment made in the default organization while the daemon was down for the upgrade is not delivered; a status set then is, from the day's look-back (if the daemon was down less than a day).  A VENTURE whose =whoami= lists no memberships is read once, without an organization, as before.  The same goes for finding a ticket or comment already filed (adoption): it is looked for in its ticket's organization.

- *What changed on its mirrored tickets* (=external_ref__like=clawtilla:<host>:%=, updated since last time).  A change is acted on only when its =version= is newer than the mirror's own last write -- the mirror never reads its own writes back -- and once:
  | The ticket was set to | While the task is | The task |
  |-----------------------+-------------------+----------|
  | =cancelled= | not finished | is cancelled, as the operator would |
  | =done= | in review | is accepted |
  | =todo= or =in_progress= | in review | has changes asked for |
  Review has two doors -- the operator's decision and the ticket's status -- and whichever answers first wins; the task's new state is then written back to the ticket.  Any other edit (a title, a priority, =blocked=) is left as the person set it: the mirror writes only what the task itself changes.
- *Comments on tickets of tasks still going*, after the newest one it has seen.  The first pass only notes where comments are up to, so it never replays a ticket's history.  The mirror's own comments (by their =external_ref=) and the assignee's own (by its account -- which needs VENTURE 0.10.1, the first to record an API comment's author; on 0.10.0 such a comment comes back to the assignee as somebody's) are skipped; anybody else's -- a person's, or another agent's through its own VENTURE tools -- is kept as a note by =venture:<author>= and said to the assignee, fenced as data.  A note from VENTURE is never mirrored back.
- *Intake*, with ~mirror_intake~ (on by default with ~mirror_tasks~): an =internal= ticket assigned to the agent's VENTURE user, still =todo= and carrying no other system's =external_ref=, becomes a task for that agent -- from the operator, titled =#<ticket> <title>=, its title and description fenced as data.  At most ten an hour per agent, counted across all its organizations.  The task is linked to the ticket at once, so the next pass leaves it alone, and the outbox's first update writes the ticket's reference and the task's status -- never its title.  Such a ticket is recognised by its receipt having no =_repo= (the mirror's own tickets always have it), so tickets taken in by earlier versions are covered too; new ones also carry =_intake=.

*Who handed it over* (since 0.47.0): before taking a ticket in, the mirror reads its timeline (=GET /api/v1/activity/ticket/:id=) for whoever made it the agent's -- the newest change setting its assignee, or whoever created it with one.  When that is another fleet agent's own VENTURE account, the ticket is a *delegation from that agent*: the task is from it, and goes to the assignee as its message, so the pair budget (~orchestration.pair_message_budget~) and the hop limit hold it exactly as =clawtilla_delegate= would -- and a refusal fails the task with the reason.  From a person, it is the operator's, as before.  Without this, two agents could hand each other work through VENTURE for ever: work from the operator renews a pair's count.

*Waking it early.*  A signed VENTURE webhook (Settings -> Webhooks, =ticket.*= and =ticket_comment.*=) pointed at a ~provider: venture~ trigger makes the poll run at once instead of within the minute.  The webhook only wakes it: the mirror reads VENTURE with each agent's own token and acts on what it finds there, never on the webhook's body.

* Runs and their cost (since 0.45.0)

A mirrored task that runs is recorded in VENTURE as an *external run* on its ticket (VENTURE's =external_runs=): opened by the assignee's account when the task starts, closed when it finishes with its state (=succeeded=, =failed= or =cancelled=), its branch, a summary from its result, and its *cost* -- every agent's turns on the task, from their usage ledgers, in US dollars.  VENTURE's agent budgets, Runs page and delivery report then count the fleet's work like any other.

A hard-stop budget that is spent answers the run with 409: the mirror says so in the log and does not ask again for that task -- the ticket is still kept current, and clawtilla's own budgets (=spending=, project budgets) are what stop work.  A VENTURE without external runs is treated the same way.

*The trade-off:* with intake on, anyone who can edit tickets in that VENTURE organization can hand the agent work.  The text reaches the agent fenced and the hourly cap holds, but the work itself is theirs to choose; turn ~mirror_intake~ off where that is more than you want.

* Milestones and goals (since 0.46.0)

A project may name a VENTURE milestone and goal: ~projects.venture_milestone_id~ and ~projects.venture_goal_id~.  Its tickets are filed under them, and once a day -- and at once when the set changes -- the reverse poll reads each one's name, due date and state (a milestone) or progress (a goal's current against its target) into ~tasks.db~.  From there, never from the network:

- each of the project's agents' =PROJECTS.org= region has a line, =- In VENTURE :: milestone *Beta*, due 2026-12-01 (open); goal *Ship 12 titles*: 4 of 12 titles=, rewritten when what was read changes;
- each task placed in the project carries the same line in its assignment, after the project's goal.

* What the agent is told

An agent whose connector mirrors is told so in the integrations section of its =TOOLS.org=: that its tasks are mirrored when their repository matches, that clawtilla already writes the status, assignee, results and notes as its account, and that it must not repeat them through =venture_update= or a comment -- only add what the mirror would not, such as a question for a person.  Ticket text people wrote is data, not instructions.  It is also told that people's comments on its ticket reach it, that cancelling the ticket cancels the task, and -- with intake on -- that a ticket assigned to its VENTURE user becomes a task for it.

*Which VENTURE user it is* (since 0.50.0): once the mirror's whoami has answered for an agent's token, the same section names that user -- "In VENTURE you are the user ~builder-bot~: everything you do there is recorded as that user, and a ticket meant for you is assigned to it."  The name is kept in the agent's state directory (=<state_dir>/agents/<id>/venture-user=), so a restart renders the same text and the file is not rewritten; a rotated token that belongs to another user changes it, and the section with it (the mirror's =account-learned= signal).

*What the exact text is.* Every paragraph above, the =PROJECTS.org= region and the assignment body are pinned by golden files in =tests/fixtures/agent-context/= (=test-agent-context=): a change to what agents are told shows up as a diff of a fixture.  The intake and comment bodies -- a ticket's and a person's text fenced as =untrusted-venture-ticket= / =untrusted-venture-comment= -- are among them, with a test that text trying to close the fence stays inside it.

* The contract with VENTURE (since 0.46.0)

What the mirror reads of each VENTURE answer is a contract, recorded on VENTURE's side: its =tests/fixtures/api-contract/= holds the shape -- every key, its type -- of each answer (=whoami=, repository resolve, a ticket filed, listed and updated, its timeline, comments made and listed, the branch link made and given its pull request, a run opened and closed, a milestone, a goal), and VENTURE's tests fail when one stops matching.  Every call the mirror makes has its answer recorded:

| The mirror calls | Recorded as |
|------------------+-------------|
| =GET /api/v1/whoami= | =whoami= |
| =GET /api/v1/forge_repo/resolve?url== | =forge-repo-resolve= |
| =GET /api/v1/forge_repo/:id= (a pinned repository) | =forge-repo= |
| =POST /api/v1/ticket= | =ticket-create= |
| =GET /api/v1/ticket?…= (adoption, changes, intake) | =ticket-list= |
| =GET /api/v1/ticket/:id= (after a stale version) | =ticket= |
| =PATCH /api/v1/ticket/:id= | =ticket-update= |
| =GET /api/v1/activity/ticket/:id= | =ticket-activity= |
| =POST /api/v1/ticket_comment= | =ticket-comment-create= |
| =GET /api/v1/ticket_comment?…= (adoption, the reverse poll) | =ticket-comment-list= |
| =POST /api/v1/ticket_link= | =ticket-link-create= |
| =PATCH /api/v1/ticket_link/:id= (a pull request) | =ticket-link-update= |
| =POST /api/v1/runs/external= | =run-start= |
| =PATCH /api/v1/runs/external/:id= | =run-finish= |
| =GET /api/v1/milestone/:id= | =milestone= |
| =GET /api/v1/goal/:id= | =goal= |

clawtilla keeps a copy in =tests/fixtures/venture/=, and =tests/test-venture-contract.c= checks every key the mirror reads is in it with the type it reads it as.  =make check-venture-contract= (with VENTURE checked out beside clawtilla, or =VENTURE_DIR=) diffs the two copies.

* Seen working

On 2026-11-16 a throwaway VENTURE (0.10.2, a scratch database) and a throwaway two-agent fleet (claude-code, sonnet) were run against each other, with a temporary repository whose remote VENTURE knew:

- an operator task became ticket #1 assigned to the agent's VENTURE user, moved =todo= -> =in_progress= -> =done= as the agent's own account, got the result as an internal comment by =API token #3=, the task branch as a =ticket_link= (origin =venture=), and an external run with its real cost (0.241634 USD);
- two tickets assigned to the agent's user in VENTURE became tasks within a minute (intake), each given its reference by the first update;
- a person's comment on one reached the task's thread as =venture:API token #1=, and cancelling that ticket cancelled the task;
- with VENTURE stopped, the next task still ran and completed -- its ticket showed queued, "VENTURE did not answer" -- and when VENTURE came back the outbox drained by itself;
- a pending task survived the daemon's restart, then ran, and its ticket was kept current.
- an agent whose connector says ~mirror_tasks: false~ had its task left alone -- "Not mirrored" with the reason and Retry on its page -- while the next agent's task, in the same repository, became ticket #1 with *Open in VENTURE* (the web client's task page, screenshotted headless).

And again the same day, for review and for comments reaching a working agent, with the agent's work reviewed by the operator (~review_by: user~):

- a person's VENTURE comment on a pending task -- "the secret word is ORCHID" -- reached the agent, whose result was =ORCHID=; the task went to review and its ticket to =review=;
- setting that ticket to =done= in VENTURE accepted the task;
- on a second task, moving its ticket out of review asked for changes ("round 1"); the agent did the work again, and the operator accepting it in clawtilla set the ticket =done=.

That run found the one thing it was for: a comment made in the minute before the reverse poll's first pass was taken as history and not delivered.  Since 0.48.0 the first pass starts from the newest comment made before the mirror started.

The whole list once more against the released clawtilla 0.49.0 and VENTURE 0.10.6, scripted with a check per step: intake, a comment made the moment the daemon was up reaching the agent (it answered with the comment's word), an agent's task completed with its ticket done, result comment by its own token, branch linked and run costed, the opt-in switch off leaving a task unmirrored, done in VENTURE accepting a reviewed task, cancel in VENTURE, VENTURE down and back with the outbox draining, a pending task surviving a daemon restart, and both task pages screenshotted.

And for 0.50.0 (the same VENTURE 0.10.6), 23 checks, none failing: everything above again, plus the agent's =TOOLS.org= naming its VENTURE user (=lead-bot=, learned from whoami), and a skill test run on a scratch copy of an agent -- passed, never in the saved config, and the copy and its workspace gone once it settled.

And the plan's step 1 in full, on the same versions, with a grok-build agent in the fleet and the GTK client on Xvfb: the grok-build agent's task completed and its ticket went =done=; the chief of staff delegated to it with ~clawtilla_delegate~, and the child's ticket was a =subtask= under the parent's, assigned to the grok agent's VENTURE user; VENTURE's activity log for that ticket shows it created by the delegator's account (=API token #2=) and every later change by the assignee's (=API token #4=); a task waiting on a backlog task was ~blocked~ and so was its ticket; and the GTK client, run under Xvfb against the fleet, showed every agent and the assignment as sent.

* Staged writes as decisions

The mirror is one half of the connector; the other is the staged-write bridge, which turns an agent's =venture_create=, =venture_update= and =venture_delete= into decisions in the operator's inbox.  The whole of it is in [[file:connectors.org::*Staged writes land in the decision inbox][connectors.org]]; what matters on a fleet where every agent has its own connector to one server:

- *Routed by requester.* Each card carries VENTURE's ~origin.name~ -- the staging token's actor, =API token #N= -- and each connector learns its own with =GET /api/v1/whoami=, as the mirror does.  Cards are matched by ~origin.token_id~ against whoami's ~token_id~ when the server sends it, falling back to the actor string otherwise.  A card becomes exactly one decision, filed against the agent whose token staged it, and its answer is posted with that agent's token only.
- *One poll per instance.* Connectors that share a base URL are one server, and its queue is read once per tick, not once per connector, with the token of a connector whose whoami has answered.  A connector whose whoami fails holds up only the changes its own token staged; everybody else's are filed as usual.
- *Unknown requester: not raised, left to VENTURE.* A person's change, the operator's own service token's (~service_token_file~), or a card whose origin matches no single connector is filed under nobody.  No token clawtilla holds may honestly answer it, so it is logged once and answered in VENTURE's own interface.

* Troubleshooting

| Seen | Why, and what to do |
|------+---------------------|
| Not mirrored: neither the delegator nor the assignee has a VENTURE connector with mirror_tasks on | turn ~mirror_tasks~ on for one of them |
| Not mirrored: no repository … the task has no checkout | give the task a checkout (~repo~), or its project a ~venture_repo_id~ |
| Not mirrored: no repository in VENTURE matches the task's remotes, or the delegator's account cannot see it | add the =forge_repo= in VENTURE, in an organization that agent's account is a member of -- and mint its token after the membership |
| gave up: VENTURE refused <agent>'s token | mint a new token for that agent and =clawtilla connector connect <connector>=, then Retry |
| gave up: … stages its writes (a viewer?) | give the agent's VENTURE user an editor membership, mint a new token, Retry |
| Waiting to be sent: VENTURE did not answer | VENTURE is down or unreachable; it catches up by itself |
| "venture mirror: … has no credential yet" in the log | the connector has no token file yet: =clawtilla connector connect <connector>= |
| "venture: confirmation … was staged by '…', which is no single connector here" | a person or a token outside the fleet staged it (or one token is configured on two connectors); answer it in VENTURE |
| "venture: could not learn who '<connector>' is", and that agent's staged writes never reach the inbox | that connector's whoami fails (revoked token?); its own cards are held until it answers, nobody else's are: =clawtilla connector connect <connector>= or remove the connector |
| Not mirrored: no repository … cannot see it, though the repository is there | the agent's membership is inactive (made through the API without ~"active": true~) or was added after its token was minted: =whoami= lists no organization; activate it, mint a new token |

* Limits, for now

- A pull request is found only in the task's result: one an agent opened and did not mention is not linked.
- A ticket assigned in VENTURE under a milestone the project does not name is not described to the agent; only the project's own are.
