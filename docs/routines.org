* Routines

A routine is the thing you would otherwise remember to ask for every
morning.  A prompt, an agent, and when to run it.

#+begin_src bash
clawtilla routine add standup chief-of-staff \
    description="Yesterday's commits" \
    instructions="Summarise the last 24 hours of commits, and call out
                  anything risky or missing tests." \
    schedule=weekdays at=09:00
#+end_src

It runs as a *delegated task*, not a message: it appears in
~clawtilla task list~ while it works, and it has a result somebody can
look at afterwards.

*** What a run shares with the conversation

A routine's turn does *not* get a libreclaw session of its own.  This
page said it did for a long time, and it was never true.

libreclaw keys a session on channel, room and sender, and *deliberately
not* on the thread -- the note in its own router says so, because a
thread there anchors a Matrix reply rather than dividing a conversation.
A routine's prompt is sent from ~user~ to the agent, so it lands in the
same room, from the same sender, as the person talking to it.  One
session, one queue.  Three consequences, all real:

- *Runs share context.* Monday's run is in Tuesday's session, and so is
  whatever the operator said in between.
- *A run waits its turn.* Queued behind an in-flight conversation, a
  09:00 brief starts whenever the agent next goes idle.
- *It happens in the operator's chat.* The prompt and the answer are in
  that transcript, because that is the room it went to.

None of that matters for an agent nobody talks to, which is what a
routine wants: *point routines at an agent that is not also a
conversational surface.*  A dedicated agent per routine, or one agent for
all of them, both work; the chief of staff is the wrong choice precisely
because it is the one somebody types at.

*** ...or give the routine a conversation of its own

#+begin_src yaml
routines:
  - id: morning-brief
    agent: chief-of-staff
    isolate: true
#+end_src

=isolate= sends the run to a room of its own from a sender of its own,
which is a session of its own: no inherited context, no waiting behind a
conversation.  *Both halves are needed* --- libreclaw's session key is
channel, room and sender together, so a distinct room reached from =user=
would put every routine on that agent in one session, and a distinct
sender in the operator's room would still be in their transcript.

One room per routine, not per run.  A room per run would be perfect
isolation and no continuity at all, and continuity between a routine's
*own* runs is the thing worth having --- it is what lets Tuesday's brief
know what Monday's said.

If the room cannot be created the run falls back to the shared path and
says nothing about it.  So a routine marked =isolate: true= whose output
turns up in the operator's chat has not been ignored; it failed to get
its room.  Check ~clawtilla room list~ for a =routine:<id>= room before
looking anywhere else.

**The cost is where the output goes.**  The prompt and the answer are no
longer in the operator's chat; they are in the task result and on the
Flow tab, which is where a delegated task's output already lives.  That
is why it is off by default: moving somebody's output is not a thing to
do to them silently, and pointing the routine at an agent nobody talks to
solves the same problem with no setting at all.

** Presets are cron

Every schedule becomes a cron expression, including the friendly ones:

| Preset     | Becomes         | Notes                              |
|------------+-----------------+------------------------------------|
| =manual=   | nothing         | only when you ask                  |
| =hourly=   | =0 * * * *=     | =at= supplies the minute; =at: "00:20"= gives =20 * * * *= |
| =daily=    | =0 9 * * *=     | =at: "09:00"=                      |
| =weekdays= | =0 9 * * 1-5=   |                                    |
| =weekly=   | =0 9 * * 1=     | =weekday: monday=                  |
| =custom=   | whatever you write |                                 |

This is deliberate rather than incidental.  Two implementations of "when
does this next run" would mean the less-exercised one is the one that is
wrong -- and it would be the one behind the friendly buttons, where most
people are.

** Custom schedules

#+begin_src bash
clawtilla routine add sweep researcher schedule=custom \
    cron="0 */6 * * *" instructions="Check the queue and report anything stuck."
#+end_src

Five fields: minute, hour, day-of-month, month, day-of-week.  Ranges,
lists and steps all work (=15,45=, =1-5=, =*/15=, =9-17/2=), months and
weekdays may be named (=jan=, =mon=), and Sunday is both =0= and =7=.

A range that wraps -- =22-2=, =fri-mon= -- means what it looks like.
Vixie cron refuses those; refusing something whose meaning is obvious
helps nobody.

A wrap with a *step* is the one case where it does not.  The stride
restarts at the bottom of the field instead of carrying across the seam,
so =23-4/2= is 23, 0, 2, 4 -- not the 23, 1, 3 a stride counted
continuously round the clock would give.  List the values (=23,1,3=) if
that distinction matters.  A wrap with no step is unaffected, which is
the form people actually write.

*** The oddity worth knowing

When *both* day fields are restricted, the match is day-of-month *OR*
day-of-week.  So:

#+begin_src
0 0 13 * 5     the thirteenth, AND every Friday
0 0 13 * *     the thirteenth
0 0 * * 5      every Friday
#+end_src

=0 0 13 * 5= is not Friday the thirteenth.  This is how every cron since
Vixie's has behaved, and getting it backwards is wrong in a way nobody
notices until the month a routine did not run.

*** What is refused, and when

A bad expression is refused *while you are still looking at what you
typed* -- when the routine is saved, not at the next tick in a warning
nobody is watching for.

#+begin_src bash
$ clawtilla routine add broken researcher schedule=custom cron="0 9 * *" ...
clawtilla: '0 9 * *' has 4 fields; a cron expression has five: minute hour day-of-month month day-of-week
#+end_src

Six fields are refused too.  A seconds field is a different dialect, and
accepting both would make a five-field expression ambiguous -- =0 9 * * *=
would be either nine in the morning or every ninth minute depending on
which we guessed.

*** How far ahead "next" looks

Four years, not one.  =0 0 29 2 *= is a legitimate schedule that fires
once every four years, and a one-year search would report it as
impossible -- so the search window is 1464 days, which is just wide
enough to step from one 29 February to the next.

An expression that matches nothing inside that window has no next time,
and =routine list= shows =-= in the NEXT column.  There are only two
ways to see that: =schedule: manual=, which has no next time by design,
and an expression that cannot fire at all -- =0 0 30 2 *=, say.  A =-=
against a =custom= schedule means the second one.

** Local time, and what that costs twice a year

Schedules are local, because somebody who wrote =09:00= means nine
o'clock where they are.  That has the usual consequences: an hour that
does not exist in spring is skipped, and one that happens twice in autumn
fires twice.  Both are what every other cron does, and the alternative --
silently running everything in UTC -- is a schedule that is an hour wrong
for half the year.

** When the machine was asleep

Routines only fire while the daemon is running.  A machine that was
asleep at nine o'clock has missed nine o'clock, and clawtilla says so
rather than pretending otherwise.

#+begin_src bash
$ clawtilla routine list
ID                 AGENT            SCHEDULE         NEXT                 LAST
standup            researcher       weekdays         Mon 24 Aug 09:00     missed: due 2026-08-21 09:00, but the daemon was not running
#+end_src

*Missed is not failed.*  A routine that did not run because the machine
was asleep is not broken, and showing it as broken would train somebody
to ignore the one that is.

Set =catch_up: true= to run it once when the daemon comes back:

#+begin_src bash
clawtilla routine set standup catch_up=true
#+end_src

*Once*, however many were missed.  A laptop opened after a long weekend
should not deliver a stack of good mornings at once.

Off by default, and worth leaving off for anything that talks to
somebody.

Catch-up is evaluated *once*, at daemon start, before the first tick --
so a routine whose time passed while the daemon was down is dealt with
deliberately rather than found by the first tick and treated as due
right now.  A routine added while the daemon is already running never
passes through it; its first missed run is the ordinary kind.

A routine that has *never* run has not missed anything, so adding one at
four in the afternoon does not immediately fire its 09:00 slot.

With =catch_up= off, a missed run still advances the last-run time.  The
"missed" note is shown once and then cleared, which is why =routine
list= stops mentioning a weekend outage after the routine next fires --
it has not been forgotten, it has been superseded.

** Where it runs

#+begin_src yaml
routines:
  - id: review
    agent: researcher
    instructions: "Review the last day of commits."
    schedule: weekdays
    at: "09:00"
    directory: "/work/clawtilla"
    worktree: true
#+end_src

*Both of these are instructions to the agent, not actions clawtilla
takes.*  They become two sentences appended to the prompt, and the agent
is what obeys them -- there is no =chdir= anywhere in the routine
runner, and clawtilla never creates, lists or removes a git worktree.

=directory= tells the agent to work in a path on its *own computer*,
which for a container or a VM is a path inside it and not on the host.

=worktree= tells it to make a fresh git worktree of that directory and
work there instead.  Worth turning on for a routine that changes files:
it keeps a scheduled run from landing on top of whatever you had checked
out at the time.  The worktree is left behind deliberately -- throwing
away work because a schedule fired is not recoverable.

Knowing that these are prompt text rather than machinery matters when
one is not obeyed.  An agent that ignores =worktree= has not hit a bug
in the scheduler; it has ignored an instruction, which is a question
about the model and the rest of the prompt.

** What does not work yet

=jitter_seconds= is in the schema, is accepted, is saved, and is read by
nothing.  The runner starts a due routine immediately.  It is documented
here rather than quietly, because a setting that is accepted and ignored
is otherwise indistinguishable from one that is working: setting it to
300 and watching a routine fire at 09:00 looks exactly like a very small
random offset.

** What the agent is told

The instructions are the whole of the prompt, plus a short note that this
run is different from a person typing:

#+begin_example
Summarise the last 24 hours of commits.

---
This is the scheduled routine 'standup', started by clawtilla rather than
by a person. Nobody is waiting on this conversation, so asking a question
here reaches nobody -- do the work with what you have, and if something
is genuinely blocking, say so with clawtilla_message_user and stop.
#+end_example

That paragraph earns its place.  An agent that asks a clarifying question
at three in the morning has not done the work, and it has no way to know
from the instructions alone that nobody will answer.

If it does use ~clawtilla_message_user~, a =notify= integration turns
that into something that reaches you -- see
[[file:integrations.org][integrations.org]].

One thing to check before relying on that for anything overnight: a
notify integration has its own =quiet_hours=, and they wrap midnight, so
a 23:00--07:00 window holds everything a 03:00 routine escalates until
morning.  That is the right default for a routine that reports; it is
the wrong one for a routine whose whole purpose is to wake you.  Quiet
hours belong to a notify *instance*, not to a routine, and they silence
that instance completely -- so "wake me for the backup check but not for
anything else" is two instances with different ~events~, one with quiet
hours and one without.  There is no ~routines.quiet_hours~; a routine
cannot exempt itself.

** Trying one before trusting it

#+begin_src bash
clawtilla routine add draft researcher schedule=manual instructions="..."
clawtilla routine run draft
#+end_src

=routine run= ignores both the schedule and =enabled=, which is the
point: a disabled routine you can still run by hand is how you find out
whether the instructions are any good before putting them on a timer.

** Run state

Run state lives in ~<state_dir>/routines.yaml~ -- the *state* directory,
which is ~~/.clawtilla~ by default and is not where ~clawtilla.yaml~
lives.  Separate on purpose: a last-run time is state, and a
~clawtilla.yaml~ that rewrote itself every time a routine fired is one
people stop keeping in git.

It holds four things per routine, not just the timestamp: ~last_run~,
the outcome (~ok~, ~failed~, ~missed~, ~never~), a detail string, and
the id of the task that run created.  That is what fills the LAST column
of ~routine list~, and it is rewritten on every start, every failure and
every missed-run sweep -- written atomically at 0600, since a run's task
id is a handle onto somebody's work.

A state file that cannot be parsed is a warning and an empty slate: it
is a convenience, and refusing to schedule anything because a timestamp
was lost would turn that into a stopped fleet.  The slate errs on the
quiet side -- every routine reads as never having run, so nothing
catches up and nothing is reported missed.  A run that really was missed
is forgotten rather than doubled, which is the right way round for
something that talks to people.

** From the GTK client

The *Routines* page lists what is scheduled, with when each is next due
-- worked out by the daemon, because an expression is not something a
person can check by reading it and "next Mon 25 Aug at 09:00" is.

The editor has the presets as a picker with the cron field revealed only
by *Custom*.  Instructions are a text view rather than an entry, because
a single line teaches people to write a reminder where an instruction is
needed.  *Run now* sits beside *Save* on an existing routine.

** From the CLI

#+begin_src bash
clawtilla routine list
clawtilla routine add <id> <agent> [key=value ...]
clawtilla routine set <id> [key=value ...]
clawtilla routine rm <id>
clawtilla routine run <id>
#+end_src

Every =key= is a schema key, so ~clawtilla config show~ and
[[file:configuration-options.org][configuration-options.org]] are the
reference for what a routine holds.

** Reacting to a routine

Three events, and it is worth being precise about which says what:

| Event | When |
|-------+------|
| ~routine.ran~ | a run *started* -- the task was created and the prompt delivered |
| ~routine.changed~ | the routine itself was added, edited or removed |
| ~task.changed~ | the run's task moved, which is where its success or failure shows up |

~routine.ran~ is not a completion and not a failure.  Every failure path
-- an agent that does not exist, a task that cannot be created, a prompt
that cannot be delivered -- returns before it is published, so a routine
that failed to *start* publishes nothing at all and shows up in the run
state as ~failed~.  A routine that started and then went wrong is a
~task.changed~ to ~failed~.  Binding a pod to ~routine.ran~ expecting to
hear about problems hears about successes.

All three are bindable from a podomation pod as ~on_routine_ran~,
~on_routine_changed~ and ~on_task_changed~ -- the DSL's lexer cannot
parse a dot in an event name.  See [[file:automation.org][automation.org]].
