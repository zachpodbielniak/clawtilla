* Getting started

This gets you from a checkout to two agents talking to each other.  It
takes about ten minutes, most of which is the first build.

** What you need

clawtilla builds on the bare host.  Everything comes from ~pkg-config~,
plus GCC and GNU make.

*** Fedora packages

| Package | Why |
|---------+-----|
| ~glib2-devel~ | glib, gobject, gio, gio-unix, gmodule |
| ~libsoup3-devel~ | HTTP, via libreclaw |
| ~json-glib-devel~ | the wire protocols |
| ~cmark-devel~ | markdown rendering |
| ~sqlite-devel~ | the mailbox store |
| ~libetpan-devel~ | the email integration |
| ~libpq-devel~ | libreclaw's postgres memory |
| ~libdex-devel~ | futures |
| ~libyaml-devel~ | yaml-glib |
| ~libxml2-devel~ | ai-glib's HTML-parsing search providers |
| ~libvirt-devel~ | podomation's ~vm_virtmanager~ module |
| ~gobject-introspection-devel~ | the ~.gir~ / ~.typelib~ step |
| ~gtk4-devel~ | the GTK client |
| ~libadwaita-devel~ | the GTK client |

Every one of those is needed to *build*, whether or not you will use what
it is for: a package missing from ~PKG_DEPS~ makes ~pkg-config~ fail for
the whole list at once, which blanks ~PKG_CFLAGS~ and surfaces as a
misleading ~glib.h: No such file or directory~.  The one exception is
~gobject-introspection-devel~, whose step is skipped with a message when
it is absent; the GTK client is skipped the same way without libadwaita,
because everything else here is headless and still useful.

Runtime, only for the features that use them:

| Package | Needed for |
|---------+------------|
| ~podman~ | ~computer.type: container~ |
| ~distrobox~ | ~computer.type: distrobox~ |
| ~bubblewrap~ | ~computer.host.confine: bwrap~ |
| ~libvirt-daemon-kvm~, ~libvirt-client~ | ~computer.vm.backend: libvirt~ |
| ~qemu-system-x86-core~ (or ~-aarch64-~) | either VM backend |
| ~qemu-img~ | VM disk creation |
| ~virtiofsd~ | mount paths into VMs |
| ~passt~ | reaching a libvirt VM's SSH |
| ~xorriso~ | the cloud-init seed that gives a VM a login |

On Immutablue / Hyacinth Macaw these are layered into the image rather
than installed on the host.  ~libadwaita-devel~, ~libxml2-devel~ and
~libvirt-devel~ are the three most likely to be missing from an older
image.

** Build

#+begin_src bash
git clone --recurse-submodules <url> clawtilla
cd clawtilla
make
#+end_src

If you cloned without ~--recurse-submodules~, ~deps/libreclaw~ is an
empty directory and the build stops there.  This is also the command to
run after any ~git pull~ that moved it:

#+begin_src bash
git submodule update --init --recursive
#+end_src

~--recursive~ is not optional.  libreclaw brings five submodules of its
own -- ai-glib, yaml-glib, mcp-glib, podomation and htmx-glib -- and
without them the failure is a missing header several directories down
rather than anything naming a submodule.

The first build compiles libreclaw and all five, so it takes a while.
Later builds do not.

#+begin_src bash
make test
#+end_src

The suite is hermetic: no network, no podman, no libvirt, no gowl.  If
something fails here, it is clawtilla and not your machine.

** Your first daemon

#+begin_src bash
mkdir -p ~/.clawtilla
./build/release/clawtilla --generate-config > ~/.clawtilla/config.yaml
./build/release/clawtillad --foreground
#+end_src

The generated config is a starter: the options worth deciding immediately
are live, the rest are commented out at their defaults.
[[file:configuration.org][configuration.org]] documents all of them, and
~data/example-config.yaml~ has every option with its default and a
comment.

Leave that running and open another terminal.

*** libreclaw does not need installing first

The daemon runs a ~libreclaw~ per process-runtime agent, and finds it
without being told: beside ~clawtillad~ first, then the
~deps/libreclaw~ build this checkout just produced, then ~PATH~.

So a fresh clone works, with nothing set.  If it ever cannot find one it
says all three places it looked, and ~defaults.libreclaw_binary~
overrides the lot -- worth setting only when the one to run is somewhere
else, such as a second checkout.

Worth not setting it otherwise.  A key somebody set once and forgot is a
config that answers for a machine rather than for the software: this
failure was invisible for months on the machine whose config pinned an
absolute build-tree path, and immediate for everybody cloning fresh.

** Your first agent

#+begin_src bash
./build/release/clawtilla agent create --id researcher \
    --model sonnet --computer none
#+end_src

#+begin_example
Created researcher.
Started it.
#+end_example

An agent with ~--computer none~ is chat-only: no container, no host
access, nothing to provision.  It is the right thing to start with.

*Creating starts it.*  An agent's computer is built when it first starts,
so one created and left alone is a configuration file and no machine --
which looks exactly like a machine that failed to build.  ~--no-start~
declines, and then ~clawtilla agent start~ is the second step.

#+begin_src bash
./build/release/clawtilla agent list
#+end_src

#+begin_example
ID                   STATE      QUEUE  LINK     DESCRIPTION
researcher           running    0      up
#+end_example

~LINK: up~ means the agent dialled back into the daemon and is reachable.
It takes a few seconds after ~running~; until then the column reads ~-~.

** Your first conversation

#+begin_src bash
./build/release/clawtilla chat researcher
#+end_src

Or without the interactive prompt:

#+begin_src bash
./build/release/clawtilla send researcher "what can you do?"
#+end_src

*Messaging an agent that is stopped is not an error.*  The message is
queued in that agent's mailbox and delivered when it next starts.  That
is the whole point of the mailbox; see [[file:mailboxes.org][mailboxes.org]].

#+begin_src bash
./build/release/clawtilla agent stop researcher
./build/release/clawtilla send researcher "look at this when you wake up"
./build/release/clawtilla mailbox list researcher    # one waiting
./build/release/clawtilla agent start researcher     # it arrives
#+end_src

** A fleet that divides its own work

Add a second agent and make one of them the chief of staff:

#+begin_src bash
./build/release/clawtilla agent create --id chief-of-staff --model opus --no-start
./build/release/clawtilla agent set chief-of-staff chief_of_staff true
./build/release/clawtilla agent start chief-of-staff

./build/release/clawtilla room create standup --members chief-of-staff,researcher
./build/release/clawtilla send chief-of-staff \
    "ask the researcher to summarise this week's commits"
#+end_src

~--no-start~ is what earns its place here.  An AI CLI lists its tools
once, when its session starts, so a ~chief_of_staff~ granted to an agent
that is already running reaches its files and not its session -- and the
agent then reports, accurately, that it has no such tool.  Setting it
before the first start avoids the question.

The chief has the orchestration tools -- ~clawtilla_list_agents~,
~clawtilla_delegate~, ~clawtilla_task_status~ -- served to it over its
link.  Watch what it does:

#+begin_src bash
./build/release/clawtilla task list
./build/release/clawtilla room history standup
#+end_src

[[file:orchestration.org][orchestration.org]] works this pattern through
properly, including the limits that stop two agents talking to each
other for ever.

*** Once there are more than a handful

Give them teams.  A team has a lead who assigns work inside it, and the
chief hands whole pieces of work to the lead rather than picking people
itself:

#+begin_src bash
./build/release/clawtilla team create research \
    "Reads sources and answers questions about them. Not for writing code."
./build/release/clawtilla team assign researcher research lead
./build/release/clawtilla team list
#+end_src

Write the description properly.  It is what the chief reads to decide
which team a piece of work belongs to, and a team without one is a team
nothing gets sent to.

Teams are optional, and a fleet of three does not need them.

** Giving an agent a computer

#+begin_src bash
./build/release/clawtilla agent create --id builder \
    --computer container --image registry.fedoraproject.org/fedora:44
./build/release/clawtilla computer exec builder -- uname -a
#+end_src

Pull the image first -- ~podman pull registry.fedoraproject.org/fedora:44~.
Creating does not pull, deliberately, so a typo in an image name fails in
a second rather than after a download.  ~clawtilla image~ lists the ones
clawtilla suggests, and ~clawtilla image vm~ the disk images for a VM
agent, which has to be given one: clawtilla ships none and downloads none,
and a VM with no disk boots nothing.

For host access -- the agent running commands on the machine clawtilla
itself is on -- read [[file:computers.org][computers.org]] first.  It is
the most useful and the most dangerous option, and it is deliberately
awkward to enable by accident.

** The desktop client

#+begin_src bash
./build/release/clawtilla-gtk
#+end_src

Same daemon, same fleet.  Everything the CLI can do the GTK client can
do, and both agree with each other because neither holds any state.

** Reaching the fleet from another machine

If Tailscale is installed and up, ~clawtillad~ already listens on this
machine's tailnet address as well as its unix socket, and said so when it
started:

#+begin_example
ipc: reachable on the tailnet at 100.72.0.41:8792 -- `clawtilla daemon
token` prints the token a remote client needs
#+end_example

A token is always required, so the listener is reachable rather than
open.  On the machine running the fleet:

#+begin_src bash
clawtilla daemon token
#+end_src

On the machine you are sitting at:

#+begin_src bash
clawtilla remote add workstation 100.72.0.41 --token "PASTE-IT-HERE"
clawtilla --profile workstation agent list
#+end_src

The desktop client picks the same saved connections up in the menu left
of its title, so switching between your machines is one click.  It also
takes ~--profile~ directly:

#+begin_src bash
clawtilla-gtk --profile workstation
#+end_src

None of this needs a daemon on the machine you are sitting at.  The
window opens whether or not a local one answers, says so in a banner with
a button that opens the connection menu, and keeps trying in the
background -- so a laptop that has never run ~clawtillad~ is a perfectly
good way to drive a workstation's fleet.  The web client will serve one
too, with the same flags:

#+begin_src bash
clawtilla-web --profile workstation
#+end_src

Turn the whole thing off with ~daemon.tailscale: false~.  See
[[file:security.org][security.org]] for why a tailnet is the one network
this is defensible on.

** Running it as a service

#+begin_src bash
./build/release/clawtilla --generate-systemd-service \
    > ~/.config/systemd/user/clawtilla.service
systemctl --user daemon-reload
systemctl --user enable --now clawtilla
#+end_src

The agents' sockets live under ~$XDG_RUNTIME_DIR~, which systemd removes
when your last session ends.  For a fleet that survives logout:

#+begin_src bash
loginctl enable-linger $USER
#+end_src
