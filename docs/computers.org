* Computers

A computer is what an agent can run commands on.  Five types, and an
optional desktop add-on that works alongside any of them.

| Type | What the agent gets | Isolation |
|------+---------------------+-----------|
| ~none~ | nothing; chat only | total |
| ~host~ | the machine clawtilla runs on | confinement, not isolation |
| ~container~ | a podman container | namespaces |
| ~distrobox~ | a distrobox container, wired into the host | namespaces, deliberately porous |
| ~vm~ | a libvirt or QEMU virtual machine | a kernel of its own |

** Three things that are true of every backend

Worth reading before the backend you actually want, because each of them
produces a failure that looks like something else.

*** ~computer_exec~ takes a command, not a shell line

Every argument is quoted and passed through as it stands, so ~>~, ~|~,
~&&~, ~;~, ~*~ and ~$VAR~ arrive at the command as literal text.  The
failure is the bad kind: ~echo hi > /dev/console~ *exits 0*, prints
~hi > /dev/console~ to stdout, and reports success having done nothing.
Wrap it in ~bash -c~ when you want shell behaviour.  Worked through at
[[*Running things in one][Running things in one]], with the case where it
bites hardest.

*** Output is truncated at 256 KiB

Both stdout and stderr, each, with a visible marker saying how many bytes
were produced.  The marker matters as much as the cut: an agent handed a
silently shortened directory listing treats it as the whole thing and
reaches a confident wrong conclusion, while one told it was cut short
asks a narrower question instead.

*** ~timeout~ means the same thing on four backends of five

~host~, ~container~ and ~distrobox~ all enforce it, and all mean the same
thing by it: the command is given that many seconds and then abandoned,
with ~CLAWT_ERROR_TIMEOUT~ and a message saying it may still be running.
A ~timeout~ of 0 means no deadline.

The odd one out is ~vm~, which turns it into an SSH ~ConnectTimeout~
capped at 30 seconds -- so there it bounds *reaching* the guest rather
than the command that runs in it.  A long command in a VM still needs its
own bound inside the guest.

A pod handler runs to completion and has no deadline to pass down, so for
~container~ and ~distrobox~ the bound is held on clawtilla's side by
~clawt_pod_bridge_call_bounded()~.  The command is not cancelled -- it
cannot be, once podman has it -- it is stopped being waited for, which is
why the message says so rather than reporting the command as killed.

This is not what these two backends used to do.  Both took ~timeout~ and
discarded it, each with a comment explaining that podomation offered no
deadline to pass on.  That was true and it was an argument for holding
the bound rather than for not having one: the tool schema advertises a
120-second default, so an agent planned around a deadline that never
arrived and a command that hung hung for the life of the daemon.  It
showed only against a quiet podman, because any answer at all -- even an
error -- ends the wait.

*** Nobody waits on the daemon's main thread for it

A command takes as long as the command takes, and whoever asked for it
chose the command.  Both callers -- the agent's ~clawtilla_computer_exec~
tool and the operator's ~computer.exec~ verb -- run the wait on a worker
through ~clawt_computer_exec_async()~ and answer when it ends, so the
fleet keeps routing messages, delivering tasks and firing timers
throughout.

One function, not one per caller.  Two implementations of "get off the
main thread" would differ exactly once, on the case nobody looked at,
and that is precisely what happened here the first time: the agent's path
was moved and the operator's was left, which was the worse of the two.

The context the answer arrives on is *named* by the daemon rather than
taken from whatever happened to be thread-default, because
~g_task_new()~ captures the thread-default of the calling thread and
dispatching a source pushes nothing -- so a caller reached from an idle
of its own would have its answer delivered on a loop nobody runs.

** none

The default, and the right starting point.  An agent that answers
questions does not need a container, and a computer it never uses is a
surface that can go wrong.

#+begin_src yaml
computer:
  type: none
#+end_src

** host

The agent runs commands on the machine clawtilla itself is on: real
filesystem, real processes, real network.  The most useful option and the
most dangerous, so it is explicit and layered.

#+begin_src yaml
computer:
  type: host
  host:
    confirm_host_control: true      # required; the daemon refuses without it
    confine: workspace              # none | workspace | allowlist | bwrap
    root: "~/agents/researcher"
    allow_paths: ["~/src", "~/Documents/notes"]
    deny_paths:  ["~/.ssh", "~/.gnupg", "~/.clawtilla/secrets"]
    allow_network: true
    allow_sudo: false
    nice: 5
#+end_src

~computer.host.shell~ is in the schema and is read by nothing.  A host
command is run as an argv through ~GSubprocess~ with no shell involved at
all, which is the point -- see the cross-backend rule above -- so there
is no shell for the key to name.

*** What each confinement mode actually prevents

This section is deliberately blunt, because the difference between
"confined" and "isolated" is where people get hurt.

**** ~confine: none~

Nothing.  A bare ~GSubprocess~.  The agent can do anything you can.

Two independent switches, both required: ~confirm_host_control: true~ on
the agent, and ~daemon.allow_unconfined_host: true~ on the fleet.  An
agent missing either is a shadow with the reason, and the computer
factory refuses to build one as well -- checked twice on purpose, since
the cost of checking twice is nothing against the cost of missing it
once.

The fleet key was in the schema, rendered into the generated config, and
read by nothing for a long time, so one line in one agent block was the
whole gate.

**** ~confine: workspace~ (default)

The working directory is pinned to ~root~, and every argument that looks
like a path is canonicalised with ~realpath()~ and rejected if it escapes.
Canonicalising first is what closes the ~..~ case and the symlink case
together, rather than with two tests that can disagree.

*What it does not stop:* a program that constructs a path clawtilla
cannot see in the argument list.  ~python3 -c "open(chr(47)+'etc/passwd')"~
reads a file the check never had a chance to notice.  Argument inspection
is a guard rail, not a wall.

**** ~confine: allowlist~

~root~ plus ~allow_paths~, minus ~deny_paths~, with the same
canonicalisation.  Denials are checked first and win outright, so
~~/.ssh~ stays out even when all of ~~~ has been allowed -- the other
order would let a broad allow silently defeat every specific deny.

Same limitation as ~workspace~: it inspects arguments.

**** ~confine: bwrap~

A real kernel sandbox, via ~bubblewrap~ (already present on Silverblue --
flatpak depends on it).  The namespace is built from nothing and added
to, which is the only order that fails safe: starting from everything and
removing means each new thing on the host is reachable until somebody
remembers to exclude it.

~/usr~ and ~/etc~ come in ~--ro-bind~.  ~root~ and every entry in
~allow_paths~ come in ~--bind~, which is *read-write* -- there is no
read-only path grant under bwrap, so a path listed there is a path the
agent can write.  ~allow_network: false~ becomes ~--unshare-net~; ~/tmp~
is private; ~--die-with-parent~ means the sandbox goes when the agent
does.

This is the only host mode where a program cannot reach outside by
constructing a path at runtime, because the paths are genuinely not in
its namespace.

*Mounts declared on the agent are the exception worth knowing.*  A mount
declared under ~computer.mounts~ works, because the factory copies its
source into ~allow_paths~.  The workspace and the three exchange
directories are added later, by a different route, and the argv builder
does not read that one -- so under ~confine: bwrap~ those paths pass the
argument check and are then simply absent from the namespace.  A host
agent that needs the exchange wants ~allowlist~, or the exchange root
named in ~allow_paths~ explicitly.

*If ~bwrap~ is missing the agent starts in ~SHADOW~ and says so.*  It
does not silently downgrade to unconfined -- a confinement that quietly
becomes no confinement is worse than none, because you stop checking.

*** sudo

~allow_sudo: false~ blocks ~sudo~, ~pkexec~, ~doas~, ~run0~,
~machinectl~, ~su~ and ~setpriv~ at the exec layer, and says so in the
agent's ~describe~ text so it does not spend turns trying.

Matched on the *basename*, so ~/usr/bin/sudo~ and a bare ~sudo~ are both
caught, and checked inside shell one-liners too -- refusing ~sudo id~
while allowing ~sh -c 'sudo id'~ would be security theatre.

*** The audit trail

A host exec run by a *person* through a client is written to the event
log: agent, command, exit status.

*An agent's own ~clawtilla_computer_exec~ is not.*  That path does not go
through the IPC handler and emits no event, so the audit trail today
covers the case somebody could have looked up in their own shell history
and not the case they would actually want it for.  Worth knowing before
treating the event log as a record of what the fleet ran.

*** In the interface

The GTK sidebar shows a red ~HOST~ badge on any agent with host control,
and the inspector states the confinement mode in words.  This is not
decoration: an agent that can run commands on the real machine should be
visibly different from one that cannot, at a glance, in the list.

** container

#+begin_src yaml
computer:
  type: container
  container:
    image: "fedora:latest"
    name: "clawt-researcher"      # optional; generated if absent
    connection: "unix"            # unix | ssh://… | tcp://… | a named connection
    keep: false                   # keep the container after the agent stops
#+end_src

~computer.container.network~ is parsed and stored and never sent to
podman -- the create call carries the target, image, name, mounts and
command, and nothing else -- so a container gets podman's default network
whatever is written there.

Implemented through podomation's ~container~ module, which speaks the
Podman REST API directly over a socket -- no libcurl, no libpod, no
shelling out to the CLI.

*** Your agent does not run inside its computer

This is the part that surprises people, so it is worth stating plainly.

An agent runs as a libreclaw process on the *host*.  Its own ~bash~,
~read~ and ~write~ tools therefore operate on the host filesystem.  Its
container or VM is a thing it *operates*, reachable only through
~clawtilla_computer_exec~ -- not a thing it lives in.

Nothing said so, and the result was an agent with a perfectly good
container sitting in its workspace running commands on the host and
reporting, correctly, that it did not appear to be in a container.

Three things now say it:

- the scaffolded ~TOOLS.org~ names the container -- ~clawt-<agent>~ --
  and says to run every shell command in it
- ~SOUL.org~ carries it as an operating parameter
- and clawtilla injects it into *every turn* as
  ~agent.prompt_suffix~ in the rendered libreclaw config

The last one matters most.  A resumed session never re-receives the
system prompt, and a long conversation drifts away from anything said
only once at the start; the suffix is appended to every turn, so it
holds on turn 200 as much as turn 1.

Set ~prompt_suffix~ on an agent to add a standing rule of your own.  It
is appended to clawtilla's, not instead of it.

Host agents get a different line -- there is nothing to redirect, so
what they are told instead is that this is somebody's real machine.

*** Which image

Defaults to ~registry.fedoraproject.org/fedora:44~ -- change it once for
the fleet with ~defaults.container_image~, or per agent with
~image~.

Any reference podman can pull works.  clawtilla suggests a list, which
is a starting point and never a restriction:

#+begin_src bash
clawtilla image
#+end_src

Add your own so they show up alongside -- and above -- the built-in
suggestions:

#+begin_src yaml
defaults:
  container_images:
    - "registry.example.com/team/devbox:latest -- ours, has the toolchain"
    - "docker.io/library/haskell:9.10"
#+end_src

The text after ~ -- ~ is a note, shown next to the entry.  Nothing here
is validated: a reference podman cannot pull fails at start with
podman's own error.

The GTK client shows this list as a dropdown with the full reference
underneath, and an /Other.../ entry that reveals a free-text field for
anything not on it.

*Name the registry.*  Every suggestion does.  A bare ~fedora:44~ is
resolved through podman's unqualified-search list, which is per-machine
configuration, so the same clawtilla.yaml can pull different images on
two hosts -- and the difference shows up much later as a missing
package.

*** Pulling

~create~ does not pull, so a typo fails in a second rather than after a
download.  When the image is genuinely absent clawtilla pulls it once and
retries, so picking something from the list works without fetching it by
hand first.  The first start on a new image is therefore slow, and
~clawtilla agent logs~ shows nothing while it happens -- the pull is the
daemon's, not the agent's.

*** Which podman

Rootless, by default: the socket under =XDG_RUNTIME_DIR= when there is
one, the system socket otherwise.  podomation's own default is the *root*
socket, which on a desktop means "Could not connect: Permission denied"
for a daemon the user was never going to be allowed to reach.

Set ~connection~ to point somewhere else -- a URI, a bare socket path, or
a podman named connection.  ="unix"= is the shorthand for "the local
one" and keeps the default.

Rootless needs the socket running:

#+begin_src bash
systemctl --user enable --now podman.socket
#+end_src

*** What the container runs

~command~, defaulting to something long-lived.  A container computer
exists to be exec'd into, and a plain base image's entrypoint exits the
moment it starts -- podman then reports the container as Exited while the
agent still believes it has one, and the first sign is an exec failing
for a reason that makes no sense.

Set it when the image has an entrypoint worth running.  A JSON array is
used as written; anything else is split on spaces.

*** Sharing folders

#+begin_src bash
clawtilla agent mount list researcher
#+end_src

#+begin_src bash
clawtilla agent mount add researcher ~/src/projects /work rw
#+end_src

#+begin_src bash
clawtilla agent mount rm researcher /work
#+end_src

The Agent tab has the same under /Shared folders/, listing what is
shared with a button to stop sharing it.

Changes apply when the computer next starts: a bind mount is part of a
container's creation, not something added to a running one.

*Relabelling defaults to shared* (~:z~).  On Fedora and friends an
unlabelled bind mount is visible inside the container with every access
denied -- which reads like a permissions bug rather than a labelling
one.  It used to default to ~none~, so every shared folder anyone
declared failed with permission denied while the documentation said
shared was usually what you wanted.  ~private~ (~:Z~) relabels the host
directory exclusively for this container and will break anything else
using it; ~none~ is right when the source is already labelled for
container access.

The mount list is the same for a VM, where the entries become virtiofs
devices rather than bind mounts.  You write source, target and mode; the
right kind is filled in from the backend.

*** A container left behind

The container name is derived from the agent id -- =clawt-<agent>= --
so it can be found again after a daemon restart.  If one is still there
when the agent next starts, it is removed and recreated rather than
failing: the name is ours, and a daemon killed at the wrong moment used
to leave an agent that could never start again without running podman by
hand.

*** A container removed behind clawtilla's back

Starting an agent asks the backend what it actually has before it acts on
what it remembers, so =podman rm -f clawt-<agent>= is recoverable:
=clawtilla agent start= notices the container is gone, provisions a new
one, and the agent comes back.

It did not use to be.  The state was written and never read back --
whatever the last operation set is what every surface reported until the
daemon exited -- so a destroyed container left the agent reading
=running= for the life of the process.  The one honest surface was the
agent's own commands, which failed naming a container id nothing could be
correlated with, because the remembered id was preferred over the name
and pointed at something that no longer existed.

Two consequences worth knowing:

- *=computer status= still reports the remembered state.*  Reconciling is
  a round trip to podman, and doing it on a status read would put a
  blocking call on the daemon's main context -- unbounded against a
  wedged podman.  A status read is a memory read; it is the *start* that
  corrects it.  So if a status looks wrong, start the agent and look
  again.
- *Only a 404 is read as "it is gone".*  Podman not running, an
  unreadable socket, a timeout: all of those mean the question could not
  be asked, and treating that as absent would provision a second
  container for an agent that already has one.  A backend that cannot be
  asked does not block the start either --- whatever is wrong produces a
  better message a moment later.

Starting an agent whose container really is running stays a no-op rather
than an error, at every backend.  Refusing it because the daemon believes
the computer is fine would refuse it in exactly the case where that
belief is the thing that is wrong.

*** Where the modules are found
:PROPERTIES:
:CUSTOM_ID: pod-modules
:END:

The ~container~ and ~vm_virtmanager~ modules are built by libreclaw as
loadable ~.so~ files, and looked for in this order:

1. every directory in the ~CLAWT_POD_MODULE_DIR~ environment variable,
   colon-separated
2. ~pod-modules/~ beside the running binary -- ~make~ links this to
   libreclaw's module output, so a build works uninstalled
3. ~modules/~ beside the running binary, where libreclaw itself puts them
4. the install location, ~$(libdir)/clawtilla/pod-modules~

Setting ~daemon.pod_module_dir~ overrides the whole list with that one
directory: a path you named is used literally, so a wrong one fails
loudly rather than being papered over by a stale set found elsewhere.

When no module is found, the error names *every* directory tried.  It
used to name one, which read as an instruction to create that directory
when the real answer was almost always that the modules were sitting in
the build tree.

** distrobox

#+begin_src yaml
computer:
  type: distrobox
  distrobox:
    image: registry.fedoraproject.org/fedora-toolbox:latest
    name: "clawt-researcher"      # optional; generated if absent
    packages: "gcc make git"
    flags: "--nvidia"             # extra flags, passed through to podman
    init: false
    keep: true
    # share_home: true    # see below before turning this on
#+end_src

=flags= is handed to the podomation module as a space-separated string
and passed through to podman -- the escape hatch for anything clawtilla
does not model.  Quote anything containing a space.  Like the rest of the
block it is read once, when the box is created.

A distrobox is a podman container, so everything the container backend
says about isolation applies to the kernel boundary --- and then
distrobox deliberately opens most of it back up.  Inside one the agent
runs as *you*: the same uid, your sockets and displays, your X and
Wayland, and =distrobox-host-exec <command>= to run something out on
the host itself.

That is what makes a distrobox a comfortable place to build things ---
a compiler that can see your real toolchain, a script that can talk to
your session --- and a poor place to put anything that should be
contained.  For that, use =type: container=, which shares none of it.

*** The home directory is the whole question
:PROPERTIES:
:CUSTOM_ID: distrobox-home
:END:

Left to itself, *distrobox mounts your real home directory* into the
box.  That is the tool working exactly as designed, and it is also an
agent that can read your ssh keys, your shell configuration and any
credential you keep in a dotfile.

clawtilla's default is the opposite.  An agent gets a home of its own
under =$XDG_DATA_HOME/clawtilla/boxes/<agent-id>/home=, and yours is
reached only by asking:

#+begin_src yaml
computer:
  distrobox:
    share_home: true
#+end_src

Same shape as the host computer defaulting to ~confine: workspace~
rather than to ~none~: the dangerous option exists, and it is spelled
out rather than arrived at by leaving a field empty.  The two are
indistinguishable from inside the box, which is why the agent is *told*
which one it got --- its own description says either "belongs to you
alone" or "is the operator's real home directory", in those words.

Turn it on when working in your environment is the point: an agent
maintaining your dotfiles, or one that should share your ssh agent.

*** What is fixed at creation
:PROPERTIES:
:CUSTOM_ID: distrobox-creation
:END:

=image=, =home=, =share_home=, =packages=, =flags= and =init= are read
when the box is made and not again, the way a VM's cloud-init reads its
seed once.  Changing one and restarting the agent does nothing visible
--- which reads as the setting not working rather than as the setting
arriving too late.  Remove the box to apply them, or
=clawtilla computer rebuild <agent>=, which does the same thing without
your having to remember the box's name.

=keep= is different: it is read every time the agent stops.

*** keep defaults to true here
:PROPERTIES:
:CUSTOM_ID: distrobox-keep
:END:

Unlike the plain container.  Making a distrobox pulls an image and then
runs a package install inside it, and a distrobox is the kind of
computer somebody chose precisely so that what the agent installs
survives --- so discarding it at every stop would mean paying that cost
on every start.

*** Mounts
:PROPERTIES:
:CUSTOM_ID: distrobox-mounts
:END:

Bind mounts, rendered as distrobox =--volume= arguments with their mode
and SELinux relabel intact.  A =tmpfs= mount is skipped, because
distrobox has no way to ask for one.

*** Requirements
:PROPERTIES:
:CUSTOM_ID: distrobox-requirements
:END:

The =distrobox= package, and podman, which it drives.  A missing
=distrobox= binary is reported as such and names the package --- it is
deliberately not the same message as a missing box, because reading it
that way sends you to inspect podman rather than to install anything.

Goes through podomation's =distrobox= module, the same way the
container backend goes through =container=; see [[#pod-modules][the
module search path]] above, which is shared.

The module must be at least the version carried by this checkout.
Earlier ones read a handler's arguments only as the positional tuple the
podomation DSL sends, and clawtilla calls from C, where they are an
=a{sv}= keyed by the same names.  Every argument was therefore dropped
and every action refused for a missing required parameter --- so
=computer.type: distrobox= could not create, start, exec or remove
anything.  The refusal names the argument rather than the marshalling,
which reads as a caller that forgot one; there is nothing to configure
around it, only a module new enough to accept both shapes.

** vm

#+begin_src yaml
computer:
  type: vm
  vm:
    backend: libvirt              # libvirt (default) | qemu
    domain: "clawt-researcher"
    uri: "qemu:///session"
    image: "~/vms/Fedora-Cloud-Base-44.qcow2"
    cpus: 2
    memory_mb: 4096
    ssh_user: "agent"
    cloud_init: true
    snapshot_on_start: true
#+end_src

That is the whole configuration for a working VM.  ~ssh_key~,
~ssh_host~ and ~ssh_port~ are all optional: clawtilla generates the key,
forwards the port and fills the address in itself.

*** How big the VM is

#+begin_src yaml
computer:
  type: vm
  vm:
    cpus: 4
    memory_mb: 8192
#+end_src

#+begin_src bash
clawtilla agent set builder computer.vm.cpus 4
clawtilla agent set builder computer.vm.memory_mb 8192
#+end_src

The Agent tab shows /Disk image/, /Cores/, /Memory (MB)/ and /SSH
address/ for a VM agent, and only for one -- no other backend reads them,
and a row that quietly does nothing is worse than no row.

Applied when the domain is defined, so a change takes effect on the next
start.  ~disk_gb~ and ~resolution~ are the same: the disk is grown on the
next provision (shrinking is refused), and the resolution reaches the
virtio GPU as its preferred mode.  None of the four needs the machine
rebuilding -- see [[*What needs the machine rebuilt][What needs the
machine rebuilt]] for the ones that do.

*** Which image

*clawtilla ships no disk image.*  ~image~ is a path to a qcow2 on this
machine, and a VM agent without one is *refused at provision*, naming
this setting.

It used to be allowed, and the result was three symptoms with nothing
connecting them: the domain defined and started with no disk, so its
console was black; SSH answered ~kex_exchange_identification: Connection
reset by peer~, because the forwarded port reached a guest with no sshd;
and virt-manager showed a running VM that had booted nothing.

It will fetch one for you, though.  Images live in
~defaults.image_dir~ (~$XDG_DATA_HOME/clawtilla/images~ by default), one
copy serving the whole fleet:

#+begin_src bash
clawtilla image vm catalog          # what is suggested
clawtilla image vm get fedora-44    # fetch it, with a progress bar
clawtilla image vm list
#+end_src

What is suggested, and which family each belongs to for the purpose of
installing a desktop into it:

| id | family | note |
|---+---+---|
| ~fedora-44~ | fedora | the default, and the only one booted end to end |
| ~fedora-43~ | fedora | the previous release |
| ~centos-stream-10~ | enterprise | closest to RHEL |
| ~debian-13~ | debian | trixie |
| ~debian-12~ | debian | bookworm |
| ~ubuntu-24.04~ | ubuntu | noble |
| ~arch~ | arch | rolling; rebuilt monthly |

~clawtilla image vm catalog~ is the authoritative version of that table
-- this one is here so you can choose before running anything.

In the GTK client the same thing is under the hamburger menu beside the
*+* button: /Settings/ → /Cloud images/, which lists what is here, offers
the suggestions, takes a URL of your own, and shows a bar per download.
Downloads belong to the daemon, so closing that window does not stop one,
and a download begun from the CLI appears in the window and vice versa.

Then point an agent at it -- or pick it from /Disk image/ in the Agent
tab, which lists what has been fetched:

#+begin_src bash
clawtilla agent set researcher computer.vm.image ~/.local/share/clawtilla/images/fedora-44
#+end_src

*** What needs the machine rebuilt

cloud-init acts on its seed at *first boot only*.  So the login, the
desktop, the package list -- everything in that seed -- is fixed for the
life of the machine, and changing it in the config and restarting the
agent looks like it did nothing at all.

| Setting | When it applies |
|---------+-----------------|
| ~ssh_user~, the SSH key | first boot -- rebuild |
| ~desktop.enabled~, ~desktop.flavour~, ~desktop.packages~, ~desktop.mcp_repo~ | first boot -- rebuild |
| the guest's fstab entries for its shares | first boot -- rebuild |
| ~cpus~, ~memory_mb~ | the domain definition -- next start |
| ~disk_gb~ | the next provision; shrinking is refused |
| ~resolution~ | the domain definition -- next start |

Worth stating in one place because people rebuild for things that never
needed it, and restart for things that never take.

#+begin_src bash
clawtilla agent stop deb-tester
clawtilla computer rebuild deb-tester
#+end_src

In the GTK client the same thing is /Rebuild computer/ in the Agent tab,
which is insensitive while the agent runs.  Destroying the machine
underneath a working agent is not something to do carefully; it is
something not to offer.

It destroys the guest and builds it again from the image: the domain, the
overlay, the seed and the generated SSH key all go, and the contents of
the machine with them.  It is also how to get one back that was deleted
outside clawtilla -- though that particular case now recovers on its own.

~computer.rebuild~ is not VM-only, despite everything around it here.  It
tears down and re-provisions a ~container~ or a ~distrobox~ too, and is
refused only for ~type: none~ -- and, for every backend, while the agent
is running.  For a distrobox it is the only way to change the image, the
packages or ~share_home~, which are fixed when the box is created.

*** A guest somebody deleted

Deleting a VM in virt-manager, or a qcow2 with ~rm~, tells clawtilla
nothing.  Starting the agent afterwards builds it again: the state
clawtilla holds is a belief about something another program owns, so it
asks the hypervisor rather than trusting what it remembers.

That was not always true, and the difference was invisible: restarting
the whole *daemon* recovered, because a freshly built computer starts out
knowing nothing and provisions.  Restarting just the *agent* did not.

The contents are gone either way -- what comes back is a fresh guest from
the image, not the machine that was deleted.

*** Where the suggestions come from

The catalog is a starting point, never a restriction: any ~https~ URL to
a qcow2 works, and ~clawtilla image vm get <url>~ takes one directly.

Three of the entries name a *directory* and a pattern rather than a
file, because Fedora and CentOS stamp the compose into the filename.  clawtilla
lists the directory and takes the newest match, so those entries stay
right until the release itself is retired -- and say so plainly when it
is, rather than failing as a 404.

A download is verified only in the sense that a short one is refused: if
the server promised more bytes than it sent, the partial file is deleted
rather than left looking like an image.  Nothing checks a signature, so
an https URL from a distribution you trust is the safe habit.

The base is never written to.  A qcow2 overlay is created per agent
under ~$XDG_DATA_HOME/clawtilla/vms/<agent>/overlay.qcow2~, so several
agents share one base and a wrecked guest is thrown away by deleting one
file.  Deleting the overlay also forgets the guest's host key, because a
rebuilt VM is a different machine answering at the same address.

*Changing ~image~ rebuilds the guest.*  The overlay records the base it
was built on, so one left in place would keep booting the old image for
ever while the config said otherwise -- a setting that silently does
nothing.  The old disk is *moved aside* to ~overlay-superseded.qcow2~
rather than deleted, and the log says where: everything installed inside
that VM is in it, and a config line changing is a poor reason for that to
be unrecoverable.  Delete it when you are sure.  An agent's own work is
in its workspace on the host, which this never touches.

Two things it will *not* do:

- *A disk whose base cannot be read is left exactly as it is.*  The
  usual reason is that a guest is running and holding it -- ~qemu-img~
  refuses an image another process has open -- and unknown is not
  different.  Reading that refusal as "the base changed" once deleted
  the disk of a running VM, which carried on against the unlinked inode
  while the file on disk was replaced by an empty one.
- *A running domain is not touched at all.*  Restarting the daemon
  re-provisions every agent, and a libvirt domain outlives the daemon,
  so this runs routinely against a VM that is up.  Its overlay and its
  seed are left alone; only the address is worked out, because that is
  read from a file.

*Deleting an image an agent is using is refused*, because the overlay
names it: without the base, the VM stops booting at all.  Point the agent
somewhere else first, or insist:

#+begin_src bash
clawtilla image vm rm fedora-44 --force
#+end_src

A plain installer ISO or a desktop image will *not* work unattended: it
has no cloud-init, so nothing creates a login and clawtilla cannot get
in.  Use a cloud image, or prepare your own and set ~cloud_init: false~.

The seed is tested against Fedora Cloud Base, and the mainstream cloud
images -- Fedora, Debian, Ubuntu, CentOS Stream -- work the same way.
Very small images can be a different matter: Alpine's ~nocloud~ image
reads the seed, sets the hostname and installs the key in the right
place, and its ~sshd~ then refuses the login anyway.  If you want one of
those, expect to prepare it yourself and set ~cloud_init: false~.

*** Getting in: cloud-init

A cloud image has no account, no password and no authorised key.  Left
alone it boots perfectly and nothing can enter it, which looks exactly
like a VM that failed to boot.

With ~cloud_init: true~ -- the default -- clawtilla builds a small ISO
labelled ~cidata~, attaches it as a CD-ROM, and cloud-init reads it on
first boot:

- creates ~ssh_user~ (default ~clawt~) with passwordless sudo, and
  nothing else.  The image's own default login -- ~fedora~, ~debian~,
  ~ubuntu~ -- is never created, so the guest has exactly the one account
  clawtilla holds a key for
- authorises the public key, and disables password authentication
- gives that account passwordless ~sudo~, unless it is already root

The key is yours if you name one in ~ssh_key~; otherwise an ed25519 key
is generated per agent beside the overlay.  A generated key has no
passphrase, because the daemon uses it with nobody present to type one.
It is mode 0600 in a mode 0700 directory and it reaches exactly one VM.
An *encrypted* key in ~ssh_key~ is refused with that reason rather than
hanging.

Building the seed needs an ISO writer: ~xorriso~ on Fedora.  Without one,
provisioning stops and says so.

Set ~cloud_init: false~ for an image that already has a login and an
authorised key, and set ~ssh_user~ and ~ssh_key~ to match it.

*** Getting in: the address

Commands run in a VM over SSH -- there is no ~podman exec~ for a guest,
and a guest agent would be one more thing to install inside every image.

Leave ~ssh_host~ unset and clawtilla arranges the route itself: it picks
a free port on 127.0.0.1, forwards it to the guest's port 22, and
remembers the choice in ~$XDG_DATA_HOME/clawtilla/vms/<agent>/ssh-port~.
It has to be remembered -- a libvirt domain is defined with the port
written into its XML, so choosing a new one on the next start would
leave the daemon dialling a port nothing is listening on.

The two backends forward differently:

| Backend | How |
|---------+-----|
| ~qemu~ | ~-netdev user,hostfwd=tcp:127.0.0.1:<port>-:22~ |
| ~libvirt~ | ~<interface type='user'>~ with a passt backend and a ~<portForward>~ |

*libvirt needs passt* (Fedora: ~passt~).  libvirt has no port forwarding
for the SLIRP backend -- a ~<portForward>~ without passt is a rejected
domain, not an unforwarded one.  Without passt installed the VM still
runs, and starting it warns that nothing reaches it; ~ssh_host~ is then
how you say what does.

Set ~ssh_host~ (and ~ssh_port~, if it is not 22) for a VM that lives
somewhere clawtilla did not put it -- a bridged network, another
machine, or a VM that existed before this agent did.  clawtilla forwards
nothing when you do, on the assumption that you have your own route.

Host keys go in a ~known_hosts~ beside the overlay rather than yours.  A
VM rebuilt from the same base answers on the same address with a
different key, which against your own file reads as an attack and is
refused.

*** Running things in one

~clawtilla_computer_exec~ takes a *command and its arguments*, not a
shell line.  Every argument is quoted and passed through as it stands, so
~>~, ~|~, ~&&~, ~;~, ~*~ and ~$VAR~ arrive at the command as literal text
-- the command runs, reports success, and does nothing you were looking
for.  This is the same for every backend.

Wrap it in a shell when you want shell behaviour:

#+begin_src bash
clawtilla computer exec researcher -- bash -c 'echo hi > /tmp/note'
#+end_src

*Writing to a VM's screen* is the case where this bites hardest, because
the naive form looks like it worked.  ~/dev/console~ is the serial
console, and it is what somebody watching in virt-manager sees:

#+begin_src bash
clawtilla computer exec researcher -- bash -c 'echo ">>> hello <<<" > /dev/console'
#+end_src

An agent's ~TOOLS.org~ says all of this, and a VM agent's own description
says it again with its name in it -- it is the kind of thing an agent
otherwise works out by trial and error, and reports as a discovery.

*** The console is black

A serial console shows what is written *while you are attached*.  The
boot messages have already gone by, and an idle guest writes nothing, so
a VM that booted before you opened virt-manager shows an empty screen.
That is not a fault.

Make it say something:

#+begin_src bash
clawtilla computer exec researcher -- bash -c 'echo hello > /dev/console'
#+end_src

A genuinely black screen *from boot* means the domain has no disk -- see
above.

*** virt-manager can take the session away

virt-manager installed as a flatpak ships its own ~virtqemud~, and
opening it can leave that daemon owning
~$XDG_RUNTIME_DIR/libvirt/virtqemud-sock~.  Its sandbox has no QEMU in
it, so every ~qemu:///session~ connection afterwards -- clawtilla's
included -- is answered by a daemon that cannot find an emulator, and
every VM stops working until it exits.

#+begin_src bash
ss -lxp | grep virtqemud-sock
#+end_src

names the process holding it.

*** When libvirt cannot find an emulator

#+begin_example
unsupported configuration: No emulator found for arch 'x86_64'
#+end_example

Not clawtilla: the session daemon has failed to probe QEMU, and *any*
domain will fail to define, including one written by hand.  Confirm with

#+begin_src bash
virsh -c qemu:///session domcapabilities
#+end_src

which will say the same thing.  Restarting the user daemon makes it
probe again:

#+begin_src bash
systemctl --user restart virtqemud.service
#+end_src

and if it persists, the cached probe is stale:

#+begin_src bash
rm -rf ~/.cache/libvirt/qemu/cache/capabilities
#+end_src

*** Stopping one

~shutdown~ first, so the guest flushes its filesystems -- a VM pulled out
from under a running write is how a disk image becomes unbootable.

Shutdown is a *request*, though, and only a guest that is listening
answers it.  One that has hung, or never booted, ignores it for ever, so
after 30 seconds the plug is pulled and the log says why.  Without that
fallback such a VM could not be stopped through clawtilla at all.

*** libvirt (default)

podomation's ~vm_virtmanager~ module: the full 22-action surface,
including snapshots.

*A VM that has been removed is rebuilt.*  Provisioning asks libvirt what
domains exist before asking about this one, so a domain you undefined --
or one that never existed -- is simply built again from scratch.  Asking
after a missing domain directly is loud: the module tries the name, then
tries the same string as a UUID, and libvirt logs both failures, which
put two alarming lines on the daemon's console for the most ordinary
path there is.

The domain carries a UUID derived from its name, so defining it again is
a *re*define.  One defined by an older build keeps whatever UUID libvirt
invented for it: provisioning reads it back and adopts it, rather than
undefining a domain you might care about.  Without one libvirt invents a fresh UUID each time and
then refuses the name it already holds -- ~domain 'clawt-x' already
exists with uuid ...~ -- which meant an agent could be provisioned once
and never started again.  ~snapshot_on_start: true~ is worth having -- an
agent that breaks its VM can be put back rather than rebuilt.

The domain is *persistent*: it is defined once and survives the agent
stopping, which is what makes snapshots and ~virsh~ useful against it.

Removing the agent with ~--with-computer~ undefines it.  ~vm_virtmanager~
did not expose ~undefine~ for a long time, which is why an older
clawtilla left domains behind for somebody to find in virt-manager; it
does now, and teardown takes the guest's disk with the domain.  Without
~--with-computer~ the domain stays defined under ~clawt-<agent>~ and is
yours to remove:

#+begin_src bash
virsh -c qemu:///session undefine clawt-<agent>
#+end_src

*** qemu (fallback)

Spawns ~qemu-system-*~ directly and drives QMP over a unix socket.  A
base image plus a qcow2 overlay; guest commands over SSH.  No libvirtd
required, which matters on a machine where you do not want one.

*** What ends up in the VM's state directory

Everything for one guest, under
~$XDG_DATA_HOME/clawtilla/vms/<agent>/~:

| File | What it is |
|------+------------|
| ~overlay.qcow2~ | the writable disk, backed by ~image~ |
| ~seed.iso~ | the cloud-init seed, labelled ~cidata~ |
| ~cloud-init/~ | the ~user-data~ and ~meta-data~ inside it |
| ~id_ed25519~ | the generated key, when ~ssh_key~ is unset |
| ~ssh-port~ | the forwarded port, remembered across restarts |
| ~known_hosts~ | this agent's guests, kept out of yours |

Deleting the directory starts the guest over from the base image.

*** Removing a VM

~clawtilla agent rm <agent> --with-computer~ destroys the guest: it stops
the domain, undefines it, and deletes the overlay, the seed, the key and
the recorded port.  The agent's *workspace* on the host is never touched
-- that is where its work is.

Without ~--with-computer~ the VM is left exactly as it is.  Removing an
agent from the fleet is reversible and deleting its disk is not, so the
destructive half is opt-in.

Two things this used to get wrong, both worth knowing if you are running
an older build:

- ~ClawtVmComputer~ had no teardown at all, and the base class answered
  TRUE for a missing one -- so the removal *reported success* and left
  the libvirt domain defined and the disk on disk. The only way to find
  out was to open virt-manager and see a VM that should not have been
  there. A backend that cannot destroy itself is now refused by name.
- The state directory survived, so a later agent created with the same
  id silently adopted the old guest instead of starting clean.

If you have such a leftover, ~virsh -c qemu:///session undefine
clawt-<agent>~ removes the definition and the directory under
~$XDG_DATA_HOME/clawtilla/vms/<agent>~ holds the disk.

A third, fixed later and with the same symptom for containers: a
teardown could refuse with *"the podomation 'container' module is not
loaded"* and leave the container on the machine.

The module was loaded as a side effect of *provisioning*, which happens
at an agent's start --- so start, stop, exec and teardown all depended
on a function that may never have run in this daemon's lifetime.
Removing a stopped agent, or any agent after a daemon restart, found no
module.  A podman container outlives the daemon by design, so this was
the ordinary case rather than an edge one.

~clawt_pod_bridge_call_for()~ loads what it needs now, rather than
assuming somebody else already did.  That is done in the bridge rather
than at each of the five container call sites, because a new call site
cannot forget what it does not have to remember --- and it covers every
backend, including any added later.

Unlike the VM case above this one *refused* rather than reporting
success, which is the right half to get wrong: the operator was told,
even if what they were told named a cause they could do nothing about.
If you have such a leftover, ~podman rm clawt-<agent>~ removes it.

** Mount paths

Mounts are how files get in and out.

#+begin_src yaml
computer:
  type: container
  mounts:
    - source: "~/src/projects"
      target: "/work/projects"
      mode: rw
      relabel: shared
    - source: "~/Documents/notes"
      target: "/work/notes"
      mode: ro
    - type: tmpfs
      target: "/scratch"
      size: "512M"
#+end_src

| Field | Meaning |
|-------+---------|
| ~source~ | the host path |
| ~target~ | where it appears inside the computer; must be absolute |
| ~mode~ | ~ro~ or ~rw~ |
| ~type~ | ~bind~ (default), ~volume~, ~virtiofs~, ~9p~ or ~tmpfs~ |
| ~create~ | create the source directory if it is missing |
| ~relabel~ | ~none~, ~shared~ (~:z~) or ~private~ (~:Z~) |
| ~required~ | fail rather than warn when the source is missing |
| ~size~ | for ~tmpfs~ |

*** SELinux relabelling

On Fedora Silverblue and friends, an unlabelled bind mount is *visible*
in the container and every access is denied -- a failure that reads like
a permissions bug rather than a labelling one.  Hence ~relabel~.

~shared~ (~:z~) is almost always what you want.  ~private~ (~:Z~)
rewrites the host directory's labels exclusively for one container, so
pointing it at a directory something else also uses will break that other
user.

*** How each backend applies them

| Backend | What a mount becomes |
|---------+----------------------|
| container | mount arguments on the podman ~create~ call |
| distrobox | ~--volume~ arguments on the ~distrobox create~ call, fixed for the box's life |
| libvirt VM | a virtiofs ~<filesystem>~ device written into the domain XML at define time |
| QEMU VM | *nothing* -- see below |
| host | *no kernel mount* -- see below |

Nothing is hot-plugged.  The libvirt device is part of the XML the domain
is defined from, so a mount added to a running VM appears at its next
provision rather than immediately.

The QEMU backend emits no share device at all: it warns, names how many
shares will be missing, and starts the guest without them.  That is
deliberate rather than an oversight -- an earlier version emitted a
~-chardev socket~ that *connected* as a client with no ~virtiofsd~ ever
started to listen, so qemu exited before the guest existed.  Harmless
while nothing had a mount by default; the moment the workspace became one
it would have stopped every VM on that backend.  libvirt is the default
backend and starts a ~virtiofsd~ per share itself, which is why this is a
warning rather than a refusal.

*** Mounts on a host computer

A host computer has no mount namespace, so a mount is not a mount: it is
a promise that a path inside the agent's world means a directory outside
it.  Nothing enforces that promise for us, so clawtilla does two things:

1. *Translates paths.*  An argument naming a mount target is rewritten to
   the source before the command runs.  Otherwise an agent told its
   exchange is at ~/mnt/clawtilla/exchange~ would be refused for using
   the path it was given, which is a maddening thing to debug.
2. *Treats the mount as a grant.*  A mount declared under
   ~computer.mounts~ is reachable in ~workspace~ and ~allowlist~, because
   its source is added to the sandbox's allowed paths.  On a container
   the kernel would make it reachable; the same config behaving
   differently depending on the backend is the kind of inconsistency that
   costs an afternoon.  ~bwrap~ is the exception noted above: the
   workspace and exchange directories the daemon adds are not bound into
   its namespace.

Translation matches whole path components, so ~/mnt/sharedx~ is not
rewritten by a mount at ~/mnt/shared~.  A ~mode: ro~ mount is honoured on
the host as a write refusal, and the most specific mount wins where two
nest.

*** What validation catches

- a relative or non-absolute ~target~
- ~target: /~
- ~..~ in the target
- two mounts with the *same* target -- nesting is allowed on purpose,
  since the exchange itself nests
- a missing source, with and without ~create:~
- a ~tmpfs~ given a source, or a ~volume~ given none

*What it does not catch, despite the code being there:* the refusal to
mount ~daemon.state_dir~ or the secrets directory.  The forbidden-source
list is populated at daemon start and the check that reads it sits inside
the ~tmpfs~ branch of the validator, so a *bind* mount -- which is every
mount anybody writes -- never reaches it.  An agent that could read the
state directory could read every other agent's mailbox and token, so
until that is fixed, check by hand that no mount source is inside
~daemon.state_dir~ or ~secrets.dir~.

There is also no ~..~ check on the mount *source* and no symlink-escape
refusal: ~clawt_mount_resolved_source()~ resolves symlinks rather than
refusing them.

** Shared with every agent

The directory you want *every* agent to see is written once, in
=defaults.mounts=, rather than copied into every agent block and then
forgotten on the next agent you create:

#+begin_src yaml
defaults:
  mounts:
    - source: "~/source"
      target: "/work/source"
      mode: rw
#+end_src

Or from a client:

#+begin_src bash
clawtilla folders add ~/source
clawtilla folders add ~/Documents/notes /work/notes --ro
clawtilla folders list
#+end_src

Settings → Shared folders in both graphical clients does the same.  Omit
the path inside and it is the same path in both places, which is usually
what you want: an agent told about =~/source= then finds it at a name
that reads the same on either side, so a note about a file is a note
either of you can follow.

*** Scoping one to a team, or to named agents
:PROPERTIES:
:CUSTOM_ID: default-mounts-scope
:END:

A folder goes to every agent unless it says otherwise.  Naming a team
covers everyone on it --- including whoever joins later, which is the
whole reason teams exist:

#+begin_src yaml
defaults:
  mounts:
    - source: "~/source"          # everybody
      target: "/work/source"
    - source: "~/src/product"     # the backend team, whoever is on it
      target: "/work/product"
      teams: [backend]
    - source: "~/notes/private"   # one named agent
      target: "/work/private"
      agents: [chief]
#+end_src

#+begin_src bash
clawtilla folders add ~/src/product /work/product --team backend
clawtilla folders add ~/notes/private /work/private --agent chief
#+end_src

The graphical clients take one field and sort it out for you: a name is
a team or an agent, and the fleet already knows which, so being asked to
say is being asked to know something the daemon does.

Same vocabulary as an integration's =scope=, and the *same rule* ---
=clawt_scope_covers()= answers "who gets this" once for both.  They were
going to be two implementations, and two would have differed exactly
once: on an agent named directly *and* on a listed team, which is the
row nobody writes a test for.  =scope: all= is the default, =scope:
selected= is implied by naming a team or an agent, and =scope: none=
parks an entry without giving it to anybody.

Integrations gained =teams:= alongside their =agents:= from the same
change.  Worth thinking about for a *channel*: two agents sharing one
Matrix account answer as the same person, so a team is rarely what you
want there.

A scope that is *written and cannot be read* reaches nobody, and says
so in a warning.  Absent is still everybody --- a list under =defaults=
should mean what the word says --- but a typo that handed your home
directory to the whole fleet is far worse than one that handed it to
nothing.

*** Which agents get them
:PROPERTIES:
:CUSTOM_ID: default-mounts-who
:END:

Container, distrobox and VM agents.  *Not* host agents --- there the
mount list is the confinement allowlist rather than a set of kernel
mounts, so applying a fleet default would quietly widen what a host
agent may reach.  A convenience has no business loosening a boundary,
and the direction that would be wrong in is the dangerous one.

Not chat-only agents either, which have nothing to mount into.

*** Overriding one, and declining all of them
:PROPERTIES:
:CUSTOM_ID: default-mounts-override
:END:

An agent that declares its own mount at the same *target* wins there,
and the default is not also applied:

#+begin_src yaml
agents:
  - id: reviewer
    computer:
      type: container
      mounts:
        - source: "~/source/public"     # this agent sees only the public tree
          target: "/work/source"
          mode: ro
#+end_src

Both being applied would put two mounts at one path, which validation
refuses --- so an agent that customised a single shared folder would
stop starting, naming the path its owner had deliberately chosen.

Declining the lot is a different question and has its own switch:

#+begin_src yaml
agents:
  - id: sealed
    computer:
      type: container
      default_mounts: false
#+end_src

Worth it for an agent whose whole point is that it sees only what it was
given.

*** When one takes effect
:PROPERTIES:
:CUSTOM_ID: default-mounts-timing
:END:

At the agent's next *start*.  A container's bind mounts and a VM's
virtiofs devices are decided when the machine is created, so adding a
folder does not reach one that is already running.  Every client says so
when you add one rather than leaving it to be discovered.

For a *VM that already exists* there is a second half, and it is worth
knowing before you go looking.  The =<filesystem>= device is written
into the domain XML on every provision, so the guest gets the share
--- but the =fstab= entry that mounts it comes from the cloud-init
seed, which is read at *first boot only*.  So a folder added to an
existing VM agent arrives as a virtiofs device that nothing mounts.

Either mount it in the guest once:

#+begin_src bash
clawtilla computer exec <agent> -- sudo mount -t virtiofs <tag> /work/source
#+end_src

or rebuild the machine with ~computer.rebuild~, which writes a fresh
seed.  A container or distrobox agent has no such split --- restarting
it is enough.

*** An agent's own page shows them
:PROPERTIES:
:CUSTOM_ID: default-mounts-visible
:END:

An agent's own /Shared folders/ list reports the mounts it *actually
gets*, with each entry saying whether it came from the fleet.  Reporting
only what the agent declared would show an empty list for an agent that
has two --- two answers to "what do I have", with the wrong one on the
screen somebody is looking at.

*** The agent is told, in its own files
:PROPERTIES:
:CUSTOM_ID: default-mounts-told
:END:

A shared folder is no use to an agent that does not know it is there.
=TOOLS.org= carries a third managed region --- =# BEGIN clawtilla
computer= --- rewritten at every agent start from the computer it
actually ended up with:

#+begin_example
# BEGIN clawtilla computer -- rewritten on every start

The machine you have right now, and the host directories shared
with it. Some of these are shared with every agent in the fleet
rather than configured for you, so they can appear without
anything about you changing.

You have a container of your own... Shared with the host, as host path =
the path inside: /home/me/source = /work/source (read-write), ...
# END clawtilla computer
#+end_example

Written to the *file* rather than left to the =clawtilla_computer_state=
tool, because an agent believes its own files: the file is in the
prompt, and a tool call is something it has to decide to make.  This
tree has recorded that failure twice already --- a chief-of-staff
reading its own stale tool table and concluding it could not create
agents, and a guest desktop telling an agent it was driving the
operator's real screen.

Written at *start*, from the built computer, because that is the only
point that knows what the fleet shared: a default reaches an agent
without any agent block mentioning it.  An earlier version wrote it
during the fleet re-render instead, which also runs for a stopped agent
--- so it filled the region on the first start and emptied it on the
next restart, which is worse than never writing it.

An agent with no computer gets nothing here.  A null computer is still a
computer object, so the first attempt gave chat-only agents a region
saying "You have no computer" wrapped in prose about which side of an
=~=~= is the host --- a distinction with no paths to apply it to.  The
scaffolded section already says it, better.

** What every computer gets

Two shares, without anybody configuring them.

*** The agent's workspace -- ~/mnt/clawtilla/workspace~

The agent's own directory: its persona, its notes, its ~MEMORY.md~, the
files it writes as it goes.  Read-write, and the same file on both sides.

This is what makes anything *produced inside* a computer reachable.  An
agent's ~read~, ~write~ and ~bash~ run on the **host**; only
~clawtilla_computer_exec~ goes inside.  So without this, a file the agent
created in its VM was a file it could not then open -- which is
indistinguishable from a file that was never created.

That is not hypothetical: a VM agent's screenshots land in the guest, and
before this the agent reasoned from window titles for a whole session
rather than looking at the screen, and reported the *capture* as broken.
It was perfect.  It was just somewhere the agent's own tools do not
reach.  A guest desktop now writes its screenshots into
~/mnt/clawtilla/workspace/screenshots~, so they arrive in the agent's
workspace on the host with no copying step to forget.

Turn it off with ~computer.workspace: false~ for an agent whose computer
should hold nothing of clawtilla's.

*** The exchange -- ~/mnt/clawtilla/exchange~

Described below.

*** Both paths, always

Every share has two names, and which one to use depends on which tool is
holding it.  An agent's own ~read~, ~write~ and ~bash~ run on the *host*;
only ~clawtilla_computer_exec~ is inside.  So
~clawt_computer_describe_mounts()~ lists them as
~host path = the path inside~, with the mode, and then says outright
which tool takes which -- because naming only the path inside is what
sent two agents looking on the host at a guest path, finding nothing, and
reporting a share that was working as absent.

Container, distrobox and VM all go through that one function, so the
sentence cannot drift between them.  The *host* backend writes its own
line and writes it the other way round -- ~/mnt/shared (~/src on this
machine)~, target first -- which is harmless where the two are the same
machine, and is one description of one thing in two orders.

** The guest has to mount them

On a container a bind mount is live the moment the container starts.  A
VM is not: the domain gets a ~<filesystem>~ device, which hands the guest
a *tag* and nothing else.  Something still has to mount it.

clawtilla writes the fstab entries into the cloud-init seed, parent
before child -- the exchange nests, and a child mounted first vanishes
under its parent -- with ~nofail~, so a share whose backing daemon did
not start cannot stop the guest booting.

A share is addressed by *tag*, not by path.  clawtilla derives one from
the target -- readable, and short enough for qemu, which refuses a tag
over 36 bytes and refuses the whole device with it, so the domain does
not start:

#+begin_example
/mnt/clawtilla/workspace              ->  workspace-14abab
/mnt/clawtilla/exchange/ubuntu-tester ->  exchange-ubuntu-tester-4106a9
#+end_example

The hash is always there rather than only when the readable half had to
be cut: it is what keeps two different targets from producing one tag,
and a branch that runs only for long paths is exercised by nobody until
the day it matters.  The tag is a pure function of the target and never
changes, because the guest's fstab is written at first boot and the
domain XML on every provision -- a tag that moved would leave the guest
mounting something that is no longer there, quietly, because of
~nofail~.

Two consequences worth knowing:

- Shares are fixed at provision time, like everything else in the seed.
  Adding one to a guest that has already booted needs
  ~clawtilla computer rebuild <agent>~.
- The **qemu fallback backend shares nothing**.  It has no virtiofsd of
  its own, and the device it used to emit pointed at a socket nothing
  listened on -- so qemu exited before the guest existed.  It now warns
  and carries on without the share.  Use ~computer.vm.backend: libvirt~,
  which is the default, if you need shares.

** The exchange directory

A shared drop-box so agents hand files around without hand-wired mounts.

#+begin_src yaml
defaults:
  exchange_dir: "$XDG_DATA_HOME/clawtilla/exchange"
  exchange_max_bytes: 1073741824
#+end_src

It is mounted into every computer at ~/mnt/clawtilla/exchange~ unless the
agent sets ~computer.exchange: false~ -- as three mounts, not one: the
whole exchange read-only, then ~shared/~ and the agent's own directory
read-write on top.  A single read-write mount of the root would make the
write rule below unenforceable, since anything inside the computer could
simply write into another agent's directory.

#+begin_example
exchange/
  shared/          rw for every agent
  <agent-id>/      rw for that agent, ro for the others
#+end_example

Reading is open across the exchange; writing is not.  An agent that could
overwrite another's drop-box could quietly replace the file that agent
was about to act on.

Reachable three ways:

#+begin_src bash
clawtilla cp ~/notes.org researcher:/mnt/clawtilla/exchange/researcher/
#+end_src

- an agent's own ~read~ and ~write~, which run on the *host*, against
  the host-side path -- ~clawtilla_computer_exec~ enters the container or
  VM and sees the path inside it, so the two are different and the
  agent's description states both
- drag-and-drop into the GTK computer panel

*Nothing bounds it today.*  ~clawt_exchange_sweep()~ removes oldest-first
and never follows a symlink out of the directory, and it is called from
nowhere -- not by the daemon's minute sweep, not on start, not by a CLI
verb.  ~defaults.exchange_max_bytes~ is handed to the exchange at
construction and is read only inside that function, so the cap has never
once been applied.  The exchange grows until somebody empties it.

** Desktop control

An add-on rather than a separate type, so it works alongside whichever
computer the agent has:

#+begin_src yaml
computer:
  type: host
  desktop:
    enabled: true
    backend: auto          # auto | gowl | gnome | guest
    socket: "$XDG_RUNTIME_DIR/gowl-mcp.sock"
    allow_input: true      # false = observe only
#+end_src

There are three backends and a selector, and the three divide into two quite different things.
~gowl~ and ~gnome~ drive *the screen a person is sitting at*: gowl through
its own MCP socket, GNOME through ~gnome-desktop-mcp~ on the host.
~guest~ drives a desktop inside the agent's own VM, which is the only one
where a misjudged click lands somewhere recoverable.

~auto~ picks ~guest~ whenever the agent has a VM, and otherwise probes
gowl and then GNOME.  An agent with a machine of its own should be
driving that screen rather than yours.

*Tools arrive through the agent's ~.mcp.json~, not through its link.*  An
AI CLI drops a tool list handed to it in-process -- see the note in
=CLAUDE.md= -- so the only route to an agent's session is a command named
in a config file the CLI finds for itself.

*** A desktop inside the agent's VM

A cloud image has no desktop at all: no display manager, no compositor,
no graphical target.  So ~computer.desktop.enabled~ on a VM agent does
not *find* a desktop, it *builds* one, through the cloud-init seed on the
guest's first boot:

#+begin_src yaml
computer:
  type: vm
  vm:
    image: "~/.local/share/clawtilla/images/Fedora-Cloud-Base-44.qcow2"
    cpus: 2
    memory_mb: 8192
    disk_gb: 128
    desktop:
      user: null           # defaults to ssh_user, or clawt when that is root
      autologin: true
      flavour: auto        # fedora | enterprise | debian | ubuntu | arch
      packages: []         # empty means the family's own list
      mcp: true
      mcp_repo: "https://git.podbielniak.com/zachpodbielniak/gnome-desktop-mcp.git"
  desktop:
    enabled: true
    allow_input: true
#+end_src

The defaults for ~cpus~, ~memory_mb~ and ~disk_gb~ are sized for this:
2 cores, 8 GB and a 128 GB disk.  A cloud image's own disk is a few
gigabytes, which a desktop fills immediately; the overlay is created at
~disk_gb~ instead and cloud-init's ~growpart~ extends the guest's
filesystem to match.  qcow2 is sparse, so it costs what is written rather
than what is asked for.  Raising ~disk_gb~ grows the disk on the next
provision.  *Lowering it is refused*, with a warning: shrinking a disk
discards whatever was past the new end, and a number edited downwards in
a config file is not consent to lose it.

**** Which distribution is in the image

cloud-init picks the package *manager* for you and nothing else, so the
seed has to know the names -- and the names are the smaller half of it.

| | Fedora | Enterprise Linux | Debian | Ubuntu | Arch |
|---+---+---+---+---+---|
| display manager | ~gdm~ | ~gdm~ | ~gdm3~ | ~gdm3~ | ~gdm~ |
| unit enabled | ~gdm.service~ | ~gdm.service~ | ~gdm3.service~ | ~gdm3.service~ | ~gdm.service~ |
| PyGObject | ~python3-gobject~ | ~python3-gobject~ | ~python3-gi~ | ~python3-gi~ | ~python-gobject~ |
| venv | in ~python3~ | in ~python3~ | ~python3-venv~ | ~python3-venv~ | in ~python~ |
| ~glib-compile-schemas~ | in ~glib2~ | in ~glib2~ | ~libglib2.0-bin~ | ~libglib2.0-bin~ | ~glib2-devel~ |
| the ~dconf~ binary | ~dconf~ | ~dconf~ | ~dconf-cli~ | ~dconf-cli~ | ~dconf~ |
| terminal | ~gnome-console~ | ~ptyxis~ | ~gnome-terminal~ | ~gnome-terminal~ | ~gnome-terminal~ |
| browser | ~firefox~ | ~firefox~ | ~firefox-esr~ | ~firefox~ | ~firefox~ |
| upgraded first | no | no | no | no | *yes* |

RHEL 10 replaced GNOME Terminal with Ptyxis, and ~gnome-terminal~ is
simply not in its repositories.  Since cloud-init treats a package it
cannot find as a failure of the *whole* install, asking for it left a
CentOS Stream 10 guest at a text login prompt with no GNOME on it --
over a terminal emulator nobody was going to open.  Every name in that
column was checked against the real CentOS Stream 10 metadata rather
than assumed from Fedora's.

Each of those on its own is enough to leave a guest that installed a
desktop and has no session, or a session with no automation.  Enabling
~gdm.service~ on Debian fails and the machine sits at a text console
with a complete desktop on it; the wrong PyGObject leaves an MCP server
that installs cleanly and dies on its first import; and without
~dconf-cli~ every default written into ~/etc/dconf/db~ stays inert, which
reads as an extension that will not enable.

~flavour: auto~ reads the family off ~computer.vm.image~.  A catalog id
says outright, and an image you downloaded keeps the distribution in its
filename -- including Ubuntu's, which never say "ubuntu" and are named
after the release adjective instead.  When neither says, clawtilla warns
naming the key and the image, and installs Fedora names; it does not
guess quietly, because a wrong guess surfaces as a failed package install
inside a guest's log, a long way from the config line that caused it.

Ubuntu is a family of its own for one entry in that table.  Debian stable
has no ~firefox~ package -- only ~firefox-esr~ -- and Ubuntu has no
~firefox-esr~; either name is wrong on the other distribution, and a
package that does not exist fails the whole install rather than merely
missing a browser.  Worth knowing about the Ubuntu one: ~firefox~ there
is a transitional package that installs the snap, so the first boot
spends a while on snapd and the browser is a confined snap rather than a
deb.  That is the only supported way to get Firefox on Ubuntu; there is
no deb to prefer instead.

A browser is in every list because an agent driving a desktop with
nothing on it can look at a wallpaper and little else.

Arch is the one that is fully upgraded before anything is installed.
cloud-init's ~package_update~ runs ~pacman -Sy~, which refreshes the
index without upgrading what is already there -- and installing against
that is exactly the partial upgrade pacman warns about, where a new
package links against libraries the image still has old versions of.  It
breaks inside the guest, after the desktop appears to have installed.
The seed asks for ~package_upgrade~ as well, which cloud-init runs
between the refresh and the install.  That costs a longer first boot, and
is why it is per family rather than always on: a point release does not
need it.

Arch also publishes two qcow2s and only one of them is any use --
~Arch-Linux-x86_64-basic.qcow2~ has no cloud-init, so a VM built from it
boots perfectly and admits nobody.  The catalog entry points at
~Arch-Linux-x86_64-cloudimg.qcow2~.  It is rebuilt monthly and the
~latest/~ URL follows, so a cached copy ages faster than the others do;
~clawtilla image rm arch~ and re-fetch if a first boot starts failing on
package signatures.

~enterprise~ deliberately asks for less: ~gnome-console~,
~gnome-text-editor~ and ~gnome-tweaks~ are not in the EL10 repositories,
and cloud-init treats a package it cannot find as a failure of the whole
install -- so asking for one takes the desktop down with it rather than
merely missing an editor.

Setting ~packages~ replaces the family's list rather than adding to it,
which is also how you take something out.  It does not reach the packages
the MCP server needs: those are not the desktop, and trimming this list
must not switch automation off by accident.

**** One account, and why it used to be two

~ssh_user~ defaults to ~clawt~, with passwordless sudo.  Commands arrive
as that account and the graphical session belongs to it, so they are the
same login.

It used to default to ~root~, and that was the wrong way round.  GDM
will not log root in -- it is right not to; a GNOME session as root is a
long-standing way to fill a home directory with root-owned files -- so a
desktop VM grew a second account for the screen while every command
still arrived as root.  Anything touching the session then needed a
workaround, and agents duly invented them: re-running things as ~clawt~
with ~XAUTHORITY~ pointed at the Xwayland cookie by hand, which is the
sort of discovery that means something belonged in the software.

It also lines the uid up.  The account is the guest's first, so it is
uid 1000 -- the same as the host user who owns the files on a shared
directory, which root was not.

An agent that needs root writes ~sudo~ and gets it without a password.
Setting ~ssh_user: root~ restores the old arrangement, second account and
all, since GDM's refusal is not clawtilla's to overrule.  A guest built
before this changed has no ~clawt~ account unless it had a desktop, so
name root there explicitly or rebuild it.

**** The guest gets the host's CPU

Naming no CPU is not neutral: libvirt fills in ~qemu64~, which is
x86-64-v1 and has neither SSE4.2 nor AVX.  Most cloud images still boot
on it, which is exactly why it survived -- a current Enterprise Linux
does not, and says so on the serial console while the graphical one
shows nothing at all.

So every domain names ~host-passthrough~, and the qemu fallback backend
passes ~-cpu max~ (rather than ~host~, which is invalid under TCG).  A
named model is deliberately not used: it would be a baseline to be wrong
about again the next time a distribution raises theirs.

**** The size of the screen

~computer.vm.resolution~, as ~WIDTHxHEIGHT~.  1280x800 is the
hypervisor's own default, which is why an agent's screenshots come back
that size unless this says otherwise.

#+begin_src yaml
computer:
  vm:
    resolution: "1920x1080"
#+end_src

Set on the *host*: the virtual GPU reports it as its preferred mode and
GNOME takes it, so there is no per-distribution file to write and
nothing that has to happen at first boot.  Which also means it is one of
the few VM settings that is *not* fixed by the seed -- it applies at the
VM's next boot rather than needing the machine rebuilt.

It costs guest memory: the framebuffer is width x height x 4 bytes.  A
value that is not a screen size is refused when the configuration is
read, rather than by the hypervisor as a domain that will not define.

**** Three families, three names for one file

Autologin is not optional here: the session account's password is
*locked* on purpose -- nothing in the guest can answer a prompt, and
neither can anybody else.  A guest that reaches a login screen is a guest
nobody can get into.

Which makes it worth knowing that GDM's configuration file has three
spellings and no two of them agree by accident:

| Family                   | File                    |
|--------------------------+-------------------------|
| Fedora, Enterprise, Arch | =/etc/gdm/custom.conf=  |
| Debian                   | =/etc/gdm3/daemon.conf= |
| Ubuntu                   | =/etc/gdm3/custom.conf= |

Ubuntu kept the upstream name under Debian's directory, which is the
second thing it does its own way and the reason it is a family of its
own rather than Debian with a different browser.

clawtilla writes exactly one, named in the flavour table beside the unit
name.  It used to write Fedora's and Debian's and let the unread one lie
there, on the reasoning that an unread file costs nothing -- which is
true, and hid the fact that there was a third: an Ubuntu guest installed
a desktop perfectly, ignored both files, and stopped at a login prompt.

**** What is switched on, and why each one matters

Four things would each, on their own, leave the agent looking at a
desktop it cannot touch, and all four are handled in the seed:

- *the extension is enabled* through a dconf system default, because
  ~gnome-extensions enable~ needs a session that does not exist yet;
- *consent is pre-acknowledged*, because the extension opens a modal
  dialog on first enable and nobody is there to dismiss it -- it would
  sit in front of everything the agent tried to look at;
- *automation is switched on* by an autostart entry that calls
  ~SetEnabled~ over D-Bus, retrying, because the extension starts with it
  off and the only other way to flip it is a click on the top bar;
- *the lock screen is disabled*, because nothing in the guest can answer
  one -- screenshots would come back showing a lock screen and clicks
  would land nowhere.

The GNOME Shell extension is not avoidable.  GNOME on Wayland refuses
screenshots and input injection to every process outside the compositor,
so the only way in is code running *inside* GNOME Shell exposing a D-Bus
interface.  ~gnome-desktop-mcp~ is cloned rather than installed from
PyPI, because the extension only exists in the repository and the two
halves have to match: the server calls D-Bus methods that exact extension
has to export.

cloud-init acts on **first boot only**.  Changing ~vm.desktop.user~ or
turning the desktop on for a VM that has already booted means deleting
the overlay, not restarting.

**** Enabling an extension is not installing it

Enabling happens in dconf, before anyone logs in.  Installing means
putting the extension somewhere GNOME Shell looks -- and those are two
separate steps that fail independently.  A guest can have the extension
enabled by name and no extension on disk, which is exactly as broken as
having neither and looks like nothing at all from the host.

GNOME Shell searches ~gnome-shell/extensions~ under each ~XDG_DATA_DIRS~
entry, so clawtilla links the checkout into
=/usr/share/gnome-shell/extensions=.  Only Fedora's ~gnome-shell~ package
ships that directory; on Debian, Ubuntu and Arch it does not exist until
something creates it, and ~ln~ will not create a parent.  The installer
creates it, links the extension, and then tests *through* the link --
a dangling symlink enumerates as a symlink rather than as a directory,
which GNOME Shell skips in silence.

All of it is one script, =/usr/local/bin/clawtilla-desktop-install=,
rather than a list of ~runcmd~ entries.  cloud-init runs ~runcmd~ without
~set -e~: a command that fails is one line in a log inside the guest and
every later command runs anyway.  A script can stop at the step that
failed and say which one it was.

It writes the answer to =/var/lib/clawtilla/desktop-install.status=:

#+begin_src bash
clawtilla computer exec <agent-id> -- cat /var/lib/clawtilla/desktop-install.status
#+end_src

#+begin_example
ok
#+end_example

...or the step that stopped it:

#+begin_example
failed: could not create /usr/share/gnome-shell/extensions
#+end_example

That file is named in the agent's own description of its desktop, so an
agent whose tools return ~DBus object has no attribute~ is told to read
it rather than left to work the answer out from the bus.

The script is safe to run again, which the seed that first ran it is not:

#+begin_src bash
clawtilla computer exec <agent-id> -- /usr/local/bin/clawtilla-desktop-install
#+end_src

Running it does not by itself fix a running guest.  GNOME Shell scans for
extensions when the session starts, so one that arrives afterwards is not
picked up until the session restarts -- on Wayland that means logging out
and back in, which for an autologin guest is a reboot.

**** Starting an application in the guest

~clawtilla_computer_exec~ is an SSH connection.  It has no session
environment -- no ~WAYLAND_DISPLAY~, no ~XDG_RUNTIME_DIR~, no session bus
-- so an agent asked to open a browser arrives at ~DISPLAY=:0 firefox~ on
its own.

The trouble with that is that it *works*.  A window appears and the
process runs, and the application has quietly been put on Xwayland rather
than in the Wayland session the desktop was built for: a different
compositing path and a different route for synthetic input, with nothing
an agent can query to say which of the two it got.

The seed writes a launcher that takes the environment from the session
instead of guessing it:

#+begin_src bash
clawtilla computer exec <agent> -- \
    /usr/local/bin/clawtilla-desktop-run firefox https://example.org
#+end_src

It becomes the session's own account (root cannot use its Wayland
socket), and starts the application with ~systemd-run --user~ -- under
the user's service manager, which gnome-session has already told about
the session.  That is the same route a desktop launcher takes.

It returns as soon as the application has started rather than when it
exits, so an agent that waits on a browser does not wait for ever, and
refuses with a sentence of its own when there is no session yet:

#+begin_example
clawtilla: clawt has no graphical session yet.
clawtilla: the desktop may still be starting; there is nothing to open
a window in until it has.
#+end_example

A guest still booting otherwise produces an error from the *application*
about a display, which points at the application.

The agent is told all of this in its own description of the desktop, for
the same reason the ~/dev/console~ case is: it is not derivable from the
tools, and an agent that works it out by trial and error arrives
somewhere plausible and wrong.

**** Looking at the screen, and finding somewhere to click

Two separate problems, and an agent solves neither by itself.

*Looking* is now a matter of reading a file: screenshots land in the
workspace share, so the agent's own ~read~ opens them.  The tool returns
the path *inside* the guest, though, and an agent that takes the return
value at face value still cannot open it -- so the description says
which of the two names to use.

*Clicking* needs a coordinate, and an image is not one.  An agent given a
screen and a pointer estimates from an assumed layout, misses controls by
a few dozen pixels, and reasonably concludes the pointer tools are
unreliable.  The route that works is OCR:

#+begin_src bash
clawtilla computer exec <agent> -- \
    tesseract /mnt/clawtilla/workspace/screenshots/x.png - tsv
#+end_src

That prints a bounding box per word; the centre of the box for the text
you want is where to click.  clawtilla installs ~tesseract~ and its
English data into every guest that can have them, and the agent is told
the technique in its own description -- an agent worked it out by trial
and error over a session and reported it as a discovery, which is the
signal that it belonged here.

Enterprise Linux is the exception: tesseract is in EPEL there, which a
cloud image does not have enabled, and a package cloud-init cannot find
fails the *whole* install.  An EL guest can drive a desktop; it cannot
read one until somebody adds EPEL.

**** ~focused: true~ is not where the keystrokes go

~list_windows~ reports ~focused~ from the window manager's idea of focus.
GNOME's Activities overview takes the *keyboard* without changing it, so
a window reads ~focused: true~ while every keystroke goes to the
overview's search entry.  The overview is open at login, before anything
has a window.

An agent hit this for a good part of a session: it typed a URL into the
overview's search box, and the one field that would have told it said the
opposite.  There is no tool that reports the shell's grab, so the
description tells the agent to send Escape before typing into a window it
has just focused, and to check a screenshot when text is not appearing
where it expects.

**** The guest needs a GPU, and gets one

A VM with no video device has no ~/dev/dri~, and GDM refuses to start a
session on a machine with no display -- while reporting nothing that
looks like the cause:

#+begin_example
Gdm: It appears that your system does not have a primary GPU!
#+end_example

Everything above that looks healthy.  cloud-init finishes, ~gdm.service~
is active, ~systemctl get-default~ says ~graphical.target~, and the
console sits on the boot log because with no video device the serial
console is the only console there is.

So every VM gets two devices, desktop or not:

- ~<video><model type='virtio'/></video>~ -- virtio because that is what
  a current GNOME on Wayland wants, and every cloud image has the driver.
- ~<graphics type='vnc' listen='127.0.0.1'/>~ -- so a person can look.
  The agent does not need it; it screenshots through the extension inside
  the guest. It is bound to loopback because a VM's screen is a live view
  of what the agent is doing, and that does not belong on the network
  because a default was convenient.

Given to headless VMs as well, deliberately.  A guest with no display
device offers only the serial console, which is the boot log for ever --
so somebody looking at it cannot tell a broken guest from a working
headless one, and on a guest that *does* have a desktop it looks exactly
like GNOME failing to start.  A framebuffer nobody reads costs a few
megabytes.

~virt-manager~ picks the graphical console when a domain has one.  A
domain first defined *without* one keeps the serial console it chose
then, per-VM -- so an older agent needs *View -> Consoles -> Graphical
Console* once, or its window closed and reopened.

**** How the tools reach the agent

The agent's ~.mcp.json~ gains a ~clawtilla-desktop~ server naming the
clawtilla CLI:

#+begin_src sh
clawtilla --socket <daemon.sock> computer desktop-mcp <agent-id>
#+end_src

It asks the daemon for the SSH command that reaches the guest, and relays
stdin and stdout to it.  SSH already carries stdio, so there is no
protocol translation -- but the relay is not a bare ~ssh~ entry, for two
reasons.

The first is the port.  It is chosen when the VM is provisioned, which is
*after* the workspace files are written, so a command line captured at
render time would name a port nothing is listening on.  The relay asks
each time it starts.

The second is the grant.  ~gnome-desktop-mcp~ offers every tool it has to
whoever connects; it has never heard of ~allow_input~.  A bare ssh entry
would hand an observe-only agent the ability to type and click.  So the
relay reads the JSON-RPC going past: it removes tools the agent may not
use from ~tools/list~, and answers a call to one of them with an error
rather than forwarding it.  A tool that is advertised and then refused is
worse than one that is absent -- the agent plans around it, calls it, and
has to work out from an error that it never had it.

~clawtilla-desktop~ is one of the keys clawtilla owns in that file.  The
~clawtilla-~ prefix is reserved wholesale -- every connector and every
MCP integration gets a ~clawtilla-<name>~ entry -- and the whole set is
rewritten on each start, alongside the plain ~clawtilla~ key.  Everything
*without* that prefix is the person's and is read back and written out
untouched.

Reserving the prefix rather than a fixed list of names is what lets an
entry *disappear*: ~clawtilla-desktop~ is removed when the agent no
longer has a guest desktop, because one left behind would start an ssh to
a VM that is not there, and a revoked connector's entry goes the same
way.

*** Acting is a separate grant from seeing

*Launching a process is separate again.*  ~allow_spawn~ is off by default
and is not covered by ~allow_input~.  The compositor's ~spawn~ tool starts
a process through the compositor's own socket, so none of clawtilla's
confinement applies to it -- not the path checks, not the sudo block, and
not bwrap.  An operator who chose bwrap would not expect enabling desktop
input to hand back unrestricted process launching.

~allow_input: false~ is a genuinely useful middle ground: the agent can
see the screen and query the compositor but cannot click or type.  Seeing
and acting are separate capabilities and clawtilla does not conflate
them.

For the host backends, gowl needs to be built with ~MCP=1~ and have
~modules.mcp.enabled: true~, and the GNOME fallback needs
~gnome-desktop-mcp~ on ~PATH~.

** Adding a backend

~ClawtComputerProvider~ is the interface a plugin would implement:
~get_type_name~ returns the ~computer.type~ value you answer to, ~create~
builds the computer.  See [[file:plugins.org][plugins.org]].

*It is not wired in yet.*  The interface exists and
~clawt_plugin_manager_find_computer_provider()~ exists, and nothing calls
the second: ~clawt_computer_factory_create()~ has no provider path, and
its ~default:~ case errors with "unknown computer type".  So a plugin can
declare a backend and no agent can use it.

What *is* true, and is the part that matters operationally, is what an
unknown ~computer.type~ does: that one agent becomes a shadow explaining
itself, and the rest of the fleet starts.  A backend a plugin has not
managed to register is indistinguishable from a typo, which is the safe
way round.
