* Computers

A computer is what an agent can run commands on.  Four types, and an
optional desktop add-on that works alongside any of them.

| Type | What the agent gets | Isolation |
|------+---------------------+-----------|
| ~none~ | nothing; chat only | total |
| ~host~ | the machine clawtilla runs on | confinement, not isolation |
| ~container~ | a podman container | namespaces |
| ~vm~ | a libvirt or QEMU virtual machine | a kernel of its own |

** none

The default, and the right starting point.  An agent that answers
questions does not need a container, and a computer it never uses is a
surface that can go wrong.

#+begin_src yaml
computer:
  type: none
#+end_src

** host

The agent runs commands on the machine clawtilla itself is on: real
filesystem, real processes, real network.  The most useful option and the
most dangerous, so it is explicit and layered.

#+begin_src yaml
computer:
  type: host
  host:
    confirm_host_control: true      # required; the daemon refuses without it
    confine: workspace              # none | workspace | allowlist | bwrap
    root: "~/agents/researcher"
    allow_paths: ["~/src", "~/Documents/notes"]
    deny_paths:  ["~/.ssh", "~/.gnupg", "~/.clawtilla/secrets"]
    allow_network: true
    allow_sudo: false
    shell: "/bin/bash"
    nice: 5
#+end_src

*** What each confinement mode actually prevents

This section is deliberately blunt, because the difference between
"confined" and "isolated" is where people get hurt.

**** ~confine: none~

Nothing.  A bare ~GSubprocess~.  The agent can do anything you can.

Requires both ~confirm_host_control: true~ *and*
~daemon.allow_unconfined_host: true~, so it cannot happen by accident or
by a single config typo.

**** ~confine: workspace~ (default)

The working directory is pinned to ~root~, and every argument that looks
like a path is canonicalised with ~realpath()~ and rejected if it escapes.
Canonicalising first is what closes the ~..~ case and the symlink case
together, rather than with two tests that can disagree.

*What it does not stop:* a program that constructs a path clawtilla
cannot see in the argument list.  ~python3 -c "open(chr(47)+'etc/passwd')"~
reads a file the check never had a chance to notice.  Argument inspection
is a guard rail, not a wall.

**** ~confine: allowlist~

~root~ plus ~allow_paths~, minus ~deny_paths~, with the same
canonicalisation.  Denials are checked first and win outright, so
~~/.ssh~ stays out even when all of ~~~ has been allowed -- the other
order would let a broad allow silently defeat every specific deny.

Same limitation as ~workspace~: it inspects arguments.

**** ~confine: bwrap~

A real kernel sandbox, via ~bubblewrap~ (already present on Silverblue --
flatpak depends on it).  Each allowed path becomes a ~--ro-bind~ or
~--bind~; ~allow_network: false~ becomes ~--unshare-net~; ~/tmp~ is
private; ~--die-with-parent~ means the sandbox goes when the agent does.

This is the only host mode where a program cannot reach outside by
constructing a path at runtime, because the paths are genuinely not in
its namespace.

*If ~bwrap~ is missing the agent starts in ~SHADOW~ and says so.*  It
does not silently downgrade to unconfined -- a confinement that quietly
becomes no confinement is worse than none, because you stop checking.

*** sudo

~allow_sudo: false~ blocks ~sudo~, ~pkexec~, ~doas~, ~run0~ and
~machinectl shell~ at the exec layer, and says so in the agent's
~describe~ text so it does not spend turns trying.

*** The audit trail

Every host exec is written to the event log: agent, command, exit status.
Commands run by a *person* through the client are logged too -- an audit
trail that only covered agents would miss exactly the case somebody would
want to look up.

*** In the interface

The GTK sidebar shows a red ~HOST~ badge on any agent with host control,
and the inspector states the confinement mode in words.  This is not
decoration: an agent that can run commands on the real machine should be
visibly different from one that cannot, at a glance, in the list.

** container

#+begin_src yaml
computer:
  type: container
  container:
    image: "fedora:latest"
    name: "clawt-researcher"      # optional; generated if absent
    connection: "unix"            # unix | ssh://… | tcp://… | a named connection
    network: "bridge"
    keep: false                   # keep the container after the agent stops
#+end_src

Implemented through podomation's ~container~ module, which speaks the
Podman REST API directly over a socket -- no libcurl, no libpod, no
shelling out to the CLI.

*** Your agent does not run inside its computer

This is the part that surprises people, so it is worth stating plainly.

An agent runs as a libreclaw process on the *host*.  Its own ~bash~,
~read~ and ~write~ tools therefore operate on the host filesystem.  Its
container or VM is a thing it *operates*, reachable only through
~clawtilla_computer_exec~ -- not a thing it lives in.

Nothing said so, and the result was an agent with a perfectly good
container sitting in its workspace running commands on the host and
reporting, correctly, that it did not appear to be in a container.

Three things now say it:

- the scaffolded ~TOOLS.org~ names the container -- ~clawt-<agent>~ --
  and says to run every shell command in it
- ~SOUL.org~ carries it as an operating parameter
- and clawtilla injects it into *every turn* as
  ~agent.prompt_suffix~ in the rendered libreclaw config

The last one matters most.  A resumed session never re-receives the
system prompt, and a long conversation drifts away from anything said
only once at the start; the suffix is appended to every turn, so it
holds on turn 200 as much as turn 1.

Set ~prompt_suffix~ on an agent to add a standing rule of your own.  It
is appended to clawtilla's, not instead of it.

Host agents get a different line -- there is nothing to redirect, so
what they are told instead is that this is somebody's real machine.

*** Which image

Defaults to ~registry.fedoraproject.org/fedora:44~ -- change it once for
the fleet with ~defaults.container_image~, or per agent with
~image~.

Any reference podman can pull works.  clawtilla suggests a list, which
is a starting point and never a restriction:

#+begin_src bash
clawtilla image
#+end_src

Add your own so they show up alongside -- and above -- the built-in
suggestions:

#+begin_src yaml
defaults:
  container_images:
    - "registry.example.com/team/devbox:latest -- ours, has the toolchain"
    - "docker.io/library/haskell:9.10"
#+end_src

The text after ~ -- ~ is a note, shown next to the entry.  Nothing here
is validated: a reference podman cannot pull fails at start with
podman's own error.

The GTK client shows this list as a dropdown with the full reference
underneath, and an /Other.../ entry that reveals a free-text field for
anything not on it.

*Name the registry.*  Every suggestion does.  A bare ~fedora:44~ is
resolved through podman's unqualified-search list, which is per-machine
configuration, so the same clawtilla.yaml can pull different images on
two hosts -- and the difference shows up much later as a missing
package.

*** Pulling

~create~ does not pull, so a typo fails in a second rather than after a
download.  When the image is genuinely absent clawtilla pulls it once and
retries, so picking something from the list works without fetching it by
hand first.  The first start on a new image is therefore slow, and
~clawtilla agent logs~ shows nothing while it happens -- the pull is the
daemon's, not the agent's.

*** Which podman

Rootless, by default: the socket under =XDG_RUNTIME_DIR= when there is
one, the system socket otherwise.  podomation's own default is the *root*
socket, which on a desktop means "Could not connect: Permission denied"
for a daemon the user was never going to be allowed to reach.

Set ~connection~ to point somewhere else -- a URI, a bare socket path, or
a podman named connection.  ="unix"= is the shorthand for "the local
one" and keeps the default.

Rootless needs the socket running:

#+begin_src bash
systemctl --user enable --now podman.socket
#+end_src

*** What the container runs

~command~, defaulting to something long-lived.  A container computer
exists to be exec'd into, and a plain base image's entrypoint exits the
moment it starts -- podman then reports the container as Exited while the
agent still believes it has one, and the first sign is an exec failing
for a reason that makes no sense.

Set it when the image has an entrypoint worth running.  A JSON array is
used as written; anything else is split on spaces.

*** A container left behind

The container name is derived from the agent id -- =clawt-<agent>= --
so it can be found again after a daemon restart.  If one is still there
when the agent next starts, it is removed and recreated rather than
failing: the name is ours, and a daemon killed at the wrong moment used
to leave an agent that could never start again without running podman by
hand.

*** Where the modules are found

The ~container~ and ~vm_virtmanager~ modules are built by libreclaw as
loadable ~.so~ files, and looked for in this order:

1. every directory in the ~CLAWT_POD_MODULE_DIR~ environment variable,
   colon-separated
2. ~pod-modules/~ beside the running binary -- ~make~ links this to
   libreclaw's module output, so a build works uninstalled
3. ~modules/~ beside the running binary, where libreclaw itself puts them
4. the install location, ~$(libdir)/clawtilla/pod-modules~

Setting ~daemon.pod_module_dir~ overrides the whole list with that one
directory: a path you named is used literally, so a wrong one fails
loudly rather than being papered over by a stale set found elsewhere.

When no module is found, the error names *every* directory tried.  It
used to name one, which read as an instruction to create that directory
when the real answer was almost always that the modules were sitting in
the build tree.

** vm

#+begin_src yaml
computer:
  type: vm
  vm:
    backend: libvirt              # libvirt (default) | qemu
    domain: "clawt-researcher"
    uri: "qemu:///session"
    image: "~/vms/fedora.qcow2"
    cpus: 2
    memory_mb: 4096
    ssh_user: "agent"
    ssh_key: "~/.ssh/clawt_vm"
    snapshot_on_start: true
#+end_src

*** libvirt (default)

podomation's ~vm_virtmanager~ module: the full 22-action surface,
including snapshots.  ~snapshot_on_start: true~ is worth having -- an
agent that breaks its VM can be put back rather than rebuilt.

*** qemu (fallback)

Spawns ~qemu-system-*~ directly and drives QMP over a unix socket.  A
base image plus a qcow2 overlay; guest commands over SSH.  No libvirtd
required, which matters on a machine where you do not want one.

** Mount paths

Mounts are how files get in and out.

#+begin_src yaml
computer:
  type: container
  mounts:
    - source: "~/src/projects"
      target: "/work/projects"
      mode: rw
      relabel: shared
    - source: "~/Documents/notes"
      target: "/work/notes"
      mode: ro
    - type: tmpfs
      target: "/scratch"
      size: "512M"
#+end_src

| Field | Meaning |
|-------+---------|
| ~source~ | the host path |
| ~target~ | where it appears inside the computer; must be absolute |
| ~mode~ | ~ro~ or ~rw~ |
| ~type~ | ~bind~ (default), ~volume~, ~virtiofs~, ~9p~ or ~tmpfs~ |
| ~create~ | create the source directory if it is missing |
| ~relabel~ | ~none~, ~shared~ (~:z~) or ~private~ (~:Z~) |
| ~required~ | fail rather than warn when the source is missing |
| ~size~ | for ~tmpfs~ |

*** SELinux relabelling

On Fedora Silverblue and friends, an unlabelled bind mount is *visible*
in the container and every access is denied -- a failure that reads like
a permissions bug rather than a labelling one.  Hence ~relabel~.

~shared~ (~:z~) is almost always what you want.  ~private~ (~:Z~)
rewrites the host directory's labels exclusively for one container, so
pointing it at a directory something else also uses will break that other
user.

*** How each backend applies them

| Backend | What a mount becomes |
|---------+----------------------|
| container | mount arguments on the podman ~create~ call |
| libvirt VM | a virtiofs ~<filesystem>~ device, hot-plugged with ~attach_device~ |
| QEMU VM | ~-device vhost-user-fs-pci~ plus a ~virtiofsd~ per mount |
| host | *no kernel mount* -- see below |

*** Mounts on a host computer

A host computer has no mount namespace, so a mount is not a mount: it is
a promise that a path inside the agent's world means a directory outside
it.  Nothing enforces that promise for us, so clawtilla does two things:

1. *Translates paths.*  An argument naming a mount target is rewritten to
   the source before the command runs.  Otherwise an agent told its
   exchange is at ~/mnt/clawtilla/exchange~ would be refused for using
   the path it was given, which is a maddening thing to debug.
2. *Treats the mount as a grant.*  A declared mount is reachable in every
   confinement mode, including ~workspace~.  On a container the kernel
   would make it reachable; the same config behaving differently
   depending on the backend is the kind of inconsistency that costs an
   afternoon.

Translation matches whole path components, so ~/mnt/sharedx~ is not
rewritten by a mount at ~/mnt/shared~.

*** What validation catches

- a relative or non-absolute ~target~
- two mounts whose targets overlap
- ~target: /~
- a missing source, with and without ~create:~
- ~..~ or a symlink escaping in either path
- a refusal to mount ~daemon.state_dir~ or the secrets directory into any
  computer -- an agent that could read the state directory could read
  every other agent's mailbox and token

** The exchange directory

A shared drop-box so agents hand files around without hand-wired mounts.

#+begin_src yaml
defaults:
  exchange_dir: "$XDG_DATA_HOME/clawtilla/exchange"
  exchange_max_bytes: 1073741824
#+end_src

It is mounted into every computer at ~/mnt/clawtilla/exchange~ unless the
agent sets ~computer.exchange: false~ -- as three mounts, not one: the
whole exchange read-only, then ~shared/~ and the agent's own directory
read-write on top.  A single read-write mount of the root would make the
write rule below unenforceable, since anything inside the computer could
simply write into another agent's directory.

#+begin_example
exchange/
  shared/          rw for every agent
  <agent-id>/      rw for that agent, ro for the others
#+end_example

Reading is open across the exchange; writing is not.  An agent that could
overwrite another's drop-box could quietly replace the file that agent
was about to act on.

Reachable three ways:

#+begin_src bash
clawtilla cp ~/notes.org researcher:/mnt/clawtilla/exchange/researcher/
#+end_src

- the ~clawtilla_computer_put_file~ / ~get_file~ / ~exchange_list~ tools
- drag-and-drop into the GTK computer panel

~exchange_max_bytes~ plus a retention sweep keep it bounded; the sweep
removes oldest-first and never follows a symlink out of the directory.

** Desktop control

An add-on rather than a separate type:

#+begin_src yaml
computer:
  type: host
  desktop:
    enabled: true
    backend: gowl          # gowl | gnome; auto-detected by default
    socket: "$XDG_RUNTIME_DIR/gowl-mcp.sock"
    allow_input: true      # false = observe only
#+end_src

~ClawtGowlDesktop~ connects straight to gowl's MCP socket with mcp-glib.
~ClawtGnomeDesktop~ spawns ~gnome-desktop-mcp~ over stdio.  Either way the
endpoint is handed to the agent through its link, so ~describe_desktop~,
~screenshot_monitor~ and ~send_key~ arrive as ordinary MCP tools.

*Launching a process is separate.*  ~allow_spawn~ is off by default and
is not covered by ~allow_input~.  The compositor's ~spawn~ tool starts a
process through the compositor's own socket, so none of clawtilla's
confinement applies to it -- not the path checks, not the sudo block, and
not bwrap.  An operator who chose bwrap would not expect enabling desktop
input to hand back unrestricted process launching.

~allow_input: false~ is a genuinely useful middle ground: the agent can
see the screen and query the compositor but cannot click or type.  Seeing
and acting are separate capabilities and clawtilla does not conflate
them.

gowl needs to be built with ~MCP=1~ and have ~modules.mcp.enabled: true~.

** Adding a backend

Implement ~ClawtComputerProvider~ in a plugin: ~get_type_name~ returns the
~computer.type~ value you answer to, ~create~ builds the computer.  See
[[file:plugins.org][plugins.org]].  An unknown ~computer.type~ with no
provider makes that one agent a shadow rather than failing the daemon.
