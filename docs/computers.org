* Computers

A computer is what an agent can run commands on.  Four types, and an
optional desktop add-on that works alongside any of them.

| Type | What the agent gets | Isolation |
|------+---------------------+-----------|
| ~none~ | nothing; chat only | total |
| ~host~ | the machine clawtilla runs on | confinement, not isolation |
| ~container~ | a podman container | namespaces |
| ~vm~ | a libvirt or QEMU virtual machine | a kernel of its own |

** none

The default, and the right starting point.  An agent that answers
questions does not need a container, and a computer it never uses is a
surface that can go wrong.

#+begin_src yaml
computer:
  type: none
#+end_src

** host

The agent runs commands on the machine clawtilla itself is on: real
filesystem, real processes, real network.  The most useful option and the
most dangerous, so it is explicit and layered.

#+begin_src yaml
computer:
  type: host
  host:
    confirm_host_control: true      # required; the daemon refuses without it
    confine: workspace              # none | workspace | allowlist | bwrap
    root: "~/agents/researcher"
    allow_paths: ["~/src", "~/Documents/notes"]
    deny_paths:  ["~/.ssh", "~/.gnupg", "~/.clawtilla/secrets"]
    allow_network: true
    allow_sudo: false
    shell: "/bin/bash"
    nice: 5
#+end_src

*** What each confinement mode actually prevents

This section is deliberately blunt, because the difference between
"confined" and "isolated" is where people get hurt.

**** ~confine: none~

Nothing.  A bare ~GSubprocess~.  The agent can do anything you can.

Requires both ~confirm_host_control: true~ *and*
~daemon.allow_unconfined_host: true~, so it cannot happen by accident or
by a single config typo.

**** ~confine: workspace~ (default)

The working directory is pinned to ~root~, and every argument that looks
like a path is canonicalised with ~realpath()~ and rejected if it escapes.
Canonicalising first is what closes the ~..~ case and the symlink case
together, rather than with two tests that can disagree.

*What it does not stop:* a program that constructs a path clawtilla
cannot see in the argument list.  ~python3 -c "open(chr(47)+'etc/passwd')"~
reads a file the check never had a chance to notice.  Argument inspection
is a guard rail, not a wall.

**** ~confine: allowlist~

~root~ plus ~allow_paths~, minus ~deny_paths~, with the same
canonicalisation.  Denials are checked first and win outright, so
~~/.ssh~ stays out even when all of ~~~ has been allowed -- the other
order would let a broad allow silently defeat every specific deny.

Same limitation as ~workspace~: it inspects arguments.

**** ~confine: bwrap~

A real kernel sandbox, via ~bubblewrap~ (already present on Silverblue --
flatpak depends on it).  Each allowed path becomes a ~--ro-bind~ or
~--bind~; ~allow_network: false~ becomes ~--unshare-net~; ~/tmp~ is
private; ~--die-with-parent~ means the sandbox goes when the agent does.

This is the only host mode where a program cannot reach outside by
constructing a path at runtime, because the paths are genuinely not in
its namespace.

*If ~bwrap~ is missing the agent starts in ~SHADOW~ and says so.*  It
does not silently downgrade to unconfined -- a confinement that quietly
becomes no confinement is worse than none, because you stop checking.

*** sudo

~allow_sudo: false~ blocks ~sudo~, ~pkexec~, ~doas~, ~run0~ and
~machinectl shell~ at the exec layer, and says so in the agent's
~describe~ text so it does not spend turns trying.

*** The audit trail

Every host exec is written to the event log: agent, command, exit status.
Commands run by a *person* through the client are logged too -- an audit
trail that only covered agents would miss exactly the case somebody would
want to look up.

*** In the interface

The GTK sidebar shows a red ~HOST~ badge on any agent with host control,
and the inspector states the confinement mode in words.  This is not
decoration: an agent that can run commands on the real machine should be
visibly different from one that cannot, at a glance, in the list.

** container

#+begin_src yaml
computer:
  type: container
  container:
    image: "fedora:latest"
    name: "clawt-researcher"      # optional; generated if absent
    connection: "unix"            # unix | ssh://… | tcp://… | a named connection
    network: "bridge"
    keep: false                   # keep the container after the agent stops
#+end_src

Implemented through podomation's ~container~ module, which speaks the
Podman REST API directly over a socket -- no libcurl, no libpod, no
shelling out to the CLI.

*** Your agent does not run inside its computer

This is the part that surprises people, so it is worth stating plainly.

An agent runs as a libreclaw process on the *host*.  Its own ~bash~,
~read~ and ~write~ tools therefore operate on the host filesystem.  Its
container or VM is a thing it *operates*, reachable only through
~clawtilla_computer_exec~ -- not a thing it lives in.

Nothing said so, and the result was an agent with a perfectly good
container sitting in its workspace running commands on the host and
reporting, correctly, that it did not appear to be in a container.

Three things now say it:

- the scaffolded ~TOOLS.org~ names the container -- ~clawt-<agent>~ --
  and says to run every shell command in it
- ~SOUL.org~ carries it as an operating parameter
- and clawtilla injects it into *every turn* as
  ~agent.prompt_suffix~ in the rendered libreclaw config

The last one matters most.  A resumed session never re-receives the
system prompt, and a long conversation drifts away from anything said
only once at the start; the suffix is appended to every turn, so it
holds on turn 200 as much as turn 1.

Set ~prompt_suffix~ on an agent to add a standing rule of your own.  It
is appended to clawtilla's, not instead of it.

Host agents get a different line -- there is nothing to redirect, so
what they are told instead is that this is somebody's real machine.

*** Which image

Defaults to ~registry.fedoraproject.org/fedora:44~ -- change it once for
the fleet with ~defaults.container_image~, or per agent with
~image~.

Any reference podman can pull works.  clawtilla suggests a list, which
is a starting point and never a restriction:

#+begin_src bash
clawtilla image
#+end_src

Add your own so they show up alongside -- and above -- the built-in
suggestions:

#+begin_src yaml
defaults:
  container_images:
    - "registry.example.com/team/devbox:latest -- ours, has the toolchain"
    - "docker.io/library/haskell:9.10"
#+end_src

The text after ~ -- ~ is a note, shown next to the entry.  Nothing here
is validated: a reference podman cannot pull fails at start with
podman's own error.

The GTK client shows this list as a dropdown with the full reference
underneath, and an /Other.../ entry that reveals a free-text field for
anything not on it.

*Name the registry.*  Every suggestion does.  A bare ~fedora:44~ is
resolved through podman's unqualified-search list, which is per-machine
configuration, so the same clawtilla.yaml can pull different images on
two hosts -- and the difference shows up much later as a missing
package.

*** Pulling

~create~ does not pull, so a typo fails in a second rather than after a
download.  When the image is genuinely absent clawtilla pulls it once and
retries, so picking something from the list works without fetching it by
hand first.  The first start on a new image is therefore slow, and
~clawtilla agent logs~ shows nothing while it happens -- the pull is the
daemon's, not the agent's.

*** How big the VM is

#+begin_src yaml
computer:
  type: vm
  vm:
    cpus: 4
    memory_mb: 8192
#+end_src

#+begin_src bash
clawtilla agent set builder computer.vm.cpus 4
clawtilla agent set builder computer.vm.memory_mb 8192
#+end_src

The Agent tab shows /Disk image/, /Cores/, /Memory (MB)/ and /SSH
address/ for a VM agent, and only for one -- no other backend reads them,
and a row that quietly does nothing is worse than no row.

Applied when the domain is defined, so a change takes effect on the next
start.

*** Which podman

Rootless, by default: the socket under =XDG_RUNTIME_DIR= when there is
one, the system socket otherwise.  podomation's own default is the *root*
socket, which on a desktop means "Could not connect: Permission denied"
for a daemon the user was never going to be allowed to reach.

Set ~connection~ to point somewhere else -- a URI, a bare socket path, or
a podman named connection.  ="unix"= is the shorthand for "the local
one" and keeps the default.

Rootless needs the socket running:

#+begin_src bash
systemctl --user enable --now podman.socket
#+end_src

*** What the container runs

~command~, defaulting to something long-lived.  A container computer
exists to be exec'd into, and a plain base image's entrypoint exits the
moment it starts -- podman then reports the container as Exited while the
agent still believes it has one, and the first sign is an exec failing
for a reason that makes no sense.

Set it when the image has an entrypoint worth running.  A JSON array is
used as written; anything else is split on spaces.

*** Sharing folders

#+begin_src bash
clawtilla agent mount list researcher
#+end_src

#+begin_src bash
clawtilla agent mount add researcher ~/src/projects /work rw
#+end_src

#+begin_src bash
clawtilla agent mount rm researcher /work
#+end_src

The Agent tab has the same under /Shared folders/, listing what is
shared with a button to stop sharing it.

Changes apply when the computer next starts: a bind mount is part of a
container's creation, not something added to a running one.

*Relabelling defaults to shared* (~:z~).  On Fedora and friends an
unlabelled bind mount is visible inside the container with every access
denied -- which reads like a permissions bug rather than a labelling
one.  It used to default to ~none~, so every shared folder anyone
declared failed with permission denied while the documentation said
shared was usually what you wanted.  ~private~ (~:Z~) relabels the host
directory exclusively for this container and will break anything else
using it; ~none~ is right when the source is already labelled for
container access.

The mount list is the same for a VM, where the entries become virtiofs
devices rather than bind mounts.  You write source, target and mode; the
right kind is filled in from the backend.

*** A container left behind

The container name is derived from the agent id -- =clawt-<agent>= --
so it can be found again after a daemon restart.  If one is still there
when the agent next starts, it is removed and recreated rather than
failing: the name is ours, and a daemon killed at the wrong moment used
to leave an agent that could never start again without running podman by
hand.

*** Where the modules are found

The ~container~ and ~vm_virtmanager~ modules are built by libreclaw as
loadable ~.so~ files, and looked for in this order:

1. every directory in the ~CLAWT_POD_MODULE_DIR~ environment variable,
   colon-separated
2. ~pod-modules/~ beside the running binary -- ~make~ links this to
   libreclaw's module output, so a build works uninstalled
3. ~modules/~ beside the running binary, where libreclaw itself puts them
4. the install location, ~$(libdir)/clawtilla/pod-modules~

Setting ~daemon.pod_module_dir~ overrides the whole list with that one
directory: a path you named is used literally, so a wrong one fails
loudly rather than being papered over by a stale set found elsewhere.

When no module is found, the error names *every* directory tried.  It
used to name one, which read as an instruction to create that directory
when the real answer was almost always that the modules were sitting in
the build tree.

** vm

#+begin_src yaml
computer:
  type: vm
  vm:
    backend: libvirt              # libvirt (default) | qemu
    domain: "clawt-researcher"
    uri: "qemu:///session"
    image: "~/vms/Fedora-Cloud-Base-44.qcow2"
    cpus: 2
    memory_mb: 4096
    ssh_user: "agent"
    cloud_init: true
    snapshot_on_start: true
#+end_src

That is the whole configuration for a working VM.  ~ssh_key~,
~ssh_host~ and ~ssh_port~ are all optional: clawtilla generates the key,
forwards the port and fills the address in itself.

*** Which image

*clawtilla ships no disk image.*  ~image~ is a path to a qcow2 on this
machine, and a VM agent without one is *refused at provision*, naming
this setting.

It used to be allowed, and the result was three symptoms with nothing
connecting them: the domain defined and started with no disk, so its
console was black; SSH answered ~kex_exchange_identification: Connection
reset by peer~, because the forwarded port reached a guest with no sshd;
and virt-manager showed a running VM that had booted nothing.

It will fetch one for you, though.  Images live in
~defaults.image_dir~ (~$XDG_DATA_HOME/clawtilla/images~ by default), one
copy serving the whole fleet:

#+begin_src bash
clawtilla image vm catalog          # what is suggested
clawtilla image vm get fedora-44    # fetch it, with a progress bar
clawtilla image vm list
#+end_src

What is suggested, and which family each belongs to for the purpose of
installing a desktop into it:

| id | family | note |
|---+---+---|
| ~fedora-44~ | fedora | the default, and the only one booted end to end |
| ~fedora-43~ | fedora | the previous release |
| ~centos-stream-10~ | enterprise | closest to RHEL |
| ~debian-13~ | debian | trixie |
| ~debian-12~ | debian | bookworm |
| ~ubuntu-24.04~ | ubuntu | noble |
| ~arch~ | arch | rolling; rebuilt monthly |

~clawtilla image vm catalog~ is the authoritative version of that table
-- this one is here so you can choose before running anything.

In the GTK client the same thing is under the hamburger menu beside the
*+* button: /Settings/ → /Cloud images/, which lists what is here, offers
the suggestions, takes a URL of your own, and shows a bar per download.
Downloads belong to the daemon, so closing that window does not stop one,
and a download begun from the CLI appears in the window and vice versa.

Then point an agent at it -- or pick it from /Disk image/ in the Agent
tab, which lists what has been fetched:

#+begin_src bash
clawtilla agent set researcher computer.vm.image ~/.local/share/clawtilla/images/fedora-44
#+end_src

*** Rebuilding one

cloud-init acts on its seed at *first boot only*.  So the login, the
desktop, the package list -- everything in that seed -- is fixed for the
life of the machine, and changing it in the config and restarting the
agent looks like it did nothing at all.

#+begin_src bash
clawtilla agent stop deb-tester
clawtilla computer rebuild deb-tester
#+end_src

In the GTK client the same thing is /Rebuild computer/ in the Agent tab,
which is insensitive while the agent runs.  Destroying the machine
underneath a working agent is not something to do carefully; it is
something not to offer.

It destroys the guest and builds it again from the image: the domain, the
overlay, the seed and the generated SSH key all go, and the contents of
the machine with them.  It is also how to get one back that was deleted
outside clawtilla -- though that particular case now recovers on its own.

*** A guest somebody deleted

Deleting a VM in virt-manager, or a qcow2 with ~rm~, tells clawtilla
nothing.  Starting the agent afterwards builds it again: the state
clawtilla holds is a belief about something another program owns, so it
asks the hypervisor rather than trusting what it remembers.

That was not always true, and the difference was invisible: restarting
the whole *daemon* recovered, because a freshly built computer starts out
knowing nothing and provisions.  Restarting just the *agent* did not.

The contents are gone either way -- what comes back is a fresh guest from
the image, not the machine that was deleted.

*** Where the suggestions come from

The catalog is a starting point, never a restriction: any ~https~ URL to
a qcow2 works, and ~clawtilla image vm get <url>~ takes one directly.

Three of the entries name a *directory* and a pattern rather than a
file, because Fedora and CentOS stamp the compose into the filename.  clawtilla
lists the directory and takes the newest match, so those entries stay
right until the release itself is retired -- and say so plainly when it
is, rather than failing as a 404.

A download is verified only in the sense that a short one is refused: if
the server promised more bytes than it sent, the partial file is deleted
rather than left looking like an image.  Nothing checks a signature, so
an https URL from a distribution you trust is the safe habit.

The base is never written to.  A qcow2 overlay is created per agent
under ~$XDG_DATA_HOME/clawtilla/vms/<agent>/overlay.qcow2~, so several
agents share one base and a wrecked guest is thrown away by deleting one
file.  Deleting the overlay also forgets the guest's host key, because a
rebuilt VM is a different machine answering at the same address.

*Changing ~image~ rebuilds the guest.*  The overlay records the base it
was built on, so one left in place would keep booting the old image for
ever while the config said otherwise -- a setting that silently does
nothing.  The old disk is *moved aside* to ~overlay-superseded.qcow2~
rather than deleted, and the log says where: everything installed inside
that VM is in it, and a config line changing is a poor reason for that to
be unrecoverable.  Delete it when you are sure.  An agent's own work is
in its workspace on the host, which this never touches.

Two things it will *not* do:

- *A disk whose base cannot be read is left exactly as it is.*  The
  usual reason is that a guest is running and holding it -- ~qemu-img~
  refuses an image another process has open -- and unknown is not
  different.  Reading that refusal as "the base changed" once deleted
  the disk of a running VM, which carried on against the unlinked inode
  while the file on disk was replaced by an empty one.
- *A running domain is not touched at all.*  Restarting the daemon
  re-provisions every agent, and a libvirt domain outlives the daemon,
  so this runs routinely against a VM that is up.  Its overlay and its
  seed are left alone; only the address is worked out, because that is
  read from a file.

*Deleting an image an agent is using is refused*, because the overlay
names it: without the base, the VM stops booting at all.  Point the agent
somewhere else first, or insist:

#+begin_src bash
clawtilla image vm rm fedora-44 --force
#+end_src

A plain installer ISO or a desktop image will *not* work unattended: it
has no cloud-init, so nothing creates a login and clawtilla cannot get
in.  Use a cloud image, or prepare your own and set ~cloud_init: false~.

The seed is tested against Fedora Cloud Base, and the mainstream cloud
images -- Fedora, Debian, Ubuntu, CentOS Stream -- work the same way.
Very small images can be a different matter: Alpine's ~nocloud~ image
reads the seed, sets the hostname and installs the key in the right
place, and its ~sshd~ then refuses the login anyway.  If you want one of
those, expect to prepare it yourself and set ~cloud_init: false~.

*** Getting in: cloud-init

A cloud image has no account, no password and no authorised key.  Left
alone it boots perfectly and nothing can enter it, which looks exactly
like a VM that failed to boot.

With ~cloud_init: true~ -- the default -- clawtilla builds a small ISO
labelled ~cidata~, attaches it as a CD-ROM, and cloud-init reads it on
first boot:

- creates ~ssh_user~ (default ~root~), and nothing else.  The image's own
  default login -- ~fedora~, ~debian~, ~ubuntu~ -- is never created, so
  the guest has exactly the one account clawtilla holds a key for
- authorises the public key, and disables password authentication
- gives that account passwordless ~sudo~, unless it is already root

The key is yours if you name one in ~ssh_key~; otherwise an ed25519 key
is generated per agent beside the overlay.  A generated key has no
passphrase, because the daemon uses it with nobody present to type one.
It is mode 0600 in a mode 0700 directory and it reaches exactly one VM.
An *encrypted* key in ~ssh_key~ is refused with that reason rather than
hanging.

Building the seed needs an ISO writer: ~xorriso~ on Fedora.  Without one,
provisioning stops and says so.

Set ~cloud_init: false~ for an image that already has a login and an
authorised key, and set ~ssh_user~ and ~ssh_key~ to match it.

*** Getting in: the address

Commands run in a VM over SSH -- there is no ~podman exec~ for a guest,
and a guest agent would be one more thing to install inside every image.

Leave ~ssh_host~ unset and clawtilla arranges the route itself: it picks
a free port on 127.0.0.1, forwards it to the guest's port 22, and
remembers the choice in ~$XDG_DATA_HOME/clawtilla/vms/<agent>/ssh-port~.
It has to be remembered -- a libvirt domain is defined with the port
written into its XML, so choosing a new one on the next start would
leave the daemon dialling a port nothing is listening on.

The two backends forward differently:

| Backend | How |
|---------+-----|
| ~qemu~ | ~-netdev user,hostfwd=tcp:127.0.0.1:<port>-:22~ |
| ~libvirt~ | ~<interface type='user'>~ with a passt backend and a ~<portForward>~ |

*libvirt needs passt* (Fedora: ~passt~).  libvirt has no port forwarding
for the SLIRP backend -- a ~<portForward>~ without passt is a rejected
domain, not an unforwarded one.  Without passt installed the VM still
runs, and starting it warns that nothing reaches it; ~ssh_host~ is then
how you say what does.

Set ~ssh_host~ (and ~ssh_port~, if it is not 22) for a VM that lives
somewhere clawtilla did not put it -- a bridged network, another
machine, or a VM that existed before this agent did.  clawtilla forwards
nothing when you do, on the assumption that you have your own route.

Host keys go in a ~known_hosts~ beside the overlay rather than yours.  A
VM rebuilt from the same base answers on the same address with a
different key, which against your own file reads as an attack and is
refused.

*** Running things in one

~clawtilla_computer_exec~ takes a *command and its arguments*, not a
shell line.  Every argument is quoted and passed through as it stands, so
~>~, ~|~, ~&&~, ~;~, ~*~ and ~$VAR~ arrive at the command as literal text
-- the command runs, reports success, and does nothing you were looking
for.  This is the same for every backend.

Wrap it in a shell when you want shell behaviour:

#+begin_src bash
clawtilla computer exec researcher -- bash -c 'echo hi > /tmp/note'
#+end_src

*Writing to a VM's screen* is the case where this bites hardest, because
the naive form looks like it worked.  ~/dev/console~ is the serial
console, and it is what somebody watching in virt-manager sees:

#+begin_src bash
clawtilla computer exec researcher -- bash -c 'echo ">>> hello <<<" > /dev/console'
#+end_src

An agent's ~TOOLS.org~ says all of this, and a VM agent's own description
says it again with its name in it -- it is the kind of thing an agent
otherwise works out by trial and error, and reports as a discovery.

*** The console is black

A serial console shows what is written *while you are attached*.  The
boot messages have already gone by, and an idle guest writes nothing, so
a VM that booted before you opened virt-manager shows an empty screen.
That is not a fault.

Make it say something:

#+begin_src bash
clawtilla computer exec researcher -- bash -c 'echo hello > /dev/console'
#+end_src

A genuinely black screen *from boot* means the domain has no disk -- see
above.

*** virt-manager can take the session away

virt-manager installed as a flatpak ships its own ~virtqemud~, and
opening it can leave that daemon owning
~$XDG_RUNTIME_DIR/libvirt/virtqemud-sock~.  Its sandbox has no QEMU in
it, so every ~qemu:///session~ connection afterwards -- clawtilla's
included -- is answered by a daemon that cannot find an emulator, and
every VM stops working until it exits.

#+begin_src bash
ss -lxp | grep virtqemud-sock
#+end_src

names the process holding it.

*** When libvirt cannot find an emulator

#+begin_example
unsupported configuration: No emulator found for arch 'x86_64'
#+end_example

Not clawtilla: the session daemon has failed to probe QEMU, and *any*
domain will fail to define, including one written by hand.  Confirm with

#+begin_src bash
virsh -c qemu:///session domcapabilities
#+end_src

which will say the same thing.  Restarting the user daemon makes it
probe again:

#+begin_src bash
systemctl --user restart virtqemud.service
#+end_src

and if it persists, the cached probe is stale:

#+begin_src bash
rm -rf ~/.cache/libvirt/qemu/cache/capabilities
#+end_src

*** Stopping one

~shutdown~ first, so the guest flushes its filesystems -- a VM pulled out
from under a running write is how a disk image becomes unbootable.

Shutdown is a *request*, though, and only a guest that is listening
answers it.  One that has hung, or never booted, ignores it for ever, so
after 30 seconds the plug is pulled and the log says why.  Without that
fallback such a VM could not be stopped through clawtilla at all.

*** libvirt (default)

podomation's ~vm_virtmanager~ module: the full 22-action surface,
including snapshots.

*A VM that has been removed is rebuilt.*  Provisioning asks libvirt what
domains exist before asking about this one, so a domain you undefined --
or one that never existed -- is simply built again from scratch.  Asking
after a missing domain directly is loud: the module tries the name, then
tries the same string as a UUID, and libvirt logs both failures, which
put two alarming lines on the daemon's console for the most ordinary
path there is.

The domain carries a UUID derived from its name, so defining it again is
a *re*define.  One defined by an older build keeps whatever UUID libvirt
invented for it: provisioning reads it back and adopts it, rather than
undefining a domain you might care about.  Without one libvirt invents a fresh UUID each time and
then refuses the name it already holds -- ~domain 'clawt-x' already
exists with uuid ...~ -- which meant an agent could be provisioned once
and never started again.  ~snapshot_on_start: true~ is worth having -- an
agent that breaks its VM can be put back rather than rebuilt.

The domain is *persistent*: it is defined once and survives the agent
stopping, which is what makes snapshots and ~virsh~ useful against it.
It also means removing the agent leaves the domain defined -- there is no
undefine in the module's action set -- so clean up by hand:

#+begin_src bash
virsh -c qemu:///session undefine clawt-<agent>
#+end_src

*** qemu (fallback)

Spawns ~qemu-system-*~ directly and drives QMP over a unix socket.  A
base image plus a qcow2 overlay; guest commands over SSH.  No libvirtd
required, which matters on a machine where you do not want one.

*** What ends up in the VM's state directory

Everything for one guest, under
~$XDG_DATA_HOME/clawtilla/vms/<agent>/~:

| File | What it is |
|------+------------|
| ~overlay.qcow2~ | the writable disk, backed by ~image~ |
| ~seed.iso~ | the cloud-init seed, labelled ~cidata~ |
| ~cloud-init/~ | the ~user-data~ and ~meta-data~ inside it |
| ~id_ed25519~ | the generated key, when ~ssh_key~ is unset |
| ~ssh-port~ | the forwarded port, remembered across restarts |
| ~known_hosts~ | this agent's guests, kept out of yours |

Deleting the directory starts the guest over from the base image.

*** Removing a VM

~clawtilla agent rm <agent> --with-computer~ destroys the guest: it stops
the domain, undefines it, and deletes the overlay, the seed, the key and
the recorded port.  The agent's *workspace* on the host is never touched
-- that is where its work is.

Without ~--with-computer~ the VM is left exactly as it is.  Removing an
agent from the fleet is reversible and deleting its disk is not, so the
destructive half is opt-in.

Two things this used to get wrong, both worth knowing if you are running
an older build:

- ~ClawtVmComputer~ had no teardown at all, and the base class answered
  TRUE for a missing one -- so the removal *reported success* and left
  the libvirt domain defined and the disk on disk. The only way to find
  out was to open virt-manager and see a VM that should not have been
  there. A backend that cannot destroy itself is now refused by name.
- The state directory survived, so a later agent created with the same
  id silently adopted the old guest instead of starting clean.

If you have such a leftover, ~virsh -c qemu:///session undefine
clawt-<agent>~ removes the definition and the directory under
~$XDG_DATA_HOME/clawtilla/vms/<agent>~ holds the disk.

** Mount paths

Mounts are how files get in and out.

#+begin_src yaml
computer:
  type: container
  mounts:
    - source: "~/src/projects"
      target: "/work/projects"
      mode: rw
      relabel: shared
    - source: "~/Documents/notes"
      target: "/work/notes"
      mode: ro
    - type: tmpfs
      target: "/scratch"
      size: "512M"
#+end_src

| Field | Meaning |
|-------+---------|
| ~source~ | the host path |
| ~target~ | where it appears inside the computer; must be absolute |
| ~mode~ | ~ro~ or ~rw~ |
| ~type~ | ~bind~ (default), ~volume~, ~virtiofs~, ~9p~ or ~tmpfs~ |
| ~create~ | create the source directory if it is missing |
| ~relabel~ | ~none~, ~shared~ (~:z~) or ~private~ (~:Z~) |
| ~required~ | fail rather than warn when the source is missing |
| ~size~ | for ~tmpfs~ |

*** SELinux relabelling

On Fedora Silverblue and friends, an unlabelled bind mount is *visible*
in the container and every access is denied -- a failure that reads like
a permissions bug rather than a labelling one.  Hence ~relabel~.

~shared~ (~:z~) is almost always what you want.  ~private~ (~:Z~)
rewrites the host directory's labels exclusively for one container, so
pointing it at a directory something else also uses will break that other
user.

*** How each backend applies them

| Backend | What a mount becomes |
|---------+----------------------|
| container | mount arguments on the podman ~create~ call |
| libvirt VM | a virtiofs ~<filesystem>~ device, hot-plugged with ~attach_device~ |
| QEMU VM | ~-device vhost-user-fs-pci~ plus a ~virtiofsd~ per mount |
| host | *no kernel mount* -- see below |

*** Mounts on a host computer

A host computer has no mount namespace, so a mount is not a mount: it is
a promise that a path inside the agent's world means a directory outside
it.  Nothing enforces that promise for us, so clawtilla does two things:

1. *Translates paths.*  An argument naming a mount target is rewritten to
   the source before the command runs.  Otherwise an agent told its
   exchange is at ~/mnt/clawtilla/exchange~ would be refused for using
   the path it was given, which is a maddening thing to debug.
2. *Treats the mount as a grant.*  A declared mount is reachable in every
   confinement mode, including ~workspace~.  On a container the kernel
   would make it reachable; the same config behaving differently
   depending on the backend is the kind of inconsistency that costs an
   afternoon.

Translation matches whole path components, so ~/mnt/sharedx~ is not
rewritten by a mount at ~/mnt/shared~.

*** What validation catches

- a relative or non-absolute ~target~
- two mounts whose targets overlap
- ~target: /~
- a missing source, with and without ~create:~
- ~..~ or a symlink escaping in either path
- a refusal to mount ~daemon.state_dir~ or the secrets directory into any
  computer -- an agent that could read the state directory could read
  every other agent's mailbox and token

** The exchange directory

A shared drop-box so agents hand files around without hand-wired mounts.

#+begin_src yaml
defaults:
  exchange_dir: "$XDG_DATA_HOME/clawtilla/exchange"
  exchange_max_bytes: 1073741824
#+end_src

It is mounted into every computer at ~/mnt/clawtilla/exchange~ unless the
agent sets ~computer.exchange: false~ -- as three mounts, not one: the
whole exchange read-only, then ~shared/~ and the agent's own directory
read-write on top.  A single read-write mount of the root would make the
write rule below unenforceable, since anything inside the computer could
simply write into another agent's directory.

#+begin_example
exchange/
  shared/          rw for every agent
  <agent-id>/      rw for that agent, ro for the others
#+end_example

Reading is open across the exchange; writing is not.  An agent that could
overwrite another's drop-box could quietly replace the file that agent
was about to act on.

Reachable three ways:

#+begin_src bash
clawtilla cp ~/notes.org researcher:/mnt/clawtilla/exchange/researcher/
#+end_src

- the ~clawtilla_computer_put_file~ / ~get_file~ / ~exchange_list~ tools
- drag-and-drop into the GTK computer panel

~exchange_max_bytes~ plus a retention sweep keep it bounded; the sweep
removes oldest-first and never follows a symlink out of the directory.

** Desktop control

An add-on rather than a separate type, so it works alongside whichever
computer the agent has:

#+begin_src yaml
computer:
  type: host
  desktop:
    enabled: true
    backend: auto          # auto | gowl | gnome | guest
    socket: "$XDG_RUNTIME_DIR/gowl-mcp.sock"
    allow_input: true      # false = observe only
#+end_src

There are four backends and they divide into two quite different things.
~gowl~ and ~gnome~ drive *the screen a person is sitting at*: gowl through
its own MCP socket, GNOME through ~gnome-desktop-mcp~ on the host.
~guest~ drives a desktop inside the agent's own VM, which is the only one
where a misjudged click lands somewhere recoverable.

~auto~ picks ~guest~ whenever the agent has a VM, and otherwise probes
gowl and then GNOME.  An agent with a machine of its own should be
driving that screen rather than yours.

*Tools arrive through the agent's ~.mcp.json~, not through its link.*  An
AI CLI drops a tool list handed to it in-process -- see the note in
=CLAUDE.md= -- so the only route to an agent's session is a command named
in a config file the CLI finds for itself.

*** A desktop inside the agent's VM

A cloud image has no desktop at all: no display manager, no compositor,
no graphical target.  So ~computer.desktop.enabled~ on a VM agent does
not *find* a desktop, it *builds* one, through the cloud-init seed on the
guest's first boot:

#+begin_src yaml
computer:
  type: vm
  vm:
    image: "~/.local/share/clawtilla/images/Fedora-Cloud-Base-44.qcow2"
    cpus: 2
    memory_mb: 8192
    disk_gb: 128
    desktop:
      user: null           # defaults to ssh_user, or clawt when that is root
      autologin: true
      flavour: auto        # fedora | enterprise | debian | ubuntu | arch
      packages: []         # empty means the family's own list
      mcp: true
      mcp_repo: "https://git.podbielniak.com/zachpodbielniak/gnome-desktop-mcp.git"
  desktop:
    enabled: true
    allow_input: true
#+end_src

The defaults for ~cpus~, ~memory_mb~ and ~disk_gb~ are sized for this:
2 cores, 8 GB and a 128 GB disk.  A cloud image's own disk is a few
gigabytes, which a desktop fills immediately; the overlay is created at
~disk_gb~ instead and cloud-init's ~growpart~ extends the guest's
filesystem to match.  qcow2 is sparse, so it costs what is written rather
than what is asked for.  Raising ~disk_gb~ grows the disk on the next
provision.  *Lowering it is refused*, with a warning: shrinking a disk
discards whatever was past the new end, and a number edited downwards in
a config file is not consent to lose it.

**** Which distribution is in the image

cloud-init picks the package *manager* for you and nothing else, so the
seed has to know the names -- and the names are the smaller half of it.

| | Fedora | Enterprise Linux | Debian | Ubuntu | Arch |
|---+---+---+---+---+---|
| display manager | ~gdm~ | ~gdm~ | ~gdm3~ | ~gdm3~ | ~gdm~ |
| unit enabled | ~gdm.service~ | ~gdm.service~ | ~gdm3.service~ | ~gdm3.service~ | ~gdm.service~ |
| PyGObject | ~python3-gobject~ | ~python3-gobject~ | ~python3-gi~ | ~python3-gi~ | ~python-gobject~ |
| venv | in ~python3~ | in ~python3~ | ~python3-venv~ | ~python3-venv~ | in ~python~ |
| ~glib-compile-schemas~ | in ~glib2~ | in ~glib2~ | ~libglib2.0-bin~ | ~libglib2.0-bin~ | ~glib2-devel~ |
| the ~dconf~ binary | ~dconf~ | ~dconf~ | ~dconf-cli~ | ~dconf-cli~ | ~dconf~ |
| terminal | ~gnome-console~ | ~gnome-terminal~ | ~gnome-terminal~ | ~gnome-terminal~ | ~gnome-terminal~ |
| browser | ~firefox~ | ~firefox~ | ~firefox-esr~ | ~firefox~ | ~firefox~ |
| upgraded first | no | no | no | no | *yes* |

Each of those on its own is enough to leave a guest that installed a
desktop and has no session, or a session with no automation.  Enabling
~gdm.service~ on Debian fails and the machine sits at a text console
with a complete desktop on it; the wrong PyGObject leaves an MCP server
that installs cleanly and dies on its first import; and without
~dconf-cli~ every default written into ~/etc/dconf/db~ stays inert, which
reads as an extension that will not enable.

~flavour: auto~ reads the family off ~computer.vm.image~.  A catalog id
says outright, and an image you downloaded keeps the distribution in its
filename -- including Ubuntu's, which never say "ubuntu" and are named
after the release adjective instead.  When neither says, clawtilla warns
naming the key and the image, and installs Fedora names; it does not
guess quietly, because a wrong guess surfaces as a failed package install
inside a guest's log, a long way from the config line that caused it.

Ubuntu is a family of its own for one entry in that table.  Debian stable
has no ~firefox~ package -- only ~firefox-esr~ -- and Ubuntu has no
~firefox-esr~; either name is wrong on the other distribution, and a
package that does not exist fails the whole install rather than merely
missing a browser.  Worth knowing about the Ubuntu one: ~firefox~ there
is a transitional package that installs the snap, so the first boot
spends a while on snapd and the browser is a confined snap rather than a
deb.  That is the only supported way to get Firefox on Ubuntu; there is
no deb to prefer instead.

A browser is in every list because an agent driving a desktop with
nothing on it can look at a wallpaper and little else.

Arch is the one that is fully upgraded before anything is installed.
cloud-init's ~package_update~ runs ~pacman -Sy~, which refreshes the
index without upgrading what is already there -- and installing against
that is exactly the partial upgrade pacman warns about, where a new
package links against libraries the image still has old versions of.  It
breaks inside the guest, after the desktop appears to have installed.
The seed asks for ~package_upgrade~ as well, which cloud-init runs
between the refresh and the install.  That costs a longer first boot, and
is why it is per family rather than always on: a point release does not
need it.

Arch also publishes two qcow2s and only one of them is any use --
~Arch-Linux-x86_64-basic.qcow2~ has no cloud-init, so a VM built from it
boots perfectly and admits nobody.  The catalog entry points at
~Arch-Linux-x86_64-cloudimg.qcow2~.  It is rebuilt monthly and the
~latest/~ URL follows, so a cached copy ages faster than the others do;
~clawtilla image rm arch~ and re-fetch if a first boot starts failing on
package signatures.

~enterprise~ deliberately asks for less: ~gnome-console~,
~gnome-text-editor~ and ~gnome-tweaks~ are not in the EL10 repositories,
and cloud-init treats a package it cannot find as a failure of the whole
install -- so asking for one takes the desktop down with it rather than
merely missing an editor.

Setting ~packages~ replaces the family's list rather than adding to it,
which is also how you take something out.  It does not reach the packages
the MCP server needs: those are not the desktop, and trimming this list
must not switch automation off by accident.

**** Why there are two accounts

GDM refuses to log root in, and ~ssh_user~ defaults to root.  So a VM
left at its defaults gets a second account -- ~clawt~ -- which owns the
graphical session, while commands the agent runs still arrive as root.
Both are created by cloud-init and both authorise the same key.  Set
~ssh_user~ to something other than root, or name
~vm.desktop.user~, and there is one account instead.

The key has to reach the session account: the MCP server talks to GNOME
Shell over the session bus of whoever is logged in at the screen, so it
is reached by an SSH connection *as that account*.

**** What is switched on, and why each one matters

Four things would each, on their own, leave the agent looking at a
desktop it cannot touch, and all four are handled in the seed:

- *the extension is enabled* through a dconf system default, because
  ~gnome-extensions enable~ needs a session that does not exist yet;
- *consent is pre-acknowledged*, because the extension opens a modal
  dialog on first enable and nobody is there to dismiss it -- it would
  sit in front of everything the agent tried to look at;
- *automation is switched on* by an autostart entry that calls
  ~SetEnabled~ over D-Bus, retrying, because the extension starts with it
  off and the only other way to flip it is a click on the top bar;
- *the lock screen is disabled*, because nothing in the guest can answer
  one -- screenshots would come back showing a lock screen and clicks
  would land nowhere.

The GNOME Shell extension is not avoidable.  GNOME on Wayland refuses
screenshots and input injection to every process outside the compositor,
so the only way in is code running *inside* GNOME Shell exposing a D-Bus
interface.  ~gnome-desktop-mcp~ is cloned rather than installed from
PyPI, because the extension only exists in the repository and the two
halves have to match: the server calls D-Bus methods that exact extension
has to export.

cloud-init acts on **first boot only**.  Changing ~vm.desktop.user~ or
turning the desktop on for a VM that has already booted means deleting
the overlay, not restarting.

**** Enabling an extension is not installing it

Enabling happens in dconf, before anyone logs in.  Installing means
putting the extension somewhere GNOME Shell looks -- and those are two
separate steps that fail independently.  A guest can have the extension
enabled by name and no extension on disk, which is exactly as broken as
having neither and looks like nothing at all from the host.

GNOME Shell searches ~gnome-shell/extensions~ under each ~XDG_DATA_DIRS~
entry, so clawtilla links the checkout into
=/usr/share/gnome-shell/extensions=.  Only Fedora's ~gnome-shell~ package
ships that directory; on Debian, Ubuntu and Arch it does not exist until
something creates it, and ~ln~ will not create a parent.  The installer
creates it, links the extension, and then tests *through* the link --
a dangling symlink enumerates as a symlink rather than as a directory,
which GNOME Shell skips in silence.

All of it is one script, =/usr/local/bin/clawtilla-desktop-install=,
rather than a list of ~runcmd~ entries.  cloud-init runs ~runcmd~ without
~set -e~: a command that fails is one line in a log inside the guest and
every later command runs anyway.  A script can stop at the step that
failed and say which one it was.

It writes the answer to =/var/lib/clawtilla/desktop-install.status=:

#+begin_src bash
clawtilla computer exec <agent-id> -- cat /var/lib/clawtilla/desktop-install.status
#+end_src

#+begin_example
ok
#+end_example

...or the step that stopped it:

#+begin_example
failed: could not create /usr/share/gnome-shell/extensions
#+end_example

That file is named in the agent's own description of its desktop, so an
agent whose tools return ~DBus object has no attribute~ is told to read
it rather than left to work the answer out from the bus.

The script is safe to run again, which the seed that first ran it is not:

#+begin_src bash
clawtilla computer exec <agent-id> -- /usr/local/bin/clawtilla-desktop-install
#+end_src

Running it does not by itself fix a running guest.  GNOME Shell scans for
extensions when the session starts, so one that arrives afterwards is not
picked up until the session restarts -- on Wayland that means logging out
and back in, which for an autologin guest is a reboot.

**** The guest needs a GPU, and gets one

A VM with no video device has no ~/dev/dri~, and GDM refuses to start a
session on a machine with no display -- while reporting nothing that
looks like the cause:

#+begin_example
Gdm: It appears that your system does not have a primary GPU!
#+end_example

Everything above that looks healthy.  cloud-init finishes, ~gdm.service~
is active, ~systemctl get-default~ says ~graphical.target~, and the
console sits on the boot log because with no video device the serial
console is the only console there is.

So every VM gets two devices, desktop or not:

- ~<video><model type='virtio'/></video>~ -- virtio because that is what
  a current GNOME on Wayland wants, and every cloud image has the driver.
- ~<graphics type='vnc' listen='127.0.0.1'/>~ -- so a person can look.
  The agent does not need it; it screenshots through the extension inside
  the guest. It is bound to loopback because a VM's screen is a live view
  of what the agent is doing, and that does not belong on the network
  because a default was convenient.

Given to headless VMs as well, deliberately.  A guest with no display
device offers only the serial console, which is the boot log for ever --
so somebody looking at it cannot tell a broken guest from a working
headless one, and on a guest that *does* have a desktop it looks exactly
like GNOME failing to start.  A framebuffer nobody reads costs a few
megabytes.

~virt-manager~ picks the graphical console when a domain has one.  A
domain first defined *without* one keeps the serial console it chose
then, per-VM -- so an older agent needs *View -> Consoles -> Graphical
Console* once, or its window closed and reopened.

**** How the tools reach the agent

The agent's ~.mcp.json~ gains a ~clawtilla-desktop~ server naming the
clawtilla CLI:

#+begin_src sh
clawtilla --socket <daemon.sock> computer desktop-mcp <agent-id>
#+end_src

It asks the daemon for the SSH command that reaches the guest, and relays
stdin and stdout to it.  SSH already carries stdio, so there is no
protocol translation -- but the relay is not a bare ~ssh~ entry, for two
reasons.

The first is the port.  It is chosen when the VM is provisioned, which is
*after* the workspace files are written, so a command line captured at
render time would name a port nothing is listening on.  The relay asks
each time it starts.

The second is the grant.  ~gnome-desktop-mcp~ offers every tool it has to
whoever connects; it has never heard of ~allow_input~.  A bare ssh entry
would hand an observe-only agent the ability to type and click.  So the
relay reads the JSON-RPC going past: it removes tools the agent may not
use from ~tools/list~, and answers a call to one of them with an error
rather than forwarding it.  A tool that is advertised and then refused is
worse than one that is absent -- the agent plans around it, calls it, and
has to work out from an error that it never had it.

~clawtilla-desktop~ is the second and last key clawtilla owns in that
file; everything else in it is read back and written out untouched.  It
is *removed* when the agent no longer has a guest desktop, because an
entry left behind would start an ssh to a VM that is not there.

*** Acting is a separate grant from seeing

*Launching a process is separate again.*  ~allow_spawn~ is off by default
and is not covered by ~allow_input~.  The compositor's ~spawn~ tool starts
a process through the compositor's own socket, so none of clawtilla's
confinement applies to it -- not the path checks, not the sudo block, and
not bwrap.  An operator who chose bwrap would not expect enabling desktop
input to hand back unrestricted process launching.

~allow_input: false~ is a genuinely useful middle ground: the agent can
see the screen and query the compositor but cannot click or type.  Seeing
and acting are separate capabilities and clawtilla does not conflate
them.

For the host backends, gowl needs to be built with ~MCP=1~ and have
~modules.mcp.enabled: true~, and the GNOME fallback needs
~gnome-desktop-mcp~ on ~PATH~.

** Adding a backend

Implement ~ClawtComputerProvider~ in a plugin: ~get_type_name~ returns the
~computer.type~ value you answer to, ~create~ builds the computer.  See

provider makes that one agent a shadow rather than failing the daemon.
